# ADR-018：编辑租约

> 状态：已接受｜日期：2026-10-04｜来源：M3-P1（`docs/v0.1/M3-编辑权与保存协议/01-P1-编辑租约.md`）｜依据：00 号计划书 §6.2–§6.4（r13）、M3 总设计 §2.1、§6.1、§6.4

## 背景

- A04（编辑唯一性）、A05（过期旧会话）、A06（撤权一致性）、A07（确认丢失）在 M3 首次验证：同一时刻只有一个人、一个标签页能写一份文档；失效的会话、失去编辑权的人写不进来；而且由数据库保证，不靠前端按钮变灰（计划书 §6.4）。
- M1、M2 的保存只按修订号条件写入（ADR-011）：两个标签页可以同时编辑，后保存的一方得到版本冲突；进行中的保存与撤权（归档、移出、降级）不互斥，撤权提交之后还可能有一个保存提交（M2-P2 审查 A3，ADR-014）。
- M2 已经在文档行上放了写入代次 `write_epoch`（删除、跨空间移动、转移时加一），并留下"收回写入权"的入口 `WriteAccessRevocation`（五种范围，实现为空）。

## 决策

### 数据

`document_edit_leases`（迁移 0022），每份文档至多一行，新的申请改写这一行：持有者、绑定的登录会话与标签页（`client_instance_id`）、令牌的 SHA-256 摘要、这一代的代次、申请 / 续租 / 到期 / 最后活动的时间、明确结束的时间与原因（`released`、`revoked`）。时间一律是数据库的 `now()`；有效期 90 秒、心跳 10 秒、空闲 12 分钟兜底回收（contracts 的常量）。

### 有效条件（纯函数，按顺序，第一条不满足的就是失效的原因）

1 有这一行（`none`）→ 2 没有明确结束（`released`、`revoked`）→ 3 代次等于文档当前的代次（`stale`）→ 4 没有到期（`expired`）→ 5 没有空闲超时（`idle`）→ 6 绑定的登录仍然有效（`session`）→ 7 持有者仍能编辑（`revoked`）。

- 6、7 两条要查数据库，前五条都满足才查；持有者自己的请求（心跳、保存）把第 6 条换成"请求的登录、标签页就是租约绑定的"，令牌对不上是 `replaced`。
- 失去访问（404）与失去编辑权（403）先于租约判断：客户端据此区分"还读得到"与"读不到"（M3 总设计 §2.1 第 4 条），不另设原因。心跳判断出失效时，先再判断一次能否编辑，再回答租约的原因（审查 A2：心跳在等租约行时遇上降级、移出，回答的是 403/404 而不是 `revoked`）。
- **持有者自己的请求（保存、心跳、申请）在事务里另核对这次登录现在仍然有效**（审查 A1）：会话守卫之后还隔着上传正文（最长到请求时限）与等锁，这期间退出、签发重置、修改密码都不经文档行，挡不住已经过了守卫的请求；所以按主键再查一次会话，失效时回 401 `SESSION_EXPIRED`（不动 Cookie，与 ADR-017 读快照的开场核对同一个说法）。位置：保存在文档行的锁下、重放之后、能否编辑与租约之前；心跳在锁住租约行之后；申请在锁住文档行与租约行之后（撤销登录之后才到的在途申请不再写下绑定失效登录的租约）。
- 每次申请产生新的一代：文档的 `write_epoch` 加一（不动 `updated_at`），租约记下它。删除、跨空间移动、转移给代次加一，这一代随即 `stale`。

### 接口

- `GET/POST/PUT/DELETE /api/documents/{id}/edit-lease`（workspace 编排，补持有者的人名）：编辑状态（读快照，ADR-017）、申请（被别人持有时 409 `EDIT_LEASE_HELD`，带持有者、最后活动时间、是不是自己；成功时另带文档当前修订的来源 `source`——产生它的那次保存的标签页与本地序号，与冲突详情同形，页面续上时据此认出本页自己一次结果未知的保存，计划书 §7.5，审查 B1）、心跳续租（失效时 409 `EDIT_LEASE_LOST`，带原因）、释放（令牌是当前这一行的、调用者就是持有者才结束，一律 204；不要求同一个登录：换了登录之后续上要先释放自己那一代，审查 A4）。
- 令牌：32 字节安全随机数，只在申请的响应里出现一次；库里只存摘要，比较用恒定时间；经请求头 `X-Edit-Lease` 传递，不进地址与日志。
- 保存（ADR-011 的顺序）：重放先于租约（已经提交的同一次保存，之后不论租约怎样，重试都拿到原来的结果）；不是重放才要求能编辑，再要求令牌、代次（查询参数 `writeEpoch`）、登录与标签页都对得上，之后才核对 `unitId` 与基准修订号。保存在文档行的锁下不加锁读租约行：能改写它的申请与收回写入权都要先拿文档行的锁。

### 收回写入权接上租约（`LeaseWriteAccessRevocation`）

在调用方改动权限的事务里：按范围（与 `coversWriter` 同义）找出没有明确结束的租约，**按文档 id 的顺序锁文档行**，再锁租约行并复核范围；逐个判断持有者还能不能编辑，不能了的一条语句记 `revoked`、一条语句给这些文档的代次加一，仍能编辑的不动（跨空间移动、转移之后在新空间里仍能编辑的持有者：调用方已经给代次加了一，他的租约按 `stale` 失效）。

"还能不能编辑"：
- 停用账户（`user` 范围）一律不能：访问策略只看空间角色与授权、不看账户状态（停用的人每个请求都被会话守卫拦下），按策略他仍是编辑者；而停用之前已经过了守卫、正在等文档行的那次保存，锁下的权限判断照样通过，能挡住它的只有已经结束的租约。
- 回收站里的文档谁也不能编辑：删除时租约记 `revoked`（代次在删除本身加的一之上再加一），有明确结束的记录。
- 其余按变化之后的权限（访问策略在同一个事务里查，看得到调用方刚做的改动）：`canEditDocument`，与有效条件第 7 条共用。

这收口了"进行中的保存与撤权不互斥"：保存在租约这一步之前锁住了文档行，撤权要给持有者的文档加代次，必须先拿到同一把锁，所以两者必有先后——保存先提交，或者撤权先提交、保存在锁下看到新的权限与代次而被拒绝。申请与撤权交错（申请在撤权提交之前判断了权限、之后才提交）留下的租约，由第 7 条在每次使用时让它失效。

### 锁的顺序

锁顺序表在"文档行"之后加"租约行"：申请与收回写入权先锁文档行、再锁租约行；心跳与释放只锁租约行（锁住之后再读文档的代次）。

### 登录与编辑权

租约绑定登录：退出、修改密码（换令牌）、签发重置链接、停用账户都会让它失效（第 6 条）。系统管理员的"强制结束编辑"没有单独的界面，由签发重置链接或停用账户承担（两者都撤销这个人的全部登录，M3 总设计 §2.1 的细化，P1 核实：现有的管理操作里没有单独的"撤销全部登录"）。

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| A. 租约放在 documents，接口在 workspace | 采用 | 保存核对租约是保存事务里、文档行锁下的条件；按空间撤权要把租约与文档连查并锁文档行；都在 documents |
| B. 新建 editing 模块，documents 定义入口、editing 运行时登记实现 | 否决（M3 总设计 §6.7 的原方案，P1 设计 §3.1 改） | 漏了登记只能在运行时发现，处理不好就是保存绕过租约；按空间撤权要跨模块联表或冗余空间 id |
| C. 租约放在进程内存（或 Redis） | 否决 | 计划书 §6.2、§9.3：状态放 PG，不以进程内的变量为准，首发不引入 Redis |
| D. 保存续租 | 否决 | 续租只靠心跳：保存不改写租约行，也就不必为它加锁 |
| E. 撤权只靠每次使用时判断（第 7 条），不加代次 | 否决 | 撤权不锁文档行，进行中的保存可以在撤权提交之后提交（M2-P2 审查 A3 的情形） |
| F. 心跳也锁文档行 | 否决 | 不必要：改写租约的一方都会改写租约行，按租约行串行即可，心跳更轻 |

## 影响

- 新错误码 `EDIT_LEASE_HELD`、`EDIT_LEASE_LOST`（ADR-006）；`edit` 的说明改为"只能查看这份文档，不能编辑"（保存与申请共用）。
- documents 引入 auth（`SessionService.isActive`），依赖图仍无环。
- 集成测试发保存之前要先申请（测试辅助）；新的 GET 接口在读快照的请求表里；新接口进"看不到 / 不存在"的探测与权限矩阵；不变量"租约的代次不大于文档的代次"。
- 编辑器页（P1 的最小接入，`features/sheet-editor/edit-lease.ts`）：能编辑时打开就申请（被占用而且是自己时隔 500 毫秒再试，最多 3 次，覆盖刷新时旧页面的释放晚到；结果未知时用同一个标签页再试一次，服务端把同一个页面的重试当作新的一代），被占用时只读并说明持有者；每 10 秒续租，带上本页多久没有键盘、鼠标操作；保存带令牌与代次；会话不是本人时暂停续租；`pagehide` 时尽力释放。
- **续上**（M3 总设计 §2.1 的细化，原定 P2，P1 提前：租约绑定登录之后，重新登录会让编辑权失效，不续上的话 US-M1-05"登录回来之后照样能保存"就会倒退）：失效的原因不是失去访问或编辑权（403、404、`revoked`）时，先释放本页手里那一代（同一个人经别处重新登录、旧登录还活着时，旧租约在服务端仍然有效），再申请一次；申请到、而且修订号等于本页保存的基准（服务端确认过的最新修订，期间没人保存过）才换上新的一代、接着编辑，用户不受打扰；修订号变了时，先看申请响应里当前修订的来源：是本页一次结果未知的保存，就按保存状态机认出"自己追自己"的同一条规则确认那次捕获、接着编辑（审查 B1）；否则才是别处保存过，释放刚申请到的、按失效处理（不覆盖）；被占用按失效处理。每一代至多续上一次；本页空闲不短于服务端的回收阈值时不立即续、等下一次操作（否则人不在时页面自己续上，空闲回收形同虚设，审查 B8）；续上前的释放结果未知时不申请、下一次心跳再判断（否则会把本页自己的旧租约说成"另一个标签页"，审查 B9）。
- **失效的界面统一**：续租与保存得到 `EDIT_LEASE_LOST`、403、404 一样转为失效，页头说明原因（404：已无法访问；403：已没有编辑权限，附服务端的原因），确实有未保存的修改时说明没有保存；心跳先发现还是保存先发现，界面相同。
- 已知的局限（登记在延期登记）：载入途中离开会留下拿不到令牌的租约，重开的页面最长 90 秒只能阅读（DEF-042，P5 的本人接管解决）；心跳会顺延登录的空闲过期——P1 有上限（人不在时续租停止），P2 阅读页的定时检查没有上限，要一起定（DEF-043）；失去访问或编辑权时不再申请，拿不到当前修订的来源，本页有一次其实已经提交的保存时说明偏保守地说"没有保存"（P2 的另存为副本一并处理）。
- 部署：反向代理的访问日志（如果开）不记 `Cookie`、`X-CSRF-Token` 与 `X-Edit-Lease`（`deploy/README.md`，审查 A4 的建议）。
- 以后：P2 的续上与另存为副本、阅读页的更新提示（后台请求不顺延登录）；P5 的请求编辑、本人接管（Web Locks）、强制接管与异常中断的提示，在本 ADR 上补充。
