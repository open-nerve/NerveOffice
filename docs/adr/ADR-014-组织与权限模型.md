# ADR-014：组织与权限模型（有效权限、单一入口、可访问文档）

> 状态：已接受｜日期：2026-09-29｜来源：M2-P2｜修订：2026-10-07，M3-P5：强制接管的权限位与操作、收回写入权只锁按时间还活着的租约（见文末）；2026-10-04，M3-P2：另存为副本的权限、位置与锁（见文末）；2026-10-01，M2-P6 第 2 片复核：团队空间的名称按判重键判重；复制在锁下对源文档重新判断；搜索的范围检查改为不变量；转移经收回写入权的入口；不判断权限的永久删除只在 documents 内部；"看不到与不存在执行同样的查询"有了覆盖全部 404 路径的语句序列核对；全员可见对系统管理员同样生效（需求方确认）；2026-10-02，M2-P5：单独授权并进有效权限（空间角色与内容权限分开带，结构性的操作只看空间角色）、"可访问文档"的两半、分享写入的锁、收回写入权的 `userDocuments`、个人空间存的名称不对别人给出；2026-10-03，M2 Codex 评审 CX1：在途的读请求在只读快照里判断权限与读数据（ADR-017）；2026-10-04，M3-P1：收回写入权接入编辑租约，锁的顺序在文档行之后加租约行（ADR-018）

## 背景

- 00 号计划书 §5 定义了组织、空间与权限：个人空间与团队空间，空间角色（空间管理员、编辑者、查看者），单独授权；有效权限取空间角色与单独授权中较高的一个；全员可见的空间里有效账户都是查看者；归档的空间里所有人至多是查看者；系统管理员默认没有内容权限，要看团队空间的内容先把自己加入（记审计），个人空间对他始终不可见——例外是所有者或空间管理员把一份文档单独分享给他（需求方 2026-10-02 确认，00 号计划书 r12：靠对方的主动分享、记审计，不靠系统角色，与全员可见对系统管理员同样生效同一个思路）；看不到的一律当作不存在（§5.5）。
- M2 总设计 §6.1 的实现约束：权限只经一个入口计算，目标是文档或空间；"可访问文档"由一个查询给出；无权与不存在一律 `NOT_FOUND`，耗时对齐。§2.1 第 8 条：文档行上的 `writeEpoch` 与"收回写入权"的入口，M3 在入口里接入租约。
- M1 的访问策略 `DocumentAccessPolicy` 只有"文档在本人的个人空间"一条规则，目标只有空间 id。
- P2 设计时发现：users、auth、documents 都依赖 spaces，空间管理员用的成员管理（要用到当前登录的人、同事的名字与状态、有效权限、收回写入权）放不进 spaces。需求方确认新增 workspace 模块（P2 设计 §3.1、§7，M2 总设计 §6.2 的补充）。

## 决策

**模块分层**：

```text
admin ─────────► documents、spaces、users、auth、audit   系统管理：团队空间的创建、全员可见、归档与恢复；停用；停用者文档的转移
workspace ─────► documents、spaces、users、auth、audit   面向成员的空间接口：我能看到的空间、空间页头、成员、改名
documents ─────► spaces、auth、audit                     文档；有效权限（唯一入口）与"可访问文档"；writeEpoch 与收回写入权
auth、users ───► spaces
spaces                                                   空间与成员的数据与不变量；没有控制器，不判断谁能做什么
```

**有效权限的唯一入口**：documents 的 `DocumentAccessPolicy`（实现 `EffectiveAccessPolicy`），目标是文档或空间：
- 事实由 spaces 给出：空间行左连接这个人的成员行，一条语句（`accessFactsOf`）；"我能看到的空间"的候选（`visibleSpacesOf`）只是候选，看不看得到仍按规则算。
- 规则是纯函数（`access-rules.ts`），不查询：
  - 个人空间：所有者是空间管理员；其他人（包括系统管理员）没有角色；个人空间的成员行一概不计。
  - 团队空间：成员的角色；全员可见时至少是查看者；归档时至多是查看者。
  - 操作规则（`spacePermissionsOf`）：新建要编辑者及以上；查看成员要有空间角色；管理成员与改名要空间管理员（归档之后没有）；系统角色只带来团队空间的管理面（查看与管理成员、改名），不带来任何内容权限。
- 同一套规则既给界面（`SpaceView.permissions`，界面只显示能做的操作），也给服务端的检查（`requireSpaceContent`、`requireSpaceManagement`）。服务不自己拼权限条件。
- **看不到与不存在执行同样的查询**：由集成测试按语句序列核对（M2-P6 复核之后，`permissions/hidden-missing-parity.test.ts`，M2-P5 之后 108 个探测（路径里带 id 的接口 34 个：探测覆盖 25 个、只给系统管理员的 9 个写明豁免；含"只凭授权的人"对所在空间的空间级接口与分享的接口）：状态、错误体、非易变的响应头与应用发出的 SQL 语句序列都相同；路径里带 id 的接口与应用的路由表对照，要么在探测里、要么写明豁免——只给系统管理员的 9 个，第 6 片复核起）。此前说的"单元测试核对查询序列"只覆盖了两个入口，文件夹与删除单元的路径没有核对。权限矩阵的 404 格与"不存在"的基准比较完整的错误体与响应头，列表类格子断言"恰好是这几条"。
- **复制在锁下对源文档重新判断**（M2-P6 复核）：目标空间的树锁 → 源空间与目标空间的空间行（`FOR SHARE`，按 id）→ 源文档行（`FOR SHARE`），锁下重新读源文档、重新判断读权限。原来源文档只在不加锁时判断一次，已被移出空间的人能复制出移出之后才写进去的内容。
- **搜索的范围检查是不变量**：结果里出现"我能看到的空间"之外的行即报错，不再静默丢掉（静默丢掉会掩盖"可访问文档"条件的回归，下一页的游标还会外泄）。
- **全员可见对系统管理员同样生效**（需求方 2026-10-01 确认）：见"备选方案与取舍"。
- **写入代次只增不减由触发器兜底**（M2-P6 复核，迁移 0019）：更新 `documents.write_epoch` 时新值小于旧值就拒绝；M3 的"撤权提交之后的保存必定被拒绝"依赖它，原来只靠服务的写法。
- **空间树锁与它保护的三类行**（M2-P6 复核订正）：结构性改动先取空间树锁（按空间 id），再取空间行（`FOR SHARE`），之后文档行、删除单元行、文件夹行的先后因操作而异（删除文件夹、恢复、永久删除是"文档行 → 删除单元行 → 文件夹行"，与原来写的"文件夹行 → 文档行 → 删除单元行"相反；永久删除文件夹单元的完整顺序是"这一单的文档行 → 删除单元行 → 子树里别的单元的文档行 → 文件夹行 → 连带的删除单元行"）。建到根目录的新文档不取树锁；保存、新建文档、复制与另存为副本的第一把锁是按 `requestId` 的 advisory lock（另存为副本自 M3-P2、保存自 M3-P3 审查 A3 起；每个事务至多一把，`RequestLedger`）；新建文件夹不取它（第一把锁是树锁，幂等靠 `request_id` 的唯一约束与 `ON CONFLICT DO NOTHING`）。不会成环，靠的是一条不变量：文件夹行与删除单元行只被持有它所在空间树锁的事务改动，所以这三类行在同一棵树里谁先谁后无关紧要；不持树锁却会锁文档行的只有保存、转移与复制的源文档，它们只碰正常状态的文档、一次锁完。**转移是唯一不取树锁的跨空间操作**：只搬来源空间里正常状态的文档、落在目标空间的根目录，不动文件夹与删除单元，所以安全。
- **单独授权**（M2-P5）：对一份文档的访问分开带三项——空间角色（结构性的操作只看它）、内容权限（空间角色与授权取较高者，授权最高只到编辑者）、访问途径（没有空间角色、只凭授权时是 `grant`），只在 `access-rules.ts` 的 `documentAccessOf` 一处合起来：先取较高者，再按归档降到查看者（被单独授权为编辑者的人在归档的空间里同样只是查看者）。只凭授权的人能读、按授权的角色保存与改名、能复制；不能移动、不能删除、不能分享（403，说明是"这份文档是单独分享给你的，不能……"），看不到所在的文件夹与空间的目录结构（文档详情只在 `toDetail` 一处去掉文件夹）。`spaceAccessOf`（空间页、按空间列出、文件夹、回收站）不看授权：授权不给空间里的任何东西开口子。

**看不到与不存在一致**：
- 看不到（不存在、没有角色、没有加入的系统管理员看内容、系统管理员看个人空间）一律 404 `NOT_FOUND`，说明相同；看得到却不能做是 403 `PERMISSION_DENIED`（ADR-006）。
- 两条路径执行同样的查询：空间事实是一条语句，不存在时照样执行；文档不存在时用全零的空间再算一次（沿用 M1）。核对的方式见上面"看不到与不存在执行同样的查询"一条（M2-P6 之后由集成测试按语句序列核对全部 404 路径；原来这里写的"单元测试核对查询序列"只覆盖了两个入口）。
- 需要锁的操作一律"先判断（不加锁）→ 加锁 → 锁下再判断"：看不到的请求不在空间行上取锁（ADR-011 的做法）。系统管理的接口同样如此：个人空间的 id 先按不存在拒绝，不锁它的行（包括转移的目标写成团队空间的个人空间，复验 N1）；转移只锁来源空间里的文档，请求里夹带的别处的文档不被锁住（M2-P2 审查 A4）。

**请求里的 id**：契约里的请求结构用统一的 `uuidSchema`，大小写都接受、转成小写。数据库按 uuid 比较不分大小写，服务端的代码却按字符串比较（是不是本人、按 id 找条目、审计的明细、收回写入权的范围）：在边界上统一，服务端只见到小写。否则系统管理员用大写的自己的 id 加入空间，审计会记成普通的添加成员（M2-P2 审查 A1）。lint 守护：契约的请求结构（`z.strictObject`）与路径里的 id（`*IdSchema`）不直接用 `z.uuid()`；服务端判断"是不是本人"、写审计的明细与收回写入权的范围，用数据库返回的 id（复验 N3）。

**可访问文档**：documents 的仓储里只有一处拼条件（`accessible(scope)`：正常状态，且在给定的空间里或者这个人有单独授权），范围由访问策略给出。M2-P5 起范围有两半，调用方写明要哪几半：按空间列出、转移只要空间那一半，搜索两半都要（"凭授权命中"由搜索的同一条语句给出），"与我共享"只要授权那一半——这时条件只剩授权的 EXISTS，由 `document_grants(user_id)` 驱动（集成测试按 EXPLAIN 核对，原来带着恒假的空间条件会扫整张文档表）。列表、搜索、计数、"与我共享"都经它；P4 排除回收站、P5 并上授权也只改这里。不在 SQL 里跨模块联表（仓储只用本模块的表，规范 §1.2）：约 100 人的规模下，一个人看得到的空间只有几个到几十个，按 id 集合过滤足够，M7 压测时复核。

**空间与成员的锁**（ADR-007 的补充延伸到空间与文档）：
- 全局顺序：system-admins 的 advisory lock → 按登录名的 advisory lock → 账户行（多行按 id）→ 重置或邀请行 → 限流计数 → 会话行 → 空间树的 advisory lock（M2-P4，按空间 id）→ 空间行（多行按 id）→ 成员行 → 文件夹行、文档行、回收站行（M2-P4；这三类行的先后因操作而异，不成环靠"文件夹行与回收站行只被持有所在空间树锁的事务改动"，见上文"空间树锁与它保护的三类行"）→ 审计。保存、新建文档、复制与另存为副本按 `requestId` 的 advisory lock 排在最前（另存为副本自 M3-P2、保存自 M3-P3 审查 A3 起；每个事务至多一把，`RequestLedger`；新建文件夹不取它，第一把锁是树锁，幂等靠 `request_id` 的唯一约束）（M2-P6 复核订正：原来停在 P2）。
- 改动空间与成员（改名、全员可见、归档与恢复、成员的添加、调整、移出）对空间行取 `FOR NO KEY UPDATE`；在空间里新建文档、转移的来源与目标取 `FOR SHARE`：归档、移出提交之后的新建一定被拒绝，进行中的新建先提交、归档再生效。
- 添加成员、首个空间管理员、转移的目标账户以 `FOR SHARE` 持住：到提交之前不会被停用。
- 空间的管理操作要用到系统角色时，事务第一步取 system-admins 的共享锁复核（`holdSystemAdmin`）：复核发现已被取消，就按普通成员判断，而不是拒绝（他可能同时是空间管理员）。
- "至少保留一个空间管理员"（409 `LAST_SPACE_ADMIN`）在空间行的锁下数成员行，不看账户状态：两个空间管理员同时降低自己，只有一个成功。
- **分享的写入**（M2-P5，由 workspace 编排，documents 不依赖 users）：不加锁判断（看不到 404，与不存在相同；不能分享 403，归档时给恢复之后能分享的人冻结的说明、其余的人通常的说明；给自己 400）→ 设置时持住被授权人的账户行（`FOR SHARE`，不存在或停用 409；取消不锁，停用的人的授权也能取消）→ 空间行（`FOR SHARE`）→ 文档行（`FOR UPDATE`）并在锁下核对文档仍在持住的空间、空间没归档、自己仍能分享 → 读写授权、收回写入权 → 审计 → 同一事务里补人名、拼响应。不取空间树的锁。文档行取 `FOR UPDATE` 是复制与保存"在锁下重新判断授权"的前提（它们对文档行取 `FOR SHARE` / `FOR UPDATE`）：取消提交之后的复制与保存一定看到取消。每把锁都有确定交错的用例（`documents/sharing-locks.test.ts`）。

**`writeEpoch` 与收回写入权**：
- `documents.write_epoch` 默认 0，删除与跨空间移动（本 Phase 只有转移）在同一个事务里加一；M3 的租约与保存按"代次与修订号都匹配"写入。
- 入口 `WriteAccessRevocation.revoke(scope, transaction)`，范围：某人（停用）、某人在某个空间（移出、调整角色）、整个空间（归档）、这些文档上的所有人（删除、跨空间移动、转移），M2-P5 加 `userDocuments`（某人在这些文档上：取消授权、编辑者降为查看者；不能用"这些文档上的所有人"代替，M3 接租约之后会把正在编辑的别人一起踢掉）。五种范围的含义写成纯函数 `coversWriter` 作为规格，M3 的租约照它实现。调用方在改动权限的同一个事务里调用，不自己判断谁失去了写入权。
- M2 没有租约，实现为空：权限的变化与调用一起提交，下一次请求重新判断权限即被拒绝（保存在锁下再判断，ADR-011）。M3 换成接入租约的实现，调用方不改（M3-P1 已换，见文末的补充与 ADR-018）。
- **在途的读请求**（M2 Codex 评审 CX1，ADR-017）：登录之后的读请求在一个只读快照里判断权限、读数据，会话守卫判断过的账户有效与系统角色在快照里再查一次。撤权之前开始的读请求返回撤权之前那一刻的数据或被拒绝，不会带出撤权之后才写进去的数据。

**停用者文档的转移**：系统管理员的操作，不经内容权限——授权是系统角色（锁里复核），而且不读内容：标题列表只给标题、类型与更新时间；转移只改所属空间与代次（`updated_at` 不变），整批拒绝（`TRANSFER_CONFLICT`），每份文档一条审计（来源与目标空间，不记标题）。只对停用的账户（`ACCOUNT_NOT_DISABLED`）。目标不能是操作者自己的个人空间（403）：转给自己就等于打开了内容；转到他自己是成员的团队空间是允许的，与把自己加入团队空间一样有审计（M2-P2 审查 A7）。

**团队空间的名称**：按**判重键**唯一（已归档的也算），由唯一索引兜住并发。判重键是数据库的生成列 `name_key`（M2-P6 复核，迁移 0016）：NFKC → 去掉名称里放行的格式字符（零宽连接符与不连字、变体选择符、组合用字形连接符、蒙古文变体选择符与元音分隔符、标签字符）→ 空白连续段合成一个空格并去首尾 → 小写 → 大小写折叠 → 再 NFKC；只有这一个来源，服务不自己判重。原来的 `lower(name)` 挡不住看起来一样的名称（夹着看不见的字符、全角与半角、连续空格），导航里同名的空间无法区分，系统管理员转移停用者的文档时可能转进外观相同、由别人管理的空间。迁移遇到已有的冲突时中止并列出冲突的空间。键按当前 PostgreSQL 的 Unicode 表算好存下，大版本升级之后要重算（DEF-031）。名称的入口另把每一段空白（一个或连续几个）只存成一个字符：第一个是普通空格、不换行空格或全角空格时保留它（日文姓名的全角空格、法文的不换行空格），否则换成普通空格（发丝空格、细空格、窄不换行空格等窄的空白夹在字中间与不夹看起来几乎一样）；两个蒙古文字母之间单独的窄不换行空格原样保留（传统蒙古文的后缀连接）。"有没有空白"算区别，"空白的种类与个数"不算：算作空白的字符只有一份清单（contracts 的 `NAME_BLANK_CHARACTERS`），判重键与按名称搜索（同事目录、团队空间的列表，名称与关键词两边都归一）共用它。判重键不认第 1 片之前入口放行、现在拒绝的零宽空格、软连字符、双向控制字符等：只影响跑过第 1 片之前 M2 构建的库（M2 没有部署，只有开发库），迁移 0017 的注释写明了这个边界。手写的迁移与表定义是否一致由集成测试核对（库里反解析出来的表达式与按表定义新建的临时列逐字相同），`gate schema` 只比较表定义与快照。并拒绝显示成空白的非格式字符（盲文空白 U+2800、契丹小字填充符 U+16FE4、乐谱的空符头 U+1D159：不是空白、也不是默认可忽略字符，标准字形却是空的；只由它们组成的标题同样拒绝），判重键也把它们当空白（迁移 0017 用 `SET EXPRESSION` 改生成列的表达式、整表重算，已有冲突时中止并列出，M2-P6 复验 R-M1）。**判重的取舍**：判得偏严——国旗的标签字符、零宽连接符组合的表情、波斯文的零宽不连字、兼容写法（① 与 1、㍿ 与株式会社）都会判成重名，只是要换个名字；判得偏宽会让人认错空间。**不处理**跨文字的同形字（拉丁 a 与西里尔 а、拉丁 O 与希腊 Ο）：要按 UTS #39 的同形字数据判定，登记为 DEF-032（M7 的安全审查）。此外，创建与改名的语句放进保存点（`inSavepoint`），撞上唯一约束时只回滚到保存点，仓储返回"名称已被使用"、事务仍可继续，服务转成 409 `SPACE_NAME_TAKEN`（集成测试经探针在一个事务里撞名之后再改一次）。代价是撞名会透露一个看不到的同名空间存在：名称唯一是为了导航里可以区分，约 100 人的组织里团队空间的名称不是秘密，接受（M2-P2 审查 A8）。

## 备选方案与取舍

- **有效权限放在 spaces**：spaces 能直接判断成员管理的权限，但文档的单独授权在 documents（M2 总设计 §6.2），documents 又要用空间的部分，两处各算一半，违背"只经一个入口"。保留在 documents，空间的部分只提供事实。
- **一条 SQL 算出可访问文档（联表或视图）**：documents 的仓储要引用 spaces 的表，或者引入跨模块的视图（要另外确认应用角色的权限，ADR-012）。按 id 集合过滤在当前规模下足够，边界清楚。
- **成员管理的接口放进 documents 或 admin**（不新增模块）：documents 已要装文档、文件夹、回收站、复制、分享、搜索与权限；admin 的约定是"全部接口只给系统管理员"，混进空间管理员的接口容易在授权上出错。需求方选定新增 workspace。
- **转移不经收回写入权**（P2 的做法）：M2-P6 复核发现它与"调用方都已接上"的说法不符，转移是跨空间搬文档，现在同一事务里调用 `revoke({kind:'documents'})`。
- **收回写入权在 M2 先不接**：调用方到 M3 再改，要重新审每个撤权的事务；现在接好空的入口，M3 只换实现。
- **系统管理员不享受全员可见带来的查看者身份**（M2-P6 S2 复核提出，2026-10-01 需求方否决）：这样"要看内容必须先加入、记审计"没有例外，但管理员作为普通员工反而看不到公司公告这类全员可见的空间。采用的做法：全员可见对所有有效账户（包括系统管理员）都生效；打开全员可见本身记审计（`spaces.visibility_changed`）、对全员可见，不是悄悄的；确认框写明"包括你自己"。
- **行级安全（PostgreSQL 的 RLS）**（M2-P6 第 6 片复核补列）：把"看得到哪些文档"写成数据库的策略，漏写条件的查询也越不了权。M2 不用：界面要的操作权限（`permissions`）仍要应用来算，规则就得在 SQL 与应用里各写一份；每个请求都要在借到的连接上设置当前用户（与连接池、事务运行器的借还耦合，漏设时整条请求的语义都变了）；"看不到与不存在执行同样的查询"的核对也更难做。作为纵深防御，M7 的安全审查时再评估。
- **spaces 给出"可访问空间"的子查询片段**（M2-P6 第 6 片复核补列）：documents 的条件里直接嵌 spaces 提供的 SQL 片段，一条语句完成、不用先取空间的 id 集合。不用：仓储只用本模块的表（规范 §1.2），片段会把 documents 的语句与 spaces 的表结构绑在一起；按 id 集合过滤在本版规模下足够，规模的复核见 DEF-026。
- **名称唯一靠 advisory lock 与先查后写**（P1 对登录名的做法）：登录名要跨账户与邀请两张表唯一，只能这样；团队空间的名称在一张表里，唯一索引更直接，保存点把"预期会失败的语句"与事务隔开（TransactionRunner 的约定）。

## 影响

- P3：编辑器身份的授权服务按文档的有效角色回答（`DocumentDetail.permissions` 已按有效角色给出）。
- P4：文件夹、移动、复制、回收站、搜索都经 `DocumentAccessPolicy` 与"可访问文档"的条件；跨空间移动在事务里递增 `write_epoch`；空间内移动不递增。
- P5（已实现）：单独授权并进 `EffectiveAccessPolicy`；取消或降低授权经收回写入权的入口；"与我共享"经"可访问文档"的条件；权限矩阵 8 个角色（加"只有查看授权""只有编辑授权"），2666 格。个人空间存的名称（所有者建号时的显示名，可伪造，规范 §2.4）不对别人给出：搜索结果与"与我共享"给所有者（契约 `spaceIdentitySchema`），文档详情里个人空间只给 id 与类型；只给本人看的地方（会话信息、空间接口里本人的个人空间）保留。
- M3：收回写入权的入口接入租约；保存按代次条件写入。注意删除与跨空间移动已经在仓储里给 `write_epoch` 加一，M3 的收回写入权如果也加，同一次操作会加两次（不出错，代次只要求单调，但设计时要知道，M2-P6 第 6 片复核）。M2 里进行中的保存与归档、移出、降级不互斥（保存只锁文档行，这些操作只锁空间行；M2-P2 审查 A3），M3 由撤权终止租约与按代次条件写入收口。
- 新的空间接口放在 workspace，系统管理员的放在 admin；spaces 保持没有控制器、不依赖 users、auth、documents（lint 的 `import-x/no-cycle` 与 Nest 的模块装配强制）。admin 与 workspace 是最上层的编排，只由 app 层组装，别的模块不引用它们（lint 的模块边界强制）：绕过内容权限的转移只由 admin 引用，也不会经 admin 转手流到别的模块。

## M3-P1 的补充：收回写入权接入编辑租约（ADR-018）

- `LeaseWriteAccessRevocation` 取代 M2 的空实现，调用方不改：在改动权限的事务里，按范围（与 `coversWriter` 同义）找出没有明确结束的租约，**按文档 id 的顺序锁文档行**、再锁租约行并在锁下复核范围；持有者不能再编辑的，一条语句把租约记 `revoked`、一条语句给这些文档的代次加一；仍能编辑的不动。停用账户（`user` 范围）一律结束（访问策略不看账户状态）；回收站里的文档谁也不能编辑。删除、跨空间移动、转移本来就给代次加一，收回写入权再加一次，代次只要求单调。
- **锁的顺序**：在"文件夹行、文档行、回收站行"之后加"租约行"。申请编辑权与收回写入权先锁文档行、再锁租约行；心跳与释放只锁租约行。
- **M2-P2 审查 A3 的窗口收口**：保存在租约这一步之前锁住了文档行；撤权要给持有者的文档加代次，必须先拿到同一把锁，所以保存要么先提交、撤权之后生效，要么在锁下看到新的权限与代次而被拒绝。"撤权提交之后的保存必定被拒绝"由数据库保证（`team-spaces.test.ts` 原来钉住"保存照样提交"的那条用例改为确定交错，`lease-revocation-locks.test.ts`）。M3-P5 起撤权不收回按时间已死的租约，但刚死不久的照样锁文档行，这条保证不变（见下文）。
- 申请与撤权交错（申请在撤权提交之前判断了权限、之后才提交）留下的租约，由有效条件的第 7 条（持有者仍能编辑）在每次使用时让它失效；停用另由第 6 条与锁下对登录的再核对挡住。

## M3-P2 的补充：另存为副本的权限、位置与锁

失去编辑权、还读得到原文档的人，把本页的内容存成一份新文档（00 号计划书 §7.5；内容与幂等见 ADR-011 的补充）。

- **只要求能读原文档**：读不到 404，与不存在执行同样的语句。失去编辑权、还读得到的人（被降为查看者、空间被归档、只凭授权而授权被降级）正是要用它的人；内容本来就能读、能复制（M2 起查看者就能复制到自己的个人空间），所以不构成绕过"不能编辑"。
- **放在哪里**（不由请求决定）：本人在原文档所在的空间能新建（与新建文档同一条规则，`creatableSpace`）→ 原文档现在所在的文件夹（文件夹不在了放空间的根目录，在一致的数据里走不到，是防御）；否则本人个人空间的根目录。不继承原文档的单独授权（与复制相同：授权只给原文档）。
- **锁**（与复制同一套顺序）：`requestId` 的 advisory lock → 原文档所在空间的树锁（只在要放进那个空间时取：看不到目录结构的人不在别人的空间树上排队）→ 原文档所在空间与本人个人空间的空间行（`FOR SHARE`，按 id）→ 原文档行（`FOR SHARE`）。锁下重新判断能读、重新决定位置：取锁之前能新建、锁下不能了（降为查看者、归档、移出先提交）→ 个人空间；取锁之前不能、锁下才能了 → 照旧个人空间（那个空间的树锁没有取，放进它的文件夹不安全，"放进个人空间"对应的正是判断那一刻的权限）。原文档在取锁之前被跨空间移走：空间行锁保护不到它，按"没找到"回答（与复制相同；页面保留内容，再试会成功）。
- 自动核对：新的权限矩阵 `permissions/conflict-copy-matrix.test.ts`（能不能做与放在哪里两张表逐格手写）；"看不到与不存在"加 6 个探测；路由表；5 个确定交错的用例（取锁之前被降级、换了文件夹、被移出、取消授权，另存持锁时被降级）；与其他操作两个方向的确定交错 27 条（`documents/conflict-copy-locks.test.ts`，写法同 `copy-locks.test.ts`：该等的等、不该等的不等、两边都结束、不成环；含"跨空间移动先提交 → 404"，守着锁下的 spaceId 复核，审查 B3）。

## M3-P5 的补充：强制接管与收回写入权的范围

- **强制接管的权限**：`DocumentPermissions` 加 `canTakeOver`（空间管理员，个人空间是所有者，并且能编辑；归档时空间角色已降为查看者，只凭授权的人没有空间角色，两者自然得不到），`DOCUMENT_CONTENT` 加操作 `takeOver`——与分享、跨空间移动同一个机制，不借用 `canShare`。申请按 `['edit', 'takeOver']` 判断，不加锁一次、锁下一次；403 的说法按先后：先判断 `edit`（查看者、归档），再判断 `takeOver`（编辑者："只有空间管理员能强制接管这份文档的编辑"；只凭编辑授权的人："这份文档是单独分享给你的，不能强制接管编辑"）。本人接管只要求能编辑。权限矩阵另核对"强制接管成功的格子恰好是编辑状态 `canTakeOver` 为真的格子"。
- **收回写入权只收回按时间还活着的租约**（ADR-018 的 M3-P5 补充）：刚死不久（一个有效期以内）的照样锁文档行、等在途的保存，只是不收回；死了超过一个有效期的不锁、不记 `revoked`、不加代次。"撤权提交之后的保存必定被拒绝"照样成立（前提由数据库与事务运行器保证：保存的事务从 BEGIN 到提交至多 70 秒，ADR-018）。锁的顺序不变；请求编辑与交出的新写路径只锁租约行。

## M3-P6 的补充：吊销本机密钥（ADR-019）

- **admin 的新操作**：吊销某人的本机密钥（`POST /api/admin/users/{id}/local-key/revoke`）照其他管理操作，在事务里先取 system-admins 的共享锁复核操作者、再锁账户行（`FOR NO KEY UPDATE`），然后才动本机密钥行、写审计 `users.local_key_revoked`。先锁账户行是必须的：两个并发的吊销只靠本机密钥行的 `FOR UPDATE` 时，后一个在 READ COMMITTED 的重新检查下拿到 0 行。
- **模块分层**加 local-keys：admin、workspace → local-keys → auth、database、config、logging；auth、users、documents、spaces 不依赖它。
- **lint**：吊销的入口 `LocalKeyRevocation` 只给 admin 的服务引用（控制器也拿不到；照 `DocumentTransferService`）；主密钥的注入标记 `LOCAL_KEYS_CONFIG` 只给 local-keys 引用。admin 的覆盖块改名为 `nerve/api-admin`，另有 `nerve/api-local-keys`。
