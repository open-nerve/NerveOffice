# ADR-021：图片处理与资源边界

> 状态：已接受（S3–S6 已实现并完成针对性验证，P1 整体门禁/CI 尚待完成）｜日期：2026-10-18，更新：2026-10-19｜来源：M5-P1-S2–S6｜依据：计划书§8.5/11.4、M5总设计§6.2、P1设计§3.2/3.6

## 背景与实测

上传大小不能代表解压后的成本，Node堆上限也不限制原生编解码器内存。四格式处理需要同时保证完整像素、隐私元数据移除、方向/透明度/动画语义和服务可用性。

S2用受控生成器、独立Pillow预期、逐图隔离处理与输出重新解码作证：[详细报告](../v0.1/M5-表格能力与资源/reviews/P1-S2-四格式处理与预算.md)。macOS ARM64小矩阵34例、Linux ARM64全矩阵44例、Linux x64仿真小矩阵34例通过；故障后正常图片恢复分别2/3/3种。仿真不证明原生x64性能。

S3 已按此契约实现正式处理器，并完成正式入口 44 样本、16 项进程故障与 20 份输出的独立 Pillow 核对，见 [S3 报告](../v0.1/M5-表格能力与资源/reviews/P1-S3-上传与故障复核.md)。S6 的正式生产镜像经公开 HTTP 再跑 44 样本、账户/全局准入压力与强制容器重建，20 接受/24 拒绝、拒绝后恢复成立；对应 10 条端到端检查首次通过，无重试/跳过。该轮 Linux ARM64 整容器 cgroup 峰值 666,939,392 B，OOM=0；最大上传阶段约 1,609.82 ms（包含样本准备、HTTP、处理及落库，不是单子进程计时）。详细回执见 [S6 部署复核](../v0.1/M5-表格能力与资源/reviews/P1-S6-部署与验收复核.md)。原生 x64 仍待同一合并提交的现有 Linux amd64 CI；这些结果不替代完整 Phase 验收。

## 处理方案

采用精确版本 **Sharp 0.35.5**，对应 `@img/sharp-libvips-* 1.3.4`，实际 **libvips 8.18.7**。沿用Node24.21.0、pnpm12.6.0和生产Debian slim镜像摘要；依赖安装不执行原生包的安装脚本。应用中 Sharp 只在图片子进程加载，不进入 API 主线程或前端；发行材料的独立离线校验进程另行加载它核对实际版本。

处理顺序固定：请求准入与有界读取 → 文件头/媒体类型/扩展名一致 → 容器完整性 → 元数据预算 → 完整RGBA解码及方向/sRGB转换 → 从像素重新编码 → 输出大小、格式、完整解码及动画语义复查 → 返回处理结果。解码器只接收字节，不接收路径、URL或客户端SVG；只允许PNG/JPEG/WebP/GIF Buffer loader，关闭libvips缓存，线程数1。

`failOn: warning`不能代替完整性：PNG检查块边界、CRC与IEND；GIF检查块、画布/帧边界及LZW的完整像素数和结束码，再做原生完整解码。APNG在本次四格式契约内明确按不支持的动画变体拒绝，不能静默取首帧。

PNG按无损重编码，JPEG质量90并先应用EXIF方向。WebP使用无损编码；动画逐帧编码后按公开RIFF/ANMF规范封装完整画布，保留重复帧、原始毫秒时长与循环。GIF使用effort7、零调色板复用误差、保留重复帧，并保留文件GCE的原始时长。GIF循环用文件的“额外重复次数”核验，不和库的“总播放次数”混用；未设置循环与无限循环有区别。输出不携带EXIF、ICC、XMP、IPTC、注释等原始元数据。

以上是正式实现的行为契约；诊断代码不直接搬进生产，S3按测试另行实现。图片任一阶段失败不得返回一个静默降级的成功文件。

## 固定预算与进程边界

| 项目 | 定值 |
|---|---:|
| 输入 / 重编码输出 | 各最多5MiB |
| 每边 / 每帧像素 | 8192 / 16,000,000 |
| 帧数 / 所有帧画布像素合计 | 100 / 32,000,000 |
| 执行并发 / 等待队列 | 1 / 最多4份 |
| 同一账户执行与排队合计 | 最多2份 |
| 排队等待 / 单图执行墙钟 | 10秒 / 5秒（含进程启动） |
| V8老生代 / 半区 | 128MiB / 16MiB |
| Linux进程地址空间硬上限 | 1536MiB，`prlimit --as` |
| 子进程环境 | `MALLOC_ARENA_MAX=2`、`UV_THREADPOOL_SIZE=1`、`VIPS_DISC_THRESHOLD=256m` |

每个任务使用新进程，结束后回收；一张图片只能占一个执行槽位。Node启用`--jitless`，减少地址空间预留；进程不继承应用机密或Node选项。父进程超时杀死并等到退出后才释放执行槽位；取消、关闭、异常或IPC断开也必须收尾，不留孤儿进程。排队准入不能等到无上限地收完所有请求体以后才执行；读取中止、排队超时、客户端断开都要归还准入名额。

Linux正式运行缺少可用`prlimit`时拒绝图片服务启动，不能悄悄只保留堆限制。macOS开发环境保留进程、堆、大小、时间和队列边界，但不宣称具有Linux地址空间硬上限。正式部署仍为既有Linux镜像。

实验容器另设512MiB、1CPU、无网络与只读根目录；Linux最终44例最大约1.55秒，单子进程maxRSS约437MiB，容器cgroup峰值约415MiB，无OOM。两项内存计量口径不同。**512MiB只是实验容器上限，生产进程硬上限是1536MiB地址空间**，不能用某轮RSS峰值替代硬预算，也不保证所有合法大小的复杂图片都能在5秒内完成。

生产应用容器预算在既有快照池公式上加1536MiB与有界上传缓冲：默认快照配置约1.7GiB，加图片处理约1.5GiB，总计约3.2GiB，建议应用容器至少4GiB，不含PostgreSQL。S6 已给测试 Compose 设置 4 GiB，并在正式 ARM64 镜像中完成真实上传/排队/释放复验；原生 x64 仍待 CI。实测峰值不能取代理论上限或允许任意提高快照并发。

## 组织配额

单租户组织同时限制物理存储和上传记录，避免同一图片反复去重后仍可无限创建asset行。

- `NERVE_ASSET_QUOTA_BYTES`：默认10GiB，合法范围5MiB–1TiB的整数。统计不可变物理对象及尚未转正的已发布对象；同hash只占一次物理字节。
- `NERVE_ASSET_QUOTA_COUNT`：默认100,000条，合法范围1–1,000,000的整数。每次成功上传独立assetId占一条，即使复用物理对象也占名额。
- 配额检查与预留必须在数据库中串行、持久化；文件发布后数据库提交失败的对象仍被计入，不能只数已提交的asset_objects而让故障遗留绕过物理配额。未知提交结果按保守占用处理。S3细化写入预留与转正的事务，S5遵守既有锁顺序。
- 缩小配额不删除已有资源；超额时拒绝新增占用，既有读取照常。P1不启动孤儿或正式对象GC；任务自有临时文件应清理，完整发布对象按既定保留策略留待P4。

## S3处理接口与错误

内部 `ImageProcessingLimits` 持有上述固定值，不允许运维调大到未经实测的范围。`ImageProcessingInput` 为有界字节、声明媒体类型、规范化后缀；原文件名不进入处理任务或日志。`ProcessedImage` 包含处理后字节、SHA-256、媒体类型、宽高、帧数、字节数；不得带原始元数据。父进程验证返回结构、字节上限及摘要后才交存储。上传响应只返回assetId、规范url、媒体类型、宽高和字节数，不暴露对象路径/内部hash。

| 情况 | 对外契约 |
|---|---|
| 请求体超过5MiB | 既有`PAYLOAD_TOO_LARGE`，413 |
| 不接受的HTTP媒体类型/编码 | 既有`UNSUPPORTED_MEDIA_TYPE`，415 |
| 伪装、损坏、尺寸/像素/帧/输出超限、不支持动画 | `ASSET_INVALID`，422，有限`details.rule`，不回显输入 |
| 单图超时或原生/堆内存边界拒绝 | `ASSET_INVALID`，422，`too-complex`；不给同一输入自动无限重试的提示 |
| 全局/账户准入满、排队超时、关闭中 | `ASSET_BUSY`，503，`Retry-After: 10` |
| 组织字节或记录配额不足 | `ASSET_QUOTA_EXCEEDED`，409，`details.kind=bytes/count` |
| 初始化/存储/不可归因的子进程或协议错误 | 既有通用500/503；服务端只记阶段/标识/错误分类 |

原生库有些分配失败只报通用解码错误，不能仅凭错误字串推导OOM；已知操作系统/协议事实与普通解码拒绝分开记录。所有失败都必须能让下一正常任务继续执行。

## 依赖许可与交付条件

Sharp和各平台绑定为Apache-2.0；已实测的`@img/sharp-libvips-darwin-arm64`、`-linux-arm64`、`-linux-x64` 1.3.4声明LGPL-3.0-or-later。本次按包接受它们作为资源处理依赖：调用经可替换共享库完成，未把库静态链接进NerveOffice应用；应用源码继续按原Apache-2.0分发。`otool`/`ldd`记录已确认实际共享库链接。

接受附带明确的实现条件，不能全局放行LGPL：

1. S3逐包登记许可例外，并约束版本与锁文件；新版本/平台要重新核对。生产许可清单必须包含GPLv3、LGPLv3正文、上游声明和附带库的许可/版权，不用仅有URL的README代替全文。
2. 保留替换兼容共享库的机制和操作说明，不新增禁止修改库或为调试修改而逆向的条款。NerveOffice和库自身的许可证分别说明。
3. 分发原生二进制时一并提供对应源码、补丁与构建说明的副本，不能只给指向主分支的链接。S2/S3 按上游 v1.3.4 脚本取得对应源码归档、补丁与 librsvg 锁定的 crate，记录精确 URL/摘要并校验 Cargo.lock checksum。S6 已将 398 份来源（201,994,917 B）及索引/许可/构建说明收集进正式镜像 `/app/licenses/native-images`，不在 Web 根内；逐文件/逐声明离线复核、真实 Sharp/绑定/libvips 版本核对均为构建与部署门禁。
4. 上游顶层声明之外还要覆盖 Rust 依赖（包括 MPL-2.0、Unicode 等）。部分 crate 不带独立 LICENSE 文件，须保留原源码中的声明并附足全文；不可伪造版权年份或把测试/其他平台依赖说成实际已链接。S3 补件与 S6 的 816 项声明核对已完成，gnulib 许可概述的标题已纠正，完整 GPLv3 另有原件。完整许可正文 4,485,036 B；来源清单与声明/正文/源码实际字节共同检查。材料不齐或版本不符时构建失败，P1 不得验收合并。

这是已批准选型中的原生依赖交付要求，不新增外部服务或改变支持格式。S2只定方案与验收契约，未改生产许可白名单、依赖锁文件或镜像。权威依据为[Sharp安装说明](https://sharp.pixelplumbing.com/install/)、[对应发行与构建](https://github.com/lovell/sharp-libvips/tree/v1.3.4)、[上游附带库声明](https://raw.githubusercontent.com/lovell/sharp-libvips/v1.3.4/THIRD-PARTY-NOTICES.md)及归档许可正文。
