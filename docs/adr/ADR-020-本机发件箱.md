# ADR-020：本机发件箱

> 状态：已接受（M4-P1）｜日期：2026-10-09｜来源：M4-P1（`docs/v0.1/M4-本地优先与离线恢复/01-P1-本机发件箱.md`）｜依据：00 号计划书 §7.2、§7.5、§7.6、§7.8（r21）；M4 总设计 §2.2、§6.1–§6.5；ADR-018（编辑租约）、ADR-019（本机密钥）

## 背景

- 计划书 r21 的原则是"先写本机、再同步服务器"：修改先加密写进浏览器的本机发件箱，再上传；断网不丢，页面崩溃或浏览器被结束之后联网重开能恢复。写入的边界仍由服务端的三重检查保证（租约、修订号、代次，ADR-018）；本机这一侧要保证的是"写下的读得回、读回的可信、旧标签页写不坏新一代的草稿"。
- M0 的原型（P6 报告）验证过原子写入、进程被结束之后恢复、加密与性能。但它不认在途的请求、代次是本机计数、用 Blob；而且它的写入耗时、`strict` 的开销与写满，是在 Playwright 默认的、不落盘的上下文里测的（Chromium 是无痕式的上下文，WebKit 是临时存储），数字要在持久的浏览器目录与真实 Safari 上重测（M4-P1 设计 §1 偏差 7）。
- M4-P1 交付底座（存储、加密、写入管道、Worker、本机密钥的客户端、崩溃工具）；接入编辑器页的保存管道在 P2，恢复在 P3，本机草稿页与清理的入口在 P4。
- P1 的崩溃用例查出：Chromium（含 Google Chrome 154）在进程被结束于 LevelDB 日志写到一半时，**再下一次启动会删掉这个来源的全部 IndexedDB**（`reuse_logs` 接在半条记录后面写，校验和不符，paranoid 打开失败）；Google Chrome 不注入时 1400 次强制结束里 5 次。只有删库之后第一个 `open()` 拿到 `dataLoss: "total"`，编辑器页里最先打开的是 Univer 自己的库，应用靠不住它。WebKit（每个库一个 SQLite）290 次 0 次。证据、确定的复现与上游报告的草稿见 UR-034，需求方 2026-10-09 决定"OPFS 冗余 + 如实告知"。

## 决策

### 威胁模型与总规则

- **本机草稿防的是**：页面崩溃、断网、浏览器被结束时丢失还没同步的修改。**加密防的是**：设备丢失（系统管理员吊销本机密钥之后再也解不开，ADR-019），以及同一台设备上的别的用户读到。
- **不防**（计划书 §7.6 的已接受风险）：
  - 本机回滚——把同一份文档的旧记录整条写回；
  - 记录的键里的文档 id 是明文；
  - 能在本页执行脚本的人能用内存里的密钥。
- **租约令牌、原始密钥不进浏览器的存储**：写入者用这一代的 `writeEpoch` 与每次登记随机生成的 `writerId` 认，不用租约令牌（令牌只在标签页的内存里，ADR-018）。
- **跨边界不抛异常**：存储、写入管道、Worker 的客户端、本机密钥的保管者，结果一律是带 `kind` 的值；未知的错误归为 `failed`，带名字与消息。
- **拿不准就不覆盖**：别的写入者留下、还没接手的草稿，存储层拒绝覆盖（`foreign-draft`），接手要显式进行（`adoptSeq`）；把"真冲突一律另存为副本"兜在最底层。

### 存储（IndexedDB）

- **库与仓库**：
  - 库 `nerve-office-outbox`，版本 1；三个对象仓库 `drafts`、`writers` 与 `notices`（恢复的提示，见"OPFS 的冗余"），键路径都是 `['userId', 'documentId']`（平台的文档 id，不用 `unitId`），没有索引。
  - 某人的全部记录用键范围 `[userId] … [userId, []]`（键序里数组排在字符串之后）取。
  - 结构只做加法的升级。
- **打开**：
  - 没有 `indexedDB` 或 `crypto.subtle` → `unsupported`；打不开 → `denied`；`VersionError` → `newer-version`；等升级超时 → `blocked`——都交回"不可用"及原因，由调用方退化为内存实现（P2）。
  - 连接收到 `versionchange` 立即关闭，让别的标签页的升级继续。
  - 开事务时连接已断（`InvalidStateError`、`UnknownError`）重开一次再试，连着两次交回 `failed`。
  - 列表的索引（`draft-index.ts`）只打开已有的库，库不存在时交回空集合，不建库。
- **记录**：
  - 草稿：明文的元数据加上 `iv`（12 字节）与 `ciphertext`（gzip 之后的快照加密、带 16 字节的认证标签）。元数据是文档、基准修订号、`writeEpoch`、`writerId`、写下它的客户端实例、草稿序号、内容的构建与数据格式、"公式待更新"、密钥版本、在途的请求、解压后的字节数、更新时间。
  - 存字节，不存 Blob（WebKit 离线时读不了 Blob）；字节是"紧凑"的（结构化克隆会把整个底层缓冲存进库）。
  - 写入者：`writeEpoch`、`writerId`、草稿序号的高水位 `lastDraftSeq`、登记时刻。
- **事务**：
  - 判定（`writer-fence.ts` 的纯函数）与写入在 `[drafts, writers]` 的同一个 `durability: 'strict'` 事务里。
  - 事务里只有 IndexedDB 的请求回调，不 await 加密、压缩这类别的异步；否则事务自动提交，判定与写入之间就能插进别的标签页。
- **写入栅栏与序号**：
  - **登记**：没有写入者、或现有写入者的代次更小 → 登记，交回高水位 = max(旧写入者的高水位, 现有草稿的序号) 与现有的草稿；代次更大、或同一代而 `writerId` 不同 → `superseded`。调用方向服务端核对，确实是当前的一代，就以 `force` 重新登记（服务端从备份恢复之后代次倒退、同一个页面重建了 Worker）。
  - **写入**：写入者与序号取自记录本身；要求是登记的写入者、序号大于高水位、不覆盖别的写入者的草稿（除非带着看过的那一份的 `adoptSeq`）。同一写入者、同一序号的重试按已写入（`duplicate`）。成功就抬高高水位。
  - **重封**：标记在途、换密钥、确认之后改基准，都是比较并交换——写入者仍是它、库里仍是这一份。
  - **确认**：序号不大于确认的就删；更新的换成重封过的那一份（基准换成新的修订号、清掉在途），认定"就是库里这一份"按同一个写入者、同一个序号。别的写入者留下的不因本页的确认而删。
  - **放弃**：用户的决定，不核对写入者；可以带 `expectedSeq`，免得删掉别的标签页刚写的。
  - **按用户清理**：先在一个 strict 事务里把 drafts、writers、notices 三个仓库中文档键的并集全部立墓碑（包括没有写入者、只有提示的文档），再删镜像目录，最后清库；镜像目录删不掉的那几份（编辑器页的发件箱 Worker 正拿着句柄）草稿与提示留着、写入者换成墓碑。之后才到的写入一律 `not-writer`。
  - **墓碑**（审查 A1、A6）：`writerId` 为 `retired` 的写入者记录（登记的 `writerId` 是随机的 UUID，存储拒绝用 `retired` 登记），代次照旧、高水位不低于现有草稿的序号。写入、重封、确认对它一律 `not-writer`（那一页的 Worker 随之放开镜像的句柄，页面经服务端核对再决定），比对时不从镜像写回。立在：按用户清理与放弃时镜像目录删不掉的那几份、保留期里登记超过 14 天又没有草稿的写入者；这份文档的镜像目录不在之后由合一的清理删掉（没有 OPFS 时一律删）。新的一代照常登记（代次更大）；同一代的页面得到 `superseded`，经服务端核对之后 `force`。
- **写满**：`QuotaExceededError` 出现在 `put` 上，或者提交时的 `tx.error` 里，都归为 `quota`；整个事务回滚，原记录与高水位都不变。存储层如实交回，重试的节奏归 P2。Chromium 写满之后用量要过一阵才降下来，这期间连小的写入、登记也写满。
- **保留期**：
  - 14 天，常量 `LOCAL_DRAFT_RETENTION_DAYS` 在契约里，服务端修订记录保留期的下限由它推出（+1，数值仍是 15）。
  - 清理按记录里**读得出的** `updatedAt` 判断，不论格式：形状不对、由更新的页面写的，只要读得出且超过 14 天就一并删，交回的键标明是哪一种；读不出的留给打开文档时（P3）、本机草稿页（P4）说明并删。
  - 写入者登记超过 14 天、又没有草稿时换成墓碑（不是删掉：镜像里没截断成的那一份不会因写入者没了而在比对时被写回来）。连续开着超过 14 天的页面因此可能遇到一次 `not-writer`，经服务端核对之后 `force` 重新登记，不丢数据。
  - 按墙上时间：设备的时钟曾慢、校正之后，刚写下的草稿可能在下一次清理时被删；时钟快时不过期。写入时刻只能取墙上时间，这是固有的限制（审查 A17）。

### 记录格式与加密

- **加密**：格式版本 `recordVersion = 1`，比本页认识的新 → `newer-format`，不动它。AES-GCM-256，每条 12 字节的随机 IV，同一把密钥不重用 IV（重封一律换新的 IV）。
- **AAD**：UTF-8 的 JSON 数组，第一项是格式标识 `"nerve-office/outbox-draft/v1"`，之后按固定的字段表排列全部明文元数据（内容的格式与在途的请求各展开成固定顺序的子数组）。字段表在类型上与元数据的键一一对应，加字段而忘了进 AAD 就过不了类型检查；改动任何一个明文字段，解密都失败。但整条记录挪到别的键下（例如槽位文件挪进别的文档的目录）照样解得开，所以读镜像时另核对记录的 `userId`、`documentId` 与目录的键一致，对不上的槽位不合格（审查 A4）。加密有已知答案测试钉住格式，期望值另用 `node:crypto` 核对。
- **读出时的形状核对**：
  - 字段的类型与范围；
  - 字节紧凑；
  - 在途的序号不大于草稿序号。反过来的记录在恢复时会把旧内容当"自己追自己"接到服务端更新的那一版上，静默退回别人已存的修改。
  - 不合格的读成 `malformed`。
- **解不开的归类**：记录的密钥版本小于当前的版本 → `revoked`（密钥已吊销，ADR-019 的版本连续）；大于当前的版本 → `stale-key`（本页手里的密钥过时了，去取新密钥再试，**绝不删除**；审查 A3）；相等 → `corrupted`（已损坏，包括被改过）。`revoked` 与 `corrupted` 都删除，只是说法不同。非认证失败的错误照常向上报，不归进这几类。

### 写入管道（`DraftWriter`）

- **一个接口，两种宿主**：进程内的实现（`createDraftWriter`）与发件箱 Worker 的客户端都实现 `DraftWriter`。编辑器页只依赖接口；放在 Worker 还是主线程，只换宿主（见最后一节）。
- **写入**：
  - 主线程只做 `save()`、序列化与一次编码，字节交给管道。管道按文档排队：去重（`save()` 原文的 SHA-256 连同"公式待更新"，与上次写入的相同、并且这次允许去重就交回 `unchanged`）→ gzip（内存里的流，不经 Blob）→ 加密 → 写入。
  - 压缩之后的每一种结果都带着 gzip 的字节（写满、没有密钥、库用不了、被栅栏拒绝时上传照旧，不必再压一次）。
  - 一次没写成之后，去重的起点作废：那一份照样会上传，服务端可能已不是上次写下的内容。
- **在途的请求**：上传发出之前先把 `inFlight`（请求标识、客户端实例、序号、发出时刻）重封进记录、落盘；上传在途时写下的新一份接着带上它，崩溃之后恢复才认得出"自己追自己"。库里的那一份比在途的旧时不标。
  - 只记这四项：原样重放只在"记录还是在途的那一份"时做，这时公式标记、构建与数据格式就是记录本身的。
  - 能否原样重放看 `canReplayAsSent`：在途的就是这一份，并且发出不满 14 天（服务端修订记录与回执的保留期至少 15 天）。
- **换密钥**：心跳得知新的版本之后（P2 接），用新密钥重封本页写下的草稿；没能重封的（例如手里没有最新的内容、又解不开）交回清单，由调用方用新密钥写一份新的。
- **发件箱 Worker**：
  - 协议带版本，用手写的守卫，不引用 zod（门禁按全部产物数 zod 的 JIT 探测）。
  - Worker 里的处理注入存储与时钟。
  - 客户端按 id 对应、每个请求有看门狗时限；到点、`error`、`messageerror`、终止时，在途的全部以失败结束，之后立即失败。
  - 写入的字节与交回的 gzip 都放进 transfer。
  - Worker 启动时开一个 100 ms 的空定时器（DEF-011），有回归用例。
  - **Worker 一侧由 lint 界定**（`eslint.config.ts` 的 `OUTBOX_WORKER_SIDE`）：`shared/outbox` 里除只在主线程用的模块之外的文件（新文件默认算在内）、编辑器页 `outbox/` 的协议、处理与 `*.worker.ts`、测试构建里探针 Worker 用到的文件。它们只许引用 Worker 一侧的文件与契约里不带 zod 的常量（转了一手的引用也拦得住）；只在主线程用的模块逐个列在 `OUTBOX_MAIN_THREAD_ONLY`（`local-key.ts`、`storage-status.ts`、`local-cleanup.ts`、`outbox-worker-client.ts` 与页面一侧的探针），不许引用（`import type` 放行）；只在页面里有的全局（`window`、`document`、`localStorage` 等，直接写与经 `globalThis` 都算）、`navigator.storage.persist` 与动态 `import()` 都拦下。lint 自测里直接、间接、DOM 各有违规与放行的样例。

### OPFS 的冗余

- **为什么不用别的**：localStorage 延后落盘（被结束 2540 次，一次都不是刚写的值），在 Chromium 里也是同样复用日志的 LevelDB；同一来源的多个 IndexedDB 库共用一个 LevelDB，分库没用；OPFS 用 `createWritable` 写时每次都改 OPFS 的目录库（同样的 LevelDB），目录库出事时被改写的文件整个消失。**只有在专用 Worker 里用同步访问句柄改写已有的文件，才不碰任何 LevelDB。**
- **做法**：IndexedDB 仍是主存储（写入栅栏、序号、确认都在它的事务里）；每次在它里面写成之后，同一份记录再镜像进 OPFS：
  - 登记写入者时为这份文档建好 `nerve-office-outbox/<userId>/<documentId>/` 下的两个槽位文件，之后只用同步访问句柄改写与截断：不新建、不改名、不删、不用 `createWritable`；只有按用户清理与保留期才删目录。
  - 两个槽位轮流写在"不是最新那一份"的槽位上：截断 → 写内容 → 写头 → `flush()`。文件 = 固定 256 字节的头 + 内容；头里有魔数 `NRVOMIRR` 与格式版本、写入者（代次、`writerId`）、草稿序号、代号（这对槽位的写入次数，同一份内容的重封靠它分先后）、内容的长度与 SHA-256、头自己的 SHA-256。内容就是存进 IndexedDB 的那一份记录，读出时照样过记录的形状核对、由 AAD 认证。写一半的槽位校验不过、落选，另一个槽位上的上一份还在。
  - 镜像只放已提交的：IndexedDB 的事务提交之后才写；没写成（写满、句柄被占、出错）不影响 IndexedDB 那一份，结果里如实带上。
  - 句柄由写入者持有，失去写入者身份或页面离开时关；拿不到时退避再试。
- **短期互斥**（独立复核 D1、D2）：`outbox-lock.ts` 用同源 Web Lock `nerve-office-outbox-operation` 覆盖完整文档任务、平台单份恢复与三种清理。等待最多 10 秒；不可用、等待取消时明确失败，不能无锁运行；已经开始的任务以实际结束为释放边界。长期 OPFS 句柄不持此锁，空闲旧 Worker 不阻塞接管。这样临时读者完成恢复之后才轮到登记，主库提交后的镜像写入完成之后才轮到清理。内部 store/mirror/recovery 不重复加锁。来源内不同文档短期串行；与 M3 的编辑权锁及其退化规则分开。
- **读与恢复**（审查之后，A2、A3、A11、A13、A18）：
  - 登记前的比对遇存储问题、镜像读取失败时不登记，稍后重试。镜像任一槽位是 newer-format 时整个镜像认不出：不写回、不报 lost、不截断、不覆盖；登记和写入结果带 not-mirrored/newer-format。保留期与用户明确清理仍按各自规则执行。
  - 镜像的两个槽位之间按代号认最新写的那一个（合格的槽位里代号最大的）。
  - 与库比对（读草稿、登记之前；打开平台、本机草稿页列出之前；一份一份地来，一份出错不拖累别的）。写回与否最终在存储的事务里按库里当前的写入者判（`decideRestore`）：
    - 库里这份文档既没有写入者也没有草稿（删库）→ 写回，写入者照它建；
    - 库里是墓碑 → 不写回，截断镜像；
    - 同一个写入者：库里是它的草稿 → 镜像的更新才写回（库悄悄退回了已提交的写入），抬高高水位；库里没有它的草稿 → 序号大于高水位才写回（不大于的是确认删掉、放弃过的，不复活）；
    - 不同的写入者（草稿序号是一份文档一条线，登记时继承高水位）：序号不大于库里写入者的高水位 → 它登记时看过这一份，不写回（含 force 登记、代次倒退之后旧一代的镜像）；候选的代次更大 → 写回，写入者换成它的（库悄悄丢了更新的那次登记与它的写入，UR-034 的变体）；库里没有草稿，或仅有候选写入者自己更早的草稿 → 写回成别人留下的草稿，不动写入者与高水位；否则按 unseen 保留双方，并留一次 lost 提示（候选未被看过但不能覆盖当前草稿）；
    - 超过保留期、库里那一条认不出 → 不写回。
  - 已知限制：服务端从备份恢复、代次倒退后，以 force 登记的较小代次连同它的写入一起被 IndexedDB 丢掉时，镜像候选的代次比库里留下的写入者小。如果库里仍有另一位写入者的草稿，单凭现有记录不能证明候选更晚；按 unseen 保留双方并留下 lost，不擅自覆盖。这与正常 force 登记后的高水位优先不同：后者登记记录还在，可以确定先后。
  - 写回连同写入者的记录与 `restored` 提示在同一个 strict 事务里。没写回而库里有草稿时：本页是写入者（拿着句柄）就用库里那一份补写镜像（被结束在"库已提交、镜像还没写完"之间，否则下一次删库会退回旧的一份）；不是写入者而镜像过时（确认删掉、放弃过、超过保留期、墓碑）就截断。
  - 两个槽位都不合格（更新的页面写的格式不算）、库里连草稿带写入者都没有 → 核对之后留下 `lost`、截断两个槽位。
  - 读草稿与登记只交回最新的那一个版本：写回了就是写回的那一份，否则库里的，库用不了时镜像里最新写的；同一个版本在库与镜像里各有一份时互为备份（解不开的那一份换另一份），不退回更旧的版本——最新的那一份解不开就如实交回它的原因。
  - 平台页面（P4 的本机草稿页）列出与清理之前先比对：经 `getFile` 只读镜像、只写回，不截断、不补写、不留 `lost`（截断不了槽位，留了每次都会再留一遍；`lost` 由编辑器页的发件箱 Worker 留下）。删库之后只在镜像里的草稿先写回库，列出、清理就都看得见（审查 A18）。
  - 提示存在库的 `notices` 仓库里（不在 Worker 的内存里，Worker 坏了也不丢），由打开文档时（P3）、本机草稿页（P4）读出、如实告诉用户，看过之后清除。
  - 比对的策略在 `draft-recovery.ts`，经接口注入写入管道（审查 A19）；写入管道只负责写。
- **放置**：进程内放置不写镜像，但默认通过 pageMirror 只读恢复后才登记，同样持短期锁（不留 lost）。三个浏览器都用 Worker 放置（DEF-011 的定论，见最后一节）；进程内放置只作 Worker 起不来时的退路，那时 Chromium 系上没有这层冗余（P2 设计退路时算进去）——WebKit 的 IndexedDB 是 SQLite，290 次强制结束没有丢失。Playwright 的 WebKit 默认上下文没有 OPFS（`getDirectory` 报 `UnknownError`），按 `unsupported` 处理。
- **防不了的**：清除站点数据、浏览器回收存储空间（两份在同一个存储桶里），`persist()` 照旧申请；本机占用约翻倍。
- **合一的清理**（`local-cleanup.ts`，页面里用）：按用户清理、放弃、保留期都把库（草稿、写入者、提示）与镜像目录一起清，"两份一起清"只写在这一处。镜像目录的句柄开着（编辑器页的发件箱 Worker 正写着）删不掉时，这一次跳过、交回 `pending`，写入者换成墓碑：按用户清理时库里那几份的草稿与提示也留着，之后再调接着清（连墓碑一起删，只在这个人仍是退出的时候）；放弃时库照删，不必再调，墓碑挡住镜像里那一份复活。保留期只回收两个槽位都超过 14 天没动过（或者文件不在）的目录——刚截断的空目录留给下一次编辑，平时不碰 OPFS 的目录库（审查 A9）；镜像目录不在的文档的墓碑一并删；库那一段删了之后，镜像那一段出了问题也照样交回删了哪几份（审查 A5）。

### 本机密钥的客户端

- **取用**：`fetchLocalKey`：`POST /api/local-key`（请求层自动带 CSRF）→ 契约校验 → base64 解成恰好 32 字节 → `importKey('raw', …, false, ['encrypt', 'decrypt'])` → 原始字节在 `finally` 里清零。导入单独成不引用 zod 与请求层的模块 `local-key-import.ts`。`atob` 的结果与响应的 JSON 文字清不掉，与 DEF-068 同一类。
- **保管者**（`createLocalKeyKeeper`）：
  - 同时只有一个取用在途；
  - 会话类失败交给页面确认会话，只有连着的第一次在确认之后立即重试；
  - 500、网络与时限按"暂时取不到"退避，不重试成风暴；
  - 心跳带来的版本不同就停用旧的、重取；
  - 退出登录、换人时 `discard()`，取用期间被丢掉的那一次交回 `discarded`，不交给调用方；
  - 计时都经注入的时钟。

### 测试构建里的探针

- 浏览器层的测试经编辑器页：测试构建的 e2e 分支在地址带 `outboxProbe` 时动态引入探针，挂上 `window.__nerveOutboxProbe`；不新建测试入口页（M3-P2 复核 B4）。门禁登记测试专用的来源、产物与禁用关键字。
- **探针不引用请求层与 zod**：探针一引用请求层，测试构建就把请求层连同 zod 与契约的错误结构拆进一个新的共享分块，而且先于 `zod-jitless` 求值，这正是会出 CSP 违规的那一类。所以：
  - 探针自己发取钥匙的请求；
  - 两份构建的入口的静态闭包模块集合核对相同；
  - lint 的区域规则把探针目录列进"不许引用 zod 与请求层"。
- **覆盖率**：IndexedDB 的接线（`database.ts`、`draft-store.ts`、`draft-index.ts`）、Worker 的薄入口与探针，不计入单元覆盖率，由三个浏览器的浏览器层用例覆盖，理由与编辑器适配层相同（规范 §8.3）。判定逻辑全部是纯函数，在单元测试里测。

### 放置与真实浏览器上的结论

M4-P1 在真实 Safari 27.0 与三个浏览器的持久上下文（会落盘，40 次）上复核，证据在 `docs/v0.1/M4-本地优先与离线恢复/reviews/P1-真实浏览器复核.md`：

- **WebKit 保留 Worker 放置**（DEF-011）：生产的发件箱 Worker 带 100 ms 的空定时器，在 Safari 上空闲 ≥ 1 秒之后写 55 次，0 次停顿，往返 p95 88 ms（含 OPFS 镜像写入，55 次都写成了）；三个浏览器的持久上下文同样 0 次（p95 77–102 ms）。不带空定时器的探针 Worker 在 Safari 与 Playwright 的 WebKit 上仍有约 1 秒的停顿（各在空闲 3 秒那一档 10 次里 1 次，各档合计 75 次里 1 次）。这一轮的次数单独证明不了空定时器有效（1/75 对带空定时器的 0/130，单侧 Fisher 检验 p ≈ 0.37）；保留它的依据是 M0（不带 60 次里 8 次、带 40 次里 0 次，p ≈ 0.014），这一轮方向一致，代价可以忽略（每 100 ms 一次空回调）。公式 Worker 上同一类的停顿见 DEF-072。主线程放置只作 Worker 起不来时的退路（主线程 gzip 的最长阻塞 p95 约 50 ms）。
- **`durability: 'strict'`**：Safari 27 支持，请求 strict 时事务的属性就是 strict；四个浏览器都反映它。磁盘上约 1.3 MiB 的写入 strict 比默认中位数多约 1 ms。断电下是否真的落盘由 M4-P6 的虚拟机实验回答（DEF-009）。
- **磁盘上的写入**：Safari 上生产存储的写入（strict）约 1 MiB p95 3 ms、约 5 MiB p95 8 ms；三个浏览器的持久上下文约 5 MiB p95 6–11 ms——与 M0 在不落盘的上下文里测的"写入 p95 ≤ 4.3 ms"同一量级。
- **OPFS 镜像的代价**：Safari 上镜像写入 p95 约 1 ms（flush ≤ 1 ms），登记与读两个槽位各 1–2 ms；Chromium 系写入 p95 1.2–1.9 ms、读 1.5–3.2 ms——可以忽略。
- **密钥交给 Worker**：不可导出的 `CryptoKey` 经 `postMessage` 交给 Worker 在 Safari 上可行（67 ms，没有钥匙串的提示）；退路（Worker 里导入原始字节、用完清零）也测过，留作备用。
- **还没核对的**：Safari 隐私浏览里有没有 OPFS（自检打不开私密窗口；没有时生产按 `unsupported` 处理，只少一层冗余）；Safari 的"7 个使用日"清理对获准持久保存的站点是否适用——都在 DEF-009 里，M4-P6 核对。

## 备选方案与取舍

- **单元测试用 fake-indexeddb**：没采用。它模拟不了配额与"事务里 await 别的异步就自动提交"，权威的结论仍要在真实的浏览器里得到；判定写成纯函数在单元测试里测，IndexedDB 的接线由三个浏览器的浏览器层覆盖，不新增依赖。
- **写入者存租约令牌**：没采用。令牌在浏览器的存储里就能被同一台设备上的人拿去写服务端；栅栏只需要"这一代、这次登记"的身份。
- **内容与状态分两条记录（状态另做认证）**：没采用。标记在途、确认之后改基准都要重封整份内容，但加密 5 MiB 只要几毫秒；一条记录、一份 AAD 更简单，也不会出现内容与状态对不上。
- **用 localStorage 留"有没上传的草稿"的记号、丢了只告知**：没采用。localStorage 延后落盘、在 Chromium 里同样会丢，记号本身靠不住；只告知救不回数据，需求方要求冗余。
- **OPFS 用 `createWritable` 写、或每次写一个新文件再改名**：没采用。都要改 OPFS 的目录库（同样复用日志的 LevelDB），目录库出事时文件整个消失。
- **发件箱只能放在 Worker**：没采用。写入管道与放置无关，真实 Safari 上 Worker 有停顿时可以换宿主，不改管道。

## 影响

- **P2（接入保存管道）**：
  - 序号在 `save()` 的同步段里从高水位往上分配；
  - 取得编辑权并拿到本机锁之后登记写入者，`superseded` 与 `not-writer` 经服务端核对处理（含连续开着超过 14 天的页面）；
  - 上传发出之前先等 `markInFlight` 落盘；
  - 写满之后页头一直说"本机存储空间不足"、每次捕获照常再试；
  - 换密钥之后没能重封的用新密钥写一份；
  - 新 Worker 的体积预算在生产构建里登记（审查修复之后测试构建里 gzip 约 12.6 KiB，登记约 15 KiB）；
  - Worker 起不来时的退路要算进"Chromium 上退到进程内就没有镜像"；
  - 编辑器页的生产代码引用 `local-key.ts` 时，再核对一次两份入口的静态闭包。
- **P3（恢复）**：
  - 判定读 `ReadDraft`、`DraftRead` 与 `canReplayAsSent`；解不开的 `stale-key` 去取新密钥再试，绝不删；
  - 接手别的写入者留下的草稿用 `adoptSeq`；
  - 原样重放成功之后用 `removeDraft(key, expectedSeq)` 删；
  - 判定表同样核对"在途的序号不大于草稿序号"；
  - 打开文档时读出恢复的提示（`restored`、`lost`），如实告诉用户，看过之后清除。
- **P4（本机草稿页与清理）**：
  - 本机草稿页列出与清理之前先比对（`reconcileAll(pageReconciliation(...), userId)` → `listDrafts` → 合一的清理），删库之后只在镜像里的草稿也看得见；`listDrafts` 认不出的也列出键，保留期清理交回删了哪几份（镜像那一段出了问题也交回）；
  - 退出登录、账户停用、放弃与保留期都经合一的清理 `local-cleanup.ts`（库与镜像一起清）；交回 `pending` 之后的重试，只在这个人仍是退出的时候做；
  - 本机草稿页列出恢复的提示；
  - 列表的标记只引用 `draft-index.ts`，并且按需加载（平台首屏的余量约 4 KiB）。
- **测试**：崩溃用例的工具与跑法见 M4-P1 设计 §3.7；E2E 与集成测试的测试库按主机标识命名，只清理本主机建的。
