# ADR-020：本机发件箱

> 状态：已接受（M4-P1 初版；"放置与真实浏览器上的结论"一节在 P1 的真实浏览器复核之后补）｜日期：2026-10-09｜来源：M4-P1（`docs/v0.1/M4-本地优先与离线恢复/01-P1-本机发件箱.md`）｜依据：00 号计划书 §7.2、§7.5、§7.6、§7.8（r21）；M4 总设计 §2.2、§6.1–§6.5；ADR-018（编辑租约）、ADR-019（本机密钥）

## 背景

- 计划书 r21 的原则是"先写本机、再同步服务器"：修改先加密写进浏览器的本机发件箱，再上传；断网不丢，页面崩溃或浏览器被结束之后联网重开能恢复。写入的边界仍由服务端的三重检查保证（租约、修订号、代次，ADR-018）；本机这一侧要保证的是"写下的读得回、读回的可信、旧标签页写不坏新一代的草稿"。
- M0 的原型（P6 报告）验证过原子写入、进程被结束之后恢复、加密与性能。但它不认在途的请求、代次是本机计数、用 Blob；而且它的写入耗时、`strict` 的开销与写满，是在 Playwright 默认的、不落盘的上下文里测的（Chromium 是无痕式的上下文，WebKit 是临时存储），数字要在持久的浏览器目录与真实 Safari 上重测（M4-P1 设计 §1 偏差 7）。
- M4-P1 交付底座（存储、加密、写入管道、Worker、本机密钥的客户端、崩溃工具）；接入编辑器页的保存管道在 P2，恢复在 P3，本机草稿页与清理的入口在 P4。

## 决策

### 威胁模型与总规则

- **本机草稿防的是**：页面崩溃、断网、浏览器被结束时丢失还没同步的修改。**加密防的是**：设备丢失（系统管理员吊销本机密钥之后再也解不开，ADR-019），以及同一台设备上的别的用户读到。
- **不防**（计划书 §7.6 的已接受风险）：
  - 本机回滚——把同一份文档的旧记录整条写回；
  - 记录的键里的文档 id 是明文；
  - 能在本页执行脚本的人能用内存里的密钥。
- **租约令牌、原始密钥不进浏览器的存储**：写入者用这一代的 `writeEpoch` 与每次登记随机生成的 `writerId` 认，不用租约令牌（令牌只在标签页的内存里，ADR-018）。
- **跨边界不抛异常**：存储、写入管道、Worker 的客户端、本机密钥的保管者，结果一律是带 `kind` 的值；未知的错误归为 `failed`，带名字与消息。
- **拿不准就不覆盖**：别的写入者留下、还没接手的草稿，存储层拒绝覆盖（`foreign-draft`），接手要显式进行（`adoptSeq`）；把"真冲突一律另存为副本"兜在最底层。

### 存储（IndexedDB）

- **库与仓库**：
  - 库 `nerve-office-outbox`，版本 1；两个对象仓库 `drafts` 与 `writers`，键路径都是 `['userId', 'documentId']`（平台的文档 id，不用 `unitId`），没有索引。
  - 某人的全部记录用键范围 `[userId] … [userId, []]`（键序里数组排在字符串之后）取。
  - 结构只做加法的升级。
- **打开**：
  - 没有 `indexedDB` 或 `crypto.subtle` → `unsupported`；打不开 → `denied`；`VersionError` → `newer-version`；等升级超时 → `blocked`——都交回"不可用"及原因，由调用方退化为内存实现（P2）。
  - 连接收到 `versionchange` 立即关闭，让别的标签页的升级继续。
  - 开事务时连接已断（`InvalidStateError`、`UnknownError`）重开一次再试，连着两次交回 `failed`。
  - 列表的索引（`draft-index.ts`）只打开已有的库，库不存在时交回空集合，不建库。
- **记录**：
  - 草稿：明文的元数据加上 `iv`（12 字节）与 `ciphertext`（gzip 之后的快照加密、带 16 字节的认证标签）。元数据是文档、基准修订号、`writeEpoch`、`writerId`、写下它的客户端实例、草稿序号、内容的构建与数据格式、"公式待更新"、密钥版本、在途的请求、解压后的字节数、更新时间。
  - 存字节，不存 Blob（WebKit 离线时读不了 Blob）；字节是"紧凑"的（结构化克隆会把整个底层缓冲存进库）。
  - 写入者：`writeEpoch`、`writerId`、草稿序号的高水位 `lastDraftSeq`、登记时刻。
- **事务**：
  - 判定（`writer-fence.ts` 的纯函数）与写入在 `[drafts, writers]` 的同一个 `durability: 'strict'` 事务里。
  - 事务里只有 IndexedDB 的请求回调，不 await 加密、压缩这类别的异步；否则事务自动提交，判定与写入之间就能插进别的标签页。
- **写入栅栏与序号**：
  - **登记**：没有写入者、或现有写入者的代次更小 → 登记，交回高水位 = max(旧写入者的高水位, 现有草稿的序号) 与现有的草稿；代次更大、或同一代而 `writerId` 不同 → `superseded`。调用方向服务端核对，确实是当前的一代，就以 `force` 重新登记（服务端从备份恢复之后代次倒退、同一个页面重建了 Worker）。
  - **写入**：写入者与序号取自记录本身；要求是登记的写入者、序号大于高水位、不覆盖别的写入者的草稿（除非带着看过的那一份的 `adoptSeq`）。同一写入者、同一序号的重试按已写入（`duplicate`）。成功就抬高高水位。
  - **重封**：标记在途、换密钥、确认之后改基准，都是比较并交换——写入者仍是它、库里仍是这一份。
  - **确认**：序号不大于确认的就删；更新的换成重封过的那一份（基准换成新的修订号、清掉在途），认定"就是库里这一份"按同一个写入者、同一个序号。别的写入者留下的不因本页的确认而删。
  - **放弃**：用户的决定，不核对写入者；可以带 `expectedSeq`，免得删掉别的标签页刚写的。
  - **按用户清理**：草稿与写入者在一个事务里一起删；之后才到的写入因写入者不在而 `not-writer`。
- **写满**：`QuotaExceededError` 出现在 `put` 上，或者提交时的 `tx.error` 里，都归为 `quota`；整个事务回滚，原记录与高水位都不变。存储层如实交回，重试的节奏归 P2。Chromium 写满之后用量要过一阵才降下来，这期间连小的写入、登记也写满。
- **保留期**：
  - 14 天，常量 `LOCAL_DRAFT_RETENTION_DAYS` 在契约里，服务端修订记录保留期的下限由它推出（+1，数值仍是 15）。
  - 清理按记录里**读得出的** `updatedAt` 判断，不论格式：形状不对、由更新的页面写的，只要读得出且超过 14 天就一并删，交回的键标明是哪一种；读不出的留给打开文档时（P3）、本机草稿页（P4）说明并删。
  - 写入者登记超过 14 天、又没有草稿时一并删。连续开着超过 14 天的页面因此可能遇到一次 `not-writer`，经服务端核对之后 `force` 重新登记，不丢数据。

### 记录格式与加密

- **加密**：格式版本 `recordVersion = 1`，比本页认识的新 → `newer-format`，不动它。AES-GCM-256，每条 12 字节的随机 IV，同一把密钥不重用 IV（重封一律换新的 IV）。
- **AAD**：UTF-8 的 JSON 数组，第一项是格式标识 `"nerve-office/outbox-draft/v1"`，之后按固定的字段表排列全部明文元数据（内容的格式与在途的请求各展开成固定顺序的子数组）。字段表在类型上与元数据的键一一对应，加字段而忘了进 AAD 就过不了类型检查；改动任何一个明文字段，解密都失败。加密有已知答案测试钉住格式，期望值另用 `node:crypto` 核对。
- **读出时的形状核对**：
  - 字段的类型与范围；
  - 字节紧凑；
  - 在途的序号不大于草稿序号。反过来的记录在恢复时会把旧内容当"自己追自己"接到服务端更新的那一版上，静默退回别人已存的修改。
  - 不合格的读成 `malformed`。
- **解不开的归类**：记录的密钥版本小于当前的版本 → `revoked`（密钥已吊销，ADR-019 的版本连续）；否则 → `corrupted`（已损坏，包括被改过）。非认证失败的错误照常向上报，不归进这两类。

### 写入管道（`DraftWriter`）

- **一个接口，两种宿主**：进程内的实现（`createDraftWriter`）与发件箱 Worker 的客户端都实现 `DraftWriter`。编辑器页只依赖接口；放在 Worker 还是主线程，只换宿主（见最后一节）。
- **写入**：
  - 主线程只做 `save()`、序列化与一次编码，字节交给管道。管道按文档排队：去重（`save()` 原文的 SHA-256 连同"公式待更新"，与上次写入的相同、并且这次允许去重就交回 `unchanged`）→ gzip（内存里的流，不经 Blob）→ 加密 → 写入。
  - 压缩之后的每一种结果都带着 gzip 的字节（写满、没有密钥、库用不了、被栅栏拒绝时上传照旧，不必再压一次）。
  - 一次没写成之后，去重的起点作废：那一份照样会上传，服务端可能已不是上次写下的内容。
- **在途的请求**：上传发出之前先把 `inFlight`（请求标识、客户端实例、序号、发出时刻）重封进记录、落盘；上传在途时写下的新一份接着带上它，崩溃之后恢复才认得出"自己追自己"。库里的那一份比在途的旧时不标。
  - 只记这四项：原样重放只在"记录还是在途的那一份"时做，这时公式标记、构建与数据格式就是记录本身的。
  - 能否原样重放看 `canReplayAsSent`：在途的就是这一份，并且发出不满 14 天（服务端修订记录与回执的保留期至少 15 天）。
- **换密钥**：心跳得知新的版本之后（P2 接），用新密钥重封本页写下的草稿；没能重封的（例如手里没有最新的内容、又解不开）交回清单，由调用方用新密钥写一份新的。
- **发件箱 Worker**：
  - 协议带版本，用手写的守卫，不引用 zod（门禁按全部产物数 zod 的 JIT 探测）。
  - Worker 里的处理注入存储与时钟。
  - 客户端按 id 对应、每个请求有看门狗时限；到点、`error`、`messageerror`、终止时，在途的全部以失败结束，之后立即失败。
  - 写入的字节与交回的 gzip 都放进 transfer。
  - Worker 启动时开一个 100 ms 的空定时器（DEF-011）。

### 本机密钥的客户端

- **取用**：`fetchLocalKey`：`POST /api/local-key`（请求层自动带 CSRF）→ 契约校验 → base64 解成恰好 32 字节 → `importKey('raw', …, false, ['encrypt', 'decrypt'])` → 原始字节在 `finally` 里清零。导入单独成不引用 zod 与请求层的模块 `local-key-import.ts`。`atob` 的结果与响应的 JSON 文字清不掉，与 DEF-068 同一类。
- **保管者**（`createLocalKeyKeeper`）：
  - 同时只有一个取用在途；
  - 会话类失败交给页面确认会话，只有连着的第一次在确认之后立即重试；
  - 500、网络与时限按"暂时取不到"退避，不重试成风暴；
  - 心跳带来的版本不同就停用旧的、重取；
  - 退出登录、换人时 `discard()`，取用期间被丢掉的那一次交回 `discarded`，不交给调用方；
  - 计时都经注入的时钟。

### 测试构建里的探针

- 浏览器层的测试经编辑器页：测试构建的 e2e 分支在地址带 `outboxProbe` 时动态引入探针，挂上 `window.__nerveOutboxProbe`；不新建测试入口页（M3-P2 复核 B4）。门禁登记测试专用的来源、产物与禁用关键字。
- **探针不引用请求层与 zod**：探针一引用请求层，测试构建就把请求层连同 zod 与契约的错误结构拆进一个新的共享分块，而且先于 `zod-jitless` 求值，这正是会出 CSP 违规的那一类。所以：
  - 探针自己发取钥匙的请求；
  - 两份构建的入口的静态闭包模块集合核对相同；
  - lint 的区域规则把探针目录列进"不许引用 zod 与请求层"。
- **覆盖率**：IndexedDB 的接线（`database.ts`、`draft-store.ts`、`draft-index.ts`）、Worker 的薄入口与探针，不计入单元覆盖率，由三个浏览器的浏览器层用例覆盖，理由与编辑器适配层相同（规范 §8.3）。判定逻辑全部是纯函数，在单元测试里测。

### 放置与真实浏览器上的结论

（P1 的真实浏览器复核之后补：发件箱放在 Worker 还是 WebKit 改在主线程、空定时器是否有效（DEF-011）；不可导出的 `CryptoKey` 能否经 `postMessage` 交给 Worker，不行就改为在 Worker 里导入；`durability: 'strict'` 在 Safari 上是否支持；持久目录与真实 Safari 上的写入耗时与 `strict` 的开销。）

## 备选方案与取舍

- **单元测试用 fake-indexeddb**：没采用。它模拟不了配额与"事务里 await 别的异步就自动提交"，权威的结论仍要在真实的浏览器里得到；判定写成纯函数在单元测试里测，IndexedDB 的接线由三个浏览器的浏览器层覆盖，不新增依赖。
- **写入者存租约令牌**：没采用。令牌在浏览器的存储里就能被同一台设备上的人拿去写服务端；栅栏只需要"这一代、这次登记"的身份。
- **内容与状态分两条记录（状态另做认证）**：没采用。标记在途、确认之后改基准都要重封整份内容，但加密 5 MiB 只要几毫秒；一条记录、一份 AAD 更简单，也不会出现内容与状态对不上。
- **发件箱只能放在 Worker**：没采用。写入管道与放置无关，真实 Safari 上 Worker 有停顿时可以换宿主，不改管道。

## 影响

- **P2（接入保存管道）**：
  - 序号在 `save()` 的同步段里从高水位往上分配；
  - 取得编辑权并拿到本机锁之后登记写入者，`superseded` 与 `not-writer` 经服务端核对处理（含连续开着超过 14 天的页面）；
  - 上传发出之前先等 `markInFlight` 落盘；
  - 写满之后页头一直说"本机存储空间不足"、每次捕获照常再试；
  - 换密钥之后没能重封的用新密钥写一份；
  - 新 Worker 的体积预算在生产构建里登记；
  - 编辑器页的生产代码引用 `local-key.ts` 时，再核对一次两份入口的静态闭包。
- **P3（恢复）**：
  - 判定读 `ReadDraft`、`DraftRead` 与 `canReplayAsSent`；
  - 接手别的写入者留下的草稿用 `adoptSeq`；
  - 原样重放成功之后用 `removeDraft(key, expectedSeq)` 删；
  - 判定表同样核对"在途的序号不大于草稿序号"。
- **P4（本机草稿页与清理）**：
  - 本机草稿页用 `listDrafts`（认不出的也列出键）与保留期清理交回的键；
  - 退出登录、账户停用用 `removeUserData`；
  - 列表的标记只引用 `draft-index.ts`，并且按需加载（平台首屏的余量约 4 KiB）。
- **测试**：崩溃用例的工具与跑法见 M4-P1 设计 §3.7；E2E 与集成测试的测试库按主机标识命名，只清理本主机建的。
