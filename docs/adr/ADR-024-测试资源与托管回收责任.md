# ADR-024 测试资源与托管回收责任

- 日期：2026-10-28
- 状态：用户批准方案 B，实施及验证中；P4 尚未关闭
- 范围：测试工具与 CI，不改变产品存储或业务数据生命周期

## 背景

历史测试将完整 VM、浏览器资料和重复环境永久放入 handoffs，导致目录曾累计约 175 GB。受管运行器已在本机实行创建前登记、独立临时目录、进程/句柄检查、有界诊断、失败期限及报告限额。

实际 GitHub Ubuntu 24.04 预检又发现，lsof 的全宿主未知 socket/内核对象会在测试尚未启动时阻止目录清理。它不能证明这些记录没有本轮路径。继续逐协议或 PID 放行会模糊删除权限，完整跨 namespace 观察则引入新的特权边界。用户在 `63cccb69` 事实报告之后明确批准方案 B。

## 决策

本机、普通 Linux、自托管和未知环境继续严格回收。仅固定的 GitHub 托管一次性 VM，显式策略及创建前 repo/run/attempt/job/runner/boot/SHA 绑定成立后，可将原环境留给 job VM 生命周期。环境变量是执行契约，不是密码学宿主证明。

测试结果与资源处置分开：`passed/failed/interrupted` 保留原退出事实；`host-disposal-pending` 和 `cleanupComplete=false` 表示等待平台回收，不表示清理完成、全局无引用或测试通过。本项目没有独立观测 VM 最终销毁。

未知引用继续阻止原目录的手工删除、搬迁或精简。只有本轮生产者与输出线程退出、无已知本轮引用、报告归属与字节稳定性核实，才复制必要证据。固定发布口持锁，发布副本按 inode、清单与摘要验证；缺失持久化回执或部分发布不能重新自签通过。

同 job 原环境按两秒采样实施 16 GiB 停止阈值，独立保留 12 GiB 磁盘余量；阈值不是配额，采样与终止期间可能超调。报告合计 5 GiB、artifact 14 天，诊断沿用 4 MiB/文件、16 MiB/用例、64 MiB/轮。文件/目录/省略项及 manifest 自身也有容量限制，避免零字节条目绕过保护。压缩运输属于本轮报告资源，另行登记并核对原清单的成员与摘要，不改签稳定清单，也不回退上传原始环境。

## 实施与后果

`hosted.py` 负责固定身份与只读预算；`stable_reports.py` 负责非破坏导出；Run/Store 保持锁、根身份、进程和发布职责；`check_ci_resources.py` 负责当前 job 的报告接收。预检收据只供诊断，上传允许产品失败的合格证据，但原失败步骤不变绿。完整流程及实际入口见[测试资源规范](../testing/test-resource-lifecycle.md)。

新 CI 证据必须绑定实际同 SHA 六项 jobs、下载原件及新资源合同。本地最终验收仍要求实际 cleanup complete；旧 full12/container02 与 v2 关闭证明保持冻结。先小型回归和独立审查、实际 CI 能力核验，再串行执行最终源码的完整本机/容器门禁和关闭流程。
