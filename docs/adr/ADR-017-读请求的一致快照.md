# ADR-017：读请求的一致快照

> 状态：已接受｜日期：2026-10-03｜来源：M2 收尾，合并之前 Codex 的 M 级对抗评审 CX1（`docs/v0.1/M2-组织空间与权限/reviews/M2-对抗评审-Codex.md`）｜修订：同日，修复之后的独立复验——快照进行中连接池上的查询一律报错（必须修 1）、开场核对另核对会话（建议 3）；2026-10-04，M3-P1：受编辑租约保护的写请求同样在事务里再核对登录（ADR-018）；同日，M3-P2：读取内容的条件请求与编辑状态的 `canEdit` 都在读快照里（见文末）

## 背景

- US-M2-14 与 A03：无权访问的对象不暴露；停用、移出空间、取消分享之后，下一次请求即生效（ADR-014）。
- 原来的读接口先判断权限，再另查数据，用的是连接池上各自自动提交的语句。在 PostgreSQL 的 READ COMMITTED 下，每条语句看到的是它执行那一刻的数据。
- 一个读请求判断完权限、读数据之前，如果别人撤了它的权（取消授权、移出空间、停用账户）并随即写入，这个在途的请求会把撤权之后才出现的数据带出去。Codex 在真实的 HTTP 与数据库上用确定的交错复现了三种：
  - 读正文：取消授权之后保存的新修订；
  - 读正文：移出空间之后保存的新修订；
  - 搜索：移出空间之后新建的文档。
- 这不是"请求开始时有权、返回当时的旧数据"：那些数据在这个人有权的时候根本不存在。
- 既有的测试都没有覆盖这种交错：
  - 撤权的生效时机只验证"撤权提交之后的下一个新请求"；
  - 矩阵与"看不到 / 不存在"的对照比较的是固定角色与失败的路径，不会产生"旧授权 + 新数据"的成功响应。
- 写接口不在此列：它们在事务里先判断、再加锁、锁下复核，撤权的一方取的锁与它们互斥（ADR-014 的锁顺序）。在途的保存与撤权不互斥，是 M3 租约的事（ADR-014、P2 设计 §7）。

## 决策

### 保证

每一个登录之后的读请求（全部 GET 接口），响应是数据库某一时刻的一致视图，而且在那一时刻，这个人有权看到响应里的全部内容。

- 权限依据的事实与返回的数据出自同一个快照。这些事实包括：这条会话仍然有效、账户仍然有效、调用者仍是系统管理员（守卫读到是的话）、空间角色、单独授权、归档状态、对象是否存在。
- 可以返回撤权之前那一刻的数据，或者拒绝；不会返回撤权之后才出现的数据。

### 机制

1. **只读快照**：`TransactionRunner.readSnapshot(work)`。
   - 借一个连接，`BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`，先执行登记的开场核对，再执行 work，最后 COMMIT。REPEATABLE READ 的快照取在第一条语句上。
   - 不往 CommitLedger 记提交：只读，没有写入生效这回事。
   - 连接归还的规则与 `run()` 一致：业务错误回滚后放回，其他失败丢弃。
2. **一个请求只开一个快照**：
   - 快照在最外层的服务里开（workspace、admin 的编排层，或者 documents、users、auth 的服务），内层方法接受事务参数。
   - 快照里再开快照或写事务直接报错（`NESTED_IN_SNAPSHOT_MESSAGE`）：另借连接会在连接池满时与外层互相等待。
   - 这个标记只在快照还没结束时生效：快照里排下、结束之后才执行的事务照常。标记在 database 模块共用的 `SnapshotScope` 里（每个应用实例一份），事务运行器与连接池用同一份。
3. **快照进行中，连接池上的查询与借连接一律报错**（`POOL_IN_SNAPSHOT_MESSAGE`，`pool.ts` 包装连接池的 `query` 与 `connect`）：快照里的语句都在快照借出的连接上，经连接池的就是快照之外的语句——仓储的读方法漏传快照的事务（`executorOf` 退回连接池），或者仓储直接用连接池的写法。它们读到的是此刻最新的数据，权限判断与读数据又分开了。原来这样漏传是悄悄的：修复之后的独立复验去掉三处事务参数（搜索取文件夹路径、文档列表按文件夹过滤、审计补空间名称），整套测试都没发现。现在测试与 E2E 里立刻失败，生产里是意外错误（500）——宁可失败，不越权。
4. **快照里的语句逐条执行**：pg 在一个连接上排队执行查询的做法已经弃用（pg 9 去掉）。同一个事务或快照上不用 `Promise.all`。
5. **会话守卫判断过的事实进快照**：守卫在处理器之前、在连接池上判断会话有效、账户有效与系统角色，这之后到快照开始之间（还包括守卫读账户、顺延会话，快照取连接的时间，这几步各有取连接、等锁的时限，负载下合计可以是数秒），会话可能被撤销、账户可能被停用、系统角色可能被取消。
   - 守卫认证通过后，把这个请求的身份（会话 id、账户 id、读到的系统角色是不是管理员）记在请求级的记录里：auth 模块的 `RequestIdentities`，AsyncLocalStorage 加中间件，与 CommitLedger 同一个做法。
   - auth 模块在初始化时向 database 登记快照的开场核对（`registerSnapshotOpening`，只能登记一次）。这是控制反转：database 不依赖 auth、users。
   - 开场核对是快照的头两条语句（第一条同时确定快照的时刻）：
     - 这条会话仍然有效（没有撤销、没有过期），否则 `SESSION_EXPIRED`——签发重置正是拿"撤销这个人的全部会话"踢出入侵者，这时账户仍然有效；
     - 账户仍然有效，否则 `SESSION_EXPIRED`；
     - 守卫读到是系统管理员的请求，仍是系统管理员，否则 `PERMISSION_DENIED`。
   - 不只看"这个接口是不是只给系统管理员"：没有加入的系统管理员看得到团队空间的成员，管理面的权限位也按系统角色给。
   - 守卫之后刚被授予系统管理员的不拒绝：他仍按普通成员判断，看到的只会更少。
   - 不在请求里（命令行、定时任务）、公开的接口：没有身份，什么也不做。
   - 守卫原有的判断照旧，作为提前拒绝、处理 Cookie。
   - 会话与账户分属 auth、users 两个模块的表，开场核对用两条按主键的语句，不跨模块联表。
   - 换令牌（同一个浏览器重新登录、在这个浏览器里修改密码）之前发出、之后才进快照的请求，开场核对回 `SESSION_EXPIRED`、不动 Cookie，与守卫对这种请求的回答相同；前端收到之后重新确认会话，还是同一个人就换上新会话，页面不动。
   - 守卫之后、快照之前被取消系统管理员时，这一次的全部 GET（包括会话信息）都回 403，前端显示没有权限、可以重试；时机极少，接受。

### 自动核对

- 确定交错的回归用例，在判断完权限、读数据之前停住：
  - 读正文时取消授权、读正文时移出空间、搜索时移出空间——三条由 Codex 的探针改写；
  - 守卫之后停用账户、取消系统管理员、撤销这条会话（签发重置、本人退出）；
  - 没有加入的系统管理员看成员列表时被取消系统管理员。
  - 用例在 `tests/integration/src/permissions/read-snapshot.test.ts`。
- 按路由表的结构性核对（`tests/integration/src/api/read-snapshots.test.ts`）：对每个登录之后的 GET 接口发一次能成功的请求，按语句与发出它的连接断言：
  - 快照之前只有守卫的语句；
  - 恰好一个 REPEATABLE READ READ ONLY 快照，开场核对在最前（按会话 id 查会话、按 id 查账户），其余语句都在同一个连接上；
  - COMMIT 之后再没有语句。
  - 新加的 GET 接口要在用例的请求表里登记、走快照，否则失败。
  - 豁免只有两个公开的健康检查。
- 集成测试每条用例之后核对：应用的一个连接上没有并发过查询（`tests/integration/src/support/single-query.ts`）。
- 结构性核对每个接口只发一组参数，走不到的分支由第 3 条的运行时拒绝兜住：整套集成测试里任何一条走到快照里漏传事务的分支，请求就失败。运行时拒绝本身有单元与集成用例（`database/pool.test.ts`：快照里查询、借连接都被拒绝，快照之外、结束之后照常，真实管线里回 500）。

## 备选方案与取舍

- **请求级的环境快照**：中间件为每个 GET 开快照，仓储在没有显式事务时自动用它。新接口不用记得开快照；但会把"仓储用哪个连接"变成隐式的，偏离"事务显式传给仓储"的约定（规范 §1.2）。守卫里还要有写（会话顺延），要专门绕开只读快照。没有采用。
- **每个响应末尾再查一次权限**：只能发现撤权，发现不了"撤权之后写入、又在撤权之前判断"的新数据，也要每个接口各写一遍。没有采用。
- **把权限条件并进读数据的那一条 SQL**：只对少数查询可行（正文、目录要跨几张表、几个模块），不是通用的做法。"与我共享"已经这样做（集合、标题与授权角色同一条语句），仍在快照里。
- **只修 Codex 的三个探针**：同一个根因在全部读接口上，只修三处会留下其余的。

## 影响

- **代价**：每个 GET 多四条语句（BEGIN、开场核对的两条、COMMIT）；处理器执行期间占住一个连接（原来是每条语句各借一次）。连接池的大小（`NERVE_DATABASE_POOL_MAX`，默认 10）按"同时在途的请求"估算，M7 的压测核对。
- **约束**：
  - 新的 GET 接口在最外层的服务里开快照，内层方法接受事务参数，不嵌套；
  - 快照里的语句逐条 await，读方法都传快照的事务（漏传在运行时报错）；
  - 结构性核对的请求表要登记新接口。
- **不在此列**：
  - 写接口的在途保存与撤权（M3 租约）；
  - 公开的一次性链接查询（没有登录的身份可以在快照里复核，凭的是令牌本身，ADR-013）；
  - 健康检查。
- 规范 §5 写明这条规则；ADR-014 的"看不到与不存在""撤权"两节引用本 ADR。

## M3-P1 的补充：写请求里的登录再核对

本 ADR 原来把写接口排除在外，理由是"撤权的一方取的锁与它们互斥"。撤销登录（退出、签发重置、修改密码）与保存之间没有共同的锁，这个理由在编辑租约这里不成立（M3-P1 审查 A1）：守卫之后还隔着上传正文与等锁。所以持有者自己的请求——保存、心跳、申请编辑权——在事务里按主键再查一次这次登录，失效时回 401 `SESSION_EXPIRED`，不动 Cookie，与本 ADR 的开场核对同一个说法（ADR-018）。其他写接口照旧：它们在锁下复核的是权限，撤权的一方取的锁与它们互斥。

## M3-P2 的补充：条件请求与编辑状态的 `canEdit`

- 读取内容的条件请求（ADR-011 的补充）不改变"读快照"的规则：304 同样恰好一个只读快照、开场核对在最前，先判断权限再比较修订号，修订号对得上时不读内容（读快照的请求表另有一条用例核对）。
- 编辑状态（`GET /api/documents/{id}/edit-lease`）的 `canEdit` 用判断能读时算出的权限位，与详情的 `permissions.canEdit` 同一个规则、同一个快照，不多一条查询。
