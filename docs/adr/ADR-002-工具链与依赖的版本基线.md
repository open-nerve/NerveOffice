# ADR-002：工具链与依赖的版本基线

> 状态：已接受｜日期：2026-09-26｜来源：M1-P1（M1 总设计 §2.2）

## 背景

- 00 号计划书 §1.3、§9.2 要求 M1 锁定 PostgreSQL 的大版本与镜像，并确定工具链。
- 需求方希望与 opennerve 仓库大体一致。审批 M1 总设计时明确："无需严格一致，差不多就行，按最佳推荐"。
- 部分依赖正处在大版本交替期：NestJS 12 在 2026-08-27 发布，改为纯 ESM，11 转为 legacy；Vitest 5 在 2026-09-03 发布。
- pnpm 12 是 Rust 重写的版本：
  - 用 `allowBuilds` 逐项决定安装脚本；
  - 显式配置 `minimumReleaseAge` 后默认严格拦截；
  - 拒绝 `pnpm-workspace.yaml` 里无法识别的设置。

## 决策

**原则**：
- 工具组合与代码风格与 opennerve 一致，版本号不强求一致。
- 取各依赖当前的稳定大版本；补丁取发布满 3 天的最新版，全部精确锁定。
- 新的大版本发布不满两个月时：
  - 上一个大版本仍在正常维护，就先用上一个大版本；
  - 上一个大版本已转为 legacy，就用新的大版本，并在第一次使用它的 Phase 开头先验证。

**锁定方式**：
- 外部依赖的版本集中写在 `pnpm-workspace.yaml` 的默认目录（`catalog`）里，各包写 `catalog:`；内部包写 `workspace:*`。门禁 `gate:pins` 检查。
- Node.js 的版本写在 `.node-version`；pnpm 的版本写在根 `package.json` 的 `packageManager`。
- 容器镜像按多架构索引的摘要引用。

**基线**（2026-09-26）：

| 类别 | 依赖 | 版本 | 说明 |
|---|---|---|---|
| 运行时 | Node.js | 24.21.0 | ADR-001；Node 22 在 2027-04-30 停止维护 |
| 包管理 | pnpm | 12.6.0 | Node 自带的 corepack 0.36 运行不了 pnpm 12 的包结构，本机与 CI 都不经 corepack 安装 |
| 语言 | TypeScript | 6.0.3 | Univer 1.0 与 NestJS 12 的命令行工具都用 6.0；typescript-eslint 还不支持 TypeScript 7 |
| 前端 | React / Vite / @vitejs/plugin-react | 19.3.0 / 8.3.0 / 6.1.1 | M0 用这组版本验证 |
| 测试 | Vitest / Playwright | 4.1.11 / 1.63.0 | Vitest 5 发布不满一个月，4.1 支持 Vite 8；Playwright 1.63 自带 Chromium 153、WebKit 26.6 |
| 规范 | ESLint / @antfu/eslint-config / eslint-plugin-boundaries | 10.11.0 / 9.5.1 / 7.2.0 | 另有 eslint-plugin-import-x（循环依赖）、eslint-plugin-jsx-a11y（无障碍）、eslint-plugin-playwright |
| 钩子 | lefthook / lint-staged | 2.1.14 / 17.5.1 | |
| 校验 | zod | 4.6.5 | |
| 数据库 | PostgreSQL | 18.6（`postgres:18.6-alpine`，按摘要） | 支持到 2030 年 11 月；新库使用内置的 `C.UTF-8` 排序规则，并默认开启数据页校验和 |
| 后端（M1-P2 起） | NestJS / Nest CLI / drizzle-orm / pg / pino / pino-http | 12.1.0 / 12.0.5 / 0.45.3 / 8.23.0 / 10.3.1 / 11.0.0 | NestJS 12 的验证通过（ADR-004）。Nest CLI 12.0.7 发布不满 3 天，用 12.0.5；不用 nestjs-pino（ADR-004） |

**不用 Prettier**：@antfu/eslint-config 本身就格式化 TypeScript、JavaScript、JSON 与 YAML，再加 Prettier 两个工具会互相改写。Markdown 文档是手写的，不做格式化。

**与 opennerve 不同的地方**：

| 项目 | opennerve | 本项目 | 原因 |
|---|---|---|---|
| Node.js | 22 | 24 | 见上 |
| 包管理 | npm（各子项目独立） | pnpm workspace + catalog | 严格的依赖隔离支撑模块边界；A01 的供应链检查依赖 pnpm 的设置 |
| 前端框架 | Vue 3 | React | Univer 的视图层是 React |
| 密码哈希 | bcrypt | Argon2id | 00 号计划书 §11.1 |
| PostgreSQL | 16 | 18 | 支持期长两年，客户自部署时升级大版本的代价高 |
| 格式化 | ESLint + Prettier | 只用 ESLint | 见上 |

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| A. 各依赖取当前的稳定大版本，工具组合与 opennerve 一致 | 采用 | 新项目避免一开始就背上大版本升级（尤其是 NestJS 的 ESM 迁移）；需求方确认版本不必严格一致 |
| B. 版本号与 opennerve 严格对齐 | 否决 | 会用上已转 legacy 或即将停止维护的版本（NestJS 11、Vite 7、Node 22、PostgreSQL 16），很快又要整体升级 |
| C. 一律追最新的大版本 | 否决 | 刚发布的大版本（Vitest 5）生态还没跟上，没有必要冒这个险 |

## 影响

- 升级：同一条主次版本线内的补丁可以随时升级，尤其是安全修复；跨主次版本的升级，要修订本 ADR。
- 发布冷却期：新发布的版本满 3 天才能安装。紧急的安全修复需要豁免时，写进 `minimumReleaseAgeExclude`，注释里写原因（`gate:config` 检查）。
- 安装脚本：新增依赖如果带安装脚本，pnpm 会直接失败，必须在 `allowBuilds` 里明确允许或拒绝，并写原因。
- 本机环境：开发者用 nvm 安装 `.node-version` 指定的 Node，用 `npm i -g pnpm@<版本>` 安装 pnpm。
