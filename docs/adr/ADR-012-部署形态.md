# ADR-012：部署形态

> 状态：已接受｜日期：2026-09-28｜来源：M1-P5

## 背景

- 00 号计划书 §9.1、§12.4：浏览器同源访问模块化单体；迁移不在应用启动时自动执行；§11.3：安全头由应用统一下发。
- M1 总设计 §2 决策 1、5、6 与 §6.2：M1 交付可以部署到测试环境的形态（应用 + PostgreSQL 18 + HTTPS 的反向代理），首个管理员用命令行初始化；正式的部署包、备份恢复、升级演练与运维手册在 M7。
- P2 起应用已经具备部署的前提：配置只来自环境变量（`NERVE_*`，机密可以用 `_FILE`），存活与就绪探针，SIGTERM 时优雅退出（时限 8 秒），迁移是单独的命令，托管前端产物（同源）。
- 审计表只追加的保护靠触发器（ADR-005）：应用的数据库角色若是表的所有者或超级用户，就能关掉触发器（P2 审查 A21）。
- 登录限流按客户端地址计数（ADR-007）：反向代理的信任设置配错时，所有人都算成代理的地址（DEF-014）；哈希的排队没有上限时，洪水下延迟与内存一直增长（DEF-015）。

## 决策

**一个镜像，多阶段构建**（`deploy/Dockerfile`）：
- 基础镜像 `node:24.21.0-bookworm-slim` 按摘要锁定，与 `.node-version` 一致；构建阶段用与 `packageManager` 相同版本的 pnpm，按锁文件安装；
- 运行镜像只有 Node、api 的生产依赖（单独一次 `pnpm install --prod`）、后端与 contracts 的构建产物、前端的生产构建；不带 pnpm、npm、corepack 与源码；
- 非 root（`node`）运行，健康检查用 Node 自带的 `fetch` 请求就绪探针；服务端的第三方许可清单随镜像生成，缺许可正文的包由 `apps/api/third-party-licenses/` 补齐，`licenses` 门禁提前核对；
- 镜像引用一律按摘要锁定，同一个镜像在开发库、测试环境与 CI 里引用得完全一样（`pins` 门禁）。

**应用同源托管，反向代理只做 TLS 与转发**：
- 一个应用容器托管前端页面与 `/api`；CSP、HSTS（只在 HTTPS 请求上）等安全头、Cookie、缓存策略都由应用下发；
- 测试环境用 Caddy：`tls internal`；不压缩（内容接口直接下发 gzip 字节）、不替客户端解压；请求体上限 6 MB；就绪探针对外 404；到应用的空闲连接 4 秒回收（应用是 5 秒）；去掉 `Server` 与 `Via`；转发头用 Caddy 的默认值（不采信客户端带来的 `X-Forwarded-For`）；
- 应用 `NERVE_TRUST_PROXY=1`，只信任紧挨着的一跳；前提是应用的端口只有代理连得到。公开地址是 HTTPS、经代理转发来的请求（带转发头）却不是 HTTPS 时，每个进程记一条告警（DEF-014）。

**迁移是一次性任务**：同一个镜像执行 `node dist/cli/migrate.js`，用所有者角色；成功结束之后才启动应用（compose 的 `service_completed_successfully`）。

**数据库两个角色**（`deploy/sql/bootstrap-roles.sql`，数据库管理员在建库时执行一次）：
- 所有者：数据库的所有者，执行迁移、拥有全部表；
- 应用：只有连接、使用 schema、增删改查 `public` 里的表、读取迁移记录的权限；不是超级用户、不拥有任何对象，关不掉审计表的触发器，也执行不了 DDL；
- 迁移不写 `GRANT`：脚本用默认权限（`ALTER DEFAULT PRIVILEGES FOR ROLE <所有者>`）让所有者以后建的对象自动授权给应用；新库对 PUBLIC 不开放连接与临时表，排序规则用内置的 `C.UTF-8`；
- 两个密码经环境变量交给 psql（`\getenv`），不出现在命令行里；
- 应用启动时检查自己的角色：超级用户或审计表的所有者（及其成员）时记一条告警，不影响启动。

**登录洪水在应用里设上限**：等待密码哈希的请求超过 `NERVE_PASSWORD_HASH_QUEUE_MAX`（默认 64）或等待超过 `NERVE_PASSWORD_HASH_QUEUE_TIMEOUT_MS`（默认 5 秒）时，立即返回 503 与 `Retry-After`；没有验证的请求退回限流的名额、不写审计（DEF-015）。反向代理上按地址限速作为运维建议，随 M7 的运维手册落实（DEF-023）。

**测试环境与容器 E2E**（`deploy/test/`、`pnpm test:e2e:container`）：
- compose 的四个服务：`db`（PostgreSQL 18.6，第一次初始化时执行角色脚本）、`migrate`、`app`（应用角色、只读根文件系统、`/tmp` 用 tmpfs、`init`、去掉全部 capabilities、`no-new-privileges`、不发布端口、`stop_grace_period` 15 秒）、`caddy`（只发布 443 到本机回环）；
- 容器 E2E 用生产镜像、受限的数据库角色与 Caddy 的 HTTPS 跑 E2E 的外部模式（只依赖测试构建的用例按标签 `@test-build` 排除），并在测试之前核对两个客户端地址（本机与编排网络里各一次登录失败，审计记下的地址不同，也都不是 Caddy 的）；CI 的 `container` job 与 `verify` 并行。
- US-M1-10 的重启用例在本机与容器两种环境里都执行：强制结束后端（SIGKILL）再启动。

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| 反向代理托管前端、应用只提供 `/api` | 否决 | 安全头与缓存策略要在两处维护，CSP 已经定稿由应用下发（§11.3）；多一个要构建与发布的产物 |
| 应用启动时自动迁移 | 否决 | ADR-005：多实例会并发执行；不可逆的迁移要先备份 |
| 应用直接用所有者或超级用户连接 | 否决 | 能关掉审计表的触发器，只追加的保护形同虚设（审查 A21） |
| 每次迁移之后补 `GRANT` | 否决 | 迁移里要写部署决定的角色名；漏补一次，应用就在生产上报权限错误 |
| 自己编译带限速插件的 Caddy | 否决 | 给测试环境引入额外的供应链；应用层的上限已经挡住"排队无限增长"这个实际的危害 |
| 容器 E2E 用测试构建的镜像 | 否决 | 测的就不是发布的东西；只依赖测试构建的 3 条用例按标签排除，它们在本机模式里照常执行 |
| distroless 或 Alpine（musl）的 Node 镜像 | 暂不采用 | 基础镜像已在 M1 总设计 §2.2 定为 `bookworm-slim`；换成 musl 要另行验证原生模块（Argon2）与域名解析的行为，distroless 里没有 shell，排查不便。体积在 ADR-001 的实测里可以接受，M7 再评估 |

## 影响

- **配置**：新增 `NERVE_PASSWORD_HASH_QUEUE_MAX`、`NERVE_PASSWORD_HASH_QUEUE_TIMEOUT_MS`。部署时 `NERVE_PUBLIC_ORIGIN` 用 HTTPS 的公开地址，`NERVE_TRUST_PROXY` 按代理的跳数配置。
- **数据库**：新的部署先执行 `bootstrap-roles.sql`，迁移用所有者、应用用应用角色；新增的对象类型（视图、函数等）若应用要用，先确认默认权限覆盖到，并在部署说明里补上。
- **反向代理**：换用别的代理时满足部署说明的要求（信任边界、不压缩、请求体上限、空闲连接回收、就绪探针不对外）。
- **E2E**：新用例若只在测试构建里成立，打上 `@test-build` 标签；外部模式不能跳过别的用例。
- **M7**：部署包、备份与恢复、升级与回滚演练、滚动发布与退出前的摘流量、按地址限速（DEF-023）、镜像的发布与签名、镜像的精简（ADR-001）。
