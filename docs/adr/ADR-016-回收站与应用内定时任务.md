# ADR-016：回收站、删除单元与应用内的定时任务

> 状态：已接受｜日期：2026-09-30｜来源：M2-P4

## 背景

- 00 号计划书 §5.3：删除的文档或文件夹进所在空间的回收站；删除者与空间管理员可以恢复；编辑者只能删除本人创建的文档，以及里面只有本人创建的文档的文件夹；空间管理员可以永久删除；30 天后自动永久删除。
- M2 总设计 §6.8：以"删除单元"为粒度；恢复回到原位置，原来的父文件夹不在时回到空间的根目录；永久删除连同内容、修订记录与单独授权；定时清理由 `jobs` 模块做，用 advisory lock 防止将来多实例重复执行，测试用可控的时钟。
- 已有的约束：应用容器跑在受限的数据库角色下（只有增删改查，ADR-012）；迁移是独立的一次性任务；仓库里此前没有任何定时任务，"已过期"一律在查询时判断（登录时顺带清理过期会话是唯一的例外，且不改状态）。
- M2-P4 的实现现状：同一个空间里的结构性改动由"空间树的 advisory lock"串行（P4 设计 §3.4 第 2 条）。

## 决策

### 1. 删除单元

一次删除产生一个删除单元（`trash_entries` 一行），内容是**一份文档**，或**一个文件夹连同它当时正常状态的全部子孙**。删除单元记下空间、种类、删除者、删除时间、到期时间（删除时间 + 30 天）、被删对象的原位置与标题。被删的行 `status='trashed'` 且 `trash_entry_id` 指向它（两列由 CHECK 绑定，必须同时写）；文档的 `write_epoch` 加一。

**已有的删除单元不重组**：子树里早先单独删过、已经在回收站里的东西留在原来的单元里。"一起删的一起恢复"——早先那次删除是另一个人、另一个时间点的决定，不该被后来的删除改变。

**永久删除有连带**：删掉一个单元时，子树里属于别的单元的行也一并永久删除（它们的原位置随之消失，恢复没有意义），变空的单元一起清掉。

**跨空间移动时删除单元跟着走**：文件夹的子树换空间时，完全落在子树里的删除单元改登记空间。由此保持一条不变量——**一个删除单元不会被拆散在两个空间**。

### 2. 权限

- 删除：空间管理员任意；编辑者只能删本人创建的文档，以及"子树里正常状态的文档全部是本人创建的"文件夹。**第二个条件在锁下用一条计数语句判断**，不进纯函数：展开子树之后仍可能有人往里移进别人的文档。
- 恢复：先要有**编辑者及以上**的有效角色（恢复是把内容放回空间里，属于改动），再看是不是删除者本人或当前的空间管理员。按**当前**权限算：删完之后被移出空间的人不能再恢复，被降为查看者的人也不能（S7 补权限矩阵时发现原来漏了这一条）。
- 永久删除：空间管理员（个人空间的所有者）。
- 归档的空间里所有人至多是查看者，所以删除、恢复、永久删除都不能做。
- 回收站里的东西对普通接口一律"不存在"（打开、保存、改名、移动、复制、再删除都是 `NOT_FOUND`），也不出现在列表与搜索里；回收站的列表则对看得到空间内容的人可见（这些标题他本来就看得到）。

### 3. 应用内的定时任务（`jobs` 模块）

**新模块只做"按时触发 + 防重复执行"**，删除的语义留在 `documents`：`jobs → documents` 单向依赖，`documents` 导出的清理入口由 lint 限定只有 `modules/jobs/**` 能引用（与 `DocumentTransferService` 只给 `admin` 同样的写法）。

- **触发**：模块自己的定时器（不引入调度框架），一轮结束才排下一轮（不叠加），±10% 抖动；进程退出时先停排程、再等正在跑的一轮收尾。
- **防重复**：每一轮先取会话级的 `pg_try_advisory_lock('nerve-office:trash-purge')`，拿不到就跳过这一轮。将来多实例（DEF-024）时，这把锁就是"只有一个实例在清"的依据。会话级的锁必须在同一个连接上取和放，而模块只拿得到连接池，所以在 database 模块加了与 `TransactionRunner` 同构的 `ExclusiveRunner`（借连接 → try lock → 执行 → 解锁 → 归还；出错就丢弃连接，会话结束即释放）。
- **一轮**：取一批到期的删除单元（默认 50），**逐个在各自的短事务里**永久删除，锁顺序与人工的永久删除完全相同（空间树锁 → 空间行 → 文档行 → 删除单元行），因此两者天然互斥；单个失败只记日志，不影响这一轮的其他条目。
  - **失败的条目暂缓**（M2-P6 复核）：原来每轮都取最早到期的一批，一直失败的条目永远排在最前，达到批量之后整个实例的自动清理就停了。现在进程里记住失败过的条目，连续失败 n 次就在之后 2^(n-1) 轮取批时让开它（上限约一天），后面到期的照常清理；成功、跳过或不再出现就清掉记录。重启之后重新尝试一次。错误日志带 `consecutiveFailures` 与 `deferredRounds`，M7 按它接告警。
  - **永久删除前核对要删的都在回收站里**（M2-P6 复核）：展开子树之后、删任何一行之前，数一遍正常状态的文件夹与文档；有就按意外错误回滚、不删（人工的永久删除回 500，定时清理记为失败并暂缓）。只要"正常的行不会挂在回收站的文件夹下"这条不变量被任何缺陷打破，原来会静默地永久删除正常的数据。
- **时钟**：`jobs` 提供 `Clock` 抽象，"是否到期"按时钟给出的时刻在 SQL 里判断（`expires_at <= $now`）。测试注入可控的时钟，不必等 30 天。**生产的时钟在每一轮开头取一次数据库的 `now()`**（M2-P6 复核：原来用应用主机的时钟，而到期时间是数据库算的；规范要求时间判断用数据库时间，主机时钟快多少就会提前多少永久删除）；取不到时这一轮按失败记日志。
- **第一轮**：启动后约 1 分钟（与间隔取较短的，带抖动）跑第一轮，之后按间隔（M2-P6 复核：原来要等满一个间隔，默认 1 小时，频繁重启的部署可能长时间不清）。
- **连接**：开启自动清理时连接池上限至少为 2（一轮占一个连接拿会话级的锁，删的时候要别的连接），配置校验检查（M2-P6 复核）。
- **审计**：操作者记为系统，来源是新增的 `job`（既不是 `http` 也不是 `cli`，审计里区分不出来会误导排查）。
- **配置**：`NERVE_TRASH_PURGE_ENABLED`（默认开）、`NERVE_TRASH_PURGE_INTERVAL_MS`（默认 1 小时）、`NERVE_TRASH_PURGE_BATCH`（默认 50）；排查数据时可以关掉，关掉期间到期的东西留着，重开之后下一轮一起清。

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| A. 删除单元 + 应用内定时任务（本 ADR） | 采用 | 恢复的语义清楚（一起删的一起恢复）；清理与人工操作共用同一套锁与同一段代码（M2-P6 复核之后，不判断权限的删除本体是 documents 内部的 `TrashEntryPurger`，不从入口导出，lint 拦住别的引用；人工的永久删除先判断权限再调用它，定时清理经 `TrashPurgeService` 调用它） |
| B. 不要删除单元，逐行标记删除时间 | 否决 | 恢复时无法判断"哪些是一起删的"：删了文件夹再恢复里面的一份文档，位置与语义都说不清 |
| C. 删除即物理删除，不做回收站 | 否决 | 00 号计划书要求 30 天可恢复 |
| D. 数据库的定时任务（`pg_cron`）或系统的 cron | 否决 | 要额外的扩展或宿主机配置，与"自部署、一套容器编排"的形态不符；删除的语义要在数据库里再实现一遍 |
| E. 引入调度框架（`@nestjs/schedule`） | 否决 | 只有一个任务，为它加一个依赖与供应链面不划算；自己的定时器加 advisory lock 已经够 |
| F. 清理任务用独立的容器（一次性任务，像迁移） | 否决 | 要多一套编排与镜像入口；应用内的一轮只用增删改查，受限角色够用。多实例时靠 advisory lock 而不是靠"只起一个容器" |
| G. 到期靠数据库的 `now()` 在 SQL 里直接判断 | 否决 | 集成测试就得等 30 天或改数据库时间；时钟注入之后一条用例几毫秒。M2-P6 之后生产的时钟取数据库的时间，两样都要了 |
| H. 永久删除时拒绝有"别的单元"的子孙，要求先处理 | 否决 | 对使用者是无法理解的报错；连带删除与"原位置已消失"的语义一致 |

## 影响

- `trash_entries` 是新表；`folders` 与 `documents` 各加 `trash_entry_id`，与 `status` 由 CHECK 绑定。永久删除时文档的内容与修订记录随外键 cascade。
- 每个空间的结构性改动（包括删除、恢复、永久删除与自动清理）都串行；保存文档内容不取这把锁，不受影响。
- M3 的编辑租约：删除与跨空间移动已经在同一事务里调收回写入权的入口（作用域支持一批文档），租约接进来时不必改调用点。
- P5 的单独授权：永久删除要连同 `document_grants` 一起删（那张表还没有，P5 建表时在同一处补上）。
- 升级要先执行迁移（审计的来源加 `job`），否则新应用写清理的审计会被数据库拒绝；顺序仍是备份 → 迁移 → 换镜像。
- 多实例（DEF-024）：清理已经用 advisory lock 防重复，滚动发布时不会两个实例同时清。
