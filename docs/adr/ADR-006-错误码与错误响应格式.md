# ADR-006：错误码与错误响应格式

> 状态：已接受｜日期：2026-09-26｜来源：M1-P2｜修订：2026-10-05，M3-P3：`CLIENT_OUTDATED`、`DOCUMENT_TOO_NEW`，`SNAPSHOT_INVALID` 带规则，503 的来源加上快照检查繁忙；2026-09-27，P4 加上可选的 `details`（加法）；2026-10-01，M2-P6 第 3 片复核：数据库繁忙回 503 带 `Retry-After`（请求里还没有事务提交时），已经提交过的回 500，带 `Retry-After` 的 503 记 warn

## 背景

- 规范对错误处理的要求：
  - 错误码在 contracts 集中定义，发布后语义不变、编号不复用；
  - 错误响应统一为 `{ "error": { "code", "message", "requestId" } }`，每个错误码对应固定的 HTTP 状态；
  - 意外错误对外只返回通用信息与请求标识，细节只写进日志（规范 §2.3、§4）。
- 没有读取权限的对象与不存在的对象返回相同的响应，不暴露对象是否存在（规范 §4、00 号计划书 §5.5）。
- 00 号计划书附录 A 列出了以后要区分的错误：无权限、租约失效、文档被占用、修订号冲突、负载超限、格式不兼容、客户端过旧。
- NestJS 默认的错误响应是 `{ statusCode, message, error }`，说明可能带着内部细节。例如请求体不是合法的 JSON 时，Nest 把解析器的 `SyntaxError` 换成 400，说明里带着请求内容的片段。

## 决策

**响应格式**：`{ "error": { "code", "message", "requestId", "details"? } }`。
- 只有这三个字段，加上可选的 `details`（contracts 的 `errorResponseSchema`），`Content-Type` 为 JSON；
- `details`（P4 起）：一个对象，结构按错误码约定，登记在 contracts 里（例如修订号冲突的 `revisionConflictDetailsSchema`：当前修订号及其来源）。只放客户端据此决策的数据，不放内部细节；客户端按错误码再校验一次。`AppError` 用 `details` 选项带上，异常过滤器原样带出；没有详情的错误响应不出现这个字段；
- `requestId` 与响应头 `X-Request-Id`、请求日志一致；
- 状态码由错误码决定。

**登记表**（`packages/contracts/src/errors/error-codes.ts`）：
- `ERROR_CODES` 登记每个错误码的 HTTP 状态与默认说明，`ErrorCode` 类型由它推导。
- 错误码写成大写下划线的名称。名称本身就是稳定的编号，不另设数字编号。
- 唯一性：错误码是同一个对象字面量的键，重复的键由 TypeScript（TS1117）与 ESLint（`no-dupe-keys`）拦下。
- 单元测试检查三件事：写法；状态码在 400–599；与退役清单 `RETIRED_ERROR_CODES` 不相交。
- 发布后语义不变；不再使用的错误码移入退役清单，不得复用。

**P2 登记的错误码**：

| 错误码 | HTTP | 用途 |
|---|---|---|
| `REQUEST_INVALID` | 400 | 输入不合法：校验失败、请求体不是合法的 JSON、非法的路径编码 |
| `NOT_FOUND` | 404 | 资源不存在或无权访问（两者同一个响应）；没有匹配的路由 |
| `PAYLOAD_TOO_LARGE` | 413 | 请求体超过上限，或 JSON 的嵌套层数、元素数量超过上限 |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | 不支持的字符集或内容编码 |
| `INTERNAL_ERROR` | 500 | 意外错误 |
| `SERVICE_UNAVAILABLE` | 503 | 未就绪、正在退出；等待密码哈希的请求太多（DEF-015）；数据库繁忙（等锁超时、语句超时、取不到连接，M2-P6 复核）；快照检查繁忙（排队满、等待超时、检查的子进程崩溃或超时，M3-P3），带 `Retry-After`：事务整体回滚，确定没有生效，稍后重试即可（只在这个请求里还没有事务提交过时，见下面的映射） |

**服务端**：
- **抛出**：业务代码只抛 `AppError(code, message?)`。`message` 会原样返回给客户端，只写面向用户的说明；不写时用登记表的默认说明。不抛字符串，不抛 Nest 的 `HttpException`（审查）。
- **映射**：全局异常过滤器 `HttpErrorFilter` 把所有异常映射为统一的响应。

| 来源 | 错误码与说明 |
|---|---|
| `AppError` | 它自己的错误码与说明 |
| 校验管道（`StandardSchemaValidationPipe` 的异常工厂） | `REQUEST_INVALID`，说明里列出不合法的字段路径，不回显取值 |
| 请求体解析（security 模块直接换成 `AppError`，不经过框架的转换） | `REQUEST_INVALID` / `PAYLOAD_TOO_LARGE` / `UNSUPPORTED_MEDIA_TYPE`，说明不回显请求内容 |
| 框架的 404（没有匹配的路由）与 400（非法的路径编码） | `NOT_FOUND` / `REQUEST_INVALID`，用默认说明，不用框架的说明 |
| 数据库繁忙：等锁超时（55P03）、语句超时（57014）、连接池等不到空闲连接，沿 cause 链识别（M2-P6） | 这个请求里还没有事务提交过：`SERVICE_UNAVAILABLE`，带 `Retry-After: 5`；已经提交过：`INTERNAL_ERROR`（结果未知） |
| 其他异常，包括其他 `HttpException` | `INTERNAL_ERROR`，通用说明 |

- **503 的前提是"确定没有生效"**（M2-P6 第 3 片复验）：database 模块的 `CommitLedger` 每个请求一份（AsyncLocalStorage，HTTP 管线里排在请求上下文之后），`TransactionRunner` 在 COMMIT 成功之后记一笔；数据库繁忙时，这个请求里还没有事务提交过才回 503，已经提交过就按意外错误回 500（写入已经生效，结果未知）、记 error。写接口在业务事务里拼好响应、复核不通过时回滚而不是提交一个空事务，提交之后只剩写 Cookie 与尽力而为、错误被吞掉的清理。不经 TransactionRunner 自动提交的写（限流的占名额与退回、事务之外写的失败审计、会话的顺延）不记：它们是认证与限流附带的记账，不是请求要做的那件事。

- **日志**：
  - 意外错误的异常与堆栈挂在 `response.err` 上，由请求日志在请求结束时记成一条 `error`，与方法、路由、状态码、请求标识在同一行；
  - 客户端中途断开的请求记成一条 `warn`（`aborted: true`，"请求中断"），不记状态码；之后处理器抛出的意外错误由过滤器直接记进这个请求的日志（审查 A4）；
  - 异常经自己的序列化：数据库错误不带绑定参数与行里的值（审查 A2）；
  - 预期中的错误不带堆栈：4xx 记 `warn`；带 `Retry-After` 的 503（繁忙，稍后重试）记 `warn`，不带的 503（未就绪、正在退出）记 `error`（M2-P6 复核：原来正常的锁竞争也会刷错误日志）；事务提交之后遇到的繁忙按意外错误由请求日志记一条 `error`（与其他意外错误一致，告警不重复计数），异常过滤器另记一条 `warn`，写明是提交之后、带着原因。
- **已经开始发送的响应**：无法改写成错误响应，直接断开连接。

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| A. contracts 里的登记表 + `AppError` + 全局异常过滤器 | 采用 | 一个错误码一个状态，前后端共用同一份登记；说明由服务端控制，不带内部细节 |
| B. 直接用 Nest 的 `HttpException` 与默认的响应格式 | 否决 | 格式与规范不一致；说明可能带内部细节；错误码没有地方登记 |
| C. RFC 9457（`application/problem+json`） | 否决 | 规范 §4 已经定了格式；前端只需要 `code` 与 `message`。以后需要时可以在出口处转换 |
| D. 数字编号的错误码 | 否决 | 可读性差；大写下划线的名称本身就是稳定的编号 |
| E. 请求体解析错误交给框架处理 | 否决 | Nest 把 `SyntaxError` 换成带原始说明的 400，说明里可能有请求内容的片段 |

## 影响

- **新增错误码**：在登记表里加一项（状态码固定），补单元测试；废弃的移入退役清单。P3 起按需要新增，例如未登录、CSRF 校验失败、登录限流；P4 新增 `DOCUMENT_REVISION_CONFLICT`（409，带 `details`）、`REQUEST_ID_CONFLICT`（409）、`SNAPSHOT_INVALID`（422）、`PERMISSION_DENIED`（403：能访问却没有这个操作的权限，例如只能查看的文档不能保存；没有任何权限时仍是 `NOT_FOUND`）。M3-P1 新增 `EDIT_LEASE_HELD`、`EDIT_LEASE_LOST`（409，带 `details`，ADR-018）；M3-P3 新增 `CLIENT_OUTDATED`（409，`details.reason`：`format` 数据格式不同、`build` 构建低于运维开关；页面的终态是"需要刷新"）与 `DOCUMENT_TOO_NEW`（409：文档由比服务端新的版本写过，回滚之后的情形，页面只能阅读），`SNAPSHOT_INVALID` 带 `details.rule`（规则的标识登记在 contracts 的 `SNAPSHOT_RULES`，宽松解析，不回显快照的内容）。
- **错误的详情**：新的错误码需要给客户端机器可读的数据时，在 contracts 里登记它的 `details` 结构，不另加顶层字段。
- **前端**（P3 起）：按 `code` 决定处理方式与展示。界面文字集中管理在前端（规范 §2.4），服务端的说明只是默认值。例外：`PERMISSION_DENIED` 的原因取决于服务端的状态（空间已归档、只能删自己创建的……），界面一律显示服务端这次的说明（M2-P6 第 5 片）。结果未知之后再提交同一个 `requestId` 得到 `REQUEST_ID_CONFLICT` 时，前端按"上一次可能已经建好"说明并刷新（ADR-008）。
- **无权限与不存在**：两种情况都用 `NOT_FOUND`，不暴露对象是否存在（US-M1-08）。
