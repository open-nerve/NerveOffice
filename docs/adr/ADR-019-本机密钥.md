# ADR-019：本机密钥

> 状态：已接受｜日期：2026-10-08｜来源：M3-P6（`docs/v0.1/M3-编辑权与保存协议/06-P6-本机密钥与收尾.md`）｜依据：00 号计划书 §7.6、M3 总设计 §6.6、US-M3-17

## 背景

- M4 的本机发件箱要把还没同步的修改加密保存在浏览器里（计划书 §7.6）：密钥按用户生成，服务端用自己的主密钥加密之后保存，登录之后按会话下发；设备丢失时系统管理员吊销，这个人所有的本机草稿随即作废，已打开的页面经心跳得知。
- M3 先做服务端：每人一把密钥、主密钥的配置、取用、吊销与审计、心跳带当前版本。客户端导入密钥、加密草稿都在 M4。
- 设计之前的探索 A 在 PostgreSQL 18.6 与 Node 24 上实测了表的约束、并发与包装的写法（`scratchpad/p6-explore-a.md`）。

## 决策

### 威胁模型与总规则

- **本机密钥防的是设备丢失**：设备上加密保存的草稿在吊销之后再也解不开。它不防服务端被攻破（服务端的库里文档本来就是明文），主密钥的保护目标是"只拿到数据库或它的备份的人解不开本机密钥"。
- **服务端是密钥的唯一来源**：每人任一时刻至多一把当前的密钥；吊销不可撤回，吊销的那一版的密钥材料随即从库里擦掉，下一版在同一个事务里生成。
- **原始密钥只经一个接口给本人**：解包、生成、主密钥环只在 local-keys 模块内部；日志、错误、审计、管理员的响应里都没有密钥材料。
- **吊销不顺带撤销登录，停用不顺带吊销**：停用（ADR-013）是可撤回的暂停；设备丢失时另一半（退出登录）由"生成重置链接"承担，吊销的确认框里引导。
- **主密钥与库里的对不上时记 error、照常启动**：文档照常可用；受影响的人取密钥得到 500；处置走显式的吊销（吊销不需要旧密钥）。

### 数据

`user_local_keys`：主键 `(user_id, version)`；`master_key_id bytea(16)`、`wrapped_key bytea(60)`（`IV 12 ‖ 密文 32 ‖ 标签 16`）、`created_at`、`revoked_at`；CHECK"当前的 ⇔ 有密钥材料"（吊销时两列擦成 NULL）、`revoked_at >= created_at`；部分唯一索引"每人至多一把当前的"（`WHERE revoked_at IS NULL`）；外键 `users` `ON DELETE RESTRICT`。不变量 I19（版本从 1 起连续）、I20（有过任何一行的人恰好有一把当前的、是版本最大的）、I21（下一版的 `created_at` 等于上一版的 `revoked_at`）。迁移 0026。

- 时刻：第 1 版的 `created_at` 是第一次取用的事务的 `now()`；`revoked_at` 取吊销语句执行时的 `clock_timestamp()`，不取事务开始的 `now()`——吊销开了事务、在锁上等着（system-admins 的锁、账户行）的时候，别的事务可能生成并提交了当前的那一把（本人第一次取用，或者另一个吊销生成的下一版），它的生成晚于吊销的事务开始，记 `now()` 的话约束失败、吊销 500（M3-P6 审查 A1，两种交错都有确定的集成用例）；下一版的 `created_at` 取同一个时刻（下一版生成于上一版被吊销的那一刻，时间线单调）。吊销看得到的那一把，插入它的事务已经提交，执行时的时刻必然晚于它的生成：`revoked_at >= created_at` 只有数据库的时钟往回调时才可能失败（这一次吊销 500、什么也没写）。
- 残留：吊销擦掉的包装结果在 MVCC 旧元组（VACUUM 之前）、WAL 归档与备份的保留期内仍在；约束失败时数据库服务器日志带出密文（不是原始密钥）。

### 包装格式

- 包装键 `HKDF-SHA256(主密钥, salt = 空, info = "nerve-office/local-keys/wrap/v1", 32)`；主密钥标识 `HKDF-SHA256(主密钥, salt = 空, info = "nerve-office/local-keys/master-key-id/v1", 16)`（不是机密，启动日志里记十六进制）。
- AES-256-GCM，12 字节随机 IV，16 字节标签；**加密与解密两边都显式传 `authTagLength: 16`**（Node 24 不传时，截到前 4 字节的真标签照样通过校验，只给弃用警告）；单元测试包住 `createCipheriv`/`createDecipheriv` 直接核对调用参数。
- AAD 是 `JSON.stringify(["nerve-office/local-key/v1", userId, version, masterKeyIdHex])` 的 UTF-8 字节；`userId` 是数据库给出的小写写法，`version` 是从 1 起的整数。
- 主密钥环：标识 → 包装键；包装一律用当前的，解包按行上的标识查环（本期环里只有当前一把，轮换见"影响"）。包装键在进程里是 `KeyObject`；主密钥以 `Secret` 包住的 base64 字符串留在配置里（进程存活期间在 JS 堆上，清不掉；用变量提供时 `process.env` 里也有，M3-P6 审查 A6 订正：原来写成"主密钥与包装键都是 `KeyObject`"）；派生用的字节、解包时解出的明文与原始密钥的 `Buffer` 用完清零（尽力而为，服务层与主密钥环的几处由单元测试钉住，审查 A2）；服务端不缓存解开的密钥。解不开时抛 `LocalKeyUnwrapError`（`reason`：`unknown_master_key` / `not_authentic`，带用户、版本、两个标识，不带任何密钥材料、不挂原来的异常）。
- **已知答案测试（KAT）**：主密钥 `0x00…0x1f`、IV `0xa0…0xab`、原始密钥 `0x40…0x5f`、用户 `0199b0c4-7d3e-7a3b-9c4e-2f1a5b6c7d8e`、第 1 版 → 标识 `8a7944620739d620ed1704a43a3ba0c1`，包装结果 `a0a1a2a3a4a5a6a7a8a9aaab7a6361a5b36384ed49e44202af05a2094f1dd87c153c86bb3665c8740012a3308c8b059c8aa954523cb72f8e74bbf1fb`（期望值另经 OpenSSL 的 HKDF 与 WebCrypto 的 AES-GCM 独立核对）。格式被改掉时库里所有的密钥都解不开，这条测试是唯一的防线。

### 主密钥的配置与启动

- 变量 `NERVE_LOCAL_KEYS_MASTER_KEY`（机密，支持 `_FILE`，两者只能设一个）。写法：标准 base64、带填充、恰好 32 字节、规范写法（`openssl rand -base64 32` 的输出）；校验三步：正则（第 43 个字符的低 2 位必须是 0）→ 解出恰好 32 字节 → 回编码等于原文。说明里不带取值。
- **只有应用进程要求它**：服务端的读法 `loadServerConfig`（类型 `ServerConfig`）对缺失报"缺少"（与别的变量的问题一起报，一次列出全部问题）；迁移、初始化管理员、签发重置链接的读法不要求（给了才查格式）。`ConfigModule.forServer` 让 `APP_CONFIG` 里没有主密钥，主密钥只经 `LOCAL_KEYS_CONFIG` 给 local-keys（lint 限制只有 local-keys 能引用它）。
- **公开地址是 HTTPS 时拒绝全是可打印字符的主密钥**：入库的开发与测试用密钥是可读的 32 个字符，抄进正式部署会被拦下。这条规则只拦"32 个字节全是可打印字符（0x20–0x7E，含两端；0x1F、0x7F 不算）"的主密钥，防的是能直接抄的可读文本；代码里算出来的测试密钥（全 0、KAT 的 `0x00…0x1f`、集成测试 HTTPS 用例的 `0x80…0x9f`）不在其列——它们不是现成的 base64 文本，被误用的可能小（M3-P6 审查 A5，边界有单元测试）。
- 缺失或格式不对：`ConfigError` → fatal（`CONFIG_INVALID`，只列变量名与原因）、退出码 1。
- **启动自检** `MasterKeyCheck`（只记日志、照常启动；等待的写法与审计表的保护共用 `shared/startup-check.ts`）：都是当前主密钥包装的 → info"本机密钥的主密钥已就绪"（`masterKeyId`、`currentKeys`）；有别的 → error（`foreignKeys`、`foreignMasterKeys`，说明处置）。
- 脱敏键加 `masterKey`、`localKey`、`rawKey`、`wrappedKey`。

### 接口

- **`POST /api/local-key`**（不用 GET：第一把在第一次取时生成，要写；登录之后的 GET 一律在只读快照里，ADR-017）：一个写事务，第一条语句 `SessionService.requireActive` 核对这次登录（失效回 401、不动 Cookie）→ 不加锁地读当前的 → 有就解包；没有就生成第 1 版 `INSERT … ON CONFLICT DO NOTHING`，没插进去就再读一次。200 `{ version, key }`、`no-store`；不是后台请求；不锁账户行（外键检查只取 `FOR KEY SHARE`，不等管理操作）；解不开回 500 并记 error。
- **`POST /api/admin/users/{id}/local-key/revoke`**（admin，`@SystemAdminOnly()`）：system-admins 共享锁复核操作者 → 账户行 `FOR NO KEY UPDATE` → 吊销入口（标记、擦除、插 `version + 1`；吊销的时刻与下一版的生成时刻见"数据"）→ 审计 `users.local_key_revoked`（对象账户，明细 `{ version }`）→ 返回 `AdminUser`（`localKey: { version, createdAt } | null`，没有密钥材料）。**必须先锁账户行**：两个并发的吊销只靠 `WHERE revoked_at IS NULL FOR UPDATE` 时，后一个在 READ COMMITTED 的重新检查下拿到 0 行、被当成"没有可吊销的"（实测）。停用的、自己的都能吊销；没有密钥时原样返回、不记审计。
- **锁的顺序**：本机密钥行只在吊销（system-admins → 账户行 → 本机密钥行 → 审计）与取用（只有本机密钥行）里出现，之后都不再取别的锁。
- **心跳**的 200 带 `localKeyVersion: number | null`（workspace 在续租成功之后、同一个事务里经 `LocalKeyVersions` 不加锁地读调用者自己的版本）；阅读时的编辑状态不带。M3 的页面按契约解析、不消费。

### 模块边界

local-keys → auth、database、config、logging；admin、workspace → local-keys；auth、users、documents、spaces 不依赖它。公开入口只转出 `LocalKeysModule`、`LocalKeyRevocation`、`LocalKeyVersions` 与两个类型。lint：`LocalKeyRevocation` 只给 admin 的服务（吊销绕过"是不是系统管理员"的判断，只能由在锁里复核过操作者的 admin 调用）；`LOCAL_KEYS_CONFIG` 只给 local-keys。命令行的模块组合不引入 local-keys。

## 备选方案与取舍

- **AES-KW（RFC 3394）**：确定性、输出 40 字节，但没有 AAD，要绑定用户与版本只能按用户派生 KEK——不选。
- **直接用主密钥按 HKDF 派生每人的密钥（不存包装结果）**：取用可以是纯读，但偏离"加密之后保存、记主密钥标识"，换主密钥等于所有人的密钥同时变——不选。
- **建账户时生成**：users 要依赖 local-keys、初始化管理员的命令要主密钥、存量账户要补发（迁移里没有主密钥）——不选，改为第一次取时生成。
- **GET + 给 ADR-017 开豁免**：改的是跨全部读接口的规则与它的自动核对，换来的只是动词好看——不选。
- **吊销时同时撤销全部登录**、**停用时自动吊销**：两件事分开（单一职责），见"总规则"。
- **主密钥对不上时拒绝启动**：主密钥真丢了时整个服务起不来；手误时自动作废会把所有人的密钥一起作废——不选。

## 影响

- **M4**：页面登录之后（打开或进入编辑时）取一次密钥、导入为不可导出的 `CryptoKey` 只放在内存；心跳得知的版本与内存里的不同 → 停用旧密钥、重新取、用新密钥重写当前内容；取用的会话类失败按 P5 交接单的口径（只有连着的第一次在确认会话之后立即重试）。
- **界面**：账户页每一行的"吊销本机密钥"（确认框引导同时生成重置链接，成功写进页面顶部的状态区）；M3 的页面对吊销不做可见的反应。
- **部署**：主密钥只给应用容器，推荐 Docker secrets 与 `_FILE`；容器 E2E 每次随机生成主密钥，部署核对的最后一步用镜像默认的命令真的启动两次（空值、写法不对），核对拒绝启动、输出里没有取值，收完日志之后扫一遍主密钥；不在数据库与数据库备份里，单独保管，恢复数据库备份时用同一把；丢失时所有人的本机密钥解不开（M4 起未同步的草稿随之丢失），逐个吊销即可恢复；见 `deploy/README.md`。
- **延期**（M7）：主密钥轮换与重新包装（DEF-065）；丢失或泄露时的批量作废（DEF-066）；恢复备份之后重做吊销的运维手册（DEF-067）；生产环境的堆快照与核心转储策略（DEF-068）。
