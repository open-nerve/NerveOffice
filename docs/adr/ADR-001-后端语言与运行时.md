# ADR-001：后端语言与运行时

> 状态：提议｜日期：2026-09-23｜来源：v0.1 规划（M0 开始前）

## 背景

- 00 号计划书 r2 选定的后端是 Node.js 24 + NestJS；初稿中也记录了"不再采用 Go 后端"。
- 需求方提出改用 Go。理由有两点：
  - Univer 可以直接复用的部分集中在前端，服务端可以自行实现；
  - Go 能节省内存、提升运行效率，并且以单个二进制交付，集成部署方便。
- 源码与设计核查得到的事实：
  - **MVP 的服务端不加载 Univer，也不重算公式**（00 号计划书 §9.1）。服务端对快照只做这几件事：解压、体积与结构校验、计算 SHA-256、读取顶层 `resources` 的名称、扫描本平台的资源地址、条件写入。它们都是与语言无关的字节与 JSON 处理。
  - **将来可能需要在服务端运行 Univer 的场景**：SDK 升级时批量迁移快照（§8.7）、服务端公式计算、Agent 自动编辑、服务端渲染。这些都依赖 Univer 在 Node.js 下的无界面运行能力。
  - **规模**：约 100 人，20 人同时编辑，保存高峰约每秒 1–2 次（§12）。

## 决策（提议）

后端改用 Go，交付物是一个二进制文件，前端静态资源也内嵌在其中；前端保持 TypeScript（React + Vite + Univer）。配套做三件事：

1. **契约先行**：以 OpenAPI 规范作为前后端接口的唯一来源，由它生成 Go 服务端接口和 TypeScript 客户端类型；CI 检查生成的代码是否为最新。
2. **插件档案语言中立**：插件档案（插件列表、资源名称白名单、空资源的判定规则）做成 JSON 清单，编辑器与服务端读取同一份。
3. **服务端只有 Go，不引入 Node**：v0.2 起，如果需要在服务端处理文档（例如供 Agent 使用的无界面接口）：
   - 读取类操作，由 Go 直接解析快照；
   - 写入与计算类操作，通过"文档运行时"接口执行。实现上优先选择在 Go 进程内嵌入 JS 引擎、运行 Univer 的无界面核心；备选方案是由 Go 驱动无头浏览器。
   
   两种方式的可行性都在 M0 中验证（见下文"服务端无界面文档处理"）。

建议的技术栈（M1 时用单独的 ADR 定稿）：
- Go 1.27；
- HTTP 使用标准库 `net/http`，必要时加上 chi；
- 契约：OpenAPI 3，用 oapi-codegen 或 ogen 生成代码；
- 数据库：pgx + sqlc；迁移工具用 goose 或 Atlas；
- 标准库和官方扩展库：`log/slog`、`golang.org/x/crypto/argon2`、`http.CrossOriginProtection`；
- 测试与检查：testcontainers-go、golangci-lint。

## 备选方案与取舍

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. Go 后端（提议） | 单个二进制分发；内存占用低，能利用多核并行；标准库覆盖了 HTTP、加密、压缩、日志与 CSRF 防护，服务端依赖少、供应链攻击面小；显式 SQL 与事务契合保存协议 | 前后端不能直接共享类型（用契约生成解决）；要维护两套工具链；将来在服务端处理文档，需要内嵌 JS 引擎或驱动无头浏览器（见"服务端无界面文档处理"） |
| B. Node.js + NestJS（r2 现状） | 全栈同一种语言，类型直接共享；可以在进程内运行 Univer 的无界面能力 | 运行时与依赖体积大，单文件分发不成熟；npm 依赖面大；解析大 JSON 时会阻塞事件循环 |
| C. TypeScript + Bun/Deno，编译为单文件 | 保留 TypeScript，同时能单文件分发 | 运行时与生态兼容性有风险（NestJS、原生模块等），生产成熟度不如前两种方案 |

## 服务端无界面文档处理

Univer 的文档逻辑是用 TypeScript 实现的，包括公式计算、插入删除行列时的引用调整、文字文档的文本模型等。想在服务端得到和前端完全一致的处理结果，只有两条路：

- 在 Go 里把这些逻辑重写一遍；
- 在服务端提供一个 JS 引擎，直接运行 Univer 本身。

Node 只是 JS 引擎的装法之一，并不是唯一的选择。

| 方案 | 能做什么 | 与前端的一致性 | 部署形态 | 主要风险 |
|---|---|---|---|---|
| A. Go 直接解析快照 | 读取值、公式、结构和文本；少量简单写入 | 读取完全一致；写入时需要自己维护数据的一致性约束 | 纯 Go | 写入范围一旦扩大，行为就会和 Univer 分叉 |
| B. Go 内嵌 JS 引擎（例如 QuickJS 编译为 WebAssembly，通过 wazero 在 Go 中运行，不需要 cgo） | 读写、公式计算（不能渲染） | 完全一致，因为运行的就是 Univer 本身 | 仍然是一个二进制 | Univer 官方不支持这种环境，需要自己补齐运行环境（定时器、Intl 等）；性能比 V8 低；需要验证 |
| C. Go 驱动无头浏览器（Chromium） | 读写、计算，还能渲染截图 | 完全一致，和用户端运行的是同一份前端代码 | Go 服务 + Chromium | 依赖重、资源占用大，需要做沙箱隔离和并发控制 |
| D. 在 Go 中重写 Univer 的编辑逻辑 | 按需实现 | 很难保持一致 | 纯 Go | 工作量巨大，而且会长期与 Univer 分叉；不推荐 |

建议的组合：
- 读取始终用 A；
- 写入与计算优先用 B；B 不可行时改用 C；
- 不采用 D，也不引入 Node。

B 和 C 里运行的 JS 就是 Univer 本身，外加一层很薄的适配代码，不会出现第二套需要我们维护的服务端代码。

## 影响

- **00 号计划书**：§1.1（后端语言）、§9（技术选型、架构图、代码组织）、§10.1 的措辞；M1 的工程底座改为 Go。
- **CLAUDE.md**：在"代码与依赖约束"中补充 Go 相关的约定。
- **M0**：验证工程中的迷你服务改用 Go 编写。V16 改为"在 Go 进程内运行 Univer 无界面核心的可行性"：先验证方案 B，B 不可行时验证方案 C。V16 不阻断 v0.1，但它的结论决定 v0.2 服务端文档处理走哪条路。
- **与语言无关、保持不变的部分**：数据模型、保存协议、租约、本地优先、安全策略，以及 E2E（Playwright）。
- **初稿"不再采用 Go 后端"的原因**：已向需求方确认，是担心将来为了在服务端做无界面处理，不得不把 Node 加回来。本 ADR 通过方案 A、B、C 的组合回应了这一点：服务端始终只有 Go，前提是 V16 验证 B 或 C 可行。
