# ADR-001：后端语言与运行时

> 状态：已接受｜日期：2026-09-23｜来源：v0.1 规划（M0 开始前）

## 背景

- 00 号计划书 r2 选定的后端是 Node.js 24 + NestJS。
- 评审中曾提出改用 Go，理由是单个二进制交付、内存占用低、运行效率高。
- 核查得到的事实：
  - MVP 的服务端不运行 Univer（00 号计划书 §9.1），就 MVP 本身而言，用哪种语言都没有障碍。
  - 但将来需要在服务端执行 Univer 的文档逻辑，例如 v0.2 供 Agent 使用的无界面编辑接口，以及 SDK 升级时的快照迁移。这些逻辑包括公式计算、插删行列时的引用调整、文字文档的文本模型等，都是用 TypeScript 实现的。
  - 这部分逻辑的规模（有效代码行，不含测试和界面）：
    - 公式引擎约 7.2 万行，包含 482 个已实现的函数；
    - core 约 3.2 万行，sheets 约 2.6 万行；
    - 各功能插件合计约 3 万行；
    - 总计约 17 万行。另外有 12 处插件，各自注册了插删行列时的引用调整逻辑。
  - 需求方明确：服务端不接受 Go 与 Node 两种运行时并存，也不接受在 Go 中内嵌 JS 引擎。

## 决策

后端保持 Node.js + TypeScript（NestJS），全栈统一使用 TypeScript。将来需要在服务端处理文档时，直接在 Node 进程内以无界面方式运行 Univer，与前端使用同一套文档逻辑。

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| A. Node.js + TypeScript | 采用 | 服务端可以直接运行 Univer 的无界面能力，结果与前端完全一致；全栈同一种语言，类型和插件档案可以直接共享；服务端只有一种运行时 |
| B. Go，服务端的文档处理用 Go 重写 | 否决 | 需要移植并长期同步约 17 万行 TypeScript 逻辑（其中包括 7.2 万行的公式引擎和 12 处引用调整逻辑），行为很难与前端保持一致 |
| C. Go，外加内嵌 JS 引擎、无头浏览器或 Node 辅助进程 | 否决 | 服务端会出现第二种运行时；内嵌 JS 引擎不在 Univer 官方支持的范围内；需求方不接受 |

## 影响

- **技术选型不变**：00 号计划书的技术选型（§9.2）保持原样。
- **放弃 Go 的收益**：不再追求单个二进制和更低的内存占用。以容器镜像交付，在 M1 控制镜像体积与内存占用，包括精简生产依赖、提供可观测的内存指标。
- **服务端依赖面较大，带来供应链风险**：应对措施是锁文件、依赖审计、尽量少用服务端依赖，并在 CI 中做依赖漏洞扫描。这些在 M1 的《工程规范与完成定义》中落实。
- **解析大 JSON 会阻塞事件循环**：保存接口对快照的解压与校验，放到 worker 线程中执行或采用流式处理，具体在 M3 设计保存协议时确定（00 号计划书 §7.4）。
- **M0 的 V16**（在 Node.js 下以无界面方式加载快照）保持为可选验证项。它是将来在服务端处理文档的可行性基础。

## 实测：镜像体积与内存（M1-P5 建立，M2-P4 复测）

镜像按 ADR-012 构建（`node:24.21.0-bookworm-slim`，运行镜像只有 Node、api 的生产依赖与构建产物）。数字由容器 E2E 的编排脚本打印（`pnpm test:e2e:container`）：体积取镜像里文件的合计（在一次性的容器里 `du -sxb /`，解压之后，与镜像存储无关，见下面的"口径"）；内存取 `docker stats`（应用容器）：E2E 开始之前的空闲值，E2E 期间每 2 秒取样的峰值（Chromium 的全部用例与重启用例）。重启用例最后执行、会重启应用，跑完之后量到的是重启过的进程，不作为指标。

| 环境 | 镜像体积：镜像里文件的合计（解压之后） | 应用容器的内存：空闲 | E2E 期间的峰值 |
|---|---|---|---|
| 本机：Docker Desktop，linux/arm64（2026-09-28，多次运行） | 285.7 MB | 约 200–205 MiB | 约 235–280 MiB |
| CI：GitHub Actions ubuntu-24.04，linux/amd64（2026-09-28，合并 `f7d6105` 的 run 36402178139） | 267.1 MB（本机按 linux/amd64 构建、同样的量法；这次 CI 打印的还是 `docker image ls`，见"口径"） | 205.6 MiB | 232.0 MiB |
| 本机复测（2026-09-30，M2-P4 收尾，机器空闲）：main 的代码（`8f7ec2b`，容器 E2E 92 条） | 286.3 MB | 206.6 MiB | 408.3 MiB |
| 本机复测（2026-09-30，M2-P4 的代码，容器 E2E 99 条，两次） | 286.9 MB | 229.8–241.1 MiB | 433.2 与 467.7 MiB |
| CI：GitHub Actions ubuntu-24.04，linux/amd64（2026-09-30，合并 `d0e0202` 的 run 36656313904） | — | — | 245.7 MiB |

- 体积的构成（arm64）：Node 可执行文件约 118 MB，api 的生产依赖约 56 MB，前端的生产构建约 21 MB，后端与 contracts 的构建产物约 1.5 MB，其余是 Debian slim 的基础层。Go 单个二进制的体积优势主要在这里；这一版的数字可以接受，精简（换基础镜像、裁剪 Node）在 M7 按部署要求再评估。
- 口径（M1 收尾时实测，同一个镜像量出几种数字）：docker 自己报的体积随镜像存储而变，不能跨环境比较。
  - CI 的 overlay2 存储：`docker image ls` 是各层的合计（amd64 283 MB），比镜像里文件的合计多出运行阶段删掉的 npm、corepack 与 yarn（约 20 MB）。它们在基础镜像的层里，删掉只减少攻击面，不减少体积。
  - Docker Desktop 的 containerd 镜像存储：`docker image ls` 把压缩的内容与解压之后的内容（按磁盘块计）一起算，P5 时本机记的 441 MB 就是这个口径，不是解压之后的体积；非本机平台的镜像没有解压时只显示压缩的部分（amd64 91.6 MB）；`docker image inspect` 的 Size 是压缩之后的。
  - 压缩之后（拉取时的下载量）两个平台都约 91.5 MB。编排脚本因此改为量镜像里文件的合计。
- 两个平台的差别：arm64 比 amd64 多约 19 MB，按各层的大小看主要在 Debian 的基础层。
- 内存（M1-P5 的量法不变，数字随版本更新）：
  - **空闲**：M1-P5 时约 200–206 MiB；M2-P4 之后约 230–241 MiB。多出来的约 23 MiB 是 M2 新增的模块、契约与提供者（组织与权限、文件夹与回收站、定时任务），属于代码规模带来的基线上移。
  - **E2E 期间的峰值**：M1-P5 时 230–280 MiB（当时容器 E2E 只有几十条）；2026-09-30 在同一台机器上复测，main 的代码 408.3 MiB（92 条）、M2-P4 的代码 433.2 与 467.7 MiB（99 条，两次）。
    **峰值主要由 E2E 套件的并发决定，不是业务代码的常态占用**：M2-P4 自己新增的四份用例单独跑时峰值 245.1 MiB（空闲 241.1），几乎不动；真正推高峰值的是编辑器那批用例并发保存快照（服务端保存时解析整份快照，DEF-018）。
    同一份代码两次全跑相差 34 MiB，说明它还受"哪些用例正好重叠"影响。
  - 密码哈希每次另占约 19 MiB（Argon2id 默认参数），同时最多 2 个。
  - 部署时按"空闲 + 并发保存的峰值"留余量；M7 的压测给出真实负载下的数字，届时这张表按压测结果重写。
  - 拿这几个数字做比较时，机器必须空闲：与别的构建、测试抢 CPU 时，Node 的垃圾回收被推迟，同一份镜像量到的峰值会明显偏高（M2-P3 收尾时量到 444.0 MiB，空闲时是 246.2 MiB）。
