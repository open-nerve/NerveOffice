# ADR-011：文档内容与保存协议

> 状态：已接受｜日期：2026-09-27｜来源：M1-P4｜修订：2026-10-05，M3-P3：完整的快照检查（子进程池）、规范化的内容哈希与"内容相同不递增"（回执）、拦截旧客户端、平台信封、"公式待更新"、修订记录与回执的保留期——见文末，取代上文"保存的处理顺序"第 2 步与"影响"里 M3 的几项；2026-10-04，M3-P2：读取内容的条件请求（DEF-017）、另存为副本（见文末）；2026-10-01，M2-P6 第 3 片复核：保存的重放只要求仍能访问（00 号计划书 §7.4），被降级、空间被归档之后重发一次已提交的保存得到原结果；2026-09-28，M1 对抗评审（Codex CX2、CX5、CX7）之后，`unit_id` 不唯一，新建的锁键按规范化的 UUID，重试原样再发结果未知的请求；2026-10-04，M3-P1：保存要求编辑租约（ADR-018），持有者的请求在锁下另核对登录

## 背景

- 00 号计划书 §7.1–§7.4、§8.1–§8.4、§12：全量快照；修订号条件写入；`requestId` 幂等；冲突附来源；快照用 `bytea` 存 gzip 压缩的原始 JSON 字节；新建用收敛的模板；`unitId` 与文档 id 独立；档案与格式版本；解压后 5 MiB 的上限。
- M1 总设计 §2.1、§6.5：显式保存（没有自动保存与租约）；M1 只做基本校验，完整的校验与内容哈希在 M3。

## 决策

**数据**（迁移 `0006_document_content`，只做加法）：
- `documents` 补上 `revision`（新建为 1，每次保存加一）、`unit_id`（服务端生成的 UUID，终身不变）、`profile`（`sheet@1`）、`format_version`（1）、`sdk_version`（写入时平台内置的 Univer 版本；客户端上报与拦截旧客户端在 M3）；
  - `unit_id` 不唯一：复制文档时快照原样复制，不改写 `unitId`，两份文档的 `unit_id` 相同（00 号计划书 §8.3）。平台的身份是文档 id；保存时核对的是"快照的 `id` 等于这份文档的 `unit_id`"，不需要唯一。0006 建了唯一约束，与复制的方案冲突，由迁移 `0007_document_unit_id_not_unique` 去掉（Codex 评审 CX5）；
- `document_contents`：每份文档一份当前快照（gzip 的字节、解压前后的字节数）；
- `document_revisions`：每次新建或保存一行（修订号、种类、`request_id` 唯一、负载摘要、保存的来源 `clientInstanceId` 与 `localSeq`、保存人），不存正文。

**接口**：
- `POST /api/documents`：`{ type, title?, requestId }`，在个人空间里建文档，内容是模板换上新的 `unitId`（服务端 `JSON.parse` → 换 `id` → `JSON.stringify`，模板本身就是 `JSON.stringify` 的输出，逐字节不变）。同一个 `requestId` 的重放同样 201，返回那份文档的当前元数据，另带 `replayed: true`（正常新建为 `false`，M2-P6 第 5 片，接口的加法；复制与新建文件夹同样带）；并发的相同请求按 `requestId` 取事务级 advisory lock 排队。锁键用数据库规范化之后的 UUID（`requestId::uuid::text`）：同一个 UUID 的大小写写法，`request_id` 的唯一约束（uuid 类型）认作同一个，锁也要认作同一个，否则并发时各拿一把锁（Codex 评审 CX7）。
- `GET /api/documents/{id}/content`：数据库里的 gzip 字节原样下发（`Content-Encoding: gzip`），修订号作 ETag（`"<修订号>"`）；修订号与内容一条语句读出。
- `PUT /api/documents/{id}/content?baseRevision&requestId&clientInstanceId&localSeq`：正文是 gzip 压缩的快照（`application/gzip`），不经 JSON 请求体的解析器；成功返回 `{ revision, savedAt }`。

**保存的处理顺序**：
1. 读取正文：在认证与 CSRF 之后（路由的拦截器）；压缩前后都限 5 MiB，解压到上限就停下（413）；只接受恰好一个完整的 gzip 成员、末尾没有别的数据：存下的字节原样下发，浏览器只解第一个成员、忽略之后的数据，只有单个完整的成员两边解出的内容才一定相同，所以用标准的 `DecompressionStream`，不用会解开全部成员的 `zlib`；上传中途断开按请求中断处理（400，warn 日志）；
2. 与文档无关的基本校验（UTF-8 的 JSON 对象、工作簿的结构、顶层 `id` 是字符串、嵌套不超过 64 层；422 `SNAPSHOT_INVALID`）；M3-P3 起由完整的快照检查取代，并排在重放预检与拦截旧客户端之后（见文末）；
3. 一个事务：先不加锁读文档并判断**能否访问**（没有权限与不存在相同；权限查询走事务的连接）→ 能编辑时锁住文档行（`FOR UPDATE`），锁下再判断一次能否访问（期间移到别的空间或授权被收回）；只能查看的不取锁（M1-P4 复验 RA7）→ 按 `requestId` 幂等（同一个人对这份文档的同一次保存才返回原结果，负载摘要按基准修订号与解压后的字节算）→ 不是重放才要求能编辑（M2-P6 复核：原来先要求能编辑、再查重放，一次结果未知的保存期间被降级或空间被归档，重发得到 403，客户端按约定当作"没有提交"，实际已经提交了；00 号计划书 §7.4 写明幂等这一步只要求仍能访问。代价：原来那次还没提交时，已被降级的人发来的重试不取锁、看不到它，得到 403；客户端留着那次结果未知的记录，下一次重试就拿到重放）→ 顶层 `id` 等于文档的 `unit_id` → 基准修订号等于当前修订号（否则 409 `DOCUMENT_REVISION_CONFLICT`，`details` 带当前修订号及其来源）→ 写内容、修订号加一、写修订记录与审计。

**客户端**：
- 保存的状态机（`features/sheet-editor/save-coordinator.ts`）：提交正在编辑的单元格 → 等公式收齐（最多 3 秒）→ 捕获 → 体积检查 → gzip → 上传。已保存的序号只前进到捕获时的序号（保存期间的修改仍算未保存）。
- 结果未知的保存（网络错误、5xx、回包读不出来）都记下来（只记序号与公式是否收齐，不留快照）：内容与基准都没变的重试原样再发那个请求，`requestId`、序号与快照都不变（服务端记下的来源是第一次的序号，换成这次捕获的序号就认不出自己追自己），成功之后按这次捕获的序号确认；某次重发被明确拒绝（例如 401、403）只说明那一次没有提交，更早那次结果未知的记录与请求都留着（Codex 评审 CX2）。冲突的来源是其中之一时，说明那次保存其实已经提交（自己追自己），换上当前修订号用新的 `requestId` 重发一次。其他冲突进入"版本冲突"，保留本页内容，禁止继续保存，提供重新加载。

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| A. 快照用 gzip 的 `bytea`，原样下发 | 采用 | 计划书 §8.1：`jsonb` 不接受 `\u0000`、会重排键；gzip 省空间，读取时浏览器自动解压 |
| B. 保存的正文用 JSON（`{ snapshot, baseRevision, … }`） | 否决 | 全局的 JSON 解析器上限 256 KiB；把 5 MiB 的快照解析再序列化一遍也没有必要 |
| C. 修订号用时间戳或内容哈希 | 否决 | 整数修订号最简单，冲突的判断与 ETag 都直接；内容哈希在 M3 另作"内容相同不递增" |
| D. 先查幂等再锁文档 | 否决 | 同一个请求的两次并发重试，后到的一方会误报冲突；先锁文档，拿到锁时前一方已经提交 |
| D2. 先锁文档行再判断权限 | 否决（P4 审查 A2） | 没有权限的请求也在别人的文档行上取锁，所有者的保存随之排队；等锁的时间还能区分"别人的"与"不存在的"。改为先不加锁判断权限，通过之后再锁 |
| E. 只按最近一次结果未知的保存识别"自己追自己" | 否决 | 连续两次都没收到回包、其实是较早的一次提交了时，会误报冲突 |

## 影响

- 新错误码：`DOCUMENT_REVISION_CONFLICT`、`REQUEST_ID_CONFLICT`、`SNAPSHOT_INVALID`、`PERMISSION_DENIED`；错误响应加可选的 `details`（ADR-006）。
- M3：完整的快照校验与规范化内容哈希（内容相同不递增）、`If-None-Match` 与 304、拦截旧客户端（`CLIENT_OUTDATED`）、编辑租约与阅读模式、自动保存与捕获时机。M4：发件箱与压缩放进 Worker。（M3 的这几项已在 M3-P1、P2、P3 实现，见文末的补充；修订记录与回执保留 30 天在 M3-P3 实现；历史版本在后续的 M。）
- 模板随 SDK 与档案更新：`pnpm --filter @nerve-office/e2e run update:sheet-template` 经产品本身生成（直到连续两次保存相同），E2E 回归"新建的文档打开后立即保存，快照与模板逐字节相同"。

## M3-P1 的补充：保存要求编辑租约（ADR-018）

- 查询参数加 `writeEpoch`（必填），请求头 `X-Edit-Lease` 带租约的令牌（不进地址与日志）。
- 顺序：能访问 → 能编辑时锁文档行、锁下再判断 → 按 `requestId` 查重放（**重放先于登录的再核对与租约**：已经提交的同一次保存，之后不论登录、租约怎样，重试都拿到原来的结果，A07）→ **这次登录现在仍然有效**（否则 401 `SESSION_EXPIRED`；守卫之后还隔着上传正文与等锁，M3-P1 审查 A1）→ 不是重放才要求能编辑 → **租约**：令牌是当前这一行的、有效、代次等于 `writeEpoch`、登录与查询参数的标签页都是租约绑定的，否则 409 `EDIT_LEASE_LOST`（`details.reason`）→ 核对 `unitId` → 基准修订号 → 写入。保存不续租，不加锁读租约行（能改写它的申请与收回写入权都先锁文档行）。
- 租约在 `unitId` 与基准修订号之前：失去编辑权的页面得到的是"编辑权已失效"，而不是修订号冲突或"内容不属于这份文档"；冲突的详情只给持有租约的页面。
- `edit` 的说明改为"只能查看这份文档，不能编辑"（保存与申请编辑权共用）。
- 冲突详情的来源抽成 `revisionSourceSchema`，申请编辑权的响应也带当前修订的来源（ADR-018）。

## M3-P2 的补充：读取的条件请求与另存为副本

- **读取内容的条件请求**（DEF-017）：`GET /api/documents/{id}/content` 带 `If-None-Match`（参数装饰器 `@IfNoneMatch()`；列表、弱校验器 `W/"n"` 与 `*` 都认），在读快照里先判断权限（看不到与不存在一致），修订号对得上回 304：只带 ETag，不读内容、不带正文与 `Content-Encoding`。认不出的实体标签按不匹配处理（200），不报 400：缓存的校验器认不出就是不新鲜。304 由响应拦截器设状态码，依赖 Nest 12 发送响应时不重设状态码（集成测试按状态码核对，变了会立即报出来）。页面脚本自己加的 `If-None-Match`，浏览器把 304 原样交给页面，页面按"手里的内容就是最新的"处理（`acceptNotModified`）。阅读页的定时检查读的是编辑状态（只有修订号与谁在编辑，ADR-018 的补充），本来就不传内容；条件请求用在进入编辑时本页落后、"有更新，点击刷新"这两处——这两处都是看到修订号变了才发，修订号只增不减，所以在页面上通常得到 200；304 是兜底（竞争、以后的调用方），浏览器把 304 原样交给页面由 Fetch 规范保证，服务端的集成测试与前端的单元测试覆盖，E2E 走不到（M3-P2 审查 B6）。
- **另存为副本**（00 号计划书 §7.5，M3 总设计 §2.1 第 4 条）：`POST /api/documents/{id}/conflict-copies?requestId&title`，正文与保存同一个读取方式（gzip 压缩的快照，压缩前后都限 5 MiB、单个完整的 gzip 成员），基本校验在事务之前；快照的 `id` 要等于原文档的 `unitId`（否则 422 `SNAPSHOT_INVALID`），副本的 `unitId` 与原文档相同（§8.3：不改写）。新文档的类型、档案、平台格式版本照原文档，SDK 版本是服务端内置的；修订号 1、代次 0、修订记录 `created`（来源为空）。标题由页面给出（contracts 的 `conflictCopyTitle`：原标题加"（冲突副本 时间）"，时间按页面所在的时区写到分钟，超过上限按码点截断原标题）。`requestId` 幂等，与新建、复制同一个做法（同一个人的同一次请求返回那份副本现在的样子，带 `replayed`）；摘要是"原文档 + 标题 + 解压后的字节"：放在哪里由服务端决定、不算进去（结果未知之后权限变了，原样的重试照样是重放），按解压后的字节算（重新压缩不影响，内容变了就是另一个请求，409 `REQUEST_ID_CONFLICT`）。审计 `documents.conflict_copied`（明细：原文档 id、副本所在的空间；不记标题）。只要求能读原文档、放在哪里与锁，见 ADR-014 的补充；P3 的完整校验同样适用于它。

## M3-P3 的修订：完整的快照检查、内容哈希、拦截旧客户端与保留期

依据 M3-P3 设计（`docs/v0.1/M3-编辑权与保存协议/03-P3-保存协议加固.md`）。

**写入的处理顺序**（保存与另存为副本；原则：**同一次写入的重放先于其余一切检查**，00 号计划书 §7.4 第 2 步）：
1. 读取正文（不变）。
2. **重放预检**：在连接池上（不开事务），按 `requestId` 查修订记录与回执；同一个人、同一份文档、负载摘要一致、仍能访问，就返回原来的结果；其余一律往下走、不提前回答——看不到与不存在的语句序列不变，留给事务里的再查。
3. **客户端的数据格式**（与文档无关）：请求里的 `clientBuild`、`univerVersion`、`profile`、`formatVersion` 等于服务端的，构建不低于运维开关 `NERVE_MIN_CLIENT_BUILD`；否则 409 `CLIENT_OUTDATED`（`details.reason`：`format`、`build`）。这些字段在契约里是可选的：旧页面重试一次结果未知的写入时，要能到达重放；缺字段按过旧处理。
4. **快照的检查**（与文档无关，子进程池，见下）：不合格 422 `SNAPSHOT_INVALID`（`details.rule`）；通过时得到 `unitId`、规范化的内容哈希、在的与非空的资源名。
5. **事务**：**`requestId` 的锁**（`RequestLedger`，事务的第一把锁：同一个 `requestId` 的写入排队，后到的一方在锁下看得到前一方写在哪张表、哪份文档上；看不到与不存在的请求同样取它，与文档无关；审查 A3）→ 访问 → 能编辑时锁文档行、锁下复核 → 再查重放（修订记录与回执两张表）→ 登录仍有效 → 文档的数据格式（记录的 SDK 版本高于服务端的，或档案、格式版本对不上：409 `DOCUMENT_TOO_NEW`——回滚之后的情形，刷新拿到的还是同一个版本，提示"刷新"会死循环，所以与 `CLIENT_OUTDATED` 分开）→ 能编辑 → 租约 → 基准修订号 → `unitId`（422，规则 `unit-id`）→ **不缩水**（上一版的非空资源名存在 `document_contents.resource_names`；存量为空时在锁下解析上一版得到，解压有上限，解析不出来的 `data` 算非空；白名单之外的旧资源不算缩水；422，规则 `resource-missing`）→ **内容哈希等于当前的**：写回执（`document_save_receipts`），"公式待更新"只清不设，修订号不变，响应 `unchanged: true`、`savedAt` 取当前修订的时间，不记审计 → 否则写内容（连同哈希与非空资源名）、修订号加一、修订记录（哈希、客户端构建）、文档的信封（`sdk_version` 记上报并核对过的版本、`client_build`、`formulas_pending`）、审计。

另存为副本走第 1–4 步，锁照 M3-P2（第一把仍是 `requestId` 的锁；回执用过的 `requestId` 回 `REQUEST_ID_CONFLICT`），锁下核对 `unitId`、写哈希与信封（类型与 `unitId` 照原文档；档案、格式版本与信封——SDK 版本、构建、"公式待更新"——取这次上传、核对过的页面的值：副本装的是页面的内容，信封描述它；不对原文档判断"比服务端新"，否则回滚之后失去编辑权的人连副本也存不了；审查 A7）；它是新文档，不做不缩水与内容相同。新建写模板的哈希（模板的顶层 `id` 换成这份文档的 `unitId`，每份单独算）；复制连同哈希、资源名、构建与"公式待更新"带过去。

**负载摘要**：保存的摘要计入 `formulasPending`（同一个 `requestId` 而标记不同就是另一个请求）；不带标记时与 M3-P3 之前逐字节相同，旧页面在升级之后的重试照样是重放。

**快照的检查**（`SnapshotInspector`，规则在 `snapshot-checks.ts` 与 contracts，标识在 `SNAPSHOT_RULES`）：
- 编码与 JSON；**解析之前先按文字数**嵌套与元素，外层与资源 `data` 累加，嵌套不超过 64 层、元素不超过 150 万，超出的不交给 `JSON.parse`（1–60 ms 内拒绝）；结构（顶层对象、`id` 非空字符串、`sheetOrder` 是字符串数组且每项是 `sheets` 的键、`sheets` 的值是对象）；资源（名称唯一、白名单、必须为空的深层为空、已知资源的最小结构，contracts 的 `profile-resources.ts`）；图片（任何深度上名为 `source` 的字段只接受相对的平台地址 `/api/assets/{uuid}`——M5 之前没有合法的图片地址，表格里的图片一律存不进去）；链接（每张表每个单元格 `p.body.customRanges` 的链接合法、等于规范写法、`rangeId` 合写法）。规则用 M0 的 41 份样本、模板与 E2E 产出的快照核实过不误拒。
- 执行：**子进程池**（`shared/process-pool.ts`，需求方 2026-10-05 决定）。S3 实测工作线程的 `resourceLimits` 不是可靠的隔离边界：线程在 V8 的内置函数里（`JSON.parse` 正在建对象、对大字典取键）撞上堆上限时，整个进程以 SIGABRT 退出。子进程用 `child_process.fork`、IPC 的 advanced 序列化传正文（5 MiB 约 2 ms）、`--max-old-space-size`（`NERVE_SNAPSHOT_INSPECTION_HEAP_MB`，默认 512、下限 128）与 16 MiB 的新生代半区；堆超限只结束子进程，这一次按 `too-complex` 拒绝，服务照常；执行任务期间被外部 SIGKILL 的（现实里几乎只有容器内存用尽时内核的 OOM killer）同样按 `too-complex` 拒绝并记 error——否则同一份内容每次重发都把容器推到上限、页面无止境地重试（审查 A4；内存的配法见部署说明"快照检查的子进程与内存"）；其余崩溃（加载时被结束、执行期间以 SIGKILL 以外的信号结束）、超时、排队满回 503 `SERVICE_UNAVAILABLE` 带 `Retry-After`。**每个账户在池子里至多 2 份**（执行与排队合计，`INSPECTIONS_PER_ACCOUNT`；一个页面的保存是串行的，两个页面同一刻各一份正好 2 份）：多出来的只对这个人回同样的 503——检查在判断访问之前，没有这条时一个账户就能占满整个池子、让别人的保存一直 503（审查 A2）；多个账户合起来仍能占满，随 M7 按账户的写接口限速处理（DEF-054）。子进程不继承 execArgv 与环境变量（不带数据库口令），IPC 断开即退出（不留孤儿），空闲 60 秒退出，Linux 上把自己的 `oom_score_adj` 调到 1000（容器的内存用尽时内核先结束子进程）。进程数、排队与内存的上界见 ADR-001 的内存一节。

**规范化的内容哈希**（`packages/contracts/src/documents/content-canonical.ts`；M4 的客户端要逐字节复现，下面每一条都是规格）：
- 以 JSON 文本为准；去掉视图状态（工作表的 `zoomRatio`、`scrollTop`、`scrollLeft`；文字文档的 `settings.zoomRatio` 在 M6 加）；
- 资源的 `data` 解析一次；深层为空（`null`、`""`、`{}`、`[]`，或每一层都为空）的资源去掉——"在而为空"与"不在"等价，"不在"由不缩水兜住；非空的、`data` 是对象的，**只在第一层**（多数资源是每张工作表一个键的那一层）去掉取值深层为空的键——M0 的 S0 与 S1 唯一的差别就在这一层（数据验证的 `{"<sheetId>": []}` 与不在）；更深的层级原样保留，`data` 不是对象时原样。理由（审查 A5）：内容相同就不写入，把语义不同的内容判成相同就是静默丢修改，所以只去掉证明了等价的空——例如筛选的"为空"（`customFilters:[{val:""}]`）、按值筛选一个也没选（`filters:{}`）与没有条件在 Univer 里含义不同，逐层去空时三者的哈希相同；按名称的 UTF-16 码元排序；
- 对象的键序：规范的数组下标形式的键（`0`–`4294967294`）按数值升序在前，其余按 UTF-16 码元字典序（M0 原型 `Object.fromEntries(Object.keys(x).sort()…)` 实际得到的顺序；按纯字典序写出的哈希不同）；
- 数字、重复的键、`__proto__`、孤立的代理项按 `JSON.parse`/`JSON.stringify` 的语义；
- 哈希是规范文字的 UTF-8 字节的 SHA-256。测试向量（M0 的 S0 与 S1 同一个结果、模板、键序的边界）在 contracts 的单元测试里。
- 存量文档的哈希为空时按"不同"处理（第一次保存多一个修订）；只改了视图状态（缩放、滚动）的保存判为相同（计划书 §7.3）。

**链接的判定与改写**（DEF-021）：判定在 contracts 的 `link-address.ts`（计划书 §11.3，r16 的细化），前后端共用。它只信任各引擎必然一致的部分，保证**任何浏览器判为合法的规范写法，服务端（Node）也判为合法且相等**——页面按本引擎的结果改写，否则那份表格在某些浏览器里从此存不进去（审查 B1：Chromium 内核把主机里的空白、`*` 编成 `%20`、`%2A`，`mailto` 在 `?` 之前的空格不编码）：`http(s)` 的主机只收 LDH 标签（另放 `_`）、点与 IPv4，不收 IPv6，别的写法原因 `host`；规范写法里空白、双引号、尖括号、反引号与 `|` 一律编码、查询里的单引号编成 `%27`，于是规范写法里不出现能改写剪贴板 HTML 结构的字符（SDK 复制带链接的单元格时把地址原样拼进双引号的 `href`，审查 B2；单引号保留的前提是 SDK 写双引号的属性，SDK 升级时重新核对）；跨引擎的性质检验（逐字符扫描与随机拼接的地址在三个浏览器里判定，合法的交给 Node 再判）在 E2E 里。反过来"Node 收、浏览器不收"的有两类——IDN 的 Unicode 版本（新近分配的字符），与 Bidi 规则（含 RTL 字符的标签本身四个引擎检查一致，只有浏览器把它核对到同一个域名里其余的标签）——只影响收不收：浏览器打不开、改写器在编辑时去掉链接，不会让存下的写法在 Node 一侧不合法（复验 C5）。页面在写入之前改写（ADR-010 的 M3-P3 补充）；服务端的检查是最终防线（被拒而不是存进不规范的地址）。P3 之前存下的内容不在载入时改写、也不做数据迁移：v0.1 上线之前没有真实数据。

**数据**（迁移 0024，只做加法）：`document_contents.content_hash`（32 字节）与 `resource_names`（两列同空同有）；`documents.client_build`、`formulas_pending`；`document_revisions.content_hash`、`client_build` 与 `created_at` 的索引；新表 `document_save_receipts`（`request_id` 主键、`document_id`、`revision`、`payload_digest`、`saved_by`、`saved_at`、`created_at`）。`requestId` 跨两张表的唯一由 `requestId` 的锁加锁下查两张表保证（`RequestLedger`，审查 A3：保存、新建、复制、另存为副本都在事务的第一步取同一把锁，每个事务至多一把、而且是第一把，不与文档行、空间行、空间树的锁成环）：回执用过的 `requestId` 再拿去新建、复制、另存为副本，新建一类用过的再拿去保存，都回 `REQUEST_ID_CONFLICT`；两张表各自的唯一约束与 `ON CONFLICT` 留作兜底。

**"公式待更新"**：保存与另存为副本带 `formulasPending`；写入新内容时把标记设成请求里的值；内容相同时只清不设（库里与请求都为真才留着：公式的结果存在单元格里、参与内容哈希，内容相同就是结果相同，库里已经收齐的不因这次捕获没等到收齐而改成待更新；审查 A6）；详情、编辑状态与申请编辑权的响应带上它（M3-P4 据此在进入编辑时强制重算、阅读页给出说明）。存量一律当作没有标记。

**保留期**：修订记录与回执保留 `NERVE_REVISION_RETENTION_DAYS` 天（默认 30，下限 15——要长于 M4 发件箱的 14 天，否则发件箱里结果未知的保存重放不到原来的结果）。应用内的定时任务（ADR-016 的补充）删掉早于保留期、**而且不是文档当前修订**的修订记录（冲突的来源与申请编辑权要读当前修订那一行；修订号只增不减，一行一旦不是当前修订就永远不是，所以不锁文档行），以及早于保留期的回执（按写下的时间）；`FOR UPDATE SKIP LOCKED`，不与保存、申请编辑权排队。保留期就是保存、新建、复制、另存为副本的幂等窗口：过了之后同一个 `requestId` 按新请求处理；新建之后没再保存过的文档，那一行就是当前修订，一直可以重放。

**档案**：快照检查用的档案现在写死为表格（`INSPECTED_PROFILE`），M6 按文档类型选。

## M3-P4 的补充：打开自检失败的上报

依据 M3-P4 设计 §3.11、§3.13（US-M3-15）。

- `POST /api/documents/{id}/open-check-failures`，204、无响应体，documents 模块。请求体（contracts 的 `open-check.ts`，严格解析）：`revision`（载入内容的修订号）、`access`（`read`、`edit`）、`trigger`（`open`、`enter`、`refresh`、`exit`、`lost`、`reload`）、`failures`（1–32 项：种类取八种之一——`profile-missing-hook`、`profile-unexpected-hook`、`parse-threw`、`parse-swallowed`、`load-threw`、`serialize-threw`、`resource-missing`、`resource-emptied`；`resource` 限 SDK 资源名的写法；`error` 只许构造器名的写法 `^[A-Z_$][\w$]{0,63}$`，生产构建压缩之后的类名带 `$`、数字与下划线）、版本四项（必填）。**不带**快照、资源的 `data`、异常的 message（`JSON.parse` 的报错带输入片段）。
- 能读就能报（只读快照里 `requireAccess`，看不到、不存在、回收站里的一律 404，语句序列相同）；标 `@BackgroundRequest()`（页面自己发的，不顺延登录）。
- 进程内去重（文档、修订号、失败签名、构建；10 分钟窗口）与按账户限量（每个账户一个固定的 10 分钟窗口、从第一次被采纳算起，至多 20 条被采纳；超出的照样 204、不记，每个窗口记一条 `event: 'open-check-reports-throttled'`）；计时用进程的单调时钟（进程内状态，不是落库的业务判断）。采纳的记一条 warn，`event: 'open-check-failed'`（M7 按它告警），服务端补上当前修订号与文档的档案；不记审计（系统信号，不是用户操作）。单实例首发，进程内状态按进程计。
- 页面每次创建的结果至多报一次，会话不是本人时不发，不看结果、不重试。
