# ADR-011：文档内容与保存协议

> 状态：已接受｜日期：2026-09-27｜来源：M1-P4

## 背景

- 00 号计划书 §7.1–§7.4、§8.1–§8.4、§12：全量快照；修订号条件写入；`requestId` 幂等；冲突附来源；快照用 `bytea` 存 gzip 压缩的原始 JSON 字节；新建用收敛的模板；`unitId` 与文档 id 独立；档案与格式版本；解压后 5 MiB 的上限。
- M1 总设计 §2.1、§6.5：显式保存（没有自动保存与租约）；M1 只做基本校验，完整的校验与内容哈希在 M3。

## 决策

**数据**（迁移 `0006_document_content`，只做加法）：
- `documents` 补上 `revision`（新建为 1，每次保存加一）、`unit_id`（服务端生成的 UUID，唯一，终身不变）、`profile`（`sheet@1`）、`format_version`（1）、`sdk_version`（写入时平台内置的 Univer 版本；客户端上报与拦截旧客户端在 M3）；
- `document_contents`：每份文档一份当前快照（gzip 的字节、解压前后的字节数）；
- `document_revisions`：每次新建或保存一行（修订号、种类、`request_id` 唯一、负载摘要、保存的来源 `clientInstanceId` 与 `localSeq`、保存人），不存正文。

**接口**：
- `POST /api/documents`：`{ type, title?, requestId }`，在个人空间里建文档，内容是模板换上新的 `unitId`（服务端 `JSON.parse` → 换 `id` → `JSON.stringify`，模板本身就是 `JSON.stringify` 的输出，逐字节不变）。同一个 `requestId` 的重放同样 201，返回那份文档的当前元数据；并发的相同请求按 `requestId` 取事务级 advisory lock 排队。
- `GET /api/documents/{id}/content`：数据库里的 gzip 字节原样下发（`Content-Encoding: gzip`），修订号作 ETag（`"<修订号>"`）；修订号与内容一条语句读出。
- `PUT /api/documents/{id}/content?baseRevision&requestId&clientInstanceId&localSeq`：正文是 gzip 压缩的快照（`application/gzip`），不经 JSON 请求体的解析器；成功返回 `{ revision, savedAt }`。

**保存的处理顺序**：
1. 读取正文：在认证与 CSRF 之后（路由的拦截器）；压缩前后都限 5 MiB，解压到上限就停下（413）；只接受恰好一个完整的 gzip 成员、末尾没有别的数据：存下的字节原样下发，浏览器只解第一个成员、忽略之后的数据，只有单个完整的成员两边解出的内容才一定相同，所以用标准的 `DecompressionStream`，不用会解开全部成员的 `zlib`；上传中途断开按请求中断处理（400，warn 日志）；
2. 与文档无关的基本校验（UTF-8 的 JSON 对象、工作簿的结构、顶层 `id` 是字符串、嵌套不超过 64 层；422 `SNAPSHOT_INVALID`）；
3. 一个事务：先不加锁读文档并判断能否编辑（没有权限与不存在相同；只能查看的同样不取锁；权限查询走事务的连接）→ 锁住文档行（`FOR UPDATE`），锁下再判断一次（期间移到别的空间或授权被收回）→ 按 `requestId` 幂等（同一个人对这份文档的同一次保存才返回原结果，负载摘要按基准修订号与解压后的字节算）→ 顶层 `id` 等于文档的 `unit_id` → 基准修订号等于当前修订号（否则 409 `DOCUMENT_REVISION_CONFLICT`，`details` 带当前修订号及其来源）→ 写内容、修订号加一、写修订记录与审计。

**客户端**：
- 保存的状态机（`features/sheet-editor/save-coordinator.ts`）：提交正在编辑的单元格 → 等公式收齐（最多 3 秒）→ 捕获 → 体积检查 → gzip → 上传。已保存的序号只前进到捕获时的序号（保存期间的修改仍算未保存）。
- 结果未知的保存（网络错误、5xx、回包读不出来）都记下来（只记序号与公式是否收齐，不留快照）：内容与基准都没变的重试沿用同一个 `requestId`；冲突的来源是其中之一时，说明那次保存其实已经提交（自己追自己），换上当前修订号用新的 `requestId` 重发一次。其他冲突进入"版本冲突"，保留本页内容，禁止继续保存，提供重新加载。

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| A. 快照用 gzip 的 `bytea`，原样下发 | 采用 | 计划书 §8.1：`jsonb` 不接受 `\u0000`、会重排键；gzip 省空间，读取时浏览器自动解压 |
| B. 保存的正文用 JSON（`{ snapshot, baseRevision, … }`） | 否决 | 全局的 JSON 解析器上限 256 KiB；把 5 MiB 的快照解析再序列化一遍也没有必要 |
| C. 修订号用时间戳或内容哈希 | 否决 | 整数修订号最简单，冲突的判断与 ETag 都直接；内容哈希在 M3 另作"内容相同不递增" |
| D. 先查幂等再锁文档 | 否决 | 同一个请求的两次并发重试，后到的一方会误报冲突；先锁文档，拿到锁时前一方已经提交 |
| D2. 先锁文档行再判断权限 | 否决（P4 审查 A2） | 没有权限的请求也在别人的文档行上取锁，所有者的保存随之排队；等锁的时间还能区分"别人的"与"不存在的"。改为先不加锁判断权限，通过之后再锁 |
| E. 只按最近一次结果未知的保存识别"自己追自己" | 否决 | 连续两次都没收到回包、其实是较早的一次提交了时，会误报冲突 |

## 影响

- 新错误码：`DOCUMENT_REVISION_CONFLICT`、`REQUEST_ID_CONFLICT`、`SNAPSHOT_INVALID`、`PERMISSION_DENIED`；错误响应加可选的 `details`（ADR-006）。
- M3：完整的快照校验与规范化内容哈希（内容相同不递增）、`If-None-Match` 与 304、拦截旧客户端（`CLIENT_OUTDATED`）、编辑租约与阅读模式、自动保存与捕获时机。M4：发件箱与压缩放进 Worker。修订记录保留 30 天与历史版本在后续的 M。
- 模板随 SDK 与档案更新：`pnpm --filter @nerve-office/e2e run update:sheet-template` 经产品本身生成（直到连续两次保存相同），E2E 回归"新建的文档打开后立即保存，快照与模板逐字节相同"。
