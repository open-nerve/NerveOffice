# ADR-005：PostgreSQL 18 与迁移策略

> 状态：已接受｜日期：2026-09-26｜来源：M1-P2

## 背景

- 00 号计划书的要求：
  - 锁定 PostgreSQL 的大版本，镜像按摘要引用（§1.3、§9.2）；
  - 用 PG 的 advisory lock 防止将来多实例时重复执行（§9.3）；
  - 数据库采用受控迁移、发布前先备份，不在每个应用实例启动时并发执行不可逆的迁移（§12.4）。
- 规范 §5 的要求：
  - 迁移由 Drizzle 生成 SQL，人工审阅后入库；合并到 main 的迁移不再修改，只向前；
  - 迁移用单独的命令执行，并用 advisory lock 防止并发；应用启动时只检查库结构的版本；
  - 命名、事务与参数化查询的规则。
- M1 总设计 §6.2：迁移用同一个镜像执行一次性命令，在启动应用之前运行。
- drizzle-orm 0.45.3 的迁移器（P2 开头的核实）：
  - 没有 advisory lock；
  - 全部待执行的迁移放在一个事务里；
  - 只按时间戳判断是否执行（`created_at < when`）。库里存了哈希但不校验：时间戳乱序的迁移会被静默跳过，已执行的迁移被改动也发现不了。

## 决策

**数据库**：
- PostgreSQL 18.6（ADR-002）；新库用内置的 `C.UTF-8` 排序规则，数据页校验和开启。
- 主键用 18 内置的 `uuidv7()`：按时间递增，索引局部性好，也不暴露自增序号（规范 §4）。

**生成**：
- `pnpm db:generate --name <名称>`：drizzle-kit 按 `src/db/schema/*/index.ts` 生成 SQL。
- drizzle-kit 用自己的加载器读表定义，运行时给 Node 加 `--conditions=@nerve-office/source`，与 TypeScript、Vite、ESLint 一样读 contracts 的源码。
- 枚举用 `text` 加 CHECK 约束；取值是代码里的常量，拼成 SQL 字面量（drizzle-kit 不会把参数内联进 CHECK）。
- 表定义之外的对象（触发器、函数）用 `--custom` 另建手写迁移。生成的与手写的分开，都要人工审阅后入库。
- 迁移目录不做 lint 与格式化，保持 drizzle-kit 的原始输出。

**执行**：`node dist/cli/migrate.js`（开发环境是 `pnpm db:migrate`）。步骤：
1. 用一个独立的连接执行 `set_config('lock_timeout', …)`，然后执行 `pg_advisory_lock(hashtextextended('nerve-office:migrations', 0))`。等不到锁就失败，提示另一个迁移正在执行。
2. 比较库里已执行的迁移与这次带来的迁移（`compareMigrations`）：
   - 已执行的必须是前缀，哈希与时间戳逐个一致；
   - 一致时不做任何事；是前缀时，交给 drizzle 的迁移器在一个事务里执行剩下的；
   - 其他情况一律拒绝，退出码 1。
3. 释放锁，关闭连接。

**库结构版本检查**：
- 就绪探针与迁移命令共用 `compareMigrations`；
- 应用启动时只检查、不迁移；版本不一致时就绪探针失败（P2-S4）。

**只向前**（门禁 `migrations`，放在静态检查里）：
- **目录本身**：
  - journal 与 SQL、快照一一对应；
  - 序号从 0 起连续；
  - 时间戳严格递增。
- **与基准版本比较**：
  - 已合并的 SQL 文件与快照都没有变化，journal 条目的名称与时间戳没有变化；
  - 新迁移只追加在末尾。
- **基准的取法**：
  - 本机是与 `main` 的分叉点；
  - CI 的推送事件是推送之前的提交（工作流把 `github.event.before` 传给 `GATE_MIGRATIONS_BASE`，检出取完整历史），一次推送里含多个合并也都在比较范围内；定时与手动触发是 `HEAD^1`；
  - 取不到基准时失败，不静默通过。
- **写法**：迁移名是"四位序号_名称"，名称只用小写字母、数字与下划线；快照的 `prevId` 连成链。
- **表定义与迁移同步**（门禁 `schema`）：对迁移目录的副本执行一次 drizzle-kit generate。生成了新文件就失败；没有生成文件，但 drizzle-kit 没有给出"没有变化"的结论（改列名等要交互确认的变更，在非交互终端里只报错），同样失败。
- **破坏性变更**：分成"扩展 → 迁移数据 → 收缩"几步发布。

**表的归属与访问**：
- 表定义放在 `src/db/schema/<模块>/index.ts`；一个模块只能引用自己的表定义，表定义之间经 `index.ts` 互相引用（外键）。由 eslint-plugin-boundaries 强制。
- 只有 database 模块、各模块的仓储与表定义能引用 `drizzle-orm`、`pg`（`no-restricted-imports`，按包名锚定开头）。后端不用动态导入，相对引用写 `.ts`，保证按路径与包名的限制认得出每一种引用（P2 设计 §3.1）。
- SQL 只用参数：
  - 不用 `sql.raw`；
  - `query()`、`execute()` 的第一个参数（SQL 文本）不能直接写成带插值的模板字符串或拼接（`+`、`concat()`）；其余写法由审查保证；
  - 表定义里的 CHECK 常量是唯一的例外。

**连接池**：
- 语句超时、等锁超时、事务中空闲的超时与 `application_name` 作用在每个连接上，取自配置；
- 每个连接挂常驻的 error 监听：借出期间连接被断开（事务中空闲超时、数据库重启、网络中断）也只记日志，不让进程退出（审查 A1）；
- TCP keepalive，空闲 10 秒后开始探测；客户端侧的查询时限为语句超时加 5 秒（审查 A8、复验 N2）；
- 退出时在 HTTP 请求与处理器排空之后关闭（ADR-004）。

**事务**：
- 服务用 `TransactionRunner.run()` 开启事务，拿到不透明的 `Transaction`，显式传给仓储；服务因此拿不到查询数据库的能力（审查 B2）；
- 仓储的方法接受可选的 `Transaction`，用 `executorOf(db, transaction)` 换回执行器，没有事务时用连接池；
- `TransactionRunner` 自己借出、归还连接，在这个连接上执行 drizzle 的事务（复验 N8）。原因是 drizzle 0.45.3 在连接池上自己借连接时有两个问题：
  - `BEGIN` 失败时不归还连接，会耗尽连接池；
  - 归还时不说明是否出错，没能发出 `ROLLBACK` 的连接会带着未结束的事务回到池里，下一个事务提交时把它一起提交。
- 归还的规则：以 `AppError` 结束时回滚已经成功，连接照常放回；其他失败，或者连接不是空闲状态，一律丢弃连接；
- work 吞掉失败的语句却正常返回时，事务已中止，`run()` 报错并回滚，不报告成功；预期会失败的语句放进保存点或改用 `ON CONFLICT`。判断的方法是在 work 之后执行一条 `SELECT 1`（事务中止时必然报 25P02），不读驱动记下的事务状态：错误与 ReadyForQuery 分开到达时，状态还没更新（M1-P3 修正）；
- 需要跨模块放进同一个事务的写入（例如 P4 的新建文档加审计），由服务开启事务并传给各个模块。

**审计表只追加**：
- `BEFORE UPDATE OR DELETE`（按行）与 `BEFORE TRUNCATE`（按语句）的触发器直接报错。
- 前提：应用使用的数据库角色不能是表的所有者或超级用户，否则它可以关掉触发器（`ALTER TABLE … DISABLE TRIGGER`）。生产上迁移用表的所有者，应用用只有必要权限的角色（P5 落实，审查 A21）。

**集成测试的数据库**：
- 每个测试文件使用独立的数据库，从模板库复制；
- 模板按迁移的名称、内容哈希与时间戳命名，迁移不变时跨运行复用；
- 模板在 advisory lock 下先用临时名创建并迁移，完成后再改名，半成品不会被复用。

## 备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| A. drizzle-kit 生成；执行时自己加锁、比较，再交给 drizzle 的迁移器 | 采用 | 迁移器的单事务与记录表够用，只缺锁与校验，包一层即可 |
| B. 直接用 `drizzle-kit migrate` 或 drizzle 的 `migrate()` | 否决 | 没有锁；不校验哈希；乱序的迁移被静默跳过 |
| C. 自己写迁移执行器 | 否决 | 重复 drizzle 已有的能力，多一份要维护的代码 |
| D. 应用启动时自动迁移 | 否决 | 00 号计划书 §12.4：多实例会并发执行；不可逆的迁移要先备份 |
| E. 用入库的校验和清单保护已合并的迁移 | 否决 | 清单本身也能被一起改掉；以 git 里的基准版本为准更可靠 |
| F. 测试之间用事务回滚隔离 | 否决 | 规范 §8.1 要求每个测试文件独立的数据库；并发、锁、DDL 与提交后的行为都需要真实提交 |

## 影响

- **新增表**：
  1. 在 `src/db/schema/<模块>/index.ts` 写表定义；
  2. 执行 `pnpm db:generate --name <名称>`；
  3. 审阅生成的 SQL，与代码一起提交。

  需要触发器等对象时，另写 `--custom` 迁移。
- **部署**（P5）：迁移作为一次性任务，在启动应用之前执行；发布前先备份（M7 完善备份与恢复）。
- **升级 drizzle**：
  - 重跑 `migrations.test.ts`，确认哈希算法仍与 drizzle 的迁移器一致；
  - 重跑迁移的集成测试。
- **安装脚本**：drizzle-kit 带来的 esbuild 的安装脚本不执行（`allowBuilds`）。它只校验本平台的原生二进制，pnpm 已按平台装好。
