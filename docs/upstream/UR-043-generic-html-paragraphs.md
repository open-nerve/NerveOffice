# UR-043 一般来源的 HTML 粘贴进表格时，段落边界被忽略

状态：草稿，未发送上游。本项目按已知限制登记（DEF-082，需求方 2026-11-10 决定，M7 前再评估），没有修补。固定 `@univerjs/sheets-ui@1.0.1`。发现于 M5-P8 S6 原生补验 N7（真实 Safari 27 与 Chrome 156，2026-11-09、11-10）。

## 现象

在 macOS“文本编辑”里写三段：文字、一张图片、文字。全选复制，到表格单元格按 ⌘V。两种浏览器交给网页的 HTML 都是三个 `<p>`，结果却不同：

- **Safari**：中间一段是 `blob:` 图片，末尾另有 `<br class="Apple-interchange-newline">`。两段文字拼进同一格，成为“Q-14 富文本样本：甲乙丙 123图片后的文字 456”，段落之间没有任何分隔。
- **Chrome**：中间一段只有一个 `<br>`（图片不在 HTML 里）。前后两段分进上下两格。

文字没有丢失，但段落结构依赖来源 HTML 里有没有 `<br>`：同一份内容在两种浏览器上得到不同的结构，Safari 上相邻段落的词语直接相连。

## 根因

sheets-ui 的 `HtmlToUSMService.convert`（`src/services/clipboard/html-to-usm/converter.ts`）分两步：

1. `process` 把整段 HTML 转成一个文档体：文字节点追加到 `dataStream`；`<br>` 追加段落标记 `\r` 并登记一个段落；`<p>`、`<div>` 等块级元素本身不产生段落标记，只有命中粘贴插件（Word、飞书、Univer 来源）的 `afterProcessRules` 时才会补上。
2. `convert` 按段落标记把文档体拆成行：每个段落写进一个单元格，向下排列；最后一段为空时跳过。

所以对一般来源，`<p>` 的边界丢失、相邻段落直接拼接；`<br>` 则变成“换到下一格”。

## 建议

对没有命中插件的一般来源，块级元素结束时同样补段落标记（或按块级元素拆行），并保证段落之间至少有一个分隔，避免词语相连。修改时需要同时考虑表格（`<table>`）与插件来源的现有行为。

## 证据与复现

- 原生记录：主目录 `.codex/handoffs/m5-p8-20261106/s6/native-host-04/cases/n7-safari/`（Safari）与 `native-host-05/cases/n7-chrome/`（Chrome）的录制器原件，含 paste 事件的 types 与 HTML，以及粘贴后的工作表快照；服务端保存的正文在 `native-host-05/saved/`。
- 最小复现（按源码推断，尚未单独运行）：在默认配置的表格里粘贴只带 `text/html` 的 `<p>甲</p><p>乙</p>`，预期两行或同一格内两段，实际一格“甲乙”；改为 `<p>甲</p><p><br></p><p>乙</p>` 则得到上下两格。提交前在 SDK 默认配置下补跑并截图。
