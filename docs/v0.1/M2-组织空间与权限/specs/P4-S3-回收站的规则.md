# P4-S3 回收站：规则细则

> 状态：定稿｜日期：2026-09-30｜修订：2026-10-01，M2-P6 第 3 片复核（§3 删掉 `origin_space_id`，§4 永久删除前的核对，§7 锁下核对的用例）｜所属：M2-P4 S3｜上层依据：00 号计划书 §5.3、§5.4；M2 总设计 §6.8；P4 设计 §3.4 第 3 条

删除与恢复的级联最容易出歧义，这份 spec 把每条规则写死，S3 的实现与测试逐条对照。

## 1. 删除单元

- **粒度**：一次删除产生一个删除单元（`trash_entries` 的一行），内容是**一份文档**，或**一个文件夹连同它当时正常状态的全部子孙**（子文件夹与文档）。
- **不重组已有的删除单元**：如果子树里有早先单独删过、已经在回收站里的东西，它们**留在原来的删除单元里**，不并入这次的。理由是"一起删的一起恢复"：早先那次删除是另一个人、另一个时间点的决定，恢复它不应该被后来的删除改变。
- **写的内容**：`space_id`（当前所在空间）、`kind`（`document` 或 `folder`）、`deleted_by`、`deleted_at`、`expires_at = deleted_at + 30 天`、`origin_parent_id`（**被删的那一个对象**的原位置；原来另有 `origin_space_id`，总是等于 `space_id`，M2-P6 复核时由迁移 0018 删掉；子孙的位置不单独记，它们跟着父辈）、`title`（被删对象删除时的标题或名称，回收站列表显示用）。
- **被删的行**：`status = 'trashed'`、`trash_entry_id` 指向这次的单元（两列必须在同一条语句里一起写，CHECK 要求二者一致）；文档的 `write_epoch + 1`（删除会改变谁能写，P2 交接单第 55 行）；文件夹的层数不变。

## 2. 谁能删

| 对象 | 空间管理员 / 个人空间所有者 | 编辑者 | 查看者 |
|---|---|---|---|
| 文档 | 任意 | 仅本人创建的 | 不能 |
| 文件夹 | 任意 | 仅当子树里正常状态的文档**全部**是本人创建的（子文件夹是谁建的不论；空文件夹满足） | 不能 |

- 判断在**锁下**用一条计数语句做（`COUNT(*) WHERE created_by <> 操作者 AND status = 'active'`），不在纯函数里：展开子树之后可能有人往里移进别人的文档。被它挡下时是 403 `FOLDER_HAS_OTHERS_DOCUMENTS`（专门的码）；归档空间里被挡是 403 `PERMISSION_DENIED`"空间已归档，只能查看"。两者不能混，界面按码给说明。
- 归档的空间里所有人至多是查看者，所以**归档空间里不能删**（403，说明"空间已归档，只能查看"）。
- 回收站里的东西不能再删（`NOT_FOUND`：回收站里的对象对普通接口一律当作不存在）。

## 3. 恢复

- **谁能恢复**：先要有**编辑者及以上**的有效角色，再看是不是删除者本人或当前的空间管理员（个人空间的所有者）。恢复是把内容放回空间里，属于改动，所以按**当前**的权限算：删完之后被移出空间的人不能再恢复（连回收站都看不到），被降为查看者的人也不能（S7 补矩阵时发现原来漏了这一条）；空间归档时有效角色至多是查看者，所以谁都不能恢复（403）。
- **整单恢复**：属于这个删除单元的全部行一起回到正常状态，`trash_entry_id` 清空；删除单元的行删掉。文档的 `write_epoch` **不再加一**（删除时已经加过，恢复不改变"谁能写"的判断依据）。
- **回到哪里**（只对被删的那一个对象判断，子孙跟着父辈）：
  1. `origin_parent_id` 为空 → 空间的根目录；
  2. 原来的父文件夹还在、状态正常、还在同一个空间里 → 回到它下面；
  3. 否则（被永久删除、自己也在回收站里）→ **回到空间的根目录**，响应里带一个标志说明位置变了。（M2-P6 复核更正：原来还列了"跨空间移动过"，这种情形不会出现——父文件夹跨空间移动时，子树里回收站的行与删除单元一起搬走；代码里改成了不变量失败。）
- **层数**：按恢复后的位置重算整棵子树的层数（**包括留在回收站里、属于别的删除单元的子孙**——否则它们带着旧层数留下来，之后这个文件夹的合法移动会被误判成超限，审查 A2）。恢复不会让层数超过 10 层：删除不改父子关系，移动时的判断已经保证整棵子树装得下。
- **同名**：同一个文件夹里允许同名，恢复不改名、不追加后缀。
- **顺序**：恢复不依赖别的删除单元。子孙里属于别的删除单元的东西**仍然留在回收站**。

## 4. 永久删除

- **谁能**：空间管理员 / 个人空间所有者（`canPurgeTrash`）。归档空间里不能（403）。
- **删什么**：这个删除单元里的全部行（文件夹与文档），文档的内容与修订记录随外键 cascade；删除单元的行本身。审计留着。
- **连带**：如果子树里还有属于**别的**删除单元的行（见 §1 的"不重组"），它们的原位置随这次永久删除消失，所以**一并永久删除**；那些删除单元的行在变空之后一起删掉。审计的 `details` 只记**份数**，不记 id 列表：审计明细有 4096 字节的上限，无界的 id 数组在连带上百个单元时会让整个永久删除失败（审查 A1 实测 110 个即 500，而且那一单永远删不掉）。
- **审计**：`documents.purged`、`folders.purged`；自动清理时操作者记为系统（`actor_type = 'system'`）。
- **删之前的核对**（M2-P6 复核之后）：展开子树之后、删任何一行之前，数一遍其中正常状态的文件夹与文档；有就按意外错误回滚、不删（人工 500，自动清理记为失败并暂缓）。不变量"正常的行不会挂在回收站的文件夹下"一旦被任何缺陷打破，原来会静默地永久删除正常的数据。

## 5. 回收站里的东西不能做什么

- 打不开：内容接口返回 `NOT_FOUND`（与"不存在"一致）；已经打开的编辑器保存时同样被拒。
- 不出现在：按空间与文件夹的列表、搜索、导航；P5 的"与我共享"同样排除。
- 不能改名、移动、复制、再删除：普通接口一律 `NOT_FOUND`。
- 能出现在：回收站的列表（按空间）。**看得到空间内容的人都能看到这个列表**（标题在删除之前他本来就看得到），但只有 §3 里的人能恢复、§4 里的人能永久删除。

## 6. 回收站的列表

- 按空间列出删除单元，`deleted_at DESC, id DESC` 的 keyset 分页（与文档列表一致）。
- 每条给出：`kind`、`title`、`deletedBy`（显示名）、`deletedAt`、`expiresAt`、原位置（父文件夹的名称，父不在时说明"原位置已不存在"）、里面的文档份数（`kind = 'folder'` 时）、以及当前这个人能不能恢复 / 永久删除（`permissions`）。
- 份数用一条按删除单元 id 的计数得到，不展开子树。

## 6b. 跨空间移动与删除单元（S2b 之后补）

文件夹的跨空间移动会把子树里**已经在回收站的东西一起搬走**（S2b 的不变量：一个删除单元不会被拆散在两个空间）。因此删除单元的登记空间要跟着改：

- 子树整体换空间时，**完全落在这棵子树里**的删除单元，`space_id` 改成新空间（原来连同已删掉的 `origin_space_id` 一起改）；`origin_parent_id` 不用改，它指向的文件夹也在这棵子树里，跟着搬了。
- 判断"完全落在子树里"：删除单元的全部行（文件夹与文档）都在子树的 id 集合里。S2b 保证的正是这一点——删除单元要么整体在子树里、要么整体不在，所以取一行判断即可。
- 实现的位置：`trash_entries` 的读写只在 S3 的仓储里，由 `FoldersService` 在搬完子树之后调用；这条要写进 S3 的集成测试（移动 → 在新空间的回收站里看得到 → 恢复回到新空间的原位置）。

## 7. 并发

- 删除、恢复、永久删除都是结构性改动：事务里先取**空间树的 advisory lock**，再 `holdSpace`，再在锁下重新判断（S1 的范式）。
- 因此下面这些组合有确定的结果：
  - 删文件夹与往里移文档同时发生：谁先拿到树锁谁先做；移动在删除之后发生时，目标文件夹已经在回收站里 → `NOT_FOUND`。
  - 恢复与永久删除同时发生：后到的那个看到删除单元已经不在 → `NOT_FOUND`。
  - 删除与保存内容同时发生：保存不取树锁，两者都可能先成功；删除之后的保存被拒（文档已在回收站），删除之前的保存照常写入（内容随后进回收站）。
- 到期的自动清理（S4）与人工的永久删除、恢复之间同样靠树锁互斥。
- **树锁取的是"取锁之前读到的那个空间"的锁**：8 处锁下核对（文件夹改名与移动、文档改名与移动、删文档、删文件夹，恢复与永久删除共用一处，到期的自动清理一处）都在锁下再确认对象还在这个空间里，期间被移到别的空间就不做改动：人工的操作回 `NOT_FOUND`，自动清理跳过这一单、留给下一轮；子树在锁下才展开。这几处是承重的：少了其中一处，正常的文档会挂到回收站的文件夹下、随那一单被永久删除。M2-P6 复核之后每处都有确定交错的用例（6 处与永久删除在 `documents/structure-locks.test.ts`，恢复在 `documents/trash.test.ts`，自动清理在 `jobs/trash-purge.test.ts`），原来只有恢复与自动清理两处有。

## 8. 集成测试要覆盖的格子

1. 编辑者删自己的文档 ✓ / 删别人的 ✗；删只有自己文档的文件夹 ✓ / 里面有别人文档的 ✗；空文件夹 ✓。
2. 空间管理员删任意；查看者一概不能；归档空间一概不能。
3. 删文件夹：子树全部进同一个删除单元；早先单独删过的那份文档仍属于原来的单元。
4. 恢复：原位置还在 → 回原处；原位置被永久删除 / 也在回收站 → 回根目录并带标志；恢复后层数正确。
5. 恢复的权限：删除者、空间管理员 ✓；同空间的另一个编辑者 ✗；被移出空间的删除者 ✗；被降为查看者的删除者 ✗；归档 ✗。
6. 永久删除：内容与修订记录一起没了；连带删除属于别的单元的子孙，那些单元也一起清掉。
7. 回收站里的文档：列表、搜索里没有；打开、保存、改名、移动、复制都是 `NOT_FOUND`。
8. 并发：§7 的四种组合各一条（用 `support/held-lock.ts`）。
9. `write_epoch`：删除加一，恢复不加。
