# M2-P2 团队空间与有效权限：架构设计与实施规划

> 状态：已完成｜日期：2026-09-29｜基于代码版本：`aa22c53`

## 1. 目标与范围

对应 M2 总设计 §5 的 P2 一行：团队协作的基本单元就位，权限按空间角色计算。

- **用户故事**：
  - US-M2-05（团队空间）、US-M2-06（成员与空间角色）全部完成；
  - US-M2-04 补上停用者文档的转移，整条故事改为 `active`；
  - US-M2-14 建立权限矩阵的框架，完成空间部分的格子（这条故事在 P5 改为 `active`）。
- **范围内**：
  1. 团队空间：系统管理员创建（名称、首个空间管理员、是否全员可见）、设置全员可见、归档与恢复；改名（系统管理员与空间管理员都可以）。
  2. 成员与空间角色：
     - 查看成员；添加（按名字搜索同事）、调整角色、移出；
     - 团队空间至少保留一个空间管理员；
     - 系统管理员把自己加入空间（记审计）。
  3. 有效权限的空间部分：
     - 权限只经 documents 的访问策略计算，目标是文档或空间；
     - "可访问文档"的查询，本 Phase 用于按空间列出；
     - 无权与不存在一致。
  4. 新建文档到任意有新建权限的空间；M1 的接口保持兼容。
  5. `writeEpoch` 与"收回写入权"的入口：
     - 停用账户、移出空间、降低空间角色、归档空间，都经这个入口；
     - 转移文档时递增代次。
  6. 停用者个人空间文档的转移：系统管理员只看得到标题。
  7. 前端：
     - 左侧导航、空间页、成员页；
     - 管理界面的团队空间页与文档转移页；
     - 编辑器页的返回链接回到文档所在的空间。
  8. 权限矩阵测试的框架与空间部分。
- **范围外**：
  - 文件夹、文档重命名、移动、复制、回收站与搜索（P4）；
  - 单独分享与"与我共享"（P5）；
  - 查看者的只读加固（P3）。本 Phase 之后查看者就出现了：服务端拒绝他们保存，编辑器仍只靠 `setEditable(false)`，见 §7。

## 2. 现状

基于 `aa22c53`（M2-P1 合并之后）：

- **spaces 模块**：
  - 只有个人空间。表 `spaces` 的类型只有 `personal`、状态只有 `active`（都是 CHECK）。
  - 已有 `visible_to_all` 列（默认假），以及"个人空间必须有所有者、不能全员可见"的 CHECK。
  - 没有创建人列，也没有成员表。
  - 服务只有三个方法：建个人空间、查个人空间、`isOwner`（不看空间类型）。
  - 没有控制器，不依赖其他业务模块。依赖它的有 users（建账户时建个人空间）、auth（会话响应带个人空间）、documents（访问策略、列表与新建）。
- **documents 模块**：
  - 访问策略 `DocumentAccessPolicy`（抽象类）只有 M1 的一条规则：文档所在的空间是这个人的个人空间。目标只有 `spaceId`。
  - `requireAccess` 对不存在的文档也用全零的空间判断一次，两条路径的查询相同（M1-P3 审查 A4）。
  - 列表只列个人空间：`GET /api/documents` 没有空间参数，契约是严格结构。
  - 新建：在事务之外读个人空间、不经策略；返回的权限写死为 `owner`；`requestId` 的负载摘要不含空间。
  - 保存：先判断、再 `FOR UPDATE` 锁文档行、锁下再判断（ADR-011）。
  - 模块没有导出任何服务；控制器从 auth 引用 `@CurrentPrincipal()`。
- **admin 模块**：
  - 只有控制器与编排。
  - 停用在一个事务里完成：改状态、作废重置、撤销会话、记审计。
  - P1 交接单约定：P2 在停用里接上"收回写入权"，文档行排在账户行之后。
- **users 模块**：
  - 同事目录 `GET /api/users?query=`，只含有效账户；
  - `findByIds` 可以批量补名字；
  - `lockActingAdmin` 在共享的 system-admins 锁里复核操作者。
- **审计**：对象类型 `space` 已经登记，但从来没有用过；审计查询只给账户与邀请补名字。
- **前端**：
  - 页头下面没有侧栏，首页是"我的空间"的文档列表；
  - 新建表格不带空间；
  - 管理界面（按需加载）有账户、邀请、审计三页；
  - 编辑器页的返回链接写死为 `/`；
  - 平台页面首屏 156.5 KiB（预算 180 KiB）。
- **测试**：
  - 集成测试里没有空间与权限矩阵的用例；
  - "无权与不存在一致"：集成测试只比较响应，查询序列相同由单元测试保证；
  - E2E 与集成测试都直接写库建个人空间与文档，负载摘要的算法在测试辅助里各有一份。

**依赖方向带来的约束**（§3.1 的出发点）：
- users、auth、documents 都依赖 spaces，spaces 不能反过来依赖它们，否则 lint 的 `import-x/no-cycle` 与 Nest 的模块装配都会失败。
- 空间管理员用的成员管理同时要用到四样东西：
  - 当前登录的人（auth 的 `@CurrentPrincipal()`）；
  - 同事的名字与状态（users）；
  - 有效权限（documents）；
  - 移出成员时的"收回写入权"（documents）。
- 所以这些接口放不进 spaces。

## 3. 设计

### 3.1 模块划分与依赖方向

```text
admin ─────────► documents、spaces、users、auth、audit   系统管理：团队空间的创建、全员可见、归档与恢复；停用（接上收回写入权）；停用者文档的转移
workspace（新）─► documents、spaces、users、auth、audit   面向成员的空间接口：我能看到的空间、空间页头、成员、改名
documents ─────► spaces、auth、audit                     文档；有效权限（唯一入口）与"可访问文档"；writeEpoch 与收回写入权
auth ──────────► users、spaces、audit
users ─────────► spaces、audit
spaces ────────► （database）                            空间与成员的数据与不变量；没有控制器
```

**spaces**：负责团队空间与成员的数据与不变量，即 M2 总设计 §6.2 里的"团队空间；成员与空间角色"。
- 查询：
  - 权限用的"空间事实"：类型、状态、全员可见、是不是所有者、成员角色，一条语句取出；
  - 我能看到的空间的候选；
  - 成员列表；
  - 团队空间的列表（管理用）。
- 变更：
  - 建团队空间（连同首个空间管理员）、改名、全员可见、归档与恢复；
  - 成员的添加、调整、移出；"至少保留一个空间管理员"在这里检查。
- 锁：改动空间与成员时，对空间行取 `FOR NO KEY UPDATE`；在空间里新建文档、作为转移的来源与目标时，取 `FOR SHARE`。
- 不判断谁能做：授权由调用方经 documents 的访问策略决定。

**documents**：
- 访问策略（§3.4）：有效权限的唯一入口，目标是文档或空间。操作规则（§3.4 的表）也在这里：接口告诉界面"能做哪些操作"，服务端做检查，用的是同一套规则。
- "可访问文档"的查询（§3.5）。
- 文档：按空间列出、新建到指定的空间、详情带所在的空间。
- `writeEpoch` 与"收回写入权"的入口（§3.7）。
- 转移：只改所属空间、递增代次，不读内容（§3.8）。
- 导出访问策略与收回写入权（workspace 与 admin 用），以及停用者文档的转移与标题列表：这一项不经内容权限，lint 只允许 admin 引用（审查 A9）。

**workspace（新）**：面向成员的空间接口与编排，没有自己的表。
- 接口都在 `/api/spaces` 下：空间列表、空间页头、成员的查看与管理、改名。
- 成员的变更要在一个事务里完成四件事：经策略授权、改 spaces 的数据、调 documents 的收回写入权、记审计。所以它放在 documents 之上。

**admin**：系统管理员的团队空间管理（创建、全员可见、归档与恢复、列表）、停用（接上收回写入权）、停用者文档的转移。

依赖图无环（lint 强制）；spaces 保持没有控制器、不依赖其他业务模块。admin 与 workspace 是最上层的编排，只由 app 层组装，别的模块都不引用它们（lint 强制，复验 N2）：admin 转出的东西流不到别的模块。

**这个划分是对 M2 总设计 §6.2 的补充**：新增 workspace 一行；spaces 一行明确为"数据与不变量"。它属于跨模块的调整，已经需求方确认（2026-09-29，选定 §7 的方案一），M2 总设计 §6.2 同步补上。

### 3.2 数据模型与迁移

一次迁移（`0009`），只做加法（ADR-005）：

| 表 | 变化 |
|---|---|
| spaces | 类型加 `team`，状态加 `archived`（都是 CHECK）。<br>新列 `created_by`：账户，外键，可空。<br>CHECK（重建原来的 `spaces_personal_check`）：团队空间没有所有者、有创建人；个人空间有所有者、没有创建人、不全员可见、不能归档。<br>部分唯一索引：团队空间的名称唯一，不区分大小写（`lower(name)`），已归档的也算 |
| space_members（新） | 列：`space_id`（外键；空间删除时级联，v0.1 不删空间）、`user_id`（外键，restrict）、`role`（`admin`、`editor`、`viewer`，CHECK）、`created_at`、`updated_at`。<br>主键（空间，用户）；按用户的索引（查"我能看到的空间"用） |
| documents | `write_epoch`：integer，默认 0，CHECK ≥ 0；存量数据为 0（M2 总设计 §6.3） |
| audit_events | 动作的 CHECK 扩充（§3.9） |

- 成员只属于团队空间，由 spaces 的服务保证。访问策略计算个人空间时只看所有者、不看成员行，多一道防线。
- 空间的 `updated_at` 在改名、全员可见、归档与恢复时更新。
- 团队空间的名称要唯一：
  - 导航里同名的空间无法区分；
  - 创建的重试不会建出两个同名空间：管理接口不带 `requestId`，与 P1 的邀请一样靠唯一约束。
  - 并发的创建与改名由唯一索引兜住：这两条语句放进保存点，撞上唯一约束时只回滚到保存点，转成 `SPACE_NAME_TAKEN`（事务里直接失败的语句会让整个事务中止）。
- 新表由迁移以所有者身份建，默认权限自动授权给应用角色（ADR-012）。

### 3.3 接口契约

请求结构严格、响应结构宽松（沿用 M1 的约定）。路径都在 `/api` 下。请求里的 UUID（路径、查询参数与请求体）大小写都接受，契约统一转成小写：服务端按字符串比较 id 的地方（是不是本人、审计的明细、收回写入权的范围）只见到小写（审查 A1）。

**文档（documents，兼容 M1）**：

| 接口 | 说明 |
|---|---|
| `GET /documents?spaceId=&limit=&cursor=` | 按空间列出：看得到这个空间才行，否则 404。没有 `spaceId` 时列个人空间（M1 兼容） |
| `POST /documents` | `{type, title?, requestId, spaceId?}`。要有新建权限；没有 `spaceId` 时建在个人空间（M1 兼容）；带 `spaceId` 时负载摘要包含它（§3.6） |
| `GET /documents/{id}` | 详情加 `space: {id, type, name}`，给编辑器页的返回链接用 |

**空间（workspace）**：

| 接口 | 访问 | 说明 |
|---|---|---|
| `GET /spaces` | 登录 | 我能看到的空间 → `{items: SpaceView[]}`。<br>包括：个人空间、我是成员的团队空间、全员可见的团队空间（含已归档的）。<br>个人空间在前，团队空间按名称排序；不分页（§7） |
| `GET /spaces/{id}` | 看得到这个空间 | `SpaceView` |
| `PUT /spaces/{id}/name` | 团队空间的空间管理员、系统管理员 | `{name}` → `TeamSpace` |
| `GET /spaces/{id}/members` | 在团队空间里有空间角色的人、系统管理员 | `{space: TeamSpace, canManage, items: SpaceMember[]}`。<br>先按角色（管理员、编辑者、查看者）、再按显示名排序；含停用的成员，带状态 |
| `POST /spaces/{id}/members` | 空间管理员、系统管理员 | `{userId, role}` → 201 `SpaceMember`。<br>操作者把自己加入时，审计记为"系统管理员加入空间"（§3.9） |
| `PUT /spaces/{id}/members/{userId}` | 同上 | `{role}` → `SpaceMember` |
| `DELETE /spaces/{id}/members/{userId}` | 同上 | 204 |

- `SpaceView`：`{id, type, name, status, visibleToAll, role, permissions: {canCreateDocuments, canViewMembers, canManageMembers, canRename}}`。`role` 是调用者的有效空间角色：查看者、编辑者、空间管理员；个人空间的所有者算空间管理员。
- `SpaceMember`：`{user: {id, username, displayName}, status, role, createdAt}`。
- `TeamSpace`：`{id, name, status, visibleToAll}`。成员页的页头与改名的响应用它，不带调用者的角色：没有加入的系统管理员也在这些地方管理团队空间，而空间的内容对他是看不到的。

**系统管理（admin，只给系统管理员）**：

| 接口 | 说明 |
|---|---|
| `GET /admin/spaces?query=&status=&cursor=` | 团队空间列表：名称包含关键词，可以按状态过滤；按创建时间从新到旧，每页 50 条 → `{items: AdminSpace[], nextCursor}` |
| `POST /admin/spaces` | `{name, adminUserId, visibleToAll}` → 201 `AdminSpace` |
| `PUT /admin/spaces/{id}/visibility` | `{visibleToAll}` → `AdminSpace` |
| `POST /admin/spaces/{id}/archive`、`POST /admin/spaces/{id}/restore` | → `AdminSpace` |
| `GET /admin/users/{id}` | 一个账户（含停用的）：转移页的页头；不存在时 404 |
| `GET /admin/users/{id}/documents?cursor=` | 停用者个人空间里的文档：`{items: [{id, title, type, updatedAt}], nextCursor}`。账户仍然有效时 409 `ACCOUNT_NOT_DISABLED` |
| `POST /admin/users/{id}/documents/transfer` | `{documentIds, target}` → `{transferred}`（转移页用自己选的目标显示结果）。<br>`documentIds`：1–100 个，不重复。<br>`target`：`{type: 'personal', userId}` 或 `{type: 'team', spaceId}`；不能是操作者自己的个人空间（403，§3.8） |

- `AdminSpace`：`{id, name, status, visibleToAll, memberCount, createdAt, myRole}`。`myRole` 是当前系统管理员在这个空间里的角色，没有加入时为空。
- 系统管理员改名与管理成员，用上面空间的接口：那些接口的授权规则里包含系统管理员。

**新增错误码**：

| 错误码 | 状态 | 用途 |
|---|---|---|
| `SPACE_NAME_TAKEN` | 409 | 团队空间的名称已被使用（不区分大小写，已归档的也算） |
| `ALREADY_MEMBER` | 409 | 要添加的人已经是成员；改角色请用调整的接口 |
| `LAST_SPACE_ADMIN` | 409 | 这个操作会让团队空间一个空间管理员都不剩 |
| `ACCOUNT_UNAVAILABLE` | 409 | 指定的账户不存在或已停用。用于添加成员、首个空间管理员、转移的目标 |
| `ACCOUNT_NOT_DISABLED` | 409 | 只有停用的账户，才能转移它的文档 |
| `SPACE_ARCHIVED` | 409 | 转移的目标空间已归档 |
| `TRANSFER_CONFLICT` | 409 | 要转移的文档里，有的已经不在这个人的个人空间里（例如被别人转走了），请刷新后重试 |

看不到的空间与不存在的空间，都是 `NOT_FOUND`；看得到却没有这个操作的权限，是 `PERMISSION_DENIED`（ADR-006）。

### 3.4 有效权限与操作规则

**唯一入口**：documents 的 `DocumentAccessPolicy`，扩展为有效权限（M2 总设计 §6.1）。
- 它只做计算，不读别的模块的表：空间的部分经 spaces 的"空间事实"；P5 再并上本模块的单独授权。
- 方法：

```ts
accessOf(userId, document?, tx?)      → DocumentAccess | undefined  // 文档：有效角色与所在的空间
spaceAccessOf(actor, spaceId, tx?)    → SpaceAccess | undefined     // 空间：有效角色与能做的操作
visibleSpaces(actor, tx?)             → SpaceAccess[]               // 导航与"可访问文档"
```

- `actor` 是 `{userId, systemAdmin}`。系统角色只影响空间的管理操作，不带来任何内容权限（00 号计划书 §5.2）。

**空间角色**（从低到高：查看者、编辑者、空间管理员）：
- 个人空间：所有者是空间管理员；其他人，包括系统管理员，都没有角色。个人空间的成员行一概不计（§3.2）。
- 团队空间：取成员的角色；全员可见时，任何有效账户至少是查看者；归档时所有人至多是查看者。
- 文档的有效角色：本 Phase 就是所在空间的角色。P5 改为与单独授权取较高者；归档时同样至多是查看者。
- M1 的 `owner` 并入"空间管理员"：角色的叫法统一为空间角色的三级。

**操作规则**：只列 M2 总设计 §6.1 中本 Phase 涉及的部分；"看不到"一律是 `NOT_FOUND`。

| 操作 | 允许 | 看得到却不允许 |
|---|---|---|
| 阅读文档、按空间列出、空间页 | 有空间角色 | — |
| 保存 | 编辑者及以上 | `PERMISSION_DENIED`（查看者、归档空间里的所有人） |
| 在空间里新建文档 | 空间角色是编辑者及以上；归档时至多是查看者，所以不能新建 | `PERMISSION_DENIED` |
| 查看成员 | 团队空间：有空间角色的人，或系统管理员 | 个人空间的所有者：`PERMISSION_DENIED` |
| 管理成员与空间角色 | 团队空间：空间管理员（空间没有归档），或系统管理员（归档的空间也可以） | 其他有空间角色的人：`PERMISSION_DENIED` |
| 改名 | 团队空间：空间管理员（空间没有归档），或系统管理员 | 其他有空间角色的人：`PERMISSION_DENIED`；个人空间不能改名 |
| 创建团队空间、全员可见、归档与恢复、转移 | 系统管理员（管理接口） | 非系统管理员：`PERMISSION_DENIED`（会话守卫）；转移的目标是操作者自己的个人空间：`PERMISSION_DENIED`（§3.8） |

**什么叫"看得到"**：
- 有空间角色；或者
- 是系统管理员，目标是团队空间，而且操作是空间的管理（查看成员、管理成员、改名）。

所以，系统管理员没有加入的团队空间，它的空间页与文档对他是 `NOT_FOUND`；个人空间对他始终是 `NOT_FOUND`。

**无权与不存在一致**（M2 总设计 §6.1）：
- 空间：空间事实用一条语句取（空间行左连接这个人的成员行）。空间不存在与看不到，执行的是同一条语句，之后同样判断、同样抛 `NOT_FOUND`。
- 文档：先按 id 读文档，再对它所在的空间计算；文档不存在时用全零的空间计算。两条路径的查询序列相同（沿用 M1）。
- 需要锁的操作，一律"先判断（不加锁）→ 加锁 → 锁下再判断"：看不到的请求不取锁（ADR-011 的做法）。
- 测试：单元测试断言两条路径的查询序列相同；集成测试比较响应；耗时的对照测试随 P5 的 US-M2-14 补齐（§4）。

**系统管理员的复核**：
- 请求里的系统角色来自会话守卫。
- 空间的管理操作要用到系统角色时，事务第一步取 system-admins 的共享锁复核（P1 的 `lockActingAdmin`）。
- 复核发现他已经不是系统管理员时，按普通成员判断。

### 3.5 "可访问文档"的查询

- 一个人能访问的文档 = 他看得到的空间里、正常状态的文档。P5 并上单独授权的文档，P4 排除回收站里的文档。
- documents 的仓储里只有一处拼这个条件：输入是空间 id 的集合，P5 再加授权。列表、搜索、计数、"与我共享"都经它（M2 总设计 §6.1）。
- 本 Phase 只有按空间列出：先经策略确认看得到这个空间，再按这一个空间取。
- 不在 SQL 里跨模块联表（规范 §1.2：仓储只用本模块的表）。约 100 人的规模下，一个人看得到的空间只有几个到几十个，把 id 集合作为参数就够了；M7 压测时复核。

### 3.6 新建文档到指定的空间

在一个事务里：
1. 按 `requestId` 取 advisory lock，查已有的修订记录；重放的处理同 M1。
2. 确定目标空间：请求里的 `spaceId`；没有时是本人的个人空间。
3. 经策略判断能否新建，不加锁：看不到是 `NOT_FOUND`，不能新建是 `PERMISSION_DENIED`。
4. 对空间行取 `FOR SHARE`，锁下再判断一次。它与归档、移出成员（`FOR NO KEY UPDATE`）互斥：归档或移出提交之后的新建，一定被拒绝。
5. 建文档、内容与修订 1，记审计；返回的权限按有效角色计算，不再写死为 `owner`。

负载摘要：
- 带 `spaceId` 时，摘要加上空间 id（按小写计）；
- 不带时与 M1 的摘要相同，升级前后的重试照样按重放处理；
- 测试辅助直接写库的文档等同于不带空间的新建，摘要不变。

### 3.7 `writeEpoch` 与"收回写入权"

- `documents.write_epoch`：M2 只递增、不检查。M3 的租约与保存按"代次与修订号都匹配"写入（00 号计划书 §6.4）。
- 递增的时机：本 Phase 只有转移（跨空间移动）；P4 的删除与跨空间移动，同样在事务里递增。
- **收回写入权的入口**：documents 导出 `revoke(scope, transaction)`。范围有四种：
  - 某人：停用账户；
  - 某人在某个空间：移出空间、降为查看者；
  - 整个空间：归档；
  - 某人在某份文档：取消或降低单独授权（P5 加）。
- M2 没有租约，入口里没有要终止的东西：权限的变化与这次调用在同一个事务里提交，下一次请求重新判断权限，即被拒绝。M3 在入口里终止失去写入权的人持有的租约，并递增那些文档的代次。调用方现在都已接上，M3 不用改调用方。
- 调用点：
  - 停用（admin），排在撤销会话之后；
  - 移出成员、调整角色（workspace）；
  - 归档（admin）。
- 调整角色时一律经入口，由入口按变化后的权限判断谁失去了写入权（M3）；调用方不自己判断。例如空间管理员降为编辑者，并不失去写入权。

### 3.8 停用者文档的转移

**标题列表**：
- 只对停用的账户；只返回标题、类型与更新时间，不返回内容（00 号计划书 §5.4）。
- documents 提供"按空间列出标题"，不经内容权限，只由 admin 调用。

**转移**：目标是操作者自己的个人空间时直接拒绝（403 `PERMISSION_DENIED`）：00 号计划书 §5.4 写的是"转移到其他人的个人空间"，转给自己就等于打开了内容（审查 A7）。界面的同事候选已排除本人；万一收到，前端按管理接口的约定多确认一次会话（得到 `PERMISSION_DENIED` 时怀疑系统角色过时），无害（复验 N4）。其余在一个事务里：
1. 取 system-admins 的共享锁，复核操作者。
2. 按 id 顺序锁账户行：
   - 来源账户 `FOR SHARE`，复核它仍是停用的；
   - 目标是个人空间时，目标账户 `FOR SHARE`：必须有效，而且不是来源账户本人。
3. 目标是团队空间时，先判断（不加锁）：不是团队空间（写成团队空间的个人空间）或不存在，一律 `NOT_FOUND`，执行同样的查询，不在那一行上取锁（复验 N1）。
4. 按 id 顺序对空间行取 `FOR SHARE`：来源的个人空间；目标空间（锁下再判断：团队空间必须没有归档）。
5. 按 id 顺序对文档行取 `FOR UPDATE`，只锁还在来源的个人空间里、状态正常的（与标题列表同一个条件）：锁到的份数少于请求的，就整批拒绝（`TRANSFER_CONFLICT`）。请求里夹带的别处的文档不被锁住（审查 A4）；等锁期间被别人转走的，拿到锁之后按新的内容重新判断，同样整批拒绝。
6. 改所属空间，`write_epoch` 加一；`updated_at` 不变，因为内容没有改。
7. 每份文档记一条审计 `documents.transferred`：来源与目标空间的 id，不记标题。

另外：
- 一次最多 100 份，界面分批转移。
- 转移不经内容权限：它是系统管理员的操作，授权靠系统角色（在锁里复核），而且不读内容。
- 转到系统管理员自己是成员的团队空间，他随后看得到内容：这与他把自己加入团队空间一样是允许的，每份文档都有审计（见 §7）。
- 转移之后再启用这个账户，他的个人空间里就没有转走的文档了。启用的确认文案随之修改。

### 3.9 团队空间与成员的流程

**锁的顺序**（ADR-007 的补充，延伸到空间与文档）：

system-admins 的 advisory lock → 按登录名的 advisory lock → 账户行（多行按 id）→ 重置行或邀请行 → 限流计数 → 会话行 → 空间行（多行按 id）→ 成员行 → 文档行（多行按 id）→ 审计。

新建文档另有按 `requestId` 的 advisory lock，排在最前。

下面各流程里的"复核"，指 system-admins 的共享锁与操作者的复核；带括号的一步，只在操作者是系统管理员时执行。

- **创建团队空间**：
  1. 复核操作者；
  2. 首个空间管理员的账户行 `FOR SHARE`，必须有效，否则 `ACCOUNT_UNAVAILABLE`；
  3. 建空间与成员行；名称冲突时 `SPACE_NAME_TAKEN`；
  4. 记审计。
- **全员可见、归档、恢复**：
  1. 复核操作者；
  2. 判断是团队空间，不加锁；不是时 `NOT_FOUND`（个人空间的行上不取锁，审查 A4）；
  3. 空间行 `FOR NO KEY UPDATE`，锁下再判断；
  4. 改状态；归档时收回写入权，范围是整个空间；
  5. 记审计。

  没有变化时原样返回、不记审计（沿用 P1）。
- **改名**：（复核操作者）→ 判断 → 空间行 `FOR NO KEY UPDATE` → 锁下再判断 → 改名 → 记审计。名称冲突时 `SPACE_NAME_TAKEN`（由唯一索引兜住并发）；名称没有变化时原样返回、不记审计。
- **添加成员**：
  1. （复核操作者）；
  2. 判断，不加锁；
  3. 目标账户行 `FOR SHARE`，必须有效，否则 `ACCOUNT_UNAVAILABLE`；
  4. 空间行 `FOR NO KEY UPDATE`，锁下再判断；
  5. 已经是成员时 `ALREADY_MEMBER`；
  6. 加成员行，记审计。
- **调整角色、移出**：
  1. （复核操作者）；
  2. 判断；
  3. 空间行 `FOR NO KEY UPDATE`，锁下再判断；
  4. 成员不存在时 `NOT_FOUND`；空间管理员会一个不剩时 `LAST_SPACE_ADMIN`；
  5. 改或删成员行；
  6. 收回写入权，范围是这个人在这个空间；
  7. 记审计。

**至少保留一个空间管理员**：
- 在空间行的锁下，数空间管理员的成员行，不看账户状态。停用的空间管理员仍占一个位置：系统管理员可以先补上新的空间管理员，再移出停用的。
- 两个空间管理员同时互相降级，只有一个成功。
- 空间管理员可以降低或移出自己（只要不是最后一个），之后立即失去相应的权限；界面另有确认文案。

**审计**：新增的动作如下；已发布的动作不改名、不复用。

| 动作 | 操作者 | 对象 | details |
|---|---|---|---|
| `spaces.created` | 系统管理员 | 空间 | 首个空间管理员的 id、是否全员可见 |
| `spaces.renamed` | 系统管理员或空间管理员 | 空间 | 原名称与新名称 |
| `spaces.visibility_changed` | 系统管理员 | 空间 | 是否全员可见 |
| `spaces.archived`、`spaces.restored` | 系统管理员 | 空间 | — |
| `spaces.member_added` | 空间管理员或系统管理员 | 空间 | 成员的 id、角色 |
| `spaces.admin_joined` | 系统管理员（把自己加入） | 空间 | 角色 |
| `spaces.member_role_changed` | 空间管理员或系统管理员 | 空间 | 成员的 id、原角色与新角色 |
| `spaces.member_removed` | 空间管理员或系统管理员 | 空间 | 成员的 id、原角色 |
| `documents.transferred` | 系统管理员 | 文档 | 来源与目标空间的 id |

- 审计不记文档标题（M2 总设计 §2.1 第 5 条）。空间的名称可以记：改名要留下原来的名字。
- 审计查询给空间补上当前的名称，做法与给账户、邀请补名字一样。

**左侧导航**（`features/spaces`）：
- 条目：我的空间（`/`）、团队空间（`/spaces/{id}`，已归档的带标记）。P5 加"与我共享"。
- 状态：加载中、失败（可以重试）、还没有团队空间时的说明。

**空间页**：`/` 是本人的个人空间，`/spaces/{id}` 是任意空间。
- 页头显示名称（个人空间显示"我的空间"）、类型、状态、是否全员可见、我的角色。
- 按 `permissions` 只显示能做的操作：新建表格（建在这个空间）、成员、改名（行内表单，不用弹窗）。
- 文档列表沿用 M1 的列表，改为按空间取。
- 看不到的空间显示"空间不存在或无权访问"。
- 页内的新建表格、改名按访问权限被拒绝（403：例如空间刚被归档；404：空间看不到了）时，页头与导航重新请求，按新的权限显示；有焦点的按钮随之消失时，焦点交给页标题（复验）。

**成员页**：`/spaces/{id}/members`，按需加载的 `features/members`。
- 成员表：名字、登录名、状态、角色。
- 能管理时：按名字搜索同事添加（选角色）、调整角色（原生选择框，每一行各自保存：选了立即显示目标角色、这一行标为忙碌，失败时恢复并在这一行说明）、移出（确认弹窗，之后焦点回到页标题）；降低或移出自己另有确认文案。
- 看不到的空间（404）显示"空间不存在或无权访问"，不管缓存里有没有旧的成员表；个人空间（403）显示服务端给出的原因（"个人空间没有成员"），不给重试；已归档的空间对系统管理员另有说明。
- 移出得到 404（这个人已经被别人移出）：刷新成员列表之后关闭确认的弹窗，在页面上说明；角色保存成功时先用响应更新这一行，再刷新（复验）。
- 只能查看时，只显示表格。
- 系统管理员从管理界面的团队空间页进来，用的也是这一页。

**同事选择**（`features/colleagues`）：
- 按名字搜索同事：用 P1 的同事目录，输入停顿之后才请求；只显示与输入框里的关键词一致的候选。
- 成员页、创建团队空间、转移的目标共用；与转移页按名称选团队空间共用一个"按关键词选一项"的组件（审查 B13）。
- 标签说选的是什么（"要添加的同事""接收文档的同事""目标团队空间"），怎么找写在输入框的提示里；选中之后标签仍在，"重新选择"带上标签。
- 只被按需加载的页面引用，不进首屏。

**管理界面**（按需加载的 `features/admin`）：
- 团队空间页（`/admin/spaces`）：
  - 列表：名称、状态、是否全员可见、成员数、我的角色；可以搜索、按状态过滤。
  - 创建：名称、首个空间管理员、是否全员可见。
  - 全员可见的开关、归档与恢复（先确认）、改名。
  - "成员"跳到成员页；没有加入时，可以"加入空间"（选角色）。
- 账户页：停用的账户多一个"转移文档"，进入转移页（`/admin/users/{id}/documents`）：
  - 标题列表：分页、可以多选；超过 100 份时说明"请分批转移"，不能提交；
  - 目标：某人的个人空间（用同事选择，操作者本人不在候选里），或者团队空间（按名称搜索没有归档的团队空间）；
  - 确认之后转移；得到 `TRANSFER_CONFLICT` 时刷新标题列表、去掉已经不在的选中项、关闭确认的弹窗，在转移按钮旁说明原因（再点确认不会原样重发，复验）；其他失败在确认弹窗里说明。
- 启用的确认文案：不再说"文档都没有变"。

**编辑器页**：
- 返回链接回到文档所在的空间：本人的个人空间显示"我的空间"（`/`）；团队空间显示它的名称（`/spaces/{id}`）。
- 加载失败时，仍然回到 `/`。

**按需加载的边界**：

### 3.11 权限矩阵测试的框架

集成测试放在 `tests/integration/src/permissions/`：
- 一套固定的角色：
  - 个人空间的所有者；
  - 团队空间的空间管理员、编辑者、查看者；
  - 与这些空间都没有关系的成员；
  - 没有加入的系统管理员。
- 一套固定的目标：个人空间、团队空间、全员可见的团队空间、归档的团队空间，以及不存在的空间与文档。
- 矩阵是一张表：每行一个操作，每列一个"角色 × 目标"，格子里写预期：成功的状态码、`PERMISSION_DENIED` 或 `NOT_FOUND`。按格子生成用例，标题以 `US-M2-14` 开头。
- 每个 `NOT_FOUND` 的格子，另与"不存在"的同一操作比较响应：去掉请求标识之后应当相同。
- 会改数据的操作（添加成员、改名等），每格用自己的空间，或者做完之后复原。
- 预期由表格直接写出，不调用生产代码的规则来算，免得"用实现验证实现"。

本 Phase 的格子：阅读文档与内容、保存、按空间列出、在空间里新建、空间页、查看与管理成员、改名，以及管理接口（创建、全员可见、归档与恢复、转移）。P4、P5 加行与列：文件夹、移动、复制、回收站、授权。

## 7. 风险与未决问题

**已确认：空间接口放在哪个模块**（2026-09-29 需求方选定方案一）。三个方案的对比留作记录：

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| 一（推荐） | 新增 workspace 模块，放面向成员的空间接口与编排；spaces 只管数据与不变量 | 每个模块的职责单一；documents 不再膨胀；依赖是单向的一层叠一层 | 多一个模块；M2 总设计 §6.2 补一行 |
| 二 | 空间接口放进 documents | 不新增模块 | documents 本来就要装文档、文件夹、回收站、复制、分享、搜索与权限，再加空间与成员的接口，成了大杂烩 |
| 三 | 空间接口放进 admin | 不新增模块 | admin 现在的约定是"全部接口只给系统管理员"；混进空间管理员的接口，权限检查容易出错，审查也难核对 |

**其他风险**：

| 风险 | 应对 |
|---|---|
| 查看者从本 Phase 起出现（全员可见、查看者角色、归档空间），编辑器的只读在 P3 之前只靠 `setEditable(false)`，SDK 可能把它改回可编辑 | 服务端拒绝保存（`PERMISSION_DENIED`），这是写入的边界；P3 紧接着做只读加固。服务端的拒绝由集成测试的矩阵逐格断言，本 Phase 的 E2E 断言界面的"只能查看" |
| 列表、搜索、计数在 P4、P5 扩展时漏掉权限条件 | "可访问文档"的条件只在仓储里拼一处；矩阵逐格覆盖，P4、P5 加格子 |
| 先查空间、再查文档是两条语句，两条之间权限可能变了 | 列出的是变化之前看得到的内容；下一次请求即生效（与 M2 总设计 §4 的承诺一致），写入另由锁与锁下的再判断保证 |
| 导航与成员列表不分页 | 约 100 人的规模下，一个人看得到的空间、一个空间的成员都是几十个的量级；登记延期，M7 压测时复核 |
| 平台页面的首屏超预算 | 导航与空间页不引入新的第三方运行时；成员页、同事选择、管理界面按需加载；预算门禁核对 |
| 一次转移大量文档，事务过长 | 一次最多 100 份，界面分批 |
| 团队空间名称唯一，与 E2E 并行共用一个库冲突 | E2E 的名称带随机后缀 |
| 进行中的保存与归档、移出、降级不互斥（审查 A3）：保存只锁文档行，这些操作只锁空间行。保存已经通过锁下的判断时，归档先提交，保存随后提交，归档空间里的文档又多一个修订。同类：空间管理员的管理操作与他本人被停用不互斥 | 已接受（与 §3.7 的承诺一致：下一次请求即被拒绝）。新建对空间行取共享锁，是因为新建在事务里判断空间；保存要与撤权互斥，得在每次保存上多锁一行，M3 接入租约时由"代次与修订号都匹配"的写入与撤权终止租约收口（交接单） |
| 团队空间的名称全局唯一，创建与改名撞名会透露一个看不到的同名空间存在（审查 A8） | 已接受：名称唯一是为了导航里可以区分；约 100 人的组织里团队空间的名称不是秘密，系统管理员都看得到；失败的改名不记审计（没有改动） |
| 系统管理员把停用者的文档转到自己是成员的团队空间，随后看得到内容（审查 A7） | 已接受：与他把自己加入团队空间一样，每份文档都有转移的审计；转到他自己的个人空间则拒绝（§3.8） |
