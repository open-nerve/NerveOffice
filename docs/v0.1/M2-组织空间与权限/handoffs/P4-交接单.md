## 与设计的偏差

都已回写 P4 设计与 ADR-016。

- **补掉一个契约缺口**：新建文档可以直接指定文件夹（原来只能"先建到根目录再移过去"，两步之间失败文档就落在别处）。只有指定文件夹时才取空间树的锁。
- **补漏排一个接口**：文件夹的跨空间移动（设计 §3.2 列了、Step 拆分漏了），补成 S2b。
- **恢复要有编辑者及以上的角色**：补权限矩阵时发现原来的规则不看当前角色，被降为查看者的人仍能把内容放回空间（已修，spec §3 订正）。
- **"文件夹里有别人创建的文档"单独一个错误码**：与"空间已归档"同为 403，前端按码给说明。
- **`AccessibleScope` 收掉了没用过的状态那一维**：回收站的列表从 `trash_entries` 出，不走"可访问文档"的条件。
- 文件夹加 `request_id`（新建的幂等）与几条 CHECK；审计新增 9 个动作、目标类型 2 个、来源 1 个（`job`）。

## 下一个 Phase 须知

- **有效权限仍然只有一个入口**（`DocumentAccessPolicy` + `access-rules.ts` 的纯函数）。P4 加了三组纯函数：`documentPermissionsOf(role, document, userId)`、`folderPermissionsOf(role)`、`trashPermissionsOf(role, deletedBy, userId)`。界面与服务端共用同一份，**服务不自己拼权限条件**。
- **"可访问文档"的条件仍只在 `documents.repository.ts` 的 `accessible(scope)` 一处**：`scope` 现在只有"范围"（空间 id 集合）这一维，状态固定为正常。**P5 的单独授权就并在这里**（范围那一维）；回收站的列表从 `trash_entries` 出，不走这里。
- **结构性改动的串行化**：新建（指定文件夹时）、改名、移动、跨空间移动、复制、删除、恢复、永久删除与定时清理，都在事务第一步取**空间树的 advisory lock**（`SpaceTreeRepository`，唯一入口，内部去重、转小写、按 id 排序）。**保存文档内容不取这把锁**，与结构改动互不阻塞。锁顺序表写在 `space-tree.repository.ts` 的文件头：
  system-admins → 按登录名 → 账户行 → 重置/邀请行 → 限流计数 → 会话行 → **空间树的 advisory lock（按空间 id）** → 空间行（按 id）→ 成员行 → 文件夹行（按 id）→ 文档行（按 id）→ 回收站行 → 审计。新建与复制的 `requestId` 锁排在最前。
- **删除单元的两条不变量**：不重组（早先单独删过的留在原来的单元里）、不拆散在两个空间（子树跨空间移动时，完全落在子树里的删除单元跟着改登记空间）。改动删除、移动、恢复任一条路径时都要保住它们，集成测试里各有一条守门用例。
- **永久删除有连带**：子树里属于别的删除单元的行一并删掉，变空的单元一起清。审计明细只记**份数**——`details` 有 4096 字节的上限，无界的数组会让整个操作失败（审查 A1 的教训，类型已收窄到定长标量）。
- **层数存在列里**（1–10，CHECK 兜底），不靠递归算。凡是"整棵子树改位置"的路径（移动、跨空间移动、恢复）都要**连回收站里的子孙一起重算层数**，否则它们带着旧层数，之后的合法移动会被误判超限（审查 A2）。
- **`jobs` 模块**（ADR-016）：只做"按时触发 + 防重复执行"，删除的语义在 `documents`；清理入口由 lint 限定只有 `modules/jobs/**` 能引用。多实例（DEF-024）时 `nerve-office:trash-purge` 这把会话级 advisory lock 就是"只有一个实例在清"的依据。时钟可注入，测试不必等 30 天。
- **审计的来源多了 `job`**：既不是 `http` 也不是 `cli`。升级要先执行迁移 `0013`，否则新应用写清理的审计会被数据库拒绝。
- **CI 已按浏览器分片**：`verify`（`--scope=no-e2e`）+ 四个 `e2e` 分片 + 容器 job。本机仍是一条 `pnpm verify`；`--scope` 必须与 `--ci` 一起用。两片合起来等于完整一套，由 `tools/src/verify/plan.test.ts` 守住——**以后往 verify 里加步骤，记得那条用例会提醒你分片是否还完整**。
- **前端的约定**：首屏页面不用弹窗（行内表单、行内两级选择），回收站与搜索是各自按需加载的页面（登记进 lint 边界、有自测）；入口一律按服务端给的 `permissions` 隐藏；403/404 之后作废空间、文件夹与文档三组查询；焦点在操作之后回到那一行的"操作"按钮，行消失时由说明条接住。
- **首屏预算**：平台页 168.3 KiB / 180 KiB，余量 11.7 KiB。**P5 要加"与我共享"与分享对话框，设计时先算一笔**；按需加载的部分不进首屏。
- **已知的坑**：
  - 文件夹的"列出一层"按 `lower(name)` 排序，用不上 `(space_id, parent_id, name)` 索引（500 行以内可接受，DEF-030）；
  - 移动文件夹时目标选择器只排除它自己，更深的子孙靠 409 `FOLDER_CYCLE` 拦下；
  - 复制的 `requestId` 按"目标位置"持有：目标 A 结果未知 → 切到 B → 切回 A → 再点，会用第三个 id，可能在 A 处多出一份副本（复制本身就是"再来一份"，危害小于新建）；
  - 本机整轮 E2E 曾出现一次 `specs/editor/conflict.spec.ts`（chrome）点保存 30 秒超时，重跑通过；如果在 CI 上复现，根因要去编辑器那侧查。
