# M2-P6 M2 复核：架构设计与实施规划

> 状态：进行中｜日期：2026-09-30｜所属：M2-P6（插入的 Phase，执行顺序排在 P5 之前）｜依据：需求方 2026-09-30 的决定｜基于代码版本：`d0e0202`（main，P1–P4 已合并）

## 1. 为什么要插入这个 Phase

M2 的 P1–P4 与 P5 的设计是在 Opus 5 上做的，不是需求方要求的 Opus 5.5。会话记录里，模型标识在 P3 的审查修复前后从 5.5 变成了 5；P1、P2 在更早的会话里，当时用的是哪个看不到。大部分代码与全部审查都由子 Agent 完成，它们传的是 `"opus"` 这个别名，很可能同样落在 Opus 5 上。

M2 的质量证据很多——两路独立审查、独立复验、变异测试、权限矩阵 1470 格——但实现者与审查者是同一个模型，**盲点是相关的**。"审查通过、测试全绿"只能说明这个模型自己没看出问题。

**会话记录的精确统计**（每条助手消息的 `message.model`）：主会话 97% 的输出在 Opus 5.5 上；9-29 20:06 起自动变成 Opus 5，之后启动的子 Agent 全部落在 Opus 5。据此，真正在 Opus 5 上做的是 P3 的收尾、9-29 的脱敏、**P4 的全部**与 P5 的设计；P1、P2 与 P3 的主体在 5.5 上。需求方仍决定整个 M2 都复核。

**为什么会自动换模型**：Claude Code 的"内容型自动回退"——安全分类器以 `[cyber]` 标记请求之后，把它换到别的模型重跑，会话随后一直停在那个模型上。两次都发生在处理安全内容的时候（撤下攻击串、核实"限流能被用来锁死账户"）。对策：用户级设置 `switchModelsOnFlag: false`（被标记时暂停让需求方选，不再悄悄换模型），以及下面原则 7、8。

需求方的决定（2026-09-30）：

1. 把 M2 的实现当作**质量不可信**，先复核，再继续 P5（P5 的设计也一起复核）；
2. 按风险切 6 片，依次复核；每片一个分支，单独审、修、合并，CI 绿了再进下一片；
3. 每片由 **Opus 5.5 独立审查**；M2 全部做完之后，再由另一家的模型（Codex）做一次 M 级的整体审核；
4. 作为插入的 Phase P6，执行顺序排在 P5 之前。

## 2. 复核的原则

1. **改动由证据驱动**：只改有复现、有失败的用例、或有存活的变异的问题。不因为"是 Opus 5 写的"就重写——那只是换一个模型再造一批没验证过的代码。
2. **测试本身也不可信**：同一个模型写的测试，可能恰好绕开它自己的盲点。复核要重新做变异与对抗探针，不把"跑一遍全绿"当作通过。
3. **先盲审**：审查者先只看需求（00 号计划书、M2 总设计、各 Phase 的设计与 spec）与代码，自己形成结论之后，再对照之前的审查报告与交接单——专门找"之前说已修复、实际没修好"的地方。
4. **不只看代码**：设计决策（ADR 与 Phase 设计里的取舍）、过程决定（放宽超时、CI 分片、登记延期、实测数字的解读）都在复核范围内。
5. **模型要核对**：主会话开工前核对自己是 Opus 5.5；每个子 Agent 在汇报开头写出自己的模型标识，不是 5.5 就停下来告诉需求方。
6. **决策边界不变**：发现架构层面的问题、要跨模块协同调整、或意料之外的高风险，先提交当前的工作，再停下来请示需求方（`CLAUDE.md` 的推进节奏）。
7. **避开容易被误判为攻击的操作**（需求方 2026-09-30）：参考仓库只用本地的 clone（`refer/univer/`），不远程同步、不去网上看上游；审查写成"代码审查 + 漏洞分诊 + 用测试验证防护是否生效"，不用"攻击者视角""去打"这类说法，也不做洪水式请求、批量伪造请求头之类的演练；攻击串一律不回显、不入库。
8. **被标记就停**：会话暂停或出现"已切到 Opus 5"的提示时，停下判断类工作，先提交、再报告，不在 Opus 5 上继续。子 Agent 的报告里若有落在 Opus 5 上的部分，那部分由主会话在 5.5 上重新核实之后才采用。

## 4. 每片的做法

1. **盲审**：审查者（Opus 5.5 的子 Agent）从工作区克隆到自己的目录，只读需求与代码，形成自己的结论；然后对照之前的审查报告与交接单，找"声称已修复、实际没修好"。每条发现写明位置、为什么是问题、**证据**（复现步骤、探针、变异）、建议的修法；另写"核实过、没有问题的要点"。
2. **核实**：主会话逐条核实，分成三类：真问题（要修）、误报（写明为什么不是问题）、设计取舍（需求方决定的，列出来请示；其余的由主会话按决策原则定）。
3. **修复**：Opus 5.5 的实现者在这一片的分支上修；每条修复都要有能检出它的测试，并做变异验证。
4. **复验**：另一位 Opus 5.5 的子 Agent 独立复验修复，找修复带来的新问题。
5. **收尾**：先 `pnpm clean` 再 `pnpm verify`，另跑容器 E2E；报告写进 `reviews/P6-S{n}-<短名>.md`（格式沿用"问题、处理、复验证据"）；设计、ADR、交接单里受影响的地方同步订正；`--no-ff` 合并、推送、等 CI 全绿，再进下一片。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 审查者提出大量低价值的意见，修复变成改风格 | 原则 1：没有证据的不改；主会话核实时分出误报与取舍，写明理由 |
| 复核中发现架构层面的问题（例如权限模型或锁的设计要推翻） | 原则 6：先提交，停下来请示需求方 |
| 前三片的修复互相牵连（例如 S2 改权限核心，影响 S3 的锁） | 严格按顺序：上一片合并、CI 全绿之后再开下一片，下一片基于最新的 main |
| 测试时长上涨 | 每片收尾时看一眼 CI 最慢的那一片 |
