# M2-P5 分享与 M2 收尾：架构设计与实施规划

> 状态：进行中｜日期：2026-09-30｜所属：M2-P5｜依据：M2 总设计 §5（Phase 规划）、§6.1、§6.3、§6.4；00 号计划书 §5.2、§5.3、§5.4、§5.5｜基于代码版本：`d0e0202`（main，P4 已合并）

## 1. 目标与范围

把"单独分享"补齐，并把越权访问全面验证一遍，然后收掉 M2：

- **单独授权**（`document_grants`）：空间管理员或个人空间的所有者把一份文档分享给同事（查看者或编辑者），可以调整与取消；编辑者不能分享。
- **有效权限并上授权**：对一份文档的有效权限 = 空间角色与单独授权中**较高**的一个；归档的空间里所有人至多是查看者，**包括被单独授权为编辑者的人**。
- **"与我共享"**：只凭授权拿到的文档出现在这里；能看到所属空间的名称，看不到空间的目录结构。
- **越权访问全面验证**（US-M2-14、上线门槛 A03）：权限矩阵补上"只有授权"的这一维；无权与不存在一致；列表、搜索、"与我共享"、回收站都不出现无权的文档；停用、移出空间、取消分享之后下一次请求即生效。
- **M2 收尾**：架构总览与 ADR、M2 交接单与收尾汇报、合并之前的对抗评审（另一家的模型）、`v0.1-m2` 标签。

用户故事：US-M2-10（分享）、US-M2-14（越权访问一律被拒绝）。

**不在本 Phase**：分享给外部链接（v0.1 不做）；文件夹的分享（授权只到文档一级）；编辑租约与强制接管（M3）。

## 2. 现状

- 有效权限只有一个入口：`DocumentAccessPolicy`（实现 `EffectiveAccessPolicy`），事实由 spaces 一条左连接给出，规则是 `access-rules.ts` 的纯函数。**授权那一半还没有**：`accessOf` 只看空间角色。
- "可访问文档"的条件只在 `documents.repository.ts` 的 `accessible(scope)` 一处，`scope` 只有"空间 id 集合"这一维（P4 把状态收成写死的"正常"）。注释里写着"P5 在这里并上单独授权"。
- 权限矩阵 1470 格（内容 150、管理 330、文档 240、文件夹 240、回收站与搜索 150、"在回收站里"360），`ACTORS` 是 6 个（所有者、空间管理员、编辑者、查看者、外人、系统管理员），**没有"只有授权"的人**。
- 永久删除时文档的内容与修订记录随外键级联（ADR-016 写明"`document_grants` 在 P5 建表时在同一处补上"）。
- 跨空间移动与移出空间都不动授权（00 号计划书 §5.4），现在没有授权可动。
- 前端：空间页、文件夹导航、回收站、搜索都已就位；左侧导航有"我的空间 / 团队空间"，**没有"与我共享"**。同事目录 `GET /api/users?query=` 与 `KeywordPicker` 可以直接用来选人。

## 3. 设计

### 3.1 模块划分与依赖方向

不新增模块：

```
workspace ──► documents、spaces、users、auth、audit    分享的接口与"与我共享"（面向成员）
documents ──► spaces、auth、audit                      document_grants 的数据与规则；有效权限（并上授权）；可访问文档
```

- `document_grants` 的表定义放 `db/schema/documents/`，仓储 `document-grants.repository.ts`（一表一仓储）。
- **授权的判断仍然只经 `DocumentAccessPolicy`**：`accessOf` 的一条查询里把"这个人在这份文档上的授权"一起取回来（空间事实左连接授权），规则仍是纯函数。服务不自己拼权限条件。
- 显示名要靠 users（分享列表要显示被授权人的名字），所以**分享列表的组装放 `workspace`**（与回收站列表把 `deletedBy` 换成显示名同一个做法）。

### 3.2 接口契约

| 方法与路径 | 说明 |
|---|---|
| `GET /api/documents/{id}/grants` | 这份文档的授权列表（谁、什么角色、谁授的、什么时候）。要有分享的权限（空间管理员 / 个人空间所有者）才看得到 |
| `PUT /api/documents/{id}/grants/{userId}` | 设置或调整授权：`{ role: 'viewer' \| 'editor' }`。幂等 |
| `DELETE /api/documents/{id}/grants/{userId}` | 取消授权 |
| `GET /api/shared?cursor=` | "与我共享"：只凭授权能访问的文档，按更新时间的 keyset 分页；每条带所属空间的**名称**（不带文件夹路径） |

- 不能给自己授权（400）；不能给停用的账户授权（400，与同事目录一致）；被授权的人必须是有效账户。
- 授权与空间角色互不覆盖：给一个已经是空间管理员的人授"查看者"，他的有效权限仍是空间管理员（取较高者）。这种授权允许存在（人可能之后被移出空间），列表里如实显示。
- 归档的空间里不能改授权（403 `PERMISSION_DENIED`"空间已归档，只能查看"）；回收站里的文档不能改授权（404）。

### 3.3 数据模型与迁移（`0014_m2_document_grants`）

| 表 | 内容 |
|---|---|
| `document_grants`（新） | `document_id`(FK→documents, **ON DELETE CASCADE**)、`user_id`(FK→users, restrict)、`role`(`viewer` \| `editor`)、`granted_by`(FK→users, restrict)、`created_at`、`updated_at`；主键 (document_id, user_id) |
| `audit_events` | `action` 的 CHECK 全量重列，加 `documents.shared`、`documents.share_changed`、`documents.share_revoked` |

- **级联删除**：永久删除文档时授权随之消失（ADR-016 的承诺）。不做软删除：取消分享就是删行，历史在审计里。
- 不加 `(user_id)` 之外的索引组合：`(document_id, user_id)` 的主键覆盖"这份文档的授权列表"与"这个人在这份文档上的授权"；**另加 `(user_id)` 索引**给"与我共享"与"可访问文档"用。
- 移动文档、移出空间、归档都不动这张表。

### 3.4 关键流程

**（1）有效权限并上授权**

`access-rules.ts` 加纯函数：

```ts
effectiveDocumentRole(space: SpaceFacts, grant: GrantRole | undefined): SpaceRole | undefined
```

- 先算空间角色（现有的 `effectiveSpaceRole`，已按归档降级）；
- 与授权取较高者（`viewer < editor < admin`，授权最高只到 `editor`）；
- **归档的空间：结果至多是 `viewer`**（对授权同样降级，00 号计划书 §6.2）；
- 两个都没有 → `undefined`（无权，按不存在回答）。

`EffectiveAccessPolicy.accessOf` 仍然**只执行一条查询**：空间事实左连接这个人在这份文档上的授权行。文档不存在时用那个全零 id 走同样的查询（耗时对齐的做法不变）。

**注意**：`spaceAccessOf`（空间页、按空间列出）**不看授权**——授权不给空间里的任何东西开口子（§5.5：只有授权的人看不到空间的目录结构）。只有"对某一份文档"的判断才并上授权。

**（2）"可访问文档"并上授权**

`accessible(scope)` 的 `scope` 加一维：

```ts
interface AccessibleScope {
  readonly spaceIds: readonly string[]      // 有空间角色的空间
  readonly userId: string                   // 授权那一半：id IN (SELECT document_id FROM document_grants WHERE user_id = ?)
}
```

条件变成 `status = 'active' AND (space_id IN (…) OR EXISTS (授权))`。仍然只有这一处，按空间列出、搜索、"与我共享"都经它：

- 按空间列出：范围是这个空间，**不并授权**（目录结构不对只有授权的人开放）——所以它传的是"只看空间"的那一种范围；
- 搜索：并上授权（能访问的文档都该搜得到）；
- "与我共享"：只要授权那一半。

因此 `accessible` 接受一个"要哪几半"的参数，三个调用方各自说明白自己要什么；停用者文档的转移仍然只看空间那一半（转移是按空间搬，授权不参与）。

**（3）分享的写入**

事务里：不加锁判断分享权限（`canShare`：空间管理员 / 个人空间所有者，归档除外）→ 锁文档行（`FOR UPDATE`，与改名、移动同一档）→ 锁下复核（文档还在、没进回收站、空间没归档、自己还是管理员）→ 读写 `document_grants` → 审计。

- **不取空间树的锁**：授权不改目录结构。
- 取消授权要在同一事务里调 `WriteAccessRevocation.revoke({ kind: 'documents', documentIds: [id] })`（M3 接租约时，取消分享要立刻终止对方的编辑租约）。降级（编辑者→查看者）同样要收回。

**（4）"与我共享"的列表**

- 条件：`accessible` 的授权那一半 + 正常状态；排序与分页与文档列表一致。
- 每条带：文档的元数据、所属空间的**名称与类型**（不带 id 之外的结构信息，不带文件夹路径）、我的有效角色。
- 回收站里的文档不出现（`status` 已经卡住）。

**（5）生效时机（US-M2-14）**

- 取消分享、移出空间、停用：都在下一次请求即生效（授权与空间事实都是每个请求重新读）。
- 已经打开的页面：编辑器页保存时被拒（403 `PERMISSION_DENIED`）；平台页面下一次请求即 404。
- 集成测试逐条验证；E2E 覆盖关键路径（取消分享后访问、移出空间后访问、停用后访问、猜文档地址）。

### 3.5 错误处理、安全与可观测性

- 看不到与不存在一致：授权这一维加进来之后，"无权"的判断路径仍与"不存在"完全相同（同一条查询、同样的 `NOT_FOUND`）。
- **耗时对齐**：`accessOf` 仍是一条查询；本 Phase 加一条"语句数量相同"的断言（无权 vs 不存在），不做时间断言（时间断言在共享机器上不稳定，属于测量噪声）。00 号计划书 A03 里"耗时"这一项以此方式满足，并在 M2 交接单里写明。
- 审计：分享、调整、取消各一条，`details` 记被授权人与角色（不记文档标题），只记定长标量（P4 审查 A1 的教训）。
- 防泄漏：分享列表要有分享权限才看得到；被授权人只看得到这份文档，看不到空间的目录结构；"与我共享"不泄漏文件夹路径。

## 4. 测试策略

| 层级 | 覆盖内容 | 用户故事 |
|---|---|---|
| 单元 | `effectiveDocumentRole`（空间角色 × 授权 × 归档的全部组合）；`canShare`；授权的服务编排（锁顺序、锁下复核、收回写入权）；契约的校验 | 10、14 |
| 集成 | 授权的增改删与幂等；不能给自己、不能给停用的人；归档与回收站里不能改；有效权限取较高者；"与我共享"的内容与分页；按空间列出**不**受授权影响；搜索受授权影响；跨空间移动与移出空间保留授权；永久删除连带删授权；**权限矩阵补上"只有授权"的两个角色**；生效时机（取消、移出、停用之后下一次请求）；无权与不存在的响应与语句数一致 | 10、14 |
| E2E | 分享对话框：按名字搜同事、给查看者/编辑者、调整、取消；对方在"与我共享"里看到并打开（查看者只读、编辑者能改）；取消之后立即不能访问；编辑者看不到分享入口；猜文档地址被拒 | 10、14 |

权限矩阵：`ACTORS` 加两个（只有查看授权的人、只有编辑授权的人），六张表全部扩一列（1470 → 约 1960 格）。新角色在"看不到的空间"里也可能有授权，这正是要验证的格子。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 授权并进"可访问文档"之后，三个调用方要的"半边"不同，容易写错（按空间列出不能并授权） | `accessible` 显式接受"要哪几半"，三处各自写明；集成测试专门验证"按空间列出不受授权影响"与"搜索受授权影响" |
| 矩阵再扩一列，格子接近 2000，集成测试变慢 | 现在 1470 格 5.3 秒，扩一列约 +33%；仍在 10 秒内。超出就把矩阵拆成两个文件并行 |
| 归档对授权的降级容易漏（只降空间角色） | 纯函数里一次降级，单元测试覆盖"授权编辑者 + 归档 = 查看者"；矩阵的 archived 行逐格验证 |
| "耗时一致"不好做成稳定的断言 | 用"语句数量相同"代替时间断言，并在交接单与 M2 收尾汇报里写明这个取舍 |
| M2 收尾的对抗评审可能提出跨 Phase 的问题 | 按既有做法：报告回来逐条核实、修复、复验、填两列，再独立复验后合并 |
