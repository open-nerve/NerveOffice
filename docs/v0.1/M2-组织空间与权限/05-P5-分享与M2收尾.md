# M2-P5 分享与 M2 收尾：架构设计与实施规划

> 状态：恢复（2026-10-02）。§2 按 P6 之后的 main 重新核对，设计按 P6 第 2、3、5、6 片的结论修订（§9）｜日期：2026-09-30｜所属：M2-P5｜依据：M2 总设计 §2.1、§5（Phase 规划）、§6.1、§6.3、§6.4；00 号计划书 §5.2、§5.3、§5.4、§5.5｜基于代码版本：`6054999`（main，P6 六片已合并）

## 1. 目标与范围

把"单独分享"补齐，并把越权访问全面验证一遍，然后收掉 M2：

- **单独授权**（`document_grants`）：空间管理员或个人空间的所有者把一份文档分享给同事（查看者或编辑者），可以调整与取消；编辑者不能分享。
- **有效权限并上授权**：对一份文档的**内容**权限 = 空间角色与单独授权中**较高**的一个；归档的空间里所有人至多是查看者，**包括被单独授权为编辑者的人**。**结构性**的操作（移动、删除、新建、分享）只看空间角色：只凭授权的人看不到空间的目录结构与回收站（00 号计划书 §5.3 补充说明与 §5.5、M2 总设计 §2.1）。
- **只凭授权的人**：能读；按授权的角色编辑内容、改名；能复制（复制到自己有新建权限的空间）；**不能移动、不能删除**（需求方 2026-10-01 确认），看不到文档所在的文件夹、空间的目录结构与回收站。
- **"与我共享"**：我有单独授权的全部文档（不论我在那个空间里有没有角色）；每条能看到所属空间的类型与名称——团队空间是空间的名称，**个人空间按所有者的人名呈现**（人名组件，登录名在前；个人空间存的名称是所有者建号时的显示名，可以伪造，规范 §2.4），看不到空间的目录结构。
- **越权访问全面验证**（US-M2-14、上线门槛 A03）：权限矩阵补上"只有授权"的这一维；无权与不存在一致；列表、搜索、"与我共享"、回收站都不出现无权的文档；停用、移出空间、取消分享之后下一次请求即生效。
- **M2 收尾**：架构总览与 ADR、M2 交接单与收尾汇报、`v0.1-m2` 标签。M2 全部做完之后由 Codex 做一次 M 级的整体审核（M2 总设计 §5，2026-09-30 的变更）。

用户故事：US-M2-10（分享）、US-M2-14（越权访问一律被拒绝）。

**不在本 Phase**：分享给外部链接（v0.1 不做）；文件夹的分享（授权只到文档一级）；编辑租约与强制接管（M3）。

**有效权限与可访问文档**（documents 模块）：
- 有效权限只有一个入口：`DocumentAccessPolicy`（`accessOf`、`spaceAccessOf`、`visibleSpaces` 与 `requireDocumentContent`、`requireDocumentOperations`、`requireCreateTarget`、`requireSpaceContent`、`requireFolderContent`、`requireTrashEntry`、`requireSpaceManagement`），规则是 `access-rules.ts` 的纯函数。`DocumentAccess` 是 `{ role, space }`，**授权那一半还没有**；`accessOf` 只有一条空间事实的查询（`spaces.accessFactsOf`），空间不存在时提前返回。另有两处在服务里手工拼 `{ role, space }`（`document-organizing.service.ts`、`document-copy.service.ts`），`document-views.ts` 的 `toDetail` 按 `access.role` 算权限位。
- "可访问文档"的条件只在 `documents.repository.ts` 的 `accessible(scope)` 一处，`scope` 只有空间 id 一维（`inIdArray`）。调用方：按空间列出、搜索、转移的标题列表与 `lockForTransfer`；**回收站列表不经它**（走删除单元与 `requireSpaceContent`）。搜索的第二层是不变量：结果里出现范围之外的行就抛错（500）；文件夹路径来自 `folders.ancestorsOf(folderIds, spaceIds)`。
- `DocumentDetail` 有 `folderId`、`spaceId`、`space { id, type, name }`，**没有** `folderPath`（它只在搜索结果里）。个人空间的 `name` 是所有者建号时的显示名（`spaces.service.ts`），没有登录名；spaces 表有 `owner_user_id`。
- 永久删除时文档的内容与修订记录随外键级联，删除的本体在不导出的 `TrashEntryPurger`（删之前核对要删的都在回收站里）；ADR-016 写明"`document_grants` 在 P5 建表时在同一处补上"。

**模块与写操作的做法**：
- 依赖：documents ──► Database、Spaces、Audit（**不依赖 users**）；workspace ──► Database、Audit、Users、Spaces、Documents。成员管理的写操作由 workspace 编排（`space-membership.service.ts`）：开事务 → 不加锁判断 → `users.holdActiveAccount`（`FOR SHARE`）→ `spaces.holdSpace`（`FOR SHARE`）→ 锁下复核 → 写入 → 审计 → 在同一事务里补人名、拼好响应。

## 3. 设计

### 3.1 模块划分与依赖方向

不新增后端模块：

```
workspace ──► documents、spaces、users、auth、audit    分享的写入编排与授权列表、"与我共享"、搜索结果里的所有者人名
documents ──► spaces、auth、audit                      document_grants 的数据与规则；有效权限（并上授权）；可访问文档；锁下复核
spaces                                                 新增：按一批 id 取空间事实（类型、名称、状态、全员可见、所有者）
```

- `document_grants` 的表定义放 `db/schema/documents/`，仓储 `document-grants.repository.ts`（一表一仓储，只在 documents 里用）。
- **授权的判断仍然只经 `DocumentAccessPolicy`**，规则仍是纯函数，服务不自己拼权限条件。批量的场合（"与我共享"）经策略的批量入口，不在服务里另算。
- **`accessOf` 是两条语句**：空间事实在 spaces 的仓储，授权在 documents 的仓储，按模块边界不能联成一条（ADR-014 已否决跨模块联表）。两条**总是都执行**：文档不存在时用全零 id 同样执行两条，无权与不存在的语句序列仍然相同。
- **分享的写入由 workspace 编排**：要锁被授权人的账户行，documents 不依赖 users（与成员管理同一个做法）。documents 提供在给定事务里锁文档行、锁下复核、写授权、收回写入权的方法；workspace 负责事务、被授权人的账户行、空间行、审计与拼响应。
- 显示人名要靠 users，所以授权列表、"与我共享"、搜索结果里个人空间的所有者，都在 workspace 补人名。

前端新增 `features/sharing`（分享对话框，按需加载）与"与我共享"页（路由级按需加载）。

### 3.2 接口契约

| 方法与路径 | 说明 |
|---|---|
| `GET /api/documents/{id}/grants` | 这份文档的授权列表：被授权人（id、登录名、显示名、状态）、角色、最后设置它的人（同样带人名）、设置的时间。要有分享的权限才看得到 |
| `PUT /api/documents/{id}/grants/{userId}` | 设置或调整授权：`{ role: 'viewer' \| 'editor' }`，200，返回这一条授权（同列表的一项）。按状态幂等 |
| `DELETE /api/documents/{id}/grants/{userId}` | 取消授权，204；没有这条授权时同样 204（按状态幂等） |
| `GET /api/shared?cursor=` | "与我共享"：我有单独授权的全部文档，按更新时间的 keyset 分页；每条带文档的元数据（不带文件夹）、所属空间（类型；团队空间带名称，个人空间带所有者的 id、登录名、显示名）、我对这份文档的内容权限 |

- **不带 requestId**：PUT 与 DELETE 按状态幂等，重试不会多出东西（规范 §4 只要求新建与保存带）。前端的"结果未知"走共用的做法：刷新授权列表、文档详情与"与我共享"，按刷新结果说明。
- **PUT**：
  - 先判断文档：看不到 → 404（与不存在相同，包括被授权人也不存在的时候）；看得到、没有分享的权限 → 403；
  - 不能给自己：400 `REQUEST_INVALID`；被授权人不存在或已停用：409 `ACCOUNT_UNAVAILABLE`（新建与调整都是）；
  - 已有同样的角色：200，什么都不写（不记审计、不收回写入权，与 `changeMemberRole` 的 `changed` 同一个做法）；
  - 新建：记 `documents.shared`；调整：更新角色、"最后设置它的人"与时间，记 `documents.share_changed`；**编辑者降为查看者时**在同一事务里收回"这个人在这份文档上"的写入权，查看者升为编辑者不收回。
- **DELETE**：被授权人已停用也能取消（停用的人的授权要能清掉），所以不要求他是有效账户、不锁他的账户行；删除时记 `documents.share_revoked` 并收回他在这份文档上的写入权；空间管理员身上自己的那条授权也能取消（不特殊处理）。
- 授权与空间角色互不覆盖：给一个已经是空间管理员的人授"查看者"，他的有效权限仍是空间管理员（取较高者）。这种授权允许存在（人可能之后被移出空间），列表里如实显示。
- **归档的空间里分享冻结**（需求方 2026-10-01 确认）：授权列表的查看、设置、调整、取消都是 403 `PERMISSION_DENIED`，说明"空间已归档，恢复之后才能调整分享"（与 `denied()` 在归档时的默认说法"只能查看"不同，要专门给出，矩阵逐格钉住）；已有的授权照常生效，一律降为查看者。要取消某人的授权，由系统管理员先恢复空间。
- 回收站里的文档不能改授权（404，回收站里的对象对普通接口一律不存在）。
- 契约：`documentPermissionsSchema` 加 `canShare`；`DocumentDetail` 加 `accessVia: 'space' | 'grant'`；搜索结果凭授权命中的行 `folderId` 为空、`folderPath` 为空数组，带 `accessVia: 'grant'`；个人空间的所有者用一个通用的"人"结构（id、登录名、显示名），界面经人名组件显示。请求里的 id 一律用 `uuidSchema` / `*IdSchema`。

### 3.3 数据模型与迁移（0020）

| 表 | 内容 |
|---|---|
| `document_grants`（新） | `document_id`(FK→documents, **ON DELETE CASCADE**)、`user_id`(FK→users, restrict)、`role`(`viewer` \| `editor`)、`granted_by`(FK→users, restrict；最后设置这个角色的人)、`created_at`、`updated_at`（数据库时间）；主键 (document_id, user_id)；另加 `(user_id)` 索引 |
| `audit_events` | 动作加 `documents.shared`、`documents.share_changed`、`documents.share_revoked`（表定义按 `AUDIT_ACTIONS` 生成全量重列的 CHECK）；明细的严格结构与成员的三个动作同形：`{ userId, role }`、`{ userId, from, to }`、`{ userId, role }`，目标是文档（`target.name` 为空），不记标题 |

- **级联删除**：永久删除文档时授权随之消失（ADR-016 的承诺）。不做软删除：取消分享就是删行，历史在审计里。
- 主键覆盖"这份文档的授权列表"与"这个人在这份文档上的授权"；`(user_id)` 索引给"与我共享"与"可访问文档"的授权那一半用。
- 移动文档（空间内与跨空间）、移出空间、归档、停用、停用者文档的转移都不动这张表：授权跟着文档走。
- `migrations-with-data`：`TABLES` 加 `document_grants`；`BASES` 加"M2-P6 结束"（0019）。`schema-parity` 与 `migrations`、`schema` 门禁照常。

### 3.4 关键流程

**（1）有效权限并上授权：空间角色与内容权限分开带**

```ts
interface DocumentAccess {
  readonly spaceRole: SpaceRole | undefined     // 空间角色（现有的 effectiveSpaceRole，已按归档降级）
  readonly contentRole: SpaceRole | undefined   // 内容权限 = spaceRole 与授权取较高者（授权最高只到 editor；归档时同样至多 viewer）
  readonly accessVia: 'space' | 'grant'         // 没有空间角色、只凭授权时是 grant
  readonly space: SpaceFacts
}
```

- 两个都没有 → 无权，按不存在回答（`NOT_FOUND`）。
- **内容**的权限位看 `contentRole`：阅读、保存（`canEdit`）、改名、复制（还要目标空间的新建权限）。
- **结构**的权限位只看 `spaceRole`：空间内移动（编辑者及以上）、`PATCH {folderId}`、跨空间移动（源空间的空间管理员）、删除（编辑者只能删本人创建的）、分享（空间管理员 / 个人空间所有者，归档除外）。只凭授权的人这几项一律 403 `PERMISSION_DENIED`（他看得到这份文档，所以不是 404）。
- **只凭授权时不给目录结构，只在一处实现**（规范 §1.3）：`toDetail` 按 `accessVia` 给 `folderId` 为空；凡是返回文档详情的接口（打开、改名的响应等）都经它，矩阵逐接口核对。复制的响应是副本（在他自己有空间角色的空间里），照常给。
- 改结构时一起改：`requireDocumentOperations` 与 `DOCUMENT_CONTENT.edit`、移动与复制里手工拼的 `{ role, space }`、`toDetail`。
- 纯函数的单元测试覆盖空间角色 × 授权 × 归档的全部组合，分别断言内容与结构两组权限位。

**注意**：`spaceAccessOf`（空间页、按空间列出、回收站、文件夹）**不看授权**——授权不给空间里的任何东西开口子（§5.5）。只有"对某一份文档"的判断才并上授权。

**（2）"可访问文档"并上授权**

```ts
interface AccessibleScope {
  readonly spaceIds: readonly string[]      // 有空间角色的空间（空数组表示不要这一半）
  readonly grantsOf?: string                // 授权那一半：这个人（EXISTS document_grants WHERE user_id = ?）
}
```

条件是 `status = 'active' AND (space_id = ANY(…) OR EXISTS (授权))`，仍然只有这一处：

- 按空间列出、转移的标题列表与 `lockForTransfer`：只要空间那一半（回收站本来就不经 `accessible`）；
- 搜索：两半都要。**"凭授权命中"由搜索的那一条语句给出**（行上带一个标志），不事后另读一次授权集合来核对（两次读之间并发的取消分享会让正常的搜索被判为不变量失败）；不变量的"范围"改成"在我能看到的空间里，或者这一行凭授权命中"；凭授权命中的行不给文件夹、不查文件夹路径；
- "与我共享"：只要授权那一半。

**（3）分享的写入（workspace 编排）**

在一个业务事务里：

1. 不加锁判断（经 documents 的策略）：看不到 → 404；没有分享的权限 → 403（归档时给冻结的说明）；PUT 给自己 → 400；
2. PUT：**锁被授权人的账户行**（`users.holdActiveAccount`，`FOR SHARE`），不存在或已停用 → 409；DELETE 不锁；
3. **取空间行的 `FOR SHARE`**（`spaces.holdSpace`，按第 1 步看到的空间）；
4. documents 在这个事务里**锁文档行（`FOR UPDATE`）并在锁下复核**：文档还在、没进回收站、**仍在第 3 步持住的那个空间**（不在 → 404，与 8 处锁下核对同一个做法：跨空间移动可以插在第 1 步与第 3 步之间，这时锁下读到的是新空间、而新空间的行没被持住，归档就能并发提交，冻结被绕过）、空间没归档、自己还是空间管理员或所有者；
5. 读写 `document_grants`；调整为查看者或取消时，收回"这个人在这份文档上"的写入权；审计；
6. 在同一事务里补人名、拼好响应（`users.findByIds(ids, transaction)`，照 `space-membership.service.ts` 的做法），提交之后不再访问数据库。

- **锁的顺序**照 ADR-007、ADR-014 的全局顺序：账户行 → 空间行 → 文档行。账户行在空间行之前：要在锁下复核被授权人仍是有效账户，持住他的账户行；放在文档行之后，会与"先锁账户行、再动文档"的操作（停用；M3 起停用时还要收回他持有的租约）互相等待。取 `FOR SHARE` 与添加成员同一个做法：与停用、启用的 `FOR NO KEY UPDATE` 互斥，停用提交之后的分享一定被拒绝。
- **文档行取 `FOR UPDATE`，这是复制与保存"在锁下重新判断授权"的前提**：复制对源文档行取 `FOR SHARE`、保存对文档行取 `FOR UPDATE`，都在锁下重新读这个人的访问权限；分享的写入对文档行取 `FOR UPDATE`，所以取消分享与它们互斥——取消提交之后的复制与保存一定看到取消。
- **不取空间树的锁**：授权不改目录结构。
- `WriteAccessRevocation` 加一种范围"某人在这些文档上"（`{ kind: 'userDocuments', userId, documentIds }`，ADR-014 的补充）。现有的 `{ kind: 'documents' }` 指"这些文档上的所有人"，M3 接租约之后会把正在编辑的别人一起踢掉，不能用。
- 确定交错的用例（`raceAgainstHeldLock`，每把锁各一条，只靠单元测试断言调用顺序挡不住——P6 第 3 片去掉 4 处空间行锁，集成测试照样全绿）：分享 × 归档、分享 × 移出空间（操作者被移出）、分享 × 停用被授权人、分享 × 跨空间移动；取消 × 保存、取消 × 复制、降级 × 保存。

**（4）"与我共享"的列表**

- 条件：`accessible` 的授权那一半 + 正常状态；排序与分页与文档列表一致（keyset）。
- 每条的内容权限经策略的批量入口算（空间事实按一批 id 取，spaces 新增的方法），不在服务里另算；个人空间的所有者经 users 补人名。
- 回收站里的文档不出现（`status` 已经卡住）。

**（5）生效时机（US-M2-14）**

- 取消分享、移出空间、停用：都在下一次请求即生效（授权与空间事实都是每个请求重新读）。
- 已经打开的页面：编辑器页的保存被拒——取消分享之后这个人对这份文档无权，按不存在回答（404 `NOT_FOUND`），平台页面下一次请求即 404。只是从编辑者降为查看者时，保存是 403。
- 集成测试逐条验证；E2E 覆盖关键路径（取消分享后访问、移出空间后访问、停用后访问、猜文档地址）。

**（6）停用、转移、复制与授权**

- 给停用的账户的授权保留（停用可以撤回，启用之后照常生效）；停用期间他登录不了，授权不起作用；取消照样可以。
- 停用者个人空间里分享出去的文档：停用之后授权照常生效（被授权的人照常能访问）；系统管理员转移这些文档时授权跟着文档走，不删。
- 复制：副本是一份新文档，**不带原文档的授权**（US-M2-08；00 号计划书 §7.5 的"另存为副本"同样不继承），要有测试。

### 3.5 前端

- **分享对话框**（`features/sharing`，按需加载）：入口在文档的行操作与编辑器的页头，只在有分享权限（`canShare`）时出现，归档的空间里不出现。对话框里：授权列表（人名组件）、用同事选择（`ColleaguePicker`，排除自己与已有授权的人）加人、选角色、调整、取消（`ConfirmDialog`，`refresh` 必填）。设置、调整、取消的"结果未知"与被拒绝之后走共用的做法（`useOutcomeRefresh` / `refreshQueries`，刷新授权列表、文档详情与"与我共享"），403 显示服务端的说明。
  - 组件级的按需加载还没有先例：`loadChunk`、`checkDeployment` 从 `app/chunk-load.ts` 挪到 `shared/lib`（功能模块引用不到 `app/`），对话框自己显示"没能加载 / 已部署新版本 / 重试"。
  - lint：`features/sharing` 加一对"只能动态引入"的规则（允许文档的行操作与编辑器页头所在的入口文件），加进 dialog、confirmation、colleagues 三处白名单；文案放 `shared/i18n/zh-cn/sharing.ts`，加进 `LAZY_TEXTS`。
- **"与我共享"页**：`app/routes.ts` 的路由级按需加载，导航入口的文字放首屏的 `messages.ts`；每条显示文档、所属空间的类型与名称（个人空间用人名组件显示所有者），不显示所在位置；分页与焦点、读屏照既有的约定（"加载更多"之后焦点到第一条新内容、骨架屏不带 role 等）。
- **只凭授权时**：文档详情与编辑器不显示所在位置、没有移动与删除的入口；编辑器的返回链接回"与我共享"。搜索结果里别人的个人空间用人名组件显示所有者，不再一律写成"我的空间"。

### 3.6 错误处理、安全与可观测性

- 看不到与不存在一致：授权这一维加进来之后，"无权"的判断路径仍与"不存在"完全相同（同样的两条语句、同样的 `NOT_FOUND`）。
- **耗时一致按语句序列验证**（需求方 2026-10-01 确认）：响应（状态、错误体、非易变的响应头）逐字节相同、执行的 SQL 语句序列相同。本 Phase 新增的带 id 的三个接口加进 `hidden-missing-parity` 的探测（路由表的覆盖核对会逼着加）：看不到的文档加不存在的被授权人 → 404，先判断文档；另加"只凭授权的人"对所在空间的空间级接口（空间页头、按空间列出、文件夹、回收站、成员）的看不到 / 不存在对照。
- 审计：分享、调整、取消各一条，明细只记定长标量，结构先加进 `audit-details.ts`；`AUDIT_ACTION_NAMES` 补三条；`admin/audit.test.ts` 的整表扫描加入三个动作。
- 防泄漏：分享列表要有分享权限才看得到；被授权人只看得到这份文档，看不到空间的目录结构（详情、搜索、"与我共享"都不带文件夹）；归档的空间里分享冻结。
- 繁忙：`busy-after-commit` 补"设置授权：拼响应补人名时繁忙 → 503，授权没变、没有审计"；提交之后繁忙按 500。

| 风险 | 应对 |
|---|---|
| 授权并进"可访问文档"之后，调用方要的"半边"不同，容易写错（按空间列出不能并授权） | `accessible` 显式接受"要哪几半"，各处写明；集成测试专门验证"按空间列出、回收站不受授权影响"与"搜索受授权影响"；矩阵的列表类格子断言"恰好是这几条" |
