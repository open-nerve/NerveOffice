# M2-P5 分享与 M2 收尾：架构设计与实施规划

> 状态：暂停（2026-09-30），等 P6「M2 复核」完成；本设计已按 P6 第 2 片的复核修订（2026-10-01，见 §9）｜日期：2026-09-30｜所属：M2-P5｜依据：M2 总设计 §2.1、§5（Phase 规划）、§6.1、§6.3、§6.4；00 号计划书 §5.2、§5.3、§5.4、§5.5｜基于代码版本：`d0e0202`（main，P4 已合并）。恢复开工前按 P6 之后的 main 重新核对 §2

## 1. 目标与范围

把"单独分享"补齐，并把越权访问全面验证一遍，然后收掉 M2：

- **单独授权**（`document_grants`）：空间管理员或个人空间的所有者把一份文档分享给同事（查看者或编辑者），可以调整与取消；编辑者不能分享。
- **有效权限并上授权**：对一份文档的**内容**权限 = 空间角色与单独授权中**较高**的一个；归档的空间里所有人至多是查看者，**包括被单独授权为编辑者的人**。**结构性**的操作（移动、删除、新建、分享）只看空间角色：只凭授权的人看不到空间的目录结构与回收站（00 号计划书 §5.3 补充说明与 §5.5、M2 总设计 §2.1）。
- **只凭授权的人**：能读；按授权的角色编辑内容、改名；能复制（复制到自己有新建权限的空间）；**不能移动、不能删除**（需求方 2026-10-01 确认），看不到文档所在的文件夹、空间的目录结构与回收站。
- **"与我共享"**：我有单独授权的全部文档（不论我在那个空间里有没有角色）；每条能看到所属空间的名称与类型，看不到空间的目录结构。
- **越权访问全面验证**（US-M2-14、上线门槛 A03）：权限矩阵补上"只有授权"的这一维；无权与不存在一致；列表、搜索、"与我共享"、回收站都不出现无权的文档；停用、移出空间、取消分享之后下一次请求即生效。
- **M2 收尾**：架构总览与 ADR、M2 交接单与收尾汇报、`v0.1-m2` 标签。M2 全部做完之后由 Codex 做一次 M 级的整体审核（M2 总设计 §5，2026-09-30 的变更）。

用户故事：US-M2-10（分享）、US-M2-14（越权访问一律被拒绝）。

**不在本 Phase**：分享给外部链接（v0.1 不做）；文件夹的分享（授权只到文档一级）；编辑租约与强制接管（M3）。

## 2. 现状

> 下面是 `d0e0202` 时的现状。P6 改动了其中几处，恢复开工时按最新的 main 重新核对：迁移号已用到 0015（本 Phase 的迁移取下一个可用编号）；审计的明细按动作有严格结构（contracts 的 `audit-details.ts`，新动作要先加结构）；"看不到与不存在执行同样的查询"已有按语句序列核对的集成测试（P6-S2），本 Phase 的新路径直接接入；矩阵的列表类格子改成断言"恰好是这几条"。

- 有效权限只有一个入口：`DocumentAccessPolicy`（实现 `EffectiveAccessPolicy`），事实由 spaces 一条左连接给出，规则是 `access-rules.ts` 的纯函数。**授权那一半还没有**：`accessOf` 只看空间角色。
- "可访问文档"的条件只在 `documents.repository.ts` 的 `accessible(scope)` 一处，`scope` 只有"空间 id 集合"这一维（P4 把状态收成写死的"正常"）。注释里写着"P5 在这里并上单独授权"。
- 权限矩阵 1470 格（内容 150、管理 330、文档 240、文件夹 240、回收站与搜索 150、"在回收站里"360），`ACTORS` 是 6 个（所有者、空间管理员、编辑者、查看者、外人、系统管理员），**没有"只有授权"的人**。
- 永久删除时文档的内容与修订记录随外键级联（ADR-016 写明"`document_grants` 在 P5 建表时在同一处补上"）。
- 跨空间移动与移出空间都不动授权（00 号计划书 §5.4），现在没有授权可动。
- 现有的权限位（`documentPermissionsOf(role, …)`）只接收**一个**角色，`requireDocumentContent` 也只带一个角色：直接把授权并进这一个角色，只凭授权的编辑者就会拿到空间内移动的权限（P6-S2 两位审查者都指出，见 §3.4(1)）。
- 前端：空间页、文件夹导航、回收站、搜索都已就位；左侧导航有"我的空间 / 团队空间"，**没有"与我共享"**。同事目录 `GET /api/users?query=` 与 `KeywordPicker` 可以直接用来选人。

## 3. 设计

### 3.1 模块划分与依赖方向

不新增模块：

```
workspace ──► documents、spaces、users、auth、audit    分享的接口与"与我共享"（面向成员）
documents ──► spaces、auth、audit                      document_grants 的数据与规则；有效权限（并上授权）；可访问文档
```

- `document_grants` 的表定义放 `db/schema/documents/`，仓储 `document-grants.repository.ts`（一表一仓储）。
- **授权的判断仍然只经 `DocumentAccessPolicy`**，规则仍是纯函数，服务不自己拼权限条件。
- **`accessOf` 是两条语句**（P6-S2 更正，原稿写的"一条查询里左连接授权"做不到）：空间事实在 spaces 的仓储（`accessFactsOf`），授权在 documents 的仓储；按模块边界（规范 §1.2、lint 的仓储与表的边界、ADR-014 已否决"跨模块联表"）不能联成一条。两条**总是都执行**：文档不存在时用那个全零 id 同样执行两条，无权与不存在的语句序列仍然相同（§3.5）。
- 显示名要靠 users（分享列表要显示被授权人的名字），所以**分享列表的组装放 `workspace`**（与回收站列表把 `deletedBy` 换成显示名同一个做法）。

### 3.2 接口契约

| 方法与路径 | 说明 |
|---|---|
| `GET /api/documents/{id}/grants` | 这份文档的授权列表（谁、什么角色、谁授的、什么时候）。要有分享的权限（空间管理员 / 个人空间所有者，归档之外）才看得到 |
| `PUT /api/documents/{id}/grants/{userId}` | 设置或调整授权：`{ role: 'viewer' \| 'editor' }`。幂等 |
| `DELETE /api/documents/{id}/grants/{userId}` | 取消授权 |
| `GET /api/shared?cursor=` | "与我共享"：我有单独授权的全部文档，按更新时间的 keyset 分页；每条带所属空间的**名称与类型**（不带文件夹、不带空间的链接） |

- 不能给自己授权（400 `REQUEST_INVALID`）；被授权人不存在或已停用：409 `ACCOUNT_UNAVAILABLE`（与现有的约定一致，P6-S2 更正原稿的 400）。
- 授权与空间角色互不覆盖：给一个已经是空间管理员的人授"查看者"，他的有效权限仍是空间管理员（取较高者）。这种授权允许存在（人可能之后被移出空间），列表里如实显示。
- **归档的空间里分享冻结**（需求方 2026-10-01 确认）：授权列表的查看、设置、调整、取消都是 403 `PERMISSION_DENIED`（说明"空间已归档，恢复之后才能调整分享"）；已有的授权照常生效，一律降为查看者。要取消某人的授权，由系统管理员先恢复空间。
- 回收站里的文档不能改授权（404，回收站里的对象对普通接口一律不存在）。

### 3.3 数据模型与迁移（取 P6 之后下一个可用的编号）

| 表 | 内容 |
|---|---|
| `document_grants`（新） | `document_id`(FK→documents, **ON DELETE CASCADE**)、`user_id`(FK→users, restrict)、`role`(`viewer` \| `editor`)、`granted_by`(FK→users, restrict)、`created_at`、`updated_at`；主键 (document_id, user_id) |
| `audit_events` | `action` 的 CHECK 全量重列，加 `documents.shared`、`documents.share_changed`、`documents.share_revoked`；明细的严格结构先加进 contracts 的 `audit-details.ts`：被授权人的 id 与角色（调整时是原角色与新角色），不记标题 |

- **级联删除**：永久删除文档时授权随之消失（ADR-016 的承诺）。不做软删除：取消分享就是删行，历史在审计里。
- 主键 `(document_id, user_id)` 覆盖"这份文档的授权列表"与"这个人在这份文档上的授权"；**另加 `(user_id)` 索引**给"与我共享"与"可访问文档"用。
- 移动文档（空间内与跨空间）、移出空间、归档、停用、停用者文档的转移都不动这张表：授权跟着文档走。

### 3.4 关键流程

**（1）有效权限并上授权：空间角色与授权分开带**（P6-S2 更正）

`DocumentAccess` 分开带两项，由纯函数算出：

```ts
interface DocumentAccess {
  readonly spaceRole: SpaceRole | undefined     // 空间角色（现有的 effectiveSpaceRole，已按归档降级）
  readonly contentRole: SpaceRole | undefined   // 内容权限 = spaceRole 与授权取较高者（授权最高只到 editor；归档时同样至多 viewer）
  // …空间事实、文档
}
```

- 两个都没有 → 无权，按不存在回答（`NOT_FOUND`）。
- **内容**的权限位看 `contentRole`：阅读、保存（`canEdit`）、改名、复制（还要目标空间的新建权限）。
- **结构**的权限位只看 `spaceRole`：空间内移动（编辑者及以上）、跨空间移动（源空间的空间管理员）、删除（编辑者只能删本人创建的）、分享（空间管理员 / 个人空间所有者，归档除外）。只凭授权的人这几项一律 403 `PERMISSION_DENIED`（他看得到这份文档，所以不是 404）。
- 移动的"同一空间"分支（`PATCH {folderId}`）同样只看 `spaceRole`：原稿按单一角色推，只凭授权的编辑者能 `PATCH {folderId: null}` 把文档挪到他看不到的根目录，还能用 200 与 404 分辨某个 id 是不是这个空间的文件夹（P6-S2 两位审查者都指出，M2 总设计 §2.1"只有单独授权的人看不到空间的目录结构，所以不能移动"）。
- **只凭授权时（`spaceRole` 为空）不给目录结构**：文档详情的 `folderId` 为空、`folderPath` 为空，并带一个说明"经授权访问"的字段（契约里写明，界面据此不显示所在位置、不链接到空间页）；搜索结果与"与我共享"同样只给空间的名称与类型。
- 纯函数的单元测试覆盖空间角色 × 授权 × 归档的全部组合，分别断言内容与结构两组权限位。

**注意**：`spaceAccessOf`（空间页、按空间列出、回收站）**不看授权**——授权不给空间里的任何东西开口子（§5.5）。只有"对某一份文档"的判断才并上授权。

**（2）"可访问文档"并上授权**

`accessible(scope)` 的 `scope` 显式说明"要哪几半"：

```ts
interface AccessibleScope {
  readonly spaceIds: readonly string[]      // 有空间角色的空间（空数组表示不要这一半）
  readonly grantsOf?: string                // 授权那一半：这个人（id IN (SELECT document_id FROM document_grants WHERE user_id = ?)）
}
```

条件是 `status = 'active' AND (space_id IN (…) OR EXISTS (授权))`。仍然只有这一处：

- 按空间列出、回收站列表：只看空间那一半（目录结构与回收站不对只有授权的人开放）；
- 搜索：两半都要（能访问的文档都该搜得到）。结果里只凭授权的行（所在空间不在"我能看到的空间"里）另按 id 取空间的名称与类型，不给文件夹。P6-S2 把搜索的第二层改成了不变量检查（结果里出现范围之外的行即报错）：这里的"范围"相应改成"在我能看到的空间里，或者我有授权"；
- "与我共享"：只要授权那一半；
- 停用者文档的转移：只看空间那一半（转移是按空间搬，授权不参与）。

**（3）分享的写入**

事务里：不加锁判断分享权限（`canShare`）→ **取空间行的 `FOR SHARE`（`holdSpace`）** → 锁文档行（`FOR UPDATE`，与改名、移动同一档）→ 锁下复核（文档还在、没进回收站、空间没归档、自己还是空间管理员或所有者、被授权人是有效账户）→ 读写 `document_grants` → 审计。

- **先取空间行**（P6-S2 更正）：归档、移出成员都对空间行取 `FOR NO KEY UPDATE`，只锁文档行的话与它们不互斥，"锁下复核空间没归档、自己还是管理员"保证不了"撤权提交之后的分享一定被拒绝"。与新建、整理的做法一致（`document-creation.service.ts`）。锁的顺序照 ADR-014：空间行 → 文档行。
- **不取空间树的锁**：授权不改目录结构。
- 取消授权与降级（编辑者 → 查看者）要在同一事务里收回**这个人在这份文档上**的写入权：`WriteAccessRevocation` 加一种范围"某人在这些文档上"（`{ kind: 'userDocuments', userId, documentIds }`，ADR-014 的补充）。原稿写的 `{ kind: 'documents' }` 指"这些文档上的所有人"，M3 接租约之后会把正在编辑的别人一起踢掉（P6-S2 更正）。

**（4）"与我共享"的列表**

- 条件：`accessible` 的授权那一半 + 正常状态；排序与分页与文档列表一致。
- 每条带：文档的元数据（不带文件夹）、所属空间的**名称与类型**、我对这份文档的内容权限。
- 回收站里的文档不出现（`status` 已经卡住）。

**（5）生效时机（US-M2-14）**

- 取消分享、移出空间、停用：都在下一次请求即生效（授权与空间事实都是每个请求重新读）。
- 已经打开的页面：编辑器页的保存被拒——取消分享之后这个人对这份文档无权，按不存在回答（404 `NOT_FOUND`；P6-S2 更正原稿的 403），平台页面下一次请求即 404。只是从编辑者降为查看者时，保存是 403。
- 集成测试逐条验证；E2E 覆盖关键路径（取消分享后访问、移出空间后访问、停用后访问、猜文档地址）。

**（6）停用、转移、复制与授权**（P6-S2 补上原稿没写的）

- 给停用的账户的授权保留（停用可以撤回，启用之后照常生效）；停用期间他登录不了，授权不起作用。
- 停用者个人空间里分享出去的文档：停用之后授权照常生效（被授权的人照常能访问）；系统管理员转移这些文档时授权跟着文档走，不删。
- 复制：副本是一份新文档，**不带原文档的授权**（US-M2-08；00 号计划书 §7.5 的"另存为副本"同样不继承），要有测试。

### 3.5 错误处理、安全与可观测性

- 看不到与不存在一致：授权这一维加进来之后，"无权"的判断路径仍与"不存在"完全相同（同样的两条语句、同样的 `NOT_FOUND`）。
- **耗时一致按语句序列验证**（需求方 2026-10-01 确认，M2 总设计 US-M2-14 已写明）：响应（状态、错误体、非易变的响应头）逐字节相同、执行的 SQL 语句序列相同，是耗时一致的充分条件，结果确定、不受机器快慢影响；M7 压测时抽查耗时。本 Phase 新增的 404 路径（授权相关的，与只凭授权时的结构性操作之外的那些）全部接进 P6-S2 建立的语句序列核对。
- 审计：分享、调整、取消各一条，`details` 记被授权人与角色（不记文档标题），只记定长标量，结构先加进 `audit-details.ts`。
- 防泄漏：分享列表要有分享权限才看得到；被授权人只看得到这份文档，看不到空间的目录结构（详情、搜索、"与我共享"都不带文件夹）；归档的空间里分享冻结。

## 4. 测试策略

| 层级 | 覆盖内容 | 用户故事 |
|---|---|---|
| 单元 | `DocumentAccess` 的两项（空间角色 × 授权 × 归档的全部组合，内容与结构两组权限位分别断言）；`canShare`；授权的服务编排（锁顺序：空间行 → 文档行；锁下复核；收回写入权的范围是"这个人在这份文档上"）；契约的校验与审计明细的结构 | 10、14 |
| 集成 | 授权的增改删与幂等；不能给自己、不能给停用的人（409）；归档里查看、设置、调整、取消都 403，回收站里 404；有效权限取较高者；**只凭授权的编辑者：空间内移动、`PATCH {folderId}`、跨空间移动、删除都 403，详情不带文件夹**；"与我共享"的内容与分页（包括我在那个空间也有角色的）；按空间列出、回收站列表**不**受授权影响；搜索受授权影响、只凭授权的结果不带文件夹；跨空间移动、移出空间、停用、转移都保留授权；复制不带授权（US-M2-08）；永久删除连带删授权；分享与归档、移出的确定交错（持锁构造）；**权限矩阵补上"只有授权"的两个角色**；生效时机（取消、移出、停用之后下一次请求）；无权与不存在的响应与语句序列一致 | 10、14 |
| E2E | 分享对话框：按名字搜同事、给查看者/编辑者、调整、取消；对方在"与我共享"里看到并打开（查看者只读、编辑者能改）；取消之后立即不能访问；编辑者看不到分享入口；只凭授权的人看不到所在位置、没有移动与删除的入口；猜文档地址被拒 | 10、14 |

权限矩阵：`ACTORS` 加两个（只有查看授权的人、只有编辑授权的人），六张表全部扩一列（1470 → 约 1960 格），并补上结构性操作的格子：两个新角色的 moveWithinSpace、`PATCH {folderId}`、moveAcrossSpaces、delete 都是 403，文档详情不带文件夹。新角色在"看不到的空间"里也可能有授权，这正是要验证的格子。列表类的格子断言"恰好是这几条"（P6-S2 的做法）。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 授权并进"可访问文档"之后，调用方要的"半边"不同，容易写错（按空间列出、回收站不能并授权） | `accessible` 显式接受"要哪几半"，各处写明；集成测试专门验证"按空间列出、回收站不受授权影响"与"搜索受授权影响"；矩阵的列表类格子断言"恰好是这几条" |
| 只凭授权的人拿到结构性的权限（移动、删除）——原稿按单一角色推，实现者与矩阵作者会一起写错 | `DocumentAccess` 分开带两项，结构性的权限位只看空间角色；矩阵的两个新角色逐格断言 403 |
| 矩阵再扩一列，格子接近 2000，集成测试变慢 | 现在 1470 格约 6 秒，扩一列约 +33%；超出 10 秒就把矩阵拆成两个文件并行 |
| 归档对授权的降级容易漏（只降空间角色） | 纯函数里一次降级，单元测试覆盖"授权编辑者 + 归档 = 查看者"；矩阵的 archived 行逐格验证；归档里分享冻结 |
| M2 的整体审核（Codex）可能提出跨 Phase 的问题 | 按既有做法：报告回来逐条核实、修复、复验、填两列，再独立复验后合并 |
