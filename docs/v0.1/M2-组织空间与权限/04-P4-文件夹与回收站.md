# M2-P4 文件夹、文档管理与搜索：架构设计与实施规划

> 状态：进行中｜日期：2026-09-30｜所属：M2-P4｜依据：M2 总设计 §5（Phase 规划）、§6.3、§6.4、§6.8；00 号计划书 §5.3、§5.4、§5.5｜基于代码版本：`8f7ec2b`（main，P3 已合并）

## 1. 目标与范围

让文档能整理、能删错了还能找回来、能找得到：

- **文件夹**：空间里的多级目录，最多 10 层；新建、改名、移动；按空间与文件夹列出。
- **文档管理**：重命名；空间内移动与跨空间移动；复制。
- **回收站**：以"删除单元"为粒度删除（一份文档，或一个文件夹连同里面的全部内容），按空间列出、恢复、永久删除；30 天后自动永久删除。
- **搜索**：按标题搜索我能访问的文档。
- **权限**：00 号计划书 §5.3 里文档管理那几行（删除、移动、复制）落到有效权限里，并进权限矩阵。

用户故事：US-M2-07（整理）、US-M2-08（复制）、US-M2-09（删除与恢复）、US-M2-12（搜索）。上线门槛：A10 的元数据部分（复制）、A14（权限矩阵的文档管理部分）。

**不在本 Phase**：单独分享与"与我共享"（P5）；历史版本与恢复为副本（M3）；图片资源随复制（M5）；文件夹的权限（v0.1 不做，权限只到空间与文档两级）。

## 2. 现状

- `documents` 表没有 `folder_id`，状态只有 `active`，没有软删除；唯一的索引是 `(space_id, updated_at DESC, id DESC)`（`apps/api/src/db/schema/documents/index.ts`）。
- 文档的读写集中在 `modules/documents/`：列表与元数据在 `documents.service.ts`，新建在 `document-creation.service.ts`，内容在 `document-content.service.ts`，三者不互相调用；**重命名、移动、复制、删除都还不存在**。
- "可访问文档"的条件只在 `documents.repository.ts` 的 `accessible(scope)` 一处（`status='active' AND space_id IN (…)`），列表、转移都经它。
- 有效权限的唯一入口是 `DocumentAccessPolicy`，规则是 `access-rules.ts` 里的纯函数（`effectiveSpaceRole`、`spacePermissionsOf`），界面与服务端共用同一份。
- 需要加锁的写操作都是"先不加锁判断 → 加锁 → 锁下再判断"（`workspace/managed-space.ts` 最典型），多行加锁按 id 排序（`admin/admin-transfer.service.ts` 的 `inIdOrder`）。
- 没有 `jobs` 模块，仓库里没有任何定时任务；现有的清理都在别的请求里顺带做。迁移由独立的一次性任务执行，应用容器跑在受限的 `nerve_app` 角色下（只有 DML）。
- 前端：空间页 = 页头 + 文档列表（无限滚动，条目是纯链接，没有行内操作）；左侧导航只有空间；顶栏没有搜索框。按权限隐藏入口一律读 `SpaceView.permissions`。

## 3. 设计

### 3.1 模块划分与依赖方向

```
workspace ──► documents、spaces、users、auth、audit      文件夹与文档管理、回收站、搜索的接口（面向成员）
jobs（新）──► documents                                    到期删除单元的清理（只调 documents 导出的清理服务）
documents ──► spaces、auth、audit                          文件夹与文档的数据与规则、有效权限、可访问文档
spaces                                                     只有数据与不变量
```

- **文件夹与回收站放在 `documents` 模块里**，不新开模块：它们与文档共用同一套有效权限、同一个空间事实、同一张审计表，而且删除单元天然跨"文件夹 + 文档"。表定义放 `db/schema/documents/`（lint 只允许模块引用同名的表定义）。
- **接口放 `workspace`**（面向成员的编排层），与空间、成员的接口同层；`documents` 仍然没有控制器。
- **`jobs` 是新模块**：只做"按时触发 + 防重复执行"，删除的语义在 `documents` 里。它调用 `documents` 导出的 `TrashPurgeService`，这个服务用与 `DocumentTransferService` 同样的 lint 规则限定为只有 `modules/jobs/**` 能引用（`eslint.config.ts` 的 `no-restricted-imports`，按 importNames 拦）。
- 新目录要先在 `eslint.config.ts` 的 `boundaries/elements` 里登记（`api-module` 与 `api-schema`），否则 `boundaries/no-unknown-files` 直接失败。

### 3.2 接口契约

新增（`packages/contracts`），路径与字段在本 Phase 锁定：

| 方法与路径 | 说明 |
|---|---|
| `GET /api/folders?spaceId=&parentId=` | 列出一层：某个文件夹的直接子文件夹（`parentId` 省略表示空间的根目录）。不分页，上限 500 条（超过时返回前 500 与 `truncated: true`，登记延期项按规模复核） |
| `POST /api/folders` | 新建：`{ spaceId, parentId?, name, requestId }` |
| `PATCH /api/folders/{id}` | 改名或移动：`{ name? , parentId? }`（`parentId: null` 表示移到空间的根目录）。跨空间移动文件夹另走下面的 `move` |
| `GET /api/documents?spaceId=&folderId=&cursor=` | 现有接口加 `folderId`（省略表示空间的根目录，`folderId=all` 表示整个空间不按目录过滤，"与我共享"与搜索另有接口） |
| `PATCH /api/documents/{id}` | 改名或空间内移动：`{ title?, folderId? }`（`folderId: null` 表示空间的根目录）。两者都不改 `updated_at`：整理不是内容的改动，列表的排序与游标不因此抖动（与停用者文档转移一致） |
| `POST /api/documents/{id}/copy` | 复制：`{ spaceId, folderId?, title?, requestId }`，返回新文档的元数据。标题默认"<源标题> 的副本"（超过 200 码点时按码点截断），规则在契约里，界面与服务端共用 |
| `POST /api/documents/{id}/move` | 跨空间移动：`{ spaceId, folderId? }`（源空间的空间管理员 + 目标空间的新建权限）。目标就是当前空间时按空间内移动处理（权限与代次都按空间内的规则），这样移动成功之后的网络重试有确定结果 |
| `POST /api/folders/{id}/move` | 跨空间移动文件夹：同上，连同子树 |
| `DELETE /api/documents/{id}`、`DELETE /api/folders/{id}` | 删除：生成一个删除单元，进所在空间的回收站 |
| `GET /api/trash?spaceId=&cursor=` | 回收站：按空间列出删除单元（谁删的、什么时候、原位置、到期时间、里面有多少份文档） |
| `POST /api/trash/{entryId}/restore` | 恢复：整个删除单元回到原位置；原来的父文件夹不在了就回到空间的根目录 |
| `DELETE /api/trash/{entryId}` | 永久删除（空间管理员 / 个人空间所有者） |
| `GET /api/search?query=&cursor=` | 按标题搜索我能访问的文档（不含回收站里的），返回文档与它所在的空间、文件夹路径 |

约定沿用现有的：请求里的 UUID 用 contracts 的 `uuidSchema`（统一小写），响应用 `z.uuid()`；分页一律 keyset（`(updatedAt, id)`，游标 base64url）；新建类接口带 `requestId` 做幂等（文件夹因此有 `request_id` 列：同一个文件夹里允许同名，看名字分辨不出重复的新建）；看不到与不存在都是 `NOT_FOUND`。

错误码（S1 实现时定的）：**在归档的空间里新建或改动是 403 `PERMISSION_DENIED`"空间已归档，只能查看"**，与 M2-P2 的"在归档空间里新建文档"一致；409 `SPACE_ARCHIVED` 留给跨空间移动与复制的"目标空间已归档"。层数超过上限是 409 `FOLDER_DEPTH_EXCEEDED`，把文件夹移进自己的子树是 409 `FOLDER_CYCLE`。

### 3.3 数据模型与迁移（`0010_m2_folders_trash`）

| 表 | 内容 |
|---|---|
| `folders`（新） | `id`(uuidv7)、`space_id`(FK→spaces, restrict)、`parent_id`(FK→folders, restrict, 可空)、`name`(1–100，不含控制字符)、`created_by`(FK→users, restrict)、`status`(`active` \| `trashed`)、`trash_entry_id`(FK→trash_entries, 可空)、`depth`(1–10)、`request_id`(唯一)、`created_at`、`updated_at`。索引：`(space_id, parent_id, name)`、`(trash_entry_id)` partial。CHECK：根目录下的文件夹层数为 1；`trashed` 与"有删除单元"互为充要（文档同样加一条）|
| `trash_entries`（新） | `id`(uuidv7)、`space_id`(FK→spaces, restrict)、`kind`(`document` \| `folder`)、`deleted_by`(FK→users, restrict)、`deleted_at`、`expires_at`、`origin_space_id`、`origin_parent_id`（原位置，可空，不做外键：原文件夹可能已被永久删除）、`title`（删除时的标题或名称，回收站列表用）。索引：`(space_id, deleted_at DESC, id DESC)`、`(expires_at)` |
| `documents` | 加 `folder_id`(FK→folders, restrict, 可空)、`trash_entry_id`(FK→trash_entries, 可空)；`status` 的 CHECK 加 `trashed`。索引加 `(space_id, folder_id, updated_at DESC, id DESC)` 与 `(trash_entry_id)` partial |
| `audit_events` | `action` 与 `target_type` 的 CHECK 全量重列（0009 的写法）：加 `documents.renamed`、`documents.moved`、`documents.copied`、`documents.deleted`、`documents.restored`、`documents.purged`、`folders.created`、`folders.renamed`、`folders.moved`、`folders.deleted`、`folders.restored`、`folders.purged`；目标类型加 `folder`、`trash_entry` |

说明：

- **深度存在列里**（`depth`），不靠递归算：新建与移动时在事务里算好并校验 ≤ 10，移动子树时整棵加上差值。这样"最多 10 层"是一个可以写进 CHECK 的不变量，列表与移动都不必递归。
- **同一个文件夹里允许同名**（M2 总设计 §6.8），所以 `(space_id, parent_id, name)` 只是索引，不是唯一约束；与团队空间名称的 `lower(name)` 唯一索引刻意不同，设计里写明。
- **不做外键的两列**：`trash_entries.origin_parent_id` 与 `origin_space_id` 只是"原位置"的记录，恢复时按当前是否还在判断，所以不做外键（与审计表里 `actor_id` 不做外键同样的理由）。
- 永久删除时：`document_contents`、`document_revisions` 由现有的 cascade 清掉；`folders`、`documents`、`trash_entries` 的行在同一个事务里删；审计留着。

### 3.4 关键流程

**（1）"可访问文档"的条件拆成两维**（复验 P2 交接单第 51 行的承诺，也是这次最容易出错的地方）

`AccessibleScope` 现在只有 `spaceIds`。P4 把它拆成：

```ts
interface AccessibleScope {
  readonly spaceIds: readonly string[]   // 范围：P5 在这里并上单独授权
  readonly state: 'active' | 'trashed'   // 状态：列表、搜索用 active；回收站用 trashed
}
```

`accessible(scope)` 据此生成条件，仍然是唯一的一处。**停用者文档的转移显式只搬 `active` 的文档**：回收站里的文档留在原处，30 天后自动清除（管理员没有内容权限，也不该替别人恢复）。这条写进 ADR 与 P4 的交接单，因为 M2 总设计没有写。

**（2）空间树的结构性改动串行化**

删除、移动、恢复一个文件夹要在事务里先递归展开子树，再对里面的每一行加锁——展开与加锁之间有窗口，别人可以往子树里移进新文档。与其在窗口上打补丁，不如让**同一个空间里的结构性改动串行**：

- 这类操作（新建、改名、移动、删除、恢复、永久删除文件夹与文档）在事务的第一步取 `pg_advisory_xact_lock('nerve-office:space-tree:<spaceId>')`；跨空间的操作按空间 id 排序取两把，避免成环。
- 保存文档内容**不取**这把锁：保存与结构改动互不阻塞（保存只锁文档行，见 M1-P4）。
- 锁下再展开子树、再判断权限（"编辑者只能删除里面只有本人创建的文档的文件夹"必须在锁下重新验证）。

锁顺序表（P2 交接单第 53 行）据此扩展为：system-admins → 按登录名 → 账户行 → 重置/邀请行 → 限流计数 → 会话行 → **空间树的 advisory lock（按空间 id 排序）** → 空间行（按 id）→ 成员行 → 文件夹行（按 id）→ 文档行（按 id）→ 回收站行 → 审计。

**（3）删除单元**

删除一份文档：建一条 `trash_entries`（kind=document），文档 `status='trashed'`、`trash_entry_id` 指向它、`write_epoch + 1`（P2 交接单第 55 行）、记原位置。
删除一个文件夹：建一条 `trash_entries`（kind=folder），子树里的全部文件夹与文档都指向这一条、状态改为 `trashed`，文档的 `write_epoch` 都加一；只在**被删的那个文件夹**上记原位置。
恢复：把指向这条删除单元的行全部改回 `active`、清掉 `trash_entry_id`；被删的那个对象回到原位置，原来的父文件夹已经不在（被永久删除，或者自己也在回收站里）就回到空间的根目录（深度按新位置重算，超过 10 层时同样回到根目录并在响应里说明）。
永久删除：删子树的行与删除单元的行；记审计（自动清除时操作者记为系统）。

文档的元数据（`DocumentDetail`）随之带上 `folderId` 与一组操作权限位（`canRename`、`canMoveWithinSpace`、`canMoveAcrossSpaces`、`canCopy`，S3 再加 `canDelete`）：界面据此隐藏入口，与服务端同一份规则（`documentPermissionsOf`）。

**（4）复制**

- 权限：能读源文档 + 在目标空间有新建权限。
- 快照**不经 `JSON.parse`**：`INSERT INTO document_contents (…) SELECT …` 直接复制压缩后的字节（DEF-018 说的解析开销不放大），`unit_id` 原样复制（A10 要求副本与源逐字节一致）。
- 副本是一份新文档：新的 `id`、`revision=1`、`write_epoch=0`、`created_by` 是操作者、修订记录写一条 `kind='created'`；不复制历史修订，不复制单独授权（P5 的 `document_grants`）。
- 标题默认是"源标题 的副本"，可以在请求里指定。

**（5）搜索**

- 条件：`accessible({ spaceIds: 我能看到的空间, state: 'active' })` + `lower(title) LIKE '%' || lower(关键词) || '%'`（关键词先做转义，`\`、`%`、`_` 都转义）。
- 排序与分页与列表一致（`updated_at DESC, id DESC` 的 keyset），不做相关度排序。
- 不建 `pg_trgm` 索引：本版的规模是约 100 人（00 号计划书 §12.1），空间集合的过滤已经很有选择性；引入扩展要动数据库初始化与部署说明。**登记延期项**：M7 压测时按真实数据量复核，需要时加 `pg_trgm` 的 GIN 索引（与 DEF-026 同一批复核）。
- 结果里带空间名与文件夹路径，路径由一次按 id 的批量查询拼出（深度 ≤ 10，不递归查库）。

**（6）30 天清理（`jobs` 模块）**

- 触发：应用启动后按固定间隔（默认 1 小时，`NERVE_TRASH_PURGE_INTERVAL`）跑一轮；不引入调度框架，用模块自己的定时器（`OnModuleInit` 起、`OnModuleDestroy` 停），带随机抖动。
- 防重复：每一轮先取 `pg_try_advisory_lock('nerve-office:trash-purge')`，拿不到就跳过这一轮（将来多实例，DEF-024）。
- 一轮的做法：按到期时间取一批（默认 50，`NERVE_TRASH_PURGE_BATCH`），**逐个在各自的短事务里**永久删除，失败只记日志、不影响这一轮的其他条目。
- 时钟：`jobs` 模块提供 `Clock` 抽象（`now()`），生产实现用系统时钟，测试注入可控的时钟；"是否到期"在 SQL 里按 `expires_at <= $now` 判断，`$now` 由时钟给出，不用数据库的 `now()`，这样集成测试不必等 30 天。
- 运行角色：只有 DML，`nerve_app` 够用；新配置项同步 `.env` 模板与 `deploy/README.md`（M1 交接单的约定）。

**（7）权限规则的扩展**

`access-rules.ts` 里加纯函数，界面与服务端共用：

```ts
spacePermissionsOf(...)   // 加 canCreateFolders（与 canCreateDocuments 同）、canPurgeTrash（空间管理员 / 个人空间所有者）
documentPermissionsOf(access, document, userId)  // canRename、canMoveWithinSpace（编辑者及以上）、canMoveAcrossSpaces（空间管理员）、canCopy（能读即可，目标空间另判）、canDelete（空间管理员任意，编辑者仅本人创建）
folderPermissionsOf(role)                        // 按 Step 加位：S1 的 canRename、canMoveWithinSpace，S2b 的 canMoveAcrossSpaces，S3 的 canDelete。始终只看空间角色：文件夹能不能删，除了角色还要"里面只有本人创建的文档"，这一条在锁下用一条计数语句判断，与文件夹自己的创建人无关，所以不进纯函数、也不需要给它传文件夹与用户
restorePermissionOf(entry, access, userId)       // 删除者本人或空间管理员
```

### 3.5 错误处理、安全与可观测性

- 看不到与不存在一致（`NOT_FOUND`），包括文件夹与删除单元；每个 404 的格子在矩阵里与"不存在"比响应对象。
- 列表、搜索、回收站都不泄漏无权文档的标题或是否存在（00 号计划书 §5.5）；搜索只在"我能看到的空间"里查。
- 跨空间移动与删除递增 `write_epoch`，并在同一事务里调 `WriteAccessRevocation.revoke`（M3 接租约）。
- 审计：每个操作记一条，`details` 里带原位置与目标位置（不记标题以外的内容）；自动清除记 `actor_type='system'`。
- 回收站里的文档打不开：内容接口按 `status` 拒绝（`NOT_FOUND`），也不出现在列表与搜索里。

## 4. 测试策略

| 层级 | 覆盖内容 | 用户故事 |
|---|---|---|
| 单元 | 权限的纯函数（新加的几组）；深度计算与 10 层上限；恢复时原位置不在的回落；搜索关键词的转义；`jobs` 的一轮（用假时钟与假的清理服务）；游标与分页 | 07、08、09、12 |
| 集成 | 文件夹的增改移删与 10 层上限；文档改名、移动（空间内 / 跨空间）、复制（快照逐字节一致、`unitId` 不变、两份各自保存互不影响）；删除单元的级联与恢复（原位置不在、同名、跨空间移动过的文档）；永久删除的级联（内容、修订记录）；30 天清理（假时钟推进）；搜索（大小写、`%` 与 `_`、只在可访问范围里）；并发（同一空间的两个结构改动串行、删除与保存并发、展开子树与移入新文档并发）；权限矩阵的文档管理部分 | 07、08、09、12、14 |

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 文件夹子树的展开与加锁之间有窗口（别人往里移进新文档） | 同一空间的结构性改动用 advisory lock 串行（§3.4 第 2 条）；并发测试用 `support/held-lock.ts` 构造确定的交错 |
| 锁顺序新增两档（空间树的 advisory lock、文件夹行），定错就与移动、删除互相成环 | 锁顺序表在本设计里写全，跨空间操作按空间 id 排序；集成测试覆盖"两个方向的跨空间移动同时发生" |
| `accessible` 一处要同时承担范围、状态、目录、关键词四件事 | 只把"范围"与"状态"放进它（两维的 `AccessibleScope`），目录与关键词是各自查询的条件，不塞进这一处 |
| 搜索没有索引，数据量大时变慢 | 本版规模下可接受；登记延期项，M7 压测时复核（与 DEF-026 一起） |
| `jobs` 是新模块，lint 边界与运行角色都有硬约束 | S4 先把边界登记与 `no-restricted-imports` 写好再写逻辑；清理只用 DML |
| 本 Phase 的 E2E 会把 CI 推向 45 分钟的时限 | 已在开工时分片（`35bee0f`）：verify 的 `--scope` 与按浏览器的矩阵 job；后续每次加 E2E 之后看一眼最慢的那一片 |
| 递归 CTE 里同名列被截走（P1 交接单第 64 行的坑） | 子查询里的列写全名（`sql.identifier`）；深度存列里，尽量不递归 |
