# M2-P6 M2 复核：总结

> 日期：2026-09-30 至 2026-10-02｜所属：M2-P6（插入的 Phase，执行顺序排在 P5 之前，计划见 `06-P6-M2复核.md`）｜被复核的版本：`d0e0202`（M2-P1 到 P4 合并之后）｜每片的报告：`reviews/P6-S1` 到 `P6-S6`

## 一、为什么有这一轮

M2 有一段是在 Opus 5 上做的，不是需求方要求的 Opus 5.5：按会话记录逐条统计，2026-09-29 20:06 起主会话被自动换到 Opus 5，之后启动的子 Agent 全部落在 Opus 5——M2-P3 的收尾、M2-P4 的全部与 P5 的设计都在其中。实现者与审查者是同一个模型时，盲点是相关的，"审查通过、测试全绿"只能说明它自己没看出问题。需求方 2026-09-30 决定：把 M2 的实现当作质量不可信，按风险切六片逐片复核，每片由 Opus 5.5 独立审查（先盲审），修复之后再请独立的复验者，合并、CI 全绿之后再进下一片；M2 全部做完之后，另由 Codex 做一次 M 级的整体审核。

复核的原则（计划 §2）：改动由证据驱动（复现、失败的用例、存活的变异），不因为"是 Opus 5 写的"就重写；测试本身也不可信，要用变异与探针检验；主会话与每个子 Agent 都核对自己的模型标识。整个复核期间所有审查者、复验者、实现者都在 Opus 5.5 上（会话记录逐个核对过，含它们分出的子任务）。

## 三、M2 现在可以信任到什么程度

**可以信任的部分**（每一条都有独立的复核、确定的用例与变异的证据）：
- **认证与一次性令牌**：令牌的生成、存放、单次与时限，会话在改密、重置、停用之后的失效，CSRF 与 Origin，登录限流的三个维度与解除，撤权之后不再有残留的链接；失败登录的计算与账户是否存在无关（两条路径做同样的计算，负载起落时同样成立，第 6 片合并之后的 CI 修复）。
- **权限核心与防泄漏**：有效权限只有一个入口；带 id 的接口里"看不到"与"不存在"的状态、错误体、响应头与执行的 SQL 语句序列完全一致（65 个探测、27 个接口；路径里带 id 的接口与路由表对照，只给系统管理员的 9 个写明豁免，其余都在核对里）；系统管理员不加入空间拿不到内容（全员可见是需求方确认的例外）；归档之后的写入全部收回；权限矩阵的预期逐格按规则独立推出、能检出错。
- **并发与数据一致性**：结构性改动的空间树锁与 8 处锁下核对各有确定交错的用例；永久删除前核对要删的都在回收站里；集成测试删库之前扫一遍只由服务保证的不变量；迁移与表定义整体一致、有数据的库能迁到最新；数据库繁忙的回答（503 确定没有生效、提交之后 500 结果未知）在每个写接口上都成立。
- **编辑器只读**：没有能改动文档内容的路径（三个浏览器、全部已注册的快捷键与六十多个界面动作）；防火墙有效的前提有用例守着；探针进不了生产构建。
- **前端与交互**：结果未知之后的重试不会多建一份，每个写操作都按同一个做法刷新并说明；人名冒充不了别人；US-M2 的核心链路经界面验证。

**还不能说已经验证的部分**：
- P5（分享与 M2 收尾）还没有实现；P5 的设计已按第 2 片的结论修订，恢复时还要按第 3、5 片的结论修订（见第五节）。
- 另一家模型的整体审核还没做（M2 全部做完之后由 Codex 做）。
- 只靠审查而没有自动检查的条目（规范里标【审查】的）依然存在；这一轮把其中已经证明会出问题的几条写成了 lint 或测试（S6），其余照旧靠审查。
- 性能与资源：E2E 期间内存的峰值波动大（迄今 236–490 MiB，多数落在约 240–270 或约 380–490，也有落在中间的），原因要等隔离的实验；部署按高档留余量，真实负载下的数字等 M7 的压测。

**这一轮本身说明的事**：复核找到的问题不只出在 Opus 5 做的部分——第 1 片的"限流被当作武器"、"撤权之后的链接残留"出在 5.5 写的 P1 代码里；第 3、5 片的复验还在本轮修复里找出了两处修复者自己引入的回归。价值在"独立的人带着变异去验证"，不在换了哪个模型；这条做法已经写进规范（见第四节）。

## 四、过程上的经验（已写进规范与审查报告的模板）

- 每条修复都做变异验证：临时改坏 → 跑对应的测试 → 还原，存活的变异就是缺口；变异里要包括"测试的前提失效"一类（S4：快捷键回归在按法换算出错时照样通过；S6：去掉门禁自测里重复的 stories 之后，静态门禁一步仍在执行它这件事没有检查守着）。
- 复验者写的、能复现问题的用例，移进仓库作为回归用例。
- 修复里引入了新的机制，这一批另请一位复验者只看它（S1、S3、S5 都在这一步找出了回归）。
- 修复里引入的全局约定要逐个接口核对（S3："503 = 确定没有生效"在提交之后读库的接口上不成立）。
- 同一类处理先抽成共用的做法再逐处接入（S5：结果未知的处理补了四批）。
- 体积之外限定首屏的文件数（S5）；CI 上 E2E 出现重试即失败（S6）。
- 计时类的判定比较计算量（CPU 时间）或墙上耗时的下四分位，不比较两组墙上耗时的中位数：负载一阵一阵地把个别请求拉长几倍（S6 合并之后的 CI）。
- 子 Agent 一律显式指定与主会话相同的模型，并在汇报的第一行写出模型标识；主会话逐个核对会话记录。
