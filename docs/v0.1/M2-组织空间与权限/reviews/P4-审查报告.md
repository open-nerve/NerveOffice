两路审查的共同点：

- **无界的字段与不变量的漏洞，都是"规模到了才出事"**。审计明细里那个连带单元的 id 数组在小数据下永远看不出问题，连带上百个单元时永久删除稳定失败、而且那一单再也删不掉（A1）。恢复少算了一部分层数，也要等"先删子、再删父、只恢复父、再移动"这条长路径才暴露（A2）。两条都不是靠读代码看出来的，是审查者自己造数据跑出来的。
- **同一个错误码承担两种原因，界面就一定会说错话**。文件夹删不掉有两种 403："里面有别人创建的文档"与"空间已归档"。前端按码猜，归档时就显示一句关于用户数据的错话。修法是给前者单独登记错误码，让文案回到"按错误码映射"这一层，而不是在组件里加分支（B2）。
- **幂等要在界面上也成立**。契约承诺同一个 `requestId` 只复制一份，但前端每次点击都换新的 id，结果未知时再点就多出一份副本（B1）。新建表格早在 M2-P1 就为此做过处理，复制没有照做。

## 这一轮的经验

- **无界字段要在类型上封住**。A1 修完把审计明细的类型收窄到定长标量，比"这次改小"更可靠：下一个人想往里塞数组时编译期就被挡住。
- **同形的两条路径要真的同形**。`moveSubtree` 与 `restoreInEntry` 都是"整棵子树改位置"，只有前者考虑了回收站里的子孙；A2 的修法就是把后者改成与前者同一个写法。凡是"另一条路径也做类似的事"，要么共用，要么在注释里写明为什么不同。
- **变异存活比测试失败更值得看**。两轮 40 处变异里，存活的那几处指出了一个真实的测试缺口（复制的目标文件夹）、两处不可达代码和三处没被交错覆盖的防御——其中不可达的那一处顺手删掉了。
