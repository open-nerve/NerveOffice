## 八、合并之后的 CI

- 合并 `6054999` 的 CI：四片 E2E 与容器 E2E 通过（容器 E2E 120 条；空闲按新的做法 210.2 MiB，各次 209.7–210.3；峰值 269.4、跑完之后 206.6 MiB；镜像 269.0 MB）。**verify 一项失败**：集成测试 `auth/login-timing.test.ts` 的"迭代次数调高"一例，已有账户与用户名不存在的耗时之比 0.67（要求 0.8–1.25）。
- **根因**（分支 `m2-ci-login-timing`）有两层：
  - 机制：失败的验证原来按各组参数实测耗时的中位数补齐，等到最慢那组的 1.2 倍。等待不随负载变慢、计算会，负载爬升时中位数跟不上，两条路径的耗时就分开了；
  - 测法：两边的墙上耗时各取中位数、不配对，本身也受负载起落的影响；
  - 本片把 lint 自测拆成五个并行的文件，CI 上覆盖率那一轮的负载更集中，正好碰上；
  - 本机构造周期性起落的负载（48 个忙线程）复现到 0.64 与 2.3、2.5。独立复验另在"整套集成测试并行跑、再加 24 线程"的条件下复现了旧代码失败（四次里一次，0.77）。
- **处理**：
  - 机制：失败的验证与"没有账户"（新加的 `reject`）按同一个顺序，把当前参数与见过的各组参数各算一次。两条路径的计算相同，与快慢、负载都无关。去掉了耗时的记录、中位数、1.2 倍、启动时的校准与假哈希。只有一组参数时，失败从 14.9 降到 13.3 毫秒；参数调整期间，每次失败要按各组真的算一次。代价与局限写进 ADR-007，改进登记为 DEF-037；
  - 测法：主判定是计算量——进程的 CPU 时间按回文的轮次取样，取各轮比值的中位数；辅判定是墙上耗时的下四分位之比。旧参数与当前参数的账户都和"不存在"比较；先核对量到了线程池里的哈希。另核对重启之后、旧参数的账户登录之前，不存在的用户名就已经算上库里的参数组。集成项目写死每个测试文件一个进程；
  - 复验者的两条用例移进仓库：第一次验证要等库里的参数读完；`reject` 与验证一样受名额与排队的上限。
- **独立复验**（一位 Opus 5.5 复验者，在负载下做了上百次复跑与 10 个变异）：**修复后通过**。新机制从机制上消除了根因：所有负载下 CPU 时间之比都约等于 1（0.93–1.05）。必须修 1 条：第一批改的 ABBA 墙上耗时判定在更重的起落负载下仍会误报，"整套集成测试并行跑、再加负载"时八次里五次越界，比旧测法还差。复验者给出改法并验证过，就是上面的计算量加下四分位。建议 6 条：第一次验证"等参数读完"没有用例守着（R5）、`reject` 进名额没有用例守着（R3）、集成只取样旧参数的账户（R1、R7 只有单元检得出）、CPU 时间的前提没有核对（R9）、ADR-007 的代价写得不准、一处旧注释。都按建议改了。
- **第二批由主会话核实**：
  - 负载复跑：单跑负载 B 五次、负载 D（96 线程）五次、负载 A 三次全部通过；整套集成测试并行跑再加负载 B，六次都是 2542 条通过。复验者此前在这两种条件下测得的是 3/4 与 5/8 次失败；

- **修复合并之后（`2f527d8`）的 CI**：verify、Chromium、Chrome、Edge 与容器 E2E 通过（登录耗时的修复在 CI 上成立；容器 E2E 空闲 211.6 MiB、峰值 250.0、跑完之后 204.8 MiB）。**WebKit 一片失败**：US-M2-07 的主链路第一次跑出现"页面里没接住的异常"、重试通过，CI 上出现重试即失败——本片加的全局夹具与"重试即失败"都起了作用。两条"异常"是"Fetch API cannot load …/api/documents/<id>（与 …/content）due to access control checks."：用例新建表格、编辑器页刚打开就跳回文件夹页，元数据与内容的请求还在路上。
- **根因**（分支 `m2-ci-webkit-cancelled-fetch`）：
  - WebKit 在整页跳转时取消还在路上的请求，会自己往控制台打这一句；Playwright 在 WebKit 上把来源为 javascript 的控制台错误一律当成页面错误（按第一个冒号拆成名称与说明）；
  - 它不是应用的错误：应用的请求都经 `apiFetch`，失败会包装成 NetworkError；真正没接住的拒绝，WebKit 报的是"Unhandled Promise Rejection: TypeError: …"（本机对照核实）；
  - 本机反复打开编辑器页、不等加载完就跳走，WebKit 每次都报，Chromium 不报；
  - 全局夹具把浏览器自己的诊断也算了进来，与第 2 片排除的 ResizeObserver 通知是同一类。
- **处理**：
  - 夹具的"浏览器通知"加这一条：只排除地址与报告时的页面同源的、写法严格匹配；排除掉的另记一份；
  - 新增 `tests/e2e/support/page-errors.test.ts` 核对写法的边界：别的源、别的协议、页面地址未知、真正没接住的拒绝、说法不同，都不排除。单元项目收进 `tests/e2e/support` 下的测试；
  - 新增 `foundation/page-errors.spec.ts`，在真实浏览器里构造这种跳转：WebKit 上要确实出现过这条诊断并被排除，真正没接住的拒绝照样报出；
  - 4 个变异全部检出：去掉排除、不核对同源（单元检出）、排除过宽、自测一次也不跳走（前提核对检出）。
