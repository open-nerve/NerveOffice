## 任务

### S1 后端骨架与工具链验证

- [x] 1. 依赖进目录（catalog）：NestJS 12.1.0 全家、Nest CLI 12.0.5、express 5.2.1、reflect-metadata、rxjs、pino、pino-http、@types/express。安装时逐个决定安装脚本（`allowBuilds`），核对许可与单例。
- [x] 2. `apps/api` 的包与配置：
  - `package.json`：ESM；导出 `.`，源码条件指向 `src/app/index.ts`；
  - `tsconfig.json`、`tsconfig.build.json`、`nest-cli.json`（入口 `app/main`）、`.env.development`；
  - 脚本：`build`（`nest build`）、`dev`、`typecheck`、`start`。
- [x] 3. config 模块（进程入口离不开它，从 S2 提前）：
  - 测试先行：变量映射、默认值、`_FILE`、两者同时设置、类型与范围、未知的 `NERVE_` 变量、错误一次列出且不含取值；
  - `loadConfig(env)`、`loadConfigFromEnvironment()`、`APP_CONFIG`。
- [x] 4. 先写失败的测试：
  - 单元测试里，经依赖注入取得健康检查的控制器；
  - 集成测试里，经 `createApplication()` 启动应用，`GET /api/health/live` 返回 200。
- [x] 5. 实现最小骨架：`app/`（`createApplication`、`ApplicationRuntime`，此时只有最基本的退出）、`modules/health/`（live，以及只看运行状态的 ready）、`app/main.ts`。
- [x] 6. 进程测试：
  - 先构建，再用 `node apps/api/dist/app/main.js` 启动，等"开始监听"的日志，发 SIGTERM，断言退出码为 0；
  - 缺少 `NERVE_DATABASE_URL` 时退出码 1，输出里有 `CONFIG_INVALID` 与变量名。
- [x] 7. ESLint：
  - api 的元素与策略；
  - 按路径的导入限制；
  - `node/no-process-env`；
  - 控制器参数的 `schema` 要求与 `@Req`、`@Res` 的禁用；
  - SQL 拼接的限制。

  lint 自测为每一条补违规样例。另加一条：`consistent-type-imports` 不会把依赖注入要用的类改成 `import type`。
- [x] 8. Vitest：api 的单元测试并入 `unit` 项目；node 项目的源码条件改到 `ssr.resolve.conditions`。故事对照改为列举全部项目。单例清单加上 NestJS 与 reflect-metadata（drizzle-orm 在 S3 引入时加入）。
- [x] 9. 脚本与 `verify`：
  - `test`：`unit`（含 api）与 `unit-web` 两个单元项目；
  - `test:integration`、`test:coverage`：先构建 api；
  - `verify`：快速与完整两种模式按设计 §3.10 调整，同步更新 `plan.test.ts`；
  - 覆盖率：加上 `apps/api/src/**` 80%。
- [x] 10. 手工验证 `pnpm dev:api` 的监听与重启，结果写进 ADR-004。
- [x] 11. ADR-004：NestJS 12（纯 ESM）的验证结论与后端工具链；ADR-002 的后端一行同步。

### S2 日志与 HTTP 管线

- [x] 1. 进程入口的日志换成 pino：配置错误时输出一行 JSON，带 `code: CONFIG_INVALID` 与变量清单；进程测试同步改为按字段断言。
- [x] 2. logging 模块：
  - 根日志与 pino-http（请求标识、字段、级别、忽略探针、脱敏）；
  - 请求上下文；
  - Nest 日志适配；应用代码用注入的 `AppLogger`（不用 Nest 的静态 `Logger`，lint 禁止）；
  - 单元测试覆盖请求标识的接受规则、脱敏清单与适配的级别映射。
- [x] 3. contracts：错误码登记表、`ErrorCode`、退役清单及其测试。健康检查的响应结构。
- [x] 4. `shared/errors`：`AppError`。全局异常过滤器：单元测试覆盖映射表的每一行，意外错误只回通用信息。
- [x] 5. security 模块：
  - 安全响应头（CSP 逐字比对、HSTS 只在 HTTPS 上、所有响应默认 `Cache-Control: no-store`）；
  - JSON 解析与上限；
  - 深度与数量检查。
- [x] 6. 全局校验管道：`StandardSchemaValidationPipe` 加上自己的异常工厂。
- [x] 7. `configureHttp()` 按设计 §3.2 的顺序组装。
- [x] 8. 集成测试（挂只在测试里存在的控制器）：
  - 各类错误响应的格式与错误码；
  - 所有响应都带安全头；
  - `X-Request-Id` 的透传与生成；
  - 请求日志的字段与脱敏；
  - 请求体上限、嵌套深度与数量。
- [x] 9. ADR-006：错误码与错误响应格式。

### S3 数据库、迁移与审计

- [x] 1. 依赖进目录：drizzle-orm、drizzle-kit、pg；决定安装脚本；单例清单加上 drizzle-orm。
- [x] 2. database 模块：连接池（超时、`application_name`、错误日志、退出时关闭）、Drizzle 实例、`DbExecutor`。
- [x] 3. `compareMigrations()`：测试先行，覆盖一致、待执行、库里更多、哈希不同、时间戳不同。
- [x] 4. 表定义 `db/schema/audit/index.ts`，`drizzle.config.ts`（通配符 `src/db/schema/*/index.ts`）。用 drizzle-kit 按表定义生成第一个迁移（CHECK 约束与部分索引写在表定义里）；只追加的触发器另用 `--custom` 写一个手写迁移。审阅后入库。
- [x] 5. 集成测试的数据库辅助：模板库（按迁移的名称、哈希与时间戳命名，advisory lock）、每个测试文件复制一份、空库、清理。
- [x] 6. 迁移执行 `runMigrations()` 与命令 `cli/migrate.ts`。集成测试：
  - 从零执行；
  - 再执行一次什么也不做；
  - 两个并发只执行一次；
  - 库里不一致时拒绝；
  - 等锁超时的提示。
- [x] 7. 库结构版本检查（database 模块对外提供），集成测试覆盖三种结果。
- [x] 8. contracts 的审计动作；audit 模块（服务、仓储、事件校验）。集成测试：
  - 写入的字段正确；
  - UPDATE、DELETE、TRUNCATE 被触发器拒绝；
  - CHECK 约束拒绝不一致的事件。
- [x] 9. 语句超时生效的集成测试。
- [x] 10. `migrations` 门禁：
  - 纯函数：journal 与文件对应、时间戳递增、与基准相比只追加；
  - 装配：从 git 读取基准；
  - 测试：合规与违规样例；
  - 接入静态检查；CI 检出取完整历史，推送事件以推送之前的提交为基准（审查 B4 之后的做法）。
- [x] 11. 根脚本 `db:migrate`、`db:generate`。
- [x] 12. ADR-005：PostgreSQL 18 与迁移策略。

### S4 健康检查与优雅退出

- [x] 1. health 模块：应用的运行状态、就绪探针（接收请求、数据库、库结构），检查语句带 2 秒的超时。
- [x] 2. 退出编排（`ApplicationRuntime.shutdown`）：
  - 单元测试（假的服务器与时钟）：顺序、超时后强制、重复调用；
  - 退出过程中响应加 `Connection: close`。
- [x] 3. 服务器超时取自配置。`main.ts` 接管信号（第二次立即退出）与未捕获的异常。
- [x] 4. 集成测试：
  - 就绪探针在正常、数据库不可达、待执行迁移、正在退出时的结果；
  - 在途的慢请求（含数据库查询）在退出过程中正常完成；
  - 新连接被拒绝；
  - 连接池关闭（`pg_stat_activity` 里没有应用的连接）；
  - 超时后强制退出。
- [x] 5. 进程测试：SIGTERM 后退出码 0，日志里有退出的开始与完成。
