# M1-P4 编辑器接入与在线保存：架构设计与实施规划

> 状态：进行中｜日期：2026-09-27｜基于代码版本：`b219558`

## 1. 目标与范围

对应 M1 总设计 §5 的 P4 一行：新建 → 编辑 → 保存 → 重开。本 Phase 交付以下用户故事：

| 故事 | 本 Phase 交付的部分 |
|---|---|
| US-M1-04 新建表格并进入编辑 | 全部：列表里新建，整页打开编辑器，空白表格立即可以输入；同一个创建请求重复提交只生成一份 |
| US-M1-05 保存到云端，看到真实的保存状态 | 全部：有未保存的修改 → 保存中 → 已保存到云端；保存期间继续输入，回包后仍是有未保存的修改；离开提示；按钮与 Ctrl/Cmd+S；保存的快照里公式结果与重算一致 |
| US-M1-06 重开看到最后一次保存的内容 | 全部：值、公式与格式一致；未保存的修改不出现；打开不被判定为有修改 |
| US-M1-07 两个标签页，旧页面的保存不覆盖新内容 | 全部：旧修订号的保存被拒绝，界面提示版本冲突并保留本页内容，服务器上是先保存的版本 |
| US-M1-08 别人的与不存在的文档结果相同（页面部分） | 编辑器页：两种情况显示同一个页面；未登录时先登录，登录后回到编辑器页 |
| US-M1-09 编辑器在定稿的 CSP 下工作（编辑器部分） | 编辑器页、编辑器脚本与公式 Worker 都带策略，编辑器（含公式 Worker）正常工作，没有违规；CI 的 Edge 通过后关闭 DEF-001 |

- **范围内**：
  1. 数据：`documents` 补上修订号、`unitId`、插件档案与格式版本；新建 `document_contents`、`document_revisions`（迁移只做加法）；
  2. 接口：新建（模板快照，`requestId` 幂等）、读取内容（gzip，修订号作 ETag）、保存（按基准修订号条件写入，`requestId` 幂等，冲突时返回当前修订号及其来源）；
  3. 收敛的模板快照：按生产档案生成、入库，三个浏览器上的回归；
  4. 编辑器适配层（M1 总设计 §6.6）：插件档案 `sheet@1`、公式 Worker、身份替换、变更检测、公式收齐、`IMAGE()` 的限制、M5 之前的入口、内部 API 登记；
  5. 编辑器页：整页加载，保存按钮、快捷键、保存状态、离开提示、版本冲突；个人空间列表里的新建与打开；
  6. 托管：编辑器的路径映射到编辑器页；
  7. 构建与门禁：编辑器入口与公式 Worker 的体积预算；产物扫描覆盖 Univer 的产物（含 DEF-016）；
  8. ADR：编辑器身份；编辑器适配层与内部 API 登记；文档内容与保存协议。
- **范围外**（M1 总设计 §1）：编辑租约、阅读模式、自动保存、捕获时机的防抖与"公式待更新"标记、完整的快照校验与内容哈希、打开自检（M3）；本机发件箱、Worker 创建失败时的重建（M4）；图片资源、超链接白名单、粘贴清洗（M5）；重命名、复制、删除（M2）；容量达到 80% 的提示（M3 随保存协议的其余部分）。

## 3. 设计

### 3.1 模块划分与依赖方向

| 位置 | 职责 | 可以引用 |
|---|---|---|
| api `documents` 模块 | 文档元数据、内容读写、修订记录、模板快照的实例化；访问策略 | spaces、audit、database、config |
| `packages/contracts` | 新建、保存的请求与响应，冲突的详情，快照的常量（体积上限、档案标识、格式版本），收敛的模板快照 | — |
| web `src/editor/`（编辑器适配层） | Univer 的一切：档案、Worker、身份、变更检测、公式收齐、`IMAGE()`、入口的隐藏与守卫；对外只有一个小接口（§3.6.1） | shared、contracts |
| web `src/editor/internal-api/` | 内部 API 的唯一出口与登记表 | — |
| web `src/features/sheet-editor/` | 编辑器页：载入、保存状态机、离开提示、快捷键、冲突与错误的界面 | shared、auth 与 contracts 的公开入口、编辑器的公开入口 |
| web `src/entries/editor/` | 编辑器页的入口：`main.tsx`（副作用导入）、`mount.tsx` | 编辑器页的公开入口、shared |
| web `src/features/documents/` | 列表里的"新建表格"与打开 | 同 P3 |

- 编辑器页与适配层分开：适配层只回答"这份快照在 Univer 里怎么编辑、怎么捕获"，页面负责请求、状态与界面。保存状态机不依赖 Univer，用假的编辑器做单元测试。
- lint 的边界：只有编辑器的入口与 `sheet-editor` 功能能引用 `src/editor/` 的公开入口；平台的应用层不得引用 `sheet-editor`（Univer 不进平台页面的包，门禁 `budgets` 另外兜底）。

### 3.2 数据模型与迁移（`0006_document_content`，只做加法）

**documents**（补列）：

| 列 | 类型 | 说明 |
|---|---|---|
| `revision` | `integer`，默认 1，CHECK `>= 1` | 当前修订号。新建即修订号 1；每次保存加一 |
| `unit_id` | `text`，唯一 | Univer 的 `unitId`，新建时由服务端生成（UUID），写进快照的顶层 `id`，终身不变（计划书 §8.3） |
| `profile` | `text` + CHECK（`sheet@1`） | 插件档案的标识与版本 |
| `format_version` | `integer` + CHECK（`1`） | 平台格式版本（计划书 §8.1："不以 SDK 版本号作为平台格式的唯一版本号"） |
| `sdk_version` | `text` | 最近一次写入时的 Univer 版本（本期 `1.0.0`） |

已有的行（只在开发与测试库里）按默认值补齐；`unit_id` 先以随机值补齐再去掉默认值。这些行没有内容，打开时按"数据不一致"处理（§3.5.4）；开发库可以重建，测试数据的辅助同步更新。

**document_contents**（每份文档一份当前快照）：

| 列 | 类型 | 说明 |
|---|---|---|
| `document_id` | `uuid`，主键，外键 `documents(id)`，`ON DELETE CASCADE` | |
| `snapshot` | `bytea` | gzip 压缩的快照 JSON 字节（计划书 §8.1，不用 `jsonb`） |
| `raw_bytes` / `stored_bytes` | `integer` | 解压后与压缩后的字节数；CHECK `stored_bytes = octet_length(snapshot)`，`raw_bytes` 在 1 与上限之间 |
| `updated_at` | `timestamptz` | |

**document_revisions**（每次新建或保存一行元数据，不存正文）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid`，默认 `uuidv7()` | |
| `document_id` | `uuid`，外键，`ON DELETE CASCADE` | 与 `revision` 联合唯一 |
| `revision` | `integer` | |
| `kind` | `text` + CHECK（`created`、`saved`） | |
| `request_id` | `uuid`，唯一 | 客户端生成；幂等的依据 |
| `payload_digest` | `bytea`（32 字节） | 请求负载的 SHA-256（§3.5.3），相同 `requestId` 的重试据此判断是不是同一个请求 |
| `client_instance_id` | `uuid`，可空 | 编辑器页每次加载生成；新建时为空 |
| `local_seq` | `integer`，可空，CHECK `>= 0` | 捕获时的本地修改序号 |
| `saved_by` | `uuid`，外键 `users(id)` | |
| `created_at` | `timestamptz` | |

- 索引：`(document_id, revision)` 唯一；`request_id` 唯一。
- 审计动作新增 `documents.created`、`documents.content_saved`（contracts 的 `AUDIT_ACTIONS` 与审计表的 CHECK 同步，迁移里一起改）。审计不含正文，只记修订号。

### 3.3 接口契约

| 接口 | 请求 | 成功 | 失败 |
|---|---|---|---|
| `POST /api/documents` | JSON：`{ type: 'sheet', title?, requestId }` | 201：文档元数据；同一个 `requestId` 重放时 200，返回同一份文档的当前元数据 | 400 `REQUEST_INVALID`；409 `REQUEST_ID_CONFLICT`（同一个 `requestId`、不同的负载） |
| `GET /api/documents/{id}` | — | 元数据（P3）补上 `revision`、`profile`、`formatVersion` | 404 `NOT_FOUND`（别人的与不存在的相同） |
| `GET /api/documents/{id}/content` | — | 200：正文是快照 JSON，`Content-Encoding: gzip`；`ETag: "<修订号>"` | 404 `NOT_FOUND` |
| `PUT /api/documents/{id}/content?baseRevision&requestId&clientInstanceId&localSeq` | 正文是 gzip 压缩的快照 JSON，`Content-Type: application/gzip` | 200：`{ revision, savedAt }`；同一个 `requestId` 重放时返回原来的结果 | 409 `DOCUMENT_REVISION_CONFLICT`（附当前修订号及其来源）；409 `REQUEST_ID_CONFLICT`；413 `PAYLOAD_TOO_LARGE`（解压后超过 5 MiB）；415 `UNSUPPORTED_MEDIA_TYPE`；422 `SNAPSHOT_INVALID`；404 `NOT_FOUND` |

- **新错误码**：`DOCUMENT_REVISION_CONFLICT`（409）、`REQUEST_ID_CONFLICT`（409）、`SNAPSHOT_INVALID`（422）。
- **错误的详情**：统一的错误响应加一个可选的 `details` 对象，按错误码约定结构。本期只有修订号冲突用它：`{ currentRevision, source: { clientInstanceId, localSeq } }`，来源取当前修订的那一行，新建出来的修订没有来源时为 `null`。`AppError` 加 `details` 选项，异常过滤器原样带出。ADR-006 的"错误响应只有三个字段"改为"三个字段加可选的 `details`"（加法）。
- **保存的元数据放在查询参数里**：沿用"输入都经 `@Query({ schema })` 校验"的写法；正文只有快照的字节。不用 `application/json`：全局的 JSON 解析器上限 256 KiB、嵌套 32 层、元素 1 万个，快照远超这些，也不该让它解析一遍再重新序列化（计划书 §7.2："同一份序列化并压缩后的数据，既用来写入本机，也用来上传"）。
- **读取**：数据库里的 gzip 字节原样下发，浏览器按 `Content-Encoding` 自动解压。响应照常带 `Cache-Control: no-store`；修订号的 ETag 供客户端读取（`If-None-Match` 与 304 随 M3 的修订号检查一起做）。反向代理不得二次压缩（写进 P5 的备注）。
- 所有新接口都要求登录；新建与保存是状态变更，照常检查 Origin 与 CSRF 令牌。

### 3.4 新建与模板快照

- **模板**：收敛后的空白工作簿快照，放在 contracts（`documents/sheet-template.ts`，服务端新建时用，E2E 用它核对收敛）。一张工作表（`工作表1`，id `sheet-1`，行列数用 SDK 默认的 1000 × 20），`locale` 为 `zhCN`；工作簿的 `name` 固定，标题只存在平台的元数据里。
- **收敛**：计划书 §8.1 要求"新建文档使用收敛后的模板快照"。判据是"用生产档案打开 → 保存"两次逐字节相同（M0-P2 报告 §2.2：手写样本要到第二次保存才稳定）。
- **生成与更新**：只经产品本身，不另写测试钩子：
  - 更新脚本（`pnpm --filter @nerve-office/e2e run update:sheet-template`）用 E2E 的服务新建一份文档，在编辑器页里保存、重开再保存，直到两次保存的快照相同，把结果（`id` 换回占位值）写回 contracts；
  - SDK 升级或档案变更时执行一次（插件档案是数据，按计划书 §8.7 做保存重开回归）。
- **回归**：E2E"新建的文档打开后立即保存，服务器上的快照与模板逐字节相同（`id` 除外）"，本机三个浏览器与 CI 的 Edge 都跑。这同时确认"替换 `unitId` 之后模板仍然收敛"（M1 总设计 §6.6）。
- **实例化**：服务端 `JSON.parse` 模板、把顶层 `id` 换成新的 `unitId`、再 `JSON.stringify`。模板本身就是 `JSON.stringify` 的输出，这一来一回逐字节不变（单元测试断言）。
- **新建**（一个事务）：
  1. 按 `requestId` 查修订记录：有，就核对负载摘要（类型与标题），一致则返回那份文档（200），不一致则 `REQUEST_ID_CONFLICT`；
  2. 在调用者的个人空间里建文档（标题默认"未命名表格"），写内容（修订号 1），写一行 `created` 修订记录，写审计 `documents.created`；
  3. 并发的两个相同请求：事务开头按 `requestId` 取事务级 advisory lock，两个相同的请求排队执行，后到的一方在第 1 步就按重放处理；修订记录的唯一约束兜底。

### 3.5 保存协议

#### 3.5.1 服务端的处理顺序

计划书 §7.4 的顺序，取 M1 的部分：

1. **解析**：路由自己的解析器只接受 `application/gzip`，压缩后上限 5 MiB；流式解压，解压后超过 5 MiB 立即停下（`413`），压缩炸弹在上限处截住。
2. **基本校验**（M1 总设计 §6.5）：UTF-8 的 JSON；顶层是对象，`sheetOrder` 是数组、`sheets` 是对象（工作簿）；顶层 `id` 等于这份文档的 `unit_id`；嵌套不超过 64 层。不合格返回 `SNAPSHOT_INVALID`。完整的快照校验（资源白名单、必须为空的资源等）在 M3。
3. **一个事务**，统一的加锁顺序：
   1. 按文档 id 锁住文档行（`FOR UPDATE`），同时判断权限（能编辑）；没有权限与不存在相同；
   2. **幂等**：按 `requestId` 查修订记录。有且属于这份文档、负载摘要一致：返回原来的 `{ revision, savedAt }`；否则 `REQUEST_ID_CONFLICT`。幂等只要求调用者仍能编辑这份文档；
   3. **条件写入**：`baseRevision` 不等于当前修订号时 `DOCUMENT_REVISION_CONFLICT`，详情带当前修订号及其来源；
   4. 写内容、修订号加一、写修订记录（`saved`，带 `clientInstanceId`、`localSeq`）、写审计 `documents.content_saved`。
- 先锁文档再查幂等：同一个请求的两次并发重试，后到的一方等锁，拿到锁时前一方已经提交，按幂等返回原结果，而不是误报冲突。
- 存储的是客户端的 gzip 字节（已经成功解压过一遍）；读取时原样下发。

#### 3.5.2 修订号与冲突

- 修订号是整数，新建为 1，每次成功保存加一；以修订号作 ETag（`"<修订号>"`）。
- 冲突只有一种：别人在中间产生了新的修订（计划书 §7.1）。M1 没有租约，两个标签页可以同时编辑，由条件写入保证不会静默覆盖（M1 总设计 §7）。
- **"自己追自己"**：本页上一次保存的请求其实已经提交、但回包丢了（网络错误），再保存时基准修订号已经过时。冲突的详情里，来源的 `clientInstanceId` 是本页、`localSeq` 是那一次请求的序号时，客户端知道那次保存已经成功：把基准换成当前修订号，用新的 `requestId` 立即重发一次（只自动重发一次）。其他来源的冲突就是真正的冲突。

#### 3.5.3 负载摘要与 `requestId`

- 新建：`sha256('created\n' + 类型 + '\n' + 标题)`。
- 保存：`sha256('saved\n' + baseRevision + '\n' + 解压后的快照字节)`。按解压后的字节算：同一份内容重试时，客户端不必保证压缩结果逐字节相同。
- `requestId` 由客户端生成（UUID），一次保存尝试一个。网络错误后，内容没有变化就用同一个 `requestId` 重发；内容变了就是新的一次保存。
- 修订记录保留 30 天与历史版本列表都不在 M1。

#### 3.5.4 读取

- 读取内容与读取元数据一样经访问策略；别人的与不存在的相同。
- 文档有记录、却没有内容行：数据不一致，按意外错误处理（500，写日志），不伪装成 404。
- 响应头：`Content-Type: application/json; charset=utf-8`、`Content-Encoding: gzip`、`Content-Length`、`ETag`。控制器返回一个值对象，由 documents 模块的拦截器写响应头与正文：控制器仍然不接触响应对象（P2 的写法限制）。

### 3.6 编辑器适配层（`apps/web/src/editor/`）

#### 3.6.1 对外的接口

```ts
createSheetEditor({ container, snapshot: string }): Promise<SheetEditor>

interface SheetEditor {
  readonly unitId: string
  /** 本地修改序号：检测到修改时加一（§3.6.5） */
  changeSeq: () => number
  onChange: (listener: () => void) => () => void
  /** 生命周期：rendered 之后可以输入，steady 之后才判断"打开是否被判定为有修改" */

  settleFormulas: (timeoutMs: number) => Promise<'settled' | 'timeout'>

```

`createSheetEditor` 在以下都完成之后才返回：工作簿创建、生命周期到达 Rendered、主线程与 Worker 的 `IMAGE()` 限制都安装成功（§3.6.7）。任何一步失败都抛出，页面显示"编辑器加载失败"，不进入编辑。

#### 3.6.2 插件档案 `sheet@1`

- 按插件档案 v1 §1：core、numfmt、formula、drawing、cf、filter、hyperlink、dv、find-replace、note、sort 各组，组内与组间的注册顺序按官方 preset；不注册 `@univerjs/network`、评论、水印、table、十字高亮等；不注册任何 `ITelemetryService` 实现。
- 影响数据的配置：
  - 公式 Worker 模式（默认启用）：主线程的 `FormulaEngine`、`Sheets`、`SheetsFormula` 设 `notExecuteFormula: true`，并注册 `RPCMainThread`；
  - `UniverSheetsPlugin` 的 `largeSheetOperation.largeSheetCellCountThreshold = Number.MAX_SAFE_INTEGER`（关掉大表操作的拆分）；
  - `onlyRegisterFormulaRelatedMutations` 在主线程不写（它的类型只允许 `true`，官方写的 `false` 等同于不写）。
- 档案是数据：插件清单、顺序、影响数据的配置、声明的资源名都集中在 `profile/sheet-profile.ts`。单元测试核对声明与构造结果一致；E2E 用"模板收敛"与"保存重开"回归。
- **声明的资源**（按 ADR-009 修订档案 v1 §3：去掉 `SHEET_AuthzIoMockService_PLUGIN`）：`SHEET_RANGE_PROTECTION_PLUGIN`、`SHEET_WORKSHEET_PROTECTION_PLUGIN`、`SHEET_WORKSHEET_PROTECTION_POINT_PLUGIN`、`SHEET_DEFINED_NAME_PLUGIN`、`SHEET_RANGE_THEME_MODEL_PLUGIN`、`SHEET_DRAWING_PLUGIN`、`SHEET_CONDITIONAL_FORMATTING_PLUGIN`、`SHEET_FILTER_PLUGIN`、`SHEET_DATA_VALIDATION_PLUGIN`、`SHEET_NOTE_PLUGIN`。
- 语言包只合并 `zhCN`；样式按档案导入各插件的 CSS；Facade 的副作用导入只保留用到的（包体积）。

#### 3.6.3 生命周期

1. `new Univer({ locale: ZH_CN, locales, theme, logLevel: WARN, override: [[IAuthzIoService, { useClass: AllowAllAuthzIoService }]] })`；
2. 创建公式 Worker 并传给 `UniverRPCMainThreadPlugin`（§3.6.4）；按档案注册插件；
3. `FUniver.newAPI(univer)`；挂上命令守卫（§3.6.8）与变更检测（必须在创建工作簿之前挂上，才能看到加载过程中的命令）；
4. `createWorkbook(JSON.parse(snapshot))`，核对返回的 `unitId` 等于快照的 `id`；
5. 用公开的 `Event.LifeCycleChanged` 等到 Rendered（可以输入）；主线程到 Ready 后安装 `IMAGE()` 限制，等 Worker 回报；
6. Steady（Rendered 之后 3 秒，SDK 固定）之后，页面才以"是否有修改"判断打开是否干净。
- 一页一份文档、整页加载与卸载（计划书 §10.2）；`dispose()` 销毁实例、终止 Worker。
- 捕获用 `FWorkbook.save()`；捕获前不调用 Facade 的读取方法（它们可能改动模型，例如 `getDataValidations()` 建空条目）。

#### 3.6.4 公式 Worker

- 入口 `src/editor/workers/formula.worker.ts`，插件组合与官方 Worker preset 相同：Sheets（`onlyRegisterFormulaRelatedMutations: true`）、FormulaEngine、RPCWorkerThread、RemoteSheetsFormula、SheetsFilter。
- 主线程用静态的 `new Worker(new URL('./workers/formula.worker.ts', import.meta.url), { type: 'module' })` 创建实例，传给插件的 `workerURL`：传字符串时插件会建一个不带 `type: 'module'` 的经典 Worker（`rpc/src/plugin.ts:86`）。Worker 由适配层负责终止。
- 构建：Vite 的 `worker.format: 'es'`（已有），Worker 以同源脚本加载，不内联成 blob（CSP 的 `worker-src 'self'`）。
- Worker 不引用 contracts 与 zod。
- Worker 创建失败时的判定与重建在 M4；M1 里 Worker 起不来时，`IMAGE()` 的回报等不到，编辑器按加载失败处理（§3.6.7）。

#### 3.6.5 变更检测

- 规则（计划书 §7.3、档案 v1 §5.3）：监听 Facade 的 `CommandExecuted`；只看 `MUTATION`；排除带 `onlyLocal`、`fromCollab`、`fromChangeset`、`fromFormula` 标记的，以及作用于其他单元的（参数里的 `unitId` 不是本文档）；排除名单只有 `sheet.operation.clear-drawing-transformer`；不排除自动行高。
- 检测到修改时，本地修改序号加一（单调递增，页面用它判断"有没有未保存的修改"，保存时作为 `localSeq` 上传）。
- 分类函数是纯函数，单元测试覆盖每一条规则；E2E 覆盖"打开不变脏""代表性的修改变脏""只改视图不变脏"。

#### 3.6.6 公式收齐

- 显式保存前等公式"收齐"（计划书 §7.3）：没有排队的一轮；这一轮没有被 stop；逐表收齐（最近一轮带结果的每张工作表都收到带 `applyFormulaCalculationResult` 的写回；修改没有牵动公式、只收到完成通知时视为收齐）。
- 跟踪器随变更检测一起订阅 `CommandExecuted`：
  - start 开新的一轮；stop 记为被 stop；result 记下带结果的工作表；带 `functionsExecutedState` 的 notification 记为完成；带 `applyFormulaCalculationResult` 的 `sheet.mutation.set-range-values` 记为这张表已写回；
  - "排队"：命令在 `IActiveDirtyManagerService` 里有脏区转换、`shouldTrigger` 没有排除它、`getDirtyData` 非空，或者它是强制重算的触发命令（与 SDK 的触发服务同一口径）。
- 不用 `onCalculationResultApplied` 作为收齐的依据：Worker 模式下它在第一张表写回后就返回，也不等排队的下一轮（M0-P3 报告 §3.3）。
- `settleFormulas(3000)`：每 20 ms 判断一次；超过 3 秒返回 `timeout`，页面照常保存并提示"公式结果尚未保存"（M1 总设计 §6.6）。显式保存不需要捕获时机里的 1 秒防抖（M3 的自动保存才有）。
- 依赖的内部约定（mutation 的 id、执行选项、`IActiveDirtyManagerService`）都经 `internal-api/`，登记在案（§3.6.9）。

#### 3.6.7 `IMAGE()` 的限制

- 采用 `restricted`（档案 v1 §6.2、计划书 §11.3）：参数是平台资源地址才交给原执行器，否则返回 `#VALUE!`，不发请求；本期没有资源服务，实际效果是所有 `IMAGE()` 都显示 `#VALUE!`。不选整体禁用：已有的 `IMAGE()` 会变成 `#NAME?`。
- 安装方式沿用 M0 验证过的做法：生命周期到 Ready 之后，取出原执行器、注册同名的包装、清掉 `IMAGE` 的公式缓存，再核对一次生效的是包装。主线程与 Worker 各装一次。
- **Worker 回报**：Worker 装好后在同一个 Worker 上发 `{ type: 'nerve:image-policy', ok }`（`type` 用字符串，Univer 的 RPC 只认数值类型、忽略其他）。主线程收到 `ok: true` 才算编辑器就绪；20 秒收不到或 `ok: false`，编辑器按加载失败处理（`setEditable(false)`，页面提示刷新）。这个回报也顺带证明 Worker 已经启动、收到了工作簿。
- 引擎插件的 `function` 配置是另一条公开途径，但 M0 没有验证，本期不采用。

#### 3.6.8 M5 之前的入口与菜单配置

- 菜单配置（按菜单项 id 隐藏，编辑模式一份）：
  - 档案 v1 §5.1 的保护类与不支持的功能（工作表背景图片）；
  - 插入图片（`sheet.menu.image` 及两个子项）、超链接（工具栏与右键两种 id）、保存单元格图片。
- **命令守卫**（Facade 的 `BeforeCommandExecute`，取消即不执行）：插入浮动与单元格图片（粘贴图片文件也走这两条）、底层的插入图片命令、打开超链接编辑与写入超链接的命令。隐藏菜单不会停用命令与快捷键（例如超链接的 Ctrl/Cmd+K），所以两者都要有。
- 清单写在 `profile/entry-guards.ts`，逐项登记出处；E2E 覆盖菜单里没有这些入口、Ctrl/Cmd+K 没有反应、粘贴图片文件不产生图片。
- 原因：M1 不替换图片服务，SDK 默认把插入与粘贴的图片存成 data URL（M0-P4 报告 §2.2），M3、M5 的服务端校验会拒收这类快照；计划书 §4.1"编辑器能力不足时，不显示用不了的按钮"。
- 超链接的界面插件启动时按 `location.hash` 导航：编辑器页的地址不用 hash 做别的用途。

#### 3.6.9 身份与内部 API

- **身份**（ADR-009）：用"全部允许"的 `IAuthzIoService` 替换本地授权服务，不调用 `setCurrentUser`：
  - `allowed` 对每个动作返回允许；`batchAllowed` 按请求的形状返回全部允许；`list` 一类返回空；`create`（创建保护规则）拒绝，界面入口也已隐藏；
  - 本地授权服务不再构造，它在构造时注册的资源 `SHEET_AuthzIoMockService_PLUGIN` 随之消失：快照不再有这一项，加载含这一项的快照时它被忽略，下一次保存时消失；
  - 决定：修订档案 v1 的资源白名单，去掉这一项（档案只描述真实存在的数据）；服务端在 M3 的校验按新白名单处理。v0.1 没有存量文档，不涉及迁移。
  - SDK 的当前用户保持匿名（`userID: ''`）：在 `sheet@1` 的范围内只有已隐藏的权限面板读它，E2E 覆盖编辑、增删工作表、筛选、排序、条件格式、数据验证、备注、查找替换都照常。
- **内部 API**（ADR-010）：
  - 只在 `src/editor/internal-api/` 引用；登记表 `internal-api/registry.ts` 逐项写明用途、M0 证据与回归用例，单元测试核对"导出的每一项都已登记"；
  - lint：受限符号清单（按包与导入名，例如 `@univerjs/engine-formula` 的 `IActiveDirtyManagerService`、`IFunctionService`、`BaseFunction`）与 `__getInjector` 的调用，在 `internal-api/` 之外一律报错，自测补样例；
  - 本期的清单：取服务的 `Univer.__getInjector()`；公式收齐的 mutation id、执行选项与 `IActiveDirtyManagerService`；`IMAGE()` 限制的 `IFunctionService`、`BaseFunction`、`ErrorValueObject`、`ErrorType` 与 Worker 里的生命周期服务；身份替换依赖的 `IAuthzIoService` 接口约定。

### 3.7 编辑器页（`apps/web/src/features/sheet-editor/`）

#### 3.7.1 载入

1. 确认会话（`requestSession()`，拿到 CSRF 令牌）；未登录整页转到登录页，带上原地址；
2. 并行读取元数据与内容；`NOT_FOUND` 显示与平台 404 相同的"内容不存在，或者你没有访问权限"（别人的与不存在的相同，US-M1-08）；
3. 核对档案与格式版本（本期只有 `sheet@1` 与格式 1，其他值按"客户端不认识的格式"显示错误，不进入编辑）；
4. 创建编辑器；记下内容的修订号（ETag）作为保存的基准；
5. 页面的状态写在容器的 `data-editor-state` 上（loading、ready、steady、failed），E2E 按它等待，不用固定时长。

#### 3.7.2 保存状态机

- 状态：`clean`（已保存到云端）、`dirty`（有未保存的修改）、`saving`（保存中）、`conflict`（版本冲突）、`failed`（保存失败），另有提示"公式结果尚未保存"。
- "有未保存的修改" = 当前的修改序号大于已保存的序号，或者上一次保存时公式还没收齐。只有服务端确认成功后，已保存的序号才前进到那次捕获时的序号（取较大值）：保存期间的新修改不会被标成已保存（A08）。正在编辑、还没提交的单元格不产生修改（它作用于单元格编辑器自己的文档），离开提示另外把它算进去（§3.7.3）。
- **一次保存**（按钮或 Ctrl/Cmd+S；同一时间只有一个保存在途，保存中再按忽略）：
  1. 单元格正在编辑：先提交（等同回车）；提交不了，中止保存并提示"请先完成单元格的编辑"；
  2. 等公式收齐，最多 3 秒；超时照常保存，保存成功后提示"公式结果尚未保存，请稍后再保存一次"；
  3. 捕获；序列化后超过 5 MiB 直接提示"表格超过容量上限（5 MiB），无法保存"，不上传；
  4. gzip（`CompressionStream`，主线程；5 MiB 时阻塞接近 100 ms，放进 Worker 是 M4 发件箱的设计）；
  5. `PUT`，带基准修订号、新的 `requestId`、本页的 `clientInstanceId`、捕获时的修改序号；
  6. 成功：基准修订号换成新的修订号，已保存的序号前进；
  7. 冲突：是"自己追自己"就换基准、换 `requestId` 立即重发一次；否则进入 `conflict`；
  8. 网络错误或 5xx：进入 `failed`，保留这次请求；内容没有变化时重试沿用同一个 `requestId`；
  9. 401：会话结束，整页转到登录页（带原地址；有未保存的修改时，浏览器会弹离开提示）；
  10. 413、422：进入 `failed`，显示对应的说明。
- 没有修改时也可以保存（显式保存按用户的意愿执行；修订号照常加一，内容相同时不递增在 M3）。
- **版本冲突**：保留本页内容，禁止继续保存，提示"别处保存了更新的版本。本页的修改没有保存；需要的话先复制出来，再重新加载查看最新版本"，提供"重新加载"按钮。另存为副本与恢复规则在 M4。
- 状态机是纯逻辑（输入：用户操作、编辑器的事件、接口的结果），用假的编辑器与假的接口做单元测试，覆盖上面每一条。

#### 3.7.3 界面

- 页头：返回"我的空间"（整页跳转）、标题、保存状态（`role="status"`，读屏软件会读出变化）、保存按钮（进行中用 `aria-disabled`）；其余是编辑器。
- 快捷键：在捕获阶段监听 Ctrl/Cmd+S（Univer 没有绑定它），阻止浏览器的"另存网页"；按真实平台判断 Ctrl 或 Cmd。
- 离开提示：有未保存的修改（含正在编辑的单元格、冲突之后本页的内容）时，`beforeunload` 让浏览器弹出提示。不把关页时的异步请求当作保存（计划书 §7.8）。
- 样式：编辑器页不加载 Tailwind 的基础重置（preflight），只用主题变量与工具类，免得影响 Univer 的界面（M1 总设计 §7 的风险）；Univer 的样式按档案导入。
- 会话：页面自己的请求得到 401 时整页转到登录页；别的标签页登录或退出（BroadcastChannel）时向服务端确认，换了人就禁止保存并提示刷新，不自动重新加载（本页可能有未保存的修改）。

#### 3.7.4 列表页的新建与打开

- "新建表格"按钮：生成 `requestId` → `POST /api/documents` → 整页打开 `/documents/<id>`。网络错误后重试沿用同一个 `requestId`（同一次点击只生成一份）。进行中用 `aria-disabled`。
- 列表的条目改为链接，整页打开编辑器页。

### 3.8 托管、入口与路由

- 编辑器页的地址是 `/documents/<文档 id>`（最后一段是 UUID，不带点）。`ENTRY_PAGES` 把它映射到 `editor.html`；其他地址照旧回退到平台页面。不是 UUID 的 `/documents/...` 由平台页面显示 404。
- 构建：生产构建与测试构建都加上 `editor.html` 入口（`entries/editor/main.tsx`：先 `zod-jitless`，再样式，再 `mount.tsx`）。
- 开发：Vite 开发服务器加一条只在开发时生效的改写，把 `/documents/<id>` 交给 `editor.html`。
- 两个入口共用 contracts：打包器可能调整模块的执行顺序（ADR-008）。先用 E2E 的违规收集确认两个页面都没有违规，再决定是否开启 `strictExecutionOrder`。

### 3.9 构建、包体积与门禁

- **依赖**：`@univerjs/*` 按 `sheet@1` 用到的包进目录，一律 1.0.0（`@univerjs/icons` 按 SDK 的依赖为 1.43.0）；没有 Pro；`protobufjs` 的安装脚本不执行（`allowBuilds`，写明原因）；许可核对，缺许可正文的包补齐。
- **`budgets`**：
  - 编辑器页入口的首屏 JS（gzip）：按生产档案实测后定，比实测多约 15%–20%（M0 的候选档案实测约 1.93–1.96 MiB）；
  - 公式 Worker 另列一项预算：Worker 在插件启动时就下载，事实上属于首屏的传输量，而现有口径不计它。门禁按构建清单找到入口引用的 Worker 产物，统计它与它静态引用的块；
  - 平台页面的预算不变，并核对它没有因为共用代码而变大。
- **`artifacts`**：
  - Univer 的产物里有大量文档链接（M0-P1 报告 §2.3：support.microsoft.com 509 处等）。允许清单支持按地址前缀放行，逐项写明来源与原因；平台页面的地址照旧按具体地址；
  - 已登记的动态代码按实际产物核对：lodash 的全局对象探测（`globalThisProbeMax: 3`）、zod 的两处；新报出的逐个核对来源；
  - DEF-016：按语法树取字符串的实际值再识别地址，补上协议由插值给出、转义的斜杠、协议相对的地址与不带域名后缀的主机。
- **`deps`**：单例清单已含 `@univerjs/*`、`@wendellhu/redi`、`rxjs`、react；Univer 的版本一致性按 `UNIVER_POLICY`。

| US-M1-05 | 修改后有未保存的修改 → 保存中 → 已保存到云端（按钮与 `ControlOrMeta+S`）；拖住保存的回包期间继续键入，回包后仍有未保存的修改；离开提示；单元格编辑中按保存，内容被提交并保存；改公式的依赖后立即保存，服务器上的快照里公式缓存值与按定义算出的一致（含跨表） |
| US-M1-06 | 保存后刷新与重新登录，值、公式、格式一致；未保存的修改不出现；打开到 steady 之后仍是已保存 |
| US-M1-07 | 同一个浏览器的两个页面：A 保存后 B 保存得到版本冲突，B 保留本页内容；从接口核对服务器上是 A 的版本 |
| US-M1-08（页面） | 别人的文档与不存在的文档，编辑器页显示相同；未登录打开编辑器页先登录，登录后回到编辑器页 |
| US-M1-09（编辑器） | 编辑器页、编辑器脚本、公式 Worker 的响应都带策略；键入值与公式、加粗、打开菜单都没有违规；公式结果正确（证明 Worker 在工作）；外链的 `IMAGE()` 显示 `#VALUE!` |
| 模板与档案 | 新建的文档打开后立即保存，快照与模板逐字节相同（`id` 除外）；图片与超链接的入口不存在，Ctrl/Cmd+K 没有反应，粘贴图片文件不产生图片 |

- 按角色与名称定位，不用设备预设，不用固定时长的等待；键入经真实的键盘事件。
- 从接口取回快照核对内容时，E2E 用会话 Cookie 请求 `GET …/content`。

### 3.11 配置

不新增环境变量。快照的上限（解压后 5 MiB）是平台格式的一部分，写在 contracts 里，与计划书 §12.1 一致；以后要调整，按格式变更处理。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 身份替换之后，某个插件依赖本地授权服务或非空的当前用户 | S2 开头在真实骨架上确认：打开、编辑、增删工作表、筛选、排序、条件格式、数据验证、备注、查找替换都照常；不通过就退回"保留同名的 hook、恒为空"（ADR-009 的备选），并记录原因 |
| 模板替换 `unitId` 后不收敛，或资源数组的顺序跨浏览器不同 | S2 的探针先在三个浏览器上验证；S4 的 E2E 回归。顺序不同时，比较时按资源名排序（服务端的哈希在 M3 也按此口径） |
| 保存前提交单元格编辑的行为（选区移动、数据验证拒绝、编辑栏里的编辑） | S2 的探针逐项实测；提交失败时中止保存并提示；E2E 覆盖编辑中按保存 |
| 公式收齐依赖的内部约定在 1.0.0 的生产构建里与 M0 不同 | S2 用 M0 的场景（跨表、计算进行中再改一次）回归；S4 的 E2E 核对保存的缓存值 |
| 编辑器页的首屏体积与加载时间 | 按生产档案实测后定预算；Facade 的副作用导入只保留用到的；M7 再压测 |
| Univer 的样式与 Tailwind 冲突 | 编辑器页不加载 preflight；E2E 检查页头与编辑器的关键界面 |
| Worker 在 WebKit 上第一次计算较慢（M0 见过 1.77 秒） | 3 秒的收齐上限照常适用；E2E 的等待按状态，不按时长 |
