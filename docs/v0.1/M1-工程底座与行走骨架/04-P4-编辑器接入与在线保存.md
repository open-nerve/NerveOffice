# M1-P4 编辑器接入与在线保存：架构设计与实施规划

> 状态：已完成｜日期：2026-09-27｜基于代码版本：`b219558`

## 1. 目标与范围

对应 M1 总设计 §5 的 P4 一行：新建 → 编辑 → 保存 → 重开。本 Phase 交付以下用户故事：

| 故事 | 本 Phase 交付的部分 |
|---|---|
| US-M1-04 新建表格并进入编辑 | 全部：列表里新建，整页打开编辑器，空白表格立即可以输入；同一个创建请求重复提交只生成一份 |
| US-M1-05 保存到云端，看到真实的保存状态 | 全部：有未保存的修改 → 保存中 → 已保存到云端；保存期间继续输入，回包后仍是有未保存的修改；离开提示；按钮与 Ctrl/Cmd+S；保存的快照里公式结果与重算一致 |
| US-M1-06 重开看到最后一次保存的内容 | 全部：值、公式与格式一致；未保存的修改不出现；打开不被判定为有修改 |
| US-M1-07 两个标签页，旧页面的保存不覆盖新内容 | 全部：旧修订号的保存被拒绝，界面提示版本冲突并保留本页内容，服务器上是先保存的版本 |
| US-M1-08 别人的与不存在的文档结果相同（页面部分） | 编辑器页：两种情况显示同一个页面；未登录时先登录，登录后回到编辑器页 |
| US-M1-09 编辑器在定稿的 CSP 下工作（编辑器部分） | 编辑器页、编辑器脚本与公式 Worker 都带策略，编辑器（含公式 Worker）正常工作，没有违规；CI 的 Edge 通过后关闭 DEF-001 |

- **范围内**：
  1. 数据：`documents` 补上修订号、`unitId`、插件档案与格式版本；新建 `document_contents`、`document_revisions`（迁移只做加法）；
  2. 接口：新建（模板快照，`requestId` 幂等）、读取内容（gzip，修订号作 ETag）、保存（按基准修订号条件写入，`requestId` 幂等，冲突时返回当前修订号及其来源）；
  3. 收敛的模板快照：按生产档案生成、入库，三个浏览器上的回归；
  4. 编辑器适配层（M1 总设计 §6.6）：插件档案 `sheet@1`、公式 Worker、身份替换、变更检测、公式收齐、`IMAGE()` 的限制、M5 之前的入口、内部 API 登记；
  5. 编辑器页：整页加载，保存按钮、快捷键、保存状态、离开提示、版本冲突；个人空间列表里的新建与打开；
  6. 托管：编辑器的路径映射到编辑器页；
  7. 构建与门禁：编辑器入口与公式 Worker 的体积预算；产物扫描覆盖 Univer 的产物（含 DEF-016）；
  8. ADR：编辑器身份；编辑器适配层与内部 API 登记；文档内容与保存协议。
- **范围外**（M1 总设计 §1）：编辑租约、阅读模式、自动保存、捕获时机的防抖与"公式待更新"标记、完整的快照校验与内容哈希、打开自检（M3）；本机发件箱、Worker 创建失败时的重建（M4）；图片资源、超链接白名单、粘贴清洗（M5）；重命名、复制、删除（M2）；容量达到 80% 的提示（M3 随保存协议的其余部分）。

## 3. 设计

### 3.1 模块划分与依赖方向

| 位置 | 职责 | 可以引用 |
|---|---|---|
| api `documents` 模块 | 文档元数据、内容读写、修订记录、模板快照的实例化；访问策略 | spaces、audit、database、config |
| `packages/contracts` | 新建、保存的请求与响应，冲突的详情，快照的常量（体积上限、档案标识、格式版本），收敛的模板快照 | — |
| web `src/editor/`（编辑器适配层） | Univer 的一切：档案、Worker、身份、变更检测、公式收齐、`IMAGE()`、入口的隐藏与守卫；对外只有一个小接口（§3.6.1） | shared、contracts |
| web `src/editor/internal-api/` | 内部 API 的唯一出口与登记表 | — |
| web `src/features/sheet-editor/` | 编辑器页：载入、保存状态机、离开提示、快捷键、冲突与错误的界面 | shared、auth 与 contracts 的公开入口、编辑器的公开入口 |
| web `src/entries/editor/` | 编辑器页的入口：`main.tsx`（副作用导入）、`mount.tsx` | 编辑器页的公开入口、shared |
| web `src/features/documents/` | 列表里的"新建表格"与打开 | 同 P3 |

- 编辑器页与适配层分开：适配层只回答"这份快照在 Univer 里怎么编辑、怎么捕获"，页面负责请求、状态与界面。保存状态机不依赖 Univer，用假的编辑器做单元测试。
- lint 的边界：只有编辑器的入口与 `sheet-editor` 功能能引用 `src/editor/` 的公开入口；平台的应用层不得引用 `sheet-editor`（Univer 不进平台页面的包，门禁 `budgets` 另外兜底）。

### 3.2 数据模型与迁移（`0006_document_content`，只做加法）

**documents**（补列）：

| 列 | 类型 | 说明 |
|---|---|---|
| `revision` | `integer`，默认 1，CHECK `>= 1` | 当前修订号。新建即修订号 1；每次保存加一 |
| `unit_id` | `text` | Univer 的 `unitId`，新建时由服务端生成（UUID），写进快照的顶层 `id`，终身不变（计划书 §8.3）。不唯一：复制文档时快照原样复制，不改写 `unitId`（计划书 §8.3）；最初建了唯一约束，与复制的方案冲突，迁移 `0007_document_unit_id_not_unique` 去掉（Codex 评审 CX5） |
| `profile` | `text` + CHECK（`sheet@1`） | 插件档案的标识与版本 |
| `format_version` | `integer` + CHECK（`1`） | 平台格式版本（计划书 §8.1："不以 SDK 版本号作为平台格式的唯一版本号"） |
| `sdk_version` | `text` | 最近一次写入时的 Univer 版本（本期 `1.0.1`，见 §3.9）。M1 写平台内置的版本（contracts 的 `UNIVER_SDK_VERSION`）；客户端上报构建版本与拦截旧客户端在 M3 |

已有的行（只在开发与测试库里）按默认值补齐；`unit_id` 先以随机值补齐再去掉默认值。这些行没有内容，打开时按"数据不一致"处理（§3.5.4）；开发库可以重建，测试数据的辅助同步更新。

**document_contents**（每份文档一份当前快照）：

| 列 | 类型 | 说明 |
|---|---|---|
| `document_id` | `uuid`，主键，外键 `documents(id)`，`ON DELETE CASCADE` | |
| `snapshot` | `bytea` | gzip 压缩的快照 JSON 字节（计划书 §8.1，不用 `jsonb`） |
| `raw_bytes` / `stored_bytes` | `integer` | 解压后与压缩后的字节数；CHECK `stored_bytes = octet_length(snapshot)`，`raw_bytes` 在 1 与上限之间 |
| `updated_at` | `timestamptz` | |

**document_revisions**（每次新建或保存一行元数据，不存正文）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid`，默认 `uuidv7()` | |
| `document_id` | `uuid`，外键，`ON DELETE CASCADE` | 与 `revision` 联合唯一 |
| `revision` | `integer` | |
| `kind` | `text` + CHECK（`created`、`saved`） | |
| `request_id` | `uuid`，唯一 | 客户端生成；幂等的依据 |

- 审计动作新增 `documents.created`、`documents.content_saved`（contracts 的 `AUDIT_ACTIONS` 与审计表的 CHECK 同步，迁移里一起改）。审计不含正文，只记修订号。

### 3.3 接口契约

| 接口 | 请求 | 成功 | 失败 |
|---|---|---|---|
| `POST /api/documents` | JSON：`{ type: 'sheet', title?, requestId }` | 201：文档元数据；同一个 `requestId` 重放时同样 201（与原请求相同的状态），返回同一份文档的当前元数据 | 400 `REQUEST_INVALID`；409 `REQUEST_ID_CONFLICT`（同一个 `requestId`、不同的负载，或者是别人、别的操作用过的） |
| `GET /api/documents/{id}` | — | 元数据（P3）补上 `revision`、`profile`、`formatVersion` | 404 `NOT_FOUND`（别人的与不存在的相同） |
| `GET /api/documents/{id}/content` | — | 200：正文是快照 JSON，`Content-Encoding: gzip`；`ETag: "<修订号>"` | 404 `NOT_FOUND` |
| `PUT /api/documents/{id}/content?baseRevision&requestId&clientInstanceId&localSeq` | 正文是 gzip 压缩的快照 JSON，`Content-Type: application/gzip` | 200：`{ revision, savedAt }`；同一个 `requestId` 重放时返回原来的结果 | 409 `DOCUMENT_REVISION_CONFLICT`（附当前修订号及其来源）；409 `REQUEST_ID_CONFLICT`；413 `PAYLOAD_TOO_LARGE`（压缩后或解压后超过 5 MiB）；415 `UNSUPPORTED_MEDIA_TYPE`（内容类型不对，或带了 `Content-Encoding`）；400 `REQUEST_INVALID`（查询参数不合法；正文不是完整的 gzip 数据）；422 `SNAPSHOT_INVALID`；403 `PERMISSION_DENIED`（只能查看，M1 的访问策略不会给出）；404 `NOT_FOUND` |

- **新错误码**：`DOCUMENT_REVISION_CONFLICT`（409）、`REQUEST_ID_CONFLICT`（409）、`SNAPSHOT_INVALID`（422）、`PERMISSION_DENIED`（403：访问策略的"查看者"不能保存；M1 只有所有者，这条路径由单元测试覆盖）。
- **新建的重放也是 201**：Nest 按方法给出默认状态码，拦截器改不了它；与 Idempotency-Key 草案"重放给出与原请求相同的状态"一致，客户端也不需要区分。
- **错误的详情**：统一的错误响应加一个可选的 `details` 对象，按错误码约定结构。本期只有修订号冲突用它：`{ currentRevision, source: { clientInstanceId, localSeq } }`，来源取当前修订的那一行，新建出来的修订没有来源时为 `null`。`AppError` 加 `details` 选项，异常过滤器原样带出。ADR-006 的"错误响应只有三个字段"改为"三个字段加可选的 `details`"（加法）。
- **gzip 的数据**：必须恰好是一个完整的成员，末尾没有别的数据。存下的字节会原样以 `Content-Encoding: gzip` 下发，浏览器只解第一个成员：几个成员拼起来、或者末尾带着数据时，服务端与浏览器会解出不同的内容（审查 A1：`gzip("")` 加上合法的成员，服务端解出合法的快照，浏览器解出空串，文档从此打不开）。所以服务端只接受单个完整的成员：解压用标准的 `DecompressionStream`（成员结束之后还有数据即出错），不用 Node 的 `zlib`（它解开全部成员、遇到 0x00 就停，末尾的检查挡不住这两种写法）。浏览器按 `Content-Encoding` 解压时更宽松（只解第一个成员、忽略之后的数据，Chromium 还接受 CRC 错），对单个完整的成员两边解出相同的内容（复验 RA9）。`CompressionStream` 的输出总是单个成员。
- **上传中途断开**：请求头到了、正文没传完客户端就断开时，按请求中断处理（400 `REQUEST_INVALID`，warn 日志，与 ADR-006 相同），不当作意外错误（审查 A3）。
- **保存的元数据放在查询参数里**：沿用"输入都经 `@Query({ schema })` 校验"的写法；正文只有快照的字节。不用 `application/json`：全局的 JSON 解析器上限 256 KiB、嵌套 32 层、元素 1 万个，快照远超这些，也不该让它解析一遍再重新序列化（计划书 §7.2："同一份序列化并压缩后的数据，既用来写入本机，也用来上传"）。
- **读取**：数据库里的 gzip 字节原样下发，浏览器按 `Content-Encoding` 自动解压。响应照常带 `Cache-Control: no-store`；修订号的 ETag 供客户端读取（`If-None-Match` 与 304 随 M3 的修订号检查一起做，DEF-017）。反向代理不得二次压缩（写进 P5 的备注）；万一改动了编码，按规范会把 ETag 标成弱校验器，客户端同样接受 `W/"<修订号>"`（修订号不变，审查 B10）。
- 所有新接口都要求登录；新建与保存是状态变更，照常检查 Origin 与 CSRF 令牌。

### 3.4 新建与模板快照

- **模板**：收敛后的空白工作簿快照，放在 contracts（`documents/sheet-template.ts`，服务端新建时用，E2E 用它核对收敛）。S2 的探针已经在三个浏览器上得到逐字节相同的收敛结果，S1 直接用它（不再放手写的占位）；S4 补上更新脚本与 E2E 回归。一张工作表（`工作表1`，id `sheet-1`，行列数用 SDK 默认的 1000 × 20），`locale` 为 `zhCN`；工作簿的 `name` 固定，标题只存在平台的元数据里。
- **收敛**：计划书 §8.1 要求"新建文档使用收敛后的模板快照"。判据是"用生产档案打开 → 保存"两次逐字节相同（M0-P2 报告 §2.2：手写样本要到第二次保存才稳定）。
- **生成与更新**：只经产品本身，不另写测试钩子：
  - 更新脚本（`pnpm --filter @nerve-office/e2e run update:sheet-template`）用 E2E 的服务新建一份文档，在编辑器页里保存、重开再保存，直到两次保存的快照相同，把结果（`id` 换回占位值）写回 contracts；
  - SDK 升级或档案变更时执行一次（插件档案是数据，按计划书 §8.7 做保存重开回归）。
- **回归**：E2E"新建的文档打开后立即保存，服务器上的快照与模板逐字节相同（`id` 除外）"，本机三个浏览器与 CI 的 Edge 都跑。这同时确认"替换 `unitId` 之后模板仍然收敛"（M1 总设计 §6.6）。
- **实例化**：服务端 `JSON.parse` 模板、把顶层 `id` 换成新的 `unitId`、再 `JSON.stringify`。模板本身就是 `JSON.stringify` 的输出，这一来一回逐字节不变（单元测试断言）。
- **新建**（一个事务）：
  1. 按 `requestId` 查修订记录：有，就核对负载摘要（类型与标题），一致则返回那份文档（201，与原请求相同，§3.3），不一致则 `REQUEST_ID_CONFLICT`；
  2. 在调用者的个人空间里建文档（标题默认"未命名表格"），写内容（修订号 1），写一行 `created` 修订记录，写审计 `documents.created`；
  3. 并发的两个相同请求：事务开头按 `requestId` 取事务级 advisory lock，两个相同的请求排队执行，后到的一方在第 1 步就按重放处理；修订记录的唯一约束兜底。锁键用数据库规范化之后的 UUID（`requestId::uuid::text`）：同一个 UUID 的大小写写法，唯一约束认作同一个，锁也要认作同一个（Codex 评审 CX7）。

### 3.5 保存协议

#### 3.5.1 服务端的处理顺序

计划书 §7.4 的顺序，取 M1 的部分：

1. **解析**：路由自己的解析器只接受 `application/gzip`，压缩后上限 5 MiB；流式解压，解压后超过 5 MiB 立即停下（`413`），压缩炸弹在上限处截住。
2. **基本校验**（M1 总设计 §6.5）：UTF-8 的 JSON；顶层是对象，`sheetOrder` 是数组、`sheets` 是对象（工作簿）；顶层 `id` 是字符串；嵌套不超过 64 层。不合格返回 `SNAPSHOT_INVALID`。这些检查与文档无关，在事务之前做；顶层 `id` 等于这份文档的 `unit_id` 要读文档，放在事务里判断权限之后（否则别人的文档与不存在的文档结果不同）。完整的快照校验（资源白名单、必须为空的资源等）在 M3。
3. **一个事务**，统一的加锁顺序：
   1. 先不加锁读文档，判断能否编辑；没有权限与不存在相同，只能查看是 `PERMISSION_DENIED`。通过之后再按文档 id 锁住文档行（`FOR UPDATE`），锁下再判断一次（加锁之前文档可能移到了别的空间，或者授权被收回，M2）。没有权限与只能查看的请求都不取锁：不会让能编辑的人的保存排队，也不能按等锁的时间区分别人的与不存在的文档（审查 A2、复验 RA7）。权限的查询走事务的连接（访问策略接受事务）：事务已经占着一个连接，再从连接池另取一个，连接池耗尽时会互相等待；
   2. **幂等**：按 `requestId` 查修订记录。有且是同一个人对这份文档的保存、负载摘要一致：返回原来的 `{ revision, savedAt }`；否则 `REQUEST_ID_CONFLICT`。幂等只要求调用者仍能编辑这份文档；然后核对顶层 `id`；
   3. **条件写入**：`baseRevision` 不等于当前修订号时 `DOCUMENT_REVISION_CONFLICT`，详情带当前修订号及其来源；
   4. 写内容、修订号加一、写修订记录（`saved`，带 `clientInstanceId`、`localSeq`）、写审计 `documents.content_saved`。
- 先锁文档再查幂等：同一个请求的两次并发重试，后到的一方等锁，拿到锁时前一方已经提交，按幂等返回原结果，而不是误报冲突。
- 存储的是客户端的 gzip 字节（已经成功解压过一遍）；读取时原样下发。

#### 3.5.2 修订号与冲突

- 修订号是整数，新建为 1，每次成功保存加一；以修订号作 ETag（`"<修订号>"`）。
- 冲突只有一种：别人在中间产生了新的修订（计划书 §7.1）。M1 没有租约，两个标签页可以同时编辑，由条件写入保证不会静默覆盖（M1 总设计 §7）。
- **"自己追自己"**：本页上一次保存的请求其实已经提交、但回包丢了（网络错误），再保存时基准修订号已经过时。冲突的详情里，来源的 `clientInstanceId` 是本页、`localSeq` 是那一次请求的序号时，客户端知道那次保存已经成功：把基准换成当前修订号，用新的 `requestId` 立即重发一次（只自动重发一次）。其他来源的冲突就是真正的冲突。

#### 3.5.3 负载摘要与 `requestId`

- 新建：`sha256('created\n' + 类型 + '\n' + 标题)`。
- 保存：`sha256('saved\n' + baseRevision + '\n' + 解压后的快照字节)`。按解压后的字节算：同一份内容重试时，客户端不必保证压缩结果逐字节相同。
- `requestId` 由客户端生成（UUID），一次保存尝试一个。网络错误后，内容没有变化就用同一个 `requestId` 重发；内容变了就是新的一次保存。
- 修订记录保留 30 天与历史版本列表都不在 M1。

#### 3.5.4 读取

- 读取内容与读取元数据一样经访问策略；别人的与不存在的相同。
- 文档有记录、却没有内容行：数据不一致，按意外错误处理（500，写日志），不伪装成 404。
- 响应头：`Content-Type: application/json; charset=utf-8`、`Content-Encoding: gzip`、`Content-Length`、`ETag`。控制器返回一个值对象，由 documents 模块的拦截器写响应头与正文：控制器仍然不接触响应对象（P2 的写法限制）。

### 3.6 编辑器适配层（`apps/web/src/editor/`）

#### 3.6.1 对外的接口

`createSheetEditor` 在以下都完成之后才返回：工作簿创建、生命周期到达 Rendered、主线程与 Worker 的 `IMAGE()` 限制都安装成功（§3.6.7）。任何一步失败都抛出，页面显示"编辑器加载失败"，不进入编辑。就绪之前不允许编辑，由编辑器页的交互屏障保证：载入期间，页头之外的用户输入（点击、悬停、键入、输入法、粘贴与拖放）在窗口的捕获阶段一律拦下，包括 Univer 挂在 `document.body` 下的浮层；浏览器的刷新与 Tab 由浏览器照常处理、但不传给 SDK（它的快捷键里 Ctrl/Cmd+R 是向右填充、Tab 是选区右移）；就绪（保存状态机建好之后）或失败时撤掉（Codex 评审 CX1，独立复验 N1、S2，第二轮复验）。不能用 `setEditable(false)` 兜底：SDK 在 Ready 时、用户变化时按授权服务初始化权限点，编辑器身份一律允许，更早设的不可编辑会被改回来；也不用 `inert`：它让 Univer 初始化时的聚焦失败，就绪之后键入进不去。每创建一样（Worker、Univer 实例、各项监听）就登记它的销毁，任何一步失败（包括创建 Univer、注册插件）都按相反的顺序销毁已经创建的一切；一项销毁出错不妨碍其余各项（审查 B8）。

#### 3.6.2 插件档案 `sheet@1`

- 按插件档案 v1 §1：core、numfmt、formula、drawing、cf、filter、hyperlink、dv、find-replace、note、sort 各组，组内与组间的注册顺序按官方 preset；不注册 `@univerjs/network`、评论、水印、table、十字高亮等；不注册任何 `ITelemetryService` 实现。
- 影响数据的配置：
  - 公式 Worker 模式（默认启用）：主线程的 `FormulaEngine`、`Sheets`、`SheetsFormula` 设 `notExecuteFormula: true`，并注册 `RPCMainThread`；
  - `UniverSheetsPlugin` 的 `largeSheetOperation.largeSheetCellCountThreshold = Number.MAX_SAFE_INTEGER`（关掉大表操作的拆分）；
  - `onlyRegisterFormulaRelatedMutations` 在主线程不写（它的类型只允许 `true`，官方写的 `false` 等同于不写）。
- 档案是数据：插件清单、顺序、影响数据的配置、声明的资源名都集中在 `profile/sheet-profile.ts`。单元测试核对声明与构造结果一致；E2E 用"模板收敛"与"保存重开"回归。
- **声明的资源**（按 ADR-009 修订档案 v1 §3：去掉 `SHEET_AuthzIoMockService_PLUGIN`）：`SHEET_RANGE_PROTECTION_PLUGIN`、`SHEET_WORKSHEET_PROTECTION_PLUGIN`、`SHEET_WORKSHEET_PROTECTION_POINT_PLUGIN`、`SHEET_DEFINED_NAME_PLUGIN`、`SHEET_RANGE_THEME_MODEL_PLUGIN`、`SHEET_DRAWING_PLUGIN`、`SHEET_CONDITIONAL_FORMATTING_PLUGIN`、`SHEET_FILTER_PLUGIN`、`SHEET_DATA_VALIDATION_PLUGIN`、`SHEET_NOTE_PLUGIN`。
- 语言包只合并 `zhCN`；样式按档案导入各插件的 CSS；Facade 的副作用导入只保留用到的（包体积）。

#### 3.6.3 生命周期

1. `new Univer({ locale: ZH_CN, locales, theme, logLevel: WARN, override: [[IAuthzIoService, { useClass: AllowAllAuthzIoService }]] })`；
2. 创建公式 Worker 并传给 `UniverRPCMainThreadPlugin`（§3.6.4）；按档案注册插件；
3. `FUniver.newAPI(univer)`；挂上命令守卫（§3.6.8）与变更检测（必须在创建工作簿之前挂上，才能看到加载过程中的命令）；
4. `createWorkbook(JSON.parse(snapshot))`，核对返回的 `unitId` 等于快照的 `id`；
5. 用公开的 `Event.LifeCycleChanged` 等到 Rendered（可以输入）；主线程到 Ready 后安装 `IMAGE()` 限制，等 Worker 回报；
6. Steady（Rendered 之后 3 秒，SDK 固定）之后，页面才以"是否有修改"判断打开是否干净。
- 一页一份文档、整页加载与卸载（计划书 §10.2）；`dispose()` 销毁实例、终止 Worker。
- 捕获用 `FWorkbook.save()`；捕获前不调用 Facade 的读取方法（它们可能改动模型，例如 `getDataValidations()` 建空条目）。

#### 3.6.4 公式 Worker

- 入口 `src/editor/workers/formula.worker.ts`，插件组合与官方 Worker preset 相同：Sheets（`onlyRegisterFormulaRelatedMutations: true`）、FormulaEngine、RPCWorkerThread、RemoteSheetsFormula、SheetsFilter。
- 主线程用静态的 `new Worker(new URL('./workers/formula.worker.ts', import.meta.url), { type: 'module' })` 创建实例，传给插件的 `workerURL`：传字符串时插件会建一个不带 `type: 'module'` 的经典 Worker（`rpc/src/plugin.ts:86`）。Worker 由适配层负责终止。
- 构建：Vite 的 `worker.format: 'es'`（已有），Worker 以同源脚本加载，不内联成 blob（CSP 的 `worker-src 'self'`）。
- Worker 不引用 contracts 与 zod。
- Worker 创建失败时的判定与重建在 M4；M1 里 Worker 起不来时，`IMAGE()` 的回报等不到，编辑器按加载失败处理（§3.6.7）。

#### 3.6.5 变更检测

- 规则（计划书 §7.3、档案 v1 §5.3）：监听 Facade 的 `CommandExecuted`；只看 `MUTATION`；排除带 `onlyLocal`、`fromCollab`、`fromChangeset`、`fromFormula` 标记的，以及作用于其他单元的（参数里的 `unitId` 不是本文档）；排除名单只有 `sheet.operation.clear-drawing-transformer`；不排除自动行高。
- 检测到修改时，本地修改序号加一（单调递增，页面用它判断"有没有未保存的修改"，保存时作为 `localSeq` 上传）。
- 分类函数是纯函数，单元测试覆盖每一条规则；E2E 覆盖"打开不变脏"（模板与重开的用例）、"代表性的修改变脏"（键入、加粗）、"只改视图不变脏"（选中、滚动、缩放、切换工作表、查找之后仍是已保存，离开不提示；`features.spec.ts`，审查 B2 补上）。

#### 3.6.6 公式收齐

- 显式保存前等公式"收齐"（计划书 §7.3）：没有排队的一轮；这一轮没有被 stop；逐表收齐（最近一轮带结果的每张工作表都收到带 `applyFormulaCalculationResult` 的写回；修改没有牵动公式、只收到完成通知时视为收齐）。
- 跟踪器随变更检测一起订阅 `CommandExecuted`：
  - start 开新的一轮；stop 记为被 stop；result 记下带结果的工作表；带 `functionsExecutedState` 的 notification 记为完成；带 `applyFormulaCalculationResult` 的 `sheet.mutation.set-range-values` 记为这张表已写回；
  - "排队"：命令在 `IActiveDirtyManagerService` 里有脏区转换、`shouldTrigger` 没有排除它、`getDirtyData` 非空，或者它是强制重算的触发命令（与 SDK 的触发服务同一口径）。
- 不用 `onCalculationResultApplied` 作为收齐的依据：Worker 模式下它在第一张表写回后就返回，也不等排队的下一轮（M0-P3 报告 §3.3）。
- `settleFormulas(3000)`：每 20 ms 判断一次；超过 3 秒返回 `timeout`，页面照常保存并提示"公式结果尚未保存"（M1 总设计 §6.6）。显式保存不需要捕获时机里的 1 秒防抖（M3 的自动保存才有）。
- 依赖的内部约定（mutation 的 id、执行选项、`IActiveDirtyManagerService`）都经 `internal-api/`，登记在案（§3.6.9）。

#### 3.6.7 `IMAGE()` 的限制

- 采用 `restricted`（档案 v1 §6.2、计划书 §11.3）：参数是平台资源地址才交给原执行器，否则返回 `#VALUE!`，不发请求；本期没有资源服务，实际效果是所有 `IMAGE()` 都显示 `#VALUE!`。不选整体禁用：已有的 `IMAGE()` 会变成 `#NAME?`。
- 安装方式沿用 M0 验证过的做法：生命周期到 Ready 之后，取出原执行器、注册同名的包装、清掉 `IMAGE` 的公式缓存，再核对一次生效的是包装。主线程与 Worker 各装一次。
- **Worker 回报**：Worker 装好后在同一个 Worker 上发 `{ type: 'nerve:image-policy', ok }`（`type` 用字符串，Univer 的 RPC 只认数值类型、忽略其他）。主线程收到 `ok: true` 才算编辑器就绪；20 秒收不到或 `ok: false`，编辑器按加载失败处理（`setEditable(false)`，页面提示刷新）。这个回报也顺带证明 Worker 已经启动、收到了工作簿。
- 引擎插件的 `function` 配置是另一条公开途径，但 M0 没有验证，本期不采用。

#### 3.6.8 M5 之前的入口与菜单配置

- 菜单配置（按菜单项 id 隐藏，编辑模式一份）：
  - 档案 v1 §5.1 的保护类与不支持的功能（工作表背景图片）；
  - 插入图片（`sheet.menu.image` 及两个子项）、超链接（工具栏与右键两种 id）、保存单元格图片。
- **命令守卫**（Facade 的 `BeforeCommandExecute`，取消即不执行）：插入浮动与单元格图片（粘贴图片文件也走这两条）、底层的插入图片命令、打开超链接编辑与写入超链接的命令。隐藏菜单不会停用命令与快捷键（例如超链接的 Ctrl/Cmd+K），所以两者都要有。
- 清单写在 `profile/entry-guards.ts`，逐项登记出处；E2E 覆盖菜单里没有这些入口、Ctrl/Cmd+K 没有反应、粘贴图片文件不产生图片。
- 原因：M1 不替换图片服务，SDK 默认把插入与粘贴的图片存成 data URL（M0-P4 报告 §2.2），M3、M5 的服务端校验会拒收这类快照；计划书 §4.1"编辑器能力不足时，不显示用不了的按钮"。
- 不属于入口、M1 保留 SDK 行为的链接来源（审查 B3）：
  - 键入网址时，SDK 自动把它识别为超链接（`sheets-hyper-link` 的 `AFTER_CELL_EDIT` 写入拦截器，不经添加链接的命令，守卫拦不到）：单元格写成富文本，链接地址是键入的原文（没有协议时补 `https://`），不是规范写法；
  - 粘贴带来的链接（粘贴清洗在 M5，M1 总设计 §6.6）；
  - 点击链接时 SDK 只放行 http、https 与 mailto（`isSafeUrl`），在新标签页打开；M1 的文档只有本人能访问。M3 的保存校验要求链接地址等于规范写法（计划书 §11.2），实现时必须一并处理自动识别这条路径（DEF-021）；E2E 锁定当前的行为。
- 超链接的界面插件启动时按 `location.hash` 导航：编辑器页的地址不用 hash 做别的用途。

#### 3.6.9 身份与内部 API

- **身份**（ADR-009）：用"全部允许"的 `IAuthzIoService` 替换本地授权服务，不调用 `setCurrentUser`：
  - `allowed` 对每个动作返回允许；`batchAllowed` 按请求的形状返回全部允许；`list` 一类返回空；`create`（创建保护规则）拒绝，界面入口也已隐藏；
  - 本地授权服务不再构造，它在构造时注册的资源 `SHEET_AuthzIoMockService_PLUGIN` 随之消失：快照不再有这一项，加载含这一项的快照时它被忽略，下一次保存时消失；
  - 决定：修订档案 v1 的资源白名单，去掉这一项（档案只描述真实存在的数据）；服务端在 M3 的校验按新白名单处理。v0.1 没有存量文档，不涉及迁移。
  - SDK 的当前用户保持匿名（`userID: ''`）：在 `sheet@1` 的范围内只有已隐藏的权限面板读它。E2E（`features.spec.ts`）经界面操作增删工作表、排序与筛选、条件格式与数据验证、批注与查找替换，按服务器上的快照核对结果，都照常（审查 B2 补上；编辑由其他用例覆盖）。
- **内部 API**（ADR-010）：
  - 只在 `src/editor/internal-api/` 引用；登记表 `internal-api/registry.ts` 逐项写明用途、M0 证据与回归用例，单元测试核对"导出的每一项都已登记"；
  - lint：受限符号清单（按包与导入名，例如 `@univerjs/engine-formula` 的 `IActiveDirtyManagerService`、`IFunctionService`、`BaseFunction`）与 `__getInjector` 的调用，在 `internal-api/` 之外一律报错，自测补样例。取注入器的两个名字（`__getInjector` 与私有字段 `_injector`）的点号访问、解构，以及这两个名字的字符串与不带插值的模板字符串（方括号访问、字符串的键、`Reflect.get`）都拦下；类型里的 `import('@univerjs/…')`、三斜杠引用、`import x = require()`、`import.meta.glob` 与带查询串或片段的 `@univerjs/*` 包名都报错；依赖一律按包名引用，写成 `node_modules` 里的路径（绕得过按包名的限制）同样报错；包名一律小写，写成 `@UniverJS/…` 时按包名的限制认不出、不区分大小写的文件系统上却照常构建（审查 B4，复验 RB4、SB7、TB5）。lint 看不出来、由审查保证的写法列在 ADR-010；
  - 本期的清单：取服务的 `Univer.__getInjector()`；公式收齐的 mutation id、执行选项与 `IActiveDirtyManagerService`；`IMAGE()` 限制的 `IFunctionService`、`BaseFunction`、`ErrorValueObject`、`ErrorType` 与 Worker 里的生命周期服务；身份替换依赖的 `IAuthzIoService` 接口约定。

### 3.7 编辑器页（`apps/web/src/features/sheet-editor/`）

#### 3.7.1 载入

1. 确认会话（`requestSession()`，拿到 CSRF 令牌）；未登录整页转到登录页，带上原地址；
2. 并行读取元数据与内容；`NOT_FOUND` 显示与平台 404 相同的"内容不存在，或者你没有访问权限"（别人的与不存在的相同，US-M1-08）；
3. 核对档案与格式版本（本期只有 `sheet@1` 与格式 1，其他值按"客户端不认识的格式"显示错误，不进入编辑）；
4. 创建编辑器；记下内容的修订号（ETag）作为保存的基准；
5. 页面的状态写在容器的 `data-editor-state` 上（loading、ready、steady、failed），E2E 按它等待，不用固定时长。

#### 3.7.2 保存状态机

- 状态：`clean`（已保存到云端）、`dirty`（有未保存的修改）、`saving`（保存中）、`conflict`（版本冲突）、`failed`（保存失败），另有提示"公式结果尚未保存"。
- "有未保存的修改" = 当前的修改序号大于已保存的序号，或者上一次保存时公式还没收齐。只有服务端确认成功后，已保存的序号才前进到那次捕获时的序号（取较大值）：保存期间的新修改不会被标成已保存（A08）。正在编辑、还没提交的单元格不产生修改（它作用于单元格编辑器自己的文档），修改序号不计它；但页头的状态把"单元格里还没提交的输入"也算作有未保存的修改（A14：一有修改立即改为"有未保存的修改"，Codex 评审 CX6）：键入字符或退格开始编辑、编辑中的内容改动之后算，只是打开（双击、F2、点编辑栏）不算，按 Esc 放弃之后回到原来的状态，回车提交之后等这次的写入再清掉（值没变时最多等 500 毫秒，独立复验 S1）。离开提示另外按"单元格编辑器开着"判断（§3.7.3）。
- **一次保存**（按钮或 Ctrl/Cmd+S；同一时间只有一个保存在途，保存中再按忽略，这时即使有确认会话在途，页头也仍是"保存中…"，复验 TB9）：
  1. 单元格正在编辑：先提交（等同回车），等这次的写入完成（跨工作表的提交先切表再写入，第二轮复验）；提交不了，中止保存并提示"请先完成单元格的编辑"；
  2. 等公式收齐，最多 3 秒；超时照常保存，保存成功后提示"公式结果尚未保存，请稍后再保存一次"；
  3. 捕获；序列化后超过 5 MiB 直接提示"表格超过容量上限（5 MiB），无法保存"，不上传；
  4. gzip（`CompressionStream`，主线程；5 MiB 时阻塞接近 100 ms，放进 Worker 是 M4 发件箱的设计）；
  5. `PUT`，带基准修订号、新的 `requestId`、本页的 `clientInstanceId`、捕获时的修改序号；
  6. 成功：基准修订号换成新的修订号，已保存的序号前进；
  7. 冲突：是"自己追自己"就换基准、换 `requestId` 立即重发一次；否则进入 `conflict`；
  8. 网络错误或 5xx：进入 `failed`，保留这次请求；内容没有变化时重试原样再发这个请求（`requestId`、序号与快照都不变，服务端记下的来源是第一次的序号），成功后按这次捕获的序号确认；某次重发被明确拒绝（例如 401）只说明那一次没有提交，更早那次结果未知的记录留着（Codex 评审 CX2）；
  9. 401：不整页跳转（本页的修改还在），进入 `failed`，向服务端确认会话：没有人登录就暂停保存、提示在新标签页中登录，本人登录回来之后恢复（§3.7.3，审查 B1）。不据此直接暂停：回包可能来自本人在别处重新登录之前发出的那次保存（复验 RB7）；
  10. 413、422：进入 `failed`，显示对应的说明；
  11. 提交编辑、等公式收齐、捕获或压缩时出了意外的错误（SDK 的缺陷等）：进入 `failed`（"出了点问题"），错误交给浏览器的错误报告；不会悄悄回到"有未保存的修改"（审查 B5）。压缩是上传之前本地的一步，出错不算"结果未知"的请求，下一次保存换新的 `requestId`（复验 RB8）。
- 没有修改时也可以保存（显式保存按用户的意愿执行；修订号照常加一，内容相同时不递增在 M3）。
- **版本冲突**：保留本页内容，禁止继续保存，提示"别处保存了更新的版本。本页的修改没有保存；需要的话先复制出来，再重新加载查看最新版本"，提供"重新加载"按钮。另存为副本与恢复规则在 M4。
- 状态机是纯逻辑（输入：用户操作、编辑器的事件、接口的结果），用假的编辑器与假的接口做单元测试，覆盖上面每一条。

#### 3.7.3 界面

- 页头：返回"我的空间"（整页跳转）、标题、保存状态（`role="status"`，读屏软件会读出变化）、保存按钮（进行中用 `aria-disabled`）；其余是编辑器。
- 快捷键：在捕获阶段监听 Ctrl/Cmd+S（Univer 没有绑定它），阻止浏览器的"另存网页"；按真实平台判断 Ctrl 或 Cmd。
- 离开提示：有未保存的修改（含正在编辑的单元格、冲突之后本页的内容）时，`beforeunload` 让浏览器弹出提示。不把关页时的异步请求当作保存（计划书 §7.8）。
- 样式：编辑器页不加载 Tailwind 的基础重置（preflight），只用主题变量与工具类，免得影响 Univer 的界面（M1 总设计 §7 的风险）；Univer 的样式按档案导入。
- 会话（审查 B1）：载入时未登录整页转到登录页（还没有内容可丢）。载入之后本页可能有未保存的修改，一律不整页跳转、不自动重新加载：
  - 登录已过期或在别处退出（保存得到 401，或者别的标签页退出之后向服务端确认）：暂停保存，提示"本页的修改还在"，给出"在新标签页中登录"的链接；本人在别处重新登录（BroadcastChannel 的消息）之后，向服务端确认是同一个人，换上新的 CSRF 令牌，恢复保存；
  - 别的标签页登录了另一个人：本页不能再保存（新会话的令牌不交给这个页面），提示原因；原来的人登录回来之后恢复；
  - 暂停或停止保存时、上一次确认会话失败时又按了保存：先向服务端确认一次（消息可能没有送到，令牌可能没有换成），是本人就换上新的令牌照常保存，否则不发请求；确认失败（例如断网）时在会话的提示里说明原因。保存得到令牌失效之后，确认没有成功就不再发保存（带着已知失效的令牌必然又是令牌失效，只会白传一遍快照，复验 UB1）；令牌被标为失效之前就已开始的那轮确认，成功了也不算换好（它的回包可能早于令牌的更换，复验 VB1）；
  - 确认会话进行中又按了保存（别的标签页的消息、401、CSRF 失效触发的确认）：等确认结束，按结果决定，这次保存不会被丢掉，也不会带着旧的令牌再发一次（复验 RB1）；
  - 保存得到 `CSRF_TOKEN_INVALID`：向服务端确认会话，提示"请求已失效，请再保存一次"，不让用户刷新（刷新会丢掉修改）；
  - 会话不是本人时，不再重复"登录已过期""请求已失效"这类失败的说明；从未登录或换了人回到本人时清掉它们（复验 RB2）。一直是本人时保留，提示"请求已失效，请再保存一次"（令牌已经换好；迟到的未登录回包同样处理，复验 SB1）；确认会话失败时令牌没有换成，改为说明确认失败的原因（复验 TB1）；
  - 与保存有关的确认会话进行中（保存得到未登录或令牌失效触发的、按了保存要先确认的）：页头的状态说"正在确认登录状态…"，按钮不可用（复验 SB5）；这类失败的说明等确认有了结果再显示，不先说"请再保存一次"（读屏软件在提示出现时就会读出，复验 TB1）；等确认期间页面卸载了，不再捕获与上传；
  - 另一个人也退出之后按没有人登录处理，给出登录的入口；保存得到未登录、确认时断网，同样按没有人登录显示（不清令牌，复验 SB4）；编辑器还在创建时换了人，保存的状态机一建好就停住；载入时还不知道本页的用户就收到的消息，知道之后补确认一次（复验 RB3、RB7）；
  - 版本冲突之后不再显示会话的提示（本页已经不能保存）；会话不是本人时不显示"公式结果尚未保存，请稍后再保存一次"（复验 SB9）。冲突之后换了人：冲突的说明里另说明重新加载会以那个账户打开，要查看最新版本先换回原来的账户（复验 TB8）。

#### 3.7.4 列表页的新建与打开

- "新建表格"按钮：生成 `requestId` → `POST /api/documents` → 整页打开 `/documents/<id>`（留下历史记录，后退回到列表）。结果未知（网络错误、5xx、回包与契约不一致：服务端可能已经建好）之后再点沿用同一个 `requestId`（同一次新建只生成一份）；只有确定失败（4xx）之后再点才换一个（审查 B6）。进行中与建好之后、页面离开之前都用 `aria-disabled`，重复点击不再请求。
- 列表的条目改为链接，整页打开编辑器页。
- 登录页登录之后要回到的地址是编辑器页时整页打开（`from` 指向另一个入口，不能在平台页面的路由里切换）；已登录时打开这样的登录页同样整页打开，只打开一次。整页跳转经 `PageLocationContext`（平台页面的运行时提供，测试换成假实现）。

#### 3.7.5 实现的结构（S3）

- `features/sheet-editor/`：
  - `save-coordinator.ts`：保存的状态机（纯逻辑）。结果未知的保存（网络错误、5xx、回包与契约不一致）都记下来，冲突的来源是其中任何一次时按"自己追自己"处理（不只是最近的一次：两次都没收到回包、其实是较早的一次提交了，同样认得出）；只自动重发一次。记下的只是序号与公式是否收齐，不留快照本身，断网期间多次保存时内存不随之增长（审查 B9）。内容（捕获的文本）与基准都没变的重试沿用上一次的 `requestId`；确定没有提交（4xx）之后换新的。
  - `editor-page.ts`：载入与会话（React 之外创建编辑器，一页一份文档，不随组件反复创建）；`editor-chrome.tsx`：页头与提示，只订阅状态；`page-guards.ts`：快捷键与离开提示；`start.tsx`：组装真实的依赖。
  - 编辑器的容器是 `editor.html` 里静态的 `#sheet-editor`，页面的状态写在它的 `data-editor-state` 上；页头挂在 `#editor-chrome`。
- 平台与编辑器页共用的部分放进 `shared/`：登录页的地址（`shared/lib/login-path.ts`，原在 `features/auth`）、确认会话的请求（`shared/api/session.ts`）、整页跳转（`shared/lib/page-location.ts`）、主题变量（`shared/ui/theme.css`）。请求层加上 `apiFetch`（不是 JSON 的请求与响应，例如快照）与错误响应的 `details`。
- 编辑器页的地址规则（`DOCUMENT_PAGE_PATTERN`）放在 contracts：托管、Vite 的开发改写与平台页面的跳转用同一个。

### 3.8 托管、入口与路由

- 编辑器页的地址是 `/documents/<文档 id>`（最后一段是 UUID，不带点）。`ENTRY_PAGES` 把它映射到 `editor.html`；其他地址照旧回退到平台页面。不是 UUID 的 `/documents/...` 由平台页面显示 404。
- 构建：生产构建与测试构建都加上 `editor.html` 入口（`entries/editor/main.tsx`：先 `zod-jitless`，再样式，再 `mount.tsx`）。
- 开发：Vite 开发服务器加一条只在开发时生效的改写，把 `/documents/<id>` 交给 `editor.html`。
- 两个入口共用 contracts：打包器可能调整模块的执行顺序（ADR-008）。先用 E2E 的违规收集确认两个页面都没有违规，再决定是否开启 `strictExecutionOrder`。
  - 实测（S3）：两个入口共用的块里，关掉 JIT 的调用排在 contracts 的结构之前；平台页面的全部 E2E 与编辑器页都没有违规。不开启 `strictExecutionOrder`。
  - contracts 声明 `"sideEffects": false`：否则经 `index.ts` 汇总导出时，只有编辑器用到的结构（保存、冲突的详情）也进了共用的块，平台页面跟着下载。

### 3.9 构建、包体积与门禁

- **依赖**：`@univerjs/*` 按 `sheet@1` 用到的包进目录，一律 1.0.1（`@univerjs/icons` 按 SDK 的依赖为 1.43.0）。原定 1.0.0：它没有来源证明，被 `trustPolicy: no-downgrade` 拒装；1.0.1 是可信发布，产物与 1.0.0 相同（S2 核对）。1.0.1 的发布时间还在 `minimumReleaseAge` 的冷却期内，目录里临时豁免，期满（2026-09-27T08:07Z）之后、P4 合并之前去掉（已去掉，去掉之后安装照常通过供应链策略的核对）；没有 Pro；`protobufjs` 的安装脚本不执行（`allowBuilds`，写明原因）；许可核对，缺许可正文的包补齐。
- **`budgets`**：
  - 编辑器页入口的首屏 JS（gzip）：按生产档案实测后定，比实测多约 15%–20%（M0 的候选档案实测约 1.93–1.96 MiB）；
  - 公式 Worker 另列一项预算：Worker 在插件启动时就下载，事实上属于首屏的传输量，而现有口径不计它。门禁按构建清单找到入口引用的 Worker 产物，统计它与它静态引用的块；
  - 平台页面的预算不变，并核对它没有因为共用代码而变大。
  - 实测（S3）：编辑器页 1991 KiB（预算 2350 KiB）；公式 Worker 673 KiB（预算 800 KiB，Worker 打成一个文件）；平台页面 147.7 → 约 151 KiB（新建表格、请求层与共用的界面文字，预算 180 KiB 不变）；
  - 没有预算的 Worker：Vite 把 Worker 的产物列在创建它的块的 `assets` 里（`new Worker(new URL(…))` 与 `?worker` 两种写法都是）；按构建清单收集每个入口能到达的块（首屏与动态加载）的这些脚本，没有登记预算的报违规（审查 A 路的建议 B2，复验 RA5：原来只认 `new URL` 的写法、只查首屏块）；构建清单里没有预算的入口同样报违规。产物里的每个脚本都要有归属（构建清单里的块、块创建的 Worker 或 Worker 能加载到的块），没有归属的报违规，例如 Worker 里再创建的 Worker（构建清单不描述 Worker 的包，复验 SA5）；公式 Worker 的名字按"名字加 8 位哈希"认，名字以它开头的另一个 Worker 不算（复验 SA9）；同一个预算匹配到两个以上同名的产物时报违规，不只量其中一个（复验 TA8）。构建清单里的块引用了清单里没有的块时报违规：展开时只能跳过它，它的体积就不计入预算（M1 对抗评审之后补，Codex 列为候选）。
- **`artifacts`**：
  - Univer 的产物里有大量文档链接（M0-P1 报告 §2.3：support.microsoft.com 509 处等）。允许清单支持按地址前缀放行，逐项写明来源与原因；平台页面的地址照旧按具体地址；
  - 已登记的动态代码按实际产物核对：lodash 的全局对象探测（`globalThisProbeMax: 3`）、zod 的两处；新报出的逐个核对来源；
  - DEF-016：按语法树取字符串的实际值再识别地址，补上协议由插值给出、转义的斜杠、协议相对的地址与不带域名后缀的主机。
  - 实测（S3）：Univer 的产物里没有新的动态代码；全局对象探测 2 处（编辑器页与公式 Worker 的 lodash 各一处），上限降为 2。地址 17 类：公式说明的两个前缀（微软约 500 条、Google 17 条）按前缀登记，其余按具体地址（依赖注入的错误说明、协同编辑的类型标识、公式参数的示例、剪贴板 HTML 的命名空间、`isLegalUrl` 里的 `http://localhost:5173` 等）。
  - 前缀的登记只对编辑器页适用：编辑器入口（`editor.html`）能加载到的全部产物（块、样式、它创建的 Worker 与 Worker 加载的块），减去其他入口（平台页面与构建清单里别的入口，含新增或改了名的）能加载到的全部产物；其余产物（public 目录的文件、清单里没有的入口、构建清单缺失时的全部文件）一律按具体地址（审查 A 路的建议 B1，复验 RA8、SA6）。
  - JS 文件的地址改为按语法树识别：字符串的值（已处理转义）、模板字符串（插值写成占位）、正则的原文与注释；其他文本文件照旧按写法匹配。
  - 值按浏览器的解析规则看一遍（审查 A4，复验 RA2–RA4、SA1–SA4、TA1–TA7，`tools/src/gates/addresses.ts`）：
    - 值从哪里来：JS 的字符串与模板字符串（压缩器把普通字符串也写成模板字符串，所以两者同一个规则）；
      - HTML 用 parse5 按 HTML 规范解析（字符引用按完整的表解码，`html-values.ts`）。属性取自分词器给出的每个开始标签，树构建丢掉的也算：parse5 仍按旧的规则解析 `<select>`，丢掉里面的 `<img>`、`<div>`，浏览器已改用新的规则保留它们（复验 TA2）。原始文本一类的元素（style、script、textarea 等）与 svg、math 的开始标签被 parse5 丢掉时，浏览器可能把之后的内容按另一种状态分词，门禁无法确定会请求什么，直接报违规（`artifacts/markup`）。截取开始标签用的是 parse5 标着 `@internal` 的 `Parser`：版本精确锁定，依赖的行为由单测锁住；
      - 每个属性的值与按空白、逗号、分号切开的各段（srcset、ping、SMIL 的 values，复验 TA6）、属性里的样式（style 与 SVG 的呈现属性）、meta refresh 的地址（按规范的声明式刷新步骤）、iframe srcdoc 里的 HTML；style 元素取直接的文字子节点连起来（SVG 的 `<style>` 可以被注释或子元素拆成几段，浏览器连起来当样式，复验 TA6）；有 noscript 时另按脚本关着解析一遍，只补上第一遍没有的（sandbox 的 iframe 里 noscript 按元素解析，复验 UA3）；
      - SVG 文件按 XML 解析（saxes，`svg-values.ts`）：作为文档加载时浏览器用的是 XML 解析器，DTD 里定义的实体会展开、`xml-stylesheet` 会加载样式表，`<svg>` 里的 `<img>` 不会像 HTML 那样跳出外来内容。只支持不带 DTD、不带处理指令、格式正确、编码是 UTF-8 的 SVG（发 SVG 时不带 charset，浏览器按 XML 声明的编码解码），其余直接报违规（复验 TA6、UA5）；XHTML 的 iframe 的 srcdoc 另按 HTML 解析（复验 UA1）；
      - 样式按 CSS 的分词规则取出字符串与 url 的值（输入的预处理把 NUL 换成 U+FFFD，转义、续行、注释都按规范处理，反斜杠在输入结尾也是合法的转义，`css-values.ts`，复验 TA3）；
      - JSON 按顺序线性地取出原文里的每个字符串字面量（键与值，重复的键也算）与嵌在里面的 HTML、样式（`json-values.ts`，复验 TA7、TA9），开头的 BOM 不算（复验 UA4）；
      - 不解开的：JS 字符串里嵌的样式与 HTML、`data:` 地址里的文档（DEF-022，由 CSP 拦下）；
    - 怎么判断：去掉开头的空白与控制字符、中间的制表符与换行，以 `http(s):`、`ws(s):`、两个斜杠（含反斜杠）或 `://` 开头的，用 WHATWG URL 按站点解析，得到跨源的地址就报出（报出的是规范写法，例如 punycode）。插值开头、后面紧跟两个斜杠的，插值当作协议；协议或端口是插值的，主机照样是固定的；主机里有插值的按运行时拼出计数。值的开头按写法认出了地址、而按浏览器的规则解析出的规范写法不同时另外报出，例如允许的地址后面接着制表符与另一个域名、制表符与 `../`、空白与别的路径（复验 TA5）；
    - 允许清单两边都按浏览器解析出的规范写法比较（点段化简，含 `%2e%2e`）：前缀后面的 `../` 跳不出去（复验 TA5）；句末只去掉跟在普通字符后面的一个句点，结尾的 `..`、`%2e.` 照样化简（复验 UA2、VA1）；
    - 只排除两类不是地址的值："//g" 这样的正则标志，与解析出的主机里既没有字母或数字、又不是 IPv6 的（React Router 里的一段正则被解析成主机 `*$`；`[::]` 照样报出，复验 TA4）；单标签的主机、以连字符开头的主机同样报出；
    - 同一处（一个属性、一段样式、一个 JSON 字符串）里规范写法相同的地址只计一次，规范写法不同的都核对允许清单（原来按来源去重，允许的地址排在前面时同一来源的其他地址被跳过，复验 TA1）；
    - 整个文件另按写法匹配一遍兜底（取出值的时候切错或漏掉的由它补上），落在报出过同一个地址的那一处里的不重复计数（按地址把范围排好、二分查找，大文件不再是平方级，复验 TA7）；字符引用或转义让写法匹配多出来的（例如接在地址后面的 `&gt`）照样报出，宁可多报。门禁的自测另有一条经 Vite 真实构建、压缩之后再扫描的用例。
  - 许可：6 个包的发布包里没有许可文件（`@univerjs/protocol`、`franc-min`、`ot-json1`、`ot-text-unicode`、`react-remove-scroll-bar`、`unicount`），正文补进 `apps/web/third-party-licenses/`，出处写在那里的 README。
- **`deps`**：单例清单已含 `@univerjs/*`、`@wendellhu/redi`、`rxjs`、react；Univer 的版本一致性按 `UNIVER_POLICY`：pnpm 目录里的版本与安装的实例都要等于它（复验 RA6 补上目录的核对）。文档记录的 SDK 版本（contracts 的 `UNIVER_SDK_VERSION`）由后端的单元测试与目录里的核心包核对（按 YAML 解析 `pnpm-workspace.yaml`，复验 TA10）；快照里的 `appVersion` 不能代表版本（Univer 载入快照时沿用其中的值）。

- 按角色与名称定位，不用设备预设，不用固定时长的等待；键入经真实的键盘事件。
- 从接口取回快照核对内容时，E2E 用会话 Cookie 请求 `GET …/content`。
- 实现（S4）：
  - 单元格画在画布上，没有可访问的元素：选中单元格按模板的默认行高、列宽与表头大小点击画布；加工作表的按钮没有可访问的名称，按 Univer 的组件标记（`data-u-comp`）定位。页头、按钮、菜单与提示照常按角色与名称定位（`tests/e2e/support/sheet.ts`）；
  - "重开看到的内容一致"：重开、不做修改立即再保存一次，服务器上的值、公式与格式与重开之前保存的相同；
  - 另加两条：断网时保存（保存失败与原因，恢复之后再保存成功）；保存已经提交、回包丢了（请求经拦截照常送达，浏览器收到的是断开）之后再保存，认出是本页自己的保存、不报冲突；
  - 实测发现：WebKit 读取 Blob 要经它的网络进程，离线时读不出来（上传的正文原来经 Blob 压缩，断网时报成"出了点问题"而不是网络错误），拦截请求时也拿不到 Blob 的请求体。压缩改为全程在内存的字节上做，请求体是字节数组；
  - 模板的更新脚本：`pnpm --filter @nerve-office/e2e run update:sheet-template`（`playwright.template.config.ts`，只跑 `tools/`，不在常规的 E2E 里）；本期执行一次，生成的模板与 S1 放进 contracts 的逐字节相同；
  - 本机三个浏览器 53 条用例全绿，编辑器的用例重复三遍没有不稳定。
- 审查之后补上与改正（S5）：
  - 复验之后再补：单元格还在编辑时按保存、依赖它的公式的缓存值（公式收齐的"排队"判断，确定能测出来的用例，复验 RB5）；确认会话还没结束时按保存（复验 RB1）；键入邮箱、粘贴纯文本的网址（DEF-021）；
  - "没有发出请求"只能等一段时间再下结论：冲突之后按快捷键的用例等 1 秒（正常的保存从按键到发出请求不到 100 ms），是"不用固定时长的等待"的例外；
  - 补上：常用的表格功能与"只改视图不变脏"（`features.spec.ts`）、登录状态变化时的编辑器页（`session.spec.ts`）、计算进行中再改一处（第一处让 300 个较重的 `SUMPRODUCT` 重算，第二处落在这一轮里、只让一个很轻的公式重算：按保存之后等的是第一轮剩下的部分加上很轻的第二轮。原来两处都让 300 个公式重算，CI 的 WebKit 上两轮合计超过公式收齐的 3 秒上限，用例偶尔失败）、键入网址的自动识别；
  - 改正可能假通过的断言（审查 B7）：快捷键核对按键事件的默认行为确实被阻止（原来的"没有下载"在无头浏览器里不可能失败）；重开之后再保存核对修订号加一；冲突之后点"重新加载"不再另外打开页面，核对离开提示确实出现过；冲突之后按快捷键核对没有发出保存的请求；
  - 常用功能的界面入口按角色与名称定位；筛选的按钮没有可访问的名称，按它的命令标记（`data-u-command`）定位；选中区域时查找只在区域里进行，查找前先选中一格。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 身份替换之后，某个插件依赖本地授权服务或非空的当前用户 | S2 开头在真实骨架上确认：打开、编辑、增删工作表、筛选、排序、条件格式、数据验证、备注、查找替换都照常；不通过就退回"保留同名的 hook、恒为空"（ADR-009 的备选），并记录原因。E2E 的回归见 §3.10（审查 B2 补上） |
| 模板替换 `unitId` 后不收敛，或资源数组的顺序跨浏览器不同 | S2 的探针先在三个浏览器上验证；S4 的 E2E 回归。顺序不同时，比较时按资源名排序（服务端的哈希在 M3 也按此口径） |
| 保存前提交单元格编辑的行为（选区移动、数据验证拒绝、编辑栏里的编辑） | S2 的探针逐项实测；提交失败时中止保存并提示；E2E 覆盖编辑中按保存 |
| 公式收齐依赖的内部约定在 1.0.1 的生产构建里与 M0 不同 | S2 用 M0 的场景（跨表、计算进行中再改一次）回归；S4 的 E2E 核对保存的缓存值 |
| 编辑器页的首屏体积与加载时间 | 按生产档案实测后定预算；Facade 的副作用导入只保留用到的；M7 再压测 |
| Univer 的样式与 Tailwind 冲突 | 编辑器页不加载 preflight；E2E 检查页头与编辑器的关键界面 |
| Worker 在 WebKit 上第一次计算较慢（M0 见过 1.77 秒） | 3 秒的收齐上限照常适用；E2E 的等待按状态，不按时长 |

**S2 探针的结论**（Chromium、Chrome、WebKit；定稿的 CSP；生产档案与生产代码；Univer 1.0.1）：

1. **身份替换**：通过。全部允许的 `IAuthzIoService` 替换之后，打开、键入、增删工作表、筛选、排序、条件格式、数据验证、备注、查找替换，与保留本地授权服务时逐项相同；40 个权限点都允许；资源与快照里都没有 `SHEET_AuthzIoMockService_PLUGIN`。查找替换要到 Steady（渲染完成后约 3 秒）才注册，之前 Ctrl/Cmd+F 没有反应，与身份无关。
2. **模板收敛**：通过。手写的空白工作簿第二次保存就逐字节收敛（第一次补齐工作表的默认字段、10 项资源与 `appVersion`；第二次只有 `SHEET_DEFINED_NAME_PLUGIN` 由 `""` 变为 `"{}"`）；换成随机的 `unitId` 之后打开、再保存仍与实例化的文本逐字节相同；三个浏览器的模板逐字节相同，资源的顺序相同；打开之后本地修改序号为 0。收敛的模板已放进 contracts（S1）。
3. **提交单元格编辑**：与回车相同，内容提交、选区下移；编辑栏里的编辑同样算正在编辑。数据验证拒绝时与原来的假设不同：SDK 先写入、校验不通过就回滚并弹出它自己的提示，提交返回时回滚已经完成，所以"提交"算成功，保存的是回滚之后的内容。捕获阶段收得到 Ctrl/Cmd+S，阻止默认行为不会结束编辑。
4. **Worker 回报 `IMAGE()` 的安装结果**：通过，约 0.5 秒；之后公式由 Worker 算出正确结果；外链的 `IMAGE()` 显示 `#VALUE!`，没有违规与外部请求；Worker 脚本加载不了时 50–120 ms 内以 `worker-failed` 失败。
5. **入口守卫**：插入菜单与右键菜单没有图片、链接与保护；Ctrl/Cmd+K 没有反应；粘贴图片文件不产生图片。发现一个 SDK 的缺陷：被 `BeforeCommandExecute` 取消的命令留在 SDK 的执行栈里，之后在命令之外执行的 mutation 带上它的 `trigger`，没有发现功能上的影响。
6. **公式收齐**：单表依赖、跨表引用、计算进行中再改一次，收齐之后的值都与按定义算出的一致；录制的命令序列进了单元测试。计算进行中再改一次（600 个 `SUMPRODUCT`）Chromium 与 Chrome 约 1.7 秒、WebKit 约 1.0 秒，在 3 秒的上限之内。
