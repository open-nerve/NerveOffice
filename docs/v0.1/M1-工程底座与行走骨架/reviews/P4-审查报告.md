初审的共同点：
- **服务端与浏览器对同一份数据的理解不同**：Node 的 zlib 解开全部 gzip 成员、遇到 0x00 就停，浏览器只解第一个成员（A1）；产物扫描按写法匹配地址，浏览器按 WHATWG URL 解析（A4）。修法都是改用与浏览器同一个规范的实现（`DecompressionStream`、`URL.parse`）。
- **测试或设计声称的覆盖与实际不符**：设计与内部 API 登记表写着有 E2E 回归，实际没有（B2）；几处 E2E 的断言不可能失败（B7）；gzip 的单元测试只测了两个非空成员（A1）。都补上了能复现原问题的用例。
- **会话与失败路径的恢复**：会话变化之后同一个人回来也保存不了（B1）；保存流程里的意外错误被吞掉（B5）；创建编辑器的前几步失败时泄漏 Worker（B8）。

## 结论与遗留

**结论**：修复后通过。阻断项与重要项都已解决，并经独立复验确认；一般与建议项已修复，或写明原因不改（VA3），或登记为延期（DEF-022）。合并前从干净状态执行 `pnpm clean && pnpm verify`，全部通过：lint、类型检查、静态门禁、单元与集成测试 1749 项（覆盖率达标）、构建、产物门禁（deps、licenses、artifacts、budgets，真实产物 0 违规）、E2E（本机 Chromium、Chrome、WebKit，201 项）。CI 另跑 Edge，合并推送后确认（DEF-001 的关闭记在 P5）。

**延期**（已登记）：
- DEF-017：读取内容的 `If-None-Match` 与 304（M3）；
- DEF-018：保存时服务端解析整份快照的内存（M7）；
- DEF-019：超链接白名单不依赖 SDK 的 `isLegalUrl`（M5）；
- DEF-020：被取消的命令留在 SDK 的执行栈里（M3）；
- DEF-021：键入或粘贴网址时 SDK 自动写入超链接，M3 的保存校验要处理这条路径（M3）；
- DEF-022：产物扫描不解开 JS 字符串里嵌的样式与 HTML、`data:` 地址里的文档，由 CSP 拦下（M7）。

**已知的限制**（写进了设计或交接单）：
- 门禁截取 HTML 的开始标签用的是 parse5 标着 `@internal` 的 `Parser`：版本精确锁定，行为由单测锁住，升级时核对。parse5 仍按旧的规则解析 `<select>`：原始文本一类的元素与 svg、math 的开始标签被它丢掉时，门禁直接报违规，不去猜浏览器怎样分词。
- 门禁偏保守、会多报的写法（复验者认可）：noscript 里的元素（脚本开着时浏览器不加载）、`image()` 与 `src()`、不闭合的字符串、写在规则之后的 `@import`、字符引用或转义让写法匹配多出来的地址、srcdoc 里的样式重复计数；带标准 DOCTYPE 的 SVG 文件报违规（去掉 DOCTYPE 即可）。
- parse5 在 HTML 里每层都查一遍打开的元素，几万层的 `<div>` 嵌套是平方级的；一个标签有 10 万个属性时也很慢。都是 parse5 自身的特性，真实产物达不到。
- 编辑器页"令牌已知失效时一定先确认"这一条眼下到不了，没有测试能锁住（见 VB1）。
