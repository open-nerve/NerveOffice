# M1-P5 容器、部署与收尾：架构设计与实施规划

> 状态：进行中｜日期：2026-09-28｜基于代码版本：`c8ae20e`

## 1. 目标与范围

对应 M1 总设计 §5 的 P5 一行：能部署到测试环境；M1 收尾。本 Phase 交付：

| 故事与门槛 | 本 Phase 交付的部分 |
|---|---|
| US-M1-10 用容器把应用部署到测试环境；API 重启后已确认的数据不丢 | 全部：按部署说明构建镜像、执行迁移、启动，就绪探针通过；强制结束 API 进程再启动后，已确认保存的内容完整；保存进行中被打断时，要么完整提交、要么没有提交，重试不会重复写入 |
| A09 进程与浏览器异常（API 重启部分） | 同 US-M1-10；浏览器异常部分在 M4 |
| M1 退出条件（M1 总设计 §8） | 能构建容器并部署到测试环境，对部署后的环境跑 E2E 通过；DEF-001 关闭；架构总览 v1；延期项复核；打 tag `v0.1-m1` |

- **范围内**：
  1. 镜像：多阶段 Dockerfile（非 root 用户、只读文件系统、健康检查），服务端依赖的第三方许可清单随镜像生成（P2 交接单）；
  2. 数据库角色：迁移用表的所有者，应用用只有必要权限的角色（审查 A21，ADR-005）；应用启动时自检；
  3. 测试环境编排：应用 + PostgreSQL 18 + Caddy（HTTPS），迁移作为单独的一次性任务，初始化管理员的命令；
  4. 反向代理的约束落到配置里：信任代理（DEF-014），登录洪水（DEF-015），不再压缩、请求体上限、长连接、就绪探针不对外；
  5. E2E：恢复"测外部环境"的模式；对容器化的环境跑 E2E；US-M1-10 的重启用例在本机与容器两种环境里都跑；
  6. CI：构建镜像，对容器化的环境跑 E2E（规范 §9）；
  7. 镜像体积与内存占用的实测（ADR-001）；
  8. 文档：部署说明、ADR（部署形态）、架构总览 v1、M1 交接单；
  9. 上游报告：把 M0 与 M1 列出的上游问题整理成可提交的草稿，建立跟踪表。**提交到上游之前先请需求方确认**；
  10. 收尾：DEF-001 关闭（P4 合并后的 CI 已在 Edge 上跑过编辑器与 CSP 的用例），延期项复核，M1 收尾汇报，打 tag。
- **范围外**：常驻的测试或生产环境、镜像仓库与发布流水线、多架构镜像、备份与恢复、监控告警、运维手册（M7）；反向代理上的限速放在运维手册里（§3.5，登记延期）。

## 3. 设计

### 3.1 目录与改动范围

```text
.dockerignore                    构建上下文的排除清单（仓库根目录是构建上下文）
deploy/
  Dockerfile                     多阶段镜像：构建、生产依赖、运行
  README.md                      部署说明（构建、数据库角色、迁移、初始化管理员、启动、升级、反向代理的要求）
  sql/bootstrap-roles.sql        数据库角色的一次性初始化（所有者、应用）
  test/
    compose.yaml                 测试环境：db、migrate、app、caddy
    Caddyfile                    只做 TLS 与转发
    db-init/10-roles.sh          测试环境的库初始化：执行 bootstrap-roles.sql
    .env.example                 环境变量模板
apps/api                         数据库角色自检、代理未被信任时告警（DEF-014）、哈希排队的上限（DEF-015）
tools/src/deploy/                容器 E2E 的编排脚本、客户端地址的核对、服务端许可清单的生成
tests/e2e                        外部模式补全、US-M1-10 的重启用例与重启项目
.github/workflows/ci.yml         新增 container job
docs/upstream/                   上游报告的草稿与跟踪表
```

- 部署相关的脚本用 TypeScript 写在 `tools/` 里（与 verify、门禁同样由 Node 直接执行），不写 shell 脚本：错误处理、超时与日志都按仓库的约定；本机与 CI 用同一个入口（`pnpm test:e2e:container`）。
- 应用代码的改动都在已有的模块里（config、auth、database、security），不新增模块。

### 3.2 镜像（`deploy/Dockerfile`）

- **基础镜像**：`node:24.21.0-bookworm-slim`，按多架构索引的摘要锁定（M1 总设计 §2.2）。Dockerfile 不写平台：CI 构建 linux/amd64，本机构建 linux/arm64，同一份文件。
- **阶段**：
  1. `base`：基础镜像加 pnpm（`npm install --global pnpm@12.6.0`，不用 corepack，ADR-002）。pnpm 自己的安装脚本要执行：它把本平台的原生二进制放到位，否则留下的是没有 shebang 的占位文件，工作区开了 `shellEmulator`，脚本里的 pnpm 由它直接启动，会得到 Exec format error（S1 实测）。取舍：这个安装脚本以 root 身份在构建阶段执行，来源是锁定版本的 pnpm；运行镜像从基础镜像重新开始，不带 pnpm。
  2. `manifests`：只复制锁文件、工作区配置与各包的 `package.json`，依赖层只在它们变化时重建；`build` 与 `prod-deps` 都从它开始。
  3. `build`：`pnpm install --frozen-lockfile --ignore-scripts`（安装脚本在 `allowBuilds` 里都是 false，`prepare` 装钩子需要 `.git`，不执行；pnpm 的存储用构建缓存）；再复制源码，按根目录的 `build` 构建 contracts、api 与 web 的生产构建；生成服务端的第三方许可清单（§3.2.1）。
  4. `prod-deps`：`pnpm install --prod --frozen-lockfile --ignore-scripts --filter @nerve-office/api...`：只装 api 与它依赖的工作区包的生产依赖，保持 pnpm 的软链接结构。不用 `pnpm deploy`：它要打开 `injectWorkspacePackages`，会改变开发时工作区包的链接方式。
  5. `runtime`：基础镜像（不含 pnpm），删掉 npm 与 corepack（运行时用不到，减少体积与攻击面）；复制生产依赖、api 与 contracts 的构建产物与 `package.json`（`"type": "module"` 决定按 ESM 加载）、api 的迁移目录（随 `dist` 一起）、web 的生产构建（`/app/web`，不是 `dist-e2e`）、许可清单。
- **运行方式**：
  - `USER node`（镜像自带的非 root 用户）；`WORKDIR /app/apps/api`，命令行工具与文档里的写法一致：`node dist/cli/migrate.js`；
  - `ENV NERVE_WEB_ROOT=/app/web`、`NODE_ENV=production`（应用不读它，Express 的默认行为按生产）；
  - `CMD ["node", "dist/app/main.js"]`（exec 形式，信号直达 Node）；
  - `HEALTHCHECK` 用 Node 自带的 `fetch` 请求本机的 `/api/health/ready`（slim 镜像里没有 curl），端口读 `NERVE_HTTP_PORT`；间隔 10 秒（就绪失败按 error 记日志，不宜太密），启动宽限 30 秒；
  - OCI 标签：来源、版本、提交号（构建参数）、许可。
- **编排层面的加固**（§3.4）：只读的根文件系统加一个 `/tmp` 的 tmpfs；`init: true`（Node 的信号处理在监听成功之后才装上，作为 PID 1 在那之前收到 SIGTERM 不会退出）；去掉全部 capabilities，`no-new-privileges`。
- **版本一致**：`pins` 门禁补上两条：Dockerfile 的 Node 镜像标签等于 `.node-version`，全局安装的 pnpm 写明版本并等于 `packageManager`；镜像引用一律带摘要。引用的来源：Dockerfile 的 `FROM`（变量按前面 `ARG` 的默认值展开，展不开的算违规）、`COPY`/`ADD` 的 `--from` 与 `RUN --mount` 的 `from`（前面定义的阶段除外），YAML 的 `image:`、工作流的 `container:` 简写与 `uses: docker://`（审查 A5）。

#### 3.2.1 服务端的第三方许可清单

- 前端的清单由 Vite 插件在构建时生成（打进产物的包）。服务端的清单在镜像构建时生成：`tools/src/deploy/server-licenses.ts` 按 api 的生产依赖图（与 `licenses` 门禁同一个来源）逐个读取许可正文，写成 `THIRD-PARTY-LICENSES-server.md`，放进镜像的 `/app/licenses/`。
- 缺许可正文的包沿用前端的补充目录（`apps/web/third-party-licenses/`）的做法：生成时找不到正文就失败，不静默跳过。
- 单元测试覆盖：清单的格式、缺正文时报错、按包名与版本排序且去重。

### 3.3 数据库角色（审查 A21）

- **两个角色**：
  - 所有者（例如 `nerve_owner`）：数据库的所有者，执行迁移，拥有全部表；
  - 应用（例如 `nerve_app`）：只有连接、使用 schema、增删改查业务表、读取迁移记录的权限；不是超级用户，不拥有任何表，所以关不掉审计表的触发器（`ALTER TABLE … DISABLE TRIGGER` 需要所有者），也执行不了 DDL。
- **一次性初始化**（`deploy/sql/bootstrap-roles.sql`，由数据库管理员在建库时执行一次）：建两个角色与数据库，数据库的所有者是 `nerve_owner`；用默认权限（`ALTER DEFAULT PRIVILEGES FOR ROLE nerve_owner …`）让所有者以后建的对象自动授权给应用：全部 schema 的 USAGE、全部表的 SELECT、`public` 里表的 INSERT、UPDATE、DELETE、序列的 USAGE 与 SELECT。迁移不写 GRANT（角色名由部署决定），也就不需要每次迁移之后补授权。
- **迁移记录表**：drizzle 在 `drizzle` schema 里建 `__drizzle_migrations`，应用只读（就绪探针要读它）。
- **启动自检**：应用启动时查询当前角色是不是超级用户、是不是审计表的所有者；是的话记一条告警（说明只追加的保护可以被绕过，指向部署说明）。开发库与本机 E2E 用的是超级用户，照常告警，不影响启动。
- 测试环境的 compose 用这两个角色；容器 E2E 因此也验证了应用在受限权限下的全部路径（任何用到超出权限的语句都会在 E2E 里失败）。

### 3.4 测试环境编排（`deploy/test/`）

- **项目名** `nerve-office-test`，与开发库（`nerve-office-dev`、54318）分开。
- **服务**：
  1. `db`：`postgres:18.6-alpine`（与开发、CI 同一个摘要），初始化脚本 `db-init/10-roles.sh` 按环境变量里的密码执行 `bootstrap-roles.sql`；数据在命名卷里；端口只发布到本机回环（默认 `127.0.0.1:54319`），供 E2E 的测试数据与运维排查使用；
  2. `migrate`：同一个镜像，`node dist/cli/migrate.js`，用所有者的连接串；依赖 `db` 健康；执行完即退出；
  3. `app`：同一个镜像，用应用角色的连接串；依赖 `migrate` 成功结束（`service_completed_successfully`）；不发布端口，只在编排的网络里对 Caddy 可见；`read_only`、`/tmp` 的 tmpfs、`init: true`、去掉全部 capabilities；`stop_grace_period` 15 秒（大于 `NERVE_SHUTDOWN_TIMEOUT_MS` 的 8 秒）；
  4. `caddy`：`caddy:2.11.4-alpine`（按摘要）；依赖 `app` 健康；只把 443 发布到本机回环（默认 `127.0.0.1:8443`）。以 nobody 运行（审查 A7）：只读根文件系统，`/data` 与 `/config` 用归 nobody 的 tmpfs（证书每次启动由自带的 CA 重新签发），去掉全部 capabilities 只留 `NET_BIND_SERVICE`（镜像里的 caddy 带着这项文件 capability，不在容许范围里时连执行都被拒绝）。
- **初始化管理员**：`docker compose run --rm -T app node dist/cli/init-admin.js --username <用户名> --password-stdin`，密码从管道输入（分配了终端时 `--password-stdin` 会被拒绝）。不做成每次启动都执行的依赖：第二次执行按设计失败。
- **Caddy（`Caddyfile`）**，只做 TLS 与转发：
  - 站点 `localhost` 与 `caddy`（后者供编排网络里的客户端使用，§3.5），`tls internal`（测试环境用 Caddy 自带的 CA）；
  - 不配置 `encode`：内容接口的 gzip 原样经过；转发时关掉压缩协商（`transport http { compression off }`），不替没带 `Accept-Encoding` 的客户端透明解压；
  - `request_body` 上限 6 MB（≥ 5 MiB 的快照加查询串）；
  - `/api/health/ready` 对外返回 404（503 的说明里有迁移名），存活探针照常转发；
  - 到应用的空闲连接 4 秒回收，小于应用的 `NERVE_HTTP_KEEP_ALIVE_TIMEOUT_MS`（5 秒），避免复用应用已经关掉的连接而得到 502；
  - 去掉 `Server` 头；不增加、不改写安全头与 `Set-Cookie`；转发头用 Caddy 的默认值（不信任客户端带来的 `X-Forwarded-For`，以实际来源替换）。
- **环境变量**（`.env.example`）：两个角色与数据库管理员的密码、公开地址（`https://localhost:8443`，与发布的端口一致）、`NERVE_TRUST_PROXY=1`、日志级别、按地址的登录失败上限（默认沿用 50，E2E 运行时调高）。模板里的密码都是占位，脚本与 CI 每次运行时随机生成。
- **单实例首发**：就绪探针在数据库比应用新时失败（审查 A16）不影响单实例的测试环境；滚动发布与 preStop 在 M7 随部署包与运维手册决定，写进部署说明的"已知限制"。

### 3.5 信任代理与登录洪水（DEF-014、DEF-015）

- **信任代理**：`NERVE_TRUST_PROXY=1`（只信任紧挨着的一跳，即 Caddy）。前提是应用的端口只对 Caddy 可达（测试环境不发布应用的端口），写进部署说明。
- **两个客户端地址的核对**（DEF-014）：容器 E2E 的脚本在测试之前，分别从本机（经发布的端口）与编排网络里的另一个容器（经站点 `caddy`）各发一次登录失败，从审计记录里取两次的客户端地址：两者必须不同，而且都不是 Caddy 的地址。配错时（例如不设 `NERVE_TRUST_PROXY`）两次都是 Caddy 的地址，核对失败。
- **运行时自检**（DEF-014）：公开地址是 HTTPS、经代理转发来的请求（带着 `X-Forwarded-For` 或 `X-Forwarded-Proto`）却不是 HTTPS（`request.secure` 为假）时，每个进程只记一条告警，说明代理没有被信任、客户端地址与 HSTS 都会出错。不带转发头的请求不算：容器的健康检查与本机排查直接访问应用，本来就是 HTTP。
- **登录洪水**（DEF-015）：
  - 哈希的排队设上限：排队的请求超过 `NERVE_PASSWORD_HASH_QUEUE_MAX`（默认 64），或者等待超过 `NERVE_PASSWORD_HASH_QUEUE_TIMEOUT_MS`（默认 5 秒）时，立即返回 503 `SERVICE_UNAVAILABLE` 并带 `Retry-After`，不再无限排队；登录页照常显示"服务暂时不可用"一类的说明；
  - 默认值按容器里的 Argon2 基准测试定（写进本文与 ADR-007）：用默认参数哈希一次的耗时 × 队列长度 ÷ 并发数，要明显小于等待时限。实测（镜像内，arm64 的 Apple M 系列，默认参数 19 MiB × 2 次）：一次验证 p50 9.0 毫秒、p95 9.7 毫秒；两个并发排空 66 个约 313 毫秒，比 5 秒的等待时限小一个数量级以上，慢十几倍的机器也等得到；
  - 没有验证的请求（排队满了或等待超时）退回限流的名额、不写审计，与限流拒绝一样只记日志；`Retry-After` 取等待时限（向上取整到秒）；
  - 比对用的假哈希生成失败时不缓存失败（否则之后不存在的用户名会一直出错），下次再生成；
  - 反向代理上按地址的限速：Caddy 的标准构建没有限速模块，自己编译带插件的 Caddy 会给测试环境引入额外的供应链。应用层的上限已经挡住"排队无限增长"这个实际的危害；代理上的限速属于运维配置，写进部署说明的建议，随 M7 的运维手册落实（登记延期）。

### 3.6 E2E 的两种运行方式与 US-M1-10

- **本机模式**（不变）：Playwright 启动服务脚本，后端是本机进程，托管测试构建（`dist-e2e`），每次运行一个测试库。
- **外部模式**（`E2E_BASE_URL`，补全）：
  - 必须同时给出 `E2E_DATABASE_URL`（被测环境的库，测试数据直接写库），缺了直接报错；
  - `E2E_BASE_URL` 是 HTTPS 时忽略证书错误（测试环境用 Caddy 自带的 CA）；
  - 管理员与本机模式是同一个账户 `E2E_ADMIN`，同样经初始化命令创建：外部模式的全局准备（`support/external-setup.ts`）查库，还没有时经 `docker compose run` 执行初始化命令（密码经标准输入）；已经有了就不再执行，同一套环境可以反复跑；
  - 浏览器项目可以用 `E2E_BROWSERS`（逗号分隔）只选其中几个：容器 E2E 在 CI 上只跑 Chromium；
  - 只依赖测试构建的用例（CSP 的阳性对照与对照要打开 `csp-probe.html`，共 2 条）打上 `@test-build` 标签，外部模式按标签排除（不是跳过）：它们在本机模式里照常执行；生产镜像里按门禁不允许有探针页。安全头的用例改用生产构建里的文件（公式 Worker 代替探针的 Worker），两种方式都执行，外部模式另核对 HSTS 与不暴露服务器软件（审查 B2）；
- **容器 E2E 的编排脚本**（`tools/src/deploy/container-e2e.ts`，`pnpm test:e2e:container`）：
  1. 构建镜像（`docker build -f deploy/Dockerfile`）；随机生成三个密码；
  2. 清理中断的运行留下的编排项目（项目名带编排脚本的进程号，进程已经不在的）；起 `db`、执行 `migrate`、起 `app` 与 `caddy`，等经 Caddy 的存活探针通过；端口每次挑空闲的，同时运行的两次互不影响；
  3. 两个客户端地址的核对（§3.5）；
  4. 以外部模式运行 E2E：`E2E_BASE_URL=https://localhost:<端口>`、`E2E_DATABASE_URL` 指向发布到本机的库，排除 `@test-build`；浏览器由参数决定（CI 只跑 Chromium，四个浏览器的覆盖由 verify 的 E2E 承担）；
  5. 记录镜像体积（`docker image ls` 的解压之后的体积：containerd 的镜像存储里 `inspect` 的 `Size` 是压缩之后的）与应用容器的内存（空闲，E2E 期间每 2 秒取样的峰值；重启用例会重启应用，跑完之后的数字不作为指标），打印出来；
  6. 无论成败都收集各容器的日志到 `tests/e2e/test-results/container/`，然后 `down -v` 清理。
- **US-M1-10 的重启用例**（`tests/e2e/specs/deploy/restart.spec.ts`）：
  - 单独的 Playwright 项目 `restart`（Chromium），依赖全部浏览器项目：它们都跑完之后才执行，强制结束后端不会打断别的用例；其他项目忽略这个文件；
  - 结束与重启后端的方式按运行方式区分（`support/api-process.ts`）：本机模式向服务脚本发 `SIGUSR2`，服务脚本对后端发 `SIGKILL` 再按原来的参数启动（进程号写在 `test-results` 里的控制文件中）；外部模式用 `docker compose kill -s KILL app`，等容器不再运行，再 `start app`；之后本机模式等就绪探针，外部模式等经 Caddy 的存活探针（就绪探针不对外）；
  - 用例：
    1. 已确认的保存：保存成功（修订号 N）→ 强制结束 → 重启 → 重新打开，内容与修订号都是 N；
    2. 保存进行中被打断：测试直连数据库锁住这份文档的内容行（`document_contents`，`SELECT … FOR UPDATE`），按保存；后端的保存事务已经写了修订记录、推进了修订号，停在替换内容上等锁（`pg_stat_activity`），这时强制结束后端，再释放锁，等被结束的后端的会话消失（拿到锁、发现连接断了、回滚）；修订号、这次 `requestId` 的修订记录与内容都没有变（没有提交；锁文档行时事务里还没有写入，证明不了原子性，审查 B1）；页面再保存一次，沿用同一个 `requestId`，修订号变成 N+1；
    3. 已经提交、回包丢了：经接口保存得到 N+2 之后立即强制结束；重启后用同一个 `requestId` 再发一次，返回原来的结果，修订号仍是 N+2（重试不重复写入）。

### 3.7 CI

- 新增 job `container`，与 `verify` 并行：检出、安装 Node 与 pnpm、`pnpm install --frozen-lockfile`、只安装 Chromium、`pnpm test:e2e:container`；无论成败都上传测试报告与容器日志。

- 两个 job 都通过才算 CI 全绿。

### 3.8 镜像体积与内存（ADR-001）

- 编排脚本每次打印：镜像的体积（`docker image ls`，解压之后）、应用容器空闲与 E2E 期间峰值的内存（`docker stats --no-stream`）。本机（arm64）与 CI（amd64）各记一次，写进 ADR-001。本机：441 MB，空闲约 200–203 MiB，峰值约 234–259 MiB（多次运行）。
- 精简的手段：只装 api 的生产依赖；运行镜像不带 pnpm、npm、corepack、源码映射之外的开发产物；前端只带生产构建。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 本机是 arm64、CI 是 amd64，平台专属的依赖（argon2 的预编译包）在两边不同 | Dockerfile 不绑定平台；两边都跑容器 E2E；锁文件里有全部平台的变体 |
| 容器 E2E 在 CI 上耗时长（构建前端、四个 CPU 以内跑全部用例） | 容器 E2E 只跑 Chromium；与 verify 并行；构建的依赖层可缓存。超过 30 分钟时再加 buildx 的缓存 |
| 容器 E2E 只能在合并后的 CI 上跑第一次（CI 只在推送 main 时执行） | 本机用同一个入口先跑通；合并后等 CI 结果，失败按 P4 的做法在分支上修复再合并 |
| 应用角色的默认权限漏掉某类对象（例如以后的序列、视图） | 默认权限覆盖表、序列与 schema；容器 E2E 在受限角色下跑全部用例；新增对象类型时在部署说明里补上 |
| 强制结束后端时影响并行的用例 | 重启用例单独一个项目，依赖全部浏览器项目，最后执行 |
| Caddy 的内部 CA 让浏览器不信任证书 | 外部模式忽略证书错误；部署说明写明正式环境换成公网证书或自有 CA |
