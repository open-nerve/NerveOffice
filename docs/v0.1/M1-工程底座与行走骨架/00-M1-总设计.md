# M1 工程底座与行走骨架：总设计

> 文档编号：00｜所属版本：v0.1｜状态：已评审（2026-09-26 审批通过），进行中｜日期：2026-09-26

## 1. 目标与范围

- **目标**：建立生产级的工程底座，M2–M8 直接在上面开发；打通最薄的一条端到端链路：初始化管理员 → 登录 → 个人空间 → 新建表格 → 编辑 → 在线保存 → 重开。对应 00 号计划书 §13.2 的 M1 一行（按 r4 调整，见 §6.8）。
- **范围内**：
  1. 工程底座：pnpm workspace、工具链与版本基线、模块边界的工具强制、单元/集成/E2E 三层测试框架、本地门禁与 CI、开发环境；《工程规范与完成定义》（`docs/v0.1/01-工程规范与完成定义.md`）由工具落地。
  2. 服务端的横切能力：配置校验、结构化日志、错误码、审计、数据库迁移、健康检查与优雅退出、安全响应头。
  3. 账户与个人空间：用命令行初始化首个管理员；登录、退出与服务端会话；个人空间与文档列表。
  4. 在线表格的最小闭环：新建、打开、显式保存（按修订号条件写入）、重开；编辑器适配层按插件档案 `sheet@1` 起步。
  5. 容器化，部署到测试环境。
  6. M0 交给 M1 的事项：M0 交接单"M1 须知"的第 1 条（`sheet@1`）、第 2 条、第 3 条（公式收齐）、第 5 条、第 7 条、第 8 条（`IMAGE()` 的限制）、第 10–12 条。
- **范围外**（归属以 00 号计划书 §13.2 为准）：
  - 邀请注册、重置密码、停用账户、团队空间、文件夹、分享、重命名、移动、复制、回收站、搜索、系统管理界面（M2）；
  - 编辑租约与交接、`writeEpoch`、阅读模式、自动保存，以及捕获时机中的防抖与"公式待更新"标记；完整的快照校验与规范化内容哈希、插件档案强制与打开自检、拦截旧客户端（M3）；
  - 本机发件箱、离线与崩溃恢复、公式 Worker 创建失败时的重建（M4）；
  - 图片资源、表格超链接的地址白名单、粘贴清洗、历史版本、CSV（M5）；文字文档，包括加载时的规范（M6）；
  - 监控告警、备份与恢复、压测、部署包与运维手册（M7）。

本设计在此基础上新增三处调整，随本总设计一起审批：
- **变更检测的判定规则提前到 M1**。原因：没有它，保存后再修改时，界面仍然显示"已保存到云端"，违反 A14，也无法做离开提示。M1 只用它驱动保存状态与离开提示；捕获时机、自动保存仍在 M3。
- **保存与新建带 `requestId`，相同请求返回原结果。** 原因：`document_revisions` 在 M1 建表，唯一约束一开始就建好，免得 M3 补约束时处理存量数据。完整的"确认丢失"语义（A07）仍在 M3 验证。
- **M5 之前不开放依赖平台服务的入口**，例如插入图片、超链接：按菜单配置隐藏，并用命令守卫取消。原因：这些入口的平台策略（图片服务、地址白名单）在 M5 实现，§4.1 要求"编辑器能力不足时，不显示用不了的按钮"。

### 2.2 版本基线

**原则**（审批时确认："与 opennerve 无需严格一致，差不多就行，按最佳推荐"）：
- 工具组合与代码风格与 opennerve 一致，版本号不强求一致。
- 取各依赖当前的稳定大版本；补丁取发布满 3 天的最新版（与规范的 `minimumReleaseAge` 一致），全部精确锁定。
- 新的大版本发布不满两个月时：
  - 如果上一个大版本仍在正常维护，先用上一个大版本（Vitest）；
  - 如果上一个大版本已转为 legacy，就用新的大版本，并在第一次使用它的 Phase 开头先验证（NestJS）。

## 3. 用户故事

E2E 用例的标题以故事编号开头。浏览器 E2E 在本机与 CI 的四个浏览器上都要通过：Chromium、Chrome、Edge、WebKit（本机装不上 Edge 时，Edge 只在 CI 覆盖，见 §2）。US-M1-01 以集成测试为主，US-M1-11 是门禁脚本的自测。

| 编号 | 角色 | 故事 | 验收 |
|---|---|---|---|
| US-M1-01 | 运维人员 | 部署后用命令行初始化首个系统管理员 | 空库中创建管理员及其个人空间，并记入审计；已有管理员时再次执行会报错，数据不变；密码不出现在命令行参数与日志里。集成测试，再加一条 E2E：用这个账户登录 |
| US-M1-02 | 成员 | 用用户名和密码登录、退出 | 凭据正确时进入个人空间；凭据错误时提示统一，不区分"用户不存在"与"密码错误"；连续失败触发限流；退出后会话失效，按后退键也看不到内容；会话过期后被引导到登录页 |
| US-M1-03 | 成员 | 登录后看到自己个人空间的文档列表 | 列表只含本人个人空间的文档；加载中、空列表、加载失败都有明确的显示 |
| US-M1-04 | 成员 | 在个人空间新建表格，并进入编辑 | 新建后整页打开编辑器，空白表格可以立即输入；同一个创建请求重复提交，只生成一份文档 |
| US-M1-05 | 成员 | 编辑后保存到云端，看到真实的保存状态 | 修改后显示"有未保存的修改"；点保存或按 Ctrl/Cmd+S 后，依次显示"保存中""已保存到云端"；保存期间继续输入，回包后仍显示有未保存的修改；有未保存的修改时离开页面，浏览器弹出提示；保存的快照里，公式结果与重算的结果一致 |
| US-M1-06 | 成员 | 刷新页面或重新登录后，打开文档看到最后一次保存的内容 | 保存后重新加载，值、公式与格式一致；未保存的修改不出现；打开文档不被判定为"有修改" |
| US-M1-07 | 成员 | 在两个标签页里编辑同一份文档，旧页面的保存不会覆盖新内容 | 标签页 A 保存后，标签页 B 基于旧修订号的保存被拒绝，界面提示版本冲突，默认保留本页的内容；服务器上保持 A 的版本 |
| US-M1-08 | 成员 | 访问别人的文档与不存在的文档，得到同样的结果 | 两种情况的接口响应与页面一致，不暴露文档是否存在；未登录时访问任何页面与接口，都要求先登录 |
| US-M1-09 | 安全负责人 | 所有响应都带定稿的 CSP 与安全头，编辑器在策略下正常工作 | HTML、脚本、Worker 脚本与接口响应都带策略；页面与 Worker 两个作用域的阳性对照中，违规的请求被拦截；表格编辑器（含公式 Worker）正常工作。Edge 上的这条用例关闭 DEF-001 |
| US-M1-10 | 运维人员 | 用容器把应用部署到测试环境；API 重启后已确认的数据不丢 | 按部署说明构建镜像、执行迁移、启动，就绪探针通过；强制结束 API 进程再启动后，已确认保存的内容完整；保存进行中被打断时，要么完整提交、要么没有提交，重试不会重复写入 |
| US-M1-11 | 维护者 | 引入不合规依赖的改动，在合并前被拦下 | 出现以下任何一种情况，门禁都失败：Pro 包、`@univerjs/*` 版本不一致、应为单例的包出现多份、许可不在白名单、未登记的安装脚本、产物中出现动态代码或第三方地址。门禁脚本带自测，用预置的违规样例证明每一条都能拦下 |

## 4. 负责的上线门槛

| 门槛 | 本 M 的验证方式 |
|---|---|
| A01 开源依赖 | US-M1-11：依赖与产物检查在本机门禁与 CI 中执行（M0 依赖报告脚本的规则，加上安装脚本白名单、产物的关键字与动态代码扫描，扫描范围包括 Worker 自己加载的子块），另有检查脚本的自测 |
| A09 进程与浏览器异常（API 重启部分） | US-M1-10：强制结束 API 进程后重启，已确认的数据完整；在途的保存要么完整提交、要么不提交，重试幂等。浏览器异常部分在 M4 |
| A14 体验真实（M1 的界面） | US-M1-02 至 US-M1-08：加载、空、失败、无权限、保存中、版本冲突的界面状态都真实。只有服务端确认后才显示"已保存到云端"，之后一有修改立即改为"有未保存的修改" |

A03（越权访问）的首次验证在 M2。M1 用 US-M1-08 覆盖本阶段的范围，即只有个人空间时的访问控制。

## 5. Phase 规划

执行顺序为 P1 → P5，分支依次为 `m1-p1-foundation`、`m1-p2-server-infra`、`m1-p3-accounts`、`m1-p4-sheet-save`、`m1-p5-deploy`。大的 Phase 可以一个 Step 一个分支。每个 Phase 的详细设计，在该 Phase 开始时基于最新代码编写。

| Phase | 目标 | 主要内容 | 依赖 | 产出 | 验收 |
|---|---|---|---|---|---|
| P1 工程底座 | 仓库、工具链与质量门禁就位，规范能由工具执行 | pnpm workspace 与目录骨架；版本基线；TypeScript、ESLint（含模块边界与格式化）、lefthook；Vitest 与 Playwright 框架（四个浏览器，不用设备预设）；A01 依赖与产物检查，带自测；`pnpm verify` 与 GitHub Actions（推送 main 时与每周定时）；pnpm 的 `minimumReleaseAge` 与安装脚本白名单；依赖漏洞扫描；本机安装 Edge | 无 | 可运行的空骨架、门禁脚本、CI、ADR（版本基线、仓库结构与模块边界）、`CLAUDE.md` 的常用命令 | 本机与 CI 全绿；每一层测试框架各有真实用例跑通；US-M1-11 |

## 6. 架构影响

### 6.1 仓库结构

按 00 号计划书 §9.4：

```text
apps/
  web/            React + Vite；两个入口：平台页面、表格编辑器页（整页加载）
    src/editor/   Univer 适配层：插件档案、平台插件、内部 API 登记；全仓库只有这里能引用 @univerjs/*
  api/            NestJS 模块化单体，同时托管 web 的构建产物；src/db/ 下放 Schema、迁移与仓储
packages/
  contracts/      前后端共享的请求与响应结构（zod）、错误码、常量
tools/            仓库工具：质量门禁、故事对照、提交钩子、verify（M1-P1，ADR-003）
tests/
  fixtures/       样本快照与测试数据
  integration/    基于真实 PostgreSQL 的集成测试
  e2e/            Playwright，按模块与用户故事组织
  stories.json    当前 M 的用户故事登记表
deploy/           Dockerfile、测试环境编排、Caddy 配置、环境变量模板
docs/architecture/overview.md    架构总览（M1 建立 v1）
docs/adr/                        ADR
```

`spikes/`、`refer/` 不属于 workspace，不参与 lint、构建与测试。

### 6.2 运行形态

```text
浏览器 ──HTTPS──► Caddy（只做 TLS 终止与转发）──HTTP──► 应用容器（Node 24）
                                                         ├─ /api/*   NestJS
                                                         └─ 其他     web 的构建产物（含 Worker 脚本）
                                                         所有响应都带 CSP 与安全头
                                                                │
                                                         PostgreSQL 18 容器（持久化卷）
```

- 迁移：用同一个镜像执行一次性命令，在启动应用之前运行。应用启动时只检查库结构的版本，不一致时就绪探针失败，不自动迁移（§12.4）。
- 反向代理只做 TLS 与转发，换成 nginx 不影响应用（opennerve 用的是 nginx）。
- 开发时由 Vite 开发服务器代理 `/api`。开发服务器的热更新需要内联脚本，所以 CSP 只在开发服务器上放宽；E2E 一律跑生产构建。

### 6.3 后端模块

| 模块 | M1 的职责 |
|---|---|
| config | 读取并校验环境变量，缺失或非法时启动失败；向其他模块提供类型化的配置 |
| logging | pino 结构化日志、请求标识、脱敏 |
| database | 连接池与超时、事务、迁移、库结构版本检查 |
| audit | 写入审计事件（只追加） |
| health | 存活与就绪探针 |
| security | 安全响应头（CSP 等）、CSRF 与 Origin 检查、请求体上限 |
| auth | 登录、退出、会话、登录限流、密码哈希 |
| users | 账户；命令行初始化管理员 |
| spaces | 个人空间（M2 扩展为团队空间与成员） |
| documents | 文档元数据、内容读写、修订记录；访问策略（M1 只有"个人空间的所有者"一条规则，M2 在同一个接口后面扩展为 §5.2 的有效权限） |
| web-hosting | 托管前端产物，把编辑器的路径映射到编辑器页 |

- 模块之间只经各自的公开入口依赖。
- 表只由所属模块的仓储读写。
- 授权由服务端对每个请求执行，默认拒绝。

### 6.4 数据模型

M1 新建以下各表，之后只做加法（§13.1）。

| 表 | M1 的字段范围 | 后续 M 的加法 |
|---|---|---|
| users | 用户名（唯一，不区分大小写）、显示名、Argon2id 哈希、系统角色、状态 | M2：邀请、停用 |
| auth_sessions | 令牌摘要、用户、创建与最后活动时间、空闲与绝对过期时间、撤销时间与原因 | M2：停用与改密时撤销 |
| spaces | 类型（M1 只有个人空间）、名称、状态、个人空间的所有者、是否全员可见（默认否） | M2：团队空间、space_members |
| documents | 所属空间、类型（M1 只有表格）、标题、创建者、状态、修订号、Univer `unitId`、插件档案的标识与版本、SDK 版本、平台格式版本 | M2：文件夹、回收站；M3：`writeEpoch` |
| document_contents | gzip 压缩的快照（bytea）、压缩前后的字节数 | M3：规范化的内容哈希 |
| document_revisions | 修订号、`requestId`（唯一）、负载摘要、`clientInstanceId`、`localSeq`、保存人、时间 | M3：内容哈希、保留期清理 |
| audit_events | 时间、操作者、动作、对象、请求标识、来源；不含正文 | 各 M 增加事件类型 |

### 6.5 接口

| 接口 | 说明 |
|---|---|
| `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/session` | 登录、退出；当前会话与个人空间 |
| `GET /api/documents`、`POST /api/documents` | 个人空间的文档列表；新建（类型白名单，`requestId` 幂等） |
| `GET /api/documents/{id}` | 元数据，以及调用者的权限 |
| `GET /api/documents/{id}/content` | 快照（gzip）、修订号（作 ETag）、档案与格式信息 |
| `PUT /api/documents/{id}/content` | 保存：按 `baseRevision` 条件写入，`requestId` 幂等；冲突时返回当前修订号及其来源 |
| `GET /api/health/live`、`GET /api/health/ready` | 存活与就绪探针 |

字段与错误结构在 P3、P4 的设计中锁定，写进 `packages/contracts`。服务端在 M1 只做快照的基本校验：解压后的体积上限、JSON 合法、顶层类型与 `unitId` 与文档记录一致。§11.2 的完整校验在 M3。

### 6.6 编辑器适配层（M1 的部分）

按插件档案 v1 与 M0 交接单的"M1 须知"：

- **档案**：`sheet@1` 的插件清单、注册顺序与影响数据的配置都按档案，包括默认启用公式 Worker、关掉大表操作的拆分；菜单配置按档案。不注册 `@univerjs/network`、评论、水印，也不注册任何 `ITelemetryService` 实现。
- **生命周期**：整页加载，一页一份文档；载入快照，用 `save()` 捕获快照，捕获前不调用 Facade 的读取方法。
- **新建**：使用收敛后的模板快照（§8.1），每份新文档生成新的 `unitId`；P4 确认替换 `unitId` 之后模板仍然收敛。
- **变更检测**：按 M0 定稿的判定规则，只看 `MUTATION`，排除名单两条。M1 只用它驱动保存状态与离开提示，M3 在它之上加捕获时机与自动保存。
- **显式保存**：
  - 按 §7.3 的收齐规则等公式结果；
  - 超过 3 秒上限时照常保存，界面提示"公式结果尚未保存"，收齐之后需要再保存一次（M3 的自动保存会自动补这一次）；
  - 保存时单元格还在编辑中怎么处理，由 P4 设计。
- **`IMAGE()` 的限制**：主线程与公式 Worker 各安装一次，Worker 回报安装结果；没有回报或安装失败时，不允许编辑。
- **身份**：
  - 用"全部允许"的 `IAuthzIoService` 替换本地授权服务。
  - 本地授权服务在构造时注册了资源 `SHEET_AuthzIoMockService_PLUGIN`（在档案 v1 中"必须为空"），替换后这个运行时资源 hook 会消失（`refer/univer` 的 `packages/core/src/services/authz-io/authz-io-local.service.ts:69、89-118`；它在核心注入器里注册，`packages/core/src/univer.ts:295`）。
  - P4 核实它的影响，决定"保留同名的 hook，恒为空"还是修订档案 v1 的白名单，写入 ADR。v0.1 还没有存量文档，不涉及迁移。
- **内部 API**：集中在 `src/editor/internal-api/`，逐项登记用途、M0 证据与回归用例。在其他位置引用受限清单中的内部符号，lint 会失败。
- **M5 之前不开放的入口**：插入图片、超链接等，按菜单配置隐藏，并用命令守卫取消。粘贴清洗在 M5；M1 期间由 CSP 保证不向第三方发请求。
- **E2E**：不用 Playwright 的设备预设；首屏以 `Rendered` 计。

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| NestJS 12 刚发布一个月，并且改为纯 ESM；ESM 下的循环引用与装饰器元数据容易出问题 | P2 第一步先验证：构建、监听、Vitest（NestJS 的依赖注入依赖装饰器元数据，Vitest 默认的转译不生成它，按 NestJS 官方的做法接入 SWC，或者全部使用显式的注入标记）、集成测试与优雅退出；lint 禁止循环依赖。不通过就退回 11.2（legacy，仍有补丁），写入 ADR |
| 生产代码的版本组合与 M0 的验证工程不完全相同（NestJS、Vitest 等 M0 没有用到） | 前端的关键依赖（Univer 1.0.0、React 19.3.0、Vite 8.3.0、TypeScript 6.0.3、Playwright 1.63.0）与 M0 相同；P4 按生产档案重新统计包体积并定出预算；M0 交接的 SDK 行为由 E2E 覆盖 |
| Univer 的样式与平台的 Tailwind 基础样式互相影响 | 编辑器页只加载必要的平台样式；P4 的 E2E 检查编辑器的关键界面 |
| 服务端的依赖面较大，带来供应链风险（ADR-001） | 精确锁版本与锁文件；`minimumReleaseAge`；安装脚本白名单；CI 做依赖漏洞扫描 |
| 本机的 GUI 浏览器依赖登录的桌面会话；Edge 可能装不上 | 长时间运行前起 `caffeinate`；Edge 至少在 CI（Linux）上覆盖；本机缺少的覆盖如实写进报告 |
| 行走骨架的范围膨胀 | 严格按 §1 的范围外清单执行；新需求登记到后续的 M |
| M3 之前的保存没有租约，两个标签页可以同时编辑 | 修订号条件写入保证不会静默覆盖（US-M1-07）；阅读模式与租约在 M3 |
