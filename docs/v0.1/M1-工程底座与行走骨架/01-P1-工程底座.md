## 1. 目标与范围

  - TypeScript、ESLint（含模块边界）、提交钩子；
  - 单元、集成、E2E 三层测试框架，各有真实用例；
  - 开发用的 PostgreSQL；
  - A01 的依赖与产物检查，带自测；
  - 故事清单与测试的自动对照；
  - `pnpm verify` 与 GitHub Actions；
  - 本机安装 Edge；
  - ADR、架构总览的初版、`CLAUDE.md` 的常用命令。
- **范围外**：
  - NestJS 后端（P2）；
  - 真实页面（P3）；
  - Univer（P4）。与 Univer 有关的检查（版本一致、单例、没有 Pro）在本 Phase 实现，用样例自测；P4 引入 Univer 后才对真实依赖生效。

## 3. 设计

### 3.1 仓库结构

| 包 | 路径 | 作用 | 本 Phase 的内容 |
|---|---|---|---|
| `@nerve-office/contracts` | `packages/contracts` | 前后端共享的请求与响应结构、错误码 | 错误响应的外层结构（规范 §4）及其单元测试 |
| `@nerve-office/web` | `apps/web` | 前端 | 占位页面（P3 换成登录页）及其单元测试；生产构建开启 `build.license` |
| `@nerve-office/tools` | `tools` | 仓库工具：门禁、故事对照、提交钩子、`verify` | 全部 |
| `@nerve-office/integration-tests` | `tests/integration` | 基于真实 PostgreSQL 的集成测试 | 数据库版本与排序规则的检查 |
| `@nerve-office/e2e` | `tests/e2e` | Playwright | 四个浏览器的框架冒烟 |

- `apps/api` 在 P2 建立。
- `tools/` 是 00 号计划书 §9.4 没有列出的目录，存放仓库自己的工具，写入 ADR，并补进规范 §1.1。
- 开发用的数据库编排放在 `deploy/dev/`。

**模块系统**：

| 包 | 方式 | 原因 |
|---|---|---|
| tools | ESM；Node 24 直接运行 TypeScript（类型剥离），相对导入写 `.ts` 扩展名；开启 `erasableSyntaxOnly` | 不需要构建步骤 |
| contracts | ESM。用 `tsc -b` 构建到 `dist/`，供 Node 使用（P2 起的 api）；同时通过自定义导出条件 `@nerve-office/source` 直接给出源码 | Vite、Vitest 与类型检查读源码，开发时不需要先构建；Node 不对 `node_modules` 里的文件做类型剥离，所以运行时读构建产物 |
| web | 打包器解析（`moduleResolution: bundler`） | 由 Vite 构建 |

**依赖方向**（eslint-plugin-boundaries；本 Phase 先建立下列规则，后面的 Phase 随新模块扩展）：
- contracts 不依赖任何内部包；
- web 只依赖 contracts；
- tools 不依赖业务包；
- 测试只经各包的公开入口引用；
- `@univerjs/*` 只能在 `apps/web/src/editor/` 下引用。这条规则从本 Phase 起就生效，虽然 Univer 在 P4 才引入；
- 禁止循环依赖。

**格式化**：ESLint（@antfu/eslint-config）统一格式化 TypeScript、JavaScript、JSON 与 YAML，不用 Prettier；Markdown 不做 lint。
- 这一条改变了 M1 总设计 §2.2 与规范 §2.2 原来"用 Prettier 格式化 JSON、YAML"的写法。原因：@antfu/eslint-config 本身就格式化 JSON 与 YAML，再加 Prettier，两个工具会互相改写。
- 两处文档在本 Phase 修订，并写修订记录。

### 3.2 工具链与配置

- **根 `package.json`**：
  - `packageManager: pnpm@12.6.0`；`engines.node: >=24.21.0 <25`；`type: module`；
  - 脚本：`verify`、`lint`、`typecheck`、`test`、`test:integration`、`test:e2e`、`build`、`gate:*`、`db:up`、`db:down`。
- **`.node-version`**：写 `24.21.0`，供 nvm、CI 与镜像读取。
- **`pnpm-workspace.yaml`** 的设置（名称以 pnpm 12 实际接受的为准；它拒绝无法识别的设置，写错会直接失败）：
  - `minimumReleaseAge: 4320`，即 3 天；
  - `trustPolicy: no-downgrade`：新版本的发布可信度（如来源证明）不得低于旧版本；
  - `allowBuilds`：逐个写明允许或拒绝的安装脚本，并在注释里写原因；
  - `engineStrict: true`；
  - 添加依赖时写入精确版本。
- **TypeScript**：
  - 根 `tsconfig.base.json` 放共用选项：`strict`、`noUncheckedIndexedAccess`、`noImplicitOverride`、`noFallthroughCasesInSwitch`、`verbatimModuleSyntax`、`isolatedModules`、`skipLibCheck`、`forceConsistentCasingInFileNames`；
  - 每个包有自己的 `tsconfig.json`；
  - 根 `tsconfig.json` 只放引用，`tsc -b` 检查全部。
- **ESLint**（`eslint.config.ts`）：
  - @antfu/eslint-config 开启 React 与类型感知规则，风格用默认值：2 空格、单引号、不写分号；
  - 按规范 §2 加上规则：禁止 `any`、非空断言（测试除外）、`@ts-ignore`、悬空的 Promise、不完整的 `switch`、`console`（tools 的命令行入口除外）、`dangerouslySetInnerHTML`；文件名用短横线小写；
  - 模块边界与循环依赖；
  - 测试文件禁止 `.only`（Vitest 与 Playwright 都查）；
  - 以 `--max-warnings 0` 运行。
- **提交钩子**（lefthook，由根 `prepare` 脚本安装）：
  - pre-commit：lint-staged 对暂存的文件执行 `eslint --fix`；
  - commit-msg：去掉 AI 署名，即 `Co-Authored-By` 中的 Claude/Anthropic 以及"Generated with Claude Code"水印；
  - pre-push：`pnpm verify --fast`。
- **Vitest**：根配置分成几个项目：
  - `unit`：Node 环境，contracts 与 tools；
  - `unit-web`：jsdom 环境，apps/web；
  - `integration`：Node 环境，tests/integration，默认不跑，需要数据库。

  覆盖率用 v8，下限：contracts 90%，web 70%（不含 `src/editor/`），tools 80%。规范 §8.3 没有给 tools 定下限，这里按门禁代码的重要性自定。
- **Playwright**（`tests/e2e/playwright.config.ts`）：
  - 四个项目：chromium、chrome（`channel: 'chrome'`）、msedge（`channel: 'msedge'`）、webkit；不用设备预设；
  - `forbidOnly: true`；重试次数本机 0 次，CI 1 次；
  - 失败时保留 trace 与截图；
  - 被测服务：本 Phase 用 web 构建产物的预览服务，P3 起换成 api 托管的生产构建。
- **开发数据库**（`deploy/dev/compose.yaml`）：
  - 镜像 `postgres:18.6-alpine`，按多架构索引的摘要锁定；
  - 用 `POSTGRES_INITDB_ARGS` 让新库使用 `builtin` 排序规则提供者与 `C.UTF-8`，排序规则与操作系统的 libc、ICU 版本无关；
  - 只监听 `127.0.0.1:54318`；有健康检查；数据放在命名卷里。

### 3.3 A01 的依赖与产物检查（US-M1-11）

| 检查 | 输入 | 规则 | 何时生效 |
|---|---|---|---|
| 精确版本 | 所有 `package.json` | 依赖只能写精确版本或 `workspace:`；`packageManager` 必须精确 | 本 Phase |
| 包管理配置 | `pnpm-workspace.yaml` | `minimumReleaseAge` 不少于 4320；设置了 `trustPolicy`；`allowBuilds` 的每一项都有明确的决定 | 本 Phase |
| Univer 版本与 Pro | 生产依赖图（`pnpm ls --prod`） | 没有 `@univerjs-pro/*`；`@univerjs/*` 使用同一个版本，独立发版的包按清单单独核对 | 本 Phase 实现，P4 生效 |
| 单例 | 同上，按安装路径区分实例 | react、react-dom、rxjs、`@wendellhu/redi` 与每个 `@univerjs/*` 包各只有一份 | 本 Phase（react 从现在起生效） |
| 许可 | pnpm 的许可清单 | 生产依赖在白名单内；开发依赖不得有 GPL、AGPL、SSPL 与没有声明许可的包 | 本 Phase |
| 产物扫描 | web 构建产物中的全部 JS，包括 Worker 及其按需加载的子块 | 见下文 | 本 Phase |
| 第三方许可清单 | 构建产物中的 `.vite/license.md` | 文件存在；打进产物的每个第三方包都有许可正文，缺的由仓库补齐（M0：6 个包的发布包里没有许可文件） | 本 Phase |
| 漏洞 | `pnpm audit --prod` | 高危及以上失败；例外清单写明原因与到期日 | 本 Phase（CI） |

**产物扫描**的规则：
- 没有 `eval`、`new Function`、字符串形式的定时器、`WebAssembly`；
- `Function('return this')` 这类全局对象探测，只允许已登记的次数（M0 在 Univer 的产物里见过 3 处）；
- 绝对地址的主机都在允许清单里，并写明理由（例如错误信息里的文档链接不会被请求）；
- 没有 Pro、许可证校验、遥测等关键字。

每项检查都是独立的模块：输入由调用方提供，规则是纯函数，所以能用样例做单元测试。每一条规则都至少有一个合规样例和一个违规样例，这就是门禁的自测。

### 3.4 故事对照

- 登记表 `tests/stories.json` 列出当前 M 的故事编号、状态（`planned` / `active`）、归属的 Phase 与验证方式（E2E、集成测试、门禁自测）。

### 3.5 本机门禁与 CI

- **`pnpm verify`**（`tools/src/verify/`）按顺序执行：
  1. lint；
  2. 类型检查；
  3. 单元测试与覆盖率；
  4. 精确版本、包管理配置与故事对照；
  5. 集成测试（开发数据库没有启动时先启动）；
  6. 构建；
  7. 依赖、许可与产物检查；
  8. E2E（四个浏览器）。

  `--fast` 只执行前 4 步，供 pre-push 使用。本机缺少某个浏览器时，E2E 失败并提示安装方法，不静默跳过。
- **CI**（`.github/workflows/ci.yml`）：
  - 触发：推送 main、每周一次定时、手动触发；
  - 一个作业，在 `ubuntu-24.04` 上运行：PostgreSQL 18 服务容器；各个 Action 按提交的 SHA 锁定；`pnpm install --frozen-lockfile`；安装四个浏览器及其系统依赖；执行 `pnpm verify`，再做依赖漏洞扫描；
  - 失败时上传 Playwright 报告与覆盖率；
  - 权限只读；有超时。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| pnpm 12 是 Rust 重写的版本，`ls`、`licenses` 等命令的 JSON 输出可能与 M0 用的不同 | S3 先核实输出格式；解析做成独立的模块，并用样例测试 |
| corepack 运行不了 pnpm 12 | 本机与 CI 都用 npm 全局安装精确版本的 pnpm；P5 的镜像构建同样处理 |
| 本机还没有 Edge | 已请用户安装；S4 的 `pnpm verify` 之前必须装好 |
| GitHub Actions 的 Linux 环境与本机不同（WebKit、Edge 的 Linux 版本） | 合并后的第一次 CI 如有问题，立即修复 |
| `pnpm/action-setup` 是否支持 pnpm 12 未知 | S4 核实；不支持就用 npm 全局安装 |
