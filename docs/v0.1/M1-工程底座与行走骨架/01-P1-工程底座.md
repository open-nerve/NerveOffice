## 3. 设计

### 3.1 仓库结构

| 包 | 路径 | 作用 | 本 Phase 的内容 |
|---|---|---|---|
| `@nerve-office/contracts` | `packages/contracts` | 前后端共享的请求与响应结构、错误码 | 错误响应的外层结构（规范 §4）及其单元测试 |
| `@nerve-office/web` | `apps/web` | 前端 | 占位页面（P3 换成登录页）及其单元测试；第三方许可收集插件（`apps/web/build/`，覆盖 Worker 的产物） |
| `@nerve-office/tools` | `tools` | 仓库工具：门禁、故事对照、提交钩子、`verify` | 全部 |
| `@nerve-office/integration-tests` | `tests/integration` | 基于真实 PostgreSQL 的集成测试 | 数据库版本与排序规则的检查 |
| `@nerve-office/e2e` | `tests/e2e` | Playwright | 四个浏览器的框架冒烟 |

- `apps/api` 在 P2 建立。
- `tools/` 是 00 号计划书 §9.4 没有列出的目录，存放仓库自己的工具，写入 ADR，并补进规范 §1.1。
- 开发用的数据库编排放在 `deploy/dev/`。

**模块系统**：

| 包 | 方式 | 原因 |
|---|---|---|
| tools | ESM；Node 24 直接运行 TypeScript（类型剥离），相对导入写 `.ts` 扩展名；开启 `erasableSyntaxOnly` | 不需要构建步骤 |
| contracts | ESM。用 `tsc -p tsconfig.build.json` 构建到 `dist/`，供 Node 使用（P2 起的 api）；同时通过自定义导出条件 `@nerve-office/source` 直接给出源码 | Vite、Vitest 与类型检查读源码，开发时不需要先构建；Node 不对 `node_modules` 里的文件做类型剥离，所以运行时读构建产物 |
| web | 浏览器代码用打包器解析（`tsconfig.app.json`）；`vite.config.ts` 与构建插件在 Node 里运行，另用 `tsconfig.node.json`；`tsconfig.json` 只引用这两份，供编辑器与 ESLint 使用 | 由 Vite 构建；Node 的类型不进入浏览器代码 |

**依赖方向**（eslint-plugin-boundaries；本 Phase 先建立下列规则，后面的 Phase 随新模块扩展）：
- 同一个元素内部的引用不受限制；跨元素时，contracts、功能模块与编辑器只能经公开入口（`index.ts`）引用；应用层与共享层是被组合的一方，可以直接引用；
- contracts 不依赖任何内部包；web 只依赖 contracts；tools 不依赖业务包；测试只经 contracts 的公开入口引用它（P2 起加上 api 的测试入口）；
- 平台页面的入口不引用编辑器；
- 元素目录里的每个文件都必须属于某个元素，每个引用的目标也必须属于某个元素，免得借一个"无主"文件中转绕过边界（审查 R6）；
- `@univerjs/*` 只能在 `apps/web/src/editor/` 下引用，静态导入、再导出与动态导入都算；动态导入的路径必须是字面量。这条规则从本 Phase 起就生效，虽然 Univer 在 P4 才引入；
- 禁止循环依赖（import-x 要声明 TypeScript 的扩展名与解析器才能看到 `.ts` 之间的引用，审查 R1）。

**格式化**：ESLint（@antfu/eslint-config）统一格式化 TypeScript、JavaScript、JSON 与 YAML，不用 Prettier；Markdown 不做 lint。
- 这一条改变了 M1 总设计 §2.2 与规范 §2.2 原来"用 Prettier 格式化 JSON、YAML"的写法。原因：@antfu/eslint-config 本身就格式化 JSON 与 YAML，再加 Prettier，两个工具会互相改写。
- 两处文档在本 Phase 修订，并写修订记录。

### 3.2 工具链与配置

- **根 `package.json`**：
  - `packageManager: pnpm@12.6.0`；`engines.node: >=24.21.0 <25`；`type: module`；
  - 脚本：`verify`、`lint`、`typecheck`、`test`、`test:integration`、`test:e2e`、`build`、`gate:*`、`db:up`、`db:down`。
- **`.node-version`**：写 `24.21.0`，供 nvm、CI 与镜像读取。
- **`pnpm-workspace.yaml`** 的设置（名称以 pnpm 12 实际接受的为准；它拒绝无法识别的设置，写错会直接失败）：
  - `catalog`：外部依赖的精确版本集中写在这里，各包写 `catalog:`（实施时加入：@antfu/eslint-config 的 pnpm 规则会强制使用目录，也让版本只有一处来源）；
  - `minimumReleaseAge: 4320`，即 3 天；`minimumReleaseAgeExcludePrune: true`，自动清理不再需要的豁免；
  - `trustPolicy: no-downgrade`：新版本的发布可信度（如来源证明）不得低于旧版本；
  - `allowBuilds`：逐个写明允许或拒绝的安装脚本，并在注释里写原因。目前是 lefthook 与 unrs-resolver，都拒绝；
  - `peerDependencyRules`：eslint-plugin-jsx-a11y 6.10.2 的 peer 只声明到 ESLint 9，放行 ESLint 10，由 lint 自测证明规则生效；
  - `shellEmulator: true`：脚本在 pnpm 内置的 POSIX shell 里执行（这个 shell 不展开未加引号的通配符，所以脚本里的目录过滤写成 `'./apps/*'`）；
  - `engineStrict: true`。
- **TypeScript**：
  - 根 `tsconfig.base.json` 放共用选项：`strict`、`noUncheckedIndexedAccess`、`noImplicitOverride`、`noFallthroughCasesInSwitch`、`verbatimModuleSyntax`、`isolatedModules`、`skipLibCheck`、`forceConsistentCasingInFileNames`；
  - 每个包有自己的 `tsconfig.json`，类型检查逐包执行 `tsc -p`（`pnpm typecheck`）；
  - 根 `tsconfig.json` 只检查根目录下的配置文件。
- **ESLint**（`eslint.config.ts`）：
  - @antfu/eslint-config 开启 React 与类型感知规则，风格用默认值：2 空格、单引号、不写分号；
  - 按规范 §2 加上规则：禁止 `any`、非空断言（测试除外）、`@ts-ignore`、悬空的 Promise、不完整的 `switch`、`console`（tools 的命令行入口除外）、`dangerouslySetInnerHTML`；文件名用短横线小写；
  - 模块边界与循环依赖；
  - 测试文件禁止 `.only`，也禁止跳过或占位的用例（`skip`、`todo`、`fixme`），Vitest 与 Playwright 都查；用例标题不要求首字母小写（标题以中文或故事编号开头）；
  - 把上游配置里的警告级别统一提升为错误，并以 `--max-warnings 0` 运行；
  - `console` 的全部方法都禁止（上游配置默认放行 `warn` 与 `error`）。
- **提交钩子**（lefthook，由根 `prepare` 脚本安装）：
  - pre-commit：lint-staged 对暂存的文件执行 `eslint --fix`；
  - commit-msg：去掉提交说明末尾署名段里的 AI 署名（AI 专用邮箱，或者整个名字就是 AI 产品名；以及"Generated with Claude Code"一类水印）；正文与人类合作者不动；
  - pre-push：`pnpm verify --fast`。
- **Vitest**：根配置分成几个项目：
  - `unit`：Node 环境，contracts、tools 与 web 的构建插件；
  - `unit-web`：jsdom 环境，apps/web；
  - `integration`：Node 环境，tests/integration，默认不跑，需要数据库。数据库的连通检查放在每个文件的 `beforeAll` 里，列举测试时不需要数据库。

  覆盖率用 v8，下限：contracts 90%，web 70%（不含 `src/editor/`），tools 80%。规范 §8.3 没有给 tools 定下限，这里按门禁代码的重要性自定。入口文件与命令行入口不计入覆盖率，它们分别由 E2E 与门禁的实际运行覆盖。
- **Playwright**（`tests/e2e/playwright.config.ts`）：
  - 四个项目：chromium、chrome（`channel: 'chrome'`）、msedge（`channel: 'msedge'`）、webkit；不用设备预设；
  - `forbidOnly: true`；重试次数本机 0 次，CI 1 次；
  - 失败时保留 trace 与截图；
  - 用例放在 `tests/e2e/specs/<模块>/`；
  - 被测服务：本 Phase 用 web 构建产物的预览服务（先构建，`pnpm test:e2e` 会先执行构建），P3 起换成 api 托管的生产构建。
- **开发数据库**（`deploy/dev/compose.yaml`）：
  - 镜像 `postgres:18.6-alpine`，按多架构索引的摘要锁定；
  - 用 `POSTGRES_INITDB_ARGS` 让新库使用 `builtin` 排序规则提供者与 `C.UTF-8`，排序规则与操作系统的 libc、ICU 版本无关；
  - 只监听 `127.0.0.1:54318`；有健康检查；数据放在命名卷里。

### 3.3 A01 的依赖与产物检查（US-M1-11）

| 检查 | 输入 | 规则 | 何时生效 |
|---|---|---|---|
| 精确版本 | 所有 `package.json` 与 pnpm 目录 | 外部依赖只能经目录引用，目录里是精确版本；内部包写 `workspace:*`；`packageManager` 必须精确 | 本 Phase |
| 包管理配置 | `pnpm-workspace.yaml` | 只允许评审过的顶层设置（`dangerouslyAllowAllBuilds`、`minimumReleaseAgeStrict`、`trustPolicyExclude`、`auditConfig` 等削弱策略的设置一律拦下）；`minimumReleaseAge` 不少于 4320；`trustPolicy`、`engineStrict`；安装脚本、冷却期豁免、`overrides`、peer 规则、补丁逐项写明原因；`overrides` 只能是精确版本或移除 | 本 Phase |
| Univer 版本与 Pro | 生产依赖图（`pnpm ls --prod`，含项目层的可选依赖；包名取真实包名，不取别名） | 没有 `@univerjs-pro/*`；`@univerjs/*` 使用同一个版本，独立发版的包按清单单独核对；依赖树里只有去重占位、从未展开的子树视为不完整 | 本 Phase 实现，P4 生效 |
| 单例 | 同上，按安装路径区分实例 | react、react-dom、rxjs、`@wendellhu/redi` 与每个 `@univerjs/*` 包各只有一份 | 本 Phase（react 从现在起生效） |
| 许可 | 生产依赖图的每个安装实例，按路径到全量的许可清单（`pnpm licenses list`）里查许可 | 生产依赖在白名单内（许可标识不区分大小写）；开发依赖不得有 GPL、AGPL、SSPL 的各种写法与没有声明许可的包（pnpm 12 输出 `Unknown`）。不用 `licenses list --prod`：它会漏掉可选依赖（审查 R2） | 本 Phase |
| 产物扫描 | web 构建产物的全部文件；文本类（JS、CSS、HTML、SVG）扫描内容，包括 Worker 及其按需加载的子块 | 见下文 | 本 Phase |
| 第三方许可清单 | web 构建插件写出的 `.vite/third-party-packages.json` | 打进产物的每个第三方包（含 Worker 的产物）都有许可正文，缺的由仓库补齐（M0：6 个包的发布包里没有许可文件）；许可在白名单内 | 本 Phase |
| 漏洞 | `pnpm audit --prod` | 高危及以上失败；例外清单写明原因与到期日；清单与 metadata 的计数不一致（漏洞被 `auditConfig` 藏起来）同样失败 | 本 Phase（CI） |

**产物扫描**的规则：
- 没有动态代码：`eval`（含 `globalThis.`、`window.`、`self.` 前缀，可选调用 `eval?.(`，逗号表达式里的间接调用，下标 `['eval']`）、`Function(`（带不带 `new` 都算）、`.constructor('…')`、字符串形式的定时器、`WebAssembly`、内联 Worker（Blob 或 data URL）与 data: 脚本；
- `Function('return this')` 这类全局对象探测，只允许已登记的次数（M0 在 Univer 的产物里见过 3 处）；
- 绝对地址（http、https、ws、wss，不区分大小写，包括 JSON 转义的写法）与字符串里的协议相对地址，主机都要在允许清单里，并写明理由（例如错误信息里的文档链接不会被请求）；
- 没有 Pro、许可证校验、第三方统计等关键字（不区分大小写）；
- 产物里只能出现登记过的文件类型，免得未知类型绕过扫描。

静态扫描判断不了运行时才拼出来的代码与地址（例如 `setTimeout(变量)`、`"https:" + "//" + host`），这部分由 CSP 兜底：策略里没有 `'unsafe-eval'`，`connect-src` 只有 `'self'`。

**第三方许可清单**：Vite 自带的 `build.license` 不收集 Worker 的产物（Worker 以 asset 的形式并入主构建，审查 R4 用样例工程证实），所以改用自己的插件 `apps/web/build/third-party-licenses.ts`：主构建与 `worker.plugins` 各挂一份，按产物里模块所在的 npm 包收集，写出随部署包分发的 `THIRD-PARTY-LICENSES.md` 与供门禁检查的 `.vite/third-party-packages.json`。它的测试用一个"第三方包只出现在 Worker 里"的样例工程做真实构建，并用"Worker 不挂插件"作对照。

每项检查都是独立的模块：输入由调用方提供，规则是纯函数，所以能用样例做单元测试。每一条规则都至少有一个合规样例和一个违规样例，这就是门禁的自测。外部工具（pnpm、Vitest、Playwright）的输出先经 zod 校验结构；它们的真实输出保存成样例（`tools/fixtures/`），检查规则用真实样例测试（审查 R14：自测样例与真实输出不一致，是门禁漏报的共同原因）。

**lint 规则的自测**（`tools/src/lint/lint-rules.test.ts`）：规范里标为【自动】的 lint 规则逐条用违规代码确认生效，包括受限导入（静态、再导出、动态导入）、模块边界（跨元素、平台入口引用编辑器、经"无主"文件中转、只能引用公开入口）、TypeScript 文件的循环依赖、`any`、非空断言、`console`、`@ts-ignore`、悬空的 Promise、不完整的 `switch`、`import type`、`dangerouslySetInnerHTML`、无障碍、`.only`、跳过与占位的用例、文件名、没有警告级别。需要"被引用的目标"时，测试临时创建探针文件（已加入 `.gitignore`），用完删除。

### 3.4 故事对照

- 登记表 `tests/stories.json` 列出当前 M 的故事编号、状态（`planned` / `active`）、归属的 Phase 与验证方式（E2E、集成测试、门禁自测）。
- 检查规则：
  - M 总设计 §3 表格里的编号与登记表一一对应；
  - 状态为 `active` 的故事，至少有一个会执行的测试，它的 describe 或用例标题以故事编号开头；验证方式为 E2E 的，这个测试必须在 `tests/e2e/` 下。
- 测试清单取自 `vitest list` 与 `playwright test --list` 的输出，所以注释掉的、字符串里的"用例"不算，跳过或标为 fixme 的 E2E 也不算（审查 R8）。
- 每个 Phase 完成时，把它负责的故事改为 `active`。本 Phase 改 US-M1-11。

### 3.5 本机门禁与 CI

- **`pnpm verify`**（`tools/src/verify/`）按顺序执行：
  1. lint；
  2. 类型检查；
  3. 单元测试与覆盖率；
  4. 精确版本、包管理配置与故事对照；
  5. 集成测试（开发数据库没有启动时先启动）；
  6. 删除旧的构建产物，再构建：构建如果没有真正执行，后面的产物检查不能拿旧产物蒙混过关；
  7. 依赖、许可与产物检查；
  8. E2E（四个浏览器）。

  `--fast` 只执行前 4 步，供 pre-push 使用。本机缺少某个浏览器时，E2E 失败并提示安装方法，不静默跳过。
- **CI**（`.github/workflows/ci.yml`）：
  - 触发：推送 main、每周一次定时、手动触发；
  - 一个作业，在 `ubuntu-24.04` 上运行：PostgreSQL 18 服务容器；各个 Action 按提交的 SHA 锁定；`pnpm install --frozen-lockfile`；安装四个浏览器及其系统依赖；执行 `pnpm verify`，再做依赖漏洞扫描；
  - 总是上传 Playwright 报告与覆盖率：重试后通过的用例也要能查到报告；
  - 权限只读；有超时。

## 4. 测试策略

| 层级 | 覆盖内容 | 对应用户故事 |
