# M1-P2 服务端基础设施：架构设计与实施规划

> 状态：进行中｜日期：2026-09-26｜基于代码版本：`13e4e24`

## 1. 目标与范围

对应 M1 总设计 §5 的 P2 一行：后端骨架与横切能力就位，后面的模块只需接入。本 Phase 没有用户故事（M1 的故事从 P3 起交付）。验收以集成测试为主，覆盖以下几项（M1 总设计 §5 的验收一列）：
- 配置缺失时启动失败；
- 迁移从零执行；
- 审计写入；
- 错误响应格式；
- 优雅退出时在途请求正常完成。

- **范围内**：
  1. 验证 NestJS 12（纯 ESM）的工具链，建立后端骨架 `apps/api`；
  2. 配置：从环境变量读取并校验，机密可以用文件注入；
  3. 结构化日志、请求标识与脱敏；
  4. 错误码（放在 contracts）与统一的错误响应；
  5. HTTP 管线：
     - 安全响应头（含定稿的 CSP）；
     - 请求体上限，JSON 嵌套深度与数量的限制；
     - 服务器超时；
     - 输入校验管道；
  6. 数据库：
     - 连接池与超时、Drizzle；
     - 迁移与独立的迁移命令（advisory lock）；
     - 库结构版本检查；
     - "迁移只向前"的门禁；
  7. 审计事件（只追加）；
  8. 存活与就绪探针、优雅退出；
  9. 基于真实 PostgreSQL 的集成测试框架，每个测试文件使用独立的数据库；
  10. 后端的模块边界（ESLint）与 lint 自测；
  11. ADR：NestJS 12 的验证结论与后端工具链；PostgreSQL 与迁移策略；错误码与错误响应。
- **范围外**：
  - 账户、会话、CSRF 与 Origin 检查、登录限流（P3）；
  - 托管前端产物；CSP 随 HTML 与 Worker 脚本下发的 E2E 阳性对照（P3，US-M1-09）；
  - 文档与快照的接口，以及快照的请求体上限（P4）；
  - 容器、部署与反向代理（P5）；
  - 监控告警、CSP 违规报告的接收（M7）。

## 3. 设计

### 3.1 模块划分与依赖方向

```text
apps/api/
  package.json          @nerve-office/api（ESM）；导出 "." 指向 src/app/index.ts（源码条件）与 dist/app/index.js
  nest-cli.json         Nest CLI：tsc 构建与监听，入口 app/main；把 src/db/migrations 复制进 dist
  tsconfig.json         类型检查（含测试）；开启 experimentalDecorators 与 emitDecoratorMetadata
  tsconfig.build.json   构建：src → dist，不含测试
  drizzle.config.ts     drizzle-kit 生成迁移的配置（只在开发时使用）
  .env.development      本机开发的环境变量（只有开发库的账号，与 deploy/dev 相同）
  src/
    app/                应用的组装：根模块、HTTP 管线、优雅退出
      main.ts           进程入口：读配置 → 建应用 → 监听 → 接管信号与未捕获的异常
      index.ts          命令行与集成测试共用的程序接口
    shared/             各模块共用的内核：AppError、审计来源等纯代码
    modules/
      config/           读取并校验环境变量；api 里只有这里读 process.env
      logging/          根日志、请求日志与请求标识、脱敏、Nest 日志适配
      security/         安全响应头（含 CSP）、请求体解析与上限（P3 加 CSRF 与 Origin 检查）
      database/         连接池、Drizzle、迁移执行、库结构版本检查
      audit/            审计事件（只追加）
      health/           存活与就绪探针、应用的运行状态
    db/
      schema/<模块>/    各模块的表定义（index.ts），目录名与所属模块同名
      migrations/       drizzle-kit 生成、人工审阅后入库的 SQL 与 journal
    cli/
      migrate.ts        独立的迁移命令
```

**仓储放在各自的模块里，表定义与迁移放在 `src/db/`**。00 号计划书 §9.4 的草图写的是"src/db/ 下放 Schema、迁移与仓储"，这里做了调整，原因有两条：
- 仓储放在模块里，"一个模块的仓储只被这个模块使用"（规范 §1.2）由模块边界直接保证：仓储不从 `index.ts` 导出，别的模块引用不到。
- 表定义仍集中在 `src/db/schema/`，每个模块一个目录：drizzle-kit 用通配符 `src/db/schema/*/index.ts` 读取；外键要引用别的模块的表，所以表定义之间可以经 `index.ts` 互相引用；但一个模块只能引用与自己同名的表定义目录，别的模块的表读写不到。
- 进程入口 `main.ts` 放在 `app/` 里，表定义按目录划分：eslint-plugin-boundaries 7 的元素只能是目录，单个文件不能单独成为元素（S1 实施时调整）。

**元素与依赖方向**（eslint-plugin-boundaries，默认禁止；同一元素内部不受限制）：

| 元素 | 范围 | 可以引用 |
|---|---|---|
| `api-app` | `src/app`（含进程入口） | 各模块的入口、`api-shared`、contracts 的入口 |
| `api-module`（按模块名） | `src/modules/*` | 其他模块的入口（`index.ts`）、`api-shared`、contracts 的入口、与模块同名的 `api-schema` 的入口 |
| `api-shared` | `src/shared` | contracts 的入口 |
| `api-schema`（按模块名） | `src/db/schema/*` | 其他 `api-schema` 的入口（外键） |
| `api-cli` | `src/cli` | 各模块的入口 |
| `integration-tests` | `tests/integration` | contracts 的入口、`api-app` 的入口（`@nerve-office/api`） |

**按路径的导入与写法限制**（规范 §1.2、§5、§7）：

| 规则 | 范围 | 工具 |
|---|---|---|
| 只有 database 模块、各模块的 `*.repository.ts` 与表定义能引用 `drizzle-orm`、`pg` | `apps/api/src` | `no-restricted-imports` |
| 控制器不引用仓储 | `*.controller.ts` | `no-restricted-imports` |
| 只有 config 模块读取 `process.env` | `apps/api/src`，config 模块除外 | `node/no-process-env` |
| 控制器的 `@Body`、`@Query`、`@Param` 必须带 `schema`；不用 `@Req`、`@Res`，需要请求里的信息时写参数装饰器 | `*.controller.ts` | `no-restricted-syntax` |
| 不拼接 SQL：不用 `sql.raw`（迁移执行除外）；`query()` 的参数不能是带插值的模板字符串或字符串拼接 | `apps/api/src` | `no-restricted-syntax` |

每一条都在 lint 自测里加违规样例（ADR-003 的约定）。

### 3.2 应用的组装与请求管线

`src/app/index.ts` 对外提供 `createApplication(config, options)`，返回运行中的应用 `ApplicationRuntime`（`listen()` 返回监听地址，`shutdown(reason)`）。进程入口与集成测试都经它建应用，所以测试走的是与生产相同的管线。`options` 只有两项：
- 日志的输出（默认标准输出，测试传内存流）；
- 附加的模块（测试用来挂只在测试里存在的控制器，例如"慢请求"）。

NestJS 用 `bodyParser: false` 创建，`abortOnError: false`（初始化失败时抛出异常，由调用方处理，而不是直接退出进程）。管线的顺序由 `configureHttp()` 一次写定，都挂在 Express 上：

| 顺序 | 环节 | 说明 |
|---|---|---|
| 1 | Express 设置 | `trust proxy` 取自配置；关闭 `x-powered-by` |
| 2 | 请求日志与请求标识（pino-http） | 放在最前面：请求体解析失败、404 等所有响应都有日志与请求标识 |
| 3 | 请求上下文（AsyncLocalStorage） | 之后在这个请求里写的日志自动带上请求标识；退出过程中给响应加 `Connection: close` |
| 4 | 安全响应头 | 在任何响应之前写入，所以错误响应、404 也带着 |
| 5 | JSON 请求体解析与上限；嵌套深度与数量检查 | 失败时交给全局异常过滤器，得到统一的错误响应 |
| 6 | Nest 路由 | 全局前缀 `/api`；全局校验管道 `StandardSchemaValidationPipe`（失败时抛出 `REQUEST_INVALID`）；全局异常过滤器 |

### 3.3 配置

- 全部来自环境变量，变量名以 `NERVE_` 开头；机密也可以用文件注入：设置 `<变量>_FILE` 时读取文件内容，两者同时设置视为错误。
- 用 zod 校验。缺失、类型不对、超出范围、未知的 `NERVE_` 变量（多半是拼写错误）都会让启动失败：
  - 一次列出全部问题：变量名与原因，不输出取值（可能是机密）；
  - 日志的错误码为 `CONFIG_INVALID`，退出码为 1。
- 配置对象冻结后以注入标记 `APP_CONFIG` 提供，带类型。
- api 里只有 config 模块读取 `process.env`【自动】：
  - `loadConfig(env)` 是纯函数，便于测试；
  - `loadConfigFromEnvironment()` 读取 `process.env`。

| 变量 | 默认值 | 说明 |
|---|---|---|
| `NERVE_DATABASE_URL`（或 `_FILE`） | 必填 | PostgreSQL 连接串 |
| `NERVE_DATABASE_POOL_MAX` | 10 | 连接池上限 |
| `NERVE_DATABASE_CONNECT_TIMEOUT_MS` | 5000 | 建立连接、从池中取连接的等待上限 |
| `NERVE_DATABASE_STATEMENT_TIMEOUT_MS` | 15000 | 单条语句的执行上限 |
| `NERVE_DATABASE_LOCK_TIMEOUT_MS` | 5000 | 等锁的上限 |
| `NERVE_DATABASE_IDLE_IN_TRANSACTION_TIMEOUT_MS` | 10000 | 事务中空闲的上限 |
| `NERVE_MIGRATION_LOCK_TIMEOUT_MS` | 60000 | 迁移命令等待 advisory lock 的上限 |
| `NERVE_HTTP_HOST` / `NERVE_HTTP_PORT` | `0.0.0.0` / 3000 | 监听地址与端口；端口可以是 0（由系统分配，测试用） |
| `NERVE_HTTP_JSON_BODY_LIMIT_BYTES` | 262144（256 KiB） | JSON 请求体上限。快照接口在 P4 单独配置 |
| `NERVE_HTTP_REQUEST_TIMEOUT_MS` | 60000 | 接收完整请求的上限（Node 的 `requestTimeout`） |
| `NERVE_HTTP_HEADERS_TIMEOUT_MS` | 20000 | 接收请求头的上限 |
| `NERVE_HTTP_KEEP_ALIVE_TIMEOUT_MS` | 5000 | 空闲长连接的保持时间；P5 按反向代理的设置复核 |
| `NERVE_TRUST_PROXY` | 不信任 | 信任的反向代理，写法同 Express 的 `trust proxy`（跳数或地址列表）；影响客户端地址与是否 HTTPS 的判断 |
| `NERVE_SHUTDOWN_TIMEOUT_MS` | 8000 | 优雅退出的上限，要小于编排工具的停止等待时间（Docker 默认 10 秒） |
| `NERVE_LOG_LEVEL` | `info` | 日志级别 |

应用不读取 `NODE_ENV`，行为只由上面的配置决定。

### 3.4 日志与请求标识

- **格式**：JSON，每行一条，写到标准输出。字段：
  - `time`（ISO 8601）、`level`（文字）；
  - `requestId`；
  - 用户（P3 加入）；
  - 请求结束时的一条日志另有 `method`、`route`（路由模板，例如 `/api/health/live`）、`path`（不含查询串）、`statusCode`、`durationMs`。
- **不记录**：请求头、请求体、响应体、查询串。
- **级别**：5xx 记 `error`，4xx 记 `warn`，其他记 `info`；探针的成功请求不记录，免得刷屏。5xx 另记一条带异常与堆栈的 `error` 日志。
- **脱敏**：在 logger 层统一配置（pino 的 `redact`）。脱敏的键名集中在一个清单里（`password`、`token`、`cookie`、`authorization`、`secret`、`databaseUrl`、`snapshot` 等），覆盖两层嵌套。清单变更经审查，由测试验证【测试】。
- **请求标识**：
  - 接受请求头 `X-Request-Id`，取值只能是 1–128 个字母、数字或 `_.:-`，不合法时生成新的 UUID；
  - 写进响应头、日志与错误响应；
  - 审计记录它，作为来源的一部分。
- **实现**：
  - 根日志与 pino-http 由 logging 模块按配置创建，每个应用实例各一份，不用全局单例；
  - Nest 的内部日志经 `LoggerService` 适配写入同一个 pino：请求内写入该请求的子日志，请求外写入根日志；
  - 其他模块用 `@nestjs/common` 的 `Logger`。

### 3.5 错误码与错误响应

- **contracts**：
  - `ERROR_CODES` 集中登记每个错误码，内容是固定的 HTTP 状态与默认的中文说明；
  - `ErrorCode` 类型由它推导；
  - 退役的错误码列入 `RETIRED_ERROR_CODES`，不得复用。
- **唯一性**：错误码是同一个对象字面量的键，重复的键由 TypeScript（TS1117）与 ESLint（`no-dupe-keys`）拦下；单元测试检查写法、状态码范围、与退役清单不相交。这是规范 §2.3【自动（唯一性检查）】的实现方式。
- **P2 登记的错误码**：

| 错误码 | HTTP | 用途 |
|---|---|---|
| `REQUEST_INVALID` | 400 | 输入不合法：校验失败、请求体不是合法的 JSON |
| `NOT_FOUND` | 404 | 资源不存在。没有读取权限时同样返回它（规范 §4，P3 起使用） |
| `PAYLOAD_TOO_LARGE` | 413 | 请求体超过上限，或 JSON 的嵌套层数、元素数量超过上限 |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | 不支持的字符集或内容编码 |
| `INTERNAL_ERROR` | 500 | 意外错误：对外只返回通用说明与请求标识 |
| `SERVICE_UNAVAILABLE` | 503 | 未就绪、正在退出 |

- **api**：
  - 业务代码抛出 `AppError(code, message?)`，不抛字符串，不抛 Nest 的 `HttpException`；
  - 全局异常过滤器把所有异常映射为 `{ error: { code, message, requestId } }`，状态码取自登记表。映射规则：

| 来源 | 错误码 |
|---|---|
| `AppError` | 它自己的错误码 |
| 校验管道 | `REQUEST_INVALID`，说明里列出不合法的字段路径，不回显取值 |
| 请求体解析：不是合法的 JSON / 超过上限 / 字符集或编码不支持 | `REQUEST_INVALID` / `PAYLOAD_TOO_LARGE` / `UNSUPPORTED_MEDIA_TYPE` |
| 嵌套深度、元素数量超过上限 | `PAYLOAD_TOO_LARGE` |
| 没有匹配的路由（Nest 的 `NotFoundException`） | `NOT_FOUND` |
| 其他异常，包括其他 `HttpException` | `INTERNAL_ERROR`；异常与堆栈只写进日志 |

- 响应头 `Content-Type: application/json; charset=utf-8`；已经开始发送的响应无法改写，直接断开连接，并记日志。

### 3.6 安全响应头与请求限制

- **安全响应头**：对所有响应生效，包括错误响应与 404。

| 响应头 | 取值 | 说明 |
|---|---|---|
| `Content-Security-Policy` | `default-src 'self'; img-src 'self' data: blob:; connect-src 'self'; font-src 'self'; style-src 'self' 'unsafe-inline'; script-src 'self'; worker-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | M0 定稿（00 号计划书 §11.3）。测试逐字比对；放宽要先写 ADR |
| `X-Content-Type-Options` | `nosniff` | |
| `Referrer-Policy` | `no-referrer` | 文档地址不带给任何外部站点 |
| `X-Frame-Options` | `DENY` | 与 `frame-ancestors 'none'` 相同，照顾旧浏览器 |
| `Cross-Origin-Opener-Policy` | `same-origin` | |
| `Cross-Origin-Resource-Policy` | `same-origin` | |
| `Origin-Agent-Cluster` | `?1` | |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=()` | 剪贴板保持浏览器的默认（同源可用），编辑器需要 |
| `Strict-Transport-Security` | `max-age=31536000` | 只在 HTTPS 请求上下发（经 `trust proxy` 识别反向代理转发的 HTTPS）。不加 `includeSubDomains`：自部署时同一域名下可能还有别的服务 |
| `Cache-Control` | `no-store` | `/api/` 下的响应；P3 托管前端产物时，带哈希的静态资源另行设置 |

- **请求体**：
  - 只解析 JSON（`application/json` 与 `application/*+json`），上限取自配置；
  - 解析后检查嵌套深度（上限 32）与元素数量（对象的键加数组的项，上限 10000）。这两个上限是代码里的常量；快照在 P4 另有自己的校验（00 号计划书 §11.2）。
- **校验**：
  - 输入都经 contracts 里的 zod 结构校验，写法是 `@Body({ schema })`；
  - 全局的 `StandardSchemaValidationPipe` 执行校验，并去掉 `__proto__` 等原型键；
  - 没写 `schema` 的参数，lint 拦下（§3.1）。
- **服务器超时**：`requestTimeout`、`headersTimeout`、`keepAliveTimeout` 取自配置。处理时间的上限由数据库的语句超时、等锁超时与取连接的超时保证。不在应用层加"处理超时后先回错误"的拦截器：处理仍在后台继续，写操作可能已经提交，回错误反而会让客户端误判。

### 3.7 数据库与迁移

- **连接池**：pg `Pool`。连接参数：
  - `application_name = nerve-office-api`；
  - `statement_timeout`、`lock_timeout`、`idle_in_transaction_session_timeout` 取自配置；
  - 空闲连接 30 秒后回收。

  池上的错误（例如空闲连接被数据库断开）只记日志，不让进程退出。退出时，在 HTTP 请求排空之后关闭连接池（`onApplicationShutdown`）。
- **Drizzle**：
  - database 模块提供 Drizzle 实例（注入标记 `DATABASE`），以及执行器类型 `DbExecutor`（数据库或事务）；
  - 仓储的方法接受一个可选的执行器，默认用连接池。需要跨模块放进同一个事务的写入（例如 P4 的新建文档加审计），由调用方开启事务并把执行器传下去；显式传递，不靠隐式的上下文；
  - 规范 §5 的事务规则：显式事务、统一的加锁顺序、事务里不做网络调用、用数据库时间。由审查保证。
- **表的写法**（规范 §5）：
  - 表名用复数的 snake_case；主键用 PostgreSQL 18 内置的 `uuidv7()`（按时间递增，索引局部性好）；
  - 时间用 `timestamptz`；
  - 枚举用 `text` 加 CHECK 约束。
- **迁移的生成**：
  - `pnpm --filter @nerve-office/api db:generate --name <名称>`：由 drizzle-kit 按表定义生成 SQL；
  - 人工审阅后与 journal、快照一起入库。
- **迁移的执行**：`node dist/cli/migrate.js`。生产环境在启动应用之前，作为一次性任务运行；开发环境用 `pnpm db:migrate`，先构建再执行。执行步骤：
  1. 用一个独立的连接执行 `SET lock_timeout`，然后执行 `pg_advisory_lock(<固定键>)`；等不到锁就失败退出，提示"另一个迁移正在执行"。
  2. 比较库里已执行的迁移与这次带来的迁移：
     - 一致：不做任何事；
     - 库里是前缀：用 drizzle 的迁移器在一个事务里执行剩下的迁移；
     - 其他情况（库里的更多、哈希或时间戳对不上）：拒绝执行，退出码 1。
  3. 释放锁，关闭连接。
- **库结构版本检查**：
  - 纯函数 `compareMigrations(expected, applied)`，结果为"一致""待执行 N 个""不一致（原因）"；
  - 已执行的记录读自 drizzle 的迁移表（`drizzle.__drizzle_migrations`，沿用默认名，与 drizzle-kit 一致），应执行的由 `readMigrationFiles()` 读取；
  - 就绪探针与迁移命令共用这个函数。应用启动时只检查、只记日志，不自动迁移（M1 总设计 §6.2）；
  - 版本不一致时就绪探针失败。
- **迁移只向前**【自动】：新增门禁 `migrations`（`tools/src/gates/migrations.ts`），检查三件事：
  1. journal 与 SQL 文件一一对应；`idx` 连续；`when` 严格递增。
  2. 与基准版本比较：基准里的每个 SQL 文件、journal 条目与快照都没有变化；新条目只追加在末尾，时间戳大于基准的最后一条。
  3. 基准的取法：
     - 本机分支取与 `main` 的分叉点；
     - CI 上取 `HEAD^1`，即合并前的 main，CI 的检出要改为 `fetch-depth: 2`；
     - 取不到基准时失败，不静默通过。
- **迁移文件的位置**：`src/db/migrations/`。Nest CLI 构建时把它复制到 `dist/db/migrations/`；运行时按模块文件的相对位置查找，源码与产物的目录结构相同。

### 3.8 审计

- **contracts**：审计动作的枚举 `AUDIT_ACTIONS`，先登记 M1 要记录的全部动作（规范 §7）：
  - `auth.login_succeeded`、`auth.login_failed`、`auth.logout`；
  - `users.admin_initialized`；
  - `documents.created`。

  以后各 M 新增动作时，同时用迁移更新数据库的 CHECK 约束。
- **表 `audit_events`**（只追加）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid`，默认 `uuidv7()` | |
| `occurred_at` | `timestamptz`，默认 `now()` | 数据库时间 |
| `action` | `text` + CHECK | 取值同 contracts 的枚举 |
| `actor_type` / `actor_id` | `text` + CHECK（`user`、`system`、`anonymous`） / `uuid` | `actor_type = 'user'` 时必须有 `actor_id`，反之必须为空。不设外键：审计记录不随账户变化 |
| `target_type` / `target_id` | `text` + CHECK（`user`、`space`、`document`） / `uuid` | 两者同时为空或同时有值 |
| `source` | `text` + CHECK（`http`、`cli`） | 来源 |
| `request_id` / `client_ip` | `text` / `inet` | 来源为 `http` 时必须有请求标识；`client_ip` 只在来源为 `http` 时可以有值 |
| `details` | `jsonb`，默认 `{}` | 只放不敏感的补充信息，必须是对象，序列化后不超过 4 KiB。不含正文、密码与令牌（规范 §6） |

  索引：`occurred_at`；`(actor_id, occurred_at)`；`(target_type, target_id, occurred_at)`。后两个是部分索引，只收有值的行。
- **只追加由数据库保证**：`BEFORE UPDATE OR DELETE`（按行）与 `BEFORE TRUNCATE`（按语句）的触发器直接报错。代码写错也改不了审计记录。将来要按保留期清理时，另行设计受控的清理路径（M7）。
- **接口**：`AuditService.record(event, { executor? })`：
  - 事件的来源（`http` 带请求标识与客户端地址，`cli`）由调用方显式传入；控制器用参数装饰器取得；
  - 写入之前按 contracts 的结构校验。

### 3.9 健康检查与优雅退出

- **`GET /api/health/live`**：进程在运行就返回 200 `{ "status": "ok" }`，退出过程中也一样。
- **`GET /api/health/ready`**：以下三项都满足时返回 200 `{ "status": "ready" }`：
  - 应用在接收请求（没有在退出）；
  - 数据库连得上（`SELECT 1`）；
  - 库结构版本一致。

  否则返回 503，错误码 `SERVICE_UNAVAILABLE`，说明里写明哪一项不满足：正在退出、数据库不可达、待执行 N 个迁移、库结构不一致。检查语句在事务里用 `SET LOCAL statement_timeout = 2000`，探针不会长时间挂住。
- **优雅退出**（`ApplicationRuntime.shutdown`；收到 SIGTERM 或 SIGINT 时执行）：
  1. 标记为"正在退出"：就绪探针改回 503；之后的响应都带 `Connection: close`。
  2. `server.close()`：不再接受新连接，同时关闭空闲的长连接。
  3. 等待在途请求完成，最多等 `NERVE_SHUTDOWN_TIMEOUT_MS`。超时就强制断开剩下的连接（`closeAllConnections()`），记警告，结果记为"强制"。
  4. `app.close()`：执行各模块的关闭钩子，连接池在这里关闭。此时已经没有在途请求。
  5. 退出码：正常退出为 0，强制退出为 1。
  6. 再次收到信号时立即退出，退出码 1。
- **未捕获的异常与未处理的 Promise 拒绝**：记 `fatal` 日志后退出，退出码 1。

### 3.10 测试框架

- **Vitest 项目**：
  - api 的单元测试（`apps/api/src/**/*.test.ts`）放进已有的 `unit` 项目：Oxc 按 `apps/api/tsconfig.json` 输出装饰器元数据；`@nestjs/common` 会先加载 reflect-metadata，不需要单独的 setup 文件（ADR-004）；
  - node 环境的项目把源码条件写在 `ssr.resolve.conditions`：Vite 8 里顶层的 `resolve.conditions` 只作用于浏览器环境（S1 发现，P1 的 node 测试没有按包名引用过工作区的包）；
  - `integration` 新增两类辅助：
    - 应用：`startTestApp()` 经 `@nerve-office/api` 的 `createApplication()` 建应用，监听随机端口，日志写进内存，可以挂只在测试里存在的控制器；
    - 进程：用构建产物 `node apps/api/dist/app/main.js` 启动真实进程，验证启动失败与信号处理。
- **每个测试文件使用独立的数据库**（规范 §8.1）：
  - 模板库按迁移文件的哈希命名：`nerve_it_tpl_<哈希前 12 位>`。第一个需要它的测试文件在 advisory lock 下创建并执行迁移，之后的运行直接复用；创建时顺带删除其他哈希的旧模板。
  - 测试文件在 `beforeAll` 里用 `CREATE DATABASE … TEMPLATE` 复制一份，名为 `nerve_it_<进程号>_<随机串>`；在 `afterAll` 里 `DROP DATABASE … WITH (FORCE)`。
  - "迁移从零执行"一类的测试用空库。
  - 测试里应用的连接池上限设为 4，免得并行的测试文件把 PostgreSQL 默认的 100 个连接用完。
  - 不在全局准备步骤里建库：`vitest list`（故事对照）不需要数据库。
- **脚本与门禁**：
  - `pnpm test`：`unit`（含 api）与 `unit-web`，不带覆盖率，供 pre-push 使用；
  - `pnpm test:integration`：先构建 api 及其依赖（进程测试用构建产物），再跑 `integration`；
  - `pnpm test:coverage`：同样先构建，再把全部项目合在一起统计覆盖率（规范 §8.3 的"单元与集成测试合计"），需要数据库。新增 `apps/api/src/**` 下限 80%，不计 `app/main.ts` 与 `cli/`（入口只做组装，由进程测试覆盖，子进程不统计覆盖率）；
  - `pnpm verify`：
    - 快速模式：lint、类型检查、单元测试（`pnpm test`）、静态检查；
    - 完整模式：lint、类型检查、静态检查、启动数据库（本机）、全部测试与覆盖率（`pnpm test:coverage`）、清理、构建、依赖与产物检查、E2E；CI 另加漏洞扫描。
    - 单元测试已包含在覆盖率那一步里，完整模式不再单独执行。

| drizzle-kit 读取带 `.ts` 扩展名导入的表定义 | S3 核实；不行就让表定义文件之间的引用只经 `index.ts` 汇总 |
| 进程测试依赖构建产物 | `test:integration`、`test:coverage` 先构建 api；构建只需几秒 |
| 不用 nestjs-pino，自己写 Nest 日志适配 | 适配约百行，有单元测试；日志字段与脱敏由集成测试验证 |
| 并行的测试文件同时创建模板库 | 创建模板在 advisory lock 下进行；模板按迁移的哈希命名，迁移不变时直接复用 |
| 集成测试的连接数 | 测试里应用的连接池上限为 4；PostgreSQL 默认 100 个连接 |
