## 与设计的偏差

| 偏差 | 原因 | 是否已回写 |
|---|---|---|
| 不用 nestjs-pino，直接用 pino 与 pino-http，另写一层 Nest 日志适配 | nestjs-pino 5 在进程里保留唯一的 pino-http 实例，中间件的顺序也不能自己定 | M1 总设计 §2.2 与变更记录、ADR-002、ADR-004 |
| Nest CLI 用 12.0.5 | 12.0.7 发布不满 3 天 | 同上 |
| 仓储放在各自的模块里，`src/db/` 只放表定义与迁移 | "一个模块的仓储只被这个模块使用"由模块边界直接保证 | P2 设计 §3.1、M1 总设计 §6.1 与变更记录 |
| 进程入口放在 `src/app/main.ts`，表定义按模块分目录 | eslint-plugin-boundaries 7 的元素只能是目录 | P2 设计 §3.1、ADR-003、ADR-004 |
| config 模块从 S2 提前到 S1 | 进程入口离不开它 | P2 设计 §6、计划 |
| api 的单元测试并入 `unit` 项目，不单建 `unit-api` | `@nestjs/common` 会先加载 reflect-metadata，不需要单独的 setup 文件 | P2 设计 §3.10、ADR-004 |
| Vitest 的 node 项目把源码条件写在 `ssr.resolve.conditions` | Vite 8 里顶层的 `resolve.conditions` 只作用于浏览器环境（P1 没有暴露） | P2 设计 §3.10、ADR-004 |
| 应用代码用注入的 `AppLogger`，不用 Nest 的 `Logger` | Nest 的 `Logger` 经进程级的静态实例转发，同一个进程里后建的应用会接管先建的应用的日志（S2 的集成测试发现） | P2 设计 §3.4 |
| 服务开事务用 `TransactionRunner`，拿到不透明的 `Transaction` | 审查 B2：服务不应拿到查询数据库的能力 | P2 设计 §3.1、§3.7，ADR-005 |
| 覆盖率改为单元与集成测试合在一起统计；`verify` 完整模式合并为一步 | 规范 §8.3 的"单元与集成测试合计" | P2 设计 §3.10、架构总览 |
| 规范 §5"已发布迁移的校验和"改为"与合并前的版本比较" | 入库的校验和清单会被一起改掉，以 git 里的基准版本为准 | 规范修订记录、ADR-005 |
| 审计的枚举与 details 上限放在 contracts | 表定义与 audit 模块都要用；表定义只有仓储能引用 | P2 设计 §3.8 |
| `TransactionRunner` 自己借出、归还连接，不用 drizzle 在连接池上的 `transaction()`；work 吞掉失败的语句时报错 | drizzle 0.45.3 在 `BEGIN` 失败时不归还连接，归还时也不带错误，未结束的事务会被下一个事务一起提交（复验 N8、G3） | P2 设计 §3.7、ADR-005 |
| 后端不用动态导入，相对引用写 `.ts`，Nest 只从包的入口引用 | 按路径与包名生效的 lint 限制只认得一种写法（复验 F2、F3） | P2 设计 §3.1、ADR-003 |

## 下一个 Phase 须知

**新增一个后端模块**（P3 的 auth、users、spaces，P4 的 documents）：
1. 目录 `apps/api/src/modules/<模块>/`，对外只经 `index.ts`；表定义放在 `apps/api/src/db/schema/<模块>/index.ts`，目录名与模块同名。
2. 表定义写好后执行 `pnpm db:generate --name <名称>`，审阅生成的 SQL 后与代码一起提交；触发器等写 `--custom` 迁移。门禁 `schema` 会在表定义改了却没生成迁移时失败；`migrations` 保证已合并的迁移不再修改。
3. 只有仓储（`*.repository.ts`）访问数据库：注入 `DATABASE`，用 `executorOf(db, transaction)` 执行；服务需要事务时用 `TransactionRunner.run()`，把拿到的 `Transaction` 传给仓储，事务里需要别的服务参与时把它传下去，不在 `run()` 里再调用 `run()`（会再借一个连接，连接池满时互相等待）。业务上的失败抛 `AppError`，连接照常放回；其他失败会丢弃这个连接。事务里预期会失败的语句（例如把唯一冲突当作"已存在"）要放进保存点（仓储里 `executorOf(...).transaction()`），或者改用 `ON CONFLICT`：work 吞掉失败的语句正常返回时，`run()` 会报错（事务已中止，提交不了）。枚举用 `text` 加 CHECK 约束，取值放在 contracts。
4. 控制器写在 `*.controller.ts`：输入写 `@Body({ schema })`、`@Query({ schema })`、`@Param('id', { schema })`，结构放在 contracts；需要请求里的其他信息时写参数装饰器（参考 `audit/request-origin.ts`），不用 `@Req`、`@Headers`、`@UploadedFile` 等。
5. 业务错误抛 `AppError`；新的错误码先登记在 contracts 的 `ERROR_CODES`（状态码固定）。
6. 日志注入 `AppLogger`，写法 `logger.info('消息', { 字段 })`；敏感字段的键名要在 `REDACTED_KEYS` 里。
7. 审计：模块导入 `AuditModule`，`AuditService.record(event, { transaction })`；控制器用 `@RequestOrigin()` 取来源；新的审计动作先加进 contracts 的 `AUDIT_ACTIONS`，再生成迁移更新 CHECK 约束。
8. lint 会拦下违反上面约定的写法；在 `tools/src/lint/lint-rules.test.ts` 里给新增的规则补违规样例（ADR-003）。后端不用动态导入，相对引用写 `.ts`，Nest 只从包的入口引用：这些限制保证按路径与包名的规则认得出每一种引用。
9. 集成测试用 `createTestDatabase()` 建自己的库，`startTestApp({ databaseUrl })` 启动应用；需要只在测试里存在的控制器时，用 `additionalModules` 挂上，并导入它依赖的模块（例如 `DatabaseModule`、`AuditModule`）。

**给 P3 的备注**：
- CSP 已随所有接口响应下发（`security/security-headers.ts`，与 M0 定稿逐字一致）；P3 托管前端产物时，HTML 与 Worker 脚本同样经过这条管线，带哈希的静态资源另行设置 `Cache-Control`（默认是 `no-store`）。
- 状态变更接口的 CSRF 与 Origin 检查、登录限流、会话 Cookie 在 P3；请求日志里的"用户"字段在有会话后加入（`requestSummary` 或请求上下文）。
- `trust proxy` 与 HSTS 已就位：P3 的 E2E 走 HTTPS 时，要按反向代理的地址配置 `NERVE_TRUST_PROXY`。
- **退出时的在途计数不含守卫与中间件**（复验 N7）：处理器从全局拦截器开始计入，守卫与中间件在它之前执行。会话守卫查数据库时，客户端断开后守卫可能还占着连接；关闭连接池时 `pool.end()` 会等它归还，整体受 `NERVE_SHUTDOWN_TIMEOUT_MS` 约束，不会无限等待。守卫里的数据库访问要短（一次按主键的查询），不要在守卫里做长事务。这样的请求如果在连接池关闭之后才拿连接，会得到错误，日志里记为"请求中断之后处理失败"，属于退出过程中的正常现象（复验 F8）。

**给 P4 的备注**：快照接口的请求体另用自己的解析器与上限（通用的 JSON 解析器上限是 256 KiB，嵌套 32 层、元素 1 万个）；新建文档与审计放在同一个事务里（`TransactionRunner`）。

**给 P5 的备注**：
- **就绪与滚动发布**（审查 A16）：数据库比应用新时，目前判为不就绪，与"扩展 → 迁移 → 收缩"的滚动发布不兼容；单实例首发时影响不大，部署形态定下后再决定。开始退出时立即停止接收新连接，编排工具实际看不到"就绪 503"；需要的话在停止接收之前留一段"只让就绪失败"的时间（preStop）。
- **就绪的说明**：503 的说明里有迁移名与原因，只应在内网可达；Caddy 不对外转发 `/api/health/*`，或只转发存活探针。
- **数据库角色**（审查 A21）：开发库的 `nerve` 是超级用户。生产上迁移用表的所有者，应用用只有必要权限的角色，否则只追加的触发器可以被绕过（`ALTER TABLE … DISABLE TRIGGER`）。这是审计只追加的前提，已写进 P2 设计 §3.8 与 ADR-005。
- `NERVE_SHUTDOWN_TIMEOUT_MS`（默认 8 秒）要小于编排工具的停止等待时间；`NERVE_HTTP_KEEP_ALIVE_TIMEOUT_MS` 按反向代理的空闲连接设置复核。
- 迁移作为一次性任务在启动应用之前执行：`node dist/cli/migrate.js`，镜像里要带上 `dist/db/migrations`（Nest CLI 构建时已复制）与 contracts 的构建产物。
- 服务端依赖的第三方许可清单随镜像生成（前端的已由构建插件生成）。

**已知的坑**：
- `pnpm install` 在锁文件没变时不会重新执行 `prepare`，合并后在主目录执行 `pnpm run prepare` 重装钩子（钩子脚本另有按仓库根目录找 lefthook 的兜底）。
- pino-http 建的子日志会覆盖根日志的序列化：给它传完整的 `serializers`，并关闭 `wrapSerializers`，否则异常的序列化被绕过，或者每个请求都 500。
- drizzle-kit 用自己的加载器读表定义：运行时要加 `--conditions=@nerve-office/source`；`--out` 只接受相对路径。
- 改列名、改表名时，drizzle-kit 要交互确认"新建还是改名"：在终端里执行 `pnpm db:generate --name <名称>` 并按提示选择。非交互的环境里它只报错、不生成文件，门禁 `schema` 会因此失败（复验 N1）。
- 后端禁止动态导入：测试里确实需要 `vi.resetModules()` 加 `import()` 时，写带理由的 `eslint-disable-next-line`，经审查。
- 进程测试用构建产物；直接运行 vitest 时先构建（`pnpm test:integration` 会自动构建），产物比源码旧时测试辅助会直接报错。
- `@nestjs/common` 与 `@nestjs/core` 会先加载 reflect-metadata；装饰器元数据由 Vite 的 Oxc 按 tsconfig 输出，tsconfig 里要开 `experimentalDecorators` 与 `emitDecoratorMetadata`（集成测试的 tsconfig 同样要开）。
