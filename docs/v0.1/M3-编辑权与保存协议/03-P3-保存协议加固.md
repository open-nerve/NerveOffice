# M3-P3 保存协议加固：架构设计与实施规划

> 状态：进行中｜日期：2026-10-05｜所属：M3-P3｜依据：M3 总设计 §2.1 第 3 条与细化（DEF-021、"公式待更新"）、§5（P3 一行）、§6.3；00 号计划书 §7.4、§8.1、§8.2、§8.4、§8.7、§11.2、§11.3（r15）；P2 交接单的"P3 须知"｜基于代码版本：`a4f966f`（main `b0f7527` 之后补记 CI）

## 1. 目标与范围

服务端对每一次写入（保存、另存为副本）做完整的快照校验；内容没变时不增加修订号；数据格式过旧的页面写不进来。

- **完整的快照校验**（计划书 §11.2、§8.2）：容量、嵌套与数量、结构、资源（名称唯一、白名单、必须为空、已知资源的结构、不缩水）、图片地址（只接受平台地址）、链接地址（合法且等于规范写法）。另存为副本同样适用。拒绝时给出机器可读的规则。
- **链接地址的判定**（计划书 §11.3）放进 contracts，前后端共用；页面在写入之前把自动识别出的链接改成规范写法，不合法的去掉链接、保留文字（DEF-021），覆盖键入、各种粘贴、编辑栏与 `HYPERLINK()` 公式的结果。
- **规范化的内容哈希**与"内容相同不递增"；不递增的确认同样留下回执，重试照样拿到原来的结果（A07）。
- **平台信封**（§8.1）：内容哈希、客户端构建版本、客户端上报并核对过的 SDK 版本。
- **拦截旧客户端**（总设计 §2.1 第 3 条）：页面在保存、另存为副本、申请编辑权与心跳时上报构建与数据格式；数据格式不同或构建低于运维开关时 `CLIENT_OUTDATED`，页面说明"需要刷新"；回滚之后文档比服务端新时 `DOCUMENT_TOO_NEW`，页面只能阅读。
- **"公式待更新"的服务端记录**（P4 据此强制重算与说明）。
- **修订记录与回执保留 30 天**（应用内的定时任务）。
- **DEF-018**：快照的检查放进工作线程，限并发与内存；专门的测量，结论写进 ADR-001 与延期登记。
- **快照达到容量的 80% 时页面提示**（US-M3-14）。
- P2 登记的 DEF-046（复制、移动时目标空间的子文件夹第一次就没取到没有"重试"）、DEF-047（登录页的初始焦点）。

用户故事：US-M3-14（服务端拒绝不合格的快照）、US-M3-16（旧版页面不能把文档写回旧格式）；P3 结束时改为 active。

**不在本 Phase**：自动保存、打开自检（P4）；"公式待更新"之后的自动补存、进入编辑时的强制重算与阅读者的说明（P4）；插入链接的入口、命令守卫与粘贴清洗（M5）；文字文档的规则（M6）；图片上传与引用关系（M5——P3 之后任何图片地址都还不是平台地址，表格里的图片一律存不进去，与计划书 §11.3"`data:` 图片也不再接受"一致）。

## 2. 现状（`a4f966f`）

两路设计前的探索（2026-10-05）给出的事实：

- **保存的顺序**（`document-content.service.ts:100-145`）：基本校验 → 负载摘要 → 事务（访问 → 能编辑时锁文档行 → 重放 → 登录 → 能编辑 → 租约 → `unitId` → 基准修订号 → 写入）。**校验排在重放之前**，与总设计 §6.3、计划书 §7.4 第 2 步"重放先于其余检查，包括快照校验与拦截旧客户端"不符；另存为副本同样（`document-conflict-copy.service.ts:66-73`）。
- **基本校验**（`snapshot-validation.ts`）只有 7 项：UTF-8、JSON、顶层是对象、`id`、`sheetOrder` 是数组、`sheets` 是对象、外层嵌套 64 层；没有数量上限、资源、链接与图片，资源 `data` 里的 JSON 不在深度检查之内。失败一律 `SNAPSHOT_INVALID`，没有 `details`。
- **服务端没有插件档案的资源清单**：`sheet@1` 的资源只在 `apps/web/src/editor/profile/sheet-profile.ts`（引用 Univer，后端用不了）与模板数据里；"必须为空"的清单在代码里没有。M0 的规则与样本在 `M0-技术验证/reports/插件档案v1.md`、P2 报告 §3.3 与 `spikes/m0/src/harness/resource-guard.ts`。
- **链接在表格快照里只在单元格的富文本**：`cell.p.body.customRanges[i]`（`rangeType: 0`、`properties.url`），没有链接资源。自动识别有五条路径，写出的地址多数不是规范写法（键入：`normalizeUrl` 的结果，邮箱写成 `mailto://`、`ftp://` 照样识别；选中单元格粘贴纯文本：原文，例如 `example.org`；单元格编辑器里粘贴：整段文字；粘贴带 `<a>` 的 HTML：相对地址原样；编辑栏：按页面地址解析），另有**第六条：`HYPERLINK()` 公式的结果**（`hyperlink-engine-formula.service.ts`），每次重算还生成新的随机 `rangeId`。五条路径与公式结果都汇合到 `sheet.mutation.set-range-values` 的 `cellValue[r][c].p.body.customRanges`；Facade 的 `BeforeCommandExecute` 交出的参数就是处理器与撤销栈用的同一个对象，就地改写在三个浏览器上实测有效、不多产生 mutation、撤销重做之后仍是改写后的写法（探索 B 的探针）。现在的服务端照样保存不规范的地址（`template.spec.ts:57-88` 锁定了这个行为）。
- **地址解析跨引擎**：36 个地址里只有路径中的 `|` 不同（Chromium、Chrome 编成 `%7C`，Node 与 WebKit 保留）；单引号四处都不编码（计划书 §11.3 说"引号都被百分号编码"只对双引号成立）。审查 B 的逐字符扫描另发现：主机里的空白与 `*`、`mailto` 在 `?` 之前的空格，Chromium 内核与 Node、WebKit 不同，双引号等在主机与 `mailto` 里四个引擎都原样保留——审查之后的收紧见 §3.2。
- **内容哈希**：没有。M0 的规范化原型（`spikes/m0/src/harness/content-compare.ts`）与 `apps/web/src/editor/testing/content-compare.ts` 对空资源的处理不同（前者保留 `{name, data: null}`，后者去掉）。M0 原型"按键排序"实际得到的是 JS 的属性顺序（整数形式的键按数值升序在前，其余按 UTF-16 字典序），按纯字典序重写哈希就不同。
- **信封**：`documents` 有 `type`、`profile`、`format_version`、`sdk_version`（写服务端常量）、`revision`、`write_epoch`；`document_contents` 有 `snapshot`、`raw_bytes`、`stored_bytes`；`document_revisions` 有 `request_id`（唯一）、`payload_digest`、来源与保存人。没有内容哈希、客户端构建版本、"公式待更新"。
- **客户端构建版本不存在**：Vite 没有 `define`，各包版本都是 `0.1.0`；镜像的 `VERSION`、`REVISION` 只在运行阶段写进标签，构建阶段拿不到，镜像里没有 `.git`。
- **"公式待更新"**：前端已有（`save-coordinator.ts` 的 `formulasPending = !capture.settled`），请求里不带，服务端不记。
- **修订记录**：没有保留期，`document_revisions(created_at)` 没有索引；应用内的定时任务有现成的写法（ADR-016 的回收站清理）。
- **DEF-018**（探索 A 的本机实测）：5 MiB 真实形状的快照，解压、解析、遍历、规范化加 SHA-256 约 134 ms（规范化 84 ms），堆上临时多约 80 MiB；恶意形状 0.3–0.7 s、堆增长可到 357 MiB；全在主线程时事件循环最长延迟约 120 ms，放进工作线程约 2 ms。`JSON.stringify` 与递归的遍历在约 5,000–10,000 层就抛 `RangeError`（`JSON.parse` 是迭代的，200 万层照样解析）。
- **测试资产**：只读样本 `tests/e2e/support/read-only-sample.json` 的两张图片是 `data:` 地址——直接写库的只读用例不受影响，但经保存接口存它的三处（页面自检的 enter-exit 场景、`update:read-only-sample`、实测的 `measure-scene.ts`）P3 之后会被拒；"内容相同不递增"让 `template.spec.ts` 的模板收敛、`reopen.spec.ts` 的再保存与两个更新工具的"存到稳定"失去依据。
- **迁移的整体核对**（`migrations-with-data.test.ts` 的 BASES）停在 0021：P1（0022）、P2（0023）都漏加了（ADR-005 约定每个 Phase 结束时加最后一个迁移）。
- **P2 的交接**：DEF-046、DEF-047 在 P3 开工时补上；完整校验接到另存为副本；304 的实现依赖 Nest 12 发送响应时不重设状态码。

## 3. 设计

### 3.1 写入的处理顺序（保存与另存为副本）

守一条原则：**同一次写入的重放先于其余一切检查**（计划书 §7.4 第 2 步、总设计 §6.3）。

1. **读取正文**（不变）：认证与 CSRF 之后；压缩前后都限 5 MiB；只接受单个完整的 gzip 成员。
2. **重放预检**（事务之外，不解析快照）：按 `requestId` 查修订记录与回执（§3.7）；同一个人、同一份文档、负载摘要一致、仍能访问，就返回原来的结果；其余情况（没有、不一致、看不到）**一律往下走，不提前回答**——看不到与不存在、另一份文档的 `requestId` 都留给事务里的再查（语句序列与现在相同，"看不到与不存在"的核对照旧）。
3. **客户端的数据格式**（与文档无关的一半，§3.5）：上报的 Univer 版本、插件档案、平台格式版本等于服务端的，构建不低于运维开关；否则 `CLIENT_OUTDATED`。新字段在契约里是可选的（旧页面重试一次结果未知的写入时，在查询校验就得到 400、到不了重放，A07 就破了），缺字段按过旧处理。
4. **快照的检查**（与文档无关的规则，§3.3；在子进程里，限并发，每个账户至多 2 份）：不合格就 `SNAPSHOT_INVALID`，`details.rule` 是规则的标识；通过时得到规范化的内容哈希与非空资源的名称。
5. **事务**（沿用 ADR-011 的加锁顺序与锁下复核）：**`requestId` 的锁**（事务的第一把锁，审查 A3）→ 访问 → 锁文档行、锁下复核 → **再查一次重放**（并发的同一个 `requestId`，查修订记录与回执两张表）→ 登录仍有效 → 文档的数据格式（文档记录的 SDK 版本高于服务端的：`DOCUMENT_TOO_NEW`，§3.5）→ 能编辑 → 租约 → 基准修订号 → `unitId` → **不缩水**（上一版非空的资源这一版都在，§3.3）→ **内容哈希与当前相同**：只写回执，"公式待更新"只清不设，修订号不变（§3.7、§3.8）→ 否则写内容（连同哈希与非空资源的名称）、修订号加一、写修订记录（含哈希与客户端构建）、更新文档的信封（SDK 版本、客户端构建、"公式待更新"）、审计。

`unitId` 移到基准修订号之后（总设计 §6.3 的顺序）：落后的页面先得到冲突，冲突的说明照旧只给持有租约的页面。另存为副本走第 1–4 步，事务照现在的锁（P2；第一把是 `requestId` 的锁，回执用过的 `requestId` 回 `REQUEST_ID_CONFLICT`），锁下的判断之后核对 `unitId`、写入哈希与信封（档案、格式版本与信封取核对过的页面的值，审查 A7）；它不做"不缩水"与"内容相同"（新文档）。新建（模板）与复制（`INSERT … SELECT`）一并写入哈希与非空资源名（模板的在启动时算一次，复制原样带过去）。

响应：保存的确认加上 `unchanged`（内容相同、修订号没变时为真，`savedAt` 取当前修订的时间）。

### 3.2 contracts 里的共享判定（前后端共用、纯函数、不依赖 Univer）

- **插件档案的资源规则**（`documents/profile-resources.ts`）：`sheet@1` 的白名单（10 项）、必须为空的 4 项（区域保护、工作表保护、保护点、区域主题）、已知资源的最小结构（`data` 是空串或 JSON，顶层是对象，每个工作表键下的值是这类资源该有的种类——数组或对象）。"空"按**深层为空**判断（`null`、`""`、`{}`、`[]`，或者每一层都为空：规则删光之后的区域保护是 `{sheetId: []}`，不能误拒）。逐字段的结构不做（没有证据支撑时误拒的风险高）。web 的插件档案改为引用这份数据，单元测试核对两边一致（档案注册的插件声明的资源 = 白名单）。
- **链接地址的判定**（`documents/link-address.ts`，计划书 §11.3 的细化）：
  - 只允许 `http`、`https`、`mailto`；含控制字符（C0 与 DEL）一律拒绝（不先删掉再判断）；首尾空白先去掉（规范写法里没有）；长度上限 2,048；
  - `http(s)`：取 WHATWG URL 的 `href`，路径与查询里的 `|` 统一编成 `%7C`（跨引擎一致）；带用户名或密码的拒绝；主机按 IDN 转成 punycode（URL 本身就做）；
  - **审查之后收紧到各引擎必然一致的部分**（审查 B1、B2）：`http(s)` 的主机只收 LDH 标签（另放 `_`）、点与 IPv4，不收 IPv6（原因 `host`）；规范写法里空白、双引号、尖括号、反引号与 `|` 一律编码，查询里的单引号编成 `%27`，`mailto` 先编码再比较——规范写法里不出现能改写剪贴板 HTML 结构的字符；
  - `mailto`：只接受没有主机部分的写法 `mailto:x@y`（SDK 键入邮箱写出的 `mailto://x@y` 由客户端改写）；
  - 本站相对地址 `/…`：按占位的站点源解析，主机必须不变（`//host`、`/\host` 换了主机，拒绝），规范写法是解析后的路径、查询与片段；
  - 文档内锚点 `#…`：不含空白、引号、尖括号与反引号；
  - 没有协议、也不以 `/` 开头的写法（`example.org`）不合法。
  - 两个入口：`canonicalLink(url)` → 规范写法或不合法的原因；`normalizeCellLinks(p)`（客户端改写用）：`mailto://` 修成 `mailto:`，地址不合法、但它覆盖的文字本身是合法的绝对地址时改用这段文字（计划书 §11.3 粘贴清洗的同一条），仍不合法就去掉这一段链接、保留文字；`rangeId` 不符合 `^[A-Za-z0-9_-]{1,64}$` 的换掉（SDK 复制链接时不转义它，计划书 §11.3）。`checkCellLinks(p)`（服务端用）只判定不改写。
  - 跨引擎的测试数据：同一组用例在 Node 的单元测试与三个浏览器的 E2E 里都跑，要求结果是两边的不动点；审查之后另有性质检验（审查 B4）：逐字符扫描与随机拼接的地址在每个浏览器里判定，浏览器判为合法的规范写法交给 Node 再判，要求合法且相等。
- **平台图片地址**（`documents/asset-address.ts`）：`/api/assets/{uuid}`，从 `apps/web/src/editor/image-function/platform-asset.ts` 移来，`IMAGE()` 的限制与服务端的图片规则共用。
- **规范化的内容**（`documents/content-canonical.ts`）：`canonicalContentText(snapshot)`：以 JSON 文本为准；去掉视图状态（工作表的 `zoomRatio`、`scrollTop`、`scrollLeft`；文字文档的 `settings.zoomRatio` 留给 M6）；资源的 `data` 解析一次，深层为空的资源去掉（与 `testing/content-compare.ts` 一致：资源"在而为空"与"不在"等价，"不在"的风险由不缩水兜住），非空的、`data` 是对象的只在第一层去掉取值深层为空的键（更深的空值是内容，审查 A5），按名称排序；对象的键序**写死为**"规范的数组下标形式的键（`0`–`4294967294`）按数值升序在前，其余按 UTF-16 码元字典序"（M0 原型实际得到的顺序；客户端在 M4 要逐字节复现）；数字、重复的键、`__proto__`、孤立的代理项按 `JSON.parse`/`JSON.stringify` 的语义。哈希是这段文字的 UTF-8 字节的 SHA-256（各端用自己的实现）。单元测试带测试向量（M0 的 S0 与 S1 得到同一个哈希、键序的边界、空值等价）。ADR-011 写进这份规格。
- **常量与契约**：`SNAPSHOT_WARN_RAW_BYTES`（容量的 80%）；客户端构建的写法（`x.y.z`，可带 `+诊断信息`，比较时忽略）与比较函数；保存、另存为副本的查询参数与申请、心跳的请求体加上 `clientBuild`、`univerVersion`、`profile`、`formatVersion`（可选），保存与副本加 `formulasPending`（可选，缺省为否）；保存的响应加 `unchanged`；文档详情加 `sdkVersion` 与 `formulasPending`，编辑状态与申请的响应加 `formulasPending`；新错误码 `CLIENT_OUTDATED`（409，`details.reason`：`format`、`build`）、`DOCUMENT_TOO_NEW`（409）；`SNAPSHOT_INVALID` 的 `details.rule`（宽松解析）。

### 3.3 服务端的快照检查（DEF-018）

- **规则**（与文档无关，按档案组织，每条一个标识）：
  - 容量与压缩炸弹（读取时已有）；
  - 嵌套：外层与资源 `data` 里的 JSON **累加**不超过 64 层；元素数量上限 150 万（真实形状的 5 MiB 约 61 万；只挡最极端的形状，真正的手段是下面的线程与并发）；
  - 结构：顶层是对象、`id` 是非空字符串；`sheetOrder` 是字符串数组、每一项都是 `sheets` 的键；`sheets` 的值是对象（这两条用 M0 的样本、模板与 E2E 产出的快照核实不会误拒，误拒就去掉）；
  - 资源：数组、每项 `{name, data}`、名称唯一、名称在白名单内、必须为空的为空、已知资源的最小结构；
  - 图片地址：任何深度上名为 `source` 的字段都是平台地址（§11.2；M5 之前没有合法的图片地址）；
  - 链接：地址提取器扫描每张表每个单元格 `p.body.customRanges` 里的链接，合法且等于规范写法、`rangeId` 符合写法（`backgroundImage.source`、`p.drawings`、`SHEET_DRAWING_PLUGIN` 归图片规则）。
  - 与文档有关的（事务里）：`unitId`；不缩水——上一版的非空资源名（存在 `document_contents`，存量为空时解析上一版得到）里、在白名单之内的，这一版都在（存量里白名单之外的资源，例如 M1 去掉的 AuthzIoMock，不算缩水）。
- **执行**（S3 之后按需求方 2026-10-05 的决定改为**子进程**，见下一条）：`SnapshotInspector`（documents）把解压后的字节交给工作线程池（`worker_threads`，默认 2 个，配置可调）：解码、解析、规则、规范化、SHA-256 都在工作线程里，只回传结果（是否通过、规则、哈希、非空资源名）；`resourceLimits` 限住单个线程的堆，超限的任务按"快照过于复杂"拒绝（`SNAPSHOT_INVALID`，规则 `too-complex`）、线程重建；排队有上限（满了 503 `SERVICE_UNAVAILABLE` 带 `Retry-After`，与数据库繁忙同一个做法）、每个任务有时限。工作线程的入口要在源码运行（单元测试）、`nest build` 的产物（集成测试、E2E）与容器三种情况下都能加载——做不到时停下来报告，不退回主线程。
- **改用子进程（需求方 2026-10-05 决定）**：S3 实测发现工作线程的 `resourceLimits` 不是可靠的隔离边界——线程在 V8 的内置函数里（`JSON.parse` 正在建对象、对大字典取键）撞上堆上限时，整个进程以 SIGABRT 退出（macOS 与 Linux 容器一致），"超限只结束线程"的前提只在堆上限远高于输入的实际需要时成立。补救：解析之前先按文字数嵌套与元素（外层与资源 `data` 累加），超限的输入不交给 `JSON.parse`（1–60 ms 内拒绝）；在此之上改为子进程池（`child_process.fork`，`--max-old-space-size` 限堆）：内存超限时只结束子进程，服务照常，这一次按 `too-complex` 拒绝；其余崩溃与超时回 503 带 `Retry-After`；IPC 断开时子进程退出，不留孤儿。`SnapshotInspector` 对外的接口不变（审查之后多了发起账户这个参数）。**审查之后**：每个账户在池子里至多 2 份（执行与排队合计），多出来的只对这个人 503（审查 A2）；执行任务期间被外部 SIGKILL 的子进程（容器内存用尽时内核的 OOM killer）同样按 `too-complex` 拒绝、记 error（审查 A4），部署说明写明容器内存的规则。
- **测量**：一个专门的脚本（不进 CI）并发提交 5 MiB 的真实快照与几种恶意形状，记 RSS、堆与事件循环延迟的峰值；结论写进 ADR-001（"放进工作线程还是流式处理"由此定）与 DEF-018。

### 3.5 拦截旧客户端

- **客户端构建**：根 `package.json` 的 `version`（`x.y.z`，发布时递增）在构建时经 Vite 的 `define` 注入页面（测试构建同样）；镜像构建可以把提交号作为诊断信息附在 `+` 之后（构建参数传进构建阶段，不参与比较）。本机 `vite dev` 同样注入。
- **运维开关**：`NERVE_MIN_CLIENT_BUILD`（可选，`x.y.z`；环境变量，改了要重启——"严重缺陷"本来就伴随一次修复发布）。
- **与文档无关的规则**（保存、另存为副本、申请编辑权、心跳都核对）：`univerVersion`、`profile`、`formatVersion` 等于服务端的（`UNIVER_SDK_VERSION`、`DOCUMENT_PROFILE_OF`、`PLATFORM_FORMAT_VERSION`），`clientBuild` 不低于开关——否则 `CLIENT_OUTDATED`（`details.reason`：`format` 或 `build`）。心跳也核对：服务端升级之后，正在编辑的页面在 10 秒之内就停下来、说明需要刷新，而不是到保存时才知道。另存为副本同样拦：旧格式的快照不能以新版本的名义写进来（M4 有发件箱之前，刷新会丢掉本页的修改——心跳的提前拦截把这个窗口压到约 10 秒，页面说明里请用户先复制出来）。
- **与文档有关的规则**：文档记录的 SDK 版本高于服务端的（回滚之后）：`DOCUMENT_TOO_NEW`——刷新拿到的还是同一个版本，提示"刷新"会形成死循环，所以单列；详情带上 `sdkVersion`，页面据此一开始就只能阅读、说明"这份文档由更新的版本保存过"。
- **页面**：`CLIENT_OUTDATED` 是终态：停住保存与续租，页头说"页面的版本过旧，本页的修改没有保存——需要的话先复制出来，再重新加载"，给"重新加载"；申请编辑权时得到它就留在阅读、给同样的说明。审查之后（B5）：转入这个终态（以及"文档比服务端新"）时还有结果未知的保存，先原样重发一次（重放先于拦截旧客户端），按结果再定说法；只有"公式待更新"没存上时单说"本页的修改都已保存，只是公式的结果没有存上"。失去编辑权之后另存为副本得到 `CLIENT_OUTDATED`（以及按规则被拒的 `SNAPSHOT_INVALID`、`PAYLOAD_TOO_LARGE`——捕获的内容不会再变，再试也一样）同样转入终态：说明先把内容复制出来，不再给"另存为副本"、不说"可以再试"（审查 B3）。E2E 用 `page.route` 改写请求伪造旧版本。

### 3.6 链接的改写（客户端，DEF-021）

- **改写器**（`editor/profile/link-policy.ts`）：订阅 `BeforeCommandExecute`，只处理 `sheet.mutation.set-range-values`，对参数里每个带 `p.body.customRanges` 的单元格调用 contracts 的 `normalizeCellLinks`、就地改写。改写不多产生 mutation、不单独进撤销栈（它就是这次编辑的一部分）。改写器**绝不抛出**（Facade 的派发没有 try/catch，抛出会让这条命令失败）：看不懂的结构按不合法处理、去掉链接。装在入口守卫之后、`createWorkbook` 之前，阅读与编辑都装。
- **公式的结果**：`HYPERLINK()` 的结果经同一条 mutation（带 `fromFormula`），改写同样生效；它的 `rangeId` 每次重算都是随机的，改写器把公式结果里的链接的 `rangeId` 换成由单元格位置与序号确定的值，重算不改变内容（"内容相同不递增"对含 `HYPERLINK()` 的表格同样成立）。**实施**（S2）：段落的 `paragraphId` 每次计算同样随机，一并按位置确定（只确定 `rangeId` 时重算之后内容照样变）；编辑栏里粘贴纯文本是第七条路径，同样经这条 mutation。
- **登记**（ADR-010）：mutation 的 id、`cellValue` 与 `p.body.customRanges` 的形状、`CustomRangeType.HYPERLINK`、"参数与处理器、撤销栈是同一个对象"的约定（M0-P5 的 C7c 与本次探针）、SDK 自动识别的各种写法（改写器的输入假设）。回归：单元测试，加上覆盖六条路径与撤销重做的三浏览器 E2E——SDK 升级之后如果改成复制参数，改写会静默失效，这组 E2E 先失败。
- **P3 之前存下的内容**：不在载入时改写，也不做数据迁移——v0.1 在上线之前没有真实数据；P3 起任何写入都经完整的校验。写进 ADR-011 与交接单。

### 3.7 内容相同不递增与回执

- 所有检查都通过之后比较内容哈希（`access.spec.ts` 证明这个位置要保留：编辑权失效之后，内容没变的保存照样被拒）。相同：写一条回执（`document_save_receipts`）、"公式待更新"只清不设（§3.8），修订号不变、不写修订记录、不记审计，响应 `unchanged: true`。
- 重放预检与事务里的再查都查修订记录与回执：结果未知的"不递增"之后重试，照样拿到原来的结果——之后失去编辑权时页面不会误说"没有保存"（P2 的"给副本之前先原样重发"由此成立）。
- 一个 `requestId` 只用于一次请求，两张表之间同样如此（审查 A3）：保存、新建、复制、另存为副本在事务的第一步取同一把 `requestId` 的锁（`RequestLedger`），锁下查两张表；回执用过的再拿去新建一类、新建一类用过的再拿去保存，都是 `REQUEST_ID_CONFLICT`。
- 存量文档的哈希为空时按"不同"处理（第一次保存多一个修订）；只改了视图状态（缩放、滚动）的保存判为相同（计划书 §7.3）。

### 3.8 "公式待更新"

保存与另存为副本的请求带 `formulasPending`（计入负载摘要：同一个 `requestId` 而标记不同就是另一个请求）；写入新内容时把标记设成请求里的值，内容相同（不递增）时只清不设——内容相同就是公式结果相同，库里已经收齐的不因这次捕获没等到收齐而改成待更新（审查 A6）；详情、编辑状态与申请编辑权的响应带上它。页面的 `prepare()` 判断能否原样重发时连标记一起比。P4 用它：进入编辑时先全量重算、收齐之后保存清掉；阅读页的说明也在 P4。存量一律当作没有标记。

### 3.9 修订记录与回执保留 30 天

`NERVE_REVISION_RETENTION_DAYS`（默认 30，下限 15：必须长于 M4 发件箱的 14 天，否则发件箱里结果未知的保存重放不到原来的结果）。**实施**（S5）：事务级的 advisory lock（连接池的下限不变）、与回收站清理共用一个调度器、一轮分批删到删完、`FOR UPDATE SKIP LOCKED`。清理入口在 documents（只给 jobs，lint 限定），任务照回收站清理的写法（ADR-016：会话级 advisory lock 或事务级的 `pg_try_advisory_xact_lock`、分批、数据库时间、退出时收尾）：删掉早于保留期、**而且不是文档当前修订**的修订记录（冲突的来源与申请编辑权要读当前修订那一行），以及早于保留期的回执。新建、复制、另存为副本的幂等窗口随之是 30 天。集成测试用可控的时钟。

### 3.10 页面

- 保存、另存为副本、申请编辑权与心跳带上客户端的构建与数据格式；保存与副本带"公式待更新"；`unchanged` 的确认按"已保存"处理。
- 保存状态加终态"需要刷新"（`CLIENT_OUTDATED`），申请得到它时留在阅读并说明；`DOCUMENT_TOO_NEW` 在载入时按详情的 `sdkVersion` 判断，只能阅读。
- 80% 的提示：保存的状态带上最近一次捕获的大小（与服务端解压后的字节同一个口径），达到 `SNAPSHOT_WARN_RAW_BYTES` 时页头给一条不打断的说明；进入编辑时按载入的内容先算一次。
- `SNAPSHOT_INVALID` 按规则给出说法（例如"表格里有不能保存的链接"），其余照"保存失败"；另存为副本被拒、再试也一样时转入终态（§3.5，审查 B3）。

### 3.11 测试资产

- 模板快照没有链接、图片，资源合规，不用重新生成；模板收敛、重开再保存与两个更新工具改为核对上传的正文或页面内存里的快照，不再看服务器上的字节变没变。
- 只读样本的 `data:` 图片：直接写库的只读用例不变；页面自检的 enter-exit 场景改用去掉图片的派生样本；`update:read-only-sample` 改为从探针取快照、不经保存；`measure-scene.ts` 的版本改为直接写库。
- M0 的保存重开样本里的图片地址（`/fixtures-assets/…`）不是平台地址，P4 移植时处理（交接单）。

### 3.12 错误处理、安全与可观测性

- 快照的检查在判断访问之前（与文档无关），看不到与不存在得到相同的结果；重放预检不提前回答，"看不到与不存在"的语句序列核对照旧通过。
- `SNAPSHOT_INVALID` 只给规则的标识，不回显快照的内容；日志记规则与文档 id。
- 子进程崩溃或超时：503 带 `Retry-After`（页面的保存照"结果未知"重试）；超出子进程的堆上限，或者执行期间被外部 SIGKILL（审查 A4）：`SNAPSHOT_INVALID`（`too-complex`）；同一个账户在池子里超过 2 份：只对这个人 503（审查 A2）。
- 新的错误码进 ADR-006 与契约的测试；新的请求字段进路由表、权限矩阵与读快照的核对（申请与心跳的请求体）。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 新规则误拒合法的保存（SDK 写出的结构、跨引擎的地址解析、深层为空） | 规则只取有证据的最小集合；M0 样本、模板、E2E 产出的快照都过一遍；链接判定要求是两边的不动点，跨引擎的同一组数据进 E2E；审查之后只信任各引擎必然一致的部分，另有"浏览器合法 ⇒ Node 合法且相等"的性质检验；被拒时给出规则 |
| 改写依赖 SDK 的内部约定（参数是同一个对象），升级后静默失效 | 登记、三浏览器 E2E 兜住；服务端的校验是最终防线（被拒而不是存进去不规范的地址） |
| 工作线程在某种运行方式下加载不了 | S3 先在三种方式下验证；做不到时停下来报告，不退回主线程 |
| 旧页面因为 `CLIENT_OUTDATED` 丢掉修改（M4 之前没有发件箱） | 心跳提前拦截，窗口约 10 秒；页面说明请先复制出来 |
| "内容相同不递增"让依赖"服务器上的字节变了"的测试与工具失效 | S4 同一步改：核对上传的正文或页面内存的快照 |
| 图片在 M5 之前一律存不进去 | 与计划书 §11.3 一致（`data:` 图片不再接受）；只读样本与测量的用法改走写库 |
| 规范化的键序被别的实现悄悄改变（M4 的客户端要逐字节复现） | 规格写进 ADR-011，测试向量进 contracts 的单元测试 |
