# P2-S5 切换耗时与反复切换的内存

> 执行：P2-S5 的实测者（子 Agent，模型 `claude-opus-5-5`）｜日期：2026-10-04｜依据：P2 设计 §3.1 第 4 条、§3.5、§4、§6 的 S5、§7 的前两行；实施计划 S5；计划书 §8.2（公式 Worker）、§10.2（编辑器页面的生命周期）、§12.2（性能目标）｜代码：私有副本的 `m3-p2-measure` 分支（基于 `b01359c`）｜环境：§一
>
> **结论**
> - **切换耗时没有明显超过 1 秒**：三个浏览器、三份文档（模板、只读样本、2 万多个单元格与 1,100 个公式的大表），每个方向 12 次，从页面收到点击到可以操作（交互屏障撤掉）p50 0.35–0.43 秒、p95 与最大值都在 **0.48 秒以内**（最慢的一次 477 ms，Chrome、只读样本、进入编辑）；页头随之进入目标状态（同一刻）。打开页面到阅读可以操作：新的浏览器上下文里第一次 0.84–0.91 秒，刷新 0.54–0.63 秒。
> - **每次重建约 0.33–0.41 秒，七成以上是 SDK 固定的延时**：Univer 的 ui（1.0.1）在 Ready 之后用 300 ms 的定时器才做第一次渲染（Rendered），之后再过 3 秒才是 Steady（`ui-shared.controller.ts` 的 `_bootstrapWorkbench`）。挂载的同步部分只有 7–10 ms（p95 不过 12 ms），销毁旧的编辑器 2–7 ms（p95 不过 11 ms），本机的请求 11–17 ms（p95 不过 36 ms）；文档的大小在这个规模里几乎没有影响（同一个浏览器、同一个方向，三份文档的 p50 相差不到 20 ms）。到 steady 一律是点击之后 3.35–3.46 秒（可以操作之后 3 秒）。
> - **内存不随切换次数持续增长，没有留住旧的实例**：Chromium 上进入再退出 60 次、"有更新，点击刷新" 60 次，每次之后强制回收：DOM 节点、事件监听、文档数一直不变，公式 Worker 一直只有 1 个；已用堆前 20 次涨约 5.5 MiB，之后越涨越慢（第 2–20 次 229 / 305 KiB/次 → 第 20–40 次 63 / 41 → 第 40–60 次 34 / 44）。堆快照的比较：多出来的九成以上是 V8 编译出的代码（函数变热之后的优化，随次数趋平）；编辑器实例的标志（主画布、公式 Worker、弹出层的门户）前后都只有 1 个，游离的画布前后都是同样的 7 个，没有平台的代码或 SDK 留住旧实例的保留路径。
> - **真实 Safari 27.0 上进入、退出编辑两次都通过**（`enter-exit` 32/32 两次）：点页头真实的"编辑"进入编辑、经 Facade 改一格、点"退出编辑"先保存再回到阅读，之后 Facade 的只读入口 22 项、写公式的 mutation、撤销与重做都被拦下，与 Playwright 的 WebKit 结论相同；服务器上那份文档恰好多了一个修订，内容里有改的那一格。Safari 里的切换：进入 452–460 ms、退出（先保存）420–455 ms 可以操作，到 steady 3.42–3.46 秒，与 WebKit 26.6 同一个量级。其中第 3 次运行四个场景 85 项全部通过；另有三次运行的部分步骤被环境挡住——Safari 的窗口在外接显示器上，前面是远程桌面（UU 远程、ToDesk）铺满那块显示器的窗口，页面被 Safari 暂停，自检如实交回"页面被隐藏"（§五）。
> - 跑真实 Safari 时发现自检的一个缺口并已修好（§五 F1）：页面在 steady 之前就被挡住时，自检不知道它已经隐藏，逐项在没有动画帧的页面上超时、给出"提示没有关掉"一类误导的说法。

## 二、做法

### 2.1 切换耗时（`measure:switch`）

- **命令**：`pnpm --filter @nerve-office/e2e run measure:switch`（先构建后端与测试构建；`playwright.measure.config.ts`：只跑 `tests/e2e/measure/`，一个工作进程、三个浏览器一个接一个、不重试；常规的 E2E 与 CI 只认 `specs/`，不跑它）。跑完 `measure/summarize.ts` 打印并写出 `measure/test-results/switch/summary.md`；每个浏览器、每份文档的原始时刻在同一个目录的 `<浏览器>-<文档>.json`。
- **三份文档**（`tests/e2e/measure/switch.spec.ts`）：
  - small：新建表格的模板（1,067 字节，一张空表）；
  - medium：只读样本（17,624 字节；5 张表，公式含跨表与定义名称、两张图片、批注、超链接、数据验证、条件格式、筛选、冻结）；
  - large：生成的大表（`support/large-sheet.ts`，531,883 字节）："数据"表 1,000 行 × 20 列两位小数的数值、每行一个 `=SUM(A:T)`，"汇总"表 100 个跨表的 `=SUM('数据'!U…:U…)`；共 21,221 个单元格（数值 20,000、公式 1,100、文字 121），公式带缓存值（与保存过的文档一样）。
- **每份文档一个用例**：作者打开（新的浏览器上下文里第一次打开，再刷新一次）→ 进入编辑、退出编辑交替 12 次（没有修改：进入时只申请编辑权，退出时只释放，用例里断言）→ 查看者打开，作者经接口保存一版（申请编辑权、保存、释放，与页面同一条路径）、页面立即读一次编辑状态（派发 `visibilitychange`，与回到前台时一样，不等 30 秒一次的检查），出现"有更新，点击刷新"之后点它，12 次。每次切换都等到 steady 再做下一次。
- **怎么计时**（`apps/web/src/editor/testing/switch-timing.ts`，只在测试构建与 E2E 里）：页面开始之前装上记录器（`addInitScript`），在页面上记下各个时刻（`performance.now()`）：
  - 页头里的按钮被点击（捕获阶段）——起点；打开时起点是导航开始；
  - 页头的按钮变了（MutationObserver）：第一次变化是"正在…"的说明，出现目标状态的按钮（进入："退出编辑"；退出："编辑"；刷新："有更新"的按钮不在了）是"页头到目标状态"；
  - 编辑器容器的 `data-editor-state`（MutationObserver）：变成 ready 时交互屏障撤掉（可以操作），之后是 steady；
  - 适配层去掉、写上容器的 `data-editor-access`（在这个元素上包一层 `setAttribute`、`removeAttribute`，同步记下）：去掉是旧的编辑器销毁完（`sheet-editor.ts` 销毁的最后一步），紧接着编辑器页把 surface 设为 creating——**重建从这一刻算起**；写上是新的编辑器开始挂载，之后的第一个微任务是挂载的同步部分（公式 Worker、Univer、插件、`createWorkbook`）结束；
  - 表格的主画布挂进容器（MutationObserver）：Univer 第一次渲染时挂上画布、随即进入 Rendered；
  - 页面经 `fetch` 发出的请求与回应（包一层 `fetch`：方法、路径、状态码），结束时刻用资源计时（Resource Timing）补上正文读完的时刻。
  只观察，不改变页面的行为（单元测试核对属性照常写上、去掉，请求照常发出、出错照常抛出）。
- **各段**（`switchDurations`）：网络是这次切换本身的请求占了多久（进入：申请编辑权；退出：保存与释放；刷新：读内容；打开：会话、详情、内容，并行的只算一次；阅读时的检查、心跳不算）；"点击到开始新建"含网络、捕获、销毁旧的编辑器；"销毁旧的"是开始新建之前最后一个切换请求结束、到开始新建；"重建"是开始新建到交互屏障撤掉、到 steady，细分为同步创建、同步部分结束到 Rendered（含 SDK 的 300 ms）、Rendered 到可以操作（公式 Worker 装好 `IMAGE()` 的限制、探针等）。
- **统计**（`support/measure-stats.ts`，单元测试覆盖）：p50、p95 按最近秩法（第 ceil(p × n) 个），每组 12 个样本时 p95 就是最大值——偏保守。

### 2.2 反复切换的内存（`measure:memory`）

- **命令**：`pnpm --filter @nerve-office/e2e run measure:memory`（只在 Chromium：CDP；次数 `MEASURE_MEMORY_ROUNDS`，默认 20；`MEASURE_HEAP_SNAPSHOTS=1` 时在第 2 次与最后一次之后取堆快照，`MEASURE_HEAP_SNAPSHOT_ROUNDS` 另给次数）。中等文档（只读样本）。
- 作者打开到阅读的 steady，连续"进入编辑 → 退出编辑"；查看者打开，连续"有更新，点击刷新"。每次之后（与打开之后）经 CDP 强制回收两次（`HeapProfiler.collectGarbage`），再读已用堆与堆总量（`Runtime.getHeapUsage`）、DOM 的计数（`Memory.getDOMCounters`：文档、节点、事件监听）与 Worker 的个数（`page.workers()`）。斜率按第 2 次之后（含）的最小二乘（第 0 次是打开之后，第 1 次有一次性的预热）。
- **堆快照**（`HeapProfiler.takeHeapSnapshot`，同一个 CDP 会话里取，对象的 id 前后一致）用 `measure/heap-diff.ts` 比较：两次的合计（全部、V8 的代码即节点类型 code、其余）、编辑器实例的标志各有几个（主画布 `univer-sheet-main-canvas_`、原生的 `Worker`、弹出层的门户 `univer-popup-portal-`、游离的画布）、按"类型 名称"多出来的前 40 项，以及多出来最多的几类里后一次才有的对象从 GC 根的最短保留路径（不走弱引用；路径上的属性名没有压缩，看得出是谁留住了它）。

### 2.3 真实 Safari：进入、退出编辑（`safari:selftest`）

- 页面自检加了场景 `enter-exit`（`editor/testing/selftest.ts`，与 S1 的自检同一套入口页、挂接、结果的交回与驱动脚本）：作者打开自己的一份只读样本（与别的步骤分开，因为它会保存一次）→ 阅读的 steady → 核对页头有"编辑"、没有保存 → 点页头真实的"编辑"按钮（合成的点击）→ 等到编辑的 steady（按挂接交给它的页面状态 `host.view`：先等切换开始，再等到目标的 steady 且容器上是 edit；中途回到别的状态就不再等）→ 页头有"保存""退出编辑" → 经 Facade 在"数据"表 K45 写一个值，等命令执行完 → 点"退出编辑"（先保存）→ 等到阅读的 steady → 阅读的编辑器里与服务器上都是保存的内容 → 用新换上的只读编辑器再跑一遍只读入口里能用 Facade 执行的那些（与 `read-only` 共用 `read-only-entries.ts`：Facade 入口 22 项、经 Facade 写公式的 mutation、Facade 的撤销与重做）、界面（没有工具栏与底栏菜单）、内容最后不变。两次切换的耗时按 2.1 的同一套计时，随结果交回（`timings`）。
- 驱动脚本另核对服务器上：`enter-exit` 的文档修订号是 2、修订记录 2 条（恰好多了一个修订），内容里 K45 是写进去的值；别的步骤的文档仍是修订号 1（`support/selftest-plan.ts` 的 `serverProblemsOf`，`selftest.spec.ts` 的校准同样核对）。
- 校准（`specs/editor/selftest.spec.ts`）：四个场景在三个浏览器上都跑，`enter-exit` 32 项都通过。

### 3.5 观察

1. **固定的延时占了大头**：Univer 的 ui 在 Ready 之后 `setTimeout(…, 300)` 才第一次渲染、进入 Rendered，再 `setTimeout(…, 3000)` 进入 Steady（`refer/univer/packages/ui/src/controllers/ui/ui-shared.controller.ts` 的 `_bootstrapWorkbench`，安装的 1.0.1 的 `lib/es/index.js` 里相同）。表格插件在 `createWorkbook` 里同步进入 Ready，所以"同步结束到 Rendered"至少 300 ms，实测 p50 319–394 ms：固定延时之外只有 20–95 ms（Univer 的界面渲染等）。每次重建到可以操作 p50 330–410 ms 里，固定延时占七成以上。这与设计 §3.1 第 4 条引的 M0 样本（到 Rendered 约 0.33–0.35 秒）一致。
2. **进入编辑比退出、刷新多约 50 ms**：可编辑的编辑器界面多（功能区的工具栏、菜单），Rendered 前后主线程更忙，编辑器页还要先建好保存的状态机再撤掉屏障。Chromium、Chrome 上这部分记在"Rendered 到可以操作"（35–46 ms），WebKit 上落在"到 Rendered"里（MutationObserver 送达的时机不同），两段加起来三个浏览器相同。
3. **文档的大小影响很小**：同一个浏览器、同一个方向，三份文档的 p50 相差不到 20 ms（大表退出、刷新时多的主要是捕获与销毁）；2 万多个单元格的挂载同步部分仍是 8–9 ms（p95 不过 11 ms：`createWorkbook` 不复制单元格，公式在 Worker 里），第一次只画看得见的区域。更大的文档（接近 5 MiB 的上限）没有测，留给 M7 的压测。
4. **网络**：本机的请求 11–17 ms（p95 不过 36 ms）。生产环境有往返延迟：进入多一次往返（申请编辑权），退出一到两次（有修改时保存，然后释放），刷新一次往返加正文的下载；按 100 ms 往返估计，进入约 0.5 秒、退出（先保存）约 0.6 秒，仍在 1 秒以内。
5. **steady**：点击之后 3.35–3.46 秒，就是可以操作之后 SDK 固定的 3 秒。可以操作、页头到目标状态都在 ready 那一刻，用户感到的切换是 ready；steady 只影响等它的东西（E2E、页面自检，P4 的打开自检要按"可以操作之后 3 秒"考虑）。
6. 打开页面到阅读可以操作：第一次（新的浏览器上下文、没有缓存）0.84–0.91 秒，刷新 0.54–0.63 秒；比切换慢的部分是加载与编译编辑器的脚本、会话与详情的请求。

- **多出来的是 V8 编译出的代码**：节点类型 code（字节码、优化之后的机器码、去优化的数据）与随它们的 `WeakArrayList`（对象形状的 dependent_code）、`ProtectedFixedArray`、`SharedFunctionInfoWrapper`。它们挂在模块作用域的闭包上（例如 SDK 的菜单项工厂 `menuItemFactory`、Facade 的 `registerEventHandler` 所在的模块），每个编辑器实例共用，随函数被反复调用、变热而编译优化；增长随次数趋平（每 20 次 5.4 MiB → 1.0 → 0.6）。
- **其余每 20 次 0.1–0.4 MiB**：浏览器的性能条目（LayoutShift、LargestContentfulPaint、LongAnimationFrame、PerformanceLongTaskTiming 等，浏览器自己的缓冲有上限）、开发者工具网络域的资源数据（`NetworkResourcesData::ResourceData`：Playwright 打开了 CDP 的 Network 域，是测试工具的）、Playwright 在元素上的缓存（`__playwright_snapshot_cache_`）。也在变慢。
- **没有旧的实例被留住**：每个编辑器各一个的标志前后都只有 1 个（当前的编辑器），游离的画布前后是同样的 7 个（SDK 模块级的离屏画布，一开始就有、不随次数变）；DOM 节点数自始至终不变（被留住的 Univer 实例会连着它的画布与界面的 DOM 一起留住）；Worker 一直只有 1 个（旧的公式 Worker 都终止了）；多出来最多的几类对象的保留路径里没有平台的代码（编辑器页、edit-mode、适配层），也没有旧的 Univer 实例。
- 结论：内存随切换次数的增长是 JIT 的预热，**不是**计划书 §10.2 担心的"反复创建、销毁 Univer 实例造成的泄漏"；不需要"切换若干次之后整页重新加载"之类的对策（设计 §7 的应对）。真实 Safari（JavaScriptCore）上没有测内存（没有 CDP），P2 的范围里也不要求。

| F1 | 自检的缺口（已修） | 页面在 steady 之前就被挡住时（开始时可见、之后隐藏），挂接照常交给自检，自检只在之后的 `visibilitychange` 里记下"被隐藏"，于是逐项在没有动画帧的页面上超时，说法是"提示没有关掉"一类，容易误判为 Safari 的问题 | `runEditorSelftest` 开始时先看一次可见性：已经隐藏就把余下的检查记为没有做、说明原因（`5687f58`；单元测试 `selftest.test.ts`，去掉这一行时用例不通过） |
| F2 | 环境 | 远程桌面（UU 远程、ToDesk）铺满外接显示器的窗口挡住了那里的 Safari，页面被暂停 | 见 5.1；没有改动环境。之后在这台机器上跑真实 Safari，先让 Safari 的窗口露出来（挪到内建显示器上，或者把远程桌面的窗口最小化） |
| F3 | 只读 | 没有发现缺口：`enter-exit` 两次 32/32，第 3 次四个场景 85 项全部通过；进入、退出编辑之后的只读与 S1 的结论相同 | — |

## 六、结论

1. **切换耗时**：没有明显超过 1 秒。点击到可以操作 p95 ≤ 0.48 秒（三个浏览器、三份文档、三个方向，最大值 477 ms），其中约 300 ms 是 SDK 固定的首次渲染延时；到 steady 再加 SDK 固定的 3 秒。按设计 §3.1 第 4 条，不需要与需求方商量。
2. **反复切换的内存**：不随次数持续增长。60 次之后已用堆的增长每次 30–45 KiB、还在变慢，九成以上是 V8 编译出的代码；DOM 节点、事件监听、Worker 不变；堆快照里没有旧的编辑器实例，也没有平台或 SDK 的代码留住它们。按设计 §7，不需要停下来商量对策。
3. **真实 Safari 的进入、退出编辑**：两次 32/32 通过（第 3 次另外三个场景也全部通过）；进入、退出编辑之后真的只读、编辑真的能编辑、保存一次且只多一个修订；Safari 里的切换 0.42–0.46 秒可以操作。部分运行的其他步骤被远程桌面的窗口挡住，是环境的问题，自检如实交回。

## 七、给后面的步骤

- **P4（自动保存与打开自检）**：重建之后可以操作要 0.35–0.48 秒，steady 要再 3 秒。打开自检若要等 steady，切换之后的 3 秒内不要据它判断；页面自检、E2E 等 steady 的写法照旧。
- **M7（性能压测）**：切换的实测命令可以直接复用（`MEASURE_ROUNDS`、换文档）；接近 5 MiB 的表格、带网络延迟的环境（容器 E2E 的 HTTPS）在 M7 补测。SDK 的 300 ms 首次渲染延时若要省掉，只能改 SDK（补丁候选，计划书 §10.3）；目前没有必要。
- **S6 的交接单**：引用本报告的结论。之后在这台机器上跑真实 Safari 时，先确认 Safari 的窗口没有被远程桌面的窗口挡住（F2）。

## 八、怎么重跑

```sh
pnpm db:up
# 切换耗时（三个浏览器、三份文档，各方向 12 次；约 25 分钟；不要与别的 E2E 同时跑）
pnpm --filter @nerve-office/e2e run measure:switch
MEASURE_ROUNDS=20 pnpm --filter @nerve-office/e2e run measure:switch          # 改次数
# 反复切换的内存（Chromium；默认 20 次；取堆快照、再比较）
pnpm --filter @nerve-office/e2e run measure:memory
MEASURE_MEMORY_ROUNDS=60 MEASURE_HEAP_SNAPSHOTS=1 MEASURE_HEAP_SNAPSHOT_ROUNDS=2,20,40,60 pnpm --filter @nerve-office/e2e run measure:memory
cd tests/e2e && NODE_OPTIONS=--conditions=@nerve-office/source node measure/heap-diff.ts measure/test-results/memory/enter-exit-2.heapsnapshot measure/test-results/memory/enter-exit-20.heapsnapshot
# 真实 Safari 的自检（四个场景，含 enter-exit；Safari 的窗口要露出来）
pnpm --filter @nerve-office/e2e run safari:selftest --front
```

- 结果：`tests/e2e/measure/test-results/switch/`（每组的 JSON 与 `summary.md`）、`…/memory/`（序列的 JSON 与 Markdown、堆快照，一个几十 MB）；真实 Safari 的在 `tests/e2e/test-results/safari/<时间>.json`。都在 `.gitignore` 里。
- 计时要在没有别的 Playwright 进程时取（`pgrep -fl playwright`）：这次第一回被另一位实现者的全量 E2E 撞上（负载从 6 升到 15），作废重来。
