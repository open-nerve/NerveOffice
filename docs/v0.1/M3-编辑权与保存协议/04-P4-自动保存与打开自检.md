# M3-P4 自动保存与打开自检：架构设计与实施规划

> 状态：进行中｜日期：2026-10-05｜所属：M3-P4｜依据：M3 总设计 §2.1 第 1 条（保存按钮保留，作用是立即保存）、§5（P4 一行）、§6.5（自动保存、保存状态、打开自检）、US-M3-02、03、15，A02、A08、A17、A18；00 号计划书 §7.2、§7.3、§7.7、§7.8、§8.2、§10.1（r16）；P2、P3 交接单的"P4 须知"；延期登记 DEF-003、DEF-020、DEF-045｜基于代码版本：`16f8a1d`（main：P3 合并 `7f4bd48` 与之后的 CI 修复）

## 1. 目标与范围

修改自动保存，保存下来的公式结果与重新计算的一致；数据不完整的文档不能编辑。

- **自动保存**（计划书 §7.2 的在线部分、§7.3）：两级——捕获（修改停 1 秒、从第一处未捕获的修改算起最长 3 秒，等公式收齐与组合输入结束）进内存里的"最近一次捕获"，上传（停 2 秒、最长 15 秒、同时至多一个在途）取它上传；立即上传：退出编辑、切到后台、保存按钮与 Cmd/Ctrl+S；会话内去重；失败按种类自动重试（退避、`Retry-After`），离线时等网络。
- **"公式待更新"**（US-M3-03）：超过 3 秒上限照常捕获并带标记，收齐之后自动补存；带标记的文档进入编辑时强制全量重算再保存；阅读页说明。
- **组合输入（输入法）感知**：组字中不捕获。
- **保存状态**（计划书 §7.7 在线的部分）：已保存到云端、有未保存的修改、保存中、公式结果尚未保存、保存失败（自动重试中）、已离线、暂停（登录）；终态照旧；读屏只播有意义的变化；DEF-045。
- **`pagehide` 时有在途的保存不释放编辑权**（探索发现的竞态，§2）。
- **打开自检**（§8.2，US-M3-15）：档案完整性（运行时的资源 hook 与白名单）、资源加载错误捕获（创建时覆盖资源管理服务，包装 `parseJson`/`onLoad`）、资源比较（加载后立即捕获，原来非空的消失或变空）、序列化抛错；失败只能阅读、页头说明、上报服务端（新接口，只带种类与资源名，不带内容）。
- **真实 Safari 的复核**（DEF-003 其余部分）：开工即做（S1），实现之后再跑一次。
- **DEF-020 的结论**：捕获时机不按 `trigger` 区分来源，加回归。
- **测试构建**：自动保存的控制、主线程公式模式（US-M3-03 的两种模式）、档案故障开关。

用户故事：US-M3-02（修改自动保存，保存状态如实显示）、US-M3-03（保存下来的公式结果与重新计算的一致）、US-M3-15（文档数据不完整时不能编辑）；P4 结束时改为 active。

**不在本 Phase**：本机发件箱与加密、公式 Worker 起不来时以主线程模式重建（M4，计划书 §10.2、§13.2）；交出编辑权与空闲释放（P5——P4 提供"立即存上"的接口）；关页时的上传（计划书 §7.8：M3 没有发件箱，关页只靠离开提示）；损坏文档的恢复（随 M5 的历史版本，登记延期）；编辑器与平台页入口块下载失败时的空白页（登记延期，M7）；文字文档（M6）。

## 2. 现状（`16f8a1d`）

两路设计前的探索（2026-10-05，`scratchpad` 的 `p4-explore-a.md`、`p4-explore-b.md`）给出的事实：

- **已有且符合 §7.3 的**：变更检测（`editor/change-tracking/`：只看 MUTATION，排除 `onlyLocal`、`fromCollab`、`fromChangeset`、`fromFormula` 与别的单元、排除名单一条，不排除自动行高，大表拆分已关）；公式收齐（`formula-settle-tracker.ts`：无排队、无 stop、逐表写回，每 20 ms 查一次，不用 `onCalculationResultApplied`）；显式保存的状态机（`save-coordinator.ts`：A08、结果未知时原样重发、自己追自己、`requestId` 与"公式待更新"进摘要、`unchanged`、终态与核对、80% 提示）；离开提示（`page-guards.ts`）；捕获前不调 Facade 的读取方法。
- **没有的**：自动保存的任何部分；组合输入感知（表格里组字时写模型的有一处：批注的输入框按 300 ms 防抖写 `SheetUpdateNoteCommand`，`sheets-note-ui/src/views/Note.tsx:110-143`）；会话内去重；收齐之后的补存（现在只说"请稍后再保存一次"）；页面读服务端的"公式待更新"（契约里详情、编辑状态、申请编辑权三处都有，页面一处没用，`edit-lease.ts:262` 只交回租约与修订号）；进入编辑时的强制重算与阅读页的说明；离线、自动重试、`Retry-After`；主线程公式模式（生产只有 Worker）；DEF-045。
- **已有但不符合**：显式保存的 3 秒上限从按下保存算，§7.3 写的是"从第一处未保存的修改算起"（显式保存保留从按下算，见 §3.4）。
- **竞态**：`pagehide` 立即释放编辑权（`editor-page.ts:480-482` → `edit-mode.ts:1020-1022`）。服务端处理保存先在子进程里检查快照、再进事务读租约；晚几毫秒发出的释放多半先提交，在途的那次保存得到 `EDIT_LEASE_LOST`（`released`），修改丢失。
- **生命周期**（Playwright 的 Chromium 153、Chrome 154、WebKit 26.6 实测）：关闭标签页与整页离开都是 beforeunload → pagehide → visibilitychange(hidden) → unload；pagehide 里同步发出的普通 fetch 在 WebKit 整页离开时一个都没到，keepalive 只有 ≤64 KiB 的发得出去；保存要先异步 gzip，关页时的上传基本发不出去（与计划书 §7.8 一致）。WebKit 26.6 没有原生的 `requestIdleCallback`（SDK 用 1 ms 的 `setTimeout` 垫片）。
- **强制全量重算**：公开配置 `UniverSheetsFormulaPlugin({ initialFormulaComputing: CalculationMode.FORCED })` 在工作簿加入与渲染完成时执行 `SetTriggerFormulaCalculationStartMutation({ forceCalculation: true })`，这条 mutation 登记为同步给 Worker 的，Worker 模式可用（M0 的 V07 基准与 P6 的恢复用的就是它）；写回带 `onlyLocal`、不算修改。
- **档案的加载**：插件全部静态打包（编辑器入口块约 7.6 MB），没有按插件的懒加载；注册或启动抛错、Worker 起不来都是"编辑器加载失败"（阅读也建不起来，比计划书 §8.2 的"只允许阅读"更严——阅读需要同一份档案）；入口块下载失败是空白页；运行时没有按档案核对。
- **资源管理服务只能在创建时覆盖**：`createUniverInjector` 构造时就 touch `IResourceLoaderService`，它拿走 `IResourceManagerService` 的实例并订阅 `register$`（`refer/univer/packages/core/src/univer.ts:300-303`）；之后替换无效，Facade 没有资源相关的入口。现有的身份替换（`sheet-editor.ts:108-116` 的 `editorIdentityOverride`）就在 `new Univer({ override })`。10 个表格 hook 全部在 `createWorkbook()` 同步返回之前注册并加载完（6 个在 Starting 经 `loadResources`，4 个在 Ready 经晚注册的 `loadHookResource`），之后不再注册。
- **三类失败与另外三件事**（三个浏览器的探针一致）：解析抛错、非空被吞成空值、加载抛错都构造得出来；另外：筛选的 `data` 为空串时晚注册路径照样 `parseJson('')` 而抛错（"解析抛错"只能对非空输入算）；筛选 `{表: 5}` 加载不报错、之后 `toJson` 抛错（第四类，现状下每次保存都失败）；备注 `{表: 5}` 静默装不进（只有资源比较拦得住）。**现状的静默丢失已复现**：条件格式被吞成空值的文档进入编辑、改一格、保存，三个浏览器都"已保存到云端"，库里的条件格式没了（服务端的不缩水只看"在不在"）。
- **DEF-020**：被取消的命令留在执行栈里，之后命令之外的 mutation 带上它的 `trigger`；变更检测不看 `trigger`，收齐判断调用 SDK 的 `shouldTrigger` 时读的是同一个 params 对象，与 SDK 的触发服务一致——捕获时机不需要按 `trigger` 区分来源。
- **页面自检**（P2-S1）可以直接扩展：探针现在读不到变更检测与公式进度，命令日志没有时刻，没有主线程模式，样本只有只读样本。
- **E2E 的影响面**：约 77 个用例定义走"编辑 → 保存"，估计 30–45 个依赖"修改一直没存"、数修订号或拦第一次保存，要按自动保存改写；只拦网络（`page.route`）会改变语义，需要测试构建里的自动保存控制。

## 3. 设计

### 3.1 两级：捕获与上传

计划书 §7.2/§7.3 与 M0 验证过的规则是两级的，P4 照做：**捕获**按 §7.3 进内存里的"最近一次捕获"（一格，只留最新的；M4 换成发件箱），**上传**按 §7.2 取它上传。这样 3 秒上限"从第一处未捕获的修改算起"的含义清楚，A18 的论证可以直接引用 M0，M4 只换底层。代价：持续编辑时每 ≤3 秒同步捕获一次（1 MiB 约 20–30 ms，5 MiB 约 75–85 ms）；大文档按计划书 §7.2 拉长间隔：两次捕获的间隔不小于上一次捕获耗时的 10 倍。

模块（都不依赖 Univer、时钟注入、可单元测试）：

| 模块 | 职责 |
|---|---|
| `features/sheet-editor/capture-policy.ts`（新） | §3.2 的规则写成纯函数：现在能不能捕获、这次捕获算不算"公式待更新"、下一次该什么时候再看 |
| `features/sheet-editor/autosave.ts`（新） | 调度：订阅编辑器的信号（修改、公式进度、组合输入）与页面的信号（可见性、联网、会话、编辑模式），持有最近一次捕获，决定何时捕获、何时上传、何时重试；暴露 `flush(reason)`（退出编辑、保存按钮、P5 的交出与空闲释放）与"全部存上了没有" |
| `features/sheet-editor/save-coordinator.ts`（改） | 上传一份给定的捕获：确认、A08、原样重发、终态与核对（现有逻辑基本保留）；去重键；失败归类为"会自动重试 / 要等新内容 / 要等会话 / 终态" |

常量放进 contracts（E2E 与页面自检引用）：`AUTOSAVE_CAPTURE_QUIET_MS = 1000`、`AUTOSAVE_CAPTURE_MAX_MS = 3000`、`AUTOSAVE_UPLOAD_QUIET_MS = 2000`、`AUTOSAVE_UPLOAD_MAX_MS = 15000`、重试退避的起点 2 秒与上限 60 秒。

**实施**（S3）：另有 `snapshot-capture.ts`（显式保存与退出、交出时的捕获：提交单元格、等公式 ≤3 秒、序号与快照在同一个同步段里取；审查之后分成按下时的 `settleInputs` 与轮到时的 `captureSettled` 两段，§3.4）与 `save-indicator.ts`（页头状态的全集，§3.9）；常量另加 `AUTOSAVE_CAPTURE_SPACING_FACTOR`（大文档的间隔倍数）。分工：调度管何时捕获、何时上传、持有最近一次捕获；保存的状态机**向来源取捕获**——`save(source, { dedupe })` 轮到这一次时才调用来源，每次上传的都是那一刻最新的一份、上传的先后不会颠倒，按下保存按钮就是"保存中"、单元格提交不了的说明仍出自同一个视图；`save` 交回结果（`saved`、`deduped`、`failed`（带归类）、`skipped`；审查之后 `skipped` 另有 `session`：轮到时会话已知不对、没有发，§3.8），从不失败。

### 3.2 捕获的规则

记号：`seq` 本地修改序号；`capturedSeq` 最近一次捕获时的序号；`firstUncapturedAt` 最近一次捕获之后第一处修改的时刻；`lastChangeAt`；组合输入的 `composing` 与 `lastCompositionEndAt`；`settled` 公式收齐（现有的跟踪器）。

1. `seq > capturedSeq` 时：
   - **静默可捕**：距 `max(lastChangeAt, lastCompositionEndAt)` 满 1 秒、`settled`、不在组字 → 捕获，不带标记；
   - **上限**：距 `firstUncapturedAt` 满 3 秒 → 照常捕获，`formulasPending = !settled`（组字中写进模型的拼音不打标记，由下一次捕获覆盖）；
   - 否则到两者中较早的时刻再看；修改、公式进度、组合结束时立即再看。
2. `seq == capturedSeq`、最近一次捕获带标记，而现在 `settled` 且不在组字 → **补捕获**（不另等防抖，与 M0-P6 原型一致）。
3. 捕获串行、同步（`JSON.stringify(workbook.save())`，序号在同一个同步段里读）；捕获前不调 Facade 的读取方法；记下耗时（大文档拉长间隔）。
4. 单元格编辑器开着、有还没提交的输入时：**自动保存不提交、不打断**，只捕获工作簿；页头照旧"有未保存的修改"。
5. "公式待更新"的初值：进入编辑时取申请编辑权响应里的标记（§3.5）。

**真实 Safari 复核之后**（S1，规则不变，补两处写法）：上限捕获之后迟到的修改由下一次捕获接住（5 万行改字号，空闲任务里的行高在 1.7–2.4 秒才到齐，可能晚于上限）；捕获的时刻按编辑器自己的修改信号（`SheetEditor.onChange`）算，不另做判定（另做判定会认不出漏存，S1 的变异 M6）。

**实施**（S3）：大文档的间隔从上一次捕获结束算起、至少隔开它耗时的 10 倍，只对定时的捕获（立即上传不受限）；调度建起来时已有的修改（没有修改时刻）按"此刻有了修改"算（审查 A9 订正）。

### 3.3 上传的节奏

1. 候选：最近一次捕获，它的去重键（§3.7）不等于最近一次确认过的；同时至多一个在途（已有）；不在退避期内。
2. **静默**：距 `lastChangeAt` 满 2 秒、捕获已覆盖全部修改（`capturedSeq == seq`）→ 上传；公式没收齐、上限没到时，等捕获出来再传。
3. **上限**：距第一处未上传的修改满 15 秒 → 上传最近一次捕获（最多落后 3 秒的修改）。
4. 在途期间照常捕获；回包之后立即再评估。
5. 只在编辑中、会话是本人且令牌不是已知失效、没被停住、不在终态时调度；会话回到本人、恢复联网、回到前台时立即评估一次。会话不对时不发（否则每 2 秒一个 401/403）。
6. M3 没有发件箱：页头**不能**说"已保存在本机"（A14）。

**实施**（S3）：恢复联网时立即评估，不等静默、跳过退避，服务端给的 `Retry-After` 照旧。

### 3.4 立即上传与离开

| 时机 | 提交单元格 | 等公式 | 去重 | 说明 |
|---|---|---|---|---|
| 保存按钮、Cmd/Ctrl+S | 是 | 是，≤3 秒（从按下算，现状） | **不去重**：一律上传 | 给用户一个"强制同步"，兜住变更检测看不见的改动（DEF-002 的派生尺寸一类）；内容相同时服务端只写回执、不加修订号（P3）。自动保存在途时可以按：等在途的结束之后立即再存一次 |
| 退出编辑 | 是 | 是，≤3 秒；没收齐就留在编辑（现状） | 是 | 开始退出就挂起调度。面板里防抖中的修改（批注浮层 300 ms、数据验证面板 1 秒，SDK 的防抖）在最后这段时间里还没写进模型，随销毁丢失：退出与交出之前先让它们提交（关闭面板或等防抖到点，S4 核实可行的做法并加 E2E） |
| 切到后台（`visibilitychange` 变成 hidden） | 否 | **不等**：没收齐就带标记，回到前台之后补存 | 是 | Safari 约 6 秒之后停计时器：同步捕获、gzip（流）与 fetch，全程不靠计时器 |
| 交出、空闲释放（P5） | 是 | ≤3 秒；没收齐就带标记交出（下一个人进入编辑时强制重算） | 是 | P4 提供 `flush(reason)` 与结果 |
| 恢复联网 | 否 | 照常规则 | 是 | |
| `pagehide` | — | — | — | 不当作保存（计划书 §7.8）。**有在途的保存时不释放编辑权**，让租约 90 秒后到期（否则释放先提交、那次保存被拒）；没有在途的照旧释放。代价：本人刷新之后最多等 90 秒才能再进入编辑（P5 的本人接管缓解），别人看到的是"异常中断"的提示 |

离开提示照旧：有没上传、没确认的修改（或单元格里有还没提交的输入）时提示。

**实施**（S4）：面板的防抖（SDK 1.0.1 核实：批注浮层 300 ms，组件卸载时不清计时器；数据验证详情面板 1 秒，范围、设置、选项三种更新共用一个、卸载时不 flush；其他面板的防抖只管界面）——面板开着时在捕获阶段记下页头以外的输入事件，到点＝最后一次输入加 SDK 的时长再加 20 ms（取几次中最晚的）；退出编辑、失去编辑权与各种 `flush` 的准备都先等到点，再判断有没有没存的修改（否则批注里刚打的字不算修改、退出就丢）。登记 `PANEL_DEBOUNCES`；盲区：SDK 改了时长（E2E 会报出来）、数据验证面板共用一个防抖时前一种更新被丢（上游缺陷，收尾时在最小页面上实测成立：1 秒内先后改两种设置，前一种丢失、面板上却显示两处都改了，上游草稿 UR-033）。`pagehide` 的"忙"含终态之后的核对（`busy()`）。

**S7 观察**（接受，不改）：紧跟在修改之后的立即捕获（尤其改完十几毫秒内就切到后台）会带"公式待更新"，即使文档里没有公式——任何修改之后 SDK 都开始一轮，收齐的跟踪器在这一轮的完成通知之前不算收齐。页面随后被关掉时标记留下：阅读的人看到"公式结果可能还没更新"的说明，下一个进入编辑的人强制重算一轮、补存之后清掉。这是保守的一边（宁可多算一轮），不影响数据。

**实施**（S3）：切到后台与恢复联网由调度按页面信号自己做，不经 `flush`；`flush` 的原因是 `save-button`（不去重，在途时排一次）、`exit`、`handover`、`idle-release`（去重）与测试构建的 `control`（不提交单元格、当场捕获，照样按会话与联网挡）；前四种不按会话、联网与测试构建的暂停挡（调用方先确认会话）。显式保存等公式的 3 秒从按下算（排队等过的也算在内）。

**审查之后**（A1、A2）：
- **提交哪一次单元格编辑，在按下的那一刻定**。立即上传分两段：调用（按下）的这一刻提交这一刻开着的单元格编辑（SDK 同步关上单元格编辑器）、开始等面板的防抖（`snapshot-capture.ts` 的 `settleInputs`）；轮到这一次上传时再等公式（时限从按下算）、捕获（`captureSettled`）。原来轮到时才提交：排在在途的保存后面时，那时开着的可能是按下之后才开始的输入——提交了它、选区随之下移，接着键入的字落进下一格，覆盖那里原来的内容（审查 A1 的复现）。按下时提交不了、而轮到时它还开着才中止（只是提示）；期间用户自己提交或放弃了就照常存。
- **会话确认在准备之后**：`flush(reason, { ready })` 先做按下时的准备，再等 `ready`（编辑器页的会话确认：`EditMode.save(ready)`，编辑器页传 `readyToWrite`）；为假时不上传，单元格的提交留在本页（等同按了回车，之后照常自动保存）。等确认期间才开始的输入因此也不会被提交。
- **连按保存的合并在调度这一层**（A2）：显式保存排着、还没开始时再按，就并进它——这一次按下的准备也等到，等公式的时限按最晚的一次按下算，同一个结果只记一次账；开始了或者结束了再按就另排一次。原来由保存的状态机合并、调度又按每次调用各记一遍：一次失败算两次，退避翻倍过快、一次意外就不再重试、422 之后挡住新的捕获。`save-coordinator` 不再合并，每次调用各自一次上传、各自一个结果。
- **P5**：交出与空闲释放同一规则——提交哪一次单元格编辑在调用的那一刻定，之后的输入不提交、不打断；要连它们一起存上的，调用方在调用之前先挡住输入（退出编辑本来就挂着交互屏障）。

### 3.5 "公式待更新"：超时、补存、强制重算与阅读页的说明

1. **超时**：上限捕获带标记，上传时请求带 `formulasPending=true`，服务端记在文档上（P3）。页头"公式结果尚未保存（算完之后自动保存）"。
2. **补存**：§3.2 第 2 条补捕获之后照上传规则上传（不带标记）；内容与上一次相同时服务端回 `unchanged` 并清标记（P3：只清不设）。去重键含标记，"内容相同、标记不同"不会被去重挡掉。
3. **进入编辑时强制全量重算**：申请编辑权的响应带 `formulasPending`（契约已有）→ 进入编辑本来就重建（P2），带标记时以 `initialFormulaComputing: CalculationMode.FORCED` 创建可编辑的编辑器（公开配置，白名单加 `CalculationMode`）→ 保存的状态机以"公式待更新"起步（页头说明、离开会提示）→ 跟踪器看到这一轮 → 收齐之后按补存规则上传 → 服务端清掉标记。重算的写回带 `onlyLocal`、不算修改，所以必须由补存接住；`HYPERLINK()` 的结果经改写器确定化，重算不改内容。
   - **前提**（S3 提出、S4 核实）：强制重算的那一轮必须在建调度之前已经开始、被收齐的跟踪器看到，否则收齐先为真，补捕获存下旧的公式值并清掉服务端的标记。S4 核实（sheets-formula 1.0.1）：创建工作簿时 `UpdateFormulaController` 同步执行带 `forceCalculation: true` 的触发命令，`TriggerCalculationController` 在 Rendered 时再触发一次；`createSheetEditor` 等到 Rendered 才返回，跟踪器在创建工作簿之前就订阅，所以建调度之前一定已经看到这一轮。跟踪器另加兜底 `forcedRound`：没看到 `forceCalculation === true` 的触发命令之前不算收齐（防 SDK 将来改顺序；`FORMULA_PROTOCOL.forceCalculationParam` 登记）。E2E：缓存值错、带标记的文档进入编辑，重算之后补存一次、标记清掉（两种公式模式）。
4. **阅读页的说明**：载入时详情的 `formulasPending`、之后每 30 秒的编辑状态里的，放进一直在的读屏状态区，不打断。能编辑的人："这份表格的公式结果可能还没更新（上次保存时公式还没算完），进入编辑之后会自动重算并保存"；查看者只说前半句。阅读时不在本页强制重算（只说明；进入编辑时重算）。

### 3.6 组合输入

在 document 上以捕获阶段监听 `compositionstart`、`compositionend`；组字的元素失焦（`focusout`）与页面隐藏时复位；目标在页头（`#editor-chrome`，例如分享对话框）里的不算。只用 DOM 事件、不认 SDK 的 DOM 标记，所以批注的输入框也盖得到。**实施**（S4）：编辑器页把页头（`#editor-chrome`）交给适配层，页头里的组合输入与面板输入不算；分享对话框挂在 body 下、不在页头里，在它里面组字也算组合输入，后果只是捕获最多推迟到 3 秒的上限。上限照计划书 §7.3：从第一处未捕获的修改算起 3 秒（同时约束公式与组字）。真实输入法在自动化里驱动不了：E2E 在 Chromium 内核上用 CDP 的 `Input.imeSetComposition`、WebKit 用合成事件，真实输入法登记为人工核对的盲区（与 M6 的 DEF-013 一起）。

### 3.7 会话内去重

- 键＝（快照文本 UTF-8 字节的 SHA-256，"公式待更新"）。与最近一次**确认过**的键相同就不上传，按这次捕获的序号确认（服务端已有一模一样的内容）。
- 初值未知（打开时不哈希载入的文本：`save()` 的写法与存下的字节不同），所以打开之后第一次有修改的上传照常发出；"改了又撤销"之后第一次由服务端回 `unchanged`，之后才被去重挡住（计划书 §7.2："只会多上传一次，不会漏传"）。
- 结果未知的请求不能当作"确认过"，照现有的规则原样重发。
- 只用于自动保存与隐藏、恢复联网时的上传；显式保存不去重。
- **S6 发现**："改了又撤销"之后第一次不一定回 `unchanged`：新建的表格里键入再撤销，`styles` 里留下一条没人引用的样式（SDK 的样式表不回收），规范化之后与之前不同，服务端多加一个修订（不丢数据）。要处理就在规范化里去掉没人引用的样式，这会改变内容哈希的规格（M4 的客户端要复现），登记 DEF-059 留给 M4 定。
- **实施**（S3）：摘要由调度算、每份只算一次；还有结果未知的请求时不去重；服务端按规则拒绝的（`SNAPSHOT_INVALID` 等）记下它的键，同一份不再自动重传。
- 哈希用 `crypto.subtle.digest('SHA-256')`；不用弱哈希——碰撞会让改过的内容不上传，就是丢数据。

### 3.8 失败、重试与离线

| 失败 | 处理 |
|---|---|
| 网络错误、5xx、回包读不出来（结果未知） | 退避重试（2、4、8……秒，上限 60 秒），内容没变就原样重发同一个 `requestId`（已有）；有新的捕获就是新请求 |
| 503 带 `Retry-After`（检查池满、每个账户 2 份、数据库繁忙） | 等 `max(Retry-After, 退避)` 再原样重发 |
| 401、CSRF | 暂停，交给页面确认会话；回到本人之后立即评估 |
| `EDIT_LEASE_LOST`、403、404 | 照现有：续上或失效 |
| `CLIENT_OUTDATED`、`DOCUMENT_TOO_NEW` | 终态（已有，含核对），不再调度 |
| `DOCUMENT_REVISION_CONFLICT` | 自己追自己或冲突（已有） |
| `SNAPSHOT_INVALID`、`PAYLOAD_TOO_LARGE`、本地超过 5 MiB | 不重试同一个去重键，有新的捕获才再试；超过上限时捕获照常节流（大文档的间隔规则） |
| `REQUEST_ID_CONFLICT` | 下次换新 id（已有） |
| 捕获或压缩出错 | 报告页面错误；退避之后再试一次，仍错就停在"保存失败" |

联网：`navigator.onLine` 与 `online`/`offline` 事件（注入，测试里可控）；离线时不发，页头"已离线：修改还在本页，恢复网络之后自动保存"；恢复时立即评估。人不在时续上进入 `dormant`（P1），保存按"会自动重试"处理，有操作时续上之后立即评估。

**实施**（S3）：失败归类（`classifySaveError`）：会自动重试（网络、5xx、503/429 带 `Retry-After`、`REQUEST_ID_CONFLICT`、`EDIT_LEASE_LOST`、403、404）、要等新内容（422、413、400、本地超过 5 MiB）、会话（401、CSRF）、终态（冲突、过旧、太新），另有单元格编辑与意外。会话类的失败同样退避，会话回来时立即重试（防止会话一直显示可写时连着发请求；审查之后只有连着的第一次立即重试，见下）；捕获或压缩出意外时退避之后再试一次，仍错就等新的修改。

**审查之后**（A3、A4、A10，另有核对 A7 时发现的 H）：
- **会话类失败的退避**：只有连着的会话类失败的第一次在会话回到本人时立即重试（多半是令牌换过了），之后照 2、4、8……秒退避；成功一次、或者遇到别的失败，计数清零。页面对每一次会话类失败都确认会话，可写随之"真 → 假 → 真"：服务端一直拒绝、而确认照常成功时，每次都跳过退避就是按网络往返的速度连着发（审查实测 60 秒 1161 次；改后 5 次）。
- **退避期内切到后台不重发**：在退避期内（自己的退避，或者服务端给的 `Retry-After`）切到后台只捕获、不立即重发，到点或者回到前台时再传——开着多份文档的人常在标签页之间切换，每次离开都重发一次就违背了服务端的节流。不在退避期时照旧立即上传。
- **排着的上传轮到时会话变差了就不发**：自动保存在途时按下的保存排在后面；在途的那一次得到令牌失效时，排着的这一次原来照样带着失效的令牌发出（一定被拒，违背 P3 复验的 UB1，还让"连着的会话类失败"多算一次）。现在调度在交给保存的状态机时记下会话可写与否，轮到时从可写变成了不可写（期间得知令牌失效、开始确认会话、换了人）就照常捕获、不发：来源交回 `'session'`，保存交回 `skipped`（`session`），不算一次失败，会话回来时照常上传这一份。交出时本来就不可写的（调用方确认会话失败、但令牌没有失效时照常保存，P3）不在此列。
- **不是约定格式的错误响应**（例如反向代理自己回的 503、429）也读响应头的 `Retry-After` 与 `Date`；`Retry-After` 是 HTTP 日期时按同一个响应的 `Date` 算出相隔几秒，没有 `Date` 时不认（不拿浏览器的时钟去比）——`shared/api` 的 `retryAfterOf`。

**复验之后**（C2、C7）：
- **`Retry-After` 至多按 5 分钟算**（`AUTOSAVE_RETRY_AFTER_MAX_MS`）：本服务给的是几秒；更长的（反向代理的维护页、写错的值）按 5 分钟，到点照常再试。原来不设上限：30 天的值让计时器超过浏览器的上限（2^31−1 毫秒，约 24.8 天），溢出成立即触发，调度每几毫秒醒一次、一直空转到下一次成功。上限只在调度这一层（登录限流的 `Retry-After` 照旧用来说明还要等几分钟）；另外页面的计时器（`browserLeaseClock`）把延迟夹到浏览器的上限，作为纵深防御。
- **会话回来时同样不早于 `Retry-After`**：与恢复联网同一个口径（原来会话回来时直接按现在算，注释与代码不一致）。

### 3.9 保存状态、读屏与 DEF-045

编辑时页头的状态：已保存到云端（服务端确认到当前序号、没有"公式待更新"、单元格里没有没提交的输入）、有未保存的修改、保存中…、公式结果尚未保存（算完之后自动保存）、保存失败（原因；稍后自动重试）、已离线、暂停（登录回来之后自动保存），以及照旧的终态（版本冲突、需要刷新、不能保存、编辑权已失效）、容量将满与超限、请先完成单元格的编辑（只在显式保存、退出编辑时）、文档数据不完整（§3.12）。

- **实施**（S4）：看得见的状态（`data-slot="header-status"`，不再是 live 区域）与读屏的播报区（`role="status"`，7 秒后清空）分开，"有未保存的修改""保存中…"不播；保存中按下"保存"排一次（核对进行中显示"确认中"）；页头原来的"公式结果尚未保存，请稍后再保存一次"提示条去掉，换成状态全集里的一种与阅读页状态区里的说明。
- **读屏**：页头的状态区现在是 `aria-live="polite"`，自动保存之后例行的"有未保存的修改 → 保存中… → 已保存到云端"每隔几秒就播一次。改为：看得见的状态照常变，读屏只播有意义的变化（失败、从失败恢复、离线与恢复、终态、"公式结果尚未保存"与它的结束）。
- 失败的说明（`role="alert"`）在自动重试期间保留上一次的原因，不清掉再出现。
- 保存按钮不再随"保存中"变灰（在途时按下排一次）。
- **实施**（S3）：状态全集由 `saveIndicator(保存的视图, 调度的视图)` 给出（11 种），先后是"再试也一样的失败 > 离线 > 暂停 > 自动重试中"（要等新内容时不能说"恢复网络之后自动保存"）；失败的说明对显式保存同样保留到下一次有结果。
- **审查之后**（A6）："暂停"按原因说——会话不是本人（没有人登录、换了人）："暂停保存：登录回来之后自动保存"；本人在登录中、正在向服务端确认："正在确认登录状态…"；本人在登录中、确认失败了（网络等）："暂停保存：暂时无法确认登录状态，稍后自动重试"（`editorMessages.pausedUnconfirmed`，页面会自己再确认，§3.10）。读屏按原因分开播；不是按保存触发的那种确认（例如别的标签页的消息触发的）进行中时不播。
- **DEF-045**：`RefreshableQuery` 加进行中的状态，`RefreshProblem`/`DetailRefreshProblem` 改用 `RetryButton`（进行中"正在重试…"），编辑器页头拼的那一份带上。

### 3.10 接线

- **编辑器适配层**（`editor/`）：`SheetEditor` 加公式进度与组合输入的信号（变更检测与收齐的跟踪器已在 `createWorkbook` 之前订阅）；`createSheetEditor` 加创建参数 `recalculate`（选 FORCED）；主线程公式模式的档案变体（§3.14）。
- **编辑模式**（`edit-mode.ts`）：调度跟保存的状态机同生命周期（`startEditing` 建、`disposeCoordinator` 去），不跟编辑器槽位；开始退出、失去编辑权（`begin({ kind: 'losing' })`）时立即停；终态之后停；进入编辑时把 `formulasPending` 交给 `slot.replace('edit', snapshot, { recalculate })`。
- **编辑器页**（`editor-page.ts`）：把"会话是本人、令牌不是已知失效"（`confirmedForWrite` 的口径）交给编辑模式；可见性、联网的事件；`pagehide` 时有在途的保存不释放；阅读页的"公式待更新"说明。

- **实施**（S4）：保存的状态机加 `busy()`（在途或核对中，`pagehide` 用）与 `SaveOptions.onOutcome`（结果在视图更新之前先交给调度，否则页头先闪"保存失败"再变"稍后自动重试"）；进入编辑时把调度交给测试构建的控制（attach）；载入时详情的"公式待更新"只在与内容同一版时用；退出到阅读时按记下的那一版的标记说明；`explicitCaptureSource` 与显式保存的等待时限移进 `snapshot-capture.test-support.ts`（生产代码都走调度的 `flush`）。
- 自动保存是编辑行为的结果，**不标** `@BackgroundRequest()`，照常顺延登录（DEF-043 的过渡问题随之消失）。
- **审查之后**（A6）：确认会话失败（`sessionProblem`：网络等，人多半一直在登录中）之后编辑器页自己再确认——恢复联网、回到前台时立即，另按自动保存的退避节奏（2、4……秒，至多 60 秒）定时；确认有了结果（成功、未登录、换了人）就停，卸载时取消。原来要等下一次写的操作或者别的标签页的消息才再确认，自动保存一直暂停。按保存改成 `mode.save(readyToWrite)`：按下的这一刻先提交单元格，会话确认之后才上传（§3.4）。
- **复验之后**（C1，P1 起就有的问题）：续租这条路的同类循环——续租得到令牌失效 → 页面确认会话 → 是本人、恢复续租 → 立即续租又被拒……服务端一直拒绝（例如网关剥掉了 CSRF 的请求头）而确认照常成功时，续租与确认按网络往返的速度连着发（实测 15 秒各一千多次，不需要有修改）。编辑租约改为记"连着的会话类失败"（续租、续上的申请得到未登录或令牌失效）：只有第一次之后恢复时立即续租（多半是登录换过了），之后按心跳的节奏（10 秒）再续；续租或申请成功了才清零（得知失效、网络错误说明不了会话，不清零——否则"失效 → 续上被拒 → 恢复 → 又失效"每一轮都从头算）；页面确认会话不是本人（暂停）时也清零，回到本人时立即续租、核对编辑权（再复核 D1）。与自动保存的会话类失败（审查 A3）同一个口径；页面每轮仍确认一次会话，次数随之有界（ADR-018 的补充）。

### 3.11 打开自检

在适配层，任何一次创建都做（阅读、编辑、退出编辑与"有更新"的重建、失去编辑权之后的重建）：

1. **资源守卫**（`editor/internal-api/resource-load-guard.ts`，登记）：`new Univer({ override })` 里以 `useFactory` + `deps: [ILogService]` 换上 `ResourceManagerService` 的子类，只覆盖 `registerPluginResource(hook)`：包装 `parseJson` 与 `onLoad`（显式委托，只观察、原样抛出、原样返回），交给 `super`。两条加载路径（`loadResources` 与晚注册的 `loadHookResource`）调的都是包装之后的函数。记录：
   - `parse-threw`：输入**非空**（非空串，且解析不了或解析之后不是深层为空）而 `parseJson` 抛错（空串的误报排除）；
   - `parse-swallowed`：输入非空、输出深层为空；
   - `load-threw`：`onLoad` 抛错。
   记下资源名、种类与异常的构造器名（`TypeError` 等），**不记 message**（`JSON.parse` 的报错带输入片段）。
2. **档案完整性**：`createWorkbook()` 返回时，business 含 `UNIVER_SHEET` 的 hook 名＝contracts 的白名单（`profileResourceNames('sheet@1')`）；缺的 `profile-missing-hook`、多的 `profile-unexpected-hook`。就绪之后再核对一次（防 SDK 把注册挪到更晚）。档案完整性独立于文档内容（模板上资源都为空，只有这一条信号）。
3. **资源比较**：`createWorkbook` 之前从载入的快照算出"之前非空"的白名单资源（同名取第一条，与 SDK 一致；`data` 是非空串而解析不了的算非空）；`createWorkbook()` 刚返回时逐个 hook 调 `toJson`（各自 try/catch）：抛错的 `serialize-threw`，之前非空、之后不在的 `resource-missing`，之后深层为空的 `resource-emptied`。这一刻还没有渲染、没有公式写回、没有用户输入，比较最纯；只捕获资源，成本与资源的大小成正比、与单元格的多少无关（常见的文档 ≤1 ms；审查实测 4.7 MB 的批注资源约多 35 ms，可以接受）。判定放进 contracts（`profile-resources.ts` 的 `lostResources`，容错，"空"用 `isDeepEmpty`），与 P3 规范化"在而为空等于不在"同一个口径。"内容有变化"不算失败（DEF-002 等会合法地改变内容）。
4. 结果：`SheetEditor.openCheck`（通过，或失败清单：去重、按种类与资源名排序、档案不全的两种在前；`createSheetEditor` 返回时就定）。**实施**（S2）：`toJson` 没给出字符串同样算 `serialize-threw`（服务端不收，之后每次保存都失败）；序列化抛错的那一项不另报 `resource-missing`；守卫记下的加载、序列化问题只算白名单里的名字（白名单之外的由 `profile-unexpected-hook` 报）；失败的种类与写法放在 contracts 不引用 zod 的 `open-check-failures.ts`——编辑器适配层引用带 zod 的模块会让编辑器页出一条 CSP 违规（ADR-010 的 M3-P4 补充）。适配层只报告，能不能编辑由编辑器页决定（ADR-015"能不能编辑在创建时决定"不变：失败的可编辑编辑器整个丢弃、以只读重建）。
5. 不做的：打开时按服务端的资源规则预检（必须为空的非空等）——这类文档进入编辑之后第一次自动保存（约 2 秒）就会得到按规则的说明，服务端是最终防线；插件注册或启动的硬失败仍是"编辑器加载失败"（阅读也需要同一份档案），计划书 §8.2 的措辞按此修订（r17）。

### 3.12 失败之后的页面

- 阅读态并列一个字段 `damaged`（失败清单），与 `blocked`（不兼容）分开：有就不给"编辑"、页头说明、上报；不因 30 秒的检查读到"能编辑"而恢复；"有更新"重建之后按新内容的结果覆盖。
- 说法：
  - 数据损坏（解析、吞空、加载、序列化、资源比较）：能编辑的人"文档数据不完整，已阻止编辑"＋"部分数据没能载入（……），继续编辑会让它们丢失。已通知管理员"；查看者"文档的部分数据没能载入，显示的内容可能不完整"；
  - 档案不全（构建问题，任何文档都会这样）："编辑器没有完整载入，已阻止编辑。请重新加载页面"＋"重新加载"。
- **编辑路径的"先取后放"**：主路径（打开即阅读、自检失败、不给"编辑"）天然不取编辑权；`?edit=new` 与"编辑"（申请得到更新的修订号、新内容自检失败）只能先取得编辑权、再按它建可编辑的编辑器——自检失败时释放编辑权、以只读重建、以 `damaged` 进入阅读，**不建保存的状态机**；`?edit=new` 的地址参数一并清掉。决定性的不变量是"**失败的编辑器绝不保存**"，单元测试与 E2E 锁住。
- 失去编辑权之后的重建：自检失败只上报，不改失去编辑权之后的选项（副本是本页的内容，服务端照常检查）。
- **实施**（S5）：打开的结果带 `damaged`；页头显示"只能查看"、没有"编辑"；能编辑的人看到提示条（`role="alert"`），"（……）"填资源的中文说法（按档案的资源名定类型，认不出的说"其他数据"）；查看者的说明放在一直在的读屏状态区；查看者遇到档案不全时说"编辑器没有完整载入，显示的内容可能不完整。请重新加载页面"（不说"已阻止编辑"）；随之消失的"编辑"上的焦点交给返回链接。可编辑的编辑器自检失败而只读的竟然通过时，仍按可编辑时的清单阻止编辑（免得来回"先取后放"）；回退时只读的编辑器也不完整就不再说"可以再试"；新建期间续租得知的"与服务端不兼容"在回退路径上直接带进阅读；申请编辑权的回答也记进"公式待更新"的最新一版。编辑器页在地址确实带了 `?edit=new`、而且进入了或 `damaged` 时去掉它。**SDK 的副作用**：先取后放在可编辑的编辑器刚渲染完时就销毁它，数据验证给非当前工作表排的空闲回调随即落空，成为一条没处理的拒绝（DEF-056，用户看不到）；文档在非当前工作表上有数据验证时必现。

### 3.13 上报接口

- `POST /api/documents/{id}/open-check-failures`，204，无响应体；documents 模块。
- 请求体（contracts，严格解析）：`revision`（载入内容的修订号）、`access`（`read`/`edit`）、`trigger`（`open`、`enter`、`refresh`、`exit`、`lost`、`reload`）、`failures`（1–32 项：`kind` 取上面八种之一，`resource` 限 SDK 资源名的写法，`error` 只许构造器名，写法 `^[A-Z_$][\w$]{0,63}$`（不区分大小写）：生产构建压缩之后的类名带 `$`、数字与下划线）、版本四项（`clientBuild`、`univerVersion`、`profile`、`formatVersion`，必填）。**不带**快照、资源的 `data`、异常的 message。
- 权限：能读就能报（`readSnapshot` + `requireAccess`，看不到、不存在、回收站里的一律 404，语句序列相同）；会话、CSRF、Origin、体积由全局管线负责；标 `@BackgroundRequest()`（页面自己发的，不是用户操作）。
- 处理：进程内去重（文档、修订号、失败签名、构建；窗口 10 分钟）与按账户限量（每个账户一个固定的 10 分钟窗口、从第一次被采纳算起，至多 20 条被采纳，超出的照样 204、不记，每个窗口记一条"上报过多"，`event: 'open-check-reports-throttled'`；计时用进程的单调时钟）；采纳的记一条 warn，带稳定的 `event: 'open-check-failed'`（M7 按它告警），服务端补上当前修订号与文档的档案；不记审计（系统信号，不是用户操作）。进程内状态按进程计（单实例首发）。
- 页面：每次创建的结果至多报一次；会话不是本人时不发；失败不重试、不打扰用户。**实施**（S5）：`open-check-report.ts` 按服务端的写法给出请求体（先筛掉不合写法的资源名与构造器名、只有抛错的种类带构造器名、至多 32 项），`apiFetch` 发普通 JSON（只引用类型、不引用带 zod 的结构），会话按编辑模式的口径判断。

### 3.14 测试构建

都在 `MODE === 'e2e'` 时由组装处动态引入测试专用的模块（放在 `src/editor/testing/`，与 P2 的约定一致：门禁 `artifacts` 按模块来源认出，生产构建里没有）：

- **自动保存的控制**：`hold()`（定时触发的自动保存不发，立即上传照常）、`release()`、`flush()`、`setLimits({ captureMaxMs, ... })`（M0 把上限调到 50 ms 测"超过上限"）、`log()`（每次捕获与上传的原因、`requestId`、时刻）；用例在打开之前经 `page.addInitScript` 选择初始是否暂停。**实施**（S4，S7 加同步订阅 `subscribe`：页面自检在调度捕获的同一个同步段里另取快照与"收齐与否"；自检的入口页在打开编辑器页之前就写 sessionStorage 暂停，审查 B1）：`editor/testing/autosave-control.ts`，挂在 `window.__nerveAutosaveControl`，另有 `resetLimits`、`clearLog`；sessionStorage 的键 `nerve-office.autosave-hold`（值 `held` 时打开即暂停）；E2E 的夹具选项 `autosave` 默认 `held`（现有用例按"显式保存"的语义继续成立，自动保存的用例放开）。生产镜像里没有这个控制，容器 E2E 里夹具的暂停不起作用、定时的上传照常发生——容器会跑的用例要在生产构建里同样成立。**S6**：容器会跑的用例（不带 `@test-build` 的）改成在自动保存照常运行时也成立的写法——要"修改没存上"的先收回编辑权或访问、再改；按保存用快捷键（自动保存的重试可能先触发失去编辑权，保存按钮已经没了）；`disconnectTab` 只拦这一页的保存与心跳；按 `requestId` 认那一次。基线里 4 条在容器里失败、另有几条靠快的机器碰巧通过，改了 22 条，1 条（lease-recovery 的"心跳先得知、续上时认出"——生产里自动保存 2 秒之后就原样重发、认出已提交，走不到这条路）标 `@test-build`。夹具另认 `E2E_AUTOSAVE=running`：本机按生产镜像的样子跑（不暂停定时的自动保存）。有几条容器用例靠的是"修改之后立即保存、自动保存最早 2 秒之后才上传"的余量，没有用控制保证（审查之后用压缩时间窗核对、改写，见下）。**审查之后**（A7）：审查者把时间窗压缩之后又找出几条靠余量通过的容器用例，改写之后都不标 `@test-build`。写法要点补充：要"第一次保存一定被拒"的，修改之前就换令牌、拦住（或断开）会话确认，第一次保存用快捷键（"保存"在确认期间不可用）；修订号按内容断言（只要求不小于某个数）；"回包丢了"的用例键入之后不回车、由快捷键提交并保存（丢了回包的一定是按的那一次），不等"保存失败，稍后自动重试"这类瞬时的状态、改看读屏播报区记下的话，之后直接用键盘键入、不点画布（重发成功时失败的提示条消失、画布上移，曾经点错格）；"保存期间继续键入"把保存请求一个一个地放行，断言在两种节奏下都成立。**核对办法（压缩时间窗）**：在私有副本里临时把 contracts 的捕获静默改成 50 ms、上传静默 100 ms、退避起点 100 ms，重建测试构建，在 `tests/e2e` 下以 `E2E_AUTOSAVE=running`、`--grep-invert @test-build` 跑容器会跑的那批（Chromium 与 WebKit；改动不入库）——修复之后 208 条全部通过，改动过的四份 spec 各重复三遍 156 条通过。改了容器会跑的用例之后照这个办法核对一遍（交接单写明）。只拦网络不够：拦住时状态是"保存中…"、失去编辑权的流程要等它，断网又会触发重试与核对，语义全变。节奏类的用例用 `page.clock`。
- **主线程公式模式**：档案里的一份变体（不注册 RPC、三处 `notExecuteFormula` 为假、`UniverFormulaEnginePlugin({ intervalCount: 20 })`，即 M0 推荐、M4 要用的退路），只在测试构建里经地址参数选用；档案标识不变（不影响数据）。M3 里只有测试在用它，写明。**S1 发现**（四个浏览器与真实 Safari 都复现）：主线程模式下，编辑器在一轮计算进行中被销毁（阅读与编辑之间一律重建）时，这一轮不会停下——运行时销毁时把停止标记复位，旧循环在让出点之后接着跑，函数表已经清空，语法树退成"#NAME?"节点并写进 engine-formula 模块级的语法树缓存（同一页里所有实例共用，键里有 unitId，重建之后不变）；新的编辑器算到同样的键时命中它，110–350 个公式得出 #NAME?。Worker 模式不受影响（缓存在 Worker 里，随它终止）。**决定**：P4 里规避（S5 做）——主线程模式下销毁之前，如果正在算，先执行 `SetFormulaCalculationStopMutation`、等这一轮结束的通知（`STOP_EXECUTION` 或完成，`FORMULA_PROTOCOL` 已登记）再销毁，限时；代价最多一个让出间隔（20 个公式，几十到两百多毫秒）。登记进 ADR-010；规避落地之后删掉页面自检的 `KNOWN_PROBLEMS`（校准用例会提醒）。**已落地**（S5）：`editor/formula-round-stop.ts`（有一轮在算：先订阅进度、再同步执行停止的 mutation〔`onlyLocal`，与 SDK 触发服务的写法相同，只读的防火墙不取消它〕、等结束的通知，时限 30 秒，到时限照样销毁并报页面错误——超时意味着 SDK 改了约定）；编辑器的销毁（含创建失败的销毁）都经它，`SheetEditor.dispose` 交回 Promise；编辑器槽位在新建之前等上一次销毁完（同一个容器不会同时有两个实例）。实测停下到收到结束通知 0–5 ms（我们的代码能运行时引擎必然停在让出点，下一轮就检查到停止标记）；去掉它时 170–410 个公式得出 #NAME?。`KNOWN_PROBLEMS` 已删，页面自检与校准恢复为全部要求通过；E2E `formula-rebuild.spec.ts`（阅读与编辑时一轮刚开始就重建，811 个公式全对）。M4 把主线程模式变成生产的退路之前，这条必须已经成立。
- **档案故障开关**：不注册指定的插件组（`?profileFault=<组>`），只给 US-M3-15 的"档案不全"用例（标 `@test-build`，容器 E2E 排除）。

### 3.15 真实 Safari 的复核（S1，实现之后再跑一次）

- 场景（都在编辑时跑）：`change-detection`（打开静默与 M0 动作矩阵里能经 Facade 执行的改内容、只改视图的动作）、`formula-timing`（五类 × Worker/主线程；"静默窗口内再改一次""计算进行中再改一次""超过上限之后补捕获"；捕获里的公式值等于页面里按定义算出的）、`auto-height`（5 万行改字号，迟到的行高）、`large-copy`（拆分已关）、`composition`（合成事件刻画批注输入框组字时写不写模型）、`environment`（`requestIdleCallback` 是否原生、`CompressionStream`、`crypto.subtle`、计时精度）；可选 `hidden-save`（驱动脚本开新标签页让编辑器页真的隐藏，查库核对隐藏之后存下）。
- 校准：`selftest.spec.ts` 在 Playwright 的三个浏览器里跑同样的场景。
- 报告：`reviews/P4-S1-真实Safari复核.md`。结论与 WebKit 26.6 不同时按真实 Safari 调整 §3.2 的规则（M3 总设计 §7 的风险表）；S7 再跑实现之后的版本（自动保存端到端：改完 → 服务器上的公式值 → 隐藏之后存下）。
- **S7**（`reviews/P4-S7-真实Safari复核.md`）：页面自检改为观察真实的自动保存——隐藏时由自动保存自己捕获、上传（不再用显式保存模拟）；公式各项等自动保存上传、服务端确认之后读回服务器上的内容核对（同一个核对先拿上传之前的那一份校准，必须能看出问题）；新增"静默到点时还在算"一项；S1 的独立参考实现（`capture-reference.ts`）删掉——第二份规则会与正式实现各自漂移，规则由 `capture-policy` 的单元测试覆盖，自检核对行为本身。真实 Safari 27.0 上 4 次 12 步全部通过：隐藏之后 +1–2 ms 发出上传、约 0.2 秒库里有这一版；两种公式模式下服务器上的 811 个公式全对（主线程模式的规避生效）。DEF-003 关闭。

### 3.16 DEF-020

捕获时机不按 `trigger` 区分来源：变更检测只看类型、执行选项、`unitId` 与排除名单；收齐判断与 SDK 的触发服务读同一个 params 对象，`trigger` 被串改不会让两边不一致；SDK 按 `trigger` 另判的只有加粗、边框、清除格式三个命令，编辑时被入口守卫取消的不是它们。ADR-010 写明；回归：单元测试（判定与跟踪器对 `params.trigger` 的任何值结果相同）与 E2E（Cmd/Ctrl+K 被入口守卫取消之后改公式的依赖，自动保存的公式值正确）。DEF-020 改为"不影响，已有回归"（上游报告照旧）。

### 3.17 错误处理、安全与可观测性

- 自动保存不改变服务端的任何规则；重放、格式拦截、快照检查、每个账户的份数都照 P3。
- 上报不带内容与异常 message；去重与限量防刷日志；上报只作诊断，不改任何状态。
- 打开自检的误报会让一份文档谁也编辑不了：判定只算白名单内的名字、空串的解析失败不算、"内容有变化"不算；模板、只读样本、大表与全部打开场景的"无误报"回归。
- 自动保存的捕获与上传记 debug 级的诊断（页面里，不上报）。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| E2E 大面积改写、出现不稳定 | 先做测试构建的控制，再改用例；新用例一律用控制或 `page.clock`，不等真实的 2 秒；看 CI 各分片的时长。实际：S4 按新语义改了约 20 处断言；S6 为容器 E2E 改了 22 条、1 条标 `@test-build`；整合之后三个浏览器全量 E2E 948 条无重试 |
| 容器 E2E 的用例靠自动保存的时间余量碰巧通过（生产构建里没有自动保存的控制） | 写法要点见 §3.14；改了容器会跑的用例之后用压缩时间窗核对（审查 A7 的方法） |
| 服务端或网关一直拒绝会话（例如剥掉了 CSRF 的请求头）而页面的确认照常成功 | 保存（审查 A3）与续租（复验 C1）都只有连着的第一次在确认之后立即重试，之后按退避或心跳；页面每轮确认一次 |
| P5 的交出、空闲释放在调用之后还有输入 | 提交哪一次单元格编辑在调用时定（§3.4）；调用方在调用之前先挡住输入（交接单） |
| 资源比较只看整项资源有没有丢：一项资源里丢了一部分、仍然非空时不报（审查实测：同一个 uid 的两条数据验证、同一个 cfId 的两条条件格式，加载之后各剩一条，自检通过） | 设计如此（"内容有变化"不算失败，避免误报）；"部分损坏"靠资源加载错误捕获，拦不住的属于 M0 已知的边界，服务端的检查是最终防线 |
| 打开自检误报，一份文档谁也编辑不了 | 空串的解析失败不算、只算白名单内的名字、"内容有变化"不算；全部打开场景的"无误报"回归；上报带足诊断信息 |
| 真实 Safari 的时序与 WebKit 26.6 不同 | S1 先复核，按真实 Safari 调整规则；S7 再跑实现之后的版本 |
| `pagehide` 不释放让本人刷新之后要等 | 只在有在途的保存时不释放；P5 的本人接管缓解 |
| 关页时最近的修改丢失 | 计划书 §7.8 的丢失边界；离开提示；M4 的发件箱 |
| 每 3 秒一次的同步捕获造成卡顿 | 大文档按捕获耗时拉长间隔；M7 实测 |
| 读屏被例行的状态变化打扰 | 只播有意义的变化 |
| 主线程模式在 M3 只有测试在用 | 档案里一份配置，M4 直接用 |
| 主线程公式模式下，销毁时还在算的一轮把坏的语法树写进 engine-formula 模块级的缓存，之后重建的编辑器命中它（S1 核实成立） | 已规避（S5）：销毁之前停下这一轮、等结束的通知（§3.14）；页面自检、`formula-rebuild.spec.ts` 覆盖；M4 的主线程退路必须保留 |
| 面板的防抖（批注 300 ms、数据验证面板 1 秒）让退出编辑之前最后的修改丢失 | §3.4；S4 核实做法并加 E2E |
| 公式 Worker 起不来时永远"公式结果尚未保存" | 已知局限，M4 的 Worker 失败判定解决 |
| 组合输入只能合成 | 表格里组字写模型的只有批注一处；真实输入法人工核对（与 DEF-013 一起） |
| 服务端负载变大 | 去重、同时一个在途、退避与 `Retry-After`、每个账户 2 份；M7 压测 |
| SDK 升级改了资源 hook 的注册时机或名字 | 就绪之后复核 hook 集合；登记的回归在升级时先跑 |
| 损坏的文档在 M5 之前没有恢复入口 | 一直只能阅读、可以选中复制；运维按上报手工处理；登记延期（M5） |
