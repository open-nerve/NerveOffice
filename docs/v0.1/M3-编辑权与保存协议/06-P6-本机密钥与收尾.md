# M3-P6 本机密钥与 M3 收尾：架构设计与实施规划

> 状态：进行中｜日期：2026-10-08｜所属：M3-P6｜依据：M3 总设计 §2.1、§4（门槛）、§5（P6 一行）、§6.6、§6.7、§8（退出条件）、US-M3-17，A06、A14、A20；00 号计划书 §7.5、§7.6、§11（r18）；P1–P5 交接单的"下一个 Phase 须知"；延期登记 DEF-048、DEF-049、DEF-062｜基于代码版本：`5511ce6`（main：M3-P5 合并 `d0567b5` 与之后的两次 CI 修复）

## 1. 目标与范围

对应 M3 总设计 §5 的 P6 一行：**本机密钥可用；M3 的全部门槛完成验证**。

本 Phase 做：

1. **本机密钥的服务端**（US-M3-17，总设计 §6.6）：每人一把当前有效的 AES-GCM-256 密钥，带版本号，服务端用主密钥包装之后保存；主密钥由部署提供，缺失或格式不对时应用拒绝启动；登录之后的页面按需取当前的密钥；系统管理员吊销某人的密钥（记审计），吊销时生成下一版；正在编辑的页面经心跳得知当前的版本。客户端用这把密钥加密本机草稿是 M4 的事：**M3 的页面不取密钥、对吊销不做可见的反应**。
2. **系统管理员吊销的界面**：账户页每一行的操作、确认框、说明与读屏；US-M3-17 的 E2E。
3. **部署与容器 E2E**：部署说明（主密钥的生成、提供、保管、丢失与泄露的处置）；容器 E2E 核对缺主密钥、格式不对时拒绝启动且输出里没有取值，日志里没有主密钥。
4. **目标为 M3 的三项延期**：DEF-048（登录失败时"为什么来到这里"的说明被错误换掉）、DEF-049（选目标位置时第一层按"上一级"之后焦点交给页面标题）、DEF-062（请求编辑的两条路在真实 Safari 上复核）。
5. **A14 的缺口**：总设计要求已知限制"同一时刻一个人编辑、阅读者看到已保存的版本"在产品中可见，后半句全仓没有明说的文案（探索 B §4.2），阅读时补一行静态说明。
6. **M3 收尾**：门槛逐条的证据、延期项复核、合并之前的对抗评审（Codex）、ADR-019（本机密钥）与各 ADR 的补充、架构总览、M3 交接单与收尾汇报、`v0.1-m3`。

不做（延期或属于后续 M）：客户端导入密钥、发件箱与草稿加密（M4）；主密钥轮换与重新包装、丢失或泄露时的批量作废、恢复备份之后重做吊销的运维手册、生产环境的内存转储策略（M7，§7）。

## 2. 现状（`5511ce6`）

两路设计前的探索：A 服务端（`scratchpad/p6-explore-a.md`，在 PostgreSQL 18.6 与 Node 24 上实测了约束、并发与包装的写法）；B 页面、E2E、真实 Safari 与收尾清单（`scratchpad/p6-explore-b.md`，在真实 Safari 27 上实测了两个源同时登录、窗口被盖住时页面的暂停）。要点：

- **配置**：`apps/api/src/modules/config/config.ts` 只读 `NERVE_*`；机密登记在 `SECRETS`，可以用 `<变量>_FILE` 读文件，变量与 `_FILE` 同时设置时报错；不合法时抛 `ConfigError`（只列变量名与原因），`main.ts` 记 fatal、退出码 1。迁移、初始化管理员、签发重置链接三个命令都读完整的配置；本机 E2E 签发重置链接时只传两个变量；测试环境的编排里迁移与应用共用一个变量锚点。
- **读快照**（ADR-017）：每个登录之后的 GET 都在 `REPEATABLE READ READ ONLY` 的快照里执行，由 `read-snapshots.test.ts` 按路由表强制；只读快照里不能写。
- **系统管理员的操作**：admin 模块、`@SystemAdminOnly()`；事务里先取 system-admins 的共享锁复核操作者、再锁账户行（`FOR NO KEY UPDATE`）；"没有变化的操作原样返回、不记审计"；`AdminUser` 上的 `loginLock` 是同一事务或快照里从别的模块读来的摘要。审计动作登记在 contracts 的 `AUDIT_ACTIONS` 与明细结构，迁移里全量重列 CHECK。
- **心跳**：`PUT /api/documents/{id}/edit-lease` 的控制器与编排在 workspace（`@BackgroundRequest()`），响应 `{ expiresAt, request }`，契约的响应结构宽松（旧页面丢弃不认识的字段）。
- **账户页**：每一行一组操作按钮，确认一律经共用的 `ConfirmDialog`（`AfterConfirmed` 在弹窗关掉、焦点交还之后才执行）；账户页现在没有状态区。
- **故事**：US-M3-01 至 16 都已 active，只差 US-M3-17（planned）。
- **真实 Safari**：P5 复核过同一个浏览器两个标签页；探索 B 实测窗口被别的应用盖住或最小化时 Safari 立即把页面置为隐藏，约 50–55 秒之后计时器与网络请求全部停下，回到前台时积压的计时器立即触发；两个源（`127.0.0.1` 与 `localhost`、各自的后端、同一个库）同时登录可行。

## 3. 设计

### 3.1 威胁模型与总规则

- **本机密钥防的是设备丢失**：设备上加密保存的草稿（M4）在吊销之后再也解不开。它不防服务端被攻破（服务端的库里文档本来就是明文），所以主密钥的保护目标是"只拿到数据库或它的备份的人解不开本机密钥"。
- **服务端是密钥的唯一来源**：每人任一时刻至多一把当前的密钥；吊销是不可撤回的，吊销的那一版的密钥材料随即从库里擦掉；下一版在同一个事务里生成。
- **原始密钥只经一个接口给本人**：解包、生成、主密钥环都只在 local-keys 模块内部；别的模块拿不到任何人的原始密钥；日志、错误、审计、管理员的响应里都没有密钥材料。
- **吊销不顺带撤销登录，停用不顺带吊销**（探索 A §8 的两条，按推荐定）：两件事分开——停用（ADR-013）是可撤回的暂停，启用之后原样恢复；设备丢失时真正要做的另一半（退出登录）由已有的"生成重置链接"承担，吊销的确认框里引导。与总设计 §6.6 一致（"停用账户、撤销登录之后，就取不到密钥了"）。
- **主密钥与库里的对不上时记 error、照常启动**（探索 A §8 第 3 条，按推荐定）：文档照常可用；受影响的人取密钥得到 500、日志说明；处置走显式的吊销（吊销不需要旧密钥）。与总设计 §6.6"主密钥丢失只影响还没同步的本机草稿"一致。

### 3.2 数据模型与迁移 0026

```text
user_local_keys（local-keys 模块的表）
  user_id        uuid        NOT NULL  REFERENCES users(id) ON DELETE RESTRICT
  version        integer     NOT NULL  CHECK (version >= 1)
  master_key_id  bytea                 CHECK (octet_length(master_key_id) = 16)
  wrapped_key    bytea                 CHECK (octet_length(wrapped_key) = 60)     -- IV 12 ‖ 密文 32 ‖ 标签 16
  created_at     timestamptz NOT NULL  DEFAULT now()
  revoked_at     timestamptz
  PRIMARY KEY (user_id, version)
  CHECK ((wrapped_key IS NULL) = (master_key_id IS NULL))
  CHECK ((revoked_at IS NULL) = (wrapped_key IS NOT NULL))   -- 当前的有密钥材料，吊销的没有
  CHECK (revoked_at >= created_at)
  UNIQUE INDEX user_local_keys_current_key ON (user_id) WHERE revoked_at IS NULL
```

- **吊销时擦掉 `wrapped_key` 与 `master_key_id`**（crypto-shredding）：库里不再留能解开旧草稿的东西；行只剩版本与时刻，足够 M4 按版本区分"已吊销"与"被篡改"。残留：MVCC 的旧元组在 VACUUM 之前、WAL 归档与备份的保留期内仍有旧值——写进部署说明的已知局限。
- 外键 `RESTRICT`：账户只停用不删除（与 `auth_sessions` 等一致）。
- 迁移 `0026_m3_p6_local_keys`：建表；全量重列审计动作的 CHECK（加 `users.local_key_revoked`）。表定义进 `TABLE_DEFINITIONS`；Phase 结束时把 0026 加进"迁移带数据"的基准。
- 不变量（集成测试删库之前扫一遍）：I19 每个人的版本从 1 起连续；I20 有过任何一行的人恰好有一把当前的、而且是版本最大的那一把。

### 3.3 包装与主密钥环

- **AES-256-GCM**：12 字节随机 IV、16 字节标签，`wrapped_key = IV ‖ 密文 ‖ 标签`（60 字节）。**加密与解密两边都显式传 `authTagLength: 16`**——Node 24 不传时，截到前 4 字节的真标签照样通过校验（只给弃用警告，探索 A 实测），类型检查拦不住，靠单元测试钉住。
- **AAD**：`JSON.stringify(["nerve-office/local-key/v1", userId, version, masterKeyIdHex])` 的 UTF-8 字节——包装结果绑定用户、版本与主密钥标识，任何一项被改都解不开。
- **派生**：包装键 `HKDF-SHA256(主密钥, salt = 空, info = "nerve-office/local-keys/wrap/v1", 32)`；主密钥标识 `HKDF-SHA256(主密钥, salt = 空, info = "nerve-office/local-keys/master-key-id/v1", 16)`。主密钥只作 IKM，不直接当 AES 密钥。
- **持有方式**：主密钥与包装键在进程里用 `KeyObject`（`inspect` 与 JSON 都是空的）；原始密钥的 `Buffer` 用完 `fill(0)`（尽力而为）；服务端不缓存解开的密钥。
- **主密钥环**：标识 → 包装键。包装一律用当前的，解包按行上的 `master_key_id` 查环。本期环里只有当前一把；"旧主密钥"的配置与重新包装的命令延期（§7）。
- **已知答案测试（KAT）**：IV 的来源可注入，用固定的主密钥、IV、原始密钥、用户与版本钉住标识与 60 字节的包装结果——格式被重构悄悄改掉时库里所有的密钥都解不开，这条测试是唯一的防线。

### 3.4 主密钥的配置与启动

- 变量 `NERVE_LOCAL_KEYS_MASTER_KEY`，加进 `SECRETS`（自动支持 `NERVE_LOCAL_KEYS_MASTER_KEY_FILE`；两者都设沿用"只能设一个"、拒绝启动）。
- **格式**：标准 base64、带填充、恰好 32 字节、规范写法（`openssl rand -base64 32` 的输出）。`Buffer.from(…, 'base64')` 极其宽松，校验写成三步：正则 `^[A-Za-z0-9+/]{42}[AEIMQUYcgkosw048]=$` → 解出恰好 32 字节 → 回编码等于原文。说明里不带取值。
- **只有应用进程要求它**：迁移、初始化管理员、签发重置链接都不需要（最小权限，与 ADR-012 同一个思路）。写法：schema 里可选、照常校验格式；服务端的读法（`loadServerConfig`）在 `crossChecks` 里对缺失报"缺少"；类型上 `ServerConfig = AppConfig & { localKeys: { masterKey: Secret } }`，`createApplication(config: ServerConfig)`。编排里只给 `app` 服务。
- **公开地址是 HTTPS 时拒绝"全是可打印字符"的主密钥**：入库的开发与测试用密钥写成可读的 32 个字符，正式部署抄错了会被拦下（随机的 32 字节全落在可打印范围的概率约 1.7×10⁻¹⁴）。
- **启动自检**（照 `AuditProtectionCheck`：只记日志、不阻止启动）：记下当前主密钥的标识（十六进制，不是机密）；库里有当前的密钥是别的主密钥包装的就记 error，带把数与处置。
- **各环境**：开发 `apps/api/.env.development` 一把可读的开发专用密钥；集成测试与本机 E2E 各一个固定的可读测试密钥常量（重启前后同一把）；容器 E2E 每次随机生成、写进临时变量文件（走 HTTPS，可读密钥会被拒绝）；CI 不用 secrets。
- **日志**：`REDACTED_KEYS` 加 `masterKey`、`localKey`、`rawKey`、`wrappedKey`；测试核对整套用例的应用日志里没有主密钥与任何一把返回过的原始密钥。

### 3.5 接口

**取当前的密钥：`POST /api/local-key`**（不用 GET：第一把在第一次取时生成，要写；登录之后的 GET 一律在只读快照里，ADR-017。POST 不在读快照的范围里，结构性核对不用改；CSRF 与 Origin 自动生效。）

- 写事务：第一条语句按主键核对这次登录（照 ADR-018 的 `requireActiveLogin`，失效回 401 `SESSION_EXPIRED`、不动 Cookie）→ 读当前的那一把 → 有就解包返回；没有就生成 32 字节随机数、包装成第 1 版 → `INSERT … ON CONFLICT DO NOTHING RETURNING`（不带冲突目标：撞主键与撞部分唯一索引都接住）→ 插进去了就返回刚生成的；没插进去（并发的另一次赢了）就再读一次、解包返回。
- 200 `{ version: number, key: string }`（`key` 是 32 字节的标准 base64）；`Cache-Control: no-store`（所有响应已默认带，测试里显式断言）；不是后台请求（ADR-007，用户操作的结果，次数有限）；不单独限流（DEF-054）。
- 遇到不认识的主密钥包装的、或者解包失败：500，记 error（带用户、版本、主密钥标识，不带密钥材料），不自动重新生成。
- 控制器在 local-keys 模块里，只按调用者自己的 id 取。

**吊销：`POST /api/admin/users/{id}/local-key/revoke`**（admin 模块，`@SystemAdminOnly()`），200，返回 `AdminUser`。

- 事务：`lockActingAdmin`（system-admins 共享锁复核操作者）→ `lockAccount`（账户行 `FOR NO KEY UPDATE`；没有这个账户 404）→ local-keys 的吊销入口：`UPDATE … SET revoked_at = now(), wrapped_key = NULL, master_key_id = NULL WHERE user_id = $1 AND revoked_at IS NULL RETURNING version` → 有就插 `version + 1`（新生成、用当前主密钥包装）→ 审计 → 同一事务里拼好 `AdminUser`。
- **必须先锁账户行**：探索 A 实测两个并发的吊销只靠 `WHERE revoked_at IS NULL FOR UPDATE` 时，后一个在 READ COMMITTED 的重新检查下拿到 0 行、被当成"没有可吊销的"。取用不锁账户行（外键检查只取 `FOR KEY SHARE`，不等管理操作）。
- **审计**：动作 `users.local_key_revoked`；对象 `{ type: 'user', id }`；明细 `{ version }`（被吊销的那一版）。
- **停用的账户能吊销**；**吊销自己**允许；**没有密钥（从没取过）时**原样返回、不记审计。
- `AdminUser` 加 `localKey: { version, createdAt } | null`（照 `loginLock` 的做法在 `view()` 与列表里查），**绝不带密钥材料**。

**停用、撤销登录之后取不到**：会话守卫挡住；守卫之后、事务之前的窗口由事务内的登录核对兜住（确定交错的集成用例钉住）。

**锁的顺序**：本机密钥行只在吊销（system-admins → 账户行 → 本机密钥行 → 审计）与取用（只有本机密钥行）里出现，之后都不再取别的锁——全局顺序里登记为"本机密钥行排在最后、审计之前"。

### 3.6 与已打开页面的联动

- **心跳的 200 加 `localKeyVersion: number | null`**（调用者自己当前那一把的版本，从没取过时为 null）：workspace 在续租成功之后、同一个事务里经 local-keys 的公开入口不加锁地读一条；documents 不依赖 local-keys。每次心跳多一条按索引的读，租约的锁顺序不变。
- **阅读时的编辑状态不加**：阅读时不写本机草稿；M4 的恢复、"另存为副本"之前都会先取一次。
- **M3 的页面不做任何反应**：没有发件箱、不取密钥；页面按契约解析出这个字段、不保存也不消费。"已打开的页面经心跳得知"在 E2E 里按网络核对（吊销之后，持有者下一次心跳的响应里版本变了）；页面的反应写进交接单给 M4。

### 3.7 模块边界

```text
admin ─────► local-keys（吊销的入口、密钥摘要）、users、auth、audit、…
workspace ─► local-keys（版本）、documents、users、auth、…
local-keys ► auth（CurrentPrincipal、SessionService）、database、config、logging
auth、users、documents、spaces ─✗─► local-keys
```

- 公开入口只转出 `LocalKeysModule`、吊销的入口（`LocalKeyRevocation`）、版本与摘要的读取（`LocalKeyVersions`）。
- **lint**：吊销的入口只有 admin 能引用（照 `DocumentTransferService` 的写法与自测）——吊销绕过任何"是不是系统管理员"的判断，只能由在锁里复核过操作者的 admin 调用。
- 自动核对：路由表（两个新接口）；后台请求清单不变；读快照的请求表不变（`AdminUser` 的新查询由已登记的两个 GET 探测自动核对）；看不到与不存在：吊销接口加进 `EXEMPT`（只给系统管理员）；一张小权限矩阵（取用 × 成员、系统管理员、未登录、会话已撤销；吊销 × 成员 403、系统管理员 200 × 有效的人、停用的人、自己、不存在 404、id 不合法 400）。
- 命令行的模块组合不引入 local-keys。

### 3.8 吊销的界面

- **入口**：账户页每一行加"吊销本机密钥"，放在"生成重置链接"旁边；所有状态的账户都给。可读名称照 `actionOn`。
- **确认框**：标题"吊销 {name} 的本机密钥？"（自己："吊销你自己的本机密钥？"）；说明：本机密钥用来加密保存在浏览器里、还没同步的草稿，吊销之后用旧密钥加密的草稿都无法再解开；已经保存到云端的文档不受影响，他的登录也不会退出；设备可能落在别人手里时，请同时为他生成重置链接（会退出他在所有地方的登录）。**不说"没同步的修改都会作废"**——M3 的页面内存里没存上的修改不受吊销影响，那样说不实（A14）。确认按钮"吊销本机密钥"（`destructive`）。
- **成功**：`run` 交回 `() => setDone(…)`，账户页顶部加一个一直在的 `StatusRegion`（与转移页一致：弹窗关掉之后再写，读屏才播）；这一行没有变化，`refresh` 用空操作。
- **结果未知**：专门的说法"没能确认是否已经吊销（原因）。再吊销一次没有坏处：会再换一把新的密钥，之前的都已作废"——吊销不是按状态幂等的，通用的"刷新之后看得出是否已经生效"不成立。
- **焦点**：回到这一行的"吊销本机密钥"；自己的账户不重新确认会话（吊销不动会话）。
- 审计页的动作名"吊销本机密钥"（`AUDIT_ACTION_NAMES` 是全覆盖的记录，漏了过不了类型检查）。

### 3.9 部署与容器 E2E

- **部署说明**新加"本机密钥的主密钥"一节，变量表加一行：只有应用容器需要；生成 `openssl rand -base64 32`；推荐 `_FILE`（Docker secrets，对 uid 1000 可读），也可以用变量，两者只能设一个；缺失、格式不对拒绝启动（fatal、`CONFIG_INVALID`、只列变量名）；启动日志里有主密钥的标识；保管与备份（不在数据库里、不在数据库备份里，单独保管，恢复数据库备份时用同一把）；不要随手更换（换了等于丢失）；丢失与泄露的后果与处置（逐个吊销，v0.1 没有批量工具与在线轮换）；恢复备份之后要重做之后的吊销；已知局限（WAL 与备份保留期内的残留、数据库服务器日志在约束失败时带出密文）。`.env.example` 加占位与生成方法；编排用 `${NERVE_LOCAL_KEYS_MASTER_KEY:?缺少 …}`。
- **容器 E2E** 的部署核对加一步：`docker compose run --rm --no-deps -T -e NERVE_LOCAL_KEYS_MASTER_KEY= app`（用镜像默认的命令真的启动一次）→ 期望退出码非 0、输出里有 `CONFIG_INVALID` 与这个变量、没有"HTTP 服务已启动"，时限内还在跑就算问题；再用一个格式不对的值跑一次，同样拒绝且输出里没有那个值。收完各容器的日志之后扫一遍主密钥的取值。判断逻辑放 `container-e2e.ts`（单元测试用样例输出），执行放 `container-e2e-cli.ts`。
- 正常时容器 E2E 外部模式跑 US-M3-17 的 E2E（经 Caddy 的 HTTPS，顺带核对 `no-store` 没被代理改掉）。

### 3.10 DEF-062：请求编辑的两条路在真实 Safari 上复核

做法从登记时设想的"两个账户都在 Safari"改为 **"被复核的一方在真实 Safari，另一方由驱动脚本经接口扮演"**（探索 B §3.3 的做法 C）：两条路要复核的都是 Safari 里那一方的行为，另一方的界面已由 Playwright 三个浏览器覆盖；两个账户都在 Safari 时，盖屏会把两方一起暂停，回来时谁先醒是竞态，路 2 不确定。两个后端（两个源）实测可行，作为备选不做。

- **路 1：请求方在后台停在"交给了我"，回到前台才进入**：驱动脚本以甲的身份经接口申请编辑权、按 10 秒心跳；Safari 里乙打开、点"请求编辑"；甲的心跳带来请求之后，驱动脚本另开标签页让乙隐藏（同一个窗口里被遮住的页面不暂停，P5 F1），甲经接口交出；核对乙停在 `granted`、不申请；隐藏页关掉自己、乙回到前台之后进入编辑。
- **路 2：持有者被暂停时自动交出走到到期**：Safari 里甲进入编辑、写一格并存上；驱动脚本用 osascript 自己的窗口盖住屏幕（约 3 分钟），甲随即隐藏、约 50 秒后被暂停，隐藏之后写的那一格只在本页；驱动脚本以乙的身份经接口发出请求、续期；甲那一代按时间到期之后乙申请成功；移走盖屏的窗口，甲回来得知失去编辑权、本页那一格给副本。判定：甲那一代没有交出、没有释放，最后一次续租到乙申请之间不短于 90 秒。
- **盖屏**只在用户空闲时跑（驱动脚本开头检查空闲），窗口上写明"NerveOffice 的 Safari 复核正在进行（约 3 分钟）"，用户回来按 Esc 或点它就中止这次复核（那一次作废，不留状态）。
- 测试构建里的场景、交接日志与挂接（`selftest-*`）、驱动脚本与校准（`selftest.spec.ts` 三个浏览器、两种打开状态；"暂停"在 Playwright 里用拦住心跳与交出模拟）；报告 `reviews/P6-真实Safari复核.md`；DEF-062 关闭。

### 3.11 收尾的前端细节

## 7. 风险与未决问题

| 风险 | 做法 |
|---|---|
| 包装格式被重构悄悄改掉，库里所有的密钥都解不开 | KAT 钉住字节；格式标签进 AAD |
| 解包没传标签长度，截短的标签通过校验 | 两边显式传、单元测试钉住；表上 CHECK 钉住 60 字节 |
| 两个并发的吊销，后一个被当成没有可吊销的 | 先锁账户行（实测）；集成用例钉住 |
| 主密钥丢失 | 文档不受影响；所有人的本机密钥解不开（M4 起未同步的草稿随之丢失）；启动自检报出把数；逐个吊销即可恢复；批量作废延期（DEF-066，M7） |
| 主密钥泄露 | 只有同时拿到数据库与设备上的草稿才有用；在线轮换延期（DEF-065，M7），处置是换主密钥并逐个吊销 |
| 恢复数据库备份之后旧的包装密钥随之回来 | 部署说明写明要重做之后的吊销；运维手册延期（DEF-067，M7） |
| 解开的密钥在进程内存、堆快照与核心转储里 | 不缓存、`Buffer` 清零、主密钥用 `KeyObject`；生产的转储策略延期（DEF-068，M7） |
| 用开发或测试的主密钥部署 | HTTPS 时拒绝可读密钥 |
| 吊销挡不住拿着还有效登录的设备取下一版 | 确认框引导同时生成重置链接（两件事分开，§3.1） |
| DEF-062 的盖屏打扰到用户 | 只在用户空闲时跑；窗口写明用途与时长；按 Esc 或点它就中止 |
| 本期的服务端改动影响已打开的旧页面 | 心跳的响应加字段：契约宽松，旧页面丢弃不认识的字段 |
