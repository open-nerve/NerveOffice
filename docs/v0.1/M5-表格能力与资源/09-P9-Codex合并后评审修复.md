## 3. 设计

### 3.1 CX6：归档候选的时间先校验（S2）

`Store.prune` 把台账的 `endedAt`（没有时用 `startedAt`）原样放进候选，排序和相减都在逐候选的错误处理之外。`sweep` 直接调用 `prune`，不经收尾用的隔离入口 `prune_isolated`。台账只经 `read_run_manifest` 解析成 JSON，不校验字段类型。于是一条时间不是数字的台账会让启动前的清扫抛错，所有类型的受管运行都起不来。

修复：候选加入列表之前，先核对时间是有限的整数或浮点数，排除布尔、字符串、null、NaN 与无穷。不合格的按 `collection-failed` 记进 skipped，这一条原样保留，其余候选照常回收。`prune_isolated` 的隔离边界、期限与总量规则都不变。

同类排查：`archive.py` 的归档回收（`Archives.prune`）有同样的写法，一并改为先校验，不合格的那一份保留。

### 3.2 CX1：缺目录的已启动运行，核验恢复后收尾（S2）

scratch 不存在时，`Run.finish` 只处理三种情况：

- reports-collected；
- 未启动（`childGroup` 为空）的 prepared 或 cleanup-pending；
- prepared 或 running。

已启动（`childGroup` 已登记）又已是 cleanup-pending 的运行，不在其中，`finish` 直接返回。`sweep` 于是每次都把它记为 active，`run.py` 从此拒绝同类运行。进入这个状态要两个异常叠加：运行期间 scratch 被外部删除，第一次收尾核验又没有通过。核验不通过的原因可以是句柄还没退、lsof 列举不完整，或者退役短根失败。

修复：组与句柄核验（`assert_quiescent`）通过之后，已启动的 cleanup-pending 与 prepared、running 走同一个中断收尾：

- 退役短根；
- 记 `status=interrupted`、`cleanupStage=complete`、`stopReason=scratch-missing`；
- `requestedStatus` 保留第一次收尾时记下的值。原写法取本次调用的参数，sweep 接手时会把原来的 passed 改写成 interrupted。

夹具、证据保留、容器归属与托管路径的先行检查不变。

台账字段的口径不改代码，写进资源规范：

- `commandExitCode` 与 `exitCode` 记的是命令结束时的事实；
- 最终结论看 `status` 与 `stopReason`；
- 结论不是所请求的时候，运行器返回非零。

### 3.3 CX2：IMAGE 首参两侧的空白与 SDK 一致（S3）

固定 SDK 的首参来源证明与平台的 `imageLiteralSource` 都用 `String.prototype.trim`，也就是全部 Unicode 空白。写入规范 `normalizeImageFormula` 的 `skipSpaces` 却只认 4 个 ASCII 空白。实测下面这些写法 SDK 都照常显示图，规范却不改写：首参前的 U+00A0、U+3000（全角空格）、U+2003、U+FEFF，括号组内的 U+00A0，首参后的 U+00A0。于是快照里留下本站绝对地址，服务端不登记这张图的引用。

修复：首参两侧、透明括号内外的空白，一律按 `/^\s$/u` 跳过。这个集合与 `trim` 相同；函数名与括号之间本来就用它。只改写字面量本身，空白原样保留。

回归用真实解释器，逐个检查 `\s` 集合里的每个码位，分别放在首参前、首参后和括号组内。判定要求两边一致：

- SDK 执行原 IMAGE、拿到本站绝对地址时，写入规范必须改写为相对地址，`extractAssetIds` 能取到引用；
- SDK 不认的写法，写入规范也不改写，用 U+200B 等非空白字符作对照。

原有的保留用例不变。

### 3.4 CX3：SDK 缓存命中时补读（S4）

单元格里的图片，包括富文本里的图片与 IMAGE 的结果，由 core 的 `ImageCacheMap` 缓存元素，键是“类型 + 来源”：

- 命中时直接返回旧元素；
- 只有未命中，才登记元素并调用平台读取。

缓存属于工作表骨架，清除与撤销都复用同一个骨架。P7（M5R-M-11）之后，刷新只重读文档仍引用的来源，已删除、没有像素的条目不再读取。于是在“首读失败 → 删除 → 刷新 → 撤销”或“静默补读失败 → 撤销”之后，SDK 拿到的是缓存里的占位元素：平台既不读取，也不报告，页头没有重试入口。

修复是在“再次显示”这一刻补一次读取：

1. **core 补丁**（只改 ES 入口，按 ADR-022 的流程）：`ImageCacheMap.getImage` 命中时，如果实例的 `IImageIoService` 提供 `revisitImageSource(source, type)`，先调用它，再返回原元素。服务在每个缓存对象里只取一次。
2. **平台**：`createImageResources` 记下这样的来源：SDK 还持有元素，但没有像素、也没有进行中的读取。具体是刷新时跳过的已删除条目，以及静默补读失败的条目。
   - SDK 命中这些来源时，合并一次正常（非静默）读取：成功就给原元素换上像素；失败照常报告，页头出现重试入口。
   - 其他来源的命中只做一次集合判断，集合为空时立即返回。
   - 暂停、换代与结束时清空记录。
   - 仍不在文档里、也没有再次显示的已删除来源，照旧不读取，保持 M5R-M-11 与 S14 复验的口径。
3. `platform-image-io.ts` 的 `IImageIoService` 实现增加这个方法。方法名与语义记入 ADR-022 的 M5-P9 补充，以及内部 API 登记表中图片服务那一项的回归说明。

回归：

- **单元**（真实 `ImageCacheMap` 与平台 IO）：
  - 首读失败 → 来源移出文档 → 刷新 → 命中：补读一次，同一元素换上像素；
  - 补读失败时照常报告；
  - 没有记录的来源命中时不读取；
  - 暂停时命中不读取。
- **E2E**（`images-lifecycle.spec.ts` 新增一条，Chromium、Chrome、WebKit）：
  - 单元格图片用一张单独的图片，首次读取返回 503；
  - 清空该格，断网再联网，然后撤销；
  - 这一格重新显示图片，之后再走一遍故障哨兵。

### 3.5 CX7：关闭诊断以回复头的错误为准（S5）

`CloseProtocolFilter.onAnswer` 已经从回复头认出错误与错误码，`disposeError` 却只在正文能解析、并带字符串 `message` 时才写。正文被截断或缺少 `message` 时，`disposeOutcome` 返回 answered，记录可被标为完整。

这种情况当前不会发生：Playwright 1.63 只在设置了 `MAX_LOG_LENGTH` 时才截断协议日志，本仓库没有设置；Chrome 的错误回复也总带 `message`。

修复：dispose 的回复头是错误时，如果正文解析不出来或没有可保存的文字，`disposeError` 记固定原因，`disposeOutcome` 因而是 `dispose-error`，记录标为不完整。回归覆盖两种：截断的错误回复，没有 `message` 的错误回复。

### 3.6 CX5：取消守卫覆盖整段扣住期（S5）

这是 `handover-same-browser.spec.ts` 的“回包乱序”用例。修改：

- 从点击“编辑”到放行，每一步都与“被扣住的申请被放弃”竞速；
- `route.fetch` 失败时，`acquisition` 以写明原因的错误拒绝，不再空等到用例总时限。

原断言、页面的 10 秒时限与真实事务都不变。
