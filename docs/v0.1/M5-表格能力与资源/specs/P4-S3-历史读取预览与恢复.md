# P4-S3 历史读取、只读预览与恢复副本规则

> 2026-10-22；基于 P4-S2 `974eef0e` 与已批准总设计 §6.5。由当前唯一 P4 worktree 实施。Phase 设计/Step 细化按既有自主推进授权自审后执行。

## 1. 用户结果与边界

有当前编辑权限的人能列出最近 7 天的小时历史、独立只读预览、恢复为一份新文档。查看者、空间归档后降为查看者的人、只有系统管理员身份而无内容权限的人不能读取历史。源正文损坏时仍可从有效历史恢复；没有可用历史则如实说明。原文档、其他人的租约、写入代次与本机草稿均不改变。

本 Step 不开放删除/升级前运维检查点、不实现就地回滚、版本差异或格式迁移。S4 再接清除/到期/升级运维，S5 再启用资源回收。

## 2. 服务端契约

| 路由 | 行为 |
|---|---|
| GET /api/documents/:id/history?cursor | 每页固定 30 条，多取一条判断后续；createdAt/id 稳定倒序 keyset；仅 kind=hourly 且 expiresAt 严格晚于该次数据库时刻 |
| GET /api/documents/:id/history/:historyId | 当前可访问源与所属历史均核对；返回历史元数据、保存人、格式兼容状态，不暴露存储路径/哈希/引用集合 |
| GET /api/documents/:id/history/:historyId/content | 独立鉴权后原 gzip 下发，Content-Encoding gzip、JSON 类型、no-store；不拿当前内容代替缺失历史 |
| POST /api/documents/:id/history/:historyId/restore | JSON requestId、spaceId、可选 folderId/title；成功 201 CreatedDocument，重放照既有 created 契约 |

元数据：历史 id、修订号、savedAt（原修订保存时间）、createdAt（采样时间）、expiresAt、savedBy（用户摘要）、历史标题、type/profile/formatVersion/sdkVersion/clientBuild、formulasPending、rawBytes/storedBytes、兼容性 supported/unsupported。不把格式兼容标记当作正文完整性验证成功。

所有 GET 的权限、历史范围、时间和保存人名称归属同一个 TransactionRunner.readSnapshot；Workspace 补人名，Documents 不依赖 Users。正文响应复用现有安全下发方式，不复用当前修订号的条件请求，历史读取始终先鉴权。缺失、其他文档的历史、已过期、运维种类一律 NOT_FOUND；能看当前正文但无历史权限是 PERMISSION_DENIED。匿名统一按现有会话守卫。

DocumentPermissions 增加 canViewHistory（有效内容角色 editor/admin）、canClearHistory（有效空间角色 admin）；规则仍在 documentPermissionsOf。canClearHistory 只表达资格，清除路由/UI 在 S4 开放，不提前提供按钮。DocumentOperation 增加 viewHistory/clearHistory，复用既有统一拒绝规则。

## 3. 历史图片的读取与合法引用

当前可读关系仍按原规则。仅存在于历史的图片，必须有一份仍有效的 hourly 历史且请求者现在有该源文档的 canViewHistory，才参与读权；before_delete/before_upgrade 永远不加入普通图片读权。本人上传的原有 24 小时窗口仍保持原规则，测试过期窗口后再验证历史独立授权。

SQL 不得仅因当前文档可读就纳入历史，也不能从任意一个查看者来源挑一行后漏掉另一个合法编辑者来源。候选查询在统一权限策略生成的历史范围内预选：可编辑空间 id；单独 editor 授权的活动文档及其未归档空间。Documents 提供授权候选空间集合，策略经 Spaces 的公开批量事实判断归档状态；不跨模块联表。该范围与具体 assetId 无关，不能因隐藏引用数量改变查询次数。

当前正文与历史引用分开查询/复核。DocumentAssetAccessService 的每次请求在同一个快照内固定数据库时刻，再按当前/历史两种来源求并集；缺失图片和只有不可见来源的图片保持相同查询序列。保留关系本身不授予权限。

图片保存的合法来源也承认有权访问的有效用户历史：prepare 固定候选源；hold 仍先空间再文档；authorize 锁下重新核对权限及有效历史，最后持 assetId。清除/到期可在此前删除历史，授权必须据此失败；一旦历史关系已消失，不凭预选结果授权。S4 清除持文档写锁，过期删除与恢复按检查点/资源顺序；S5 最终互斥协议另加资源回收复核。普通当前文档复制仍只复制当前关系，不把同源的全部旧图带进去。

## 4. 恢复为副本

### 4.1 原字节、检查与资源预算

恢复先按请求账本检查已完成重放；新请求在只读快照内取得当前可读历史材料。正文验证不占写事务：gzip 字节 SHA-256、完整单成员 gzip、压缩/解压长度、格式兼容、现有子进程快照检查、SDK unitId 与记录一致；现代正文同时核对规范化哈希和非空资源名，旧空哈希如实允许。不得重新序列化或改写 gzip。

无效/损坏历史使用有明确文案的 HISTORY_UNUSABLE（422），不输出正文或诊断位置；不支持的格式标记 unsupported，恢复仍拒绝。检查进程忙/超时沿既有 503 重试，不能误判为历史损坏。调用现有 gunzipWithin 与 SnapshotInspector，不在主线程解析大 JSON。

读取大正文前先取得恢复专用准入：全局最多 2 份、每账户最多 1 份，不无限排队；忙时 503 + Retry-After。准入覆盖加载、解压、检查到写事务结束，每条失败都释放；旧已完成重放不需要解压或准入。此上界限制新增恢复路径的内存，不更改保存/图片子进程预算。恢复服务不得通过 source 当前正文判断历史可用性，当前损坏不妨碍读取有效历史。

### 4.2 事务、竞态与幂等

新恢复的写事务顺序：requestId → 目标空间树 → 源/目标空间按 id → 源文档共享锁 → 对应检查点共享锁 → 图片资源按 id。先重新核对当前源历史权限、源位置、目标创建权限和文件夹；检查点仍属于源、是有效 hourly 且尚未过期。预检之后的撤权、移动、归档、删除、清除或到期不能被旧材料绕过。检查点不可 UPDATE，所以持锁重读同 id 的摘要/信封后可复用先前验证结果；不把长检查放在数据库锁内。

创建新平台 id，修订 1、代次 0、创建人/保存人是恢复者；保留历史原 unitId、gzip、格式信封与已获权图片集合。目标继承自己的空间规则，不复制源的单独授权；不复制源全部历史。初始正文照 S2 生成新文档自己的小时历史。正文/关系/修订/历史/审计同事务，失败全部回滚。

请求摘要包含源文档 id、历史 id、目标空间/文件夹及请求中的标题，不依赖源或历史后来显示的标题。已完成同 requestId 的重放只返回调用者仍可访问的新副本当前信息，不再读旧历史；因此源随后撤权/过期/清除不会造成未知结果的恢复被重复创建。不同人/不同负载复用 id 拒绝。恢复审计以新文档为 target，details 只含 sourceId/historyId/目标位置等有界元数据。

## 5. 前端流程

- 历史列表是平台的按需加载页面 `/documents/:id/history`。编辑器和文档操作入口按 canViewHistory 展示。列表显示本地时间、保存人、修订、格式说明，处理加载、分页、真实空态、网络重试、撤权和缺失。
- 每条历史可在新标签页打开 `/documents/:id/history/:historyId/preview`。采用独立 history-preview.html 入口，绕开平台/编辑器现有会启动草稿维护的运行时；不申请租约、不启动 outbox/自动保存，也不向当前正文写入。
- 预览通过编辑器公开适配层创建新的 read 实例，单实例只装一份快照，SDK 类型不流入平台契约。复用当前图片身份控制器的通用行为，移到共享的会话身份层时保留原测试；历史预览的会话/权限确认由专用控制器负责。
- 预览在加载、重新可见、会话变化及有界周期复核当前历史资格。身份变化先暂停图片、销毁旧实例并转到登录或无权状态；晚到的旧请求不能重挂已销毁的实例。正文/格式/SDK 自检失败显示不可预览，不能给“恢复成功”的假承诺。
- 列表恢复面板复用已有目标空间/文件夹选择和 requestId 账本，明确说明会创建副本，不改变原件。成功提供新副本链接，原编辑标签不导航；结果未知重试沿用请求标识。
- 当前编辑器打开自检失败时为有资格的人显示历史入口（DEF-061）；没有可用历史显示准确空态。禁止默认复制当前损坏快照来“恢复”。

新增预览入口首屏预算沿现有编辑器 2350 KiB gzip / 公式 Worker 800 KiB，全部可达 JS（含延迟语言包）另设 3300 KiB；两项都检查。已有入口的体积上限不变；平台的首屏文件数按三个独立入口的共享关系由 2 调整为 3，理由与基线证据见下方裁决。预览不得引入 outbox Worker。既有无第三方请求/CSP/只读守卫仍适用。

## 6. 必验反例

1. 查看者、归档、已撤 editor 分享、只有系统管理员身份、跨空间移动：列表/元数据/正文/图片/恢复每个入口独立拒绝；未知与隐藏路径不泄露。
2. 旧图已从当前移除、只在历史保留：编辑者可读，查看者不可读；运维检查点不授权；同物理 hash 的陌生 assetId 不串权；存在多个来源时合法历史不能被一个不合法候选遮住。
3. 原正文损坏但旧历史有效；历史 gzip/信封/摘要/unitId/资源名不一致；未知格式；检查进程忙：只能有效历史恢复，错误不混淆。
4. 预检后撤权/清除/过期/移动与两并发同 requestId；未知提交后源撤权再重放；恢复故障后半成品清零。
5. 预览、换人、晚到请求、重复卸载；三浏览器历史→预览→恢复→图片重开，原编辑会话/正文/本机草稿不变。

## 8. 生产构建后的口径裁决（2026-10-22）

原第 5 节把既有编辑器的“首屏 2350 KiB”误作“全部可达依赖 2350 KiB”。P3 已冻结 full05 的生产 manifest、模块来源和构建日志证明：旧编辑器已有 101 个可达 JS，日志合计约 3183 KiB；其中约 1 MiB 是 SDK 的延迟语言包。S3 新预览初测全部约 3060 KiB，新增部分是历史宿主，未新增这些语言依赖。因此按旧口径保留首屏 2350 KiB，另外增加全闭包 3300 KiB 的检查，不删除 SDK 内容能力以迎合错误估计。公式 Worker 仍为 800 KiB。旧产物只保留 manifest/来源与日志，日志的 kB 合计仅作近似对照；最终数值以本次门禁实际 gzip 为准。

第三个独立入口使共享关系变为“所有页面共用”与“平台/编辑器共用”两组；后者含草稿维护，不能为合并分块而让预览依赖它。统一三个页面的标题 hook 后，平台首屏由初测 4 块减少到 3 块，保留自动分块，不采用实验性的打包器内联选项。按既有预算规则允许在 Phase 设计记录结构变更，文件数上限为 3，体积上限仍为 180 KiB。代价是平台首屏比两入口基线多一次同源 JS 请求；不增加总量上限。产物来源、禁止预览草稿 Worker、真实无草稿/保存请求和三浏览器回归继续共同验证。
