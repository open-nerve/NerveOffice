## 已知事实与归因边界

full21 的原范围覆盖率主进程收到 SIGKILL（退出 137），运行器没有请求中断；lint、类型、静态门禁通过，后续阶段未执行。磁盘保护未触发，系统日志没有给出发送者。失败原件保留，不能用后续结果改写历史原因。

容器编排测试有三处先等就绪文件存在，再执行 `Number(readFileSync(...))` 并把结果登记到清理数组。文件已创建但内容尚未写入时，空字符串得到 0；`signalGroup(0, 'SIGKILL')` 变为 `process.kill(-0, 'SIGKILL')`，会结束发送者所在的整个进程组。其后还有直接 `process.kill(pid, 'SIGKILL')`，所以只把前者改成返回 false 不能修复。Linux 真实进程契约有六个同型读取调用点，其中一个覆盖两种环境；该文件在 macOS 不执行，不能解释本机 full21。

Q 为主目录 `.codex/handoffs/m5-p4-20261022/s6/hosted-vm-policy/final-ci-40947141649-investigation`。`Q/r12-full21-sigkill01/empty-ready-group-root-result01.json` 记录独立样本：确认自己是运行器创建的独立组首后，用原函数消费受控空文件，只结束本轮组，实得 commandExitCode=-9、exitCode=137、interrupted=false，实际文件/组/锁/句柄闭合。它证明缺口可触发，但没有证明 full21 当次实际读到 0。原 full21 与旧 CI 的发送者、原始就绪内容仍未知。

Node 24.21.0 的 UTF-8 同步文件写入分别调用 open/write，同步仅约束写者；另一个进程的 exists/read 仍可能落在中间。[Node 源码](https://raw.githubusercontent.com/nodejs/node/v24.21.0/src/node_file.cc)及 [Apple kill(2)](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/kill.2.html)支持窗口与信号语义。

## 修复边界与选择

只改工具的信号参数边界和两类测试夹具的 PID 就绪协议，不改变应用、SDK、数据库、CI 工作流、用例范围、retry、worker、覆盖率阈值或原有测试/等待预算。

只校验消费者会把危险组杀变成随机夹具失败；只原子发布也没有保护其他非法调用。采用两者并加信号入口校验，是 root 在现有自主修复范围内的实现选择。无需另建进程监督器或改变既有资源运行器。

1. 可用于这些子进程信号的数字 ID 范围固定为整数 **2–2147483647**。拒绝 0、-0、1、负数、非整数、非有限及越界值；拒绝发生在任何 `process.kill` 调用之前，并明确抛错。数字合法不代表归属已被证明，既有身份/归属检查不能删。
2. PID 就绪内容为无空白、无符号、无前导零的十进制文本，再应用同一范围。空串、空白、科学计数法、十六进制和尾部垃圾不能进入清理数组或探测/发信号调用。
3. 单写者使用本轮唯一 marker 路径，在同目录 staging 文件完整写入 `String(process.pid)`，然后 rename 发布最终文件。旧的仅表示布尔闸门的空文件保持原语义；不把全部 exists 等待改成 PID 等待，也不延长等待预算。
4. 容器测试三处及 Linux 契约全部 PID writer/read 成对更新；只登记已校验 ID，直接单进程清理同样不得收到 0。
5. `signalGroup(validPid, 0)` 仍是合法只读存在探测。只有真实 ESRCH 返回不存在；权限/未知错误不能被当作已消失。
