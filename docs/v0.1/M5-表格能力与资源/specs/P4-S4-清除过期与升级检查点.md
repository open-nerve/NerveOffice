# P4-S4 清除、过期与升级前检查点规则

2026-10-22；基于 S3 `a115822e`；落实已批准 M5 总设计与 P4 §3.3–3.6。按项目自主设计规则自审，继续唯一 P4 分支。

## 1. 用户结果与选择

空间管理员可以清除一份文档的用户历史；当前正文、小时占位、保存回执及运维检查点保留。到期任务分批清理 7 天小时历史与 30 天运维检查点，并释放它们的保留关系；本 Step 不删除图片文件。

运维在升级前生成完整、可接续的检查点批次。只扫描当前文档不能覆盖并发写入；把所有 gzip 放进一个长事务又使大库失败时全部重来。因此采用持久维护标记、数据库写入屏障和有界短批：先排空在途源写入并冻结源集合，之后逐批复制原字节，完整核对后成为 ready，仍保持冻结，最后由运维明确 release 或 abort。进程退出不自动解除冻结。

代价：源写入语句多一次共享屏障检查；升级维护期间相关写入暂不可用，读取继续。writeEpoch/权限撤销等不属于检查点材料的更新保持可用。此 Phase 不升级 SDK、不做快照格式转换，也不提供绕过冻结的 HTTP 或会话变量。

## 2. 用户清除

- `DELETE /api/documents/:id/history` 无请求正文，返回 200 `{ cleared: 非负整数 }`。仅当前 `clearHistory` 资格（所在空间 admin；个人空间所有者），系统管理员身份或 editor 单独授权不额外授予。
- 初查后按源空间共享锁 → 源文档写锁复核资格与位置；只删除这个源的 `kind=hourly`，包括已过期但尚未清扫的小时历史，图片关系随外键级联删除。用数据库聚合计数，不能把正文或无界 id 数组读入进程。
- 审计 `documents.history_cleared`，明细 `{ spaceId, cleared }`，与删除同事务。0 条同样明确记录这次操作。异常整单回滚；原件、修订/回执、运维检查点、小时桶及原编辑会话不改变。
- 与保存/恢复通过源文档锁排序；与过期清扫通过检查点锁排序，清扫不反向取空间或文档锁。恢复已先持住历史时完成后才清除；清除先完成则恢复必须找不到旧历史。
- 列表响应增加同一快照下计算的 `canClearHistory: boolean`，不靠另一份缓存猜角色。
- 页面复用按需加载的 ConfirmDialog，说明清除不可撤销及保留范围。确认中禁止重复触发；成功先清列表缓存、按既有有界刷新流程同步，再在弹窗关闭后提示数量并接住焦点。
- DELETE 不复用保存 requestId：每次确认是一次清除当前集合的独立意图。结果未知时重新读取历史、明确说明可能已生效，并禁用本次弹窗的再次确认；须关闭、核对成功刷新的列表后重新确认。不能把下一小时的新历史当作上一次未知请求的自动重试清掉。

## 3. 过期任务

- 新增 `NERVE_HISTORY_PURGE_ENABLED=true`、`NERVE_HISTORY_PURGE_INTERVAL_MS=3600000`（1000–86400000）、`NERVE_HISTORY_PURGE_BATCH=100`（1–1000），映射到 `jobs.historyPurge`，使用现有 JobScheduler。
- 每轮由 Jobs 数据库时钟固定 now；每批独立事务，沿 ExclusiveRunner 的事务级锁 `nerve-office:history-purge` 防重入。Documents 负责判断与删除，Jobs 只编排。
- 检查点按 `(expires_at,id)` 选择 `expires_at <= now`，`FOR UPDATE SKIP LOCKED`，每批至多 batchSize；删除关联关系，不碰当前引用。三个检查点种类使用各自 S1 生成的固定期限，不自行缩短。
- 小时桶独立按时间/源 id 清理，每批至多 batchSize；仅删 `hour_bucket < UTC 当前自然小时 - 168 小时`，因此每个桶至少保留完整 7 天，同小时清除不会再次采样。仍有对应 hourly 检查点（包括被锁住而跳过的到期行）的桶保留，待检查点实际删除后再清，保持 S1 的对应不变量。不同表逐条 await，事务失败两部分都回滚。
- 有实际清理时审计 `documents.checkpoints_expired`，系统 actor、job origin，无 target，明细 `{ checkpoints, buckets }`，不输出正文或无界 id。
- 两部分都不满批则结束；失去独占锁、应用退出、批次失败时记录明确结局。禁用任务只延迟物理清理，历史读取与图片授权仍立即按期限拒绝。

## 4. 升级批次的持久事实

Documents 新增以下表，向前迁移；保持既有检查点不可变触发器。

- `document_upgrade_batches`：id、目标版本标识（1–128 ASCII 字符，字母/数字开头，仅字母数字及 `._:@/-`）、status（preparing/failed/ready/released/aborted）、sourceCount、createdAt、updatedAt、completedAt 可空、有限 failureCode 可空。没有正文、标题或凭据。
- `document_upgrade_sources`：`(batchId, documentId)` 主键、冻结时 revision、checkpointId 可空；源 id 不跟随文档删除；checkpoint FK 删除设空，便于识别到期与接续。完整源集合在冻结事务中写入，而非边翻页边猜。
- `document_upgrade_barrier`：只有 id=1 的一行，activeBatchId 可空。缺少这一行时写入守卫拒绝，不按“没有维护”放行。

批次只供 CLI；不增加普通成员的运维历史读取或恢复入口。系统管理员也不能通过公开历史接口读取 before_upgrade。

## 5. 数据库屏障与锁顺序

固定 advisory 键 `nerve-office:document-upgrade-writes`。下列源表在源材料变化语句之前执行触发器：

1. documents 的 INSERT、DELETE、TRUNCATE，以及 UPDATE OF id/title/type/unit_id/profile/format_version/sdk_version/client_build/revision/formulas_pending；不拦仅 write_epoch、updated_at、位置/状态等未进入检查点材料的变化。
2. document_contents、document_asset_links、document_revisions 的 INSERT/UPDATE/DELETE/TRUNCATE。

触发器为 statement BEFORE：尝试同键事务级共享 advisory lock，拿不到立即以 SQLSTATE 55P03 拒绝；不能拿着既有业务锁等待反向的全局锁。随后 `SELECT ... FOR SHARE` 读取屏障行；有 activeBatchId 时同样拒绝。行锁读取保证旧事务快照不能把已经冻结的状态误读为开放；旧 REPEATABLE READ 触发的 serialization_failure 也转成 55P03。55P03 沿已有完整事务回滚/确定未生效的 503 语义处理。

准备事务先取同键事务级独占 advisory lock（受既有数据库等待时限限制），再锁屏障行；已有源写事务的共享锁结束后才能开始。然后建立批次、完整源 id/revision 清单、计数和 activeBatchId，同事务审计。不能成功冻结不完整的源材料：源缺少当前正文/修订时失败回滚。

后续复制/失败登记/释放按 屏障行 → 批次行 → 源文档 id 顺序 → 检查点/资源 顺序。复制批次持屏障共享锁，控制状态持必要行锁；release/abort 不能在一批中途放开源写入。普通写入的守卫只尝试全局锁，避免与原有空间/文档/资源锁成环。源清单不先取写锁：到期删除检查点会经 FK SET NULL 更新回执，复制也须按检查点 → 源回执顺序，批次互斥由屏障与批次行承担。完成/释放先按 id 聚合持住全部证明检查点的共享锁，再取新数据库时刻核对；审计可能等待，返回完成回执前再次核对期限，失效整单回滚。真实锁交错归 S4 验证。

锁和触发器的机制依据 PostgreSQL 18 [显式锁](https://www.postgresql.org/docs/18/explicit-locking.html)、[触发器时机](https://www.postgresql.org/docs/18/trigger-definition.html)与[函数快照](https://www.postgresql.org/docs/18/xfunc-volatility.html)；正确性最终以本仓真实库交错和进程用例验证。

## 6. 运维服务与命令

使用独立 CLI 应用上下文，沿现有 app 层组合模式；不启动 HTTP、Jobs、SDK 或图片进程。配置/数据库/日志沿现有模块公开入口，领域服务仍在 Documents。

`node dist/cli/document-checkpoints.js` 提供：

- `prepare --target <标识>`：建立冻结批次并输出 batchId/状态/源数量/writeFrozen。已有批次时拒绝另建，提示先 status/resume/release/abort；未知提交后按 status 查现有批次，不生成第二份。
- `resume --batch <uuid> [--batch-size <1..100，默认 20>]`：逐批处理待完成源。原 gzip、信封与实际图片关系经 S1 before_upgrade 捕获，eventId=batchId；检查点和对应 source 回执在同事务。检查点已到期/缺失时重新捕获；源 revision 必须与冻结清单相同。处理中断只回滚当前批，已提交批次保留。
- `status [--batch <uuid>]`：只读给出当前/指定批次、目标、状态、计数及 writeFrozen；不输出文档 id 列表、正文或用户信息。
- 全部 source 都对应本批、本源、未过期的 before_upgrade 后，状态才转 ready；完整性复核与完成审计同事务。ready 仍冻结，重复 resume 在事实仍完整时不重复审计；已过期时回到处理并补齐。
- `release --batch <uuid>`：仅 ready 且即时完整复核通过时解除冻结，标 released 并审计。重复 release 只回自己的既有结果，不影响其他批次。未来真正转换快照的升级流程另行设计，不提供临时绕过守卫的开关。
- `abort --batch <uuid>`：明确放弃未释放批次、解除冻结；已生成检查点保留 30 天，标 aborted 并审计，不能宣称升级检查点完成。重复 abort 幂等。

审计使用有界 `batchId/targetVersion/documents`（失败只给有限 reason），系统 actor、cli origin，无 target；prepare/ready/failed/released/aborted 各明确区分。失败不会自动 release；SIGINT/SIGTERM 做完当前短批后退出，输出仍冻结和接续方式；硬终止依赖数据库事务回滚及持久状态恢复。CLI 参数错误退出 2、执行失败退出 1、完成命令退出 0；中止返回非零。标准输出为有界 JSON 回执，日志写标准错误，不带连接串。

## 7. 必验反例与自审

- 清除时 admin 已降级/被撤/源移走或归档；viewer/单独 editor/无内容权系统管理员；清除和恢复双向等待；审计故障全部回滚；当前正文、租约、小时桶/回执、ops、其他文档与副本不变。
- 7/30 天边界、锁住到期行后的跳过/下一轮补清、未过期源、同小时清除后保存不重采、停止/独占竞争/批次异常；引用减少但文件仍在。
- freeze 前已有保存必须先完成；freeze 后所有源 DML（含零行语句/TRUNCATE）拒绝；已有旧 REPEATABLE READ 事务不能绕过；仅写入代次与权限撤销仍可用；读/重放不变。
- 多批捕获、并发 CLI、缺失/损坏源、原 gzip 与格式/引用保持、部分批失败、当前批硬终止、未知提交、异进程 resume、ready 前拒绝 release、错误 batchId、不误解冻别的批次、过期回执再捕获。
- 三浏览器清除确认/结果未知/空态/预览失效；完整生产构建、原预算、全仓门禁及阶段独立审查保持。S4 不替代 S5 资源 GC 或 M7 备份恢复演练。

自审：选定边界均来自 P4；新模块不反向依赖；源集合/冻结/批次/审计有明确事务归属；不可变正文不更新；危险运维行为只在运维明确调用时发生。具体锁交错、实际 CLI 和异常取证归计划中的测试任务，未通过前不宣称可用。
