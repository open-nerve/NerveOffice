## 1. 目标与范围

落实已批准总设计 §6.5：编辑者能读回最近 7 天的小时级历史，独立只读预览，恢复为新文档；空间管理员可清除用户历史并留审计。删除和升级前另存 30 天运维检查点。资源回收同时保护当前文档、历史、检查点、副本及备份水位。覆盖 US-M5-10、11、09 的历史恢复部分与 DEF-061。

这是一个新增子系统，按架构设计处理。用户已批准 M5 总设计并授权按 Phase 自主推进；依 CLAUDE.md 的 JIT 流程，自审后实施，无需重复请求常规 Phase 审批。意外的数据丢失、权限或架构风险仍须按项目规则处理。没有逐操作回放、差异比较、就地回滚、SDK 升级或服务端快照迁移。

## 2. 代码事实

- `document_contents` 只存当前 gzip；`document_revisions` 和 `document_save_receipts` 支持修订与幂等，不存历史正文，不可冒充历史。
- `DocumentContentService.save` 先校验/去重，锁下核对权限、租约、代次和基准修订；changed 分支写正文后替换已授权图片关系。相同正文及请求重放提前返回。
- 创建、当前复制、本机草稿副本各有独立服务，均复用请求账本。复制保留 SDK unitId、原 gzip 和获授权关系，平台 id 重新生成。
- `document_asset_links` 只表示当前引用；`DocumentAssetAccessService` 的当前访问不会因未来保留关系而自动放宽。
- Assets 已有不可变文件、按 hash 去重、持久配额和失败 claim，但没有正式删除能力；文件 IO 不在数据库事务里。必须完成完整引用判定和故障恢复后才启用删除。
- P3 已按实际关闭回执完成交付。旧证据归档不改变 P4 的完整质量门槛。Excel/Safari/Finder 及 M4 既有挂账继续隔离。

## 3. 设计

### 3.1 方案选择与边界

考虑三种方式：只保留修订元数据不能恢复正文；另做文件快照增加数据库/文件双写和恢复边界；在 PostgreSQL 中保存不可变 gzip 检查点可与正文、引用一起提交。因此采用第三种，复用现有 bytea 与事务模型，不增加依赖。

Documents 持有历史正文、小时采样、权限、恢复及引用的业务规则。Assets 负责对象生命周期、文件操作与配额，始终不导入 Documents。Workspace 编排用户查询与保存人姓名；Jobs 只调用公开服务。前端历史流程使用编辑器适配层的独立阅读实例，SDK 对象不进入平台 API。

### 3.2 数据与时间

`document_checkpoints` 保存 UUID、源平台文档 id、种类 `hourly/before_delete/before_upgrade`、源标题/类型/unitId、平台与插件档案、SDK/客户端版本、修订、公式待更新状态、gzip、raw/stored 字节数、原规范化内容哈希、gzip 字节 SHA-256、资源名、保存人、生成时间、到期时间。写下后禁止 UPDATE；删除只能由有权限的清除/过期流程执行。

检查点的源文档 id 是溯源身份，不通过级联外键跟随永久删除；否则删除前检查点会一起丢失。普通历史 API 必须先找到当前仍可访问的源文档，运维检查点只走运维入口。原正文或旧信封的缺陷不被“修复”为假数据：旧存量的规范化哈希允许如实为空，但 gzip 字节摘要始终存在；读取和恢复复核格式/完整性，不把损坏正文当有效恢复材料。

`document_checkpoint_assets` 保存每份检查点已经获授权的 assetId 集合，checkpoint 删除级联删关系，asset 外键 RESTRICT。不得从正文里的任意地址补出授权。

`document_history_buckets` 单独保存源文档/UTC 小时的唯一占位，不带正文，随文档删除；清除用户历史不删除该小时占位，防止同小时清除后再保存制造第二份。到期清理按独立短批处理，保留不少于用户历史周期。正文与小时占位在同一事务里成功或回滚。

采样时间取数据库，UTC 自然小时第一次成功写入的 changed 内容生成一份，后续同小时不覆盖；新建/副本初始正文也计入当小时。无变化、失败和请求重放不采样。服务端时钟可在测试中替换，客户端不能提交采样时刻。时间在取得必要业务锁后固定，所有同批元数据用同一时刻，列表按生成时间与 id 稳定倒序分页；界面显示本地时间。

### 3.3 写入、复制与运维检查点

小时采样通过文档域内部的 `DocumentCheckpointService.captureHourly(documentId, transaction)` 入口：调用方已持文档写锁，或该行是本事务新建且尚未公开；先占小时桶，再在数据库中 INSERT…SELECT 当前正文、信封、实际修订保存人和已授权关系，不把大正文搬出数据库再压缩。必须在正文和引用都落入本事务之后调用。

用户恢复以历史 id 和目标空间/文件夹、标题、requestId 请求。按当前源文档的历史权限和目标新建权限锁下复核；复制历史原 gzip、unitId 与格式信封，产生新平台 id、修订 1、独立权限和合法图片关系。请求摘要包含源文档、历史 id 与目标输入，重放不受后续改名/移动影响。原文档、编辑代次、租约及本机草稿不变。

删除文档及删除文件夹中的全部活动文档，在现有锁下、改变状态前生成 `before_delete`，失败则删除整体回滚；再次恢复后删除是另一实际删除事件，可有新检查点。永久删除不清除仍有效的运维检查点。

升级前提供只供部署使用的检查点命令和批次回执，记录目标版本、完整源集合、完成/失败状态。写入与升级检查点使用同一屏障协议，禁止仅扫描一遍就宣称覆盖并发修改；S4 的 spec 确定锁范围、退出和接续，并用真实并发证明。此 Phase 不执行 SDK 升级、不实现快照格式转换。

### 3.4 用户契约和界面

- `GET /api/documents/:id/history`：有界分页，时间、保存人、修订与格式说明；仅有效内容角色 editor/admin。
- `GET /api/documents/:id/history/:historyId`：元数据和兼容性；`.../content` 返回原 gzip；两者均独立鉴权、只读事务快照、禁止缓存。
- `POST .../:historyId/restore`：恢复为副本，沿用创建的 requestId、目标权限与响应约定。
- `DELETE /api/documents/:id/history`：仅当前空间管理员；清除 hourly 与其引用，写审计；不清当前正文、运维检查点、小时占位、保存回执和本机草稿。

查看者对历史列表、正文、恢复均不能取得材料；不可见对象与不存在统一回答。图片读取的授权并集为当前可读引用，或有效用户历史且调用者现在可看该历史；运维检查点不加入普通成员授权。降级、归档、撤权、跨空间移动和过期后，每次请求重新判定。

历史页面/入口置于已有文档流程，处理加载、空、失败、撤权与格式不兼容。预览独立实例，绝不申请编辑租约、创建发件箱、自动保存或改写原文档。损坏历史明确不可恢复；打开自检失败时提供历史入口与无历史的真实说明，不能直接复制当前损坏正文来“恢复”。

### 3.5 回收、备份与并发

先过期检查点，再判断 assetId 的全部保留引用，最后判断物理对象是否仍被任何 assetId、上传 claim 或删除任务占用。不能以当前可读权限代替保留资格，也不能仅以对象上传时间计算宽限：资源成为无引用候选时才开始计时，任何新合法引用使候选失效。

所有引用写入与 assetId 回收在同一有序资源锁协议下互斥。顺序沿已有 requestId → 空间树 → 空间 → 文档 → 检查点/资源；回收不倒向取文档/空间锁，在持资源锁后重新查全部保留关系。物理回收使用持久删除任务，先确认可删并提交，再执行文件 IO，最后确认并释放配额；崩溃、未知提交、重复执行均可接续。文件删除与新上传相同 hash 必须有可靠的代次隔离，不能只靠进程内锁或超时租约。S5 详细设计须以现有 hash 对象、claim 和私有文件规则为基础，明确旧文件兼容与故障注入结果，再开放删除。

部署显式声明备份保留期、GC 宽限及恢复水位，宽限不得短于备份保留期。缺少或不可信的恢复水位时暂停物理回收并说明原因，不影响保存、读取和历史功能；不能把“没有当前引用”当作备份已安全。S5 把此安全停用条件、运维设置及测试写进部署文档，不宣称已完成 M7 备份恢复演练。

### 3.6 错误、审计与容量

坏格式、缺失历史、权限、存储损坏与系统忙按现有统一错误规则处理；禁止日志输出正文、图片字节、密钥或请求摘要原文。清除、恢复、删除前/升级前检查点及 GC 记录有界元数据，批量操作记数量和批次，不写无界 id 数组。

至少按现有小、中、大三份快照实测小时采样写入延迟、数据库/TOAST、WAL 与 7/30 天保留估算，测有图片与重复字节的成本。初版保留原 gzip 不承诺跨版本去重；若容量不能满足部署预算，先用证据说明再决定，不悄悄降低保留期。重型验证串行，实际磁盘余量满足门禁再开始。
