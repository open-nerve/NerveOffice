# P4-S6 数据库错误日志帧脱敏修复

日期：2026-10-29（上海）。状态：局部实现、回归及独审通过；P4未关闭。

## 受控复现与影响边界

七万资源CI诊断审查发现，旧数据库异常序列化对整个stack筛选`at`开头行，却没有先剥离完整错误消息。Drizzle会把绑定参数拼进消息，参数内部换行后的伪帧因此可能保留在stack；按键名的日志脱敏不处理这个字符串。

受管KiB控制探针使用实际searchKeywordSchema和titleSearchPattern、真实Drizzle错误类及生产root/child logger。普通单行自制标记没有进入stack，合法内部换行伪帧标记在两种日志中均进入stack，msg字段均未泄露标记。六份来源在导入前、输出后相同；运行91f7de7d-effe-4a92-81b3-bde6507ceae2通过并实际清理。原件见主目录`s6/hosted-vm-policy/logger-frame-probe-20261029/`，报告SHA-256 `8d61581d29c8fdcdb50c19c6b3bf70c845022763abd7479facf0ff2f85cd6583`。

该控制探针没有执行HTTP/数据库请求，没有使用真实业务数据。后续回归另在现有测试HTTP路由和真实PostgreSQL22P02错误中复现。证据确认局部参数脱敏缺陷，不能宣称历史用户数据已经泄漏或存在越权外传。独审据此限定为应修的单模块隐私加固，不改变搜索输入契约、SQL、权限或资源门槛。

## 最小实现

生产仅修改logging/error-serializer.ts的数据库分支：用Error的完整name/message构造准确header，确认stack以整个header加换行开始，移除后才筛选调用帧。空name/message按标准文本形态处理；字段非字符串、读取异常或前缀不匹配时省略DB stack，不回退扫描整串。SQLSTATE、占位符查询和其他既有结构化诊断保留，普通异常及现有framesOnly文本筛选语义保持。

测试沿用logging模块的结构化Error夹具，没有增加对pg/drizzle库的跨模块例外。真实库链由现有HTTP/PostgreSQL测试覆盖：只强化已有/failure探针的自制参数，保持原route、`SELECT $1::uuid`、22P02、500响应及旧断言，新增根/子/请求结束日志和响应均不含伪帧标记的核对。

唯一跨测试联动是bulk诊断的non-string-stack案例：生产serializer现在合法省略该stack，不再要求它触发diagnostic-incomplete；SQLSTATE、无标记、无原异常对象断言保持，throwing-getter仍要求不完整标志。没有修改bulk helper、七万案例、数据规模或超时。

## 验证过程

先RED后实现：serializer、root/child原始JSON与真实HTTP/PG路径合计8个目标失败，证明旧参数伪帧进入日志。首次GREEN有131通过、3失败，其中1项为上述明确联动，另2项来自新增空header夹具。
