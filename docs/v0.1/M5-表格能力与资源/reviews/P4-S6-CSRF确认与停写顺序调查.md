## 为什么不能简单删掉第二次确认

同一 requester 页的原始 trace 单调时间如下，单位 ms：

| 事件 | 开始 | 耗时 |
|---|---:|---:|
| PUT 请求编辑续期，403 | 371277.957 | 2.629 |
| 加载 browser-session-failure 脚本，200 | 371280.696 | 2.000 |
| 第一次 GET session，200 | 371281.185 | 11.438 |
| 第二次 GET session，200 | 371299.631 | 7.583 |
| 十次健康检查的第一、最后请求 | 371299.774 / 371326.359 | 均成功 |

第一次 GET 已发出时，执行本机停写的模块还没有完整接收。生产 `session-activation` 在发 GET 前就固定本机票据，`session-fence` 不允许旧票据穿越后来的停写代次。因此按当前代码和原件推导，第一次响应至多仍关联旧许可，或者因停写而不再关联许可；不能声称第一次确认已经取得新的有效许可。trace 没有直接记录内部停写/接受的先后，具体属于这两支中的哪一支仍需受控回归核实。

`f2e28647` 的页面匹配 stopped 后补查解决了图片 401 后本机许可缺失、无法再次编辑的问题。但遇到普通 CSRF 错误时，错误处理触发的确认可能已经在路上，本机停写又需要一次新的确认。这与现有续期节奏断言发生冲突。此前局部图片通过和 505 项回归没有覆盖这条完整组合路径；本轮完整门禁发现了它。

## 已排查的局部方案

1. **在途确认若已取得新许可，就消掉冗余补查。** 这是可以单独验证的优化，但上面的原件反证说明不能将其当作本次根修。没有为这个不同顺序写一个绿色用例来代替原失败，也未修改生产代码。
2. **只在用户下一次点击编辑时补查。** 自动交出后获得编辑权的 grant 路径会直接进入状态机，绕过页面按钮的确认入口；同时 `beginRestore` 锁存点击时的恢复代次与所见原件。整体后移准备步骤可能改选确认期间才出现的原件。要保持这些边界就必须扩展状态机接线，不是等价的一行修复。
3. **推荐：统一相关请求失败与后续确认的顺序。** 原认证错误仍立即交给调用方；同时准确登记该原请求已经触发的本机失效处理。后续会话查询在取得本机票据之前，先以有界方式等待与本轮来源相关的已登记失效处理结束，再执行真实查询。不能等待任意任务，不能持同源锁等待，也不能给旧响应换发新票据、自动重放失败操作或吞掉原错误。

第三项涉及请求层、会话跟踪、本机资格和页面协调：主要候选入口为 `shared/api/client.ts`、`shared/api/session-tracking.ts`、`shared/local-drafts/session-activation.ts` 与 `features/sheet-editor/editor-page.ts`。仅在 API 增加等待仍不够：页面须识别已被这次新许可覆盖的 stopped 复核，避免它继续设置冗余下一轮；其他错误、广播和令牌新鲜度要求的 checkAgain 仍保留。精确登记身份、等待上限、取消和存储不可用的终态还要在实施计划与先行失败测试中固定；等待超时不得凭旧许可放行持久写入，也不能一并禁用合法的初始内存模式。本报告不把未验证的队列或等待策略写成既成安全保证。
