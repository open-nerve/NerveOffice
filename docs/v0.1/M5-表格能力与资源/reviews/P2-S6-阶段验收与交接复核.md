## 源码因果链

逐段核对了以下实际实现，而非只依据实验说明：

1. `fake-lease-clock.test-support.ts` 的 `settle()` 只是一个真实 `setTimeout(resolve, 0)`。`advance()` 内部也使用这个帮助函数。有限次让步不能保证 `CompressionStream`、WebCrypto 或后续 Promise 链完成。
2. 该用例的 `setup()` 没有传入 localDrafts，编辑草稿走内存来源。`memory-working-draft.ts` 的 `write()` 实际执行 `Promise.all([gzipBytes(bytes), sha256Hex(bytes)])`；没有使用假的压缩结果。gzip 通过流读取异步完成。
3. 首次 `save()` 被 `NetworkError` 拒绝后，保存协调器保留结果未知的请求和固定上传。失权调用 `captureLostContent()`，其 `commitCellEditing=false` 形成 `inputLeft=true`，并以 `dedupe:false` 捕获当前正文。
4. `working-draft-source.ts` 的 `capture()` 启动 `pump()` 写入任务；执行期间 `running=true`。与此同时 `readLatest()` 在 `entry.snapshot` 仍被保留时可以直接返回该文本，因此 `lose()` 可先重建只读编辑器、进入 `lost` 且 `checking=true`，无须等待新捕获的 gzip/摘要已结束。这解释了“已经 lost”也不能证明核对完成。
5. `lose()` 接着等待 `saver.replayUnknownOutcome()`。`save-coordinator.ts` 的 `replayOnce()` 在真正 `send()` 之前必须 `await mark(target)`，后者等待 `draft.markInFlight()`。
6. 工作草稿的 `markInFlight()` 经 `mutate()` 加入 `controls`；同一个 `pump()` 在 `running=true` 时不会执行控制操作。因此新捕获 write 尚未完成时，旧请求的重放标记需要排队，第二次 API 保存尚不能发生。即使内存后端的标记操作本身很快，也不能绕过公共串行队列。
7. write 结束后控制队列继续，重放发送、确认并完成；`lose()` 最后以 `mode.inputLeft || saver.hasUnsavedWork()` 计算剩余未保存工作，再设 `checking=false`。所以核对旧保存成功后仍须保留 `unsaved=true,inputLeft=true`，正是原用例要守住的语义。

这个等待缺口足以解释已观测的 “save=1” 症状；没有证据表明应改草稿串行化、失权重放或未提交输入的产品行为。
