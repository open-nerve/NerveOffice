## S3 IMAGE 首参两侧的空白：CX2（2026-11-16）

先写测试：

- `image-formula-address-sdk.test.ts`（新增，真实解释器）：把 JS 的 `\s` 集合（与 `trim` 相同，共 25 个码位）逐个放在首参前、首参后与括号组内，要求两边一致——SDK 以本站地址执行原 IMAGE 的，写入规范必须改写；改写之后 SDK 仍以相对地址执行，`extractAssetIds` 能提取引用。另以 U+200B、U+180E、U+00AD、U+2060 作对照：SDK 不认，规范也不改。
- `image-formula-address.test.ts`：补 7 条显式改写用例（U+00A0、U+3000、U+2003、U+FEFF 在首参前，U+00A0、U+3000 在首参后，括号组内的 U+00A0）。

旧代码上 8 条失败：7 条显式用例，以及一致性用例列出的 63 处不一致——21 个非 ASCII 空白码位（U+000B、U+000C、U+00A0、U+1680、U+2000～U+200A、U+2028、U+2029、U+202F、U+205F、U+3000、U+FEFF）在三个位置都是“SDK 执行、规范未改写”；4 个 ASCII 空白与 4 个非空白对照都一致。

修复：`skipSpaces` 改用与函数名、括号之间相同的 `/^\s$/u`，去掉只有 4 个 ASCII 空白的集合。修复后 4 个相关文件 109 条通过（含 `image-source-policy.test.ts`、`image-formula-source.test.ts`）。

## S4 SDK 缓存命中时补读：CX3（2026-11-16）

先写测试：`platform-image-io.test.ts` 新增“SDK 缓存命中时补读刷新跳过的来源（M5-P9 CX3）”4 条，用真实 `ImageCacheMap` 与平台 IO：

1. 首读失败 → 来源移出文档 → 恢复联网刷新（不读取）→ 撤销后命中：补读一次，同一元素换上像素，之后的命中不再读取；
2. 补读仍失败照常报告，同一轮不反复读取；
3. 已显示的图删除 → 暂停 → 恢复时静默补读失败 → 撤销后命中照常读取；
4. 暂停时命中不读取；读取进行中与已有像素时命中不另读。

旧代码上前 3 条失败，第 4 条是防止多读的约束，前后都通过。

修复：

- **core 补丁**：在既有的 core 补丁上（按 ADR-022 的流程，编辑目录与日志在主目录 `.codex/handoffs/m5-p9-20261116/cx3/`），`ImageCacheMap.getImage` 命中时若实例的 `IImageIoService` 提供 `revisitImageSource` 就先调用；服务每个缓存对象只取一次。摘要：
  - ES 入口 `b6c2ba0d…` → `3d01c872…`；
  - 补丁 `e2754858…` → `c5e46592…`；
  - `patches/univer-images.json` 同步；CJS 未改。
  - `linux_browser_evidence.installed_patches` 核对 16 个补丁包的补丁与安装字节一致。
- **平台**：`image-resources.ts` 的 `unread` 集合与 `revisit`（刷新时跳过的、SDK 仍持有而没有像素的已删来源，与静默补读失败的来源；暂停、刷新与结束时清空）；`platform-image-io.ts` 的 `revisitImageSource`。
- **旧用例注释**：`image-resources-lifecycle.test.ts` 里“在用的读取加入”手工调用 `load`，那是浮图重建图元的路径；单元格图片的路径改由新用例覆盖，补了一句说明。
