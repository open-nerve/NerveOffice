不建议直接恢复当前开发机的整轮浏览器长测；现有证据不能证明首次崩溃风险已消失。分段运行也只是一种待验证的减负方式，不能先声称能防止崩溃或等价覆盖全部用例。

独立 Mac 的可用性不是已经验证的事实。GitHub 提供标准 Mac runner，但其 service container 仅支持 Linux；现有 PostgreSQL service、仅接受 Ubuntu 的托管资源合同和 Mac 桌面条件不能原样搬过去。标准规格也不等于项目实测可用空间。[GitHub runner 说明](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)、[service container 限制](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers)（2026-11-04 只读核对）。本建议未创建新 runner、改工作流或购买资源。

## 建议方案的限定执行范围

若需求方选择先工程交付，批准对象仅为 **M5-P6 的工程合并和开发接续时序**：

1. 当前 Linux 六项全部通过，精确用例/首过/原跳过、CSV、请求对照最终附件、实际预算与资源记录全部核对，独立原件审查接受后才进入工程收尾。真实产品或自动化失败仍先处理；不沿环境欠账放行。
2. 更新计划书修订记录、工程完成定义、ADR、M5 总设计/交接和延期登记，明确工程交付与完整平台验收的区别。记录待验用例范围、固定输入、执行前提、责任与 M7 前的补验/裁决节点，不把时间到期当作自动接受。
3. 沿唯一 P6 分支完成结果文档和审查，正常中文提交及 hooks；主目录保持 main，用 `--no-ff` 合并并正常推送。源代码相对已验输入若再变更，先完成对应复验与审查，不能用文档等价掩盖代码变化。
4. 最终 main 必须取得同 SHA 原六项 CI 与原件接受；Phase 分支预验收不替代它。通过后才冻结必要证据、核对本轮资源，正常退役 P6 worktree/分支。保留来源不明的旧残留，托管 VM 仍只记 `host-disposal-pending`。
5. 状态写为“M5 工程交付完成，Mac/原生平台完整验收待补”，不关闭完整 M5、不打里程碑标签、不宣布可发布。M4 的独立欠账不随之关闭。
6. 后续可准备 M6 总设计，仍按原规则先经需求方审批，再实施各 Phase。DEF-013 在 M6 实施前的真实 macOS 输入法核对仍有效，不随本建议推迟到 M7。新阶段的产品缺陷、平台失败和验证范围逐次判断，此次例外不自动适用于后续所有 Phase。

上述调整会改变原 P6 合并的前置顺序，因此必须明确批准。它保留全部测试、断言、覆盖率、重试判失败、资源限制和最终上线要求，但会把 Mac 回归的发现时机后移；这是建议的实际取舍，不能写成“没有任何验收缺口”。

## 后续验收如何关闭

Mac 待验最终需要相应受测源码的原完整范围、报告/源码对应、资源处理与独立接受；Linux 或旧 Mac 通过不能直接代签。WindowServer 根因调查独立保留：在合格的隔离 Mac 上实际通过可以提供产品平台证据，但不能据此宣称当前开发机故障根因已修。

若到 M7 仍无可用环境，必须带剩余范围请求明确裁决，不能自动取消 Mac/Safari 支持、关闭质量门槛或发布。当前用户无需安装 Excel、提供密码、手动运行脚本，也无需为本建议先购买设备。
