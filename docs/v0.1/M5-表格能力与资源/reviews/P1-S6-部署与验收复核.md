## 正式处理、并发与持久化（Task3）

新增 `specs/deploy/image-deployment.spec.ts`，与既有后端重启共用 restart 项目。该项目固定一个工作进程，等所有普通浏览器和崩溃项目结束后执行；矩阵、配额锁与重启不会干扰其他图片故事。本机模式同样执行所有公开协议检查，容器指标仅在真实容器中记录。

1. 全部 44 份输入先核对原始摘要，再走正式 HTTP 上传：20 份成功、24 份按对应规则拒绝。成功图片全部经过浏览器解码，核对尺寸、类型、返回字节与数据库对象摘要、动画帧数；最后再次成功上传最小图片。矩阵不复用诊断处理器，也不把浏览器首帧解码冒充逐帧像素验证；逐帧独立验证原件仍见 S3 报告。
2. 用独占的真实数据库行锁阻塞第一份上传，观察 `pg_blocking_pids` 确认正式应用确实在等待。本人后续五份仅一份排队、四份返回 ASSET_BUSY；再来四名用户仅三份排队、一份繁忙。释放锁后共 5 成功/5 繁忙，成功 ID 独立，繁忙响应均 Retry-After=10，存活探针与下一次上传正常。没有产品测试开关或伪造服务。
3. 真实上传后经租约/保存建立当前引用，移出上传者 24 小时窗口，再强制结束后端。在容器模式额外 `--force-recreate` 并断言容器 ID 变化；正文/修订、元数据/关系及图片字节不变，匿名鉴权地址返回 401，静态路径不能读到原件。本机模式只证明进程重启，容器持久性由真实镜像那一轮作证。
