## S2 M5R-I-04 地址提取的包裹符剥离改为线性实现

**修复**

`packages/contracts/src/documents/asset-references.ts`：去掉 `^[([{<]+|[)\]}>]+$` 这个可回溯正则，改为下标线性扫描 `stripWrappers`。它去掉词首连续的 `([{<` 和词尾连续的 `)]}>`，语义不变。另加前缀预筛：字符串不含 `/api/assets/` 时直接返回空，绝大多数正文字符串不再分词。

**失败用例（修复前）**

| 层级 | 用例 | 修复前结果 |
|---|---|---|
| 单元 | `asset-references.test.ts` 的四个对抗长度用例 | “长串结尾包裹符后接普通字符”“地址前缀后接长串结尾包裹符与普通字符”两例分别耗时 20,012 ms、20,058 ms，超过 1,000 ms 上限，失败。其余两例原实现不回溯，修复前已通过 |
| 集成 | `asset-save.test.ts` 新增 “M5R-I-04 …保存在检查时限内正常返回” | 正文含两段百万字符的对抗串。快照检查子进程约 10.3 秒后超时，保存返回 503 而非 200。这证明一次请求就能占住一个检查进程直至超时 |

集成用例的修复前运行，是把实现临时还原为 HEAD 版本并重新构建 api 后执行的；随后恢复修复版本、重新构建，再验证通过。

**差分与有效变异**

- **差分对照**：新增用例以原正则实现为对照。字母表为 `([{<)]}>x/`，在地址前后各接 0～2 个字符，并覆盖三种上下文，共 36,963 个组合（111×111×3）与原实现逐一一致；另覆盖只有包裹符、首尾交错和中间夹括号的样本。
- **变异一**：把词首剥离的 `while` 改为 `if`。差分用例与“合法地址被长串包裹符包住”失败（3 项）。
- **变异二**：词尾剥离误用词首集合。原有“独立地址或公式字面量”两例与差分用例失败（5 项）。
- 两次变异均已恢复。

**同类检查**

contracts 与 api 中其余带 `$` 的正则都以 `^` 锚定，并且只有单一字符类或分隔确定的量词，是线性的。没有发现别处存在“未锚定起点的 `[…]+$`”写法。检查子进程启用 V8 线性正则回退作为兜底，这次不做，因为根因已经消除。

## S3 M5R-I-01 图片写入策略的预算口径，联动 M5R-M-10 拒绝反馈通道

**修复**

- `apps/web/src/editor/images/image-source-policy.ts`：
  - 片段访问器的预算改为按顶层片段计。一次 `normalizeImageFragment` 的整个值共用一份预算；单元格与行列的每个 `p`/`s` 各自一份。预算只约束单个片段的规模（10 万节点）与深度（64）。整次写入的规模由原有 `cells: 1.5M` 上限约束，不再让大范围写入共用一份预算。
  - SDK 撤销与清除为每格补的 `p: null`、`s: null` 不作为片段访问。
  - 新增 `imageTransition`，返回带原因的结果（source/limit/structure）。原 `acceptsImageTransition` 保留为布尔包装，语义不变。
- `apps/web/src/editor/profile/image-command-input.ts`：拒绝时带上片段的有界原因。
- `apps/web/src/editor/profile/image-policy.ts`：判定器返回“放行”或最后一个失败判定的有界原因：
  - `write-source`、`write-limit`、`write-structure`；
  - 背景图命令为 `write-unsupported`；
  - 未归类的失败按 `write-structure` 处理。

  `installImagePolicy` 的第三个参数改为 `{ failed, rejected }` 两个通道：图片显示与资源请求失败仍走 `failed`，写入策略拒绝改走 `rejected`。
- `apps/web/src/editor/sheet-editor.ts`：`rejected` 转成 `onImageOperation({ kind: 'failed', operation: 'edit', reason })`。编辑页显示“操作未完成。＋原因”，不再置 `imageProblem`（“部分图片暂时无法显示 / 重新加载图片”）。
- 新增操作 `edit` 与四个原因的类型和文案（`system-image-input.ts`、`shared/i18n/zh-cn/editor.ts`）。原因文案不回显来源、文件名或输入内容。

**失败用例（修复前）**

| 层级 | 用例 | 修复前结果 |
|---|---|---|
| 单元（纯函数，`image-source-policy.test.ts`） | 6 万格 `{p:null,s:null}`、6 万格加粗、6,000 格四边框、1 万格样式加富文本、6 万项行样式 | 均返回 limit |
| 单元（纯函数） | 大范围写入中的非法来源 | 被预算抢先判成 limit，不是 source |
| 单元（纯函数） | `imageTransition` | 尚不存在 |
| 单元（真实 SDK，`image-commands.test.ts`，3,000×20 表） | 6 万格清除后撤销 | 撤销被拒，即“能删不能撤销” |
| 单元（真实 SDK） | 6 万格加粗；6,000 格四边框；1 万格带格式富文本写入；3,000 个链接格写入 | 均被拒 |
| 单元（真实 SDK） | 写入拒绝的通道 | 只走了图片失败通道 |

**修复后新增覆盖**

- 同一批大范围用例都断言：图片失败通道与拒绝通道均未被调用；
- 大范围写入中只要一格含非法来源，仍整批拒绝，并给出 `write-source`；
- 同源绝对地址仍归一；
- 单个片段超出规模或深度时仍按 limit 拒绝；
- `sheet-editor.test.ts`：`rejected` 只产生编辑失败状态，`failed` 仍报图片失败；
- `image-input-notice.test.ts`：四个原因的可见文案。

**有效变异**

|---|---|
| 去掉每个片段的预算重置 | 11 项失败（纯函数 6 项、真实 SDK 5 项）。“6 万格清除后撤销”一例在这个变异下仍通过，因为空位不计数的改动本身也覆盖了这一形态 |

## S4 M5R-I-03 `IMAGE()` 首参的本站绝对地址写入时规范为相对地址（D-02）

**修复**

- 新增 `apps/web/src/editor/images/image-formula-address.ts` 的 `normalizeImageFormula`。识别 `IMAGE(` 之后首参恰为字符串字面量（可包透明括号，前后可有空白）的调用。字面量解码后是 `${origin}/api/assets/<uuid>` 时，改写为 `"/api/assets/<uuid>"`。识别规则与固定 engine-formula 补丁的首参证明一致（P2-S3 §3）。
  - 扫描时跳过字符串字面量（`""` 转义）、单引号工作表名（`''` 转义）和结构化引用 `[…]`，不会误认其中的文字。
  - 名称须完整等于 IMAGE，不区分大小写，紧跟 `(`。
  - 以下写法原样保留：引用、拼接、一元运算、计算、第二个及以后参数、外站与非规范地址、未闭合的字面量。
- `image-source-policy.ts` 的单元格访问器对 `f` 调用它。普通命令与底层 mutation 都传页面 origin，因此复制粘贴与公式输入走同一策略，不另开入口。撤销与重做沿用改写后的值。历史预检传空 origin，不改写，也不阻拦旧记录。服务端仍只认相对地址。按 D-02 不做存量迁移。

**失败用例（修复前）**

|---|---|---|
| 单元（策略） | `image-source-policy.test.ts` “写入时把首参改为相对地址…” | 失败，公式未改写 |
| E2E（Chromium，`image-policy.spec.ts` 新增 US-M5-07 用例） | 同表只放绝对写法；保存后核对正文公式，另一成员分享后读取 | 用临时关闭改写的构建运行一次：保存的公式仍为 `http://127.0.0.1:…/api/assets/…`，用例失败。这说明原用例里同表的相对写法掩盖了缺引用 |

**有效变异**
