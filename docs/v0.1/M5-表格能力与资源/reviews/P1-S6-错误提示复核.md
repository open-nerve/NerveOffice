## 仅追加 Markdown 结果时的源码等价证据

可以保留已经通过的长时门禁证据，前提是证明后来变化确实只有已审阅的结果落档文件，而不是用扩展名概括所有变更。建议采用以下闭环：

1. **冻结实际受测代码。** 把本次两个源文件修复提交到 T，再启动完整门禁；记录 T 的完整 SHA、实际命令、工具/镜像版本及工作区状态。沿用现有 run-full-gate.py 的 source-before.json、source-after.json、源码副本、working.patch 和 checksums.json。每次完整运行必须 exit 0、前后源码清单完全相同；若运行中改过源文件，不能事后用“最终一样”推导全程未变。
2. **枚举实际文档差异。** 结果落档提交 F 后，对 T→F 保存完整 name-status/raw/binary diff；用精确路径白名单列出允许变化的审查报告、复核/交接记录，逐份审阅实际内容。不能使用“排除所有 *.md”或整个 docs 目录的宽白名单。
3. **比较剩余全部输入。** 将 T 的受测文件清单与 F/current 工作树清单逐路径对照：除已审阅白名单外，路径集合、文件内容 SHA-256/大小均须一致，新增/删除也算变化。已有 source_manifest 主要记录文件内容；另用 Git 的 raw diff/ls-tree 核对文件类型、可执行位和符号链接目标，避免同内容不同入口类型漏检。核对 staged/unstaged 与未跟踪文件，不能只比较 HEAD 或 index。
4. **单独判断文档是否也是机器输入。** [storiesGate](../../../../tools/src/gates/run.ts#L117) 会读取 tests/stories.json 中登记的总设计 Markdown；若更动这些文件，要核对提取的故事 ID/语义，必要时只重跑对应 stories 门禁。deploy/native-images/README.md 被实际材料收集器读取并随镜像分发，不能作为普通结果文档排除。CLAUDE.md、许可材料、构建说明等也须按实际差异判断。仅 reviews/交接中的结果计数与证据链接变化，且未被程序/门禁读取时，无需因此重跑数小时测试。
5. **留下可审计结论。** 生成独立的 source-equivalence.json/Markdown：记录受测 T、落档 F、各通过回执路径/摘要、完整文档变更白名单、非白名单输入比较结果、工作树干净状态及是否另跑文档相关检查。该报告应引用原始回执，不改写旧回执中的 SHA、时间或失败记录。

准确的表述应是：“完整门禁运行于 T；T 到 F 仅有列出的结果文档变更，已核对其余受测源、测试、配置、锁文件和必要构建输入未变，因此沿用 T 的本机完整门禁证据。”不能写成“已经在 F 重新运行了全部门禁”。

源码等价也不等于镜像逐字节相同。当前 [client-build.ts](../../../../apps/web/build/client-build.ts#L14) 与 Dockerfile 会把提交号写入客户端版本/镜像标签；文档提交造成 SHA 变化时，这些诊断元数据可以变化。最终合入 main 的同一 SHA 六项 CI 仍必须实际通过，不能由源码等价报告替代。

这套做法允许避免“结果文档写入→整套重跑→又写结果”的循环，但不豁免任何新的实现/测试/配置变化，也不把失败运行转为有效验收。
