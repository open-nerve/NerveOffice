## M1（Minor，待 S6 修复复核）：确定性图片拒绝丢失原因并提示稍后重试

### 触发、根因与后果

正式菜单选择本地元数据合法、内容非法的图片，或图片组织配额用尽。共享 API 已返回可信的结构化 ApiError，但 system-image-input.ts:34–41 只认识本地输入/剪贴板/解码异常和 NotAllowedError；ApiError 全部退到 request。editor.ts:128 将其显示为“请求失败，请稍后重试。”，确定性拒绝因此无法指导用户换图、减小图片或联系管理员。

现有真实可达例为 tests/e2e/specs/editor/image-production.spec.ts:265–272 选择 html-disguised.png。文件扩展名/MIME/输入大小检查可以通过，服务端完整解码返回 ASSET_INVALID（422）；当前故事只断言“未完成”，没有断言错误原因。配额路径更明确：packages/contracts/src/errors/error-codes.ts:75–76 定义 ASSET_QUOTA_EXCEEDED（409）和“图片存储配额不足，请联系管理员”；:110–111 定义 ASSET_INVALID（422）和“图片无法处理，请检查格式或使用较小的图片”。ASSET_INVALID details.rule 还区分 type/corrupt/dimensions/pixels/frames/animation/output/too-complex；这些都是既有上传服务和 codec/runner 可返回的业务拒绝，不是猜测的未来错误。

同一根因还出现在 platform-image-io.ts:131–137：仅本地 ImageFileInputError 映射大小/格式，服务端 BODY_TOO_LARGE（413）和 UNSUPPORTED_MEDIA_TYPE（415）均退为 ERROR_IMAGE，与计划书 §8.5 的 413 → ERROR_EXCEED_SIZE、415 → ERROR_IMAGE_TYPE 映射不符。它不绕过服务器限制，也不导致正文或权限损坏，因此列为 Minor，而非 Critical/Important。

### 建议与验证缺口

以已校验 code/status/details 的有限集合归类业务拒绝；不要直接把 error.message、文件名或原始地址搬进页面。保留取消/身份失效和网络/5xx 的既有行为。用实际 ApiError 补系统输入与 SDK saveImage 回归：413、415、422、409 quota，以及普通网络/未知错误仍通用提示。将真实 html-disguised 正式故事从仅“未完成”补到正确拒绝原因，并继续断言零插图/正常后续输入。
