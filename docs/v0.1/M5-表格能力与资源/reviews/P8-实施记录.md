## S2 Q-10 收紧与托管例外

### Q-10：lsof 全量列举只接受退出码 0

**决定**（2026-11-06）：三轮 CI 共 51 次采样，本机（macOS 27.0.1、普通用户、同一命令 `lsof -nP -F pfnt`）3 次，全部退出码 0、stderr 为空。需求方据此决定：退出码 1 即便 stderr 为空，也判为不完整。

**修复**：

- `tools/test-resources/lifecycle.py` 的 `open_paths` 由“退出码 0 或 1 且 stderr 为空”改为只接受退出码 0 且 stderr 为空；不完整时照旧保留资源，详情带上退出码与 stderr 字节数。
- `lsof_exit_sample` 与 CI 注解保留，作为新环境（例如托管 Mac）的观测。

**测试**：原用例“退出码 1、stderr 为空按没有打开的文件接受”改为三种情形——退出码 0 接受；退出码 1 且 stderr 为空判不完整；有警告判不完整。两种不完整都核对详情里的退出码与 stderr 字节数，采样函数照旧如实返回。

### 托管例外改为本分支

`tools/test-resources/hosted.py` 里 workflow_dispatch 的精确分支，由已退役的 `refs/heads/m5-p7-review-fixes` 改为 `refs/heads/m5-p8-final-closeout`。拒绝用例补两条：单改 ref 为已退役的 P7 分支；ref 与工作流 ref 都一致地指向 P7 分支。后一条在改动前被接受，用来证明例外确实随 P7 退役失效。

## S3 托管 Mac 探测

### 实现

- `.github/workflows/mac.yml`：
  - 触发：只由推送本分支触发，合并后可手动触发；不随 main 推送运行，`ci.yml` 不变。
  - job：`probe` 在 `macos-26`（Apple 芯片）与 `macos-26-intel` 上各跑一次。
  - 步骤：先记系统事实，再装 Node、pnpm 与依赖；PostgreSQL、Docker、浏览器安装与启动、Safari 这几步 `continue-on-error`，环境缺的能力只记下；最后记磁盘与内存。
- `tools/test-resources/ci_mac_probe.py`：
  - 只收集环境事实，不跑产品测试、不经运行器、不读写台账；
  - 每个命令都有时限，输出只留退出码、字节数与有界的尾部，环境变量只取固定的几个非敏感键；
  - 每段在日志里打印完整 JSON，并写一条 notice 注解。注解按工作流命令规则转义 `%`、CR、LF，超长截断。
  - lsof 用与运行器相同的固定命令，普通权限与 `sudo -n` 各采样 3 次；PostgreSQL 与 Docker 镜像都取与 `ci.yml` 相同的大版本和摘要。
- `tools/test-resources/test_ci_mac_probe.py`：11 项单测，覆盖命令时限与有界输出、找不到程序、注解转义与截断、只取允许的环境变量、lsof 固定命令与 C locale、brew JSON、浏览器启动失败照样记下、vm_stat 解析。

### 本机核对

- 本机试跑只读的 `final` 段时发现：vm_stat 的输出超过错误尾部的长度，页大小那一行在开头，只留尾部就解析不出空闲内存。已改为允许调用方取更长的 stdout，并补用例；把上限改回尾部长度的变异会被这条用例抓到（经 `run.py unit` 执行）。
- 本机没有试跑带 `sudo -n` 或钥匙串查询的 `system` 段，以免在开发机上留下提权尝试的记录。

### 改为 Apple 芯片版（第 3 轮之前，本地实现）

**会话保护**（`tools/test-resources/desktop_session.py`）：

### 第 3 轮（run `42407334017`，`af8badb3`）

四个 job 都在 `macos-26`（Apple M1 虚拟机，3 核，7 GB）上运行，PostgreSQL 那一步都成功（`postgresql@18 18.6_1`，版本核对通过）。

**verify（no-e2e）：失败，约 46 分钟。** 步骤汇总：lint 725 秒（7 GB 内存装得下 ESLint）、typecheck、静态门禁、clean、build、产物门禁（含许可）都通过；只有 tests 失败：

- 覆盖率部分通过：758 个文件、17,945 项，覆盖率达标；
- 随后的测试资源工具 Python 回归在第 51 项停下（`-f`）：`test_ci_preflight_receipt` 的 `test_manifest_limit_and_malformed_json_are_rejected`，2000 层嵌套的数组期望 `invalid-json`，实际 `invalid-manifest`。

**根因**：托管镜像的 `python3` 是 3.15.2，开发机是 macOS 自带的 3.9.6。2000 层嵌套在 3.9、3.12 上触发 RecursionError（本机两种解释器实测），工具据此判 `invalid-json`；3.14 起 CPython 改按实际栈深保护，3.15 能把它解析成列表，再被台账结构校验判为 `invalid-manifest`。两种都拒绝，安全性不受影响，但分类依赖解释器的递归上限。

#### 发现一：滚动状态下浮图的终点锚点混入了视口滚动量（缺陷）

N4 第二次及之后在表格滚动时插入的三张图，`sheetTransform.to` 分别是“第 26 行 −336 像素”“第 32 行 −312 像素”“第 36 行 −312 像素”，应为“第 12/18/22 行 +0”。换算回绝对位置与正确值相同，所以当下显示正常；但之后在受影响的行列范围内插入、删除行列或改行高列宽时，图片会跳位或拉伸。

根因在 SDK：core 的 `SheetSkeleton.getCellIndexAndOffsetByPosition`（engine-render 的 `SpreadsheetSkeleton` 继承它）找格时会加上当前滚动量并除以缩放比例，格内偏移却按未滚动、未缩放的坐标算；而它在 SDK 里仅有的两个调用方 `convertPositionCellToSheetOverGrid`（插入）与 `transformToDrawingPosition`（移动、拖拽缩放、翻转、图片复制粘贴）传入的都是表格绝对坐标。表格只要滚动过（或缩放不是 100%），这些操作存下的锚点就会偏。产品插入路径（`image-input-insert.ts`）直接调用前者，所以粘贴、选文件、拖放都受影响，与浏览器无关。按 S6 的判定规则，按根因修复（在已有的 `@univerjs/core` 补丁上让这个换算按绝对坐标进行）、补回归，复验后重做；原件保留。

- **WebKit 中途停止：会话保护误判。** 台账 `stopReason: desktop-session`，`desktopSession.reason: session-changed`，`commandExitCode` −15、`exitCode` 143。基线与停下时的 WindowServer 是同一个进程（pid 154，启动时间与可执行文件相同），只有 `uid` 由 88 变成 0；控制台用户（501）与 loginwindow 都没变。保护共读 4,545 次，最慢 1.216 秒，远低于 10 秒的时限，不是读取超时。保护用 `ps -o uid` 读的是有效用户号；本机实测 WindowServer 的有效、真实、保存用户号是 88、0、0，loginwindow 是 501、0、0：两者都以 root 启动、平时降为普通用户号运行，可以临时切回 root。同一进程临时切换有效用户号，被判成了“会话变了”。身份比较里不该有有效用户号；loginwindow 也按有效用户号挑选，切换的那一刻同样会误判为“身份不唯一”。Chrome、Chromium 两片的保护各读 2,920、3,110 次，最慢 0.373、0.316 秒，没有触发；第 4 轮三片也没有触发，所以这种切换很少见，诱因不明。
- **WebKit 的 `conflict.spec.ts:166`：原因未知。** 用时 22.5 秒，短于 30 秒的整例时限，是断言没过，不是超时。整片被停之后，测试结果留在保留的 scratch 里，没有上传；列表报告器只在结束时打印失败详情，所以报错、截图与 trace 都拿不到。
- **只读对照（Chrome）：菜单晚于两帧出现。** 测试一侧：右键 87.5 毫秒，名称框显示 C3（4 毫秒），等两帧（25 毫秒），只看一次就失败。浏览器一侧的逐帧画面：等两帧之后的那一帧和失败后约 50 毫秒的一帧都没有菜单；失败后约 150 毫秒的下一帧里菜单正在淡入，失败时抓下的页面结构快照里菜单各项都在。菜单没有被拦住，只是比两帧晚：SDK 在下一个动画帧里改菜单状态，React 之后再渲染，什么时候渲染完没有保证。这条校准（M2-P3 审查 B14）依赖“两帧之内一定看得到”这个时间假设，在慢的虚拟机上不成立。只读一侧（只读档案 `contextMenu: false`，SDK 不渲染右键菜单，`sheet-profile.ts`）还没有执行到。
- **图片 offline（Chromium）：托管虚拟机真实断网，恢复时按设计重读了一次；初步分析的“编辑实例读得晚”不成立。** 请求记录显示整条用例只读了两次图片：阅读实例在点“编辑”之前读一次（13:30:33Z）；编辑实例重建时没有读（页面保留这张图的失败，`createEditorImageAccess` 的 `preserveReadFailures`，只换上占位图）；第二次读取在点“保存”之后。逐帧画面：13:30:34.9Z 页面正常，13:30:37.4Z 出现“此操作需要联网”，其间用例只在等编辑器就绪，没有请求失败；此后约 6 秒页面一个请求都没有，连接监视也没有探测（浏览器明确离线时不探测，`browser-connection.ts`）。13:30:40.1Z 先后发出三个请求：重读失败的图片（浏览器回到在线时 `editor-page.ts` 调 `refreshImages()`）、立即复核编辑权（`editing-session.ts`：从离线回来立即核对）、会话探测（回到在线立即探测）。那张图再次被用例拦截失败之后 2 秒，又复核一次编辑权（请求失败之后的间隔），随后保存成功。只有浏览器的 `navigator.onLine` 先离线、再回到在线，这些请求才会这样排列；所以是这台托管虚拟机的网络断了约 3～5 秒。P2-S2 规格（`specs/P2-S2-图片实例与可靠渲染.md` 第 55 行）写明“普通失败本代内不自动循环重读；用户明确重试、权限重核、联网恢复或实例重建才创建新代”：回到在线时重读一次是规定的行为，不是自动循环。用例记下 `before` 之后断言读取次数不再变化，没有考虑测试期间真实的断网与恢复。
- **结论**：Chrome、Chromium 两片的失败与 WebKit 片中途被停，原因都不在被测产品（独立审查 M-1 之后改准：WebKit 片的 `conflict.spec.ts:166` 原因未知，不在此列）。WebKit 片被停是会话保护的身份判定有缺陷；Chrome 是用例校准依赖时间假设；Chromium 是托管虚拟机的真实断网，加上用例的判定没有覆盖规格允许的“联网恢复”这一新代。WebKit 的 `conflict.spec.ts:166` 原因未知，要在下一轮取得原件。处置涉及会话保护的判定与用例的断言，按“未知异常即停止”与“不改断言”请需求方决定；在决定之前不改代码、不重跑、不推送。

### 图片 offline 用例：判定与 P2-S2 规格一致

- `tests/e2e/support/browser-online.ts`：在页面脚本之前装上记数，听 `online`、`offline` 事件，按 `navigator.onLine` 的真实变化记“由离线回到在线”的次数，每次载入重新从 0 记。同一目标上的监听按登记先后执行，所以页面因回到在线发出读取之前，这里已经记下。
- `images.spec.ts` 六种失败的用例（含第 5 轮失败的 offline 一例）的判定：
  - 打开并进入编辑时：`before` ≤ 首读上限（401 为 4，其余为 2，原值）+ 记下 `before` 之后读到的回到在线次数。
  - 编辑、绘制与保存之后：
    - 多读次数 ≤ 至今回到在线的次数。从没回到在线时一次也不许多读，与原来的“不自动循环请求”一样严。
    - 总读取次数 ≤ 首读上限 + 至今回到在线的次数。
  - 回到在线的次数都在读取次数之后再读。按“至今”而不按“这段期间”计数：回到在线若发生在记下 `before` 之前，它带来的读取可能在之后才到，这也是规格允许的那一次。
  - **残余（独立审查 M-3）**：回到在线若发生在记下 `before` 之前，而且它带来的读取已经计入 `before`，编辑、绘制与保存期间还能多放过一次没有起因的读取。例：首读 1 次，打开期间回到在线 1 次并重读，`before` 为 2；之后一次自动重读，`after` 为 3，回到在线 1 次，判定通过，原判定会拦下。来源是原断言的首读上限 2 本身留有一次空间（编辑实例因 `preserveReadFailures` 不重读），再叠加按“至今”计数。严格说，余量至多是“打开期间已计入 `before` 的回到在线次数”与“首读上限没用完的部分”中较小的一个：非 401 的变体实际首读 1 次，余量至多 1 次；401 的变体首读上限为 4，打开期间多次断网又恢复时余量可能超过 1 次（概率极低，401 的实际首读次数没有核实）。为避开在途读取的竞态，接受这一残余：它只在测试期间真实断网又恢复时出现；从没回到在线时判定与原来等价；新增的 `:220` 对“回到在线只再读一次、之后不再读”是严格的。
- 新增用例 `images.spec.ts:220`（US-M5-07，断网再恢复）：
  1. 503 的假图读取失败之后，浏览器离线：页面显示“此操作需要联网”。
  2. 恢复在线，等提示消失再按坐标操作，与 `image-production.spec.ts` 的离线用例相同。
  3. 读取正好多一次，回到在线正好一次，失败提示照旧。
  4. 之后编辑、绘制与保存不再读。

  - 此后 4 分钟，这个用例的两个账户都没有请求。

**新发现：两次失败都没有失败截图。**

- 配置是 `screenshot: 'only-on-failure'`。Playwright 1.63 在关闭 context 之前，先给各页截一张临时图（5 秒时限，失败不报错）；用例最后失败时，再把这张图存成 `test-failed-*.png`。
- 两次都没有这张图，说明关闭前的这次截图没有成功。
- 本机复现的 40 次里，这次截图共发出 40 次：成功 38 次，2 次返回错误，关闭照常完成（方法计数里的 `Page.captureScreenshot`；它不在当时的白名单里，所以只有计数，没有错误文字）。所以截图失败本身不会让关闭卡住；它可能与卡住同源，也可能只是巧合。
- 截图有 5 秒时限，不会让关闭等 4 分钟。截图之后，Playwright 向浏览器发出 `Target.disposeBrowserContext`，等回复不设时限。
- 内置的 Chromium 在无头模式下用精简的 headless shell（Playwright 1.63 的 `getExecutableName`）；Chrome 与 Edge 片跑的是完整浏览器。两次卡住都出在完整浏览器上。
- 按 Chromium 的实现，完整浏览器销毁 context 时，要等这个 context 的窗口全部关掉才回复。卡住期间页面一直活着，与“窗口没有关掉、回复一直没来”相符。这是推断，还没有证据。

**结论：原因仍未知。**

- 新证据收窄了范围：最可能是浏览器一直没有回复 `Target.disposeBrowserContext`，关闭前截图失败是同时出现的异常。
- 要确认，只能在 CI 上取得这一段的协议记录。

### Chrome、Edge：关闭阶段的协议记录

**做法。** 新增 `tests/e2e/support/context-close-protocol.ts`，由原来的关闭阶段记录器（`context-close-diagnostic.ts`）在同一开关、同一条用例里启动：

- 只在固定用例（`catalog-boundaries.spec.ts:231`，Chrome、Edge，retry 0/1）所在的工作进程里、只在这条用例期间接上。
- 接法是进程内接 Playwright 的协议日志：从 Node 的模块缓存里找到这个进程已经加载的那一份 playwright-core（须为 1.63.0），取它的内部日志对象，只接管 `protocol` 这一类，其余原样交还。context 关闭、浏览器断连或满 330 秒即撤掉。
- 原始消息只在内存里过一遍，不落盘、不输出；要保存的方法名、会话号与枚举值先复制成独立的字符串，不连带留住整条原文。落盘的有：
  - 与关闭有关的命令、回复与事件：方法名、编号、时刻、类别（发出、回复、事件）、会话与目标的类型、截短到 8 位的标识（目标、会话、context、打开者）与等待时长；
  - 少量布尔与枚举值：是否已附着、是否等待调试器、关闭是否成功、截图格式与是否超出视口、新建目标是否新窗口与是否后台、对话框的类型与是否由浏览器处理、对话框是否接受与结果、崩溃的状态与错误码、`Inspector.detached` 的原因；
  - 错误只留错误码与截短的 ASCII 文字；
  - 各方法名的计数；关闭前 100 条与关闭后 600 条的序列，每条是方法名、类别、时刻、编号、会话与目标类型、错误码与回复用时；仍在等待回复的命令。
- 白名单在本机那次的基础上加了 `Page.captureScreenshot`（Playwright 自己的关闭前截图，不另外截图）与 `Page.bringToFront`。
- 写入时机：关闭开始时写一次，之后 2、10、30、90、200 秒各重写一次。所以关闭卡住、用例超时之后也有记录。
- 文件为 `context-close-protocol.json`，0600，最多 192 KiB，作为用例的附件进报告。关闭相关的记录超过 300 条时留最近的；文件需要裁剪时，关闭后的序列留开头，关闭前的序列与关闭相关的记录留离关闭最近的结尾。
- 接不上时不安装（版本不符、找到不止一份、协议日志已在别处开启、接法出错）：写一份 `state: stopped` 的文件、写明原因，并登记注解 `context-close-protocol-incomplete`；原来的阶段记录照常。

**完整的判定。**

- 记录在 context 的 close 事件、浏览器断连或满 330 秒时结束。
- 只有以 close 事件结束、而且关闭开始之后发出的 `Target.disposeBrowserContext` 都得到回复（没有错误），才算完整。否则原因记为 `close-not-started`、`dispose-not-sent`、`dispose-unanswered` 或 `dispose-error`。
- 关闭卡住、用例超时之后，工作进程收尾时关掉浏览器。Playwright 先派发 context 的 close，再派发断连（`Browser.didClose`），所以这种情形的记录是 `state: closed`、原因 `dispose-unanswered`。
- 判读时以 `contexts[].disposeSentT`、`disposeDoneT` 与 `pending` 为准。
- 初版只看 close 事件，独立审查 I-1 指出会把卡住写成完整，已改。

**测量本身的影响。**

- 接上之后，这条用例期间 Playwright 会把每条协议消息格式化一次（含截屏帧和回复正文），再交给过滤器。本机这条用例 1.7 秒，影响很小。
- 它会不会让 CI 上的卡住不再出现，无法预判；本机那次的 `DEBUG` 做法也一样。

**与批准原话的差别：没有用本机那次的环境变量加命名管道。** 批准写的是“做法同本机那次”，本机那次用 `DEBUG=pw:protocol` 加 `DEBUG_FILE` 命名管道。这次改为进程内接法。

- 数据范围与本机那次同类：方法名、编号、时刻、目标类型、截短的标识、少量布尔与枚举值、错误码与截短的错误文字；原始消息只在内存里。
- 有两处不同：每次都留关闭前后的序列（本机那次只在关闭慢于 10 秒或没有回复时才留）；白名单加了截图一步。
- 这个偏离已在 11-12 的汇报里向需求方说明。

改用进程内接法的原因：

- CI 的浏览器片有 2 个工作进程。Playwright 1.63 的日志把消息正文和换行分两次写入，两个进程写同一个管道时行会交错，过滤器认不出。
- 用 `DEBUG` 环境变量的话，整片所有工作进程约一小时的全部协议流量都要经过管道；进程内接法每个工作进程各管各的，只在这条用例期间开启，不需要环境变量、管道或文件。
- 代价是用到了 Playwright 的内部对象（`utils.debugLogger`），所以版本钉在 1.63.0，形状不符即不安装。

**其他改动**：

- 关闭阶段记录器扩到 msedge（项目集合为 `chrome`、`msedge`，归属里记项目名）；`ci.yml` 把开关给 Chrome、Edge 两片，`tools/src/verify/ci-workflow.test.ts` 同步。
- 两份报告共用的独占写法抽成 `tests/e2e/support/exclusive-report.ts`，写法不变。
- 资源规范（`docs/testing/test-resource-lifecycle.md`）的一节改名为“固定 Chrome、Edge 用例的关闭阶段诊断”，补“协议记录”一段。
- 新代码的单元用例与实现一起写，没有单独的失败运行；独立审查之后的修正先有失败的用例（见下文）。WebKit 用例改动的失败证据是第 6 轮的原件与下文的对照。
