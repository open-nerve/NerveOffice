# M5-P1-S2 四格式处理与资源预算：实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** 用真实自生成图片和受限进程验证处理库，固定S3生产实现的资源与格式契约。

**Architecture:** 独立诊断工程 `spikes/m5-image-processing/`，候选依赖仅装在主目录handoff的 `s2/candidate-runtime/`；每个case启动独立Node进程，报告与原始输出位于外部证据目录。Linux沿用生产Node镜像摘要并施加容器资源上限。生产代码在S3按测试重新实现。

**Tech Stack:** Node24.21.0、pnpm12.6.0、候选Sharp0.35.5 / @img预编译包1.3.4（实际libvips8.18.7）；自生成样本使用既有Pillow12.3。生产锁文件暂不变。

**Spec:** `../specs/P1-S2-四格式处理与资源预算.md`。

## 全局约束

同一P1分支/工作树，根目录main不动；新包满3天、精确锁定、禁止安装脚本。图片输入/输出5MiB，所有样本自生成，不从网络下载图片。不开放P2入口。所有峰值结论带平台与样本范围；堆/缓存/RSS采样不等同OS硬上限。失败原件不可覆盖，压力实验串行。

## 审查重点

1. 只读metadata或只解首帧却宣称完整解码：Task2核对后续损坏及逐帧像素。
2. 删除EXIF让照片方向改变、动画静默截帧：Task1给出独立预期，Task2核验方向/帧时延与内容。
3. 高压缩图片与多帧导致内存超出堆限制：Task2在512MiB容器测边界，Task3明确硬/软限制。
4. 不同平台装到不同原生库或跳过安装脚本后不可用：Task2分别记录实际versions与完整输出，Task3保留部署验收条件。
5. 预编译库的许可正文与源码说明漏分发：Task3检查发布包真实内容与上游构建来源，不全局允许所有LGPL包。

Task2执行结果：最终44个样本，macOS小矩阵34/34及2种故障恢复；Linux ARM64全矩阵44/44及3种故障恢复；Linux x64仿真小矩阵34/34及3种故障恢复。三轮分别由Pillow独立完整解码输出并重算摘要。原始语义与资源失败未删除，见诊断README及外部`s2/task-2-acceptance.json`。透明动画的缺alpha标志样本单独保留并说明差异，未伪造旧轮通过。

Ruling：保持原有16M/32M像素、100帧和5MiB/5秒候选边界；实验明确需要Linux `prlimit` 地址空间1536MiB、jitless、heap128MiB/semi16MiB、`VIPS_DISC_THRESHOLD=256m`。PNG/GIF完整性、动画文件原始时长、WebP逐帧无损编码与封装属于已批准的四格式处理细化，不新增服务或改变前端入口。生产RAM规划与许可分发由Task3定稿，S3实现正式进程调度。
