## 选择与边界

先以两类各 256 条真实关系的 EXPLAIN ANALYZE 测量旧触发器和 FK 成本。若结果支持该方向，再用新增迁移把**两个关系表的 INSERT 活动**改为 AFTER STATEMENT + NEW transition table，一次有序、去重写入活动。UPDATE 继续使用原逐行函数，避免扩大修改范围。

其它方向：应用层主动写活动会改变模块/事务边界；提高超时、降低七万规模或重试到绿不能证明原门槛成立，均不采用。如果测量不支持集合化收益，返回调查，不叠加猜测修复。

必须保持：

- 活动表及 `(asset_id, transaction_id)` 主键、FK 和每事务去重；不同事务互不覆盖。
- 活动与实际关系同事务提交/回滚；插入又删除仍留下已提交活动；零行、冲突未插入不制造活动。
- UPDATE 同值无活动，真正更换只记录新资源；升级写入屏障继续生效。
- 不改变资源锁升级规则、有序锁、GC 锁下查询/时钟/消费、宽限、备份水位或业务接口。
- 不改已合并 0036/0037；增加 0038 SQL、journal 和链式 snapshot，更新 schema-parity 的完整手写定义。
- 原七万用例、15 秒 statement / 5 秒 lock / 20 秒客户端及 60 秒用例门槛保持；生产保存事务预算不变。
- 每轮测试经受管入口，串行并核实真实清理；旧 r04 门禁、工具、证明及失败原件不改写，不用于新源码验收。

## 审查重点

集合触发器仍会在零行语句执行，其 transition table 必须为空才不产生活动；ON CONFLICT DO UPDATE 的更新路径不能丢失；集合化必须同时覆盖检查点关系；活动失败必须使原关系写入回滚；新增迁移不能造成升级后的重复触发或删除已有活动。以上均归 Task 1 的真实库验证，不能仅靠 SQL 文本断言。
