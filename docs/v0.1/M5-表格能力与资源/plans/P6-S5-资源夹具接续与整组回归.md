# P6-S5 资源夹具接续与整组回归

> 执行方式：superpowers:executing-plans；沿唯一 P6 worktree 实施，小型反例、必要修正、集中独审后串行执行整组资源回归。

**目标：** 补齐已发现的真实子运行失败保全缺口，取得当前源码的整组资源机制结果，再接续既有云端预验收授权。

**依据：** 用户阅读整体进度与剩余四项安排后明确“OK，那继续吧”。这覆盖前轮仅三条取证结束后的夹具核对与整组回归接续；不恢复本机浏览器长测，不追认历史 full02，不要求重复批准原云端发布。

**结构：** 复用 `fixture_retention.ManagedFixture` 的创建前外层 hold、原件导出和严格闭合检查；真实 runner 用例不再使用会无条件删除台账的临时目录 finalizer。刻意模拟外部状态的用例与真实环境清理分开，任何例外仅限测试夹具，不改变生产判断。

**技术：** Python unittest、既有 run.py、文件锁及 KiB 级自建子进程。

## 约束与选择

- 主目录保持 main，所有修改在 codex/m5-p6-closeout；正常中文提交和 hooks。
- 不放宽 lsof、身份、租约、进程组或资源预算；历史三个缺创建身份的短根继续保留。
- 不把全部模拟测试改造成真实环境测试。逐项检查真实 runner 入口；无实际外部服务的纯协议/故障模型保留原断言和模拟身份。
- 使用原 64 KiB/子轮、1 MiB/整轮诊断上限。失败、异常和中断保留台账；成功释放本轮资源。
- 整组只串行跑一轮，fail-fast；未知异常停止调查，不自动整轮重试。通过后正常推送现有 P6 分支并接续已批准的六项 CI；本轮不合并 main。

## 复核重点

- 夹具构造、setUp、测试正文、tearDown 任一失败都不能触发无条件删除受管原件。
- 预期 pending 模型不能使真实进程、短根、打开句柄或未知 Docker 状态获得清理豁免。
- 故障注入解除前后必须明确；真实清理核验不得使用模拟成功查询。
- 嵌套/邻接夹具及失败后首次导出不可覆盖；总报告预算不能随接入增多而放宽。
- 保留状态不可因测试框架异常或外层重启被清除；测试全集与原断言不能缩水。

自审：本计划细化用户刚批准的第一项安排，沿用原资源机制与集中预验收方案；真实 Safari、Mac 长测、main 合并及 M5 完整验收的边界保持。
