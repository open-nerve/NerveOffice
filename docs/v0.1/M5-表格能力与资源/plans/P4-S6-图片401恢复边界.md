## 事实与局部范围

CI `40787715273`、attempt 1、旧 SHA `323b957b5302208de965e76e6590052cc60a84e2` 的 Chrome 图片 401 场景首次等待 `editor-access=edit` 超时，重试通过仍被严格门禁判为 flaky/failure。原始 trace 显示编辑租约 POST 201 后主动 DELETE 204，约 30.8 秒中同一图片 544 次 401、本人会话 544 次 200，后者响应正文完全相同。

完整证据在外部 `final-ci-40787715273-investigation/chrome-artifact-investigation.md`（SHA-256 `1e24f564295148f6a3a134d93fc3623f60bca46d355a938232e95a8d9b016a7b`）。原件保留；这不是最终验收，也没有证明既有用户数据泄漏、越权访问或数据损坏。

已确定的回环是：图片 401 暂停原本机许可与图片，随后同身份自动确认又激活图片订阅；资源刷新清掉失败任务并重读，持续 401 再次暂停。修复前单测分别覆盖同令牌确认和“确认后才到达停写”，未组合“停写先到，随后同人同 CSRF 确认”的顺序。原trace不记录本机代次；具体交错由后续受控RED验证。

早期曾提出编辑准备窗口假设：`beginRestore` 在等待会话确认之前捕获恢复代次，确认时的新许可可能使旧恢复代次失效。但本机local01两次点击均发生在session 200约0.5秒之后，该窗口不能作为本次失败的已证原因。trace没有记录内部reason或本机许可代次。后续两个受控RED证明的是匹配停写后缺少本页补核、真实recovery reader遇缺许可而阻止编辑的路径；本轮不移动`beginRestore`，既有“等待确认时原件变更不能改选新候选”守卫保持。

## 状态设计与不可放宽项

1. 图片读取失败的重试状态，与真实会话许可分开。`imageAccess.current()` 继续表示已确认的原会话响应；同人复核后不能因失败图片而禁止上传或正文保存。
2. 图片 401 仍立即沿原请求许可停写、取消旧请求并清除旧像素。本人同身份的自动确认不得清掉已有失败或自动重读同一失败源；read/edit 重建不能丢失失败及明确重试入口。
3. 只有原有明确重试完成会话与详情核对、且页面/身份/请求轮次仍有效，才允许一轮新读取；再次失败继续保留，不自动循环，不重放上传、剪贴板或保存操作。
4. 真正换人、CSRF 变化、退出、销毁、旧回包、网络失败和权限撤销保持原有严格行为。若调整共享图片许可接口，历史预览的默认行为必须有对应回归；不放宽全局会话失败或恢复栅栏协议。
5. 编辑准备若确有反例，只修有效身份确认与当前恢复准备之间的接线；不得将 cancelled/blocked 当作 none，不复用旧许可，不自动改选用户没有确认的新恢复原件。

本轮实现以页面共享的失败来源集合表示读取轮次，只存规范图片 source，不存图片内容；请求捕获发出时的集合。第二版在显示读取的原 `readAsset` Promise 上观察认证失败：401 自身撤权即使先取消外层任务，只要仍属同一读取轮次且实例未销毁，仍登记该来源；任务已确定的取消结果不变，取消原因本身不能被当作认证失败。旧轮次已替换时，迟到错误不得写入当前集合。普通错误与原始认证观察去重；上传、独立读取和下载不登记显示失败。

编辑页选择在同身份暂停/恢复与 read/edit 重建时保留失败；显式刷新、真实身份或权限变化退休旧轮次。当前许可仍独立更新，因此新上传与新 source 不被旧图片失败锁住。共享控制器的历史预览默认仍在暂停后确认时刷新，另有回归约束。`beginRestore`、全局会话栅栏、后端与恢复原件选择接线未改。

页面收到与当前本机许可user/generation精确匹配的`stopped`后，仍先撤许可、取消图片、暂停恢复并关闭旧宿主/密钥，再调用既有`recheckSession()`；有查询在途时沿`checkAgain`合并补核。缺许可本身不被改成全局认证失败，存储不可用或部署关闭本机草稿时的内存编辑/云端保存退路保持。旧UID/代次、销毁后迟到回包及真实退出/换人/停用均有对应回归；补核不重放失败图片或用户操作。

不修改服务器会话/编辑租约协议、数据或迁移、图片资源权限、GC/恢复删除权限。若实际需要这些跨模块变化，先说明具体必要性与风险，由主任务按项目边界处理。
