# P4-S2 写入与删除前采样实施计划

> 基于 S1 `698c799c`；当前唯一 P4 worktree 内使用 executing-plans 逐项实施，TDD，Step 验证后中文提交。

**目标**：所有正式写入入口在原事务中建立小时历史；删除前保存独立运维检查点。历史失败时原业务整体回滚。

**设计**：[P4 设计](../04-P4-历史与资源回收.md) §3.2–3.3。Documents 内部接线，不改变 HTTP 契约、权限、租约或 requestId 规则。

## 全局约束与接口

- S1 的 `captureHourly(documentId, transaction)` 必须在当前正文、修订和合法引用写完后调用；调用方已经持源文档锁或新建私有行。
- `captureOperation(documentId, 'before_delete', entry.id, transaction)` 在删除状态改变前调用；一个删除单元的全部活动文档用新增内部 `captureOperations(documentIds, kind, eventId, transaction)` 固定一次数据库时刻后按已持有的 id 顺序逐条等待，不能并发使用连接。
- 新建与两种副本都生成自己的初始小时历史，不继承源的旧历史；unchanged、重放、失败、改名、移动不生成小时历史。
- 普通复制的当前原 gzip、SDK unitId 与合法引用不变；本页副本保留上传的那份正文；小时采样不得扩大图片授权。
- 没有新增历史读取/恢复或 GC 入口。正式历史查询、容量与最终完整门禁在后续 Step。

## 审查重点

1. 下一小时发 unchanged 或旧 requestId：不会偷偷采样旧内容。Task 1 正式 HTTP 回归。
2. 图片正文里有陌生/未知 assetId：保留正文，不建立历史读权；旧图从当前移除后仍由历史保护。Task 1 正式上传/保存/复制回归。
3. 已写正文、引用、历史之后故障：新建/保存/两类副本全回滚，原 requestId 可重试。Task 1 原服务调用后故障注入并查真实库。
4. 删除文件夹第二份文档捕获失败：先捕获的第一份及删除单元、目录状态、文档代次一起回滚。Task 2 批量反例。
5. 删除在等并发保存时：持锁后采到最新已提交正文；没有混入早先单独删除的文档，再恢复后删除产生另一事件。Task 2 确定交错和整单回归。
