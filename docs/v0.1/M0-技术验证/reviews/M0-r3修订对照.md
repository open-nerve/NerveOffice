## 二、几处取舍的说明

- **P6 的数字**：r3 引用的是 P6 的最终数据（三个浏览器；写入管道在 macOS 27.0 上重跑，功能用例在 26.5.1 上）。主要的几个：5 MiB 表格的主线程同步段 p95 74–87 ms；gzip 在 Chromium 内核约 90 ms、WebKit 约 63 ms；恢复路径 p50 21–30 ms、p95 29–45 ms；丢失窗口 Chromium 与 Chrome 约 0.2、1.7、0 秒，WebKit 约 0.5、2.0、0.5 秒；接手 0–13 ms（崩溃 11–219 ms）；从修改停止到"已保存在本机"p50 1.02–1.18 秒。
- **§12.2 的最坏值**：写的是 WebKit 上发件箱 Worker 的偶发停顿（5 MiB 表格约八分之一的捕获约 2.2 秒）与对策（Worker 保持空定时器后 40 次都在 1.19 秒以内，DEF-011）。P3 记录的"WebKit 公式 Worker 模式打开后第一次修改 1.77 秒"，P6 在同样条件下没有复现，r3 没有把它当作最坏值。
- **捕获时机写成一条规则**（报告之间原来的口径不一：P3 §3.4 没有给时限，P5 的组合输入上限 3 秒，P6 原型从第一处未保存的修改算起 3 秒）：r3 按 P6 §1.2 第 5 条统一为"从第一处未保存的修改算起最长 3 秒，这个上限同时约束公式收齐与组合输入的等待"。
- **捕获时机放在哪个 M**：各报告的说法不一（P3 写 M4，P5 写"M4：组合输入感知"，P6 交接单写 M1 的适配层），r3 按结束评审的建议放在 M3；其中"组合输入感知"随文字文档编辑器放在 M6（文字文档到 M6 才接入，DEF-008 也在 M6）。各报告保持原样，以 r3 为准。
- **§7.8 删去 r2 的"（大文档按实测放宽）"**：5 MiB（单快照上限）上，停顿后到"已保存在本机"的 p50 约 1.17–1.18 秒，"停顿后约 1 秒"在容量上限内成立；公式计算慢的文档单独写明。
- **§13.3 不加列**：为保持表格格式，"M0 原理验证"写成表后的注记。
- **新建文档的模板快照放在 §8.1**：它讲新建文档的初始快照内容，与插件档案无关。
- **包体积**：§8.2 只引用 `doc@1` 的数字，并注明是按 `doc@1` 的插件清单单独构建的口径；按最终档案重新统计两种编辑器的包体积交给 M1（M0 交接单）。
- **CSP 的两项遗留**（样式哈希能否代替 `'unsafe-inline'`、`report-to`）：r3 写明没有评估，保留 `'unsafe-inline'`，违规上报只作抽样信号，由 M7 的独立安全审查复核；不另登记延期。

- 【§4.5-1】第 3 条"输入法候选框的位置可能与文字有偏差"：结束评审对 SC-4 第 3 条的建议是"看 macOS 真实输入法核对的结果再定"，核对还没做，所以没有写进 §4.5。§4.3 写了实测的隐藏输入元素偏移，M6 一行已含"候选框位置的缓解"。核对确认偏差明显时，§4.5 加一条："在文字文档里用输入法输入时，候选框的位置可能与文字有偏差。"

- 【§0-2】的第二种写法（保留 §0 作为 r1/r2 的历史）：没有采用，§0 的"本版"一列按 r3 改写，这样 §0 始终反映当前方案。
- 【§13.3-1】"加一列"：改为注记段落（第二部分）。
- 【§9-1】"IndexedDB、Web Locks、WebCrypto、CompressionStream 在 Worker 中都可用；Univer 自己不使用 Service Worker"：只写了"压缩、加密与写入放在发件箱 Worker"。Web Locks 在 Worker 里可用，只来自 P6 Phase 文档里的 Chromium 探针，报告没有三个浏览器的结论；"Univer 不使用 Service Worker"已写在 §8.3，§9.3 保持不动。
- 【附B-3】P6 的可选条目（`Styles.add` 随机生成样式 id、`SheetsNoteModel.updateNote` 随机生成批注 id、移动区域的 mutation 不看 `unitId`）：只有纳入 mutation 增量日志时才用得上，SC-2 不纳入，留在 P6 报告与 DEF-010。
