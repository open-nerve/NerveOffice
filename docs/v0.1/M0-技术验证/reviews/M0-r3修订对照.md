## 二、相对清单的调整与原因

1. **P6 已有三个浏览器的数据**，清单里"只有 Chromium"的数字全部按 P6 最终报告替换：

   | 项目 | 清单 | r3（依据） |
   |---|---|---|
   | 5 MiB 主线程同步段（含编码） | Chromium 约 73 ms | p95 73–84 ms，三个浏览器（P6 §2.1、§2.3） |
   | Worker 放置后异步段的最长阻塞 | 约 6 ms | Chromium 内核约 6 ms，WebKit 约 9 ms |
   | IndexedDB 写入 | 不到 3 ms | p95 不超过 4 ms（WebKit 的 `strict` 有一次 10 ms） |
   | 接手耗时 | 0–15 ms | 关闭、导航离开 0–13 ms；渲染进程崩溃 11–219 ms（只在 Chromium 内核上测） |
   | 恢复路径（5 MiB） | 约 26–43 ms | p50 21–27 ms、p95 27–42 ms |
   | 持续编辑的丢失窗口 | Chromium 0.2–1.9 秒 | Chromium 与 Chrome 约 0.2、1.7、0 秒；WebKit 约 0.5、2.0、0.5 秒；口径改为"第一处丢失的修改到杀进程" |
   | 从修改停止到"已保存在本机" | p50 1.01–1.08 秒、最大 1.18 秒（只有 Chromium） | 不牵动公式：p50 1.01–1.12 秒（按 P6 §2.2 表格，三个浏览器）；牵动约 320 个公式：p50 1.03–1.04 秒、最大 1.07 秒；最坏值写占位符 |

2. **P6 审查后的方案变化**写进 §7.5、§7.6、§7.7 与 M4 一行：AAD 覆盖全部参与恢复决策的明文元数据（清单只写了用户、文档、序号）；写入栅栏（持有者令牌 + 代次，同一事务核对，`FenceError`）；"公式待更新"标记、补捕获与恢复时强制重算；等锁与待恢复时只读；接手时服务端修订号变了先重新加载；按密钥版本区分吊销与篡改；本机回滚为已接受的风险；提交附近被杀 8 次都是新记录；捕获串行、序号在 `save()` 的同步段里分配（所以管道图里 `localSeq` 的位置从"变更检测"挪到了"捕获"）。
3. **K-1、K-2、K-3** 按 P6 §1.2 第 5 条与 §5 写成一条规则，r3 里没有保留"待补"或口径争议的说法。§7.8 的上限两处写法不同：P6 §5 写"再加一次写入（几十毫秒）"，§2.3 写"3 秒加 50 ms 的轮询与最多两次管道"。r3 承诺一栏写"再加上写入本机的耗时（几十毫秒）"，实测段落引用 §2.3 的精确上限。
4. **K-12**：DEF-007 的数字已由 P5 定稿。r3 §12.2 直接引用 P5 §5.2 的数字，不转述 DEF-007。
5. **文字文档性能基线**（清单是【待补】）用 P5 §5.2 定稿：到 `Rendered` 0.49–0.52 秒，键入画出来 p50 94–110 ms，组合更新画出来 p50 90–107 ms，快速键入最长阻塞 81–123 ms（主线程排版，三个浏览器）。
6. **§12.2 最坏值**：清单按 P3 写"WebKit 公式 Worker 模式打开后的第一次修改，光捕获就要 1.77 秒"。P6 在同一条件下（`perf-50k`、公式 Worker、打开后第一次修改）测到 1.052 秒，没有复现；另有 WebKit 5 MiB 表格的 2.097 秒离群值。按你的要求写成【待定：§12.2 最坏值】，1.77 秒没有写进 r3（见第五部分第 3 条）。
7. **评审编号以结束评审为准**：结束评审的确认-3 是"能力矩阵定稿"、确认-4 是"CSP 与 `IMAGE()`"；清单的确认-3 是 CSP。本说明第四部分按结束评审的编号。
8. **SC-6 的 A17**：清单留给评审决定，结束评审建议采纳（加严），r3 已采纳。
