# M0-P6 本地优先可行性：架构设计与实施规划

> 状态：已完成｜日期：2026-09-25｜基于代码版本：`7b7a92b`（P5 分支的最新提交，P5 等 Chrome、WebKit 复验后合并；合并后本分支变基到 main）

## 1. 目标与范围

对应 M0 总设计 §5 的 P6 一行，覆盖验证项 V14、V15、V16（00 号计划书 §7、§8.7、§13.4 第 14–16 条）：

- **V14 本地优先所需的浏览器能力与成本**（阻断）：
  - 把 1–5 MiB 的快照写进 IndexedDB 的耗时，以及整条管道（捕获 → 压缩 → 加密 → 写入）的主线程阻塞；
  - 配额行为：可用空间、持久化存储的申请、写满时的错误与已有记录是否完好；
  - Web Locks 的多标签页协调：同一文档只有一个标签页能编辑，关闭或崩溃后锁自动释放，恢复流程只在拿到锁之后启动；
  - AES-GCM 加密的开销；
  - 浏览器进程被杀之后的恢复：本机记录是否完好、能否解密并恢复到最后一次写入本机的内容、丢失窗口多大。
- **V15 mutation 增量日志是否可行**（非阻断）：能否序列化、能否确定性重放、能否与快照组合恢复；给出"纳入 M4"或"不纳入"的结论。
- **V16 在 Node.js 下以无界面方式加载**（可选，非阻断）：用与浏览器相同的资源插件加载快照再保存，为将来的服务端迁移工具做可行性记录。

结论要回答 00 号计划书 §12.2 的"从修改停止到已保存在本机 p95 ≤ 2 秒"：P3 实测捕获部分约 1.04–1.09 秒，给本机写入与加密留约 0.9 秒（P3 报告 §4.4），本 Phase 实测这 0.9 秒够不够。

不在本 Phase：

- 生产实现：本机发件箱、恢复流程与保存状态由 M4 实现，密钥的服务端管理由 M3 实现。本 Phase 在验证工程里做最小原型，证明方案可行并测出成本；
- 服务端提交（§7.4 的租约、修订号、幂等）：验证服务只模拟"修订号没变"这一条件，用于恢复流程；
- 真实 Safari、真实断电（系统层面的数据落盘）：Playwright 只能杀进程，不能模拟断电。断电时的持久性只做源码与文档层面的说明（`durability: 'strict'`），登记延期项。

## 2. 现状

- **验证工程**（P1–P5 交付）：
  - 捕获：`FWorkbook.save()` / `FDocument.save()`；捕获时机按 P3 报告 §3.4（修改停止 1 秒后，逐表等公式写回）与 P5 的组合输入感知（`src/harness/capture-timing.ts`）；
  - 捕获成本：`src/harness/perf.ts` 的 `measureCapture`（`save()` → 序列化 → gzip（`CompressionStream`）→ SHA-256），以及事件循环延迟、帧间隔、Long Tasks 探针；
  - 样本：`big-1m`、`big-5m`（表格）、`doc-20k`、`doc-1m`（文字文档）由 `ensureGenerated` 生成进验证服务的文档存储（`e2e/p3-helpers.ts`）；
  - 变更检测（`change-detector.ts`）：P3 的规则，另用协同钩子 `onMutationExecutedForCollab` 记录 `syncOnly`（内部 API，只用于分析）；
  - 验证服务：文档存储（内存，`PUT`/`GET /api/docs/:id`），会话 Cookie（P4）。
- **前序结论**：
  - P3（V08）：1 MiB 表格整条捕获管道约 50–55 ms，主线程最长阻塞 p95 ≤ 32 ms；5 MiB 的同步段与 gzip 各有 60–100 ms 的阻塞，建议大快照的压缩、加密放进 Worker。压缩率：表格约 25%，文字文档约 45%。
  - P3：`largeSheetCellCountThreshold` 设为最大值，关掉了大表操作的拆分，所以不会出现 `syncOnly` 的大表复制分块。
  - P5：组合进行中不捕获，组合持续超过 3 秒照常捕获，失焦时复位。
- **本 Phase 前的源码与探针调研**（v1.0.0，`packages/` 省略）：
  - **协同钩子** `ICommandService.onMutationExecutedForCollab`（`core/src/services/command/command.service.ts:270、403-414`）：
    - 每条 MUTATION 都会送达一次，包括 `onlyLocal`、`fromCollab`、`fromSync`、`syncOnly`，不做过滤；
    - 开源代码里没有使用者（协同插件闭源），不是公开的稳定 API。
  - **参数的序列化**：命令与 mutation 的约定是"参数应可序列化"。协同协议把参数存成字符串，Worker 同步走结构化克隆。例外是个别只在本地出现的参数：`Map`、函数、`layoutState`。
  - **参数会被原地改写**：文字文档编辑会改写 `params.actions`，样式 id 会被换成样式对象，筛选会写 `filteredOutRows`，`trigger` 在撤销重做时被重写。所以要在监听器里同步复制参数。
  - **重放**：`syncExecuteCommand(id, params, { fromCollab: true })`，在顶层调用；`fromCollab` 保留公式重算与渲染，不写撤销栈。
  - **不确定的地方**：
    - 样式 id 在 mutation 里随机生成，重放后 id 不同。复制工作表的 mutation 按字符串引用样式 id，所以会留下悬空的引用；
    - 文字文档的段落 id 可能在执行过程中分配，所以要记录执行之后的参数；
    - 部分状态不走 mutation：本地授权的保护策略、缩放、图片变换的刷新。
  - **输入法**：组合中的每次更新都是带 `noHistory` 的 mutation；提交的文字与最后一次更新相同时，不再有新的 mutation。日志必须记录这些 mutation。
  - **Node**：
    - 厂商有 Node 预设，但仓库里没有在纯 Node 下运行的测试；
    - 核心包没有模块级的 DOM 访问；
    - 文字文档编辑要注册 `UniverRenderEnginePlugin`；
    - 生命周期只到 Ready；
    - `saveUnit` 只输出已注册插件的资源，所以 Node 实例必须注册与浏览器相同的资源插件；
    - 迁移用 `NO_CALCULATION`，避免加载时重算公式改变输出。
  - **浏览器能力（Chromium 探针）**：
    - Web Locks 可用：`ifAvailable` 在锁被占用时返回 null；持有锁的页面关闭或渲染进程崩溃后，另一个页面约 3 ms 内拿到锁；
    - `navigator.storage.persist()` 在无头 Chromium 里返回 false，`estimate()` 的配额约 10 GiB；
    - IndexedDB 事务支持 `durability: 'strict'`；
    - Worker 里可以用 `CompressionStream`、`crypto.subtle`、IndexedDB 与 Web Locks；
    - 用 SIGKILL 杀掉浏览器进程后重新启动，已提交的 IndexedDB 记录完好。

### 3.2 实验方案

**V14-1 写入管道的成本**（`e2e/v14-pipeline.spec.ts`，单独运行）：

- 样本：表格 1 MiB、5 MiB，文字文档 2 万字、1 MiB（与 V08 相同）。
- 组合：放置方式（`main`、`worker`）× 持久性（默认、`strict`）。
- 每组预热 2 次后测 10 次，记录：
  - 各段耗时：`save()`、序列化、gzip、加密、写入、合计；
  - 主线程阻塞：同步段直接计时；异步段用事件循环延迟探针与 Long Tasks；
  - 字节数：JSON、gzip、密文。
- 另测解密与解压（恢复路径）的耗时。

**V14-2 端到端**（同一用例文件）：在表格 1 MiB、5 MiB 与文字文档 1 MiB 上修改后停止，测"最后一次修改 → 已保存在本机"，各 5 次，对照 §12.2 的 2 秒。

**V14-3 配额**（`e2e/v14-quota.spec.ts`）：

- 三个浏览器：`estimate()`、`persisted()`、`persist()` 的结果。
- 写满的行为：
  - Chromium 内核：用 CDP `Storage.overrideQuotaForOrigin` 把本站配额设小，反复写入更大的记录，直到失败；
  - WebKit：记录默认配额，写入到一个上限为止（上限在实施时按写入速度定）。
- 检查：
  - 错误类型（`QuotaExceededError`）；
  - 失败的写入整体回滚，已有记录仍能解密；
  - 发件箱报告"容量不足"。

**V14-4 多标签页协调**（`e2e/v14-locks.spec.ts`，同一浏览器上下文里的多个页面）：

- 标签页 A 编辑时持有锁，标签页 B 打开同一文档：拿不到锁，进入"另一个标签页正在编辑"，不写发件箱。
- 释放锁的三种方式，B 之后都能拿到锁，并启动恢复流程：
  - A 关闭；
  - A 崩溃：Chromium 内核用 CDP `Page.crash`；WebKit 结束页面的进程；
  - A 导航离开。
- `steal`：B 抢锁，A 收到通知并停止写入。
- 恢复：
  - 两个标签页同时打开有未同步记录的文档，只有拿到锁的一方提示恢复；
  - 同一文档在同一用户的另一个浏览器上下文里（不同的存储）互不影响。

**V14-5 加密**（并入 V14-1）：加密与解密的耗时；密钥不落盘（`CryptoKey` 不可导出，只在内存）；吊销后原有记录无法解密，恢复流程按"不可恢复"处理。

**V14-6 进程被杀之后的恢复**（`e2e/v14-crash.spec.ts`，持久化的浏览器上下文）：

- **正常路径**：编辑并等到"已保存在本机"，再做几处修改，不等保存；然后杀掉这个浏览器的全部进程（SIGKILL），用同一个用户目录重新启动，打开同一文档。检查：
  - 提示恢复，恢复出的内容等于最后一次写入本机的快照；
  - 未保存的修改丢失，丢失窗口符合 §7.8（停顿后约 1 秒，连续输入最多约 3 秒）。
- **写入中被杀**：在写入 5 MiB 记录的过程中杀进程，重复多次。检查重启后的记录要么是旧的、要么是新的，不会半截：能解密、能解压、能解析。
- **修订号已变**：恢复时服务端的修订号与记录的基准不同，不自动恢复，进入"真冲突"（另存为副本的入口只记录，不实现）。
- **密钥吊销**：恢复时拿不到原密钥，记录作废。

**V15 mutation 增量日志**（`e2e/v15-mutation-log.spec.ts`）：

- **重放等价**：在快照 S0 上执行一组操作，同时记录日志。另开一个实例加载 S0，按顺序重放日志，等公式与微任务完成后 `save()`，与原实例的 `save()` 按规范化内容比较。
  - 表格：
    - 输入数值与公式、样式、数字格式；
    - 插入删除行列（带浮动图片）；
    - 复制工作表（含"先设样式再复制"）；
    - 条件格式、数据验证、筛选、批注；
    - 粘贴、自动行高、撤销重做。
  - 文字文档：
    - 键入、中文输入（组合中的 `noHistory` mutation）；
    - 粘贴、表格、图片、列表；
    - 撤销重做。
- **组合恢复**：日志与快照的位置在同一事务里记录。模拟崩溃（杀进程）后，用"最后的快照 + 之后的日志"恢复，与崩溃前的内容比较。
- **成本**：每条 mutation 的记录耗时、写入 IndexedDB 的方式（逐条或按帧批量）、日志体积（大粘贴、图片的 Base64）。
- **结论口径**：
  - "纳入 M4"：重放在全部场景下一致（或有可靠的补救），成本可接受，依赖的内部 API 可以封装并用回归锁定；
  - 否则"不纳入"：说明原因与代价，本机只保留快照（丢失窗口按 §7.8）。

**V16 Node 加载**（可选，`scripts/v16-node-load.ts`）：

- 在 Node 24 下，不用 happy-dom，用发布的包加载 P2 的全部表格与文字文档样本（`fixtures/`）。插件按档案的无界面部分注册，公式用 `NO_CALCULATION`。
- `save()` 之后，与浏览器保存的结果按规范化内容比较；同时记录资源名是否一致、耗时与内存、需要的额外配置、遇到的错误。

### 3.3 关键设计

**原型只证明可行，不决定产品实现**：发件箱、恢复、锁都是最小原型，目的是测出成本与行为。

**一条记录一份快照**：发件箱的每份文档只保留最新一份快照（00 号计划书 §7.5）。写入是覆盖同一个键，由 IndexedDB 事务保证原子性，不需要"先写新、再删旧"。

**加密的边界**：

- 密钥由服务端下发，只在内存里；
- 发件箱里只有密文、IV 与明文的元数据（文档 id、修订号、`localSeq`、时间）；
- AAD 绑定用户、文档与序号；
- 恢复时重新向服务端取密钥。

**Worker 放置**：SDK 的模型只在主线程上，`save()` 加序列化（5 MiB 时 p95 66–82 ms）必须在主线程做。之后的压缩、加密、写入能否搬进 Worker、能省多少阻塞，由 V14-1 比较。

**锁的名字与粒度**：每份文档一把排他锁（`nerve-doc:<文档 id>`）。拿不到锁的标签页不写发件箱、不上传，只读展示。

**V15 的记录点**：

- 用协同钩子，不用 Facade 的 `CommandExecuted`：后者收不到 `syncOnly` 的 mutation，这些 mutation 的内容还会在之后以 `onlyLocal` 重放，被规则排除。本档案关掉了大表拆分，这条路径不会出现，但记录点要完整；
- 参数在监听器里同步复制（结构化克隆），因为 SDK 会在之后原地改写参数；
- 顺序以执行前取的序号为准：部分命令不等待 mutation 执行完，监听器的触发顺序可能与执行顺序不同。

### 3.4 实施中的调整

- 分支：P6 从 P5 分支的最新提交拉出（P5 等 Chrome、WebKit 复验期间先推进 P6），P5 合并后变基到 main。
- V15 的补全：直接往 `sheet.mutation.insert-sheet` 的 `styles` 里塞样式，会改变之后按内容查到的样式 id；改为"样式附带记录"（记录时附上样式表的增量，重放前按原 id 装入），另加批注 id 回填。
- 按审查意见（`reviews/P6-审查报告.md`）修订原型：
  - 写入栅栏（R1）；
  - "公式待更新"标记、补捕获与恢复时强制重算（R3）；
  - AAD 覆盖全部参与恢复决策的明文元数据（G1）；
  - 捕获串行、序号在同步段里分配（G2）；
  - 等锁与待恢复时只读、接手时对齐服务端（G3）；
  - 按密钥版本区分吊销与篡改（S4）；
  - Worker 出错与数据库升级的处理（S5）。
- 用例的调整：
  - 端到端增加牵动约 320 个公式的修改（R2）；
  - 杀进程改为整棵进程树，WebKit 另杀 XPC 服务（G6）；
  - 增加提交附近被杀（G5）；
  - 丢失窗口改为"第一处丢失的修改到杀进程"（S1）。
- 收尾自查：
  - 表格修改的测试辅助在 P3 大样本上从第二次修改起内容不变，捕获被去重跳过；修正后端到端断言每次都真的写入，三个浏览器重跑写入管道用例；
  - WebKit 上 5 MiB 表格、发件箱 Worker 放置偶发约 2.2 秒：端到端增加分段计时与对照参数（`outboxhash=main`、`outboxkeepalive=1`），定位在 Worker 空闲之后的第一次异步操作，空定时器可以避免（报告 §2.3 第 11 条，DEF-011）。
- 运行环境：本机断电重启后桌面会话一度没有登录，Chrome 与 WebKit 在桌面会话恢复后补跑；收尾期间本机自动升级到 macOS 27.0，写入管道用例在 27.0 上三个浏览器整套重跑，功能用例保留 26.5.1 的结果，WebKit 杀进程另做冒烟。

### 3.5 错误处理与安全

- **发件箱写入失败**（配额、存储被清除、事务中止）：保持"未保存"状态并提示，不删除已有记录。
- **解密失败**（密钥被吊销、记录被篡改）：记录作废，提示"本机的未同步修改无法恢复"。
- **锁被抢走**：立即停止写入与上传，转为只读。
- **日志记录器绝不抛错**：SDK 不捕获监听器的异常，抛错会跳过后面的监听器。
