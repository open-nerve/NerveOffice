# P5 验证报告：文字文档与中文

> 日期：2026-09-25｜所属：M0-P5｜Univer 版本：1.0.0｜验证工程：`spikes/m0/`

## 摘要

| 编号 | 验证项 | 结论 | 一句话 |
|---|---|---|---|
| V13 | 文字文档的能力与中文输入 | **有条件通过** | 00 号计划书 §4.3 的能力逐项可用：能力矩阵 C1–C9 在三个浏览器上都能用，撤销重做与保存重开一致；中文输入、复制粘贴与无分页版式也可用。但 SDK 有几处缺陷必须由平台处理，这就是结论的条件（§1.2）：<br>• 正文里键入的 `/` 被吞掉，其后键入的字丢失；<br>• 按 WebKit 的事件顺序提交输入法时，撤销多删字、重做插回拼音；<br>• 组合进行中捕获，会把拼音存进快照；<br>• 链接地址：链接框接受 `javascript://…`，命令路径与内部片段不做检查，复制时 `href` 不转义；<br>• 表格单元格里仍能放进图片：段落菜单、`/` 菜单、粘贴，以及把浮动图片拖进单元格；<br>• 隐藏菜单不会停用命令（切换版式、页面设置、形状仍可执行），隐藏父菜单后子项仍能被功能搜索找到。<br>这些缺陷都已在验证工程里用平台策略解决，并在三个浏览器上与 SDK 默认对照验证。还差一项：真实 Safari 与系统输入法的人工核对，M0 结束评审前完成（附录 A）；Windows 输入法登记为 DEF-005 |

**影响设计的发现**：

- **`/` 键**：段落菜单服务在任何位置拦下 `/` 并弹出菜单，菜单抢走焦点，其后键入的字全部丢失（`a/b c` 只剩 `a`）；表格单元格里连菜单也不弹出，`/` 直接被吞掉。日期、网址、"和/或"都无法键入。
  - 平台在捕获阶段处理 keydown 与 beforeinput 两条路径：光标在表格之外的空段落里时，交给 SDK 弹出 `/` 菜单；其他位置由平台插入 `/`（§2.3 第 1 条）。
  - 空段落里弹出菜单后，其后键入的字仍然丢失，列为已知限制，由 M6 处理。
- **输入法的撤销缺陷**：`compositionend` 的数据与最后一次 `compositionupdate` 不同时，SDK 的撤销记录按拼音的长度计算，撤销会多删后面的字，重做会插回拼音。
  - 这正是 WebKit 的提交顺序（§3.3 第 1 条附 WebKit 源码位置）。
  - 按这个顺序的合成事件在三个浏览器上都能复现：13 种输入情形中 11 种撤销出错。
  - 平台在 `compositionend` 之前补发一次携带最终文字的 `compositionupdate`，13 种情形全部正确（§3.3 第 1 条）。
- **捕获时机要感知组合输入**：SDK 在每次 `compositionupdate` 时就把拼音写进模型。按 P3 的规则，停在候选框上超过 1 秒就会捕获到拼音。
  - 改为组合进行中不捕获，`compositionend` 之后再计防抖；
  - 组合持续超过 3 秒照常捕获，与 00 号计划书 §7.2"持续编辑时最长每 3 秒捕获一次"一致（§3.3 第 2 条）。
- **排版 Worker 暂不启用**：约 2 万字的文字样本（含 8 个表格、10 张图片）上：
  - 从按键到画出来，主线程模式约【待补】ms，Worker 模式约【待补】ms；
  - 更大的差别在主线程阻塞：快速键入时，最长阻塞约【待补】ms 对比【待补】ms。
  - 但 Worker 模式下，在表格单元格里键入后立即按 Tab，Tab 会丢失，后面的字写进同一格。修复之前不启用，v0.1 用主线程排版；DEF-007 在 M6 重新评估（§5.3 第 4 条）。
- **公式引擎可以去掉**：文字文档启用的插件都不依赖它。去掉后：
  - 首屏 JS 从 5.13 MiB 降到 3.75 MiB（未压缩，−27%），gzip 后从 1.23 MiB 降到 0.99 MiB（−19%）；
  - 样本的保存重开完全一致（§5.3 第 5 条）。
- **目录**：建议纳入只读的大纲侧栏（docs-ui 的 `toc` 配置，按标题导航，不写内容），不纳入目录块插件。目录块会在正文里写 FIELD、HYPERLINK 区间，页码在无分页版式下没有意义，链接也没有地址（§5.3 第 3 条）。
- **粘贴的保真度**：Word、WPS、网页、Google Docs、飞书的常见结构大多保留。但有一批转换偏差：
  - Google Docs 的内容全文变粗体；`<em>` 变成粗体；
  - `<br>` 丢失；嵌套列表的父项并进子项；
  - 中文编号留在文字里；WPS 与 Word 的"标题"段落样式不识别；
  - 往表格单元格里粘贴含表格的内容时，整体放弃。

  这些列入已知限制与 M6 的改进项（§4.3）。
- **CSP**：P1–P5 的全部场景（含排版 Worker、中文输入、粘贴、表情与符号）都没有触发 `font-src data:`、`worker-src blob:`，P4 的定稿建议成立。

**环境**：与 P3、P4 相同：
- macOS 26.5.1、Apple M4 Pro；
- Playwright 1.63.0（无头），自带的 Chromium 153、本机 Google Chrome 153、Playwright 自带的 WebKit 26.6。

**验证范围**：
- **能力矩阵**：走用户的入口，包括工具栏与下拉、快捷键、右键菜单、`/` 菜单、段落把手、图片的浮动工具条、链接的信息框、查找替换对话框。
- **撤销口径**：能力矩阵里"撤销回到原状"比较的是正文的结构摘要（文字、段落样式、表格、链接、文字样式、图片），不是整份快照；整份快照的一致性由保存重开检查。
- **中文输入**：无头浏览器无法驱动系统输入法，用两种方式代替：
  - CDP 驱动（只有 Chromium 内核）：`Input.imeSetComposition` 与 `Input.insertText`。事件由浏览器渲染层的输入法接口产生，不经过系统输入法与平台视图层，也没有 keyCode 229 的 keydown；
  - 合成事件（三个浏览器）：分别按 Chrome 与 WebKit 的提交顺序派发。

  真实系统输入法的核对见附录 A。
- **粘贴**：用 P4 的合成粘贴，与快捷键粘贴走同一条路径。剪贴板内容是按 Word、WPS、网页、Google Docs、飞书的真实结构编写的样本（`spikes/m0/fixtures/paste/README.md`），不是真实截取。真实来源的复核登记为 DEF-006。
- **真实剪贴板**：跨标签页、表格与文字文档之间的复制用真实剪贴板，只在 Chromium 内核上测，因为无头 WebKit 不能读写剪贴板。

### 1.2 平台方案（结论的条件）

以下每一条都已在验证工程中实现并验证。生产实现由 M1 的编辑器适配层统一设计，依赖的内部行为见 §7：

1. **`/` 键**：在捕获阶段处理两条路径：隐藏输入元素上的 `/` keydown，以及数据为 `/` 的 `insertText` beforeinput（不经过 `/` 键的输入，例如系统文字替换）。
   - 光标在表格之外的空段落里时放行，由 SDK 弹出 `/` 菜单；
   - 其他位置阻止默认行为与传播，由平台执行插入文字的命令，沿用左侧文字的样式与所在链接；
   - 文档不可编辑时不介入，由 SDK 的权限检查处理。
2. **输入法事件归一**：`compositionend` 的数据与最后一次 `compositionupdate` 不同时：
   - 先拦下它，补发一次携带最终文字的 `compositionupdate`；
   - 等一个宏任务，再派发 `compositionend`；
   - 等待期间来了 keydown、beforeinput、input、compositionstart、focusout、mousedown 或 paste，先同步派发 `compositionend`，否则这些输入会被 SDK 当成组合中的输入丢掉（§3.3 第 5 条）。
3. **捕获时机**：这是对 P3 报告 §3.4 规则的补充：
   - 组合进行中不捕获；
   - 防抖从"最后一次修改"与"最后一次组合结束"中较晚的一个算起，因为 Chrome 的提交路径在 `compositionend` 时不产生 mutation；
   - 组合持续超过 3 秒就照常捕获。快照里的拼音会被提交后的下一次捕获覆盖，组合开始之前的修改不会一直写不进本机；
   - 隐藏输入元素失焦时复位组合状态，防止 `compositionend` 没有到达时一直挡住捕获。
4. **链接地址的白名单与规范写法**：命令守卫、粘贴清洗与服务端保存校验共用同一个判定，判定之后一律保存规范写法：
   - 含控制字符（制表符、换行等）的地址一律拒绝，因为浏览器解析时会去掉它们，`/\t/evil.example` 会变成协议相对地址；
   - `http`、`https`、`mailto`：保存 URL 解析后的 `href`，引号、尖括号、空格都被百分号编码，复制时不会注入 HTML；
   - 本站相对地址：按站点源解析，结果必须仍在本站，保存解析后的路径；
   - 文档内锚点 `#…`：不能含空白、引号与尖括号。

   各处的做法：
   - 命令守卫：添加、修改链接的命令，地址不合法就取消，写法不规范就改成规范写法再执行。守卫对任何来源的命令生效（链接框、Facade、协同回放）；
   - 粘贴清洗（包括内部片段）：规范化链接地址，不合法的去掉。纯文本粘贴时，SDK 把整段文字当成链接地址，这时链接文字本身合法就改用它；
   - 服务端保存校验（M3、M6）：地址必须合法，并且等于它的规范写法。
5. **表格单元格里不放图片**（00 号计划书 §4.3）：
   - 命令守卫：插入图片、移动内联图片、拖动浮动图片的目标位置在单元格里时取消；锚点在单元格里的图片不能改为内联；
   - 粘贴清洗：粘贴目标在单元格里时去掉图片。
6. **不支持的功能**：
   - 隐藏菜单：`DOC_UNSUPPORTED_MENUS` 共 30 个菜单项，包括形状（含子项）、页面设置、页眉页脚、分隔符、分节设置，以及 §4.3 之外、没有验证的浮动图片组合、层级与对齐；
   - 命令守卫：隐藏菜单不会停用命令，平台另外取消 15 个命令，涵盖切换版式、页面设置、分节与分节符、分栏符、页眉页脚、形状；
   - 粘贴清洗：去掉表格之外的分节符；
   - 加载时规范：版式改为 MODERN，并去掉页眉页脚数据与多余的分节符（验证工程只实现了版式一项，其余由 M1 补齐）；
   - 服务端保存校验：只接受 MODERN；不接受页眉页脚；表格之外只允许文末一个分节符（§5.1）。
7. **档案**：去掉公式引擎；排版 Worker 暂不启用；大纲侧栏纳入，目录块插件不注册（§5）。

### 2.3 发现

1. **`/` 键被吞掉**（`docs-ui/src/services/doc-paragraph-menu.service.ts:405-466`）：
   - 光标折叠时，keydown 与 input 两条路径都会检查 `/` 并弹出段落菜单，不论位置；
   - 菜单弹出后抢走焦点。Chromium 内核里其后键入的字全部丢失（` a/b 2026/9/25` 只剩 ` a`）；WebKit 里斜杠丢失，部分文字丢失；
   - 表格单元格里 `/` 同样被吞掉，但菜单不弹出（C8b：键入 `a/b` 得到 `ab`）；
   - 不经过 `/` 键的输入（系统文字替换、CDP 的 `insertText`）走 input 路径，结果相同；
   - 没有配置开关（服务作为渲染模块注册，不能 `override`）；
   - 平台的处理见 §1.2 第 1 条。空段落里的菜单仍会吞掉其后键入的字（平台与 SDK 默认相同），M6 的处理方向：菜单打开时收到可打印字符，就关闭菜单并插入 `/` 与这个字符；
   - 向上游报告，建议只在空段落开头触发，或者先插入 `/`，再弹出可过滤的菜单。
2. **链接地址**：
   - 编辑框用 `isLegalUrl` 校验：`javascript:alert(1)` 被拒，`javascript://x@example.com/%0Aalert(1)` 却能通过并原样保存（三个浏览器）；`data://…` 在编辑框里被拒（C7b）；
   - 添加、修改链接的命令本身不做任何检查（C7c 的 SDK 默认：`/\t/evil.example` 等 5 种绕过写法都原样保存）；
   - 打开链接时 SDK 再用 `isSafeUrl` 检查，所以点击不会执行。但地址会随复制写进其他应用，而复制时 `href` 不转义（`docs-ui/src/services/clipboard/udm-to-html/convertor.ts:214`）：带引号的地址复制出去，就会在剪贴板 HTML 里注入元素；
   - 平台按白名单规范化（§1.2 第 4 条）。C7c 的平台配置下，5 种绕过写法都不保存，带引号的地址保存为编码后的写法，修改链接的命令被取消。
3. **单元格里的图片**：
   - SDK 只在工具栏按钮上禁用（记录值 `class:disabled`）；
   - 段落菜单与 `/` 菜单的"插入图片"执行同一个命令，粘贴图片文件也能把图片放进单元格；
   - 把浮动图片（四周型）拖进单元格，锚点会落进单元格，再改成内联，就得到单元格里的内联图片（`doc.command.transform-non-inline-drawing`；锚点计算显式支持单元格，`docs-drawing-ui` 的 `doc-drawing-transformer-update.controller.ts` 里 `DocumentSkeletonPageType.CELL` 的分支）；
   - SDK 默认下以上三条路径都能放进图片，平台配置下都是 0（C5b）；
   - SDK 默认下，单元格里的内联图片、粘贴的图片与拖进来的浮动图片，保存重开都一致。这可以作为以后评估放宽这条限制的依据（需要走范围变更）。
4. **隐藏菜单不停用命令**：SDK 默认下，`doc.command.switch-mode` 把文档切成 TRADITIONAL，`docs.command.page-setup` 改动页面设置，形状命令插入 SVG；平台配置下全部取消（§5.2）。另外，隐藏父菜单后，子项（"插入矩形""插入椭圆"）仍能被功能搜索找到，所以子项要一并隐藏。
5. **图片**：浮动工具条有淡入动画，动画期间的点击只触发提示，不打开环绕方式的下拉。用户正常操作不受影响，自动化要等动画结束。

### 3.1 结论

### 3.3 发现

1. **WebKit 顺序下，撤销与重做破坏正文**（`docs-ui/src/controllers/render-controllers/doc-ime-input.controller.ts:160-166`、`services/doc-ime-state-change-interceptor.service.ts`）：
   - **两种提交顺序**：
     - Chrome 提交时先发一次携带最终文字的 `compositionupdate`，`compositionend` 的数据与之相同；
     - WebKit 提交时，先删除组合文字（`deleteCompositionText`），再插入提交的文字（`insertFromComposition`），最后派发 `compositionend`，中间没有携带最终文字的 `compositionupdate`。依据：WebKit 源码 `Source/WebCore/editing/Editor.cpp` 中 `Editor::setComposition(const String&, SetCompositionMode)` 的确认分支（2026-09 的主干）。macOS 上系统输入法选定候选时，走的正是这个确认分支。
   - **缺陷的机理**：在"数据不同"的分支里，拦截器在最后一次 mutation 执行时同步运行。这时这次更新的参数还没有缓存，撤销记录缺了最后一步替换。结果撤销按拼音的长度删除，会多删后面的字，在单元格里会删掉结构符；重做则插回拼音。
   - **影响范围**：正文本身正确，保存的快照也正确；出错的是撤销与重做。
   - **与浏览器无关**：合成事件在三个浏览器上结果一致，说明这是 SDK 的逻辑缺陷。真实 Safari 是否走这个分支，要用附录 A 的记录确认。
   - **处理**：平台的事件归一在三个浏览器上把 13 种情形全部修正；向上游报告。
2. **组合进行中会被捕获**：SDK 把每次更新写进模型（带 `noHistory`），变更检测看到的是有修改。
   - P3 的规则下，停在候选框上 1.5 秒，捕获时快照里是拼音；
   - 平台规则下，组合进行中不捕获，直到组合持续满 3 秒才照常捕获（快照里仍是拼音，会被提交后的捕获覆盖）；提交后按防抖捕获到最终文字；
   - 组合进行中调用一次 `save()` 不会打断输入。
3. **候选框的锚点**：系统输入法的候选框贴着隐藏输入元素里的 DOM 光标。
   - **隐藏输入元素的现状**：它放在画布上组合文字的末尾；字体固定为 16px，不随缩放变化；宽度很窄，会换行。
   - **默认的偏移**：组合文字变长时，DOM 光标比画布上的光标偏右 13–27 px，并随换行向下偏 18–54 px。缩放 150% 时画布上的组合文字变宽，偏移不变。
   - **不换行的效果**：让隐藏输入元素不换行（`white-space: pre`），纵向偏移变为 0；但横向偏移变成 13、44、89 px，约等于组合文字在隐藏输入元素里的全宽。两种方式都对不齐。
   - **M6 的缓解方向**：隐藏输入元素定位到组合开始处，字号按缩放与画布一致，并且不换行。真实候选框的位置要人工确认（附录 A）。
4. **CDP 与合成事件的差别**：浏览器派发原生事件时，每个监听器执行完都会清空微任务队列；脚本里的 `dispatchEvent` 是同步的，不会。SDK 在异步流程里记下组合文字，所以合成驱动每次派发之后都要清空一次微任务队列，否则会误报错乱。同一次提交里的几个事件之间不让出宏任务，因为原生事件也是在同一个任务里派发的。
5. **事件归一的延后派发**：归一把 `compositionend` 延后一个宏任务。SDK 在这段时间里仍认为在组合中，会忽略 keydown 与 input（`docs-ui/src/services/selection/doc-selection-render.service.ts` 的 `_initInputEvents`：`_isIMEInputApply` 为真时直接返回）。所以在同一个任务里紧接着到来的输入（例如提交后立即输入的标点）会丢失。平台在这些事件到来时先同步派发 `compositionend`，用例"提交后同一任务里紧接着输入"在两种顺序下都得到"你好，"。

### 5.3 发现

1. **切换版式的命令仍然注册**：1.0 注释掉了切换按钮，但 `doc.command.switch-mode` 可以执行，并且会改写图片的纵向定位；"页面设置"在 MODERN 下是"内容宽度"，会通过 `docs.command.page-setup` 改写版式。两者都要隐藏并守卫。
2. **Facade 的 `ensurePageHeader`** 在 MODERN 文档上直接报错（"modern document, header/footer is not supported"），与源码梳理的推测不同，不需要额外处理。
3. **目录的两种形态**：
   - **大纲侧栏**（docs-ui 配置 `toc: true`）：列出标题（标题、H1–H5，不含副标题），点击跳转，不产生任何修改，阅读模式下同样可用。
   - **目录块插件**：
     - 在正文里写入 `FIELD`（`fieldType: 'TOC'`）、每条目录的 `HYPERLINK`（只有 `headingId`，没有地址；首次保存补上空的 `url`），以及 `PAGEREF` 页码字段（无分页版式下全是 1）；
     - 只认带 `headingId`、`outlineLevel` 的标题：界面设置的标题有，样本构建器（Facade 的 `setStyle`）设置的没有，于是插不进目录；
     - 更新命令需要界面上的参数；
     - 纳入它，要扩展链接白名单与服务端校验，还要处理页码，收益有限。
   - **建议**："目录"以大纲侧栏的形式纳入 v0.1，目录块延期。00 号计划书 §4.4 已把目录列为暂缓项，r3 写明两者的区别。
4. **排版 Worker**（性能表的两种口径：画出来，从事件的 `timeStamp` 起，到光标右侧的画布像素变化为止；两帧，从监听器执行起，到两次 `requestAnimationFrame` 之后。Worker 模式下排版结果异步回到主线程，两帧时通常还没画出来，所以只有前者可比）：
   - **响应**：约 2 万字的样本上，键入画出来 p50 主线程约【待补】ms、Worker 约【待补】ms；组合更新画出来 p50 主线程约【待补】ms、Worker 约【待补】ms。小样本两种模式都约【待补】ms，没有差别。
   - **阻塞**：快速键入时，主线程模式最长阻塞约【待补】ms，Worker 模式约【待补】ms。
   - **内存**：Worker 模式多约 20 MiB（页面 35 MiB + Worker 17 MiB，对比主线程 32 MiB）。
   - **缺陷**：Worker 模式下，在表格单元格里键入后立即按 Tab，Tab 被吞掉，后面的字写进同一格。
     - 能力矩阵的 Worker 变体中，C5 的"单元格中键入与 Tab"步骤在【待补：浏览器】上都得到"甲一甲二"在同一格；
     - 审查者的探针：等待 100 ms（2 万字样本）或 200 ms（小样本）后再按 Tab 就正常；键入后立即按方向键、回车，两种模式都正常；主线程模式下各种等待时间都正常；
     - 其余能力项在 Worker 变体下与主线程模式一致。
   - **结论**：Worker 模式能明显减少主线程阻塞，但画出来的延迟改善有限，还有上面的缺陷。修复之前不启用，v0.1 用主线程排版。DEF-007 登记重新评估的前提：缺陷修复（上游，或平台在排版结果发布之前把 Tab 等导航键排到发布之后）、三个浏览器的表格导航用例、`worker=1` 下回归 V06 的文字文档动作。Worker 创建失败时的退路，届时与表格的公式 Worker 一起由 M4 的设计覆盖。
5. **公式引擎**：文字文档启用的插件都不依赖 `@univerjs/engine-formula`。
   - 去掉后，8 份文字文档样本打开后的快照与带公式引擎时一致（手写样本加载时随机生成的 `sectionId` 除外），保存重开一致，基本编辑正常；
   - 按 `doc@1` 的插件清单单独构建：首屏 JS 从 5.13 MiB 降到 3.75 MiB（未压缩，−27%），gzip 后从 1.23 MiB 降到 0.99 MiB（−19%）。
6. **CSP**：严格策略下没有强制违规。探测策略只报告两类，都是必要的：
   - `style-src` 的内联样式（界面与粘贴）；
   - `img-src blob:`（粘贴图片文件时量尺寸）。

   排版 Worker 模式下也没有 `worker-src blob:`。
7. **性能表里的 Steady**：打开后到"安静"的判定有约 3 秒的固定延迟（小样本同样约 3.3 秒），不能当作性能指标，汇总表只列 Rendered。

## 6. 对设计的影响

- **00 号计划书 §4.3**：
  - 能力清单按 §2.1 的结论标注；"`/` 快捷插入"写明只在空段落里触发；
  - 隐藏的入口改为 §5.1 的清单：增加页面设置、分节设置，以及浮动图片的组合、层级与对齐；内嵌公式在开源版不存在；
  - "目录"改为：大纲侧栏纳入，目录块延期；
  - 单元格里不放图片，由平台落实。SDK 默认下单元格图片保存重开一致，以后可以评估放宽（走范围变更）。
- **00 号计划书 §4.5（已知限制）**：增加三条：
  - 从其他应用粘贴时，部分格式可能丢失（§4.3 的偏差）；
  - 空段落里键入 `/` 会打开插入菜单（M6 改进前，其后键入的字会丢失）；
  - 输入法候选框的位置可能与文字有偏差（人工核对后定）。
- **00 号计划书 §7.3**：捕获时机加上组合输入，见 §1.2 第 3 条：组合进行中不捕获；防抖从最后一次组合结束算起；组合持续超过 3 秒照常捕获；失焦时复位。
- **00 号计划书 §8.1、§8.5**（服务端保存校验）：
  - 文字文档只接受 MODERN 版式，不接受页眉页脚，表格之外只允许文末一个分节符；
  - 链接地址必须合法，并且等于它的规范写法（与图片的默认拒绝同一处实现）；
  - 不接受目录块的区间。
- **00 号计划书 §11.3**：CSP 定稿（P4 报告 §3.3）不变。
- **00 号计划书 §12**：文字文档的性能基线（§5.2，"画出来"的口径）；排版 Worker 暂不启用。
- **插件档案 v1 §2、§5.1、§7**：`doc@1` 的最终范围（§1.2 第 7 条）、隐藏清单与平台策略。
- **M1（编辑器适配层）**：
  - 集中封装 §1.2 的平台策略与 §7 的内部 API；
  - 加载时的规范补齐：去掉页眉页脚数据与表格之外多余的分节符；
  - 用 `e2e/v13-*.spec.ts` 的对照用例锁定 SDK 行为，升级 SDK 时先跑。
- **M4**：捕获时机的组合输入感知（含 3 秒上限与失焦复位）。
- **M6（文字文档模块）**：
  - 粘贴的转换偏差：决定平台侧的 HTML 规范（粘贴前处理 `<br>`、Google Docs 的外层 `<b>`、`<em>`、`<h6>`、Word 与 WPS 的标题样式、列表标记），或者提交上游；
  - 空段落里 `/` 菜单吞字（§2.3 第 1 条）；
  - 候选框位置的缓解（§3.3 第 3 条）；
  - 单元格里的表格按钮禁用、向前删除键删除图片等可用性问题；
  - 延期项：Windows 输入法（DEF-005）、真实来源的粘贴（DEF-006）、排版 Worker 的重新评估（DEF-007）、真实 Safari 的复核（DEF-008）。
- **上游报告**（M1 起跟踪）：
  - `/` 键被吞掉（含单元格里不弹菜单、空段落里菜单吞字）；
  - WebKit 顺序的撤销缺陷；
  - 链接框接受 `javascript://`，添加、修改链接的命令不检查地址；
  - 复制时 `href`、`data-rangeid` 不转义；
  - 纯文本粘贴的链接地址是整段文字；
  - 粘贴转换的偏差；
  - 单元格里粘贴含表格的内容静默失败；
  - 浮动图片可以拖进单元格，再改为内联；
  - 隐藏父菜单后，子项仍能被功能搜索找到；
  - Worker 模式下单元格里的 Tab 丢失；
  - 候选框锚点（隐藏输入元素放在组合文字末尾、字号固定、会换行）。

## 7. 内部 API 登记

| 用途 | 依赖 | 说明 |
|---|---|---|
| `/` 键、输入法事件归一 | 隐藏输入元素 `div#__editor_<unitId>` 及其事件顺序；段落菜单服务在 keydown 与 input 上的行为；SDK 在组合中忽略 keydown 与 input | 在捕获阶段监听 `document`；升级 SDK 时由 `e2e/v13-capabilities.spec.ts`（C8、C8b）与 `v13-ime.spec.ts` 回归 |

| 捕获时机 | 隐藏输入元素上的 `compositionstart`、`compositionend`、`focusout` | DOM 事件，不依赖 SDK 服务 |
| 大纲侧栏 | docs-ui 配置 `toc: true` | 公开配置 |

## 附录 A：真实输入法的人工核对（macOS）

无头浏览器无法驱动系统输入法，以下由人在真实的 Safari 与 Chrome 里操作，约 15 分钟。**这是 V13 结论的前提，M0 结束评审前完成**（待办、负责人与结果不符时的处理见 P5 交接单）。

1. **准备**：在 `spikes/m0` 下执行 `npx vite build`，再执行 `node scripts/ime-real.ts --open`。脚本启动验证服务（端口 4790），并在 Safari 与 Chrome 中打开记录页（SDK 默认行为的页面）；对照页面（平台策略）的地址会打印在终端里。
2. **输入法**：系统设置 → 键盘 → 输入法里要有"简体拼音"（本机已有）；五笔可选。
3. **操作**：按页面右下角的清单进行：
   1. 切换到简体拼音；
   2. 在正文末尾输入 `nihao`，空格上屏，留意候选框是否贴着正在输入的文字；
   3. ⌘Z 撤销一次，⇧⌘Z 重做一次；
   4. 输入 `zhongwenshuru`，空格上屏；
   5. 选中两个字，输入 `tihuan` 替换；
   6. 输入中文逗号与句号；
   7. 在中文标点状态下按 `/` 键（得到顿号），再按 Shift 切到英文标点后按 `/` 键；
   8. 输入 `ceshi` 后按 Esc；再输入 `ceshi` 后按 Shift 切换中英文；再输入 `ceshi` 后点一下工具栏（焦点切走）；
   9. （如已安装五笔）输入 `a` 空格、`khlg`；
   10. 点"上传记录"。在另一个浏览器里重复；再在平台策略的页面里重复第 2–3、7–8 步。
4. **汇总**：回到终端按回车，脚本汇总记录，写入 `e2e/results/v13/ime-real/`。汇总只统计浏览器产生的事件（`isTrusted`）：平台策略页面上补发的事件不是浏览器产生的，计入会误判提交顺序。
5. **判定**：
   - Safari 的提交是否为"不同（WebKit 顺序）"；SDK 默认页面上，撤销后是否多删字、重做后是否出现拼音；平台策略页面上是否正确；
   - Chrome 的提交是否为"相同（Chrome 顺序）"，撤销是否正确；
   - 英文标点状态下按 `/`：keydown 的 `key` 与 beforeinput 的数据；平台策略页面上 `/` 是否原样插入；
   - Shift 切换中英文、焦点切走时，未提交的组合文字是否提交或保留，捕获与撤销是否正常；
   - 候选框是否明显偏离输入位置（§3.3 第 3 条）。
6. **回放**：记录的事件序列用合成驱动回放，结果补进 §3。
