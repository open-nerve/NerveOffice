| 编号 | 验证项 | 结论 | 一句话 |

| V09 | 阅读模式下的拦截，以及入口隐藏 | **通过** | 采用"本地权限点 + mutation 防火墙"：表格 28 个、文字文档 8 个编辑入口在三个浏览器中全部被拦截（编辑模式对照组证明这些入口都有效），不留痕迹，不产生页面错误；撤销重做被拦截；复制可用；原地切换与销毁重建都干净，原地切换可以在运行时关掉工具栏与右键菜单。**00 号计划书 §6.5 的做法不可用**：表格的 `setReadOnly()` 要求先创建保护规则，会写入必须为空的保护类资源，禁止复制，而且筛选、排序、增删工作表等 9 个入口照样能用 |
| V10 | 性能基线 | **通过** | 5 万单元格、1,000 公式的样本：首屏 0.52–0.74 秒，第一次键入全部被接受，按键到下一帧 p95 ≤ 36 ms。**主线程模式下，一次牵动约 320 个公式的修改会冻结界面 0.66–0.83 秒**（公式引擎每 500 个公式才让出一次主线程）；Worker 模式下帧间隔 p95 ≤ 34 ms，代价是多约 8–9 MiB 内存。据此决定：表格默认启用公式 Worker；Worker 不可用时，销毁后以主线程模式重建，并把让出间隔调到 20（冻结降到 67–88 ms） |

**另有两条影响设计的发现**：

- **真实用户身份会锁死编辑**：给 SDK 设置一个不以 `Owner_`、`Editor_` 开头的用户 id 后，没有任何保护规则的单元格也改不了（三个浏览器一致）。平台不能把真实用户交给 SDK 自带的本地授权服务（§5.3）。
- **删除大表时会清空整个撤销栈**，而"大表"是按数据**行**数判断的（SDK 的计数函数按行计数，与复制时按单元格计数不一致，§2.3 第 5 条）。

**环境**：macOS 26.5.1、Apple M4 Pro（12 核）、48 GiB 内存、Node.js 24.3.0；Playwright 1.63.0（无头模式）自带的 Chromium 153.0.8010.12、本机 Google Chrome 153.0.8010.53、Playwright 自带的 WebKit 26.6。性能数据只作相对基线（M0 总设计 §7）。

**验证范围**

- 三个浏览器全部覆盖；表格的公式 Worker 模式在 V06 打开静默、V06 大表复制、V07、V08 端到端、V09（选定的 `combined` 方案）、V10 中三个浏览器都覆盖了，补上了 P2 交给本 Phase 的 Worker 回归。

## 1. 验证工程与样本

- **变更检测原型**（`src/harness/change-detector.ts`）：在创建文档单元之前挂上，用 Facade 的 `CommandExecuted` 事件（公开 API，带执行选项）按 §2.1 的规则判定"检测到修改"，并记录全部命令（id、类型、选项、`unitId`、时间）；另外跟踪公式计算会话（§3.4）。`syncOnly` 的 mutation 这个事件收不到，只在分析时通过协同钩子旁路记录。
- **捕获时机**（`src/harness/capture-timing.ts`）：§3.4 的规则。
- **内容比较**（`src/harness/content-compare.ts`）：以 JSON 文本为准；资源按名称排序并展开，做空值等价归一化；去掉视图状态字段（工作表的 `zoomRatio`、`scrollTop`、`scrollLeft`，文字文档的 `settings.zoomRatio`）。其余任何差异都算内容变化。
- **阅读模式的四种方案**（`src/harness/read-mode.ts`）、**菜单审计**（`src/harness/menu-audit.ts`）、**计时工具**（`src/harness/perf.ts`）。
- **样本**：P2 的 19 个 fixtures（15 个 SDK 生成、2 个手写最小样本、2 个空白样本）；另由确定性构建器（`src/experiments/p3-samples/`，固定随机种子）生成、写入验证服务的文档存储、不入库：

  | 样本 | 内容 | 体积 |
  |---|---|---|
  | `big-1m` | 明细表 20 列，约 2,300 行，每 10 行一个行合计公式 | 1.0 MiB |
  | `big-5m` | 同上，约 13,300 行（265,800 个单元格） | 5.0 MiB |
  | `perf-50k` | 数据表 5,000 行 × 10 列（其中 600 个行合计公式）+ 汇总表 400 个公式（分类统计、列统计、300 个 `VLOOKUP`），共 50,410 个单元格、1,000 个公式 | 0.95 MiB |
  | `formula-scenarios` | 依赖链 200 层；2 万行的聚合；跨表引用；200 个 2 万行的 `SUMPRODUCT`；`NOW`、`TODAY`、`RAND`、`RANDBETWEEN` | 0.48 MiB |
  | `doc-20k` | 约 2 万汉字，含一级、二级标题、有序与无序列表、加粗 | 90 KiB |
  | `doc-1m` | 同样的结构，按字节数生成到约 1 MiB | 1.0 MiB |

- **汇总**：`node scripts/p3-summary.ts [v06 … v10]` 把结果文件汇总成本报告中的表格。

## 2. V06 变更检测

### 2.1 结论：通过

- **打开静默**：23 个样本的 37 种组合（19 个 fixtures，其中 11 个表格另跑 Worker 模式；4 个大样本，其中 3 个表格另跑 Worker 模式）× 3 个浏览器，打开后到 `Steady` 再 5 秒，**检测到修改 0 次，迟到的内容变化 0 处**。唯一出现过的非本地 mutation 是单元格编辑器内部文字文档的 `doc.mutation.rich-text-editing`，按"其他单元"排除。
- **动作矩阵**：56 种动作 × 3 个浏览器全部通过；表格的 42 种动作另在公式 Worker 模式下跑一遍，也全部通过（平台默认启用 Worker，§6.3）。48 种改内容的动作都被检测到，内容确实改变，捕获之后 5 秒内没有未被检测到的迟到变化；8 种只改视图的动作（选区、滚动、缩放、切换工作表、查找）没有被检测，内容不变。
- **规则**（修订 00 号计划书 §7.3，见 §2.4）：
  1. 监听 `CommandExecuted`（Facade 的公开事件，带执行选项），只看 `MUTATION`；
  2. 排除带 `onlyLocal`、`fromCollab`、`fromChangeset`、`fromFormula` 的 mutation；
  3. 排除作用于其他单元的 mutation（参数里有 `unitId` 但不是本文档）；
  4. 排除名单：`sheet.operation.clear-drawing-transformer`、`doc.operation.clear-drawing-transformer`。这两个命令名为 operation，类型却声明为 `MUTATION`，实际只清除界面上的图片变换框（`packages/sheets-drawing/src/commands/operations/clear-drawing-transformer.operation.ts:21-23`）。它们没有出现在打开数据里；表格的这一条单独出现时，正好是 DEF-002 的刷新路径改了图片的派生尺寸（`sheet-drawing-transform-affected.controller.ts:330-337`），排除它意味着这类变化只随下一次修改保存，与 DEF-002 的处理一致；
  5. **不排除**自动行高 `sheet.mutation.set-worksheet-row-auto-height`；
  6. 关掉大表操作的拆分：`UniverSheetsPlugin` 配置 `largeSheetOperation.largeSheetCellCountThreshold = Number.MAX_SAFE_INTEGER`。
- **排除 `onlyLocal` 的前提**：`onlyLocal` 不等于"不改持久化内容"。备注、超链接的位置联动（`sheets-note-ref-range.controller.ts:136`、`sheets-hyper-link` 的 `ref-range.controller.ts:138`）、公式文本的引用更新、公式结果写回都以 `onlyLocal` 修改持久化内容。规则成立，是因为前几类都紧随一次被检测到的修改、由同一次捕获带上；公式结果由 §3.4 的捕获时机收齐。

| 用例 | 捕获时刻 | 最后一条行高变化 | 行高 mutation | 捕获之后才到达 |
|---|---|---|---|---|
| 1,500 行改字号 | 约 1.01 秒 | 0.05–0.09 秒 | 4 | 0 |
| 2 万行改字号 | 约 1.03 秒 | 0.54–0.96 秒 | 41 | 0 |

**大表复制**（`perf-50k` 的数据表 50,010 个单元格；`big-5m` 的明细表 265,800 个单元格）：

| 配置 | 立即捕获中的单元格 | 按 §3.4 的时机捕获（S1） | 同步复制耗时 | 本地 mutation 的最后一条（含懒执行与公式写回） |
|---|---|---|---|---|
| 默认拆分 | **3,000**（两种样本、三个浏览器都一样） | 完整 | 10–17 ms（5 万）/ 29–58 ms（26.6 万） | 0.10–0.35 秒 |
| 关掉拆分 | 完整 | 完整 | 18–27 ms / 69–113 ms | 0.12–0.47 秒（这时没有懒执行，只有公式写回） |

- 默认拆分时，第一批 3,000 个单元格随插入工作表执行，其余先以 `syncOnly` 宣告（`CommandExecuted` 收不到；5 万单元格的样本 17 条，26.6 万单元格的样本 89 条），再在空闲时以 `onlyLocal` 执行（不会被检测到）。
- 平台在"释放编辑权、交出编辑权、标签页转入后台"时会立即上传（00 号计划书 §7.2）。如果用户复制大表后马上切走，上传的快照里复制品只有 3,000 个单元格，其余部分之后也不会再触发检测。
- 本机上懒执行通常在 1 秒防抖之内完成，S1 都是完整的；但它跑在 `requestIdleCallback` 上（超时 60 秒，`lazy-execute-schedule.service.ts:141-145`），忙碌或后台的标签页可以把它任意推迟，这时按时机捕获也会不完整。
- 关掉拆分后，复制完全同步执行，多花 4–56 ms 的主线程时间，立即捕获也是完整的；代价是大表复制、删除的撤销记录会带上整表数据（占内存）。Worker 模式下复制品的公式结果与原表一致（两种配置都是）。
- WebKit Worker 模式下，复制品 600 个公式的结果写回有时要 1.1 秒：上一次运行里两种拆分配置都是，本次为 0.13–0.15 秒。关掉拆分时同样出现，所以它来自公式写回，不是懒执行。Worker 里第一次计算的耗时波动较大，V08 端到端也有同样的现象。捕获都按 §3.4 等到了写回。

**观察者效应**（`sheet-all`、`sheet-core`、`sheet-dv`，三个浏览器）：对每个工作表调用 `getDataValidations`、`getConditionalFormattingRules`、`getFilter`、`getImages` 之后，`sheet-all`、`sheet-core` 的 `save()` 字节变了，但规范化之后的内容不变；没有执行任何非本地 mutation，也没有被检测为修改。

### 2.3 发现

1. **1.0.0 打开文档不会触发自动行高**。自动行高改成了"命令内同步计算 + 其余交给空闲任务"：
   - 命令内只同步计算视口附近的 `ceil(10000 / 工作表列数)` 行（`packages/sheets/src/commands/commands/util.ts:35-43`，`getSuitableRangesInView`，按离视口的远近排序），作为命令的 mutation 同步产生；
   - 其余行由一个 `onlyLocal` 的 `MarkDirtyRowAutoHeightOperation` 交给空闲回调，每轮 500 行（`packages/sheets-ui/src/services/auto-height.service.ts:77、124-189`），算完执行的 `SetWorksheetRowAutoHeightMutation` 不带 `onlyLocal`；
   - `maxAutoHeightCount` 配置（`packages/sheets-ui/src/config/config.ts`）在 1.0.0 中没有被使用；
   - 所以列数多的表，几百行的操作就会走空闲路径（样本"数据"表 26 列，同步约 385 行，1,500 / 2 万 / 5 万行分别产生 4 / 41 / 101 条行高 mutation）。
   - 00 号计划书 §7.3（依据 rc.0）的"必须排除自动行高"已经不需要，而且会造成漏存（§2.2）。
2. **排除名单只需两条**，都是类型声明错误的"只改界面"的命令（§2.1）。
3. **大表复制的拆分会让"立即捕获"不完整**（§2.2），关掉拆分即可。
4. **观察者效应不产生 mutation**（§2.2）：读取方法对保存字节的影响属于空值等价。平台的编辑器适配层不应在捕获前调用这类读取方法（P2 报告 §2.3 第 5 条）。
5. **删除大表会清空整个撤销栈，且"大表"按行数判断**：删除工作表时，`util.countCells(worksheet.getCellMatrix())` 用 `ObjectMatrix.forEach` 计数，而它遍历的是**行**（`packages/sheets/src/commands/commands/util.ts:111-117`、`remove-sheet.command.ts:62-104`）；复制时用的是文件内按单元格计数的同名函数（`copy-worksheet.command.ts:56`）。实测：删除 5,001 行（5 万单元格）的表，撤销记录照常压栈；删除约 13,300 行的表，撤销栈被清空（1→0）。这不影响数据，但用户会失去全部撤销历史。关掉拆分（阈值设为最大）后，删除也不再清空撤销栈。建议向上游报告计数不一致的问题。
6. **视图状态**：表格缩放由渲染控制器直接写进 `zoomRatio`；文字文档缩放由 operation 写进 `settings.zoomRatio`（`packages/core/src/docs/data-model/document-data-model.ts:301-307`）。两者都不产生 mutation，随下一次真实修改保存（00 号计划书 §7.3 已接受），内容比较时去掉。

## 3. V07 公式一致性

### 3.1 结论：有条件通过

**条件**：捕获时机采用 §3.4 的规则。按这条规则，全部场景都一致，包括"计算进行中再改一次"。只用等待接口时，Worker 模式下不一致；只等"最近一轮"收齐时，计算进行中再改一次会存下过期值（§3.3）。

### 3.2 证据

- 命令：`npx playwright test e2e/v07-formula.spec.ts e2e/v07-worker-timeline.spec.ts`（5 个场景 × 2 种模式、2 个"静默窗口内再改一次"、10 个"计算进行中再改一次"、2 个时间线探针，× 3 个浏览器，共 72 个用例，全部通过；耗时数字取单独运行的结果）
- 结果：`e2e/results/v07/`、`v07/edit-during-quiet/`、`v07/edit-during-calc/`、`v07/timeline/`；汇总：`node scripts/p3-summary.ts v07`
- **判定**有两层：
  - 按公式定义，从快照中的输入独立推算公式结果，不依赖 SDK（跨表 A3 = `SUM(聚合!B) − 聚合!B1`，A1 = `(链!A1 + 199) × 2`）；
  - 用 `calc=forced`（`initialFormulaComputing = FORCED`）打开同一份快照，让 SDK 重算全部公式。审查者把 406 个公式的缓存值改成 0 后验证过这个基准：默认模式重开仍是 0，强制重算全部纠正。
- **易变函数**只能核对快照内部的一致性（A5 = A3 × 2、A4 的取值范围）；"修改无关单元格后是否重算"另外比较修改前后的 `RAND`。

**每个场景的三次修改各自独立**：

1. 修改 1：立即捕获（不等待）→ 只用等待接口后捕获；
2. 修改 2：从修改时刻起按 §3.4 的时机等待后捕获；
3. 修改 3：用 50 ms 的超时强制走超时后捕获 → 只用等待接口补捕获 → 按 §3.4 的时机补捕获；
4. 把第 2 步的快照重开（默认模式、强制重算）。

- **静默窗口内再改一次**（改"链!A1"后立即开始等待，300 ms 后再改"聚合!B1"，同时按新旧两种规则等待并各自捕获；核对"链"与"慢"两张表共 399 个公式）：

  - 旧规则：只等"最近一轮"逐表收齐，遇到 stop 视为收齐，在用例里内联复现；

  | A：Worker，两次都改"聚合!B1"（范围相交，走 stop） | 是 | 第二次修改 | 2.34–2.40 秒，**204/406 过期** | 4.69–4.81 秒，0 | 0 / 0 |
  | | 是 | 第一次修改 | 4.71–4.78 秒，0 | 5.20–5.27 秒，0 | 0 / 0 |
  | B：Worker，第一轮只有"聚合"一张表有结果，再改"链!A1" | 是 | 两种 | 0（时序侥幸） | 0 | 0 / 0 |

  - 新规则在 5 种情形、2 种起点、三个浏览器下没有超时，全部 0/406。
  - 计算结束后模型都正确；WebKit 的慢计算不到 1 秒，单独运行时旧规则也没有出错。

**等待的耗时**：

- 没有计算时，等待接口也要约 500 ms 才返回（三个浏览器 500–510 ms）；按 §3.4 的规则，它落在 1 秒防抖之内，不额外增加延迟。
- 按 §3.4 的规则，从修改到可以捕获：没有重计算的场景约 1.02–1.05 秒；牵动 200 个 `SUMPRODUCT` 的场景，Chromium、Chrome 上约 2.18–2.40 秒，WebKit 上约 1.02–1.03 秒（WebKit 的这类计算不到 1 秒，落在防抖之内）。
- 50 ms 超时：Worker 模式下按时超时。主线程模式下，重计算同步执行、整段阻塞主线程，超时的计时器要等计算结束才能触发，结果先写回，所以没有走到"超时"；依赖链、易变函数在 50 ms 内就算完了，本来也不会超时。

### 3.3 发现

1. **修改后不等待就捕获，公式值是旧的**：依赖链 199/199、`SUMPRODUCT` 200/200。计算不在修改的同一时刻完成，捕获前必须等待（00 号计划书 §7.3 的原则成立）。
2. **Worker 模式下，等待接口在第一张表的结果写回后就返回（SDK 缺陷）**：
   - Worker 模式下，主线程的 `UniverSheetsPlugin` 设了 `notExecuteFormula`，不注册结果写回控制器（`packages/sheets/src/plugin.ts:140-142`）。结果由 Worker 按**每张工作表一条** `SetRangeValuesMutation` 同步到主线程（`calculate-result-apply.controller.ts:47-99`；`data-sync-replica.controller.ts`、`remote-instance.service.ts:40-47`，同步时保留 `applyFormulaCalculationResult` 选项）；
   - 主线程的公式会话收到第一条带 `applyFormulaCalculationResult` 的写回，就把会话标为"结果已写回"（`packages/sheets-formula/src/controllers/sheet-formula-calculation-result-apply.controller.ts:30-31`），等待接口随即返回，其余工作表的结果还在路上；
   - 时间线（`e2e/results/v07/timeline/`）：Worker 模式下，结果 mutation、第一张表"聚合"的写回与等待接口的返回在同一毫秒，此时"慢!A1"还是旧值；"跨表""慢""易变"的写回在之后 1–3 ms 内陆续到达；
   - 主线程模式下，全部工作表在同一次同步执行中写回，等待返回时已经完整。
3. **捕获时机的第一版（等待接口一次 + 活动静默 1 秒）有漏洞**（审查 R1）：等待只在进入待捕获时发起一次，之后的修改只延长静默，不会重新等计算；第二次修改的计算超过 1 秒时就会捕获到旧值，而且公式结果写回不进入待捕获，之后不会补捕获。§3.2 的"静默窗口内再改一次"复现了它。§3.4 的规则修正了这一点。
4. **第二版（只等"最近一轮"逐表收齐）仍有漏洞**（第二轮审查 S1）：
   - **根因**：SDK 不把新的修改并进正在进行的一轮。不相交就排队，相交就先发 stop，但计算只在让出点检查 stop，常常照样算完。这一轮的完成通知处理完、再过 10 ms 防抖，才发新一轮的 start（`packages/engine-formula/src/services/formula-calculation-trigger.service.ts:122-188`）。"最近一轮收齐"不代表最后一次修改的结果已经算出，等待接口也只等调用时正在进行的那一轮。
   - **复现**：在第二次修改之后才开始等时，旧规则在情形 A 存下 204/406 个过期值，情形 C 存下 201/406；情形 B、D 没有出错，只是 20 ms 的轮询恰好晚于 10 ms 的防抖。
   - **从第一次修改开始等**：旧规则碰巧没有出错。检测到第二次修改后"从头重来"，又调了一次等待接口，而第一轮刚好算完，这次调用就等到了新一轮。但这依赖等待接口的内部行为，下面两种情况都会出错：
     - 打开时的计算还没算完，用户就改了单元格；
     - 实现把"又检测到修改"理解为立即重新开始等待。
   - **修正**：§3.4 的规则按状态判断：有没有排队的一轮、这一轮有没有被 stop、是否逐表收齐。两种起点、三个浏览器全部 0。
   - **严重程度**：过期值一旦被捕获，公式写回不会触发补捕获，默认模式重开也不重算，会一直留在服务端。
5. **重计算在主线程模式下会冻结界面**：公式引擎默认每执行 500 个公式（`intervalCount`）才让出一次主线程（`packages/engine-formula/src/services/calculate-formula.service.ts:65、295、328-333`）。
   - 200 个 `SUMPRODUCT` 不足 500 个，落在同一段里，主线程被一次性阻塞约 2.4 秒（Chromium、Chrome）/ 约 1.0 秒（WebKit）。时间线探针每 250 ms 采样一次，这段时间里一次都没有发生：最大间隔 2,403 / 2,416 ms（Chromium、Chrome）、986 ms（WebKit）。Worker 模式下采样不受影响。
   - V10 的性能样本也一样：一次牵动约 320 个公式的修改，在主线程模式下冻结界面 0.66–0.83 秒（§6.3）。
6. **易变函数**：打开时会被重算（§2.2）；修改无关单元格后也会重算（§3.2）；空闲 5 秒内没有持续触发计算（0 次），不会造成持续的写回或检测。

### 3.4 捕获时机（建议写入 00 号计划书 §7.2、§7.3）

实现与回归用例：`src/harness/capture-timing.ts`（判定"收齐"用的状态由 `src/harness/change-detector.ts` 跟踪）、`e2e/v07-formula.spec.ts`。

1. 用户修改被检测到后进入"待捕获"。公式结果写回本身**不**进入待捕获，否则打开含易变函数的文档就会被当成有修改。
2. 待捕获时循环：
   1. 记下最后一次修改的时刻，**在它之后**发起一次 `onCalculationResultApplied(timeout)`；
   2. 等到距最后一次修改满 1 秒（00 号计划书 §7.2 的"修改停止 1 秒后捕获"）；
   3. 等公式计算**收齐**，下面三条同时满足：
      - **没有排队的一轮**：最近一轮的 start 之后，没有再执行会触发计算的命令。SDK 不把新的修改并进正在进行的一轮（`packages/engine-formula/src/services/formula-calculation-trigger.service.ts:122-188`）。不相交就排队；相交就先发 stop，但计算只在让出点检查 stop，常常照样算完。这一轮的完成通知处理完、再过 10 ms 防抖，才发新一轮的 start。"会触发计算"与 SDK 的触发服务同一口径：命令在 `IActiveDirtyManagerService` 中登记了脏区转换，`shouldTrigger` 没有排除它，`getDirtyData` 非空，或者它是强制重算的触发命令。
      - **这一轮没有被 stop**：被 stop 的一轮不写回结果，没算完的部分会并进下一轮重新开始。
      - **逐表收齐**：以最近一条 `formula.mutation.set-formula-calculation-result` 中带结果的工作表为准，每张都收到带 `applyFormulaCalculationResult` 的 `sheet.mutation.set-range-values` 写回（已删除的工作表不计）。修改没有牵动任何公式时，SDK 仍会开始一轮计算，但只发带 `functionsExecutedState` 的完成通知、不发结果 mutation，这时视为收齐。
   4. 这期间又检测到修改，就回到第 1 步；否则捕获。
3. 捕获时刻 ≈ max（最后一次修改 + 1 秒，最后一次修改所触发的那一轮结果收齐）。没有计算时，约 0.5 秒的起始等待落在 1 秒防抖之内，不额外增加延迟。
4. 超过时限仍未收齐：照常捕获，标记"公式待更新"；收齐后补捕获。
5. 规则只看状态（排队、stop、逐表收齐），不依赖等待从哪一刻开始。§3.2"计算进行中再改一次"从第一次修改开始等和从第二次修改开始等，两种起点都一致。
6. 主线程上的顺序是"结果 mutation → 各表写回 → 完成通知"，"只有完成通知就视为收齐"依赖这个顺序：
   - 结果先于通知：`packages/engine-formula/src/controllers/calculate.controller.ts:232-257`；
   - 写回在结果 mutation 的监听里按表依次同步执行：`packages/sheets/src/controllers/calculate-result-apply.controller.ts:47-99`，监听在 mutation 执行后同步触发，`packages/core/src/services/command/command.service.ts:448-459`；
   - Worker 端按执行顺序同步回主线程：`packages/rpc/src/controllers/data-sync/data-sync-replica.controller.ts:59-70`，`postMessage` 保序。
7. 这条规则依赖几个内部约定（§7）：
   - `applyFormulaCalculationResult` 执行选项；
   - 公式 mutation 的 id，以及完成通知的 `functionsExecutedState`；
   - `IActiveDirtyManagerService` 的脏区转换。

   升级 SDK 时由以下用例回归：`e2e/v07-formula.spec.ts`（含"计算进行中再改一次"）、`e2e/v07-worker-timeline.spec.ts`（写回与通知的顺序）、`e2e/v06-actions.spec.ts`。

### 3.5 对设计的影响

- **00 号计划书 §7.2、§7.3**：写入 §3.4 的规则；删掉"捕获前等 `onCalculationResultApplied` 就够"的含义。
- **上游报告**（M4 实现管道时提交，平台规则已规避）：
  - Worker 模式下的公式会话应在收到全部工作表的写回之后才标记完成；
  - 等待接口不覆盖排队的下一轮：调用时正在进行的一轮结束就返回，调用之前的修改所排队的下一轮还没开始。
- **M4**：表格默认启用公式 Worker（§6.3），捕获时机必须按 §3.4 实现。

## 4. V08 捕获成本

### 4.1 结论：通过

- **1 MiB 表格**：捕获时主线程的最长阻塞 p95 不超过 32 ms。同步段（`save()` + 序列化）p95 为 21–32 ms；gzip 期间的最长阻塞 p95 为 24–29 ms；Chromium 内核里没有 50 ms 以上的长任务。00 号计划书 §12.2 的"p95 ≤ 100 ms"成立，余量充足，建议确认。
- **5 MiB 表格（单快照上限）**：同步段 p95 为 66–82 ms，gzip 期间的最长阻塞 p95 为 63–92 ms（Chromium 内核里是一个 88–90 ms 的长任务），都还在 100 ms 以内，但余量很小；规范化又是一段 76–85 ms 的同步计算（§4.3）。
- **文字文档**：1 MiB 的同步段 p95 不超过 11 ms，gzip 期间最长阻塞 p95 为 25–42 ms；2 万字的文档各项都在 12 ms 以内。

  - 00 号计划书 §12.2 要求"从修改停止到已保存在本机 p95 ≤ 2 秒"。捕获部分用掉约 1.1 秒，给本机写入与加密留下约 0.9 秒（P6 测量）。
  - 按默认配置（公式 Worker）的最坏值算，WebKit 打开后第一次修改只剩约 0.23 秒。
  - 这个目标只在公式计算不超过约 0.9 秒时成立。V07 的慢计算在 Chromium、Chrome 上光是等到能捕获就要 2.2–2.4 秒（§3.2），这类文档达不到；§12.2 要写明样本条件。
- **压缩率**：表格约 25%–26.5%，文字文档约 43%–47%，都高于 00 号计划书 §12.3 假设的 10%–20%（§4.4）。

### 4.3 发现

1. **1 MiB 的捕获成本很低**：整条管道约 50–55 ms，其中主线程被连续占用的最长一段约 30 ms。按 00 号计划书 §7.2 的"修改停止 1 秒后捕获"，捕获本身不会造成可感知的卡顿。
2. **5 MiB 接近 100 ms 的阻塞上限**：同步段与 gzip 期间的长任务各自都在 60–100 ms；再加上规范化（§4.3 第 3 条）就会超过。大快照的压缩、规范化与加密适合放进 Worker。但主线程至少要做完整个同步段：`save()` 加序列化（或代价相近的结构化克隆）才能把内容交给 Worker，5 MiB 时 p95 为 66–82 ms（SDK 的模型只在主线程上）。P6 按这个数估算。
3. **内容哈希要分两种口径**：
   - **会话内去重**（00 号计划书 §7.2 的"内容哈希与上次相同则跳过"）：直接对 `save()` 的 JSON 文本（或它的 gzip 结果）算哈希即可，1 MiB 约 1–2 ms。同一次加载里，内容不变时文本也可能变：视图状态（缩放写进 `zoomRatio`，不产生 mutation，§2.3 第 6 条）、观察者效应的读取方法（平台不调用，§2.3 第 4 条）。V06 比较的是规范化后的内容，不是字节。但这种口径的误差只会让内容没变的快照多上传一次，不会漏传，所以会话内去重不必规范化。
   - **跨加载与服务端**（服务端"内容哈希与当前相同时不递增修订号"、客户端重开后与服务端比较）：同样的内容在两次加载之间，`save()` 的文本可能不同（SDK 补齐默认字段、资源顺序、空值写法、视图状态，§1 与 P2 报告 §2.3），要用规范化口径（`content-compare.ts`）。规范化是同步计算，1 MiB 约 19–26 ms、5 MiB 约 73–85 ms，放在 Worker 或服务端做；客户端与服务端必须用同一种规范化算法。
4. **压缩率比预期低**：表格样本 gzip 后约为原来的 25%，文字文档约 45%。表格样本的数值是随机生成的两位小数，比真实数据难压缩，这个数字偏保守；文字文档的正文是汉字，UTF-8 下每个字 3 个字节，重复度低。真实文档的压缩率取决于内容，M7 压测时用真实样本复核。
5. **gzip 结果因浏览器而异**：同一份 JSON，WebKit 压缩后比 Chromium 内核大（表格约 5%，1 MiB 文字文档约 2%），两者的 gzip 实现不同。所以**不能对 gzip 结果跨浏览器比较哈希**，这也是第 3 条跨加载要对解压后内容算哈希的原因之一。

### 4.4 对设计的影响

- **00 号计划书 §12.2**：
  - 确认"1 MiB 文档捕获快照时的主线程阻塞 p95 ≤ 100 ms"（实测 ≤ 32 ms）。
  - "从修改停止到已保存在本机 p95 ≤ 2 秒"中，捕获部分约 1.04–1.09 秒，本机写入与加密的预算约 0.9 秒，由 P6 实测确认。按默认配置的最坏值（WebKit Worker 模式打开后第一次修改，1.77 秒）只剩约 0.23 秒。
  - 写明这个目标的样本条件：公式计算不超过约 0.9 秒。
- **00 号计划书 §12.3**：压缩率改为实测值（表格约 25%，文字文档约 45%）。按原公式重算示例：20 人持续编辑 1 MiB 的表格、每 15 秒上传一次，WAL 约 20 × 0.25 MiB ÷ 15 秒 ≈ 1.2 GiB/小时（原估计 0.5–1 GiB/小时）。会话内去重只能跳过"内容完全没变"的上传，持续编辑时不减少写入量。
- **00 号计划书 §7.4、§8.1**：服务端"内容哈希与当前相同时不递增修订号"（§7.4）与平台信封的"内容哈希（SHA-256，基于解压后的字节计算）"（§8.1）改为"基于规范化后的内容计算"，客户端与服务端用同一种规范化算法；§7.2 的会话内去重口径不变（第 3 条）。
- **P6**：本机写入与加密的实测从约 0.9 秒的预算里扣（最坏约 0.23 秒）；5 MiB 的压缩、规范化与加密考虑放进 Worker，主线程仍要承担 `save()` 加序列化（p95 66–82 ms）。
- **M4**：捕获管道按第 2、3 条实现。

   - 它还关掉了复制：复制要求 `WorkbookCopyPermission` 与 `WorksheetCopyPermission`（`packages/sheets-ui/src/commands/commands/clipboard.command.ts:155-161`），`readOnly` 模式只保留"查看"。
   - 即使补上 `protect()`，筛选、排序、增删复制隐藏工作表、合并、超链接、备注这 9 个入口也没被拦住（00 号计划书 §6.5 只提到了增删工作表）。
   - 文字文档的 `setReadOnly()` 在平台配置下只设置本地权限点：`ObjectPermissionService.supports()` 要求配置 `objectPermissionTypes` 包含文档类型（`packages/core/src/services/permission/object-permission.service.ts:188-191`），平台没有配置它，所以没有写入 `DOC_OBJECT_PERMISSION_PLUGIN`（实测为空）。以后若配置了 `objectPermissionTypes`，它就会写规则，需要复核。
2. **只靠权限点拦不全**：权限检查没有覆盖上面 9 个入口，防火墙兜住了它们。防火墙取消的是 mutation，命令会失败，但实测没有产生未捕获的异常或控制台错误。
3. **防火墙必须只拦本文档**（审查 R2）：每次点选单元格，SDK 都用 `ReplaceSnapshotCommand` 往隐藏的单元格编辑器（`__INTERNAL_EDITOR__DOCS_NORMAL`）写入当前单元格的内容（`packages/sheets-ui/src/controllers/editor/editing.render-controller.ts:395`），这是作用于其他单元的非本地 mutation。第一版防火墙不看 `unitId`，把它也挡了，原地退出后按 F2 编辑会把上一个单元格的内容写进当前单元格。收窄后，入口仍然全部被拦住，退出后的编辑正确。
4. **真实用户身份会锁死编辑**：本地授权服务按用户 id 的前缀判断角色，只有 `Owner_`、`Editor_` 前缀才允许编辑（`packages/core/src/services/authz-io/authz-io-local.service.ts:81-87、159、175`）。设置 `user-reader-1` 后，没有任何保护规则的单元格也改不了（两种样本、三个浏览器一致；对照组在默认身份下能改；审查者另外核对了其他 `Owner_`、`Editor_` 前缀的 id 仍能编辑）。平台要么不把真实用户交给 SDK，要么在编辑器适配层用自己的 `IAuthzIoService` 实现（全部允许；写入边界在服务端）。
5. **P2 交接的问题**：`setReadOnly` 是否写入保护类资源——表格会（经由必需的 `protect()`），文字文档不会；工作表背景图片的入口——隐藏（本期目标能力之外）。

## 6. V10 性能基线

### 6.1 结论：通过；据此决定表格启用公式 Worker

性能数据齐全。样本为 00 号计划书 §12.1 的表格样本 `perf-50k`：50,410 个单元格、1,000 个公式。

- **首屏**：从导航开始到 `Rendered`，第一次打开 0.64–0.74 秒，之后的打开中位数 0.52–0.56 秒；两种模式没有可测的差别。
- **第一次键盘输入**：画布一出现就点单元格键入。三个浏览器、两种模式、每种 3 次全部被接受，提交时刻在导航后 0.67–0.90 秒。
- **编辑响应**：键入 ASCII 字符，按键到下一帧 p50 为 24–26 ms，p95 为 33–36 ms。
- **公式计算**：两种模式的耗时相近。
  - 改一个被约 320 个公式引用的数据单元格，到结果收齐 0.69–0.86 秒；
  - 强制重算全部 1,000 个公式，0.75–0.96 秒。
- **计算期间的界面冻结**（本 Phase 最重要的性能发现）：
  - 主线程模式下，**这两种计算都整段冻结界面**：Chromium 内核约 0.78–0.89 秒，WebKit 约 0.66–0.71 秒。事件循环探针、帧间隔、Long Tasks 三种口径一致；
  - Worker 模式下，主线程最长阻塞 p95 不超过 15 ms，帧间隔 p95 不超过 34 ms。
- **内存**（Chromium 内核）：
  - 主线程模式：打开后 JS 堆 34.8–34.9 MiB，50 次编辑后 41.4 MiB；
  - Worker 模式：打开后页面 31 MiB 加 Worker 12.3 MiB，50 次编辑后 36.1–36.3 MiB 加 13.9 MiB；
  - Worker 模式合计多约 8–9 MiB。

据此决定：**表格默认启用公式 Worker**（插件档案 v1 原定"由 P3 的性能数据决定"）。Worker 不可用时，销毁实例、以主线程模式重建，并把公式引擎的让出间隔 `intervalCount` 调到 20 左右（§6.3）。

### 6.3 发现与公式 Worker 的取舍

1. **主线程模式的冻结来自公式引擎的让出间隔**：
   - 引擎每执行 `intervalCount`（默认 500）个公式才让出一次主线程，用 `MessageChannel` 让出（`packages/engine-formula/src/services/calculate-formula.service.ts:65、295、328-333`）；
   - 增量计算牵动的约 320 个公式不足 500 个，落在同一段里；
   - 全量重算的 1,000 个公式虽然分成两段，最长的一段仍有 0.85–0.89 秒（Chromium 内核的长任务）；
   - 调小让出间隔后，冻结随之缩短（上表），证实了这一点。
2. **调小让出间隔是主线程模式下的有效缓解**：
   - 让出间隔 20 时帧间隔降到 67–88 ms，5 时降到 38–55 ms，Chromium 内核里不再有 50 ms 以上的长任务；
   - 到结果收齐的总耗时，Chromium 内核多 0%–5%，WebKit 多 9%–15%。

   它的局限是：
   - 单个公式本身很重时，它帮不上忙。例如 V07 的 `SUMPRODUCT` 每个约 10 ms（Chromium），几十个就是一段可感知的冻结；
   - 主线程总的计算量不变，计算期间的输入仍要和它抢时间；
   - 两段计算之间执行的修改更容易赶上"计算进行中"，捕获必须按 §3.4 等排队的下一轮（§3.2 情形 C）。
3. **两种冻结口径的差别**：
   - **现象**：调小让出间隔后，Chromium 内核里的事件循环探针（`setTimeout` 链）比帧间隔长很多，而最长的长任务与帧间隔一致。例如间隔 100 时，探针约 0.49–0.50 秒，帧间隔约 0.25–0.28 秒，最长长任务约 0.25–0.27 秒。
   - **原因**：主线程并没有被连续占住那么久，是 `setTimeout` 被推后了。两段计算之间，先轮到渲染和 `MessageChannel` 的任务。
   - WebKit 没有这种差别；用户看到的冻结以帧间隔为准。
   - 间隔为 500 时，增量计算只有一整段，全量重算的两段里最长的一段占了几乎全部时间，三种口径一致。
4. **测量工具的两处修正**（审查之后的复验中发现，`src/harness/perf.ts`）：
   - 事件循环探针与 Long Tasks 观察器原来都在"计算刚结束、await 的后续代码与这段长任务同属一个任务"时就停止采集。前者漏掉了最后这段阻塞，后者把记录算进了下一次测量。
   - 修正前的 V10 把主线程模式的冻结记成 6–63 ms，是错的。
   - 修正后重跑了 V08 的捕获成本、V10 与 V06 的大表复制。V08 与 V06 的停止点之前本来就有空闲时间，结论不变，数字只有运行之间的正常波动。
5. **首屏与内存**：
   - Worker 模式首屏没有可测的变慢：第一次打开时，两种模式分别是 0.71 / 0.71 秒（Chromium）、0.73 / 0.74 秒（Chrome）、0.64 / 0.65 秒（WebKit）；之后的打开相同；
   - Worker 模式合计多约 8–9 MiB 的 JS 堆，页面自己的堆少约 4 MiB（公式数据移到 Worker）；
   - 50 次编辑后，两种模式都增长约 6.5–7 MiB，没有看到持续增长的迹象（正式的内存增长测试在 M7）。
6. **第一次输入不会丢**：画布出现后立即键入，三个浏览器、两种模式都被接受；最慢的一次提交在导航后 0.90 秒（第一次打开）。

**公式 Worker 的取舍**：

| | 主线程（默认让出间隔） | 主线程（让出间隔 20） | **Worker（推荐）** |
|---|---|---|---|
| 计算期间界面冻结（本样本） | 0.66–0.89 秒 | 67–88 ms | ≤ 34 ms（帧间隔 p95） |
| 单个重公式 | 整段冻结 | 仍然冻结 | 不冻结 |
| 到结果收齐 | 基准 | Chromium 内核多 0%–5%，WebKit 多约 9% | Chromium 内核多约 3%–5%，WebKit 多约 7%–8%（Worker 模式下等待接口在第一张表写回后就返回，逐表收齐的轮询最多多计 20 ms） |
| 内存 | 基准 | 基准 | 本样本（约 1 MiB）多约 8–9 MiB；Worker 持有整本工作簿的副本，随文档变大，5 MiB 没有测（M7） |
| 捕获时机 | 需要 §3.4：等待接口只等调用时正在进行的一轮，排队的下一轮不覆盖 | 同左（两段计算之间执行的修改更容易排队） | 需要 §3.4：此外等待接口在第一张表写回后就返回，要逐表收齐 |
| 已验证的范围 | V06–V10 | V07（计算进行中再改一次）、V10 | V02（CSP，P1）、V06（打开静默、动作矩阵、大表复制）、V07、V08 端到端、V09（`combined`）、V10 |

推荐 Worker：它是唯一不受单个公式开销影响的方案。代价是约 8–9 MiB 内存（本样本），以及依赖 §3.4 的捕获时机，这条规则两种模式本来都要实现。主线程加小让出间隔作为 Worker 创建失败时的退路。需要注意：

- **退路要销毁重建**：Worker 模式下，主线程的三个公式相关插件注册时就设了 `notExecuteFormula`（`packages/sheets/src/plugin.ts:140-142`）。Worker 起不来时，公式永远不会计算，每次捕获都要等到超时（按源码推断，未验证）。所以"退回主线程"要销毁实例，再以主线程模式重建；判定条件与重建流程由 M4 设计。
- **Worker 里的让出间隔**：Worker 里也是默认每 500 个公式才让出一次，而 stop 只在让出点检查。所以计算进行中再改一处时，stop 基本不生效，要等这一轮算完再从头算。
  - §3.2"计算进行中再改一次"的情形 A 里，最新结果 4.7–4.8 秒才收齐，单独一次计算约 2.3–2.4 秒，晚了约一倍；
  - 给 Worker 配小一些的让出间隔（20–100）可以让 stop 及时生效，开销由 M4 测量。

### 6.4 对设计的影响

- **插件档案 v1**：表格默认启用公式 Worker。主线程注册 `UniverRPCMainThreadPlugin`，三个公式相关插件设 `notExecuteFormula: true`；Worker 内的注册见档案 §1。退路为销毁后以主线程模式重建，`UniverFormulaEnginePlugin` 配置 `intervalCount: 20`。

  - "编辑响应"与"事件循环延迟"的目标值在 M7 定，建议以"计算期间帧间隔 p95 ≤ 100 ms"作为界面不冻结的目标。
