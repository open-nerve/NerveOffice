# P3 验证报告：编辑语义与性能基线

> 日期：2026-09-24｜所属：M0-P3｜Univer 版本：1.0.0｜验证工程：`spikes/m0/`｜修订：初稿（审查前）

## 摘要

| 编号 | 验证项 | 结论 | 一句话 |
|---|---|---|---|
| V06 | 打开文档不被误判为有修改 | **通过** | 37 种样本（含 Worker 模式与大样本）在三个浏览器中打开后都没有被检测到修改；48 种改内容的动作都被检测到，8 种只改视图的动作都没有被检测，检测安静后没有漏掉的迟到变化。规则要按 1.0.0 修订：**取消"排除自动行高"**（它会让捕获早于迟到的行高变化），排除名单只收录两个只清除图片变换框的命令，并**关掉大表操作的拆分**（否则复制大表后立即捕获只能拿到 3,000 个单元格） |
| V07 | 公式结果一致性 | **通过** | 按本报告建议的捕获时机（等待接口返回后，再等"活动"静默 1 秒，活动包括公式结果写回），五类场景在主线程与 Worker 两种模式、三个浏览器下，快照中的公式值都与公式定义一致，重开与强制重算也一致。**只用等待接口不够**：Worker 模式下它在第一张表的结果写回后就返回（SDK 缺陷），其他表的公式值可能是旧的 |
| V08 | 快照捕获的成本 | **通过** | 1 MiB 表格一次捕获：同步段（`save()` + 序列化）p95 为 21–31 ms，gzip 期间最长阻塞 p95 为 21–29 ms，都远低于 00 号计划书 §12.2 的 100 ms。5 MiB 表格的同步段为 66–79 ms，gzip 时有一段 66–95 ms 的阻塞，接近上限，建议大文档把压缩放进 Worker。表格压缩后约为原来的 25–26%，文字文档约 43–47%，都高于 §12.3 估算用的 10%–20%。打开自检与资源加载错误捕获的开销都很小 |
| V09 | 阅读模式下的拦截，以及入口隐藏 | **通过** | 采用"本地权限点 + mutation 防火墙"，表格 26 个、文字文档 8 个编辑入口在三个浏览器中全部被拦截，不留痕迹，不产生页面错误；撤销重做被拦截；保护类与不支持功能的入口已隐藏，阅读模式关掉工具栏、右键菜单与底栏菜单。**00 号计划书 §6.5 的做法不可用**：表格的 `setReadOnly()` 要求先创建保护规则，会写入必须为空的保护类资源，而且筛选、排序、增删工作表等 9 个入口照样能用 |
| V10 | 性能基线 | **通过** | 数据齐全。5 万单元格、1,000 公式：首屏（到 `Rendered`）p50 0.52–0.56 秒，按键到下一帧 p50 22–26 ms，修改一个被约 320 个公式依赖的单元格后 0.66–0.83 秒写回，全量重算 0.72–0.92 秒，JS 堆 31–41 MiB（Chromium）。常见公式在主线程上是分片计算的，计算期间最长阻塞不超过 51 ms；但 V07 的 200 个数组运算会让主线程一次性阻塞 2.1 秒，Worker 模式没有这个问题。**建议启用公式 Worker**（§6.3） |

**另有两条影响设计的发现**：

- **真实用户身份会锁死编辑**：给 SDK 设置一个真实用户 id（不以 `Owner_` 开头）后，没有任何保护规则的单元格也改不了（三个浏览器一致）。平台不能把真实用户交给 SDK 自带的本地授权服务（§5.3）。
- **删除大表时会清空整个撤销栈**，而"大表"是按数据**行**数判断的（SDK 的计数函数按行计数，与复制时按单元格计数不一致，§2.3 第 5 条）。

**环境**：macOS 26.5.1、Apple M4 Pro（12 核）、48 GiB 内存、Node.js 24.3.0；Playwright 1.63.0 自带的 Chromium 153.0.8010.12、本机 Google Chrome 153.0.8010.53、Playwright 自带的 WebKit 26.6。性能数据只作相对基线（M0 总设计 §7）。

**验证范围**

- 三个浏览器全部覆盖；表格的公式 Worker 模式在 V06 打开静默、V06 大表复制、V07、V10 中三个浏览器都覆盖了，补上了 P2 交给本 Phase 的 Worker 回归。
- 文字文档只做变更检测、阅读模式与捕获成本；文字文档的能力、中文输入与性能在 P5。本机存储、加密与锁在 P6，V08 只测到"压缩与哈希完成"。
- 编辑入口大部分通过 Facade 或命令触发（与界面走同一个命令），键盘输入、粘贴、快捷键撤销重做、拖动填充、编辑栏、滚动等用真实的键盘鼠标操作（各表格标明了方式）。
- 真实 Safari 没有覆盖本 Phase 的交互实验（P1 的页面自检只覆盖 CSP）；WebKit 的结果作为 Safari 的代表。

## 2. V06 变更检测

### 2.1 结论：通过

- **打开静默**：37 种样本 × 3 个浏览器，打开后到 `Steady` 再 5 秒，**检测到修改 0 次，迟到的内容变化 0 处**。唯一出现过的非本地 mutation 是单元格编辑器内部文字文档的 `doc.mutation.rich-text-editing`，按"其他单元"排除。
- **动作矩阵**：56 种动作 × 3 个浏览器全部通过。48 种改内容的动作都被检测到，内容确实改变，5 秒内没有未被检测到的迟到变化；8 种只改视图的动作（选区、滚动、缩放、切换工作表、查找）没有被检测，内容不变。
- **规则**（修订 00 号计划书 §7.3，见 §2.4）：
  1. 监听 `onCommandExecuted`，只看 `MUTATION`；
  2. 排除带 `onlyLocal`、`fromCollab`、`fromChangeset`、`fromFormula` 的 mutation；
  3. 排除作用于其他单元的 mutation（参数里有 `unitId` 但不是本文档）；
  4. 排除名单：`sheet.operation.clear-drawing-transformer`、`doc.operation.clear-drawing-transformer`。这两个命令名为 operation，类型却声明为 `MUTATION`，实际只清除界面上的图片变换框，不改内容（`packages/sheets-drawing/src/commands/operations/clear-drawing-transformer.operation.ts:21-23`）。
  5. **不排除**自动行高 `sheet.mutation.set-worksheet-row-auto-height`；
  6. 关掉大表操作的拆分：`UniverSheetsPlugin` 配置 `largeSheetOperation.largeSheetCellCountThreshold = Number.MAX_SAFE_INTEGER`。

检测到的 mutation 逐项见 `node scripts/p3-summary.ts v06` 的"动作矩阵"一节。

**按 00 号计划书 §7.3（排除自动行高）推演**：用同一批检测记录计算——如果排除自动行高，捕获会发生在最后一次其他检测之后 1 秒：

| 用例 | 捕获时刻 | 最后一条行高变化 | 行高 mutation | 捕获之后才到达 |
|---|---|---|---|---|
| 1,500 行改字号 | 约 1.0 秒 | 0.06–0.09 秒 | 4 | 0 |
| 2 万行改字号 | 约 1.03 秒 | 0.53–0.93 秒 | 41 | 0 |
| **5 万行改字号** | 约 1.06 秒 | **1.58–2.58 秒** | 101 | **32–62** |

5 万行时，三个浏览器都有三到六成的行高变化在捕获之后才到达，而且它们被排除、不会再触发检测，于是一直漏存到下一次修改。按现行规则（不排除），静默窗口会一直等到最后一条行高变化之后，三个浏览器都通过。

**大表复制**（`perf-50k` 的数据表 50,010 个单元格；`big-5m` 的明细表 265,800 个单元格）：

| 配置 | 立即捕获中的单元格 | 1 秒静默后捕获（S1） | 同步复制耗时 | 懒执行最后一条 |
|---|---|---|---|---|
| 默认拆分 | **3,000**（两种样本、三个浏览器都一样） | 完整 | 10–17 ms（5 万）/ 29–57 ms（26.6 万） | 0.08–0.36 秒；WebKit 的一次 Worker 模式达 1.13 秒 |
| 关掉拆分 | 完整 | 完整 | 18–25 ms / 67–106 ms | —（没有懒执行） |

- 默认拆分时，第一批 3,000 个单元格随插入工作表执行，其余先以 `syncOnly` 宣告（`onCommandExecuted` 收不到，17 条），再在空闲时以 `onlyLocal` 执行（不会被检测到）。
- 平台在"释放编辑权、交出编辑权、标签页转入后台"时会立即上传（00 号计划书 §7.2）。如果用户复制大表后马上切走，上传的快照里复制品只有 3,000 个单元格，其余部分之后也不会再触发检测。
- 在 1 秒静默窗口内，懒执行通常已经完成；但 WebKit 有一次拖到 1.13 秒，那次靠复制品里公式结果的写回延长了静默窗口才赶上。没有公式的大表就没有这层保护。
- 关掉拆分后，复制完全同步执行，多花 8–50 ms 的主线程时间，立即捕获也是完整的。Worker 模式下复制品的公式结果与原表一致（两种配置都是）。

### 2.3 发现

1. **1.0.0 打开文档不会触发自动行高**。自动行高改成了"命令内同步计算 + 大范围时交给空闲任务"（`packages/sheets-ui/src/controllers/auto-height.controller.ts`、`services/auto-height.service.ts:124-189`）：命令能算的行高作为命令的 mutation 同步产生；超过 `maxAutoHeightCount`（默认 1,000 行）的部分，由一个 `onlyLocal` 的 `MarkDirtyRowAutoHeightOperation` 交给空闲回调，算完执行的 `SetWorksheetRowAutoHeightMutation` 不带 `onlyLocal`。所以 00 号计划书 §7.3（依据 rc.0）的"必须排除自动行高"已经不需要，而且会造成漏存（§2.2）。
2. **排除名单只需两条**，都是类型声明错误的"只改界面"的命令（§2.1）。DEF-002 的刷新路径也会执行其中的 `sheet.operation.clear-drawing-transformer`（`sheet-drawing-transform-affected.controller.ts:336`），不排除的话，自动行高牵动图片时会多一次检测。
3. **大表复制的拆分会让"立即捕获"不完整**（§2.2），关掉拆分即可。
4. **观察者效应不产生 mutation**：P2 发现的 `getDataValidations()` 等读取方法只改模型、不执行 mutation，不会被检测到；它们对下一次保存字节的影响属于空值等价（内容比较已归一化）。平台的编辑器适配层不应在捕获前调用这类读取方法（P2 报告 §2.3 第 5 条）。
5. **删除大表会清空整个撤销栈，且"大表"按行数判断**：删除工作表时，`util.countCells(worksheet.getCellMatrix())` 用 `ObjectMatrix.forEach` 计数，而它遍历的是**行**（`packages/sheets/src/commands/commands/util.ts:111-117`、`remove-sheet.command.ts:62-104`）；复制时用的是文件内按单元格计数的同名函数（`copy-worksheet.command.ts:56`）。实测：删除 5,001 行（5 万单元格）的表，撤销记录照常压栈；删除约 13,300 行的表，撤销栈被清空（1→0）。这不影响数据，但用户会失去全部撤销历史。关掉拆分（阈值设为最大）后，删除也不再清空撤销栈。建议向上游报告计数不一致的问题。
6. **视图状态**：表格缩放由渲染控制器直接写进 `zoomRatio`；文字文档缩放由 operation 写进 `settings.zoomRatio`（`packages/core/src/docs/data-model/document-data-model.ts:301-307`）。两者都不产生 mutation，随下一次真实修改保存（00 号计划书 §7.3 已接受），内容比较时去掉。

### 2.4 对设计的影响

- **00 号计划书 §7.3**：
  - 用 §2.1 的规则替换现有描述；删掉"行高自适应要单独排除"一条；
  - 排除名单随 SDK 版本维护，纳入回归（`e2e/v06-open-quiet.spec.ts`、`e2e/v06-actions.spec.ts`）；
  - 补充"大表操作关掉拆分"与"删除大表清空撤销栈"。
- **00 号计划书 §7.2**：捕获时机按 V07 的规则（§3.4），静默窗口按"活动"计算。
- **插件档案 v1**：表格核心组的 `UniverSheetsPlugin` 增加 `largeSheetOperation` 配置；档案增加"变更检测排除名单"一项。
- **M4**：平台的变更检测按 §2.1 实现；"内容哈希相同则跳过"时，哈希按内容比较的口径计算（资源按名称排序，§1）。

## 3. V07 公式一致性

### 3.1 结论：通过

条件是捕获时机采用 §3.4 的规则。只用等待接口时，Worker 模式下不一致（§3.3），规则已经把它覆盖。

### 3.2 证据

- 命令：`npx playwright test e2e/v07-formula.spec.ts`（5 个场景 × 2 种模式 × 3 个浏览器，全部通过）
- 结果：`e2e/results/v07/`；汇总：`node scripts/p3-summary.ts v07`
- **判定**有两层：一是按公式定义，从快照中的输入独立推算公式结果（不依赖 SDK）；二是用 `calc=forced`（`initialFormulaComputing = FORCED`）打开同一份快照，让 SDK 重算全部公式。

**每个场景依次做**：修改输入后立即捕获（不等待）→ 只用等待接口后捕获 → 按建议时机捕获 → 再修改一次，用 50 ms 的超时强制走超时后捕获 → 只用等待接口补捕获 → 按建议时机补捕获 → 把按建议时机捕获的快照重开（默认模式、强制重算）。

| 场景 | 模式 | 不等待 | 只用等待接口 | **按建议时机** | 超时后立即捕获 | 只用等待接口补捕获 | **按建议时机补捕获** | 重开 | 强制重算 |
|---|---|---|---|---|---|---|---|---|---|
| 依赖链 200 层 | 主线程 | 199/199 | 0 | **0** | 0 | 0 | **0** | 0 | 0 |
| | Worker | 199/199 | 0 | **0** | 0 | 0 | **0** | 0 | 0 |
| 2 万行聚合 | 主线程 | 4/4 | 0 | **0** | 0 | 0 | **0** | 0 | 0 |
| | Worker | 4/4 | 0 | **0** | 3/4 | 0 | **0** | 0 | 0 |
| 跨表引用 | 主线程 | 2/3 | 0 | **0** | 0 | 0 | **0** | 0 | 0 |
| | Worker | 2/3 | **1/3** | **0** | 2/3 | **1/3** | **0** | 0 | 0 |
| 200 个 `SUMPRODUCT` | 主线程 | 200/200 | 0 | **0** | 0 | 0 | **0** | 0 | 0 |
| | Worker | 200/200 | **200/200** | **0** | 200/200 | **200/200** | **0** | 0 | 0 |

**等待的耗时**：

- 没有计算时，等待接口也要约 500 ms 才返回（三个浏览器 500–513 ms）。
- 修改会牵动 200 个 `SUMPRODUCT` 时（"2 万行聚合""跨表""SUMPRODUCT"三个场景都改同一个输入）：
  - 主线程模式：计算在修改之后的下一个任务里同步执行，主线程被完整阻塞 2.10–2.16 秒（Chromium、Chrome）/ 0.87 秒（WebKit）；这段时间连验证脚本也无法运行，所以之后调用的等待接口只用了约 0.5 秒的起始等待就返回；
  - Worker 模式：等待接口在 2.23–2.28 秒（Chromium、Chrome）/ 0.84–0.86 秒（WebKit）后返回，期间主线程不被阻塞。
- 50 ms 超时：Worker 模式下按时超时；主线程模式下，超时的计时器要等同步计算结束才能触发，而结果先写回，所以"超时"在主线程模式下形同虚设（上表"超时后立即捕获"一列在主线程模式下全部一致，就是这个原因）。

### 3.3 发现

1. **修改后不等待就捕获，公式值是旧的**：依赖链 199/199、`SUMPRODUCT` 200/200。计算不在修改的同一时刻完成，捕获前必须等待（00 号计划书 §7.3 的原则成立）。
2. **Worker 模式下，等待接口在第一张表的结果写回后就返回（SDK 缺陷）**：
   - Worker 模式下，主线程的 `UniverSheetsPlugin` 设了 `notExecuteFormula`，不注册结果写回控制器（`packages/sheets/src/plugin.ts:140-142`）。结果由 Worker 按**每张工作表一条** `SetRangeValuesMutation` 同步到主线程；
   - 主线程的公式会话收到第一条带 `applyFormulaCalculationResult` 的写回，就把会话标为"结果已写回"（`packages/sheets-formula/src/controllers/sheet-formula-calculation-result-apply.controller.ts`），等待接口随即返回，其余工作表的结果还在路上；
   - 实测时间线：结果 mutation 与等待返回都在 2,529 ms，此时"慢"表的值还是旧的；4 ms 后的下一条通知到达时，新值才出现（`e2e/results/v07/` 之外的探针实验，脚本见 §8）；
   - 主线程模式下，全部工作表在同一次同步执行中写回，等待返回时已经完整，所以一致。
3. **重数组公式会在主线程模式下冻结界面**：200 个 `SUMPRODUCT` 数组运算的重算让主线程一次性阻塞 2.1–2.2 秒（Chromium、Chrome）/ 0.87 秒（WebKit），期间页面没有任何响应（探针实验中，这段时间内每 250 ms 一次的采样一次都没有发生）。常见公式则是分片计算的，不会冻结（V10，§6.3）。Worker 模式下两种情况界面都始终可用。是否启用公式 Worker，见 §6.3。
4. **易变函数**：打开时会被重算（§2.2）；修改无关单元格后也会重算；空闲 5 秒内没有持续触发计算（0 次），不会造成持续的写回或检测。

### 3.4 捕获时机（建议写入 00 号计划书 §7.2、§7.3）

1. 用户修改被检测到之后，进入"待捕获"。公式结果写回本身**不**进入待捕获，否则打开含易变函数的文档就会被当成有修改。
2. 待捕获时，先等 `onCalculationResultApplied(timeout)`，再等"活动"静默 1 秒后捕获。活动包括：检测到的修改，以及带 `applyFormulaCalculationResult` 选项的 mutation（公式结果写回）。
   - 这 1 秒就是 00 号计划书 §7.2 的"修改停止 1 秒后捕获"，不额外增加延迟；
   - Worker 送来的各表结果几乎同时到达，1 秒的窗口能把它们全部收进来（三个浏览器实测）。
3. 等待超时：照常捕获，标记"公式待更新"；计算结束、活动再次静默后补捕获。
4. 起始参数：从修改停止到捕获，至少包含 1 秒静默与约 0.5 秒的起始等待（没有计算时），超过"修改停止 1 秒后捕获"的直觉值；§12.2 的"从修改停止到已保存在本机 p95 ≤ 2 秒"要把这 0.5 秒算进去（V08 的端到端数据）。

### 3.5 对设计的影响

- **00 号计划书 §7.2、§7.3**：写入 §3.4 的规则；删掉"捕获前必须等待 `onCalculationResultApplied`"中"只等它就够"的含义。
- **补丁候选与上游报告**：Worker 模式下的会话在收到全部工作表的写回之后才标记完成。平台规则已规避，M4 实现管道时仍应向上游报告。
- **M4**：启用公式 Worker（§6.3 的建议与条件）。

### 4.3 发现

1. **1 MiB 的捕获很便宜**：同步段约 20–25 ms，异步段的阻塞约 20–30 ms，哈希不到 1 ms。§7.2 的"修改停止 1 秒后捕获，持续编辑时最长每 3 秒捕获一次"对主线程的占用约为 1–2%。
2. **5 MiB 时 gzip 成了最大的一块阻塞**：`CompressionStream` 在主线程上以一个 60–95 ms 的任务完成大部分工作。建议 M4 把压缩放进 Worker（例如公式 Worker 或专用 Worker）；同步段（`save()` 与序列化）约 65–79 ms，无法移出主线程。
3. **压缩率高于估算**：表格压缩后约为原来的 25–26%，文字文档约 43–47%（汉字的熵更高）。00 号计划书 §12.3 按 10%–20% 估算的 WAL 写入量要上调：20 人持续编辑 1 MiB 的表格、每 15 秒上传一次，约为每小时 1.2 GiB。
4. **打开自检**（加载后立即捕获一次并比较资源，P2 报告 §3.3）：1 MiB 约 7–14 ms，5 MiB 约 37 ms，可以直接纳入打开流程。
5. **端到端的主要部分是等待**：约 1 秒的静默窗口是设计值；约 0.5 秒的起始等待来自等待接口本身（§3.2）。§12.2 的"从修改停止到已保存在本机 p95 ≤ 2 秒"扣掉 1.57 秒后，留给本机写入与加密的只有约 0.4 秒。M4 可以改为"只在有计算进行时才等待"，省下这 0.5 秒；这要读公式会话的状态（内部 API）。

### 4.4 对设计的影响

- **00 号计划书 §12.2**：确认"1 MiB 捕获的主线程阻塞 p95 ≤ 100 ms"（实测约 25–31 ms）；补充 5 MiB 的数据与"压缩放进 Worker"的建议。
- **00 号计划书 §12.3**：压缩率改为实测值（表格约 25%，文字文档约 45%），重算 WAL 预算。
- **00 号计划书 §7.2**：起始参数表补充"从修改停止到捕获约 1.5 秒（含起始等待）"，以及"只在有计算进行时等待"的优化。
- **P6**：本机写入与加密的预算，按"总计 2 秒减去 1.57 秒"评估。

   - 即使补上 `protect()`，筛选、排序、增删复制隐藏工作表、合并、超链接、备注这 9 个入口也没被拦住（00 号计划书 §6.5 只提到了增删工作表）。
   - 文字文档的 `setReadOnly()` 在当前配置下只设置本地权限点：`ObjectPermissionService.supports()` 要求配置 `objectPermissionTypes` 包含文档类型（`packages/core/src/services/permission/object-permission.service.ts:188-191`），平台没有配置它，所以没有写入 `DOC_OBJECT_PERMISSION_PLUGIN`（实测为空）。
2. **只靠权限点拦不全**：权限检查没有覆盖上面 9 个入口，防火墙兜住了它们。防火墙取消的是 mutation，命令会失败，但实测没有产生未捕获的异常或控制台错误。
3. **真实用户身份会锁死编辑**：本地授权服务按用户 id 的前缀判断角色，只有 `Owner_`、`Editor_` 前缀才允许编辑（`packages/core/src/services/authz-io/authz-io-local.service.ts:81-87、159、175`）。设置真实用户 id 后，没有任何保护规则的单元格也改不了（两种样本、三个浏览器一致；对照组在默认身份下能改）。平台要么不把真实用户交给 SDK，要么在编辑器适配层用自己的 `IAuthzIoService` 实现（全部允许；写入边界在服务端）。
4. **P2 交接的问题**：`setReadOnly` 是否写入保护类资源——表格会（经由必需的 `protect()`），文字文档不会；工作表背景图片的入口——隐藏（本期目标能力之外）。

### 5.4 对设计的影响

- **00 号计划书 §6.5**：用下面的做法替换"逐个工作表设置 `readOnly`"：
  - 本地权限点：表格 `setEditable(false)` 加上关掉工作表的编辑类权限点；文字文档关掉文档的编辑权限点（内部 API，在编辑器适配层集中封装并登记）；
  - mutation 防火墙：`BeforeCommandExecute` 取消所有不带 `onlyLocal` 的 mutation；
  - 拦截撤销重做，清空撤销栈；
  - 阅读模式的界面：关掉工具栏、右键菜单与底栏菜单，隐藏新增工作表按钮；保护相关与不支持功能的菜单在两种模式下都隐藏（插件档案 v1 §5）；
  - 进入编辑：本地修订号落后，或阅读模式下检测到过本地改动（有防火墙时不应出现），就销毁重建；否则可以原地切换。
- **00 号计划书 §6.5 / §11.1**：写明"不把真实用户身份交给 SDK 的本地授权服务"，或者替换 `IAuthzIoService`。
- **插件档案 v1**：补充界面配置（§5）。

### 6.3 发现与建议

1. **首屏与编辑响应都在可接受的范围**：5 万单元格、1,000 公式的表格在 0.52–0.56 秒内渲染出来（p95 不超过 0.72 秒）；按键到下一帧 p50 约 22–26 ms，p95 约 31–37 ms，也就是 1–2 帧。
2. **公式写回需要约 0.7–0.9 秒**，两种模式差别不大。这段时间会计入捕获前的等待（§3.4）。
3. **主线程模式是否冻结界面，取决于公式类型**：
   - 性能样本里的常见公式，计算期间最长阻塞 p95 只有 17–26 ms（增量）、38–51 ms（全量）——SDK 在主线程上分片计算；
   - 但 V07 的 200 个 `SUMPRODUCT` 数组运算会让主线程一次性阻塞 2.1 秒（Chromium、Chrome）/ 0.87 秒（WebKit）；
   - Worker 模式下，两种情况的最长阻塞都在 16 ms 以内。
4. **建议启用公式 Worker**（插件档案 v1 的待定项）：
   - 理由：界面不会被重公式冻结；首屏、编辑响应、计算耗时与主线程模式相当；JS 堆还少 4–5 MiB（计算放到了 Worker 里）；
   - 条件：捕获时机按 §3.4 的规则（否则会捕获到部分旧值）；CSP 已允许同源 Worker（P1）；向上游报告等待接口的缺陷；
   - 代价：多一个 Worker 线程；首屏 p95 在 Chromium 上高约 0.15 秒（Worker 启动）。
   - 最终在 M0 结束定稿插件档案时确认。
