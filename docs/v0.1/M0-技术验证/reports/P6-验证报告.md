**影响设计的发现**：

- **写入管道的放置**：gzip 是整条管道里最大的一段（1 MiB 表格约 28 ms，5 MiB 约 90 ms），在主线程上会形成一个长任务。
  - 放进 Worker 后，异步段的最长阻塞约 6 ms，主线程只剩 `save()`、序列化与编码（1 MiB 表格约 23 ms，5 MiB 约 71 ms）；
  - 加密（AES-GCM）不到 1 ms，写入 IndexedDB 不到 3 ms，`durability: 'strict'` 在 macOS 上没有可测的额外开销；
  - 建议 M4 把压缩、加密与写入都放进 Worker（§2.3 第 1 条）。
- **写入栅栏**：只靠 Web Locks 不够。锁被抢走时，原标签页可能已经在等待一次捕获，或者 Worker 里还有一次写入在途。拿到锁后要把"持有者令牌"写进本机，之后每次写入、删除都在同一个事务里核对令牌（§2.3 第 6 条）。
- **捕获的 3 秒上限与公式**：持续编辑时"最长 3 秒捕获一次"会截断公式等待，这时的快照带着没算完的公式结果。记录要标上"公式待更新"，公式收齐后补捕获；恢复带标记的快照时要强制全量重算（§2.3 第 9 条）。
- **丢失窗口与 §7.8 一致**：
  - 停顿后：约 1 秒写入本机（公式计算慢的文档延长到公式收齐，受 3 秒上限约束）；
  - 持续编辑：丢失 0 到约 2 秒，上限约为 3 秒加轮询与两次管道。
- **一份文档一条记录，靠事务保证原子性**：覆盖写入同一个键，写入中被杀时，重启后要么是旧记录、要么是新记录，不需要"先写新、再删旧"。
- **持久化存储申请不可靠**：无头浏览器的 `persist()` 都返回 false，真实浏览器的授予条件各不相同（DEF-009）。产品要显示存储状态，并处理写满（`QuotaExceededError`）。
- **加密绑定明文元数据**：AAD 覆盖全部参与恢复决策的明文元数据，改动任何一项都会让解密失败；吊销与篡改按密钥版本区分。把同一文档的旧记录整条写回（本机回滚）防不住，作为已接受的风险。
- **V15 的根本难点**：部分 mutation 在处理器里随机生成 id，重放时生成不同的值。要么在记录时补全参数（协同层就是这么做的），要么放弃确定性重放。

**环境**：
- macOS 26.5.1、Apple M4 Pro；Node 24.3.0；
- Playwright 1.63.0（无头），自带的 Chromium 153、本机 Google Chrome 153、Playwright 自带的 WebKit 26.6。

**验证范围**：
- **原型**：发件箱、恢复、锁都是验证工程里的最小原型（`src/harness/outbox/`），目的是测出成本与行为，生产实现由 M4 按正式流程设计。
- **进程被杀**：用持久化的浏览器上下文，以 SIGKILL 杀掉这个浏览器实例：带用户目录的进程与它的整棵子进程树。WebKit 的网络进程（承载 IndexedDB）、渲染进程与 GPU 进程是 launchd 拉起的 XPC 服务，不在进程树里，要另外把启动之后出现的这些进程一并杀掉；只有一个 WebKit 实例在跑时才这样做。Playwright 不能模拟断电与系统崩溃；这种情况下的持久性，只按 `durability` 选项与浏览器文档说明（§2.3 第 4 条，DEF-009）。
- **配额**：无头浏览器的配额与持久化申请，和真实浏览器不同；写满的行为用 CDP 把配额设小来验证，只有 Chromium 内核能做（配额覆盖要在本站第一次写入之前设置）。
- **服务端**：验证服务只模拟修订号与密钥下发；租约、幂等与上传不在本 Phase，"自己追自己"的判断（§7.5）没有验证。

### 1.2 原型方案（M4 的实现要求）

1. **管道**：`save()` 与序列化在主线程（SDK 的模型只在主线程上），编码后把字节转移给 Worker；Worker 里做去重哈希、gzip、加密与写入。捕获串行执行，序号在 `save()` 的同步段里分配，同一份文档的写入排队。
2. **记录**：每个用户的每份文档一条记录，覆盖写入，由 IndexedDB 事务保证原子性；写入用 `durability: 'strict'`（在 macOS 上没有可测的开销，但不等于已经完整落盘，DEF-009）。
3. **加密**：
   - AES-GCM-256，密钥只在内存里（不可导出的 `CryptoKey`，可以传给 Worker），每条记录一个随机 IV；
   - AAD 覆盖全部参与恢复决策的明文元数据；
   - 恢复时重新向服务端取密钥，按密钥版本区分"已吊销"与"被篡改"；
   - 本机回滚（把同一文档的旧记录整条写回）防不住，作为已接受的风险；键里的文档 id 是明文，需要时改用按用户密钥计算的 HMAC。
4. **标签页协调**：
   - 每份文档一把排他锁（`nerve-doc:<文档 id>`）；拿到锁后登记为持有者（令牌 + 代次），写入、删除都在同一事务里核对令牌（写入栅栏）；
   - 拿不到锁的标签页只读、不写发件箱、排队等锁；接手时服务端修订号比打开时新，先从服务端重新加载；
   - 拿到锁之后才检查未同步记录，待恢复决定期间只读；
   - 锁被抢走时立即停止自动保存，转为只读，不再处理上传确认的删除；
   - 同一浏览器内正常交出时，旧标签页先同步再释放锁；没有响应时新标签页用 `steal` 接手，从发件箱恢复。
5. **捕获时机**（统一 P3 §3.4 与 P5 的规则）：修改停止 1 秒后捕获；从第一处未保存的修改算起最长 3 秒捕获一次，这个上限同时约束公式收齐与组合输入的等待；超过上限时照常捕获并标记"公式待更新"，公式收齐后补捕获；恢复带标记的快照时强制全量重算，算完再捕获。
6. **恢复**：修订号与记录的基准相同才能一键恢复。原型不上传，所以修订号不同一律按冲突处理；生产上要按 §7.5 先用原来的 `requestId` 幂等重试，修订号由本机早先的请求产生时不算冲突（本 Phase 未验证）。解密失败或密钥已吊销的记录作废。
7. **错误**：写满时保留已有记录并提示"容量不足"；Worker 出错时捕获失败并重试；数据库结构升级时旧连接主动关闭。

## 2. V14 本地优先所需的浏览器能力与成本

### 2.1 结论：通过

- **写入管道**：1 MiB 表格合计约 50 ms，5 MiB 约 165 ms；其中加密与写入合计不到 4 ms。放进 Worker 后，5 MiB 的主线程阻塞只剩同步段（p95 约 73 ms）。【待补：三个浏览器】
- **端到端**（最后一次修改 → 已保存在本机）：
  - 不牵动公式的修改：p50 为 1.01–1.08 秒，最大 1.18 秒；
  - 牵动约 320 个公式的修改：【待补】；
  - 00 号计划书 §12.2 的"p95 ≤ 2 秒"在这些条件下成立；P3 的样本条件（公式计算不超过约 0.9 秒）仍然适用，公式计算更慢的文档达不到。
- **恢复路径**：5 MiB 表格读取、解密、解压、解析合计约 26–43 ms。
- **进程被杀**：恢复到最后一次写入本机的内容；之后没来得及保存的修改丢失；持续编辑时丢失 0 到约 2 秒（上限约 3 秒）。写入过程中被杀、提交附近被杀，重启后都是完整的旧记录或新记录。
- **标签页协调**：持有者关闭、崩溃、导航离开之后，等锁的标签页十几毫秒内接手，并发现未同步的记录；锁被抢走的标签页停止写入，绕过锁检查的写入被栅栏拒绝；等锁时只读，接手时对齐服务端。
- **配额**：写满时报 `QuotaExceededError`，失败的写入不留下记录，覆盖已有记录失败时原记录不变，之前的记录仍能解密，自动保存报告错误。
- **安全**：修订号已变时不自动恢复；改动明文元数据后解密失败；密钥吊销后按版本判为已吊销；不同用户的记录互不可见。

### 2.3 发现

1. **gzip 是主要成本，适合放进 Worker**：
   - 主线程放置时，5 MiB 表格的 gzip 期间有一个约 88 ms 的长任务，与 P3（V08）一致；
   - Worker 放置时，主线程在异步段的最长阻塞约 6 ms（这是探针能测到的下限）；来回一次（转移字节、Worker 里的全部工作）约等于 Worker 里各段耗时之和，没有明显的额外开销；
   - 主线程仍要承担 `save()`、序列化与编码。5 MiB 时 p95 约 73 ms，接近 100 ms，是单快照上限（5 MiB）下的主线程成本下限。
2. **加密与写入的开销可以忽略**：
   - AES-GCM 加密 1.2 MiB 的 gzip 结果约 0.3–0.8 ms；
   - IndexedDB 写入 1.2 MiB 约 1–3 ms；
   - 去重用的 SHA-256（对编码后的 JSON）5 MiB 约 2 ms。
3. **丢失窗口**（丢失窗口 = 第一处丢失的修改到杀进程，没有丢失为 0）：
   - 停顿后：修改停止约 1 秒（防抖）加一次管道，就已保存在本机；
   - 持续编辑：每 200 ms 改一处，分别编辑 3.2、4.6、6.1 秒后杀进程，恢复出的修改都是连续的前缀，丢失窗口约 0.2、1.7、0 秒【待补：三个浏览器】。丢失多少取决于被杀时离上一次捕获多远，上限约为 3 秒加 50 ms 的轮询与最多两次管道。
4. **持久性的边界**：
   - 进程被杀（SIGKILL）不会丢失已提交的事务，默认持久性也是如此；
   - 断电与系统崩溃时，默认（relaxed）持久性可能丢失最近提交的事务，`strict` 要求落盘后才算完成。`strict` 在 macOS 上没有可测的开销，也可能意味着没有做完整的落盘，不能默认它等于已落盘；Playwright 无法验证断电，与真实浏览器的配额、持久化申请一起登记为 DEF-009（M4）。
5. **写入中被杀**：
   - 压缩、加密阶段：在 5 MiB 表格写入的不同时刻杀进程 7 次，杀得早是旧记录，晚一些是新记录；
   - 提交附近：写入 IndexedDB 之前页面发出信号，测试端收到就杀，8 次都是新记录——从发出信号到杀掉进程之间，1–3 ms 的提交已经完成；
   - 两种情况下重启后的记录都能解密、解压、解析。这条结论依据的是 IndexedDB 事务的原子性（覆盖同一个键的事务要么整体提交、要么整体回滚），实验只是没有观察到反例。
6. **Web Locks 与写入栅栏**：
   - 锁在页面关闭、渲染进程崩溃、导航离开时都会立即释放；`ifAvailable` 让第二个标签页立即知道"另一个标签页正在编辑"，排队的请求在释放后十几毫秒内拿到锁；
   - `steal` 让持有者的请求以 AbortError 结束，平台据此停止写入、转为只读；
   - 审查发现：只靠锁不够。原标签页在被抢锁时如果正在等待一次捕获，等待结束后仍会写入，并显示"已保存在本机"，而新持有者看到的已是旧记录。加上写入栅栏后，被抢锁的标签页不再写入，绕过锁检查的写入以 `FenceError` 失败，两种放置方式都是如此。
7. **配额**：
   - 无头浏览器的配额估算：Chromium 约 10 GiB，Chrome 约 9 GiB，WebKit 1 GiB；`persist()` 都返回 false（无头浏览器不授予）；
   - 写满时失败的是这一次写入的整个事务，之前的记录不受影响；覆盖已有记录时配额不足，原记录不变；
   - 自动保存遇到配额不足时报告 `QuotaExceededError`，不删除已有记录。
8. **恢复要重新取密钥**：密钥只在内存里，进程被杀后要重新向服务端取，所以离线时打开文档没法解密本机记录。这与"不承诺离线冷启动"（§7.8）一致，恢复在联网之后进行。
9. **公式没收齐时的捕获**：
   - 在公式 Worker 模式下持续修改慢计算的输入（V07 的 formula-scenarios，每轮约 2 秒），3 秒上限到了公式还没收齐；
   - 审查发现：这时的快照带着旧的公式结果，恢复后按默认计算模式打开，已有的缓存值不会重算，恢复出的公式结果是错的；
   - 修复后：记录标上"公式待更新"（也绑定在 AAD 里）；公式收齐后补捕获；恢复带标记的快照时强制全量重算，再补捕获。恢复后 201 个公式与输入一致，最后的记录不再带标记【待补：三个浏览器】。
10. **并发捕获**：两次捕获同时在途时，原型曾把同一个序号分给两份内容。改为捕获串行、序号在 `save()` 的同步段里分配后，后捕获的序号更大、内容也是后写入的。

## 3. V15 mutation 增量日志是否可行

### 3.1 结论：可行；建议 v0.1 不纳入

- **能序列化**：参数都能结构化克隆（执行之后立即克隆），日志写进 IndexedDB 再读出来重放，全部成功。
- **能确定性重放，但要补全参数**：
  - 不补全时，表格的样式 id 在处理器里随机生成：内容相同、id 不同；批注 id 与复制工作表的样式引用则不一致（悬空的样式引用会让复制出的工作表丢样式）；
  - 补全之后（样式附带记录、批注 id 回填），表格 12 个场景重放后规范化内容逐字节一致；
  - 文字文档 7 个场景不补全就逐字节一致（处理器把执行中分配的段落 id 写回了参数）。
- **能与快照组合恢复**：快照记下所含的最后一条日志序号，恢复时重放更大的序号；进程被杀后恢复到被杀前的内容。
- **是否纳入**：见 §3.4。建议 v0.1 不纳入，由 M0 结束评审决定。

### 3.2 证据

- 命令：`npx playwright test e2e/v15-mutation-log.spec.ts`
- 结果：`e2e/results/v15/`；汇总：`node scripts/p6-summary.ts replay combined`
- 做法：
  - 记录：协同钩子 `onMutationExecutedForCollab`，排除 `onlyLocal`、`fromCollab`、`fromSync`、界面伪 mutation 与其他单元；执行后同步做结构化克隆；序号在执行前的监听器里取；每 100 ms 或满 50 条批量写入 IndexedDB；
  - 重放：从保存过一次的 S0 开始，按序号在顶层逐条 `syncExecuteCommand(id, params, { fromCollab: true })`；
  - 比较：规范化内容；表格另比"样式按 id 展开"之后的内容，并找出悬空的样式引用。
- 静态排查：独立的审查代理（与主会话同为 Claude Opus）读了档案所用 23 个包里的 79 个文件、约 115 处 MUTATION 声明，逐个核对处理器与它同步调用的模型或服务；所有随机与时间来源都反查了调用链，结论见 §3.3 第 3 条。P6 的独立审查抽查成立，并在公式 Worker 模式下补跑了 sheet-core 的重放（48 条，逐字节一致）。

【待补：三个浏览器最终一轮的汇总表】

### 3.3 发现

1. **大多数场景可以确定性重放**：表格的数值与公式、样式、数字格式、条件格式、数据验证、筛选、超链接、浮动与单元格图片、插入删除行列（带图片）、自动行高、粘贴、撤销重做，文字文档的键入、中文输入（组合中的 `noHistory` mutation）、格式、列表与表格、图片、粘贴、撤销重做，重放后内容一致。
2. **样式 id 不确定**：样式 id 在处理器里随机生成，所以重放后样式按 id 比较不一致，按内容展开后一致；这对大多数操作没有影响。
3. **需要补全的 mutation**（静态排查，已用补全后的重放验证）：
   - **样式**：`Styles.add` 随机生成样式 id（`core/src/sheets/styles.ts`）。会走到它的有 `sheet.mutation.set-range-values`、`sheet.mutation.set.numfmt`、`sheet.mutation.remove.numfmt` 三类。补全办法是"样式附带记录"：
     - 记录每条日志时，附上"自上一条日志以来样式表新增的 id 及内容"。按增量算，是因为公式结果写回（`onlyLocal`，不进日志）也会新增样式；
     - 重放这一条之前，先把附带的样式按原 id 装进样式表。处理器按内容查找时就会命中同一个 id，不再生成新的；
     - 复制工作表（`sheet.mutation.insert-sheet`）、撤销删除工作表、移动区域的撤销数据、行列与默认样式，都按字符串引用样式 id；有了样式附带记录，这些不用逐个补全；
     - 不宜把引用到的样式直接塞进 `insert-sheet` 的 `styles` 参数：基底快照里有内容重复的样式时，会改变之后按内容查到的 id。
   - **批注**：`sheet.mutation.update-note` 在参数里没有 id 时，由 `SheetsNoteModel.updateNote` 随机生成。记录时从模型读回 id，写进日志里的参数。界面路径已经在命令里生成 id，是 Facade 的 `createOrUpdateNote` 等不带 id 的调用会触发。
   - **补不了的一类**：`sheet.mutation.set-worksheet-range-theme-style` 的键在模型里随机生成，而且每次加载都会重新生成。本档案不注册它的界面，插件档案要求这个资源为空（§3），不影响。
   - **文字文档不需要补全**：段落与分节的 id 虽然在执行中分配，但处理器把它们写回了参数（`params.actions`），执行之后克隆的日志是完整的。理论上还有两条不写回的路径（重复段落 id 的"保留 id"插入、缺 `sectionId` 的分节替换），开源命令里没有找到能触发的操作，要用随机编辑加撤销重做的重放测试兜底。
4. **组合恢复**：快照记录"所含的最后一条日志序号"（与 `save()` 在同一个同步段里读取），恢复时重放更大的序号。进程被杀后，表格与文字文档都恢复到了被杀前的内容；只用快照时，快照之后的修改丢失。
   - 这依赖一个隐含前提：mutation 执行与协同钩子之间不会插入捕获；
   - 用例在杀进程前手动写入了日志，"约 0.1 秒"的丢失窗口是按批量间隔推算的，不是实测；
   - 重放的 mutation 不会被变更检测计入，恢复后要主动捕获一次。
5. **成本**：每个场景的克隆耗时合计不到 1 ms，日志体积为几 KiB 到十几 KiB；批量写入 IndexedDB 的开销与发件箱写入同一量级。样式附带记录每条都要遍历整张样式表，这部分耗时不在克隆耗时里，纳入时要优化。
6. **不进日志、重放时重新产生的值**：
   - 公式结果写回属于 `onlyLocal`，重放时重新计算；
   - 易变函数（NOW、TODAY、RAND）的值会不同；
   - `HYPERLINK()` 每次重算都会生成新的区间 id。
   - 所以比较时要对这些单元格归一化，恢复出来的易变公式本来就应当重算。
7. **其他隐患**：
   - 移动区域的 mutation 不看参数里的 `unitId`，作用于当前活动的工作簿，重放时必须先激活目标工作簿；
   - 行高、列宽、显隐变化后，图片变换在微任务里直接写进模型，不走 mutation，重放后要等微任务；
   - `FWorkbook.addStyles` 与缩放直接写快照，不走 mutation；
   - 静态排查没有覆盖"监听器同步触发的后续 mutation"，它们在重放时可能执行两次。

### 3.4 纳入与否

- **收益**：丢失窗口从"停顿后约 1 秒、连续输入最多约 3 秒"降到约 0.1 秒（日志的批量间隔，推算）。
- **代价与风险**：
  - 依赖不公开的协同钩子，开源代码里没有使用者（协同插件闭源）；
  - 确定性要靠补全：4 类 mutation（表格），每次升级 SDK 都要重新排查全部 mutation；
  - 恢复时没有"标准答案"可比。重放一旦出错，会悄悄写坏文档；而只用快照时，最坏只丢最后几秒；
  - 日志同样要加密、按用户隔离、随快照截断，发件箱的复杂度与测试面大约翻倍。
- **建议**：快照已经满足 00 号计划书 §7.8 的承诺，v0.1 不纳入，M4 只做快照。登记 DEF-010（v0.2）：纳入时按 §3.3 的补全清单实现，由适配层封装钩子，加上随机编辑、撤销重做的重放测试，升级 SDK 时先跑 V15 回归。
- **决定**：00 号计划书 §7.5 的原意是"验证通过后再纳入"，而本结论建议不纳入，所以提交 M0 结束评审，由你决定。

## 4. V16 在 Node.js 下以无界面方式加载

### 4.1 结论：可行（记录）

- 纯 Node 24（不用 happy-dom），用发布的 ESM 包，加载 fixtures 的 11 个表格样本与 9 个文字文档样本，全部到达 Ready、保存成功、没有错误。
- 与浏览器里"加载再保存"的结果按规范化内容比较：
  - SDK 生成的样本一致，只有表格浮动图片的一处高度不同：浏览器按自动行高重算了图片的变换（与 DEF-002 同一条路径），Node 下没有文字测量，保持原值；
  - 手写样本（`empty`、`minimal`、`p5-cap`）只差加载时随机生成的 `sectionId`。

- 默认计算模式的输出同样与样本一致，所以"迁移要用 `NO_CALCULATION` 才不会改变输出"是按源码推断（加载时的 `WHEN_EMPTY` 会计算空缓存的公式），没有样本证据。

- 结果：`e2e/results/v16/node-load.json`、`browser/`；汇总：`node scripts/p6-summary.ts node`

### 4.3 发现

1. **插件**：只注册有数据的无界面插件（资源 hook 与浏览器一致，表格 11 个资源名、文字文档 5 个），外加 `UniverRenderEnginePlugin`（文字文档的编辑 mutation 与表格图片的刷新要用 `IRenderManagerService`，它不碰 DOM）。不注册任何界面插件。
2. **生命周期只到 Ready**：Rendered、Steady 由界面推进；需要这两个阶段才初始化的控制器（定义名称、数据验证的公式等）在 Node 下不工作，迁移时要逐项确认。
3. **没有文字测量**：自动行高、依赖行高的图片变换在 Node 下不会重算。迁移工具只做"打开再保存"时这是优点（不改内容），需要重排版的迁移不能在 Node 下做。
4. **公式**：迁移用 `NO_CALCULATION`，避免加载时重算改变输出（按源码推断，见 §4.1）。
5. **导入**：Node 的原生 TypeScript 执行要求导入带扩展名，验证工程的 `content-compare.ts` 已改为带扩展名。

## 5. 对设计的影响

- **00 号计划书 §7.2**：
  - 管道确认；压缩、加密与写入放进 Worker，主线程只做 `save()` 与序列化；
  - 捕获时机写成一条规则（§1.2 第 5 条）：修改停止 1 秒后捕获；从第一处未保存的修改算起最长 3 秒，这个上限同时约束公式收齐与组合输入的等待；超过上限照常捕获并标记"公式待更新"，收齐后补捕获。
- **00 号计划书 §7.5**：
  - 每份文档一条记录、覆盖写入，由事务保证原子性；
  - Web Locks 的协调方式确认，并加写入栅栏；拿不到锁与待恢复决定时只读；接手时对齐服务端；
  - 同一浏览器内的交接写清两种情形：正常交出时旧标签页先同步再释放锁；没有响应时新标签页 `steal` 接手，从发件箱恢复；
  - 恢复需要联网取密钥（与"不承诺离线冷启动"一致）；带"公式待更新"的快照恢复时强制全量重算。
- **00 号计划书 §7.6**：
  - AES-GCM-256，AAD 覆盖全部参与恢复决策的明文元数据；本机回滚作为已接受的风险；
  - `persist()` 不可靠，要显示存储状态并处理写满；
  - 写入用 `durability: 'strict'`。
- **00 号计划书 §7.8**：丢失边界的数字确认：停顿后约 1 秒（公式计算慢的文档延长到公式收齐，受 3 秒上限约束）；连续输入最多约 3 秒，再加一次写入（几十毫秒）。
- **00 号计划书 §12.2**："从修改停止到已保存在本机 p95 ≤ 2 秒"在"公式计算不超过约 0.9 秒"的样本条件下成立（P3 §4.4）；同时写明默认配置下的最坏值【待补】。
- **00 号计划书 §7.5 的"可选增强"**：按 §3.4 的结论处理。
- **00 号计划书 §8.7**：Node 下的"打开再保存"迁移可行，前提见 §4.3。
- **M3**：
  - 密钥按用户生成、服务端主密钥加密保存、按会话下发、可吊销；吊销后已打开的标签页要尽快停止写入（与在线会话联动）；
  - 文档修订号与条件写入。
  - 密钥管理放在 M3 还是 M4，在 00 号计划书 r3 里统一。
- **M4**：本机发件箱、恢复、锁与保存状态按 §1.2 实现，包括写入栅栏、公式待更新与恢复时重算、等锁与待恢复时只读、接手时对齐服务端、"自己追自己"的幂等重试。
