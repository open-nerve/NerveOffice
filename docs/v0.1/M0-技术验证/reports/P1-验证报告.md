## 3. V02 严格 CSP 下能否运行

### 3.1 结论：通过

00 号计划书 §11.3 的策略原样可用，不需要任何放宽：

```text
default-src 'self'; img-src 'self' data: blob:; connect-src 'self'; font-src 'self' data:;
style-src 'self' 'unsafe-inline'; script-src 'self'; worker-src 'self' blob:;
frame-ancestors 'none'; base-uri 'self'; form-action 'self'
```

公式 Worker 与文字文档的排版 Worker 都以同源的 ES 模块脚本加载，在该策略下工作正常。**前提是策略随 Worker 脚本的响应一起下发**（§3.4）。

### 3.2 证据

**方法**

- 同一份构建产物由三个服务提供：`full`（所有响应都带策略）、`off`（不带策略）、`html-only`（只有 HTML 带策略）。`full` 同时发送强制策略与只报告的探测策略。
- 违规从三条渠道采集：页面的 `securitypolicyviolation` 事件、服务端的 `report-uri` 报告、浏览器控制台（包括 Worker 作用域的消息）。
- 编辑场景全部用真实的键盘和鼠标操作：
  - 表格：在 B2 输入"hello 你好"，在 B3 输入 `=SUM(1,2)`，用工具栏给 B2 加粗，打开数字格式下拉菜单和右键菜单，最后用 `save()` 核对快照；
  - 文字文档：在正文输入"追加ABC"，全选后用工具栏加粗，打开段落样式下拉菜单，用 `save()` 核对快照；
  - Worker 场景额外记录往来的 RPC 方法与响应类型，证明 Worker 确实参与了计算或排版。

**命令与结果**

- `npx vite build && npx playwright test`（33 个用例，其中 V02 编辑场景 12 个、阳性对照 9 个、V01 网络核验 12 个）
- `node scripts/safari-selftest.ts`（真实 Safari）
- 结果：`e2e/results/v02/<浏览器>-<场景>.json`、`e2e/results/v02/probe/<浏览器>-<模式>.json`、`e2e/results/v02/safari/`

**编辑场景（`full` 模式）**

| 浏览器 | 场景 | 功能核对 | 首次渲染（ms） | 强制违规（三渠道） | 页面错误 | 控制台错误 | Worker 调用 / 成功响应 |
|---|---|---|---|---|---|---|---|
| Chromium 153 | 表格·主线程 | 全部通过 | 425 | 0 | 0 | 0 | — |
| Chromium 153 | 表格·Worker | 全部通过 | 419 | 0 | 0 | 0 | 12 / 12 |
| Chromium 153 | 文字·主线程 | 全部通过 | 364 | 0 | 0 | 0 | — |
| Chromium 153 | 文字·Worker | 全部通过 | 359 | 0 | 0 | 0 | 5 / 5 |
| Chrome 153 | 表格·主线程 | 全部通过 | 427 | 0 | 0 | 0 | — |
| Chrome 153 | 表格·Worker | 全部通过 | 423 | 0 | 0 | 0 | 12 / 12 |
| Chrome 153 | 文字·主线程 | 全部通过 | 368 | 0 | 0 | 0 | — |
| Chrome 153 | 文字·Worker | 全部通过 | 367 | 0 | 0 | 0 | 5 / 5 |
| WebKit 26.6 | 表格·主线程 | 全部通过 | 479 | 0 | 0 | 0 | — |
| WebKit 26.6 | 表格·Worker | 全部通过 | 490 | 0 | 0 | 0 | 12 / 12 |
| WebKit 26.6 | 文字·主线程 | 全部通过 | 394 | 0 | 0 | 0 | — |
| WebKit 26.6 | 文字·Worker | 全部通过 | 390 | 0 | 0 | 0 | 5 / 5 |

- "首次渲染"是从调用 `createEditor` 到生命周期进入 `Rendered` 的时间，**不含脚本下载解析和样本加载**，只是冒烟数据；性能基线在 P3 建立。
- "控制台错误"是浏览器控制台中的错误级消息（含 Worker），不含 CSP 提示（CSP 提示已计入违规）。WebKit 会把探测策略的提示（`[Report Only] Refused…`）以错误级输出，这些属于预期。页面脚本主动调用 `console.error/warn` 的次数同样为 0。
- Worker 的 RPC 往来：
  - 表格：主线程调用 Worker 的 `remote-instance-service.whenReady / createInstance / syncMutation`，Worker 反向调用主线程的 `remote-sync.service.syncMutation` 回传计算结果；
  - 文字：`docs-layout-worker.initialize → getCapabilities → createSession → startLayout ×2`；
  - 两者都没有失败的调用。

**阳性对照**（`e2e/v02-csp-probe.spec.ts`）：在页面与 Worker 中各发起一次跨源 `fetch`、一次 `eval`、一次 `new Function`。

| 模式 | 页面 | Worker | 说明 |
|---|---|---|---|
| `off` | 全部放行 | 全部放行 | 证明探测目标可达、探测动作本身有效 |
| `full` | 全部拦截 | 全部拦截 | 三个浏览器一致：策略在页面与 Worker 中都生效 |
| `html-only` | 全部拦截 | **全部放行** | 三个浏览器一致：只给 HTML 加头时，Worker 完全不受约束 |

**各渠道能看到哪些违规**（`full` 模式）：

| 违规 | Chromium / Chrome | WebKit |
|---|---|---|
| 页面·跨源请求 | 页面事件、服务端报告、控制台 | 页面事件、服务端报告、控制台 |
| 页面·动态代码 | 页面事件、服务端报告 | 页面事件、服务端报告 |
| Worker·跨源请求 | 服务端报告 | 只有控制台 |
| Worker·动态代码 | 服务端报告 | **任何渠道都看不到**（只抛出 EvalError） |

因此，"强制违规为零"在 WebKit 的 Worker 中对动态代码没有运行时证据，由 §2.1 的静态扫描兜底：编辑器产物（含两个 Worker）里没有可执行的动态代码。其余情况都至少有一条渠道覆盖。

**真实 Safari 26.5**（`scripts/safari-selftest.ts`）：Playwright 无法驱动真实 Safari，改为用 `open -g -a Safari` 在后台打开自检链接。页面用 Facade 命令完成同样的编辑（不是键盘输入），再把结果交回服务。

| 步骤 | 结果 |
|---|---|
| 表格·主线程 / 表格·Worker / 文字·主线程 / 文字·Worker | 功能核对全部通过；强制违规为零（页面事件、服务端报告）；页面错误为零；Worker 调用的 RPC 方法与 WebKit 相同、全部成功（调用次数因编辑方式不同而不同） |
| 阳性对照 `full` / `html-only` / `off` | 与 WebKit 完全一致：`full` 下页面与 Worker 全部拦截；`html-only` 下 Worker 全部放行；`off` 下全部放行 |

自检只能采集页面事件与服务端报告，看不到浏览器控制台；而 Safari 与 WebKit 一样，不会通过这两条渠道报告 Worker 内的违规。所以真实 Safari 的"强制违规为零"只覆盖页面作用域，Worker 作用域依靠 Playwright WebKit 的控制台渠道和静态扫描兜底。

### 3.3 探测策略：哪些放宽是必要的

探测策略比强制策略更严：去掉 `style-src` 的 `'unsafe-inline'`、`img-src`/`font-src` 的 `data:`、`img-src`/`worker-src` 的 `blob:`。它只报告、不拦截。以页面事件为准（服务端的 `report-uri` 在 Chromium 中会把相同的报告去重，计数不可用）：

| 放宽项 | 是否必要 | 依据 |
|---|---|---|
| `style-src 'unsafe-inline'` | **必要** | 每次运行 4 次内联 `<style>` 违规，来自 3 次注入：`@univerjs/ui` 的主题变量（`ThemeSwitcherService`，元素 id `univer-theme-css-variables`，`packages/ui/src/services/theme-switcher/theme-switcher.service.ts:21,51-54`）、格式刷光标样式（`packages/ui/src/controllers/format-painter.controller.ts:57`）、`sonner` 通知组件（先插入空的 `<style>` 再追加文本，计 2 次）。三者都不支持 nonce。**替代方案待评估**：这些样式在给定主题下内容固定，理论上可以用哈希白名单代替 `'unsafe-inline'`，代价是升级或换主题时要重新计算，交给 P4 实测 |
| `img-src data:` | **必要** | 表格界面把图标以 `data:` 图片加载：页面事件 84 次（WebKit 按来源分为 83 + 1），三浏览器一致；文字文档场景没有 |
| `font-src data:` | 本 Phase 未触发 | 没有使用 `data:` 字体；是否删除，由 P4 在覆盖图片、粘贴等场景后定稿 |
| `worker-src blob:`、`img-src blob:` | 本 Phase 未触发 | Worker 从同源地址加载；`blob:` 图片要等 P4 的图片场景验证 |

### 3.4 对设计的影响

- **CSP 必须随所有响应下发，至少包括 HTML 与 Worker 脚本。** Worker 内生效的是它自己脚本响应上的策略；常见的"只给 HTML 加头"的反向代理写法会让 Worker 完全失去约束（阳性对照，三浏览器与真实 Safari 一致）。M1 的部署配置要照此编写，E2E 要带上 Worker 作用域的阳性对照。
- **违规上报只能当抽样信号。** Chromium 会把相同的报告去重；WebKit 与 Safari 不上报 Worker 内的违规；`report-to` 尚未验证。生产上的违规上报接口（00 号计划书 §11.3、附录 A）不能被当作"没有违规"的完整证据。这一点交给 P4 定稿，并纳入 M1/M5 上报接口的设计。
- 00 号计划书 §11.3 的起点策略可以直接使用；最终策略由 P4 定稿，重点是 `font-src data:`、`blob:` 能否收紧，以及样式哈希能否代替 `'unsafe-inline'`。
- M1 的构建约束：Worker 必须以同源脚本加载，不能改成内联或 `data:` Worker；构建工具不得注入内联脚本。

### 3.5 未覆盖的部分

- **Microsoft Edge**：本机没有安装，登记为 DEF-001，在 M1 建立 E2E 浏览器矩阵时用 Playwright 的 `msedge` 通道补测。Edge 与 Chrome 同为 Chromium 内核，本项结论可以类推，但仍需实测。
- **真实 Safari 中的键盘输入**：自检用 Facade 命令编辑，没有键盘输入；键盘路径由 Playwright WebKit 覆盖，中文输入法由 P5 验证。
