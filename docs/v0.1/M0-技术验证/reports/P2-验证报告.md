## 2. V03 保存重开保真

### 2.1 结论：有条件通过

- **收敛**：17 个样本 × 3 个浏览器共 51 次。
  - S1 → S2：除 1 处"空值等价"外完全一致，这 1 处在手写样本上；
  - S2 → S3：全部完全一致。
- **保真**：
  - S0 → S1 的实际差异全部与基线一致：手写样本补齐默认字段，以及 DEF-002 的一处图片尺寸变化；其余只有"空值等价"；
  - 语义方面，每个样本在生成时、第一次打开时、重开后都与预期一致。
- **跨浏览器**：三个浏览器对同一样本得到的 S1 内容哈希一致（资源按名称排序后计算）。唯一例外是手写的文字文档样本：SDK 会给缺少的 `sectionId` 生成随机值。
- **Worker 模式**（Chromium）：15 个 SDK 生成的样本在 Worker 模式下的 S1 与非 Worker 模式相同。
- **条件**：DEF-002（§2.3 第 2 条）。

### 2.3 发现

1. **"空值等价"的归一化**。资源数据会在空字符串 `""` 与 `{}` 之间变化，按工作表分组的资源也会删掉取值为空数组的键。两者在内容上都等价。
   - 根因：资源有两条加载路径。
     - 文档单元创建时，走 `ResourceManagerService.loadResources`，遇到空数据会跳过；
     - 插件晚于文档单元注册资源 hook 时，走 `ResourceLoaderService` 的 `loadHookResource`，只要条目存在，就调用 `onLoad`（`packages/core/src/services/resource-loader/resource-loader.service.ts:40-55`）。
   - **即使是 SDK `save()` 的输出，也要再经过一次"重开 → 保存"才逐字节稳定**：9 个表格样本的 S0 与 S1 哈希都不同，差别只是空值等价；S1 之后完全稳定。
   - 影响：
     - 平台新建文档使用的模板快照，要取收敛之后的版本（S1 或之后）；
     - 服务端做"内容哈希相同就不增加修订号"时，要么先做空值归一化，要么接受第一次保存多出一个修订。
2. **浮动图片在所跨行自动变高后，尺寸会被静默改写（SDK 缺陷，本项的条件，DEF-002）**。
   - **根因**（`packages/sheets-drawing/src/controllers/sheet-drawing-transform-affected.controller.ts`）：
     - 自动行高的 mutation 属于 `REFRESH_MUTATIONS`（125–134 行，其中 131、132 行），由 `_sheetRefreshListener`（1393–1431 行）交给 `_refreshDrawingTransform`（1433–1486 行）处理；
     - 对 `Position` 锚点（默认值：随单元格移动、保持尺寸）的图片，刷新时只重算位置、保留原宽高（1466–1479 行）；
     - 刷新只调用内存中的 `refreshTransform`，不产生 mutation（`_finalizePlan` 的 refresh 分支，331–338 行），而且**不回写** `sheetTransform` 与 `axisAlignSheetTransform` 的终点锚点。
     - 对比：手动改行高、插入行走的是显式命令（101–123 行的 `UPDATE_COMMANDS`），会生成更新锚点的 mutation，所以没有问题。
   - **后果**：之后凡是按锚点重算尺寸的时机，图片都会被拉伸。一是切换工作表（`packages/sheets-drawing-ui/src/controllers/sheet-drawing-active-render.controller.ts:41-43、101`），二是渲染初始化，也就是重新打开（`packages/sheets-drawing-ui/src/controllers/render-controllers/sheet-drawing.render-controller.ts` 中按 `sheetTransform` 重算的循环）。拉伸发生后的任何一次保存，都会把新尺寸永久写进快照，属于静默改写内容属性。
   - **实测**（`e2e/v03-drawing-autoheight.spec.ts`，三个浏览器一致）：

     | 触发 | 触发后（界面） | 切换工作表后 | 重开后 | 终点锚点 |
     |---|---|---|---|---|
     | 单元格图片 | 120×80 | 120×99 | 120×99 | 未更新 |
     | 换行文字（固定文本） | 120×80 | 120×186 | 120×186 | 未更新 |
     | 36 号字 | 120×80 | 120×111 | 120×111 | 未更新 |
     | 手动改行高（阴性对照） | 120×80 | 120×80 | 120×80 | 已更新 |
     | 插入行（阴性对照） | 120×80 | 120×80 | 120×80 | — |

   - **与上线门槛的关系**：浮动图片属于 00 号计划书 §4.2 的目标能力；A02 要求"保存、关闭、重开后内容一致"。DEF-002 必须在 M5 修复。如果改为"已知限制"，须走范围变更并经你审批，不能由实施自行决定。
   - **补丁必要性与规模评估**（M0 总设计 §8：只评估，不实施）：

     | 方案 | 做法 | 规模 | 问题 |
     |---|---|---|---|
     | 上游修复（首选） | 在 `_refreshDrawingTransform` 中，对 `Position` 锚点按保留的尺寸调用 `transformToDrawingPosition` 重算终点锚点，随刷新一并写入图片模型 | 约 10 行，局限在一个方法里 | 需要上游合入；合入前可以按 00 号计划书 §10.3 以 `pnpm patch` 管理 |
     | 平台插件 | 监听同一批 `REFRESH_MUTATIONS`，在 SDK 刷新之后为受影响的 `Position` 图片重算锚点并写回 | 一个插件、一个控制器 | 要写回就得产生 mutation。它会进入撤销栈；在"打开即自动行高"的场景下，还会被变更检测（P3 V06）当成修改。要么用"仅本地"加上"下一次真实修改时一并保存"，要么接受打开即有修改。两者都要在 M5 验证 |
     | 保存时修正 | 捕获快照时按内存中的尺寸修正锚点 | 适配层内 | 切换工作表时内存里的尺寸已经被拉伸，修正不了，**不可行** |

     建议 M5 先向上游报告；以补丁或插件的方式实现修复，并用本 Phase 的用例验证（届时"预期失败"的 3 个用例应当转为通过）。
3. **手写快照在第一次打开时会被补齐默认字段，缺少的 id 会被随机生成**。例如文字文档缺少 `sectionId` 时，每次打开生成的值都不同。这是平台新建文档要用收敛后的模板快照的另一个原因。
4. **内存中的特殊数值**：单元格内嵌文档的 `pageSize` 在内存中是 `Infinity`，写成 JSON 后变成 `null`。重开后能正常还原，并继续收敛。服务端校验与哈希都要以 JSON 文本为准，并且计算哈希前应当把资源数组按名称排序：资源数组的顺序取决于插件的注册顺序。
5. **Facade 的读取方法可能改动模型**：`getDataValidations()` 会给每个还没有规则的工作表建一个空数组，下一次 `save()` 就会多出这些空条目（空值等价，内容不变）。验证脚本因此先保存、再读语义。平台的编辑器适配层不应在捕获快照前调用这类读取方法；P3 做变更检测时要确认它们不产生 mutation。
6. **图片与链接的存储位置**（服务端的地址检查必须覆盖全部位置）：

   | 文档类型 | 位置 |
   |---|---|
   | 表格 | 浮动图片在 `SHEET_DRAWING_PLUGIN` 资源里；单元格图片在单元格富文本的 `p.drawings` 里；工作表背景图片在 `sheets[*].backgroundImage.source`，入口在"视图 → 显示"，本期目标能力里没有它；超链接在单元格富文本的 `customRanges` 里 |
   | 文字文档 | 图片在顶层 `drawings` 与 `DOC_DRAWING_PLUGIN` 资源里；超链接在正文 `customRanges` 与 `DOC_HYPER_LINK_PLUGIN` 资源里，**加载时资源中的地址覆盖正文中的地址**（`packages/docs-hyper-link/src/controllers/resource.controller.ts`）；页眉页脚（`headers`、`footers`）、备注（`notes`）、脚注尾注（`footnotes`、`endnotes`）也可以包含链接与图片 |

   - 两种地址都以同源相对地址保存（例如 `/fixtures-assets/…`、`#gid=…`），加载正常。这对 P4 的 `/api/assets/{id}` 方案是好消息。
   - 服务端的检查要像 SDK 的 `isSafeUrl` 一样，按平台的源解析相对地址，否则会误拒合法保存。
   - **建议**：服务端用统一的"地址提取器"扫描上表的全部位置；对本期不支持的结构（页眉页脚、脚注尾注等）要求为空，不为空就拒绝。

### 2.5 保护类资源

- `sheet-protection` 样本中，`SHEET_RANGE_PROTECTION_PLUGIN`、`SHEET_WORKSHEET_PROTECTION_PLUGIN`、`SHEET_AuthzIoMockService_PLUGIN` 变为非空。
- 用完整档案打开后，三个浏览器一致：
  - 受保护区域 A1 照样能用键盘改掉；
  - 界面显示保护区域的阴影与工作表标签上的锁图标（截图 `e2e/results/v03/protection-*.png`）。
- **原因**：本地模拟的授权服务 `AuthzIoLocalService` 构造时，如果当前用户为空，就把它设为 `Owner_<8 位随机串>`（`packages/core/src/services/authz-io/authz-io-local.service.ts:73-79`），之后按用户 id 的前缀判断角色（`:81-87`，`packages/core/src/services/user-manager/const.ts:44-45`）。所以表格页上人人都是"所有者"（实测当前用户 id 为 `Owner_…`）；文字文档页则是空 id 的匿名用户。
- **风险**：平台以后如果调用 `setCurrentUser` 设置真实用户，本地授权服务可能会把伪造的保护规则从"不生效"变成"锁死编辑"。没有保护规则的普通编辑是否也受影响，待 P3 核实。
- **结论**：保护规则在本平台既不是安全边界（与 00 号计划书 §4.2 一致），又会留下解除入口被隐藏后无法去掉的视觉状态，还有被真实用户身份"激活"的风险。服务端必须要求保护类资源为空（§2.4）。

### 2.6 对设计的影响

- 00 号计划书 §8.2：
  - 资源名称清单与每项的服务端处置（§2.4）；
  - 客户端打开自检与资源加载错误捕获（§3.3）；
  - 新建文档使用收敛后的模板快照。
- 00 号计划书 §11.2 / §11.3：
  - 统一的地址提取器，覆盖全部位置，并按平台源解析相对地址；
  - 不支持的结构要求为空；
  - 文字文档超链接资源必须与正文一致。
- 00 号计划书 §8.7：SDK 或档案升级前，用 `fixtures/` 做保存重开回归（`e2e/v03-roundtrip.spec.ts`：基线、语义、声明与运行时核对），并先做空值等价归一化。
- M5：DEF-002（修复，或经范围变更列为已知限制）。

## 3. V04 资源丢失与防护

### 3.1 结论：通过

三类问题都能稳定复现；防护组合经逐一实测可行，可以直接写成 M3 的规则。

### 3.2 证据

- 命令：`npx playwright test e2e/v04-resource-loss.spec.ts`（21 个用例 × 3 个浏览器，全部带断言）
- 结果：`e2e/results/v04/missing/`、`corrupt/`、`late/`、`duplicate-*.json`、`guard-no-false-positive-*.json`

**情况 1：插件缺失**（用去掉某个插件组的档案打开样本，然后保存）

| 去掉的组 | 资源 | 不走资源的数据 | 页面报错 | 服务端检查 | 打开自检 |
|---|---|---|---|---|---|
| 表格 cf、dv、filter、note | 对应条目**消失** | — | 无（静默） | 拦住 | 拦住 |
| 表格 drawing | `SHEET_DRAWING_PLUGIN` 消失 | 单元格图片保留 | 无 | 拦住 | 拦住 |
| 表格 hyperlink | 没有资源 | 单元格里的 4 个链接保留 | 无 | 不涉及 | 不涉及 |
| 文字文档 drawing | `DOC_DRAWING_PLUGIN` 消失 | 顶层 `drawings` 的 2 张图保留 | 无 | 拦住 | 拦住 |
| 文字文档 hyperlink | `DOC_HYPER_LINK_PLUGIN` 消失 | 正文的 2 个链接保留 | 无 | 拦住 | 拦住 |

**情况 2：资源损坏**（资源数据截断成非法 JSON，或者换成结构不对的合法 JSON）。平台里损坏的快照就是服务端的"上一版"，所以两种检查都拿"损坏版"与"加载后立即保存的结果"比较。

| 损坏的资源 | 打开后 | 控制台 / 页面异常 | 服务端检查 | 打开自检（资源比较） | 加载错误捕获 |
|---|---|---|---|---|---|
| 条件格式、数据验证、备注、表格图片、文字文档图片：非法 JSON | **被清空** | 无：这些插件的 `parseJson` 自己吞掉了错误 | 拦不住（变为空不能作为拒绝理由） | 拦住 | 发现（解析被吞） |
| 筛选：非法 JSON | 被清空 | `Load Workbook{…} … Data Error.` | 拦不住 | 拦住 | 发现（解析抛错） |
| 文字文档超链接：非法 JSON | 从正文重新生成，与损坏前一致 | `loadResources error` | 不涉及（无损失） | 不涉及 | 发现（解析抛错） |
| 条件格式：结构不对 | 变成无意义的数据 | `loadResources error`，另有 **15 条未捕获的页面异常**，编辑器已处于异常状态 | 拦不住 | **拦不住** | 发现（加载抛错） |

资源加载错误捕获在正常样本上没有误报：`sheet-all`、`doc-all` 与两个手写样本，三个浏览器都没有误报。

**情况 3：重复资源名**：伪造一份文字文档快照，放两条 `DOC_HYPER_LINK_PLUGIN`，前一条把地址改成 `https://evil.example/phish`，后一条保持原样。
- SDK 加载时取第一条（`resource-manager.service.ts` 与 `resource-loader.service.ts` 都用 `find`），**正文中的两个链接都被改写成伪造地址**；
- 新的服务端结构检查识别出重复并拒绝；
- 合法客户端不会产生重复条目：SDK 按资源名唯一注册、唯一输出。

**情况 4：晚注册**（文档创建之后再注册 cf、note、文字文档 hyperlink 插件组）：资源被补加载，保存结果与原样本一致。文字文档超链接这一例区分不了"补加载"与"从正文重新生成"，只作参考。

### 3.3 防护规则（建议直接写入 M3 的设计）

1. **服务端检查**：
   - 结构：资源名唯一、`data` 为字符串；
   - 资源名在档案白名单内；
   - 上一版中非空的资源，新提交中不得消失；
   - 按 §2.4 的处置：保护类与"必须为空"的资源为空；已知资源做结构校验；文字文档超链接资源与正文一致。

   注意：不能因为"资源变为空"而拒绝，用户删除全部规则时资源也会变为空。
2. **客户端打开自检**（编辑器适配层）：
   - 档案完整性：用运行时注册的资源 hook（按文档类型过滤）与档案白名单比对，不一致就只允许阅读。这一步不依赖文档里有没有数据；本 Phase 已把它作为 V03 的断言。
   - 资源比较：加载完成后立即捕获一次，与刚加载的快照比较。原来非空、现在消失或变为空，就判定加载失败。
   - 资源加载错误捕获：通过依赖注入覆盖 `IResourceManagerService`，包装每个 hook 的 `parseJson` 与 `onLoad`，识别"解析抛错""非空输入被吞成空值""加载抛错"三种失败（原型见 `spikes/m0/src/harness/guarded-resource-manager.ts`，已实测）。它能发现资源比较拦不住的"结构不对"。这是内部 API，按 00 号计划书 §10.1 集中封装并登记。
   - **失败后的处置**：
     - 只允许阅读，并明确提示"文档数据不完整，已阻止编辑"；
     - 把失败详情（文档、资源名、失败类型、客户端版本）上报服务端并告警；
     - 恢复路径由运维处理：从历史版本或检查点恢复，或修复档案后重新打开。
   - 这一次捕获的耗时，交给 P3 的捕获成本测量。
3. **档案完整性**：编辑器必须把档案里的插件全部注册成功，才允许进入编辑（00 号计划书 §8.2 原有规则）。本项证明缺插件是**静默**的，所以这条规则必不可少。

### 3.4 对设计的影响

- 00 号计划书 §8.2：
  - 把"服务端校验两点"扩展为上面的服务端规则；
  - 补充客户端打开自检三部分与失败处置；
  - 明确"资源解析失败在多数插件中是静默的"。
- 00 号计划书 §11.2：快照校验增加"资源结构（名称唯一、`data` 为字符串）"与"已知资源的结构校验"。
- M3 的编辑器适配层：打开自检与资源加载错误捕获。

## 4. V05 复制不改 unitId

### 4.1 结论：通过

### 4.2 证据

- 命令：`npx playwright test e2e/v05-copy.spec.ts`（12 个用例，三个浏览器全部通过）
- 结果：`e2e/results/v05/`

| 检查 | 表格（`sheet-all`） | 文字文档（`doc-all`） |
|---|---|---|
| 复制品与原文档的 `unitId` | 相同（`m0-sheet-all`） | 相同（`m0-doc-all`） |
| 两个标签页同时打开、各自编辑、保存、重开 | 各自只有自己的修改 | 各自只有自己的修改 |
| 与原文档的差异 | 只有被编辑的单元格，以及它引用的新样式条目 | 正文去掉插入的文字后与原文档相同 |
| 语义（条件格式、数据验证、筛选、备注、图片、链接、标题、列表、表格） | 两份都与原文档一致 | 两份都与原文档一致 |
| 资源（与原样本比较） | 没有丢失或变空 | 没有丢失或变空 |
| 内部链接（`#gid=…`）在复制品中指向的工作表 | 存在 | 不涉及 |
| 同一个 Univer 实例里再创建相同 `unitId` 的文档 | 抛异常：`cannot create a unit with the same unit id` | 同左 |

另外核对了浏览器存储：
- Univer 的持久化存储是 IndexedDB 库 `UniverLocalStorage`，不可用时回退到 localStorage（键前缀 `UniverLocalStorage/`，见 `packages/ui/src/utils/storage-driver.ts`）。里面存用户习惯，例如最近使用的数字格式，不按 `unitId` 区分。
- 移动端的公式面板另用了 localStorage 键 `univer-mobile-recent-formula-functions`。
- Univer 没有使用 BroadcastChannel、SharedWorker 或 Service Worker。

所以两个同 `unitId` 的文档在两个标签页中不会互相干扰。

### 4.3 对设计的影响

- 00 号计划书 §8.3 的方案成立：复制时原样复制快照，不改 `unitId` 与工作表 id。
- 约束照旧：一页只加载一份文档（§10.2）。将来如果要在一页里同时加载两份文档，需要先引入 `unitId` 改写方案。
- M4：本机发件箱的键、Web Locks 的锁名，都必须用平台的 `documentId`，不能用 `unitId`。
- M4 / 00 号计划书 §7.6："退出登录后清空本机数据"要覆盖 Univer 自己的存储：IndexedDB 库 `UniverLocalStorage`、localStorage 中以 `UniverLocalStorage/` 开头的键、`univer-mobile-recent-formula-functions`。也可以用依赖注入把 `ILocalStorageService` 换成内存实现。
