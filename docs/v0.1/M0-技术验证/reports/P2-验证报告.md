## 2. V03 保存重开保真

### 2.1 结论：有条件通过

- 17 个样本 × 3 个浏览器共 51 次，全部收敛：
  - S1 → S2：除 1 处"空值等价"外完全一致，这 1 处出现在手写样本上；
  - S2 → S3：全部完全一致。
- S0 → S1：由 SDK 生成的 15 个样本，只有"空值等价"的差异，外加一处图片尺寸变化（§2.3 第 2 条）。
- 三个浏览器对同一样本得到的 S1 完全一致（按内容哈希比较）。唯一例外是手写的文字文档样本：SDK 会给缺少的 `sectionId` 生成随机值。
- **条件**：见 §2.3 第 2 条。

### 2.2 证据

### 2.3 发现

1. **"空值等价"的归一化**。资源数据会在空字符串 `""` 与 `{}` 之间变化，按工作表分组的资源也会删掉取值为空数组的键。两者在内容上都等价。
   - 根因：资源有两条加载路径。
     - 文档单元创建时，走 `ResourceManagerService.loadResources`，遇到空数据会跳过；
     - 插件晚于文档单元注册资源 hook 时，走 `ResourceLoaderService` 的 `loadHookResource`，只要条目存在，就调用 `onLoad`。
   - 所以缺少资源条目的快照，第一次保存得到 `""`，之后得到 `{}`（`packages/core/src/services/resource-loader/resource-loader.service.ts:40-55`，`packages/core/src/services/resource-manager/resource-manager.service.ts` 的 `loadResources`）。
   - 影响：平台做"内容哈希相同就不增加修订号"时，第一次保存会多出一个修订，没有实际危害。平台新建文档时，应当用 SDK 保存过的模板快照（资源条目齐全、id 齐全），这样从第一次保存起就稳定。
2. **浮动图片在所跨行自动变高后，重开会被拉伸（SDK 缺陷，本项的条件）**。
   - 默认锚点类型是 `Position`：随单元格移动，但保持尺寸。行高变化时，SDK 通过显式的行列命令（设置行高、插入删除行列、隐藏等）更新图片的终点锚点。但**自动行高**（换行文字、放大字号、插入单元格图片触发的行高自适应）没有被处理（`packages/sheets-drawing/src/controllers/sheet-drawing-transform-affected.controller.ts:101-127`）。
   - 于是界面上图片保持原尺寸，快照里的终点锚点却已经过时；重开时 SDK 按锚点重算尺寸，图片就被拉伸了。
   - 实测：先插浮动图片，再让它所跨的行自动变高。结果如下（手动改行高、插入行都不受影响）：

     | 触发方式 | 图片尺寸 |
     |---|---|
     | 单元格图片 | 120×80 → 120×99 |
     | 换行文字 | 120×80 → 120×186 |
     | 36 号字 | 120×80 → 120×111 |

   - 数据没有丢失（锚点与图片地址都在），只是重开后显示尺寸不同。
   - 处理建议：M5 验收表格图片能力时二选一：
     - 平台插件监听自动行高 mutation，为 `Position` 锚点的图片重算终点锚点（优先；同时向上游报告）；
     - 列为已知限制。
3. **手写快照在第一次打开时会被补齐默认字段，缺少的 id 会被随机生成**。例如文字文档缺少 `sectionId` 时，每次打开生成的值都不同。这是平台新建文档要用模板快照的另一个原因。
4. **内存中的特殊数值**：单元格内嵌文档的 `pageSize` 在内存中是 `Infinity`，写成 JSON 后变成 `null`。重开后能正常还原，并且继续收敛（S2 = S3）。服务端校验与哈希都要以 JSON 文本为准。
5. **图片与链接的存储位置**：
   - 表格的浮动图片在 `SHEET_DRAWING_PLUGIN` 资源里，单元格图片在单元格的富文本（`p.drawings`）里。两者都以同源相对地址保存（`/fixtures-assets/…`），相对地址可以正常加载，这对 P4 的 `/api/assets/{id}` 方案是好消息；
   - 文字文档的图片同时存在正文的 `drawings` 与 `DOC_DRAWING_PLUGIN` 资源里；
   - 文字文档的超链接同时存在正文的 `customRanges` 与 `DOC_HYPER_LINK_PLUGIN` 资源里，**加载时资源中的地址会覆盖正文中的地址**（`packages/docs-hyper-link/src/controllers/resource.controller.ts`）。所以服务端的链接协议检查必须同时检查这两处，否则可以构造出"正文正常、资源里藏着危险地址"的快照。

### 2.5 保护类资源

- `sheet-protection` 样本中，`SHEET_RANGE_PROTECTION_PLUGIN`、`SHEET_WORKSHEET_PROTECTION_PLUGIN`、`SHEET_AuthzIoMockService_PLUGIN` 变为非空。后者保存的是每条规则的权限策略。
- 用完整档案打开后，三个浏览器的表现一致：
  - 受保护区域 A1 照样能用键盘改掉。原因是默认所有用户都是同一个匿名身份（`userID` 为空），SDK 认为改的人就是规则的所有者；
  - 界面显示受保护区域的阴影，工作表标签上有锁图标（截图核对）。
  - 结果：`e2e/results/v03/protection-<浏览器>.json`。
- 结论：
  - 保护规则在本平台既不是安全边界（与 00 号计划书 §4.2 一致），又会留下解除入口被隐藏后无法去掉的视觉状态；
  - 建议服务端要求保护类资源为空，非空即拒绝：表格 4 项、文字文档的 `DOC_OBJECT_PERMISSION_PLUGIN`（见插件档案 v1 §3）；
  - P3 需要核实阅读模式的 `setReadOnly` 是否会写入这些资源。

- 00 号计划书 §8.2：
  - 补充资源名称清单（§2.4）与"保护类资源必须为空"的规则；
  - 补充"客户端打开自检"（§3.3）；
  - 平台新建文档使用 SDK 保存过的模板快照。
- 00 号计划书 §11.2 / §11.3：链接协议检查同时覆盖文字文档正文的 `customRanges` 与 `DOC_HYPER_LINK_PLUGIN` 资源；图片地址检查覆盖表格资源与单元格富文本、文字文档正文与资源。
- M5：处理浮动图片的自动行高缺陷（§2.3 第 2 条），登记为 DEF-002。

## 3. V04 资源丢失与防护

### 3.1 结论：通过

"插件缺失导致资源丢失"可以稳定复现，防护思路可行，并且可以直接写成 M3 的规则。

### 3.2 证据

- 命令：`npx playwright test e2e/v04-resource-loss.spec.ts`（19 个情况 × 3 个浏览器 = 57 个用例，全部通过，三个浏览器结果一致）
- 结果：`e2e/results/v04/missing/`、`corrupt/`、`late/`

**情况 1：插件缺失**（用去掉某个插件组的档案打开样本，然后保存）

| 去掉的组 | 结果 | 页面报错 | 服务端检查 | 打开自检 |
|---|---|---|---|---|
| 表格 cf、dv、filter、note、drawing | 对应资源条目在保存结果中**消失** | 无（静默） | 拦住 | 拦住 |
| 表格 hyperlink | 没有资源；单元格里的 4 个链接都保留 | 无 | 不涉及 | 不涉及 |
| 文字文档 drawing | `DOC_DRAWING_PLUGIN` 消失；正文的 `drawings` 仍保留 2 张图 | 无 | 拦住 | 拦住 |
| 文字文档 hyperlink | `DOC_HYPER_LINK_PLUGIN` 消失；正文的 2 个链接仍保留 | 无 | 拦住 | 拦住 |

**情况 2：资源损坏**（把资源数据截断成非法 JSON，或者换成结构不对的合法 JSON，再用完整档案打开并保存）

| 损坏的资源 | 打开后 | 控制台 | 服务端检查（与上一版比） | 打开自检（与刚加载的快照比） |
|---|---|---|---|---|
| 条件格式、数据验证、备注、图片（表格与文字文档）：非法 JSON | 资源**被清空** | **无任何报错**：这些插件的 `parseJson` 自己吞掉了错误 | 拦不住（条目还在，只是空了） | 拦住 |
| 筛选：非法 JSON | 资源被清空 | `Load Workbook{…} Resources{…} Data Error.` | 拦不住 | 拦住 |
| 文字文档超链接：非法 JSON | 资源从正文的链接重新生成，内容与损坏前一致 | `[ResourceManagerService] loadResources error` | 不涉及（无损失） | 不涉及 |
| 条件格式：结构不对的 JSON | 资源变成无意义的数据 | `loadResources error … is not iterable` | 拦不住 | 只比较资源拦不住，要靠捕获加载错误 |

**情况 3：晚注册**（文档创建之后再注册 cf、note、文字文档 hyperlink 插件组）：资源都被补加载，保存结果与原样本一致，没有丢失。

### 3.3 防护规则（建议直接写入 M3 的设计）

1. **服务端**：
   - 资源名必须在档案白名单内；
   - 上一版中非空的资源，新提交中不得消失；
   - 保护类资源必须为空；
   - 已知资源做结构校验，拦住"结构不对"的数据。
   
   注意：不能因为"资源变为空"就拒绝，用户删除全部规则时，资源也会变为空。
2. **客户端打开自检**（编辑器适配层）：
   - 加载完成后立即捕获一次，与刚加载的快照逐条比较资源。原来非空、现在消失或变为空，就判定加载失败，只允许阅读。
   - 同时捕获资源加载错误：通过依赖注入覆盖 `IResourceManagerService`，包装每个 hook 的 `parseJson` 与 `onLoad`，两条加载路径都能覆盖。
   - 这一次捕获的耗时，交给 P3 的捕获成本测量。
3. **档案完整性**：编辑器必须把档案里的插件全部注册成功，才允许进入编辑（00 号计划书 §8.2 原有规则）。本项证明缺插件是**静默**的，所以这条规则必不可少。

### 3.4 对设计的影响

- 00 号计划书 §8.2：把"服务端校验两点"扩展为上面的服务端规则，并补充客户端打开自检；明确"资源解析失败在多数插件中是静默的"。
- 00 号计划书 §11.2：快照校验增加"已知资源的结构校验"。
- M3 的编辑器适配层：打开自检与资源加载错误捕获（内部 API `IResourceManagerService`，按 00 号计划书 §10.1 集中封装并登记）。

## 4. V05 复制不改 unitId

### 4.1 结论：通过

### 4.2 证据

- 命令：`npx playwright test e2e/v05-copy.spec.ts`（12 个用例，三个浏览器全部通过）
- 结果：`e2e/results/v05/`

| 检查 | 表格（`sheet-all`） | 文字文档（`doc-all`） |
|---|---|---|
| 复制品与原文档的 `unitId` | 相同（`m0-sheet-all`） | 相同（`m0-doc-all`） |
| 两个标签页同时打开、各自编辑、保存、重开 | 各自只有自己的修改 | 各自只有自己的修改 |
| 资源（与原样本比较） | 没有丢失或变空 | 没有丢失或变空 |
| 内部链接（`#gid=…`）在复制品中指向的工作表 | 存在 | 不涉及 |
| 同一个 Univer 实例里再创建相同 `unitId` 的文档 | 抛异常：`cannot create a unit with the same unit id` | 同左 |

另外：Univer 在浏览器中唯一的持久化存储是 IndexedDB 库 `UniverLocalStorage`，用来存用户习惯（最近使用的数字格式等），不按 `unitId` 区分；也没有使用 BroadcastChannel、SharedWorker 或 Service Worker。所以两个同 `unitId` 的文档在两个标签页中不会互相干扰。

### 4.3 对设计的影响

- 00 号计划书 §8.3 的方案成立：复制时原样复制快照，不改 `unitId` 与工作表 id。
- 约束照旧：一页只加载一份文档（§10.2）；将来如果要在一页里同时加载两份文档，需要先引入 `unitId` 改写方案。
- 本机发件箱（M4）必须以平台的 `documentId` 为键，不能用 `unitId`，因为复制品与原文档的 `unitId` 相同。
