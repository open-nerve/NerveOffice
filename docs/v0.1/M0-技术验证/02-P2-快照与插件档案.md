# M0-P2 快照与插件档案：架构设计与实施规划

> 状态：已完成｜日期：2026-09-24｜基于代码版本：`68cd726`（main，P1 已合并）

## 1. 目标与范围

对应 M0 总设计 §5 的 P2 一行，覆盖验证项 V03、V04、V05：

- **V03**：定出插件档案 v1 草案（表格 `sheet@1`、文字文档 `doc@1`）；为档案内每个带数据的插件准备样本，验证"保存 → 重开 → 再保存"的保真度；产出资源名称清单；
- **V04**：稳定复现"插件缺失导致资源丢失"，并验证防护思路；
- **V05**：复制文档时不改 `unitId`，两份文档各自编辑、保存、重开都正常。

不在本 Phase：
- 变更检测、公式等待与只读（P3）；
- 图片服务替换（P4）。本 Phase 的图片样本使用验证工程提供的同源静态图片；
- 文字文档的能力验收与中文输入（P5）。本 Phase 只做文字文档样本的保真。

## 2. 现状

- **P1 交付的验证工程**：候选档案、`window.__m0`、三种 CSP 模式的服务、三浏览器的 Playwright 配置、真实 Safari 自检（见 P1 交接单）。
- **与本 Phase 相关的源码事实**（v1.0.0）：
  - `saveUnit` 用已注册插件的资源整体覆盖快照的 `resources`（`packages/core/src/services/resource-loader/resource-loader.service.ts:164-173`）。晚注册的插件会给已有文档补加载资源（同文件 `:60-100`）。
  - `loadResources` 在插件解析资源失败时，只记一条 `[ResourceManagerService] loadResources error` 日志，丢弃该资源（`packages/core/src/services/resource-manager/resource-manager.service.ts`）。下次保存时，该插件以空状态写回。
  - 保护类资源也写进快照：区域保护、工作表保护（规则与权限点两项）、`SHEET_AuthzIoMockService_PLUGIN`。
  - Univer 自带的 IndexedDB 库 `UniverLocalStorage` 不按文档区分；没有 BroadcastChannel、SharedWorker 或 Service Worker。

## 3. 设计

### 3.1 验证工程的增量

| 位置 | 增量 |
|---|---|
| `server/serve.ts` | 文档存储（内存，只用于验证）：`GET/PUT /api/docs/:id`、`POST /api/docs/:id/copy?to=<新 id>` |
| `src/profiles/` | 候选档案改为按"插件组"组织，每组声明自己的插件、资源名与可否单独去掉；页面参数 `without=<组,…>` 生成去掉某些组的档案变体（V04）。档案 id 改为 `sheet@1-draft`、`doc@1-draft` |
| `src/harness/` | 页面参数 `doc=<id>`：从存储加载；`window.__m0` 增加：`resourceHooks()`（运行时注册的资源 hook）、`persist(id)`（把当前快照写回存储）、`builders`（样本构建器）；`resource-guard.ts`：资源比对函数 |
| `src/experiments/v03-samples/` | 样本构建器：在页面内用 Facade、`RichTextBuilder` 或编辑器命令生成样本 |
| `public/fixtures-assets/` | 样本用的同源静态图片 |
| `e2e/` | `v03-build-samples`（只在设置 `M0_BUILD_SAMPLES=1` 时运行）、`v03-roundtrip`、`v04-resource-loss`、`v05-copy` |

### 3.2 插件档案 v1 草案

- **档案的内容**：插件列表（按组）、影响数据的配置、适用的 SDK 版本（1.0.0）、资源名称白名单（含每个资源适用的文档类型）。
- **本 Phase 定什么**：插件与资源。界面类配置（菜单隐藏等）由 P3 补充，图片服务替换由 P4 补充，文字文档的最终范围由 P5 定稿；M0 结束时汇总定稿。
- **说明文档**：写在 `reports/插件档案v1.md`，代码在 `spikes/m0/src/profiles/`（仅供参考，M1 按正式流程重写）。

### 3.3 实验方案

**V03 保存重开保真**

1. **样本集**：每个带数据的插件至少一个样本，另有表格、文字文档各一个"全部功能"的综合样本。
   - 样本由 SDK 生成：在空文档上执行构建器，再调用 `save()`，写入 `fixtures/`。这样样本本身就是 SDK 的输出。
   - 另外保留 P1 的手写最小样本，用来观察 SDK 对手写快照做了哪些归一化。
2. **流程**：对每个样本 S0：
   - 新页面加载 S0，等到 `Steady` 后调用 `save()`，得到 S1，写入存储；
   - 再开一个新页面加载 S1，得到 S2。
   - 三个浏览器各跑一遍。
3. **判定**：
   - **稳定**：同一浏览器内 S1 与 S2 完全一致。如果有易变字段，逐个说明来源。
   - **保真**：逐条列出 S0 与 S1 的差异，归为三类：默认值补齐、归一化、内容丢失。
   - **资源**：S1 的资源名都在白名单内；S0 中非空的资源，在 S1 中依然非空且内容相同。
   - **跨浏览器**：比较三个浏览器得到的 S1 是否一致。例如自动行高依赖字体度量，可能不一致；有差异就记录影响。
4. **资源名称清单**：以运行时注册的 hook 为准（名称与适用的文档类型），与源码检索结果交叉核对。
5. **保护类资源**：用 Facade 创建一条区域保护和一条工作表保护，观察哪些资源变为非空，以及对编辑的影响，给出服务端或适配层的处理建议。

**V04 资源丢失与防护**

1. **插件缺失**：对每个带资源的可去掉插件组，用去掉该组的档案加载对应样本，保存后比较资源，确认丢失可以稳定复现。同时观察不走资源的数据，例如单元格富文本里的超链接，缺少插件时是否保留。
2. **资源损坏**：把样本中某个资源的数据改坏，用完整档案加载。确认控制台出现加载错误，保存后该资源以空值写回。
3. **晚注册**：文档创建之后再注册某个插件，确认资源被补加载、不会丢失。
4. **防护思路**，对上面三种情况逐一验证：
   - **服务端检查**：资源名白名单，加上"原来非空的条目在新快照中消失就拒绝"。预期能拦住第 1 种，拦不住第 2 种。
   - **客户端打开自检**：加载完成后立即 `save()` 一次，与原快照逐条比较资源；原来非空、现在为空或消失，就判定加载失败，只允许阅读。预期能拦住第 1、2 种。自检的耗时交给 P3 的捕获成本测量。

**V05 复制不改 unitId**

1. 用两个综合样本分别在存储中建文档 A，再复制出 B。A、B 内容完全相同，`unitId` 也相同。
2. **两个标签页同时打开 A 和 B**：各自用键盘编辑不同的单元格（文字文档则各自输入不同文字），并写回存储。
3. **分别用新页面重开**：核对 A、B 各自只有自己的修改，其余内容与资源不变。表格样本中的内部链接、图片、条件格式都要在复制品中正常工作。
4. **负向核对**：在同一个 Univer 实例里先后创建两份 `unitId` 相同的文档，确认会抛异常，把这条约束记录下来。

**审查后补充**（`reviews/P2-审查报告.md`）

- 样本的预期语义（`e2e/samples-expected.ts`）：生成时与每次重开后都用 Facade 核对，避免保真测试变成自证。
- 差异基线（`e2e/v03-baselines.ts`）：S0→S1 的实际差异必须与基线一致，使 V03 能充当升级回归门禁。
- 档案声明的资源名与运行时 hook 自动核对。
- Worker 模式等价核对（Chromium）。
- DEF-002 复现脚本（`e2e/v03-drawing-autoheight.spec.ts`，含阴性对照与切换工作表场景）。
- V04：资源加载错误捕获原型（`guard=1`）、重复资源名、不走资源的数据。
- V05：与原文档的差异比对与语义核对。

### 3.4 资源比对函数（`resource-guard.ts`）

- **判断资源是否为空**：只在顶层解析一次 `data`；解析后是 `null`、空字符串、空对象、空数组，或者各层都为空。内部的字符串不再当作 JSON 解析（审查后修正）。
- **`compareResources(before, after, whitelist)`** 返回：
  - `duplicates`：新快照中重复的资源名（SDK 加载时只取第一条）；
  - `invalid`：`data` 不是字符串的资源；
  - `unknown`：不在白名单内的资源名；
  - `missing`：原来非空、新快照中消失的资源；
  - `emptied`：原来非空、新快照中变为空的资源；
  - `changed`：前后都非空但内容不同（去掉空值后比较，仅供参考）。
- **两种用法**：
  - 服务端检查看 `duplicates`、`invalid`、`unknown`、`missing`。用户正常删除全部规则时也会出现"变为空"，所以 `emptied` 不能作为拒绝理由。
  - 客户端打开自检还要看 `emptied`，因为刚打开的文档不可能有用户删除。再配合资源加载错误捕获（`guarded-resource-manager.ts`），用来发现结构错误和被插件吞掉的解析错误。

## 7. 风险与未决问题

| 风险 / 问题 | 应对 |
|---|---|
| Facade 覆盖不到某些功能的样本构建 | 退到编辑器命令，或在构建脚本中用 Playwright 做界面操作；仍然坚持样本由 SDK 生成 |
| 去掉某个插件组时，其他插件依赖它而无法启动 | 只去掉叶子组；无法单独去掉的组，在报告中写明依赖关系 |
| 自动行高等依赖字体度量的字段在不同浏览器中取值不同 | 按浏览器分别判定"稳定"；跨浏览器差异单独记录，并评估对"资源不缩水"和内容哈希的影响 |
| 生成的样本包含随机 id，重新生成时产生噪音 | 样本只在需要时重新生成（设置环境变量才运行），生成后入库 |
