# M0 技术验证：总设计

> 文档编号：00｜所属版本：v0.1｜状态：已评审｜日期：2026-09-23

## 1. 目标与范围

- **目标**：在写任何生产代码之前，用可以复现的证据，回答那些会阻断架构决策的 Univer SDK 问题；同时锁定 SDK 版本基线和插件档案 v1。对应 00 号计划书 §13.2 中的 M0 一行。
- **范围内**：00 号计划书 §13.4 的验证项 V01–V16，其中 V16 可选。
- **范围外**：
  - 生产代码、产品界面；
  - 服务端业务逻辑、账户与权限；
  - 正式的 CI 与部署。
  
  这些都从 M1 开始。`spikes/` 里的代码一律不迁入生产。

## 2. 输入与依赖

- **上层文档**：00 号计划书中的以下章节：
  - §3 版本基线；
  - §6.5 前端只读加固；
  - §7 本地优先管道；
  - §8 存储与插件档案；
  - §11.3 外部资源与 CSP；
  - §12 性能目标；
  - §13.4 验证清单；
  - 附录 B 源码核查记录。
- **前序 M**：无。
- **环境要求**：
  - 能访问 npm registry；
  - 目标浏览器：Chrome、Edge 的当前版本，以及 Safari 的当前版本；
  - 中文输入法验证至少覆盖 macOS。如果没有 Windows 环境，把 Windows 输入法验证登记为 M6 开始前的补充验证项。

## 5. Phase 规划

执行顺序为 P1 → P2 → P3 → P4 → P5 → P6。每个 Phase 的详细设计（`NN-P{k}-<短名>.md`），在该 Phase 开始时再写。

| Phase | 目标 | 验证项 | 依赖 | 产出 | 验收 |
|---|---|---|---|---|---|
| P1 SDK 基线与验证工程 | 建好验证工程；锁定版本；确认依赖、许可与 CSP | V01、V02 | 无 | 验证工程骨架（后续 Phase 复用）、版本基线、依赖与许可清单、CSP 兼容性结论、包体积记录 | 表格与文字文档在严格 CSP 下能加载、能编辑，否则列出必须放宽的指令及原因；依赖中没有 Pro；许可全部可接受 |
| P2 快照与插件档案 | 确定插件档案 v1；验证快照保真与复制 | V03、V04、V05 | P1 | 插件档案 v1 草案、样本集、保真验证脚本与结果、资源名称清单 | 档案内每个插件的样本，"保存 → 重开 → 再保存"结果一致；插件缺失丢资源可以稳定复现，防护思路可行；复制后两份文档互不影响 |
| P3 编辑语义与性能基线 | 验证变更检测、公式一致性、捕获成本和只读加固；建立性能基线 | V06–V10 | P2 | 变更检测方案与排除名单、公式等待方案、捕获与性能的测量数据、只读拦截点清单、菜单隐藏配置 | 打开样本不产生"有修改"；公式一致性用例全部通过；阅读模式下每个编辑入口都有结论；性能数据齐全 |
| P4 资源与外部请求 | 验证图片服务替换、同源读取，以及对外部请求的治理 | V11、V12 | P1 | 图片服务替换方案、插入与粘贴路径清单、`IMAGE()` 限制方案、CSP 策略的定稿建议 | 所有插入、粘贴路径都得到同源地址，或者有明确的处理方式；外部请求在 CSP 下被拦截，功能降级可以接受 |
| P5 文字文档与中文 | 验证 §4.3 的能力清单和中文输入；确定 `doc@1` 档案的范围 | V13 | P2 | 文字文档能力矩阵、输入法与粘贴的测试记录、范围变更建议（如有） | 每一项能力都有结论：可用、有条件可用，或不稳定（隐藏） |
| P6 本地优先可行性 | 验证本地优先管道所需的浏览器能力与成本；决定是否纳入 mutation 日志 | V14、V15、V16 | P3 | 存储、加密、压缩、锁、崩溃恢复的测量与实验结论；mutation 日志的结论；（可选）Node 加载记录 | 本地优先的关键假设都有数据支撑；对 mutation 日志给出"纳入 M4"或"不纳入"的结论 |

## 6. 验证工程

所有验证代码都放在 `spikes/m0/`。它是一个**独立项目**，不属于生产 workspace；M1 建立生产 Monorepo 时，会把 `spikes/` 排除在外。

```text
spikes/m0/
├── package.json        独立的依赖；Univer 版本与版本基线一致，全部精确锁定
├── vite.config.ts
├── index.html          实验入口：选择样本、文档类型和模式
├── src/
│   ├── profiles/       候选的插件档案：sheet、doc
│   ├── harness/        通用工具：加载、捕获、比对、计时
│   └── experiments/    按验证项组织的实验代码，例如 v03-roundtrip/
├── server/             最小的 Node 服务：CSP 响应头、图片上传与同源读取（只用于验证）
├── e2e/                Playwright 的自动化验证与测量脚本；测量结果以 JSON 保存
├── fixtures/           样本文档（JSON 快照）与图片
└── README.md           运行方式、环境要求，以及"不进入生产"的声明
```

- **宿主页面用 React**：与生产环境一致，顺带验证 React 版本与 Univer 的兼容性。
- **代码要求**：验证代码要可读、可复现，但不套用生产级的规范，也不为验证工程本身补测试。
- **P1 顺带完成参考源码的对齐**：把 `refer/univer` 检出到与锁定版本对应的 tag，使阅读的源码与依赖保持一致。执行前会征得你确认。

## 7. 证据标准

每个验证项的结论，都写进 `reports/P{k}-验证报告.md`，格式固定为以下四项：

| 项目 | 要求 |
|---|---|
| 结论 | 通过、有条件通过（写明条件）、不通过、未决，四选一 |
| 证据 | 可复现的脚本或测试路径、运行命令、测量数据，必要时附截图 |
| 环境 | 操作系统、浏览器与版本、机器配置、Univer 版本 |
| 对设计的影响 | 需要修改 00 号计划书的哪一节；是否产生 ADR 候选、延期项或范围变更 |

判断标准是：**另一个人照着记录，能够复现同样的结论。** 性能数据只作为相对基线使用，正式的压测放在 M7。

## 8. 停止规则

验证工作很容易无限扩张，所以约定以下规则：

- 每个 Phase 的设计文档中，要为每个验证项写明计划采用的实验方案。计划的方案全部尝试完仍然没有结论时，就停止，记为"未决"；在该 Phase 的审查中，再决定是追加实验、接受风险，还是做范围变更。
- 不为了"让验证通过"，而在 `spikes/` 里实现超出验证目的的功能。
- 如果某一项必须修改 Univer 源码才能通过，就记录为补丁候选（00 号计划书 §10.3）。M0 只评估补丁的必要性和规模，不实施补丁。

## 9. 审查与交接

- **每个 Phase 结束时**：
  - 做一次结论审查，优先由独立的审查者进行，报告写入 `reviews/P{k}-审查报告.md`；
  - 编写交接单，写入 `handoffs/P{k}-交接单.md`。
- **Git**：每个 Phase 一个 worktree 分支，例如 `m0-p1-sdk-baseline`；审查通过后，以 `git merge --no-ff` 合并到 `main`；M0 结束时打 tag `v0.1-m0`。
- **推进方式**：本总设计审批通过后，按 `CLAUDE.md` 中"推进节奏与决策边界"的约定，自主推进 P1–P6。阻断项结论为"不通过"，属于必须停下来请示的情况。
- **M0 结束评审**，要完成以下几件事：
  - 确认版本基线、插件档案 v1 和能力矩阵；
  - 按结论把 00 号计划书更新到 r3；
  - 登记范围变更与延期项；
  - 编写 M0 交接单，作为 M1 的输入。交接单重点写明生产编辑器适配层需要沿用的结论：排除名单、只读拦截点、公式等待、CSP 策略、图片服务替换方式。

## 11. 风险与应对

| 风险 | 应对 |
|---|---|
| M0 期间 rc 版本有更新 | P1 锁定版本后不再跟随，除非新 rc 修复了某个阻断问题。确需切换版本时，在报告中记录，并重跑受影响的验证 |
| 验证工作无限扩张 | 执行 §8 的停止规则；每个验证项先写实验方案，再动手 |
| 验证环境与生产环境不同 | 报告中记录环境；性能数据只作相对基线 |
| 中文输入法覆盖不全 | 至少覆盖 macOS；缺少的 Windows 部分登记为 M6 前的补充验证 |
| 阻断项结论为"不通过" | 立即提出架构调整或范围变更，评审通过并更新 00 号计划书后，再继续后面的 Phase |
| `spikes/` 里的代码被当作生产代码复用 | 目录隔离、README 中明确声明；M1 按正式流程重写 |
