# M0-P3 编辑语义与性能基线：架构设计与实施规划

> 状态：已完成｜日期：2026-09-24｜基于代码版本：`62b5109`（main，P2 已合并）

## 1. 目标与范围

对应 M0 总设计 §5 的 P3 一行，覆盖验证项 V06–V10：

- **V06 变更检测**：打开文档不会被判定为"有修改"；定出变更检测的规则与排除名单；用户的每一类编辑都能被检测到；检测安静之后，不会再有没被检测到的内容变化。
- **V07 公式一致性**：修改公式依赖的单元格后立即保存，快照中的公式结果与重新计算的结果一致。覆盖依赖链、大范围聚合、跨表、慢计算、易变函数，主线程与 Worker 两种模式。
- **V08 捕获成本**：`save()`、序列化、压缩、哈希的耗时与主线程阻塞（表格 1 MiB、5 MiB）。另测 P2 提出的"打开自检"那一次捕获，以及资源加载错误捕获的开销。
- **V09 阅读模式**：阅读模式下，每个编辑入口都被拦截，或者不会产生可提交的内容；阅读与编辑模式之间的切换；保护类与不支持功能的入口已隐藏。
- **V10 性能基线**：5 万单元格、1,000 个公式的表格样本：首屏、编辑响应、公式计算、内存。

不在本 Phase：
- 图片服务与外部请求（P4）；
- 文字文档的能力、中文输入与文字文档的性能（P5）。本 Phase 的文字文档只做变更检测、阅读模式与捕获成本；
- 本机存储、加密与锁（P6）。V08 只测到"压缩与哈希完成"为止。

## 2. 现状

- **验证工程**（P1、P2 交付）：样本集与预期语义、文档存储、插件组、资源比较与加载错误捕获、Worker 统计、三种 CSP 服务（见 P2 交接单）。
- **与本 Phase 相关的源码事实**（v1.0.0，本 Phase 核对）：
  - **命令事件**：
    - `onCommandExecuted` 收不到 `syncOnly` 的命令；`onMutationExecutedForCollab` 能收到，但不是公开稳定 API（`packages/core/src/services/command/command.service.ts:255-270、441-460`）。
    - `beforeCommandExecuted` 对所有命令都会触发，包括 mutation 与 `syncOnly`。Facade 的 `BeforeCommandExecute` 事件设置 `cancel` 后抛出 `CanceledError`，但它不处理撤销与重做；撤销与重做走 `BeforeUndo`、`BeforeRedo`（`packages/core/src/facade/f-univer.ts:222-267`）。
  - **大工作表复制**（单元格数不少于 `largeSheetCellCountThreshold`，默认 6,000，`packages/sheets/src/config/config.ts`）：
    - 第一批内容随插入工作表的 mutation 执行；其余先以 `syncOnly` 宣告，再由 `SheetLazyExecuteScheduleService` 在空闲时以 `onlyLocal` 执行（`copy-worksheet.command.ts:256-306`、`lazy-execute-schedule.service.ts:176`）。
    - 所以"只听 `onCommandExecuted`、排除 `onlyLocal`"的检测，会漏掉复制内容的大部分。
    - 可以用 `UniverSheetsPlugin` 的配置 `largeSheetOperation.largeSheetCellCountThreshold` 关掉拆分。
  - **自动行高**（1.0.0 与 00 号计划书附录 B 核对时的 rc.0 不同）：
    - 命令内能算的行高，作为命令的 mutation 同步产生；
    - 大范围的行高，由命令附带一个 `onlyLocal` 的 `MarkDirtyRowAutoHeightOperation`，交给 `AutoHeightService` 在空闲回调里计算。算完执行的 `SetWorksheetRowAutoHeightMutation` **不带 `onlyLocal`**（`packages/sheets-ui/src/controllers/auto-height.controller.ts`、`services/auto-height.service.ts:124-189`）。
    - 源码里没有找到"打开文档就触发自动行高"的路径。00 号计划书 §7.3 的"必须排除自动行高"是否还需要，由 V06 的打开数据决定：排除它会漏掉编辑之后迟到的行高变化。
  - **公式**：
    - 结果以 `onlyLocal`、`fromFormula` 写回（`calculate-result-apply.controller.ts:94-95`）；默认计算模式为 `WHEN_EMPTY`，可用 `initialFormulaComputing` 配置（`trigger-calculation.controller.ts:150`）。
    - `onCalculationResultApplied(timeout)` 实际调用 `FormulaCalculationSessionService.waitForLatestApplied`（`packages/engine-formula/src/services/formula/formula-calculation-session.service.ts:202`）：
      - 有进行中的计算时，等它的结果写回；
      - 没有时，先等 500 ms，看有没有新的计算开始；
      - 超时则以 `Calculation end timeout` 拒绝。
    - 所以每次捕获前的等待，至少要算上这 500 ms。
  - **只读**：
    - 表格：
      - `FWorkbook.setEditable(false)` 只更新本地权限点，不产生 mutation。
      - `FWorksheetPermission.setReadOnly()` / `setMode()` **要求工作表先有保护规则**，否则抛错（`f-worksheet-permission.ts:338-375`）。
      - 创建保护规则（`protect()`）会执行 `AddWorksheetProtectionMutation`，并通过授权服务写数据。这正是 P2 规定"必须为空"的保护类资源。
    - 文字文档：`FDocumentPermission.setReadOnly()` 通过 `ObjectPermissionService.setPoint` 生效（`packages/core/src/services/permission/object-permission.service.ts:306-324`）。注册了规则模型的对象类型，会保存一条权限规则，文字文档的规则模型对应资源 `DOC_OBJECT_PERMISSION_PLUGIN`（`packages/docs/src/services/permission/document-permission-rule.model.ts`）。实际是否写入，由 V09 实测。
    - 清空撤销栈：`IUndoRedoService.clearUndoRedo(unitId)`（`packages/core/src/services/undoredo/undoredo.service.ts:69、278`），Facade 没有暴露。
  - **菜单**：
    - 各 UI 插件的 `menu` 配置合并到同一个全局配置里，按菜单项 id、功能区标签或分组的 key 生效（`packages/ui/src/services/menu/menu-manager.service.ts:343-376`）；
    - 运行时可以用 `IMenuManagerService.updateMenuConfig` 修改；
    - 工具栏按钮带 `data-u-command` 属性（`packages/ui/src/views/components/ribbon/ToolbarItem.tsx`）；
    - 保护相关的菜单在 `packages/sheets-ui/src/menu/schema.ts`（工具栏、右键、工作表标签）；工作表背景图片是 `sheet.menu.worksheet-background-image`（`packages/sheets-drawing-ui/src/menu/worksheet-background-image.menu.ts`）。
  - **缩放**：缩放比例由渲染控制器直接写进工作表配置 `zoomRatio`，不产生 mutation（`packages/sheets-ui/src/controllers/render-controllers/zoom.render-controller.ts:47`）。
- **P2 交接给本 Phase 的事项**：
  - `setReadOnly` 是否写保护类资源；设置真实用户身份后，本地授权服务对普通编辑有没有影响；
  - 打开自检的捕获耗时与资源加载错误捕获的开销；
  - 变更检测与"空值等价"：内容比较要先归一化，计算哈希前资源按名称排序；
  - 三个浏览器上的公式 Worker 模式回归；
  - 工作表背景图片的入口：隐藏，还是纳入。
  - 另有 Facade 读取方法的观察者效应：`getDataValidations()` 会在模型里建空条目。

### 3.2 变更检测的候选规则

候选规则来自 00 号计划书 §7.3，由 V06 的数据修订：

1. 监听 `onCommandExecuted`，只看 `MUTATION` 类型；
2. 排除带 `onlyLocal`、`fromCollab`、`fromChangeset`、`fromFormula` 选项的 mutation；
3. 排除作用于其他单元的 mutation：参数里有 `unitId`、但不是本文档的 id，例如表格单元格编辑器内部的文字文档；
4. 排除名单：初始为空，只收录 V06 打开数据中出现、并且确认不改变内容的 mutation。

`syncOnly` 的 mutation 收不到，这是大表复制的漏洞。候选对策有两种，由 V06 选一种：
- 关掉拆分（配置）；
- 监听协同钩子并等待懒执行完成（内部 API）。

### 3.3 实验方案

**V06 变更检测**

1. **打开静默**：
   - **范围**：P2 的全部样本（15 个 SDK 生成、2 个手写）加上大样本（1 MiB、5 万单元格）；三个浏览器；表格另跑 Worker 模式。
   - **做法**：检测器在创建文档单元之前挂上，等到 `Steady` 后再等 5 秒。
   - **判定**：检测到修改的次数为 0。
   - **记录**：全部非 `onlyLocal` 的 mutation 与 `syncOnly` 的 mutation，据此定排除名单。
   - **附带**：在 `Steady` 与 5 秒后各捕获一次并比较内容，列出"没有 mutation 的内容变化"（例如 DEF-002 的派生尺寸、空值等价），写明处置。
2. **动作矩阵**：
   - **范围**：表格约 30 个、文字文档约 12 个用户动作（清单见 `plans/P3-实施计划.md`）。大部分用 Facade 或命令执行（与界面走同一个命令），键盘输入、粘贴、快捷键撤销重做、拖动图片等用真实的键盘鼠标操作。
   - **流程**：每个动作都是 S0 → 执行动作 → 等到检测静默 1 秒、公式结果写回 → 捕获 S1 → 再等 5 秒 → 捕获 S2。
   - **判定**：
     - 改变内容的动作：检测到修改，S1 与 S0 的内容不同；S2 与 S1 相同，或者 S1 之后另有检测；
     - 只改视图的动作（选区、滚动、缩放、切换工作表、查找）：没有检测，内容不变；
     - 撤销与重做：检测到修改，内容回到或前进到对应的状态。
3. **大表复制**：复制一个 5 万单元格的工作表，分默认拆分与关掉拆分两种配置，记录：检测是否漏报、S1 是否完整、关掉拆分后复制时的主线程阻塞。另外核对删除大表的路径。
4. **观察者效应**：确认 P2 发现的 `getDataValidations()` 等读取方法不产生 mutation，因此不会被检测到；它们对下一次保存字节的影响，归入空值等价。

**V07 公式一致性**

1. **场景**（构建器生成）：
   - 依赖链：200 层；
   - 大范围聚合：2 万行上的 `SUM`、`AVERAGE`、`COUNTIF`；
   - 跨表引用；
   - 慢计算：200 个 2 万行的 `SUMPRODUCT`；
   - 易变函数：`NOW`、`TODAY`、`RAND`、`RANDBETWEEN`。
2. **做法**：每个场景在主线程与 Worker 两种模式、三个浏览器下各跑一遍。先修改上游单元格，再分下面四种情况捕获：
   - **不等待**：修改后立即保存。记录快照里的公式值是否过期，用来证明必须等待；
   - **等待**：`onCalculationResultApplied(5000)` 之后保存；
   - **超时**：用很短的超时（例如 50 ms）强制走超时，标记"公式待更新"，等计算结束后补捕获一次；
   - **重开**：用默认计算模式重开，确认显示的值就是快照里的值（不会自动重算）。
3. **判定基准**：用 `calc=forced`（`initialFormulaComputing = FORCED`）打开同一份快照，等计算结束后读出全部公式值。"等待"与"超时补捕获"两种快照的值必须与基准一致；易变函数只核对"快照值 = 捕获时刻的值"。
4. **附带测量**：等待本身的耗时（含 500 ms 的起始等待）；易变函数是否让文档持续产生写回，这些写回不应触发检测。

**V08 捕获成本**

1. **样本**：表格 1 MiB、5 MiB；文字文档 2 万汉字、1 MiB。三个浏览器，每项预热 2 次后测 10 次，取 p50 与 p95。
2. **分段**：`save()`、`JSON.stringify`、gzip（`CompressionStream`）、SHA-256（`crypto.subtle`）的耗时；序列化与压缩后的体积、压缩率。
3. **主线程阻塞**：同步部分（`save()` + 序列化）直接计时；压缩与哈希期间，用 Long Tasks（Chromium）和事件循环延迟探针（三个浏览器）取最长阻塞。
4. **附带**：
   - 打开自检：捕获加资源比较的耗时；
   - 资源加载错误捕获：`guard=1` 与不开时，各打开 5 次，比较耗时；
   - 端到端：从修改停止到压缩与哈希完成，含 1 秒防抖与公式等待。本机写入与加密不在内，留给 P6。

**V09 阅读模式**

1. **候选实现**：

   | 方案 | 表格 | 文字文档 |
   |---|---|---|
   | A：00 号计划书 §6.5 的做法 | `setEditable(false)`，每个工作表 `setReadOnly()`（1.0.0 要求先 `protect()`） | `getPermission().setReadOnly()` |
   | B：本地权限点 | `setEditable(false)`，用 `IPermissionService` 关掉工作表的编辑类权限点，不创建保护规则（内部 API） | 用 `IPermissionService` 关掉文档的编辑权限点（内部 API） |
   | C：mutation 防火墙（兜底） | `BeforeCommandExecute` 取消所有不带 `onlyLocal` 的 mutation | 同左 |

   三种方案都拦截撤销与重做（`BeforeUndo`、`BeforeRedo`）。
2. **动作矩阵**：在阅读模式下逐个执行编辑入口，入口清单见实施计划。
   - **表格入口**：键盘输入、删除、粘贴、剪切、拖动填充、撤销重做（快捷键与工具栏）、筛选排序，增删、重命名、复制、隐藏、移动工作表，拖动、缩放、删除图片，行列的调整、插入、删除，合并，工具栏格式与格式刷，条件格式、数据验证、超链接、备注的编辑，查找替换，编辑栏。
   - **文字文档入口**：输入、删除、粘贴、格式快捷键、列表、表格、拖动图片、撤销重做。

   每个入口记下三种结论之一：
   - 拦截：模型不变；
   - 没有拦截，但被检测到：进入编辑前必须重新加载；
   - 没有拦截，也没有被检测到：不可接受。
3. **痕迹**：每种方案进入阅读模式后，是否产生 mutation，保护类资源与 `DOC_OBJECT_PERMISSION_PLUGIN` 是否变为非空。
4. **模式切换**：比较两种做法：
   - 原地切换：解除只读，并用 `clearUndoRedo` 清空撤销栈；
   - 销毁重建：从存储重新加载。

   记录切换后的状态是否干净、撤销栈是否为空、耗时多少。
5. **入口隐藏**：
   - **隐藏的菜单**：保护相关的全部菜单、阅读模式下的增删工作表，以及工作表背景图片（本期目标能力之外，隐藏）；
   - **核对方式**：在 DOM 中核对对应的 `data-u-command` 不存在；
   - **附带核对**：运行时用 `updateMenuConfig` 切换隐藏是否生效。
6. **P2 交接的身份问题**：用 `setCurrentUser` 设置一个非 `Owner_` 前缀的用户，核对普通编辑、以及含保护规则的样本在编辑模式下的表现。

**V10 性能基线**

1. **样本**：5 万单元格（5,000 行 × 10 列）加 1,000 个公式，包括行合计、跨表汇总、`VLOOKUP`、条件统计。
2. **范围**：三个浏览器；主线程与 Worker 两种模式；每项 5 次。
3. **指标**：
   - 首屏：到 `Rendered`、`Steady`，以及第一次键盘输入被接受的时间；
   - 编辑响应：从按键到 mutation 执行完成、再到下一帧，p50 与 p95；
   - 公式计算：修改被 1,000 个公式依赖的单元格，到结果写回的时间；
   - 内存：Chromium 用 `performance.memory`，分别在打开后与 50 次编辑后读取；WebKit 没有对应的接口，记为"无法测量"；
   - 打开过程中的长任务。

- V08 增加规范化内容哈希的开销，端到端按新捕获时机分三种修改测量（含性能样本）。
- V09 增加编辑模式对照组、阅读模式下复制、图片缩放与拖动行高两个入口、原地退出后经单元格编辑器编辑的核对。"拖动浮动图片"用 Facade 的 `setPositionAsync`（与界面拖动走同一类 mutation）；格式刷、文字文档拖动图片没有单独覆盖，由防火墙按构造拦截（报告 §5.3）。
- V10 增加计算期间主线程的最长阻塞、首次键入、页面与公式 Worker 各自的 JS 堆（CDP），首屏分第一次打开与之后的打开；编辑响应只测 ASCII 按键（汉字经输入法送入、不触发 `keydown`，由 P5 覆盖）。
- 审查之后的复验中发现两处测量问题并修正（`src/harness/perf.ts`）：事件循环探针与 Long Tasks 观察器在"计算刚结束、后续代码与这段长任务同属一个任务"时停止采集，前者漏掉最后一段阻塞，后者把记录算进下一次测量。V10 改为三种口径同时测量冻结（事件循环探针、帧间隔、Long Tasks），并增加主线程模式调小让出间隔（`intervalCount`，页面参数 `interval`）的对比；据此决定表格默认启用公式 Worker（报告 §6.3）。
- V09 的 `combined` 方案在表格的公式 Worker 模式下另跑一遍入口矩阵与原地切换。
- 捕获时机的"逐表收齐"补上一种情况：修改没有牵动任何公式时，这一轮只有完成通知、没有结果 mutation，视为收齐（否则每次都要等到超时）。
- 第二轮审查（S1）后，捕获时机的"收齐"补上两条：最近一轮开始之后又执行过会触发计算的命令（新的一轮还在排队），或这一轮被 stop，都不算收齐。"会触发计算"按 SDK 触发服务的口径判断（`IActiveDirtyManagerService`，内部 API，报告 §7 登记）。V07 新增"计算进行中再改一次"（5 种情形 × 2 种等待起点，新旧规则对照）。
- 第二轮审查（S12）后，V06 动作矩阵的表格动作另跑公式 Worker 模式；V10 的样本改在另一个浏览器上下文里生成（冷启动）；V08 端到端计到哈希完成为止；让出间隔对比补上 Long Tasks。
- 验证工程的端口、构建目录、输出目录可以用环境变量改掉（`playwright.config.ts`），便于并行；性能测量仍须单独运行。

### 3.4 内容比较的口径

- 以 JSON 文本为准（沿用 P2）。资源按名称排序，展开 `data`；只在顶层对资源数据判空，`""`、`{}` 等价（沿用 P2 的 `isEmptyValue`）。
- **视图状态**：工作表的 `zoomRatio`、`scrollTop`、`scrollLeft`，文字文档的 `settings.zoomRatio`。它们不产生 mutation，会随下一次真实修改保存（00 号计划书 §7.3 已接受）。
- 其余任何差异都算内容变化。DEF-002 的派生尺寸也算内容变化，按已登记的 DEF-002 处理。
