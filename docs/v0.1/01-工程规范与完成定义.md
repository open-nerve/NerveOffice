# 工程规范与完成定义

> 文档编号：01｜适用版本：v0.1｜状态：定稿（随 M1 总设计于 2026-09-26 审批通过）｜日期：2026-09-26

本规范约束 v0.1 的全部生产代码与测试，范围是 `apps/`、`packages/`、`tests/`、`deploy/`；`spikes/` 与 `refer/` 不适用。总原则见 `CLAUDE.md` 的"质量底线"：**范围可以延期，质量门槛不能降**。

规则后面的标记：
- 【自动】由工具在本机门禁与 CI 中强制，违反即失败；
- 【测试】由测试用例保证；
- 【审查】由代码审查检查。

能写成工具的规则一律写成工具；写不成的，才依靠审查。

## 1. 仓库与模块边界

### 1.1 目录

目录结构按 00 号计划书 §9.4：`apps/web`、`apps/api`、`packages/contracts`、`tests/{fixtures,integration,e2e}`、`deploy/`，文档在 `docs/`；另有 `tools/`，存放仓库自己的工具（质量门禁、故事对照、提交钩子、`verify`，ADR-003）。`spikes/`、`refer/` 不属于 workspace，不参与 lint、构建与测试【自动】。

### 1.2 依赖方向

- `packages/contracts` 只依赖 zod，不使用 Node 或浏览器特有的 API。web 与 api 之间没有代码依赖，只经 HTTP 与 contracts 协作【自动】。
- **api**：
  - 每个模块只经自己的公开入口（`index.ts`）对外，跨模块的深层引用会失败【自动】；
  - 只有仓储访问数据库，控制器不访问数据库、不写业务规则【自动（导入限制）+ 审查】；
  - 一个模块的仓储只被这个模块使用；需要别的模块的数据时，调用它的服务【自动 + 审查】（M2-P6 起 lint 拦下经任何模块入口引用 `*Repository`；入口里改名导出认不出，靠审查）。
- **web**：
  - `@univerjs/*` 只能在 `src/editor/` 下引用；内部 API（受限符号清单）只能在 `src/editor/internal-api/` 下引用，并逐项登记【自动】；internal-api 之外只经它的两个出口（`index.ts`、`ui.ts`）引用，`@univerjs/*` 的值引用只许公开符号的白名单，登记表的自测扫描 internal-api 的全部文件（清单与目录由 tools 的测试核对，internal-api 里不用动态 `import()`，M2-P6）【自动】；
  - 平台页面的入口不引用 `src/editor/`，编辑器不进入平台页面的包【自动（导入限制 + 产物检查）】；
  - 功能模块之间只经公开入口依赖，共用的代码放在 `src/shared/`【自动】。
- 不允许循环依赖【自动】。
- 新的共享包等出现第二个使用方时再拆（00 号计划书 §9.4）【审查】。

具体的目录名与分层由各 Phase 的设计确定，写入 ADR 与边界配置。

### 1.3 设计原则【审查】

- 单一职责、依赖倒置：业务逻辑依赖接口（仓储、时钟、ID 生成器等），这样才能用假实现做单元测试。
- 从根因解决问题：不在调用方堆特殊判断，不绕过已有的边界，不打补丁、不乱接线。
- 显式优于隐式：配置、错误、状态都有名字和类型；不依赖副作用的执行顺序。
- 不为假想的需求建抽象；但接口要给已经计划好的 M 留出位置，例如 M1 的文档访问策略在 M2 扩展时，调用方不用改。
- 同一类处理（例如"写操作结果未知之后刷新并说明"）先抽成一个共用的做法，再逐处接入；逐处各写各的，会一处一处地漏（M2-P6 第 5 片：同一件事补了四批才覆盖全部写操作）。
- 修复里引入的全局约定（例如"503 等于确定没有生效"），要逐个接口核对它是否处处成立，不能只在引入它的那几处验证（M2-P6 第 3 片：这条约定在提交之后读库的接口上不成立，复验才发现）。

## 2. 代码规范

### 2.1 TypeScript

- 开启 `strict`、`noUncheckedIndexedAccess`、`noImplicitOverride`、`noFallthroughCasesInSwitch`；开启 `skipLibCheck`，因为 Univer 的类型声明自身有错误（M1 总设计 §2.2）；`strict` 管着的那一组检查（`strictNullChecks` 等）不得单独关掉（M2-P6 起由 `tsc --showConfig` 逐份 tsconfig 核对）【自动】。
- 禁止 `any`：外部数据先当作 `unknown`，经 zod 校验后再使用【自动】。
- 禁止非空断言 `!`（测试代码除外）【自动】。
- 禁止 `@ts-ignore`；确实需要时用 `@ts-expect-error`，并写明原因【自动】。
- Promise 必须 `await` 或显式处理，不能悬空【自动】。
- `switch` 必须覆盖联合类型的全部分支【自动】。
- 只用于类型的导入写成 `import type`【自动】。

### 2.2 风格与命名

- TypeScript、JavaScript、JSON 与 YAML 的格式都由 ESLint（@antfu/eslint-config）统一：2 空格缩进、单引号、不写分号，与 opennerve 一致；不用 Prettier，以免两个工具互相改写；Markdown 不自动格式化【自动】。
- lint 不设"警告"级别：一条规则要么是错误，要么关闭，以 `--max-warnings 0` 运行【自动】。
- 命名：
  - 文件名用短横线连接的小写，例如 `document-list-page.tsx`【自动】；
  - React 组件、类型、类用 PascalCase，变量与函数用 camelCase，常量用 UPPER_SNAKE_CASE，数据库对象用 snake_case【审查】。
- 标识符用英文；注释与文档用中文，写"为什么"，不复述代码【审查】。
- 生产代码不使用 `console`，日志一律走 logger；命令行工具与脚本除外【自动】。
- 关掉检查的注释（`eslint-disable`）必须写原因【自动】（M2-P6）。

### 2.3 错误处理

- 业务错误抛出带错误码的错误类型，由统一的异常过滤器映射为 HTTP 状态与错误响应；不抛字符串，不在中途吞掉错误【审查】。
- 错误码在 `packages/contracts` 中集中定义；发布后语义不变，编号不复用【自动（唯一性检查）+ 审查】。
- 意外错误对外只返回通用信息与请求标识，细节只写进日志【测试】。

### 2.4 前端

- 使用函数组件与 Hooks。服务端数据经统一的请求层获取，不在组件里散落 `fetch`【审查】。
- 每个数据视图都处理加载中、空、失败、无权限四种状态。异步操作显示进行中，并防止重复提交【审查 + 测试】。
- 界面只显示真实的状态：只有服务端确认之后，才显示"已保存到云端"（A14）【测试】。
- 不使用 `dangerouslySetInnerHTML`，不注入内联脚本，不从第三方加载任何资源【自动】。
- 界面文字为简体中文，集中管理，不散写在组件里【审查】。
- 可访问性：表单控件有标签；主要操作能用键盘完成；交互元素有可读的名称。E2E 按角色与名称定位元素，顺带检查这一条【测试 + 审查】。
  - M2-P6 起另要求：每个页面有自己的标题（浏览器标签页）；输入不合法时有文字说明并与输入框关联，不只标红或让按钮不可用；操作之后焦点不落到 body（行消失、控件随权限消失时交给稳定的元素）；加载中的状态读屏读得到；文字与背景的对比度不低于 4.5:1【测试 + 审查】。
  - 人名一律经人名组件显示（登录名在前、单独呈现，显示名隔离），纯文字里同样登录名在前，不拼成"显示名（登录名）"一段文字（lint 近似拦下拼接）；个人空间存的名称是所有者建号时的显示名，不对别人显示，按所有者的人名呈现（接口里也不给，M2-P5）；内容会变化的说明与进展用的读屏状态区（`role="status"`）一直在无障碍树里、内容变化时往里填，空的时候只做视觉隐藏，不用 `display: none`（共用的 `StatusRegion`，lint 近似拦下藏起来的写法；随内容一起出现的加载状态不在此列，M2-P5）；确认框里做完一件事的说明由确认的操作交回，等确认框关掉、`aria-hidden` 解除、焦点交还之后再写（模态弹窗打开时，它之外的内容都在 `aria-hidden` 之下，只有打开那一刻已经在的、显式写了 `aria-live` 的元素除外，这时写进状态区的读屏不播报；`ConfirmDialog` 的共用做法，M2-P5）；模态弹窗开着时也可能变化的、弹窗之外的状态（后台完成的保存这一类，不是弹窗里的操作引起的）：常驻的状态元素显式写 `aria-live`，遮罩跳过它，结果照样播报；随之出现的详细说明留在页面上，弹窗关掉之后读得到（编辑器页头的保存状态，M2-P5）；按需加载的页面加载失败时有自己的说明与重试；写操作"结果未知"之后走共用的做法（M2-P6）；写操作成功之后的刷新同样有时限（`refreshAfterSuccess`，与失败之后同一个时限），到了时限操作照常结束（弹窗关掉、说明写出、焦点交还），说明里说列表还在刷新；界面要依赖刷新结果才对的（例如取消之后那一行要先消失），先按确定的写入结果改缓存再刷新；列表留着旧数据、刷新却失败时明说"没能刷新"、给出重试（共用的 `RefreshProblem`，Codex 评审 CX4、CX5）；详情（页头、面板里取的权限等）同样如此，用详情的变体 `DetailRefreshProblem`：403、404 与 id 不合法由页面按访问状态处理，不说成"没能刷新"（M3-P2，DEF-040）；说明连同重试按钮消失时，焦点交给一直在的元素（`fallbackFocus`），不落到 `body`【测试 + 审查】。

### 2.5 编辑器适配层

- 适配层是 SDK 与平台之间唯一的边界（00 号计划书 §9.4、§10.1），对外只暴露平台需要的入口【自动 + 审查】。
- 插件档案是数据：插件清单、注册顺序、影响数据的配置、资源白名单。改动档案按数据格式变更处理（§8.7）【审查】。
- 优先使用公开的稳定 API。内部 API 集中封装并登记，每一项都有回归用例【自动（受限导入）+ 审查】。
- 不修改 `node_modules`；补丁只用 `pnpm patch`，并登记（§10.3）【自动（补丁清单检查）+ 审查】。
- 锁定 SDK 行为的对照用例（M0 交接的规避做法）放进 E2E，升级 SDK 时先跑【审查】。

## 3. 依赖管理

- 外部依赖的版本集中写在 `pnpm-workspace.yaml` 的目录（`catalog`）里，一律是精确版本，不用 `^` 或 `~`；各包写 `catalog:`，内部包写 `workspace:*`。锁文件入库，CI 用 `--frozen-lockfile` 安装【自动】。
- 版本基线的原则与清单见 M1 总设计 §2.2 及对应的 ADR。同一条主次版本线内的补丁可以随时升级，尤其是安全修复；跨主次版本的升级，要更新 ADR【审查】。
- 新增依赖要说明必要性：平台 API 能做的，不引入依赖；要有人维护【审查】。
- 许可【自动】：
  - 生产依赖只接受白名单：MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、0BSD，其他许可逐个评审后加入白名单；
  - 开发依赖不得出现 GPL、AGPL、SSPL 与没有声明许可的包。
- Univer【自动 + 审查】：
  - 全部 `@univerjs/*` 使用同一个精确版本；禁止 `@univerjs-pro/*`；
  - react、react-dom、rxjs、`@wendellhu/redi` 与每个 `@univerjs/*` 包都只有一份实例；
  - 只在 Phase 边界升级，并按 00 号计划书 §8.7 回归。
- 供应链【自动】：
  - pnpm 配置 `minimumReleaseAge`，新发布的版本满 3 天才允许安装。豁免名单的变更在提交说明里写明原因；
  - 只有白名单中的包可以执行安装脚本；
  - CI 做依赖漏洞扫描。生产依赖出现高危或严重漏洞时失败，在当前 Phase 内处理：升级、替换，或者登记例外并写明缓解措施。
- 第三方许可清单随构建产物生成，随部署包分发；缺少许可正文的包要补齐（00 号计划书 §3.3）【自动】。

## 4. API 与契约

- 使用 REST + JSON，统一前缀 `/api`。请求与响应的结构用 zod 定义在 contracts；服务端对每个输入做运行时校验，并限制体积、嵌套深度与数量。TypeScript 类型不能代替运行时校验（§11.2）【自动（校验管道）+ 审查】。
- 错误响应统一为 `{ "error": { "code", "message", "requestId" } }`，每个错误码对应固定的 HTTP 状态。没有读取权限的对象与不存在的对象返回相同的响应（§5.5）【测试】：带 id 的接口与路由表对照，要么在"看不到与不存在"的核对里、要么写明豁免（M2-P6）【自动】。
- 写操作可以安全重试：新建与保存带客户端生成的 `requestId`，相同的请求返回原来的结果【测试】。"相同"按新建时存下的不可变请求摘要判断，不按对象现在的样子：改名、移动之后原样重试仍是重放（文档的新建、复制与保存一直如此，文件夹的新建自 M2 Codex 评审 CX6 起）。新建（文档、文件夹）与复制先查重放，再看这次请求的目标：重放按对象现在所在的位置判断还看不看得到，看不到（包括进了回收站）时是请求标识冲突；保存先判断地址里的文档，看不到时是 404。
- 并发控制用修订号做条件更新，不在应用层"先读再写"地判断【审查 + 测试】。
- 时间使用 ISO 8601 的 UTC 格式；ID 使用 UUID，不暴露自增序号【审查】。
- 令牌不出现在 URL、日志与错误信息中【审查 + 测试】。

## 5. 数据库与迁移

- 迁移由 Drizzle 生成 SQL，人工审阅后入库。合并到 main 的迁移不再修改，只向前；破坏性变更分成"扩展 → 迁移数据 → 收缩"几步发布【自动（与合并前的版本比较，门禁 `migrations`）+ 审查】。
- 迁移用单独的命令执行，并用 advisory lock 防止并发执行。应用启动时只检查库结构的版本，不一致就不就绪【测试】。
- 命名与类型：表名用复数的 snake_case；时间用 `timestamptz`；枚举用 `text` 加 CHECK 约束；外键写明删除时的行为【审查】。
- 事务：
  - 多条语句的写入放进显式事务，按统一的顺序加锁；
  - 事务里不做网络调用，事务尽量短；
  - 与时间有关的判断使用数据库时间（M2-P6 起 lint 禁止后端用 `Date.now()` 与不带参数的 `new Date()`，进程自己的计时按文件放行）【自动 + 测试】；
  - 登录之后的读请求（全部 GET 接口）在一个只读快照里判断权限、读数据（`TransactionRunner.readSnapshot`，REPEATABLE READ、READ ONLY）：快照在最外层的服务里开，内层方法接受事务参数，不嵌套；会话守卫判断过的会话、账户有效与系统角色由快照的开场核对在快照里再查一次（ADR-017，M2 Codex 评审 CX1）。快照进行中连接池上的查询一律报错（读方法漏传快照的事务、直接用连接池的写法都在内），集成测试另按路由表核对每个 GET 接口恰好一个快照【自动 + 测试】；
  - 同一个事务或快照上的语句逐条 await，不用 `Promise.all` 并发：pg 在一个连接上排队执行查询的做法已经弃用（pg 9 去掉）。集成测试在每条用例之后核对应用的连接上没有并发过查询【自动】。

  【审查 + 测试】
- 只用参数化查询；动态的 SQL 片段只能来自代码里的白名单【自动（限制原始 SQL 的拼接）+ 审查】。
- 数量没有上界的一串 id 作为**一个数组参数**传给数据库（`= ANY($1::uuid[])`，documents 模块用 `inIdArray`），不要逐个展开成 `IN (…)` 的参数：绑定参数最多 65535 个，超出时语句失败（M2-P6）【审查 + 测试】。documents 与 users 的仓储由 lint 禁用 `inArray`、`notInArray`（users 自 M2-P5 起）；在 `sql` 模板里直接插入数组、用 `sql.join` 拼列表同样会逐个展开参数，lint 拦不住，审查时点名看。

## 6. 安全

按 00 号计划书 §11，每次改动都要满足：

- 每个请求都在服务端做认证与授权，默认拒绝。每个新接口都要有"未登录""无权限"两类反向测试【测试】；未登录的一类由路由表覆盖全部接口（公开清单之外的未登录一律 401，M2-P6）【自动】。
- 会话 Cookie 设置 HttpOnly、Secure、SameSite；状态变更接口做 CSRF 防护与 Origin 检查【测试】。
- 密码只存 Argon2id 哈希；各种令牌只存摘要【审查 + 测试】。
- CSP 与安全头随所有响应下发，包括 Worker 脚本。不放宽定稿的策略；确需放宽时，先写 ADR【测试】。
- 日志与审计不包含密码、令牌、本机密钥和快照正文【测试（脱敏配置）+ 审查】。
- 请求体与上传都有体积上限；解压时限制解压后的体积，防止压缩炸弹【测试】。

## 7. 日志、审计与运维

- 日志：
  - 为 JSON 格式，至少包括时间、级别、请求标识、用户（有会话时）、路由、状态码、耗时；
  - 敏感字段在 logger 层统一脱敏。
  - 意外错误里的 SQL 截断到 4096 个字符（注明已截断与总长），参数不写进日志、只记个数（M2-P6）。

  【测试】
- 请求标识：一律由服务端生成（UUID），写进响应头、日志、错误响应与审计；客户端带来的 `X-Request-Id` 不当作请求标识，合法时只在日志里另记一个字段 `clientRequestId`，用来对上客户端那边的记录【测试】。
- 审计事件只追加，事件类型在 contracts 中枚举。M1 起记录：登录成功与失败、退出、初始化管理员、新建文档【测试】。
- 配置全部来自环境变量，机密也可以用文件注入；启动时校验，缺失或非法时退出。只有配置模块读取 `process.env`【自动】。
- 进程收到 SIGTERM 后：停止接收新请求，处理完在途请求，关闭连接池，然后退出；有超时兜底【测试】。
- 存活探针与就绪探针分开。就绪探针检查数据库连通与库结构版本【测试】。

## 8. 测试

### 8.1 分层

| 层 | 工具 | 位置 | 覆盖什么 | 约束 |
|---|---|---|---|---|
| 单元 | Vitest | 与源码相邻的 `*.test.ts(x)` | 纯逻辑、领域规则、组件行为，以及适配层中不依赖浏览器渲染的部分 | 不访问网络与数据库；依赖用假实现；时间与随机数可控 |
| 集成 | Vitest + 真实的 PostgreSQL 18 | `tests/integration/**/*.test.ts` | 仓储与事务、并发与条件更新、经真实 Nest 应用的 HTTP 接口、迁移从零执行、启动与退出 | 每个测试文件使用独立的数据库；不 mock 数据库 |
| E2E | Playwright | `tests/e2e/specs/<模块>/*.spec.ts` | 每个用户故事的完整链路；安全头与 CSP；锁定 SDK 行为的对照用例 | 跑生产构建；按角色与名称定位；不用固定时长的等待；不用设备预设 |

- 每个用户故事至少有一条 E2E，用例标题以故事编号开头，例如 `US-M1-05 …`。各 M 的故事累计登记在 `tests/stories.json`（归属的 Phase、状态、验证方式；列出已开始的各份 M 总设计），与这些总设计、测试标题自动对照，缺了就失败【自动】。之前 M 的故事保持登记，它们的测试作为回归继续执行（M2-P1 起）。
- 每个接口至少有四类集成测试：正常路径、校验失败、未登录、无权限（或不存在）【审查】。
- 修复缺陷时，先写能复现它的测试【审查】。
- 集成测试的库在删除之前扫一遍没有写进数据库约束的不变量（例如回收站的文件夹下没有正常的东西、行与父文件夹同一个空间），有违反就让这个文件失败；用例自己造出的违反要在结束前收拾干净；扫描的每条查询先排序再取前几行（结果确定），扫描出错时照样删库（M2-P6）。并发的用例用 `support/held-lock.ts` 构造确定的交错：持锁 → 等请求停在锁上 → 改数据、提交（`raceAgainstHeldLock`，前提是应用等锁的时限远长于这段操作；提交之前辅助函数自己核对被测的请求还没有结局、仍在锁上等，不成立就报"前提不成立"，M2-P6 第 6 片）；预期在最后一步遇到繁忙时用 `cancelWhenWaiting` 取消等锁的语句，不等满时限（M2-P6）【自动】。
- 性能测试单独运行，不进默认套件；结果要记录环境与样本【审查】。

### 8.2 浏览器矩阵

全部 E2E 都在下列浏览器上跑：

- 本机：Playwright 自带的 Chromium 与 WebKit、Google Chrome；
- CI（Linux）：同上，另加 Microsoft Edge。

Edge 与 Chrome 是同一个内核，在本机再跑一遍基本是重复，安装还要管理员权限，所以只在 CI 上跑，每次推送 main 都覆盖。真实 Safari 的复核按延期登记，在对应的 M 进行。

### 8.3 覆盖率

- 单元与集成测试合计的行覆盖率下限：`packages/contracts` 90%，`apps/api` 80%，`apps/web` 中编辑器适配层以外的部分 70%。编辑器适配层以 E2E 为主，其中的纯逻辑做单元测试【自动】。
- 覆盖率是底线，不是目标。审查看的是关键分支与反向路径有没有测到【审查】。

### 8.4 稳定性

- 不稳定的测试按缺陷处理：
  - 单元与集成测试不重试；
  - CI 中的 E2E 最多重试 1 次，出现重试就记为不稳定，在当前 Phase 内修掉根因；M2-P6 起 CI 上出现重试即让这个 job 失败（原来只出报告、job 仍然成功，M2-P6 第 2 片合并时的一次不稳定跨了三片没人发现）。
  - 计时类的测试（比较两条路径的耗时）按交错的轮次取样，比较计算量（进程的 CPU 时间）或墙上耗时的下四分位，不比较两组墙上耗时的中位数：负载一阵一阵地把个别请求拉长几倍，墙上耗时的中位数跟着变；量计算量时先核对确实量到了要量的东西（M2-P6 第 6 片合并之后的 CI，登录耗时的测试）【审查】。

  【自动】
- 不允许 `.only`。用户故事的用例不允许跳过；其他用例临时跳过时，要写明原因，并在当前 Phase 内恢复【自动】（M2-P6 起 `skipIf`、`runIf`、用例里的 `skip()` 一并拦下；"在当前 Phase 内恢复"靠审查）。

## 9. 质量门禁

| 门禁 | 时机 | 内容 |
|---|---|---|
| 提交钩子（lefthook） | 每次提交 | 改动文件的 lint 与格式修正；从提交说明中去掉 AI 署名 |
| `pnpm verify`（本机） | 合并到 main 之前 | 格式、lint、类型检查、单元、集成（真实 PostgreSQL）、构建、依赖与产物检查（A01）、覆盖率、E2E（本机的三个浏览器） |
| CI（GitHub Actions，Linux） | 推送 main 之后；每周定时一次 | 与 `pnpm verify` 相同，另加依赖漏洞扫描；从 M1-P5 起，还要构建镜像并对容器化的环境跑 E2E。从 M2-P4 起分成几个 job 并行：`verify`（除 E2E 之外的步骤，`--scope=no-e2e`）、`e2e`（按浏览器分片，每片 `--scope=e2e`）、`container`。分片合起来与本机的一条 `pnpm verify` 步骤相同（`tools/src/verify/plan.test.ts` 守住，门禁的三步合起来恰好是全部门禁；`ci.yml` 的实际接线由 `ci-workflow.test.ts` 核对：分片、浏览器矩阵与容器 E2E 的 job，执行检查的 job 与步骤不带条件、不改 `CI` 与浏览器，M2-P6），全部 job 通过才算全绿；E2E 出现重试即让 job 失败 |

- main 上的 CI 失败时，先修复，再做其他工作。
- 门禁不能被绕过：不用 `--no-verify` 跳过钩子，也不临时关闭检查项。检查项本身有问题时，修正检查，并在提交说明里写明。

## 10. 完成定义

### 10.1 Step

- 代码与对应的单元、集成测试完成，并且全部通过；
- lint 与类型检查通过；
- 提交，说明用中文。

### 10.2 Phase

- Phase 设计文档中的 Step 全部完成，文档与实际一致；
- 本 Phase 负责的用户故事，E2E 在 §8.2 的浏览器上通过（本机三个，CI 另加 Edge）；
- `pnpm verify` 通过；
- 代码审查（优先由独立的审查者进行）→ 修复 → 复验，报告写入 `reviews/`；
- 架构总览与 ADR 已更新；交接单写入 `handoffs/`；延期项已登记；
- 以 `--no-ff` 合并到 main；推送后 CI 通过。

### 10.3 M

- 总设计的退出条件全部满足；
- 负责的上线门槛都有可以复核的测试结果；
- 打 tag。

### 10.4 面向用户的功能

每个面向用户的功能，都要满足：

- 服务端授权默认拒绝，并有反向测试；
- 输入经过运行时校验，错误有错误码；
- 需要审计的操作写入审计；
- 界面状态完整而真实：加载中、空、失败、无权限、进行中；不显示虚假的成功；
- 日志不含敏感信息；
- 对应的用户故事有 E2E。

"页面能打开""编辑器能输入"不是完成标准（00 号计划书 §13.2）。

### 10.5 代码审查的清单

- 正确性与边界条件；
- 安全（§6）；
- 模块边界（§1）；
- 测试是否覆盖关键分支与反向路径；
- 错误处理与界面状态；
- 日志与审计；
- 文档与 ADR 是否同步；
- 每条修复都做变异验证：临时改坏 → 跑对应的测试 → 还原，存活的变异就是缺口；变异里要包括"测试的前提失效"这一类（例如按法换算出错、读取器读不出时返回空、等待的时限比测试的操作还短、去掉一处重复的检查之后另一处其实没在执行），回归用例要能证明自己确实测到了（M2-P6）；
- 复验者写的、能复现问题的用例，移进仓库作为回归用例（M2-P6）；
- 修复里引入了新的机制（例如换令牌、会话确认、请求级的提交记录），这一批另请一位复验者只看它（M2-P6）。

## 11. 性能与体积预算

- 每个前端入口的首屏 JS（gzip）都有预算，超出即失败【自动】。预算在建立这个入口的 Phase 中定下，表格编辑器在 M1-P4；调整预算要在 Phase 设计中写明原因。
- 体积之外，平台页面的首屏文件数也有上限（2 个）：共用模块经桶文件被另一个入口一起引用时，打包会悄悄多拆出小块，体积还在预算内，门禁原来发现不了（M2-P6）【自动】。
- 服务端的请求超时、请求体上限与连接池大小都有配置项与默认值。00 号计划书 §12.2 的性能目标在 M7 压测，之前各 Phase 记录基线【审查】。
