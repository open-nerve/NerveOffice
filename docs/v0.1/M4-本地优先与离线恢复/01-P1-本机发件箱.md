# M4-P1 本机发件箱：架构设计与实施规划

> 状态：进行中｜日期：2026-10-09｜基于代码版本：`fc4868ff`

## 1. 目标与范围

对应 M4 总设计 §5 的 P1：草稿可靠地写进浏览器、加密、能读回；在真实浏览器上确认存储与 Worker 的行为。本 Phase 交付底座，不接入编辑器页的保存管道（P2）。它不单独交付完整的用户故事，为 US-M4-01、04、05、06、10、11 打底，验收见 §8。

**范围内**：
1. 真实浏览器的前置复核：DEF-009 中断电之外的各项、DEF-011、DEF-012 的部件部分（§3.6）。
2. 契约：发件箱的保留期常量；服务端修订记录保留期的下限由它推出。
3. 记录、AAD、编解码与写入者的判定（纯逻辑）。
4. IndexedDB 的存储：库与三个对象仓库（草稿、写入者、恢复的提示）、写入栅栏、草稿序号、只删到已确认的序号、写满、按用户列出与清理、保留期、列表索引。
5. 写入管道与发件箱 Worker：与放置无关的写入管道，Worker 的协议、处理、入口与客户端，空定时器，出错不挂住。
6. 本机密钥的客户端：取用、导入、清零、保管者与失败的口径。
7. 崩溃工具：持久化的浏览器目录、结束整棵浏览器进程、以同一个目录重开（macOS 与 Linux）；写入中途结束进程的原子性用例。
8. 测试构建里的探针，以及门禁、lint 的登记。
9. OPFS 的冗余（§3.8，S9）：Chromium 在崩溃重开时可能删掉整个来源的 IndexedDB（S7 的调查），同一份记录镜像进 OPFS，删库之后从它恢复并如实告知。

**不在本 Phase**：
- 接入保存管道、页头、离线、密钥版本变化时换钥匙的触发（P2）；
- 恢复与标签页接手（P3）；
- 本机草稿页、列表的标记、清理的入口、会话失效的原因（P4）；
- 公式 Worker 的退路（P5）；
- 断电实验、DEF-069（P6）。

**与总设计的偏差**（本 Phase 定下的细化，收尾时回写总设计、计划书与 ADR）：
1. **崩溃工具从 P3 提前到 P1**：P1 的验收要"写入中途结束进程时的原子性"。P3 沿用这套工具。
2. **写入者不存租约令牌**：
   - 存这一代的 `writeEpoch` 与每次登记随机生成的 `writerId`。总设计写的"代次与这一代的令牌"，这里的"令牌"就是 `writerId`。
   - 租约令牌只在标签页的内存里（ADR-018），不进浏览器的存储。
3. **在途的请求只记请求标识、客户端实例、序号与发出时刻**：
   - 原样重放只在"记录还是在途的那一份"时做（§3.4.5），这时公式标记、构建与数据格式就是记录本身的，不必另存。
   - 计划书 r21 §7.5 的字段表随之订正（§8）。
4. **草稿序号的高水位放在写入者记录里**：登记时交回；写入的事务里要求序号单调；草稿删掉之后高水位还在，序号不回头。
5. **不覆盖别的写入者留下、还没接手的草稿**：这是存储层的不变量，把"拿不准的一律给副本"兜在最底层。接手要显式进行（§3.4.3，P3 用）。
6. **新 Worker 的体积预算在 P2 登记**：门禁读的是生产构建，P1 的生产构建里还没有这个 Worker；P1 只在测试构建里量出体积，记进复核报告。
7. **M0 的部分数字要重测**：Playwright 默认的浏览器上下文不落盘——Chromium 是无痕式的上下文，WebKit 用临时存储。M0 的写入耗时、`strict` 的开销、写满的结论都是在内存里的 IndexedDB 上测的。P1 在持久化的浏览器目录与真实 Safari 上重测，按结果订正计划书 §7.5、§7.6、§12.2 的相应说法。
8. **不引入 fake-indexeddb**：
   - IndexedDB 的事务在三个浏览器的浏览器层测试里测；判定逻辑是纯函数，在单元测试里测。
   - IndexedDB 的接线（`database.ts`、`draft-store.ts`）与 Worker 的薄入口不计入单元覆盖率，理由与编辑器适配层相同（规范 §8.3），在 `vitest.config.ts` 的排除项里写明。
9. **加了 OPFS 的冗余**（§3.8）：S7 的调查发现 Chromium（含 Google Chrome）崩溃重开时可能删掉整个来源的 IndexedDB，需求方 2026-10-09 决定"OPFS 冗余 + 如实告知"。总设计、计划书 §7.5、§7.6、§7.8 与 ADR-020 随之补写。

- **保存管道（M3）**：
  - 两级的自动保存；捕获进内存里的"最近一次捕获"（`features/sheet-editor/autosave.ts:309-311`）。

```ts
// shared/outbox/draft-record.ts
export const DRAFT_RECORD_VERSION = 1
export interface DraftKey { readonly userId: string, readonly documentId: string }   // 平台的文档 id，不用 unitId

/** 写下内容的页面的构建与数据格式（计划书 §8.7） */
export interface ContentFormat {
  readonly clientBuild: string, readonly univerVersion: string, readonly profile: string, readonly formatVersion: number
}

/** 在途的保存：认"记录就是在途的那一份"与"自己追自己" */
export interface InFlightSave {
  readonly requestId: string
  readonly clientInstanceId: string
  readonly localSeq: number            // = 那次上传的草稿序号
  readonly sentAt: number              // 墙上时间（毫秒）：原样重放只在保留期以内做
}

/** 明文元数据：全部进 AAD */
export interface DraftMeta extends DraftKey {
  readonly recordVersion: number       // = DRAFT_RECORD_VERSION
  readonly draftSeq: number
  readonly baseRevision: number
  readonly writeEpoch: number          // 写下它的那一代
  readonly writerId: string            // 写下它的那次登记
  readonly writtenBy: string           // 写下它的客户端实例（同一标签页意外重新载入时认"是不是上一个实例写的"，P3）
  readonly format: ContentFormat
  readonly formulasPending: boolean
  readonly keyVersion: number
  readonly inFlight: InFlightSave | null
  readonly rawBytes: number            // 解压后的字节数
  readonly updatedAt: number           // 墙上时间（毫秒）
}

/** 存进去的：字节，不是 Blob */
export interface StoredDraft extends DraftMeta { readonly iv: Uint8Array, readonly ciphertext: Uint8Array }

/** 这份文档当前的写入者（不存租约令牌） */
export interface WriterRecord extends DraftKey {
  readonly writeEpoch: number
  readonly writerId: string            // 每次登记 crypto.randomUUID()
  readonly lastDraftSeq: number        // 草稿序号的高水位
  readonly registeredAt: number
}

export type ReadDraft =
  | { readonly kind: 'draft', readonly draft: StoredDraft }
  | { readonly kind: 'newer-format', readonly recordVersion: number }   // 更新的页面写的：不动它
  | { readonly kind: 'malformed' }
```

// shared/outbox/writer-fence.ts（纯函数，单元测试的主体）
export interface WriterIdentity { readonly writeEpoch: number, readonly writerId: string }

/** force：本页刚经服务端核对确认这一代是当前的（锁的争用以服务端的事实裁决，ADR-018）——任何现存的写入者都已陈旧 */
export function decideRegistration(writer: WriterRecord | undefined, draft: DraftMeta | undefined,
  incoming: WriterIdentity, force: boolean):
  | { readonly kind: 'register', readonly lastDraftSeq: number }    // max(旧写入者的高水位, 现有草稿的序号)
  | { readonly kind: 'superseded', readonly currentEpoch: number, readonly sameEpoch: boolean }

/** adoptSeq：接手别的写入者留下的那一份草稿（调用方确实看过它，P3 的恢复用） */
export function decideWrite(writer: WriterRecord | undefined, draft: DraftMeta | undefined,
  incoming: WriterIdentity & { readonly draftSeq: number, readonly adoptSeq?: number }):
  'ok' | 'duplicate' | 'not-writer' | 'stale-seq' | 'foreign-draft'

/** 重封（标记在途、换密钥、确认之后改基准）：仍是 expectedSeq 那一份、写入者仍是它 */
export function decideReplace(writer: WriterRecord | undefined, draft: DraftMeta | undefined,
  incoming: WriterIdentity & { readonly expectedSeq: number }): 'ok' | 'not-writer' | 'changed'

/** 服务端确认了 confirmedSeq：不大于它的删掉；更新的改基准、清掉在途 */
export function decideConfirm(writer: WriterRecord | undefined, draft: DraftMeta | undefined,
  incoming: WriterIdentity & { readonly confirmedSeq: number }): 'delete' | 'rebase' | 'absent' | 'not-writer'

export function isExpired(meta: Pick<DraftMeta, 'updatedAt'>, now: number): boolean          // 超过 14 天
export function canReplayAsSent(meta: DraftMeta, now: number): boolean                         // 在途的就是这一份，并且发出不满 14 天

export type StoreWriteOutcome =
  | { readonly kind: 'written' }
  | { readonly kind: 'fenced', readonly reason: 'not-writer' | 'stale-seq' | 'foreign-draft' | 'changed' }
  | { readonly kind: 'quota' }                         // QuotaExceededError：put 上或提交时，整个事务回滚
  | { readonly kind: 'failed', readonly error: unknown }

export interface DraftStore {
  readonly registerWriter: (key: DraftKey, writer: WriterIdentity, options: { readonly now: number, readonly force: boolean }) => Promise<
    | { readonly kind: 'registered', readonly lastDraftSeq: number, readonly existing: ReadDraft | undefined }
    | { readonly kind: 'superseded', readonly currentEpoch: number, readonly sameEpoch: boolean }
    | { readonly kind: 'failed', readonly error: unknown }>
  readonly writeDraft: (draft: StoredDraft, writer: WriterIdentity, options?: { readonly adoptSeq?: number }) => Promise<StoreWriteOutcome>
  readonly replaceDraft: (draft: StoredDraft, writer: WriterIdentity, expectedSeq: number) => Promise<StoreWriteOutcome>
  readonly confirmDraft: (key: DraftKey, writer: WriterIdentity, confirmedSeq: number, rebased: StoredDraft | undefined) =>
    Promise<'deleted' | 'rebased' | 'absent' | 'fenced' | 'needs-rebase'>
  readonly readDraft: (key: DraftKey) => Promise<ReadDraft | undefined>
  readonly listDrafts: (userId: string) => Promise<readonly DraftMeta[]>          // 元数据，不交出密文
  readonly removeDraft: (key: DraftKey, expectedSeq?: number) => Promise<'removed' | 'changed' | 'absent'>   // 用户的决定：不核对写入者
  readonly removeUserData: (userId: string) => Promise<void>                      // 草稿与写入者一起删
  readonly purgeExpired: (now: number) => Promise<readonly DraftKey[]>            // 不论属于谁；写入者一并清
  readonly close: () => void
}

type HostProblem =                        // 管道这一侧的问题：没有密钥、库不可用、未知的错误
  | { readonly kind: 'no-key' } | { readonly kind: 'unavailable', readonly reason: string }
  | { readonly kind: 'failed', readonly error: { readonly name: string, readonly message: string } }
export type RegisterResult =
  | { readonly kind: 'registered', readonly lastDraftSeq: number, readonly existing: DraftRead | undefined }   // 现有草稿已解封或归类
  | { readonly kind: 'superseded', readonly currentEpoch: number, readonly sameEpoch: boolean } | HostProblem
export type ConfirmResult = { readonly kind: 'deleted' | 'rebased' | 'absent' } | { readonly kind: 'fenced' } | HostProblem

export interface DraftWriter {
  readonly register: (key: DraftKey, writer: WriterIdentity, force: boolean) => Promise<RegisterResult>
  readonly write: (capture: CaptureToWrite) => Promise<CaptureWritten>
  readonly markInFlight: (key: DraftKey, writer: WriterIdentity, inFlight: InFlightSave) => Promise<StoreWriteOutcome>
  readonly confirm: (key: DraftKey, writer: WriterIdentity, confirmedSeq: number, revision: number) => Promise<ConfirmResult>
  readonly read: (key: DraftKey) => Promise<DraftRead>
  readonly remove: (key: DraftKey, expectedSeq?: number) => Promise<'removed' | 'changed' | 'absent'>
  readonly setKey: (key: LocalKeyHandle | undefined) => Promise<void>   // 换了版本：重封本页写下的草稿（CAS）
  readonly seedDigest: (key: DraftKey, digest: string | undefined) => Promise<void>   // 恢复之后去重的起点
  readonly dispose: () => void
}

### 3.3 数据模型

**IndexedDB**：库 `nerve-office-outbox`，版本 1。三个对象仓库，键路径都是 `['userId', 'documentId']`，没有索引：
- **`drafts`**：`StoredDraft`。
- **`writers`**：`WriterRecord`。
- **`notices`**：`RecoveryNotice`，恢复的提示（S9 加，§3.8）：种类（`restored` 已从备份恢复、`lost` 因浏览器存储损坏丢失）与留下的时刻；一份文档一条，后来的盖掉先前的。

某个用户的全部记录用键范围 `IDBKeyRange.bound([userId], [userId, []])` 取（IndexedDB 的键序里数组排在字符串之后）。结构以后有变，只做加法的升级。

**记录格式**：
- `recordVersion = 1`；比本页认识的新 → `newer-format`，不动它。
- IV 每条 12 字节、随机；AES-GCM 的认证标签 128 位。
- 密文是 gzip 之后的快照字节。

**AAD**：UTF-8 的 JSON 数组。第一项是格式标识 `"nerve-office/outbox-draft/v1"`，之后按字段表的固定顺序排列 `DraftMeta` 的每一个字段（`format` 与 `inFlight` 各展开成固定顺序的子数组；`inFlight` 为空时是 `null`）。字段表在类型上核对与 `DraftMeta` 的键一一对应：加字段而忘了进 AAD，类型检查就过不了。

**契约**：`packages/contracts/src/documents/local-drafts.ts` 导出 `LOCAL_DRAFT_RETENTION_DAYS = 14`（照 `TRASH_RETENTION_DAYS` 的写法，不引用 zod）。服务端修订记录保留期的下限改为 `LOCAL_DRAFT_RETENTION_DAYS + 1`，数值仍是 15。

**服务端**：不改数据模型。

### 3.4 关键流程

**3.4.1 打开与升级**
- 没有 `indexedDB`、没有 `crypto.subtle`（非安全上下文）→ `unsupported`。
- 打开出错 → `denied`。
- `VersionError`（库被更新的页面升级过）→ `newer-version`。
- 等升级超过时限 → `blocked`。

这几种都交回"不可用"及原因，由调用方退化为内存实现（P2）。连接上 `versionchange` 时立即关闭，让别的标签页的升级继续；连接被浏览器断开（Safari 的已知问题"Connection to Indexed Database server lost"）时重开一次，写入的重试是幂等的（§3.4.3 的 `duplicate`）。

**3.4.2 登记写入者**

取得编辑权并拿到本机锁之后（P2 接），在 `[drafts, writers]` 的 strict 事务里：
- 没有写入者，或者现有写入者的代次更小 → 登记，交回高水位 = max(旧写入者的高水位, 现有草稿的序号)，并交回现有草稿（有就由 P3 决定恢复）。
- 代次更大，或代次相同而 `writerId` 不同 → `superseded`（交回当前的代次）。
  - 调用方向服务端核对：本页这一代确实是当前的，就以 `force` 重新登记——现存的写入者必然陈旧。例如服务端从备份恢复之后代次倒退，或同一个页面重建了 Worker。
  - 不是当前的，就按 ADR-018 处理（失去编辑权，或者交给租约的失效处理）。

**3.4.3 写入**
1. 主线程：`save()`、序列化、编码一次；在同步段里从高水位往上分配草稿序号；字节转移给写入管道。
2. 管道（Worker 或主线程）：
   - 去重：SHA-256 与上次写入的相同、并且这次允许去重 → `unchanged`。序号留下空号，没关系。
   - gzip。
   - 加密：AAD 由这次的元数据生成，`updatedAt` 取这一刻。
3. 存储，一个 strict 事务（事务里不 await 加密与压缩）：读写入者与草稿 → `decideWrite`：
   - `ok` → 写草稿、把高水位抬到这个序号；
   - `duplicate`（同一写入者、同一序号，提交了而回应丢了的重试）→ 按已写入；
   - `not-writer`、`stale-seq` → 不写；
   - `foreign-draft`：现有的草稿是别的写入者留下的，这次又没带上 `adoptSeq`（接手的那一份的序号）→ 不写。
4. 写成功之后，gzip 的字节交回主线程上传（P2）；管道记下这份文档最新的元数据与 gzip，供重封用。

**3.4.4 重封**

记录的明文元数据变了，就要换 AAD 重封：密文按新的 AAD 与新的 IV 重新加密（同一把密钥不重用 IV），再在 strict 事务里按 `decideReplace` 比较并交换——草稿仍是 `expectedSeq` 那一份、写入者仍是它才写。管道手里没有最新的 gzip（例如刚恢复）时，先解开现有的记录。需要重封的有三种：
- **标记在途**：上传发出之前写下 `inFlight` 与 `updatedAt`。必须先落盘再发请求，崩溃之后才知道有一次在途。
- **换密钥**：心跳得知新版本（P2）之后，用新密钥重封本页写下的草稿。
- **确认之后改基准**：服务端确认了 `confirmedSeq`，草稿的序号却更大（期间又写了新的），就把基准换成新的修订号、清掉在途。

**3.4.5 确认**

服务端确认（保存成功或内容相同）之后，在 strict 事务里按 `decideConfirm` 处理：
- `delete`：草稿的序号不大于 `confirmedSeq`，删掉；
- `rebase`：草稿更新，写入重封过的那一份（基准 = 新修订号，`inFlight = null`）；
- `absent`：已经没有草稿；
- `not-writer`：写入者不是它，不动。

管道事先按"草稿是不是更新"准备好重封的那一份；判定在事务里做，事务外看到的状态与事务里不同时，交回 `needs-rebase`，由管道重做。

**3.4.6 读回与解封**

按键读草稿。形状不对 → `malformed`；格式版本更新 → `newer-format`；用当前的密钥按记录的元数据生成 AAD 解封。解不开时：
- 记录的密钥版本小于当前版本 → `revoked`（密钥已吊销）；
- 大于当前版本 → `stale-key`（本页手里的密钥过时了：去取新密钥再试，**绝不删除**——另一个标签页可能已用新版本的密钥写下完好的草稿；审查 A3）；
- 相等 → `corrupted`（记录已损坏，包括被改过）。
`revoked` 与 `corrupted` 都删除，只是说法不同。

是否原样重放由 `canReplayAsSent` 判断：在途的就是这一份，并且发出不满 14 天（服务端修订记录与回执的保留期至少 15 天）。

**3.4.7 放弃、清理与保留期**
- **放弃**：用户的决定，不核对写入者。可以带 `expectedSeq`，免得删掉别的标签页刚写的新一份。
- **按用户清理**：草稿、写入者与提示在一个事务里一起删；之后才到的写入一律 `not-writer`。
- **保留期**：
  - 删除这台设备上 `updatedAt` 超过 14 天的草稿，不论属于谁（别人的本来就解不开）；
  - 写入者记录登记超过 14 天、又没有草稿的换成墓碑（S9 审查之后；见下）；
  - 交回删掉的键，属于当前用户的由 P4 说明。
- **与 OPFS 镜像一起清**（S9）：页面里的清理一律经合一的清理 `local-cleanup.ts`，库与镜像目录两份一起清。镜像目录删不掉（编辑器页的发件箱 Worker 正拿着句柄）的那几份交回 `pending`，写入者换成**墓碑**（`writerId` 为 `retired`，代次照旧、高水位不低于现有草稿的序号；写入、重封、确认对它一律 `not-writer`，比对时不从镜像写回）：按用户清理时那几份的草稿与提示留着，之后再调接着清；放弃时库照删、不必再调；镜像目录不在之后墓碑一并删。保留期只回收两个槽位都超过 14 天没动过（或者文件不在）的镜像目录（审查 A1、A5、A6、A9）。
- **列表索引**：`draftDocumentIds(userId)` 只读键；库不存在或不可用时交回空集合。

**3.4.8 Worker 与客户端**
- **握手**：带协议版本与空定时器的开关（只有测试构建能关）。
- **按 id 对应**：同一份文档的请求在 Worker 里排队。
- **看门狗**：每个请求有时限。到点、`error`、`messageerror` 或终止时，在途的全部以失败结束，之后的请求立即失败（`broken`），由页面按"本机写入失败"处理（P2）。
- **转移**：写入的字节与交回的 gzip 都放进 transfer。
- **空定时器**：Worker 启动时开一个 100 ms 的空定时器（DEF-011）；S1、S8 在真实 Safari 上复核它是否有效。
- **密钥**：主线程把不可导出的 `CryptoKey` 经 `postMessage` 交给 Worker。S1 先在真实 Safari 上确认可行：会不会弹钥匙串的提示、会不会失败。不行就改为把原始字节转移给 Worker、在 Worker 里导入、用完清零。

**3.4.9 本机密钥的客户端**
- **取用**：`fetchLocalKey`：`POST /api/local-key`（请求层自动带 CSRF）→ 契约校验 → base64 解成恰好 32 字节 → `importKey('raw', …, false, ['encrypt', 'decrypt'])` → 在 `finally` 里把原始字节清零。响应的 JSON 字符串清不掉，与 DEF-068 同一类，写进 ADR。
- **保管者**：
  - 同时只有一个取用在途。
  - 会话类失败交给页面确认会话，只有连着的第一次在确认之后立即重试。
  - 500、网络与时限按"暂时取不到"退避，不重试成风暴；计时都经注入的时钟。
  - `observeVersion` 收到不同的版本，就停用旧密钥、重取（P2 接心跳）。
  - `discard` 用于退出登录、换人。

### 3.5 错误处理、安全与可观测性

- **结果的写法**：跨模块的结果一律是带 `kind` 的值，不靠异常传递；未知的异常归为 `failed`，带名字与消息。
- **写满**：`QuotaExceededError` 可能出现在 `put` 上，也可能在提交时的 `onabort`（`tx.error`）里，两处都归为 `quota`。整个事务回滚，原记录与高水位都不变。
- **不可用**：§3.4.1 的四种原因。由调用方退化为内存实现（P2），并如实说明（US-M4-11）。
- **安全**：
  - 租约令牌、原始密钥不进浏览器的存储；
  - AAD 覆盖全部明文元数据；IV 不重用；
  - 记录的键里的文档 id 是明文，这是计划书 §7.6 的已接受风险；
  - 本机回滚防不住（同上）；
  - 加密的已知答案测试钉住格式（照 ADR-019 的 KAT）。
- **日志**：不记内容、不记密钥。Worker 的错误只带名字与消息；测试构建里的探针结果只有计时与事实。

### 3.6 真实浏览器的复核（S1、S8）

复核分两轮：S1 用不依赖生产代码的探针，结果可能改变放置；S8 用生产的发件箱 Worker 再跑一次。

**做法**：
- 页面自检照 M3 的结构加步骤：入口页登录 → 编辑器页 → `editor/testing/` 下的场景 → 整页跳到收集端。
- 不需要编辑器的探针以阅读打开；探针与它的 Worker 在 `editor/testing/` 里，门禁按来源自动算作测试专用。
- 结果的报告加一个 `facts` 字段（计时与事实）与运行次数的地址参数。
- 是否通过由驱动脚本里的纯函数判定，结果写进 `tests/e2e/safari-results/`；页面一侧只检查"跑完、数据齐"。
- Playwright 里的校准只跑小样本、少次数，核对探针本身（进 CI）；大样本只在真实 Safari 与本机的持久上下文里跑（不进 CI）。

### 3.7 崩溃工具（S7）

- **接口**（`tests/e2e/support/browser-crash.ts`）：
  - `launchPersistent(browserName, profileDir, options)`：持久上下文，自己挂上夹具的那几样——CSP 违规、页面错误、自动保存的打开状态、`locale`、`timezoneId`、`baseURL`、`ignoreHTTPSErrors`。
  - `crashBrowser(handle)`：结束之前现取进程表，按角色认出这次启动的全部进程，在同一个同步循环里发出结束；之后核对全部退出、没有幸存者。
  - `relaunch(profileDir, { cookies: 'restore' | 'clear' })`：以同一个目录重开。
- **认进程**：
  - Linux：三个浏览器的进程全在这次启动的进程树里（读 `/proc`）。
  - macOS：Chromium、Chrome 在树里；WebKit 的 Networking 由 launchd 拉起，用它打开着资料目录里的文件来认。WebContent 与 GPU 只能按安装路径、启动时刻，并且机器上只有这一个 Playwright WebKit 实例时才认；有别的实例时报错说明，不静默跳过。
  - 绝不按名字模糊匹配：chrome 项目的可执行文件就是需求方自己在用的 Google Chrome，只能从这次启动的根往下认；系统的 WebKit 与 Safari 的进程一律不碰。
- **断言**：
  - 按角色核对被结束的进程：Chromium 系有根、渲染进程、网络服务；WebKit 有启动脚本、浏览器、网络进程、页面进程。
  - 资料目录经 `support/persistent-profile.ts` 的 `profileDirFor` 取：`<项目的输出目录>/persistent-profiles/<用例 id>-<重复>-<重试>-<名字>`，只有 ASCII——Linux 上 Playwright 的 WebKit（WPE 的 MiniBrowser）遇到非 ASCII 的路径起不来，与区域设置无关，而 `testInfo.outputPath` 带着中文的用例标题（P1 审查 B1）。别的持久上下文（OPFS 镜像的浏览器层用例、写满、测量）同样走它。
- **跑法**：
  - 崩溃用例单独成项目，每个浏览器一个，`workers: 1`，依赖全部浏览器项目。
  - 重启后端的项目（restart）要依赖崩溃项目，两者不同时跑。
- **Cookie**：Cookie 不一定已落盘，重开时走两条确定的路：
  - `restore`：模拟已落盘，崩溃之前存下 Cookie、重开之后加回；
  - `clear`：模拟没落盘，重新登录。

  两条路各写用例；浏览器实际留没留下只记录，不断言。
- **原子性用例**：
  - 持久上下文里反复写约 5 MiB 的草稿，按 0–260 ms 的延迟，或者"写入之前"的信号结束整棵进程，再以同一个目录重开。
  - "写入之前"的信号：主线程放置时，存储包一层，`put` 之前经 `page.exposeBinding` 通知测试进程。
  - 断言每次读回的都是旧的或新的一份、都能解开、序号是两者之一。
  - 每个浏览器至少 15 次，Worker 与主线程两种放置都跑。
- **Linux 先在本机跑**：Linux 上的崩溃用例先用 Docker 里 Playwright 的官方 Linux 镜像跑多轮，再上 CI；拉镜像之前告诉需求方。
- **单元测试**：进程表的解析、树、角色分类、WebKit 进程的候选，都是纯函数。

### 3.8 OPFS 的冗余（S9）

**为什么**（S7 的调查，证据与数字写进 `reviews/P1-真实浏览器复核.md`）：
- Chromium 的 IndexedDB 每个来源一个 LevelDB（同一来源的全部库共用），开着 `reuse_logs`。
- 进程在往日志追加一条记录的两次 write 之间被结束（记录头写了、内容没写）。下一次打开时这半条被悄悄丢掉、一切正常，但新数据接在它后面写；再下一次打开时校验和不符，Chromium 删掉这个来源的全部 IndexedDB 重建。删库重建之后，这个来源里第一个 `open()`（不论打开哪个库）的升级事件拿到 `dataLoss: "total"`（`dataLossMessage` 是"IndexedDB (database was corrupt): checksum mismatch"），之后的都是 `none`——编辑器页里最先打开 IndexedDB 的是 Univer 自己的 `UniverLocalStorage`（它也一起没了），别的标签页、Worker 也可能抢先，所以应用靠不住这个标记（S7 调查的订正）。
- 实测：
  - Google Chrome 154 不注入时，1400 次强制结束里删库 5 次；chrome-headless-shell 153（macOS）1100 次里 9 次；Linux 的 chrome-headless-shell 300 次里 1 次；
  - 每一次之前都有"日志结尾只剩记录头"的前兆（15 次前兆对 15 次删库）；只在写入进行中被结束时出现，写完再结束 300 次 0 次；
  - 变体：之后写入的字节不够那半条声明的长度时不删库，但之后每次提交的写入，在下一次被结束后都悄悄丢失；
  - WebKit（每个库一个 SQLite）290 次 0 次。
- 删库时 localStorage 与 OPFS 的文件都还在，但：
  - localStorage 不能用：它延后落盘，2540 次被结束后一次都不是刚写的值；在 Chromium 里它也是同样的 LevelDB。
  - OPFS 用 `createWritable` 写时，每次都改 OPFS 的目录库（同样的 LevelDB），目录库出事时被改写的文件整个消失；只有在 Worker 里用同步访问句柄改写已有的文件，才不碰任何 LevelDB。

**做法**：IndexedDB 仍是主存储，写入栅栏、序号、确认都在它的事务里；每次在它里面写成之后，同一份记录再镜像进 OPFS，作为崩溃之后的备份。

- **只在发件箱 Worker 里，用同步访问句柄，改写事先建好的文件**：
  - 登记写入者时，为这份文档建好两个槽位文件（`nerve-office-outbox/<userId>/<documentId>/` 下的 `a` 与 `b`）；
  - 之后只改写与截断：不新建、不改名、不删，也不用 `createWritable`；
  - 只有用户的数据清理（退出登录、账户停用、本机草稿页的放弃）与保留期才删目录——这几处碰 OPFS 的目录库，次数少，碰坏了的后果也正是"删掉"。
- **两个槽位轮流写**：
  - 每次写在"现在不是最新那一份"的槽位上，原地改写：截断 → 写内容 → 写头 → `flush()`。
  - 头的长度固定，里面有：魔数与格式版本、写入者（代次、`writerId`）、草稿序号、内容的长度与 SHA-256、头自己的校验。
  - 内容就是存进 IndexedDB 的那一份记录的序列化（明文元数据、IV、密文；元数据仍由 AAD 认证）。
  - 写一半的槽位校验不过，读时落选，另一个槽位上的上一份还在。
- **顺序**：IndexedDB 的事务提交之后才写镜像，镜像只放已提交的。镜像没写成（写满、句柄拿不到、出错）不影响 IndexedDB 那一份，写入的结果里带上"镜像没写成"，由页面如实说明（P2）。
- **句柄独占**：同步访问句柄同一时刻一个文件只有一个。写入者持有自己两个槽位的句柄，失去写入者身份或页面离开时关掉；新的写入者拿不到时退避再试，期间镜像暂缺，照旧写 IndexedDB，结果里带上。
- **确认与清理**：服务端确认、草稿删掉时，两个槽位截断为 0；标记在途、确认之后改基准、换密钥，镜像都跟着写新的一份。用户的数据清理与保留期经合一的清理（§3.4.7），删不掉镜像目录时立墓碑。
- **读与恢复**：
  - 镜像的两个槽位之间按代号认最新写的那一个；与库谁胜出不按代次比（审查 A2、A11），按下面的规则；读草稿与登记只交回最新的那一个版本，同一个版本在库与镜像里各有一份时互为备份，不退回更旧的版本（审查 A3）。
  - 打开平台、登记写入者之前先比对（一份一份地，审查 A13），写回与否在存储的事务里按库里当前的写入者判（审查之后的规则）：
      - 库里这份文档既没有写入者也没有草稿（删库）→ 写回，写入者照它建；
      - 库里是墓碑 → 不写回，截断镜像；
      - 同一个写入者：库里是它的草稿 → 镜像的更新才写回（库悄悄退回了已提交的写入），抬高高水位；库里没有它的草稿 → 序号大于高水位才写回（不大于的是确认删掉、放弃过的，不复活）；
      - 不同的写入者（草稿序号是一份文档一条线，登记时继承高水位）：序号不大于库里写入者的高水位 → 它登记时看过这一份，不写回（含 force 登记、代次倒退之后旧一代的镜像）；候选的代次更大 → 写回，写入者换成它的（库悄悄丢了更新的那次登记与它的写入，UR-034 的变体）；库里没有草稿 → 写回成别人留下的草稿，不动写入者与高水位（活着的那一页按自己交回的高水位分配序号）；否则不写回（不覆盖库里写入者自己的草稿）；
      - 超过保留期、库里那一条认不出 → 不写回。
    写回时连同写入者的记录（代次、`writerId`、高水位；删库时写入者也没了），并留下"已从备份恢复"的提示（`restored`，与写回草稿、写入者在同一个 strict 事务里写进 `notices` 仓库）。
  - 没写回而库里有草稿、本页是写入者时（例如被结束在"库已提交、镜像还没写完"之间），登记时用库里那一份补写镜像——否则下一次写成之前发生删库，从镜像恢复出来的会比最后一次提交的旧（崩溃工具的实现者读实现时发现的缺口）。补写由持有句柄的写入者做，没写成照"镜像没写成"如实交回。
  - 没写回、本页不是写入者而镜像过时（确认删掉、放弃过、超过保留期、库里是墓碑）的，截断两个槽位。
  - 平台页面（P4 的本机草稿页）列出与清理之前先比对：只读镜像、只写回，不截断、不补写、不留 lost（审查 A18）。
  - OPFS 有文件、两个槽位都不合格（更新的格式不算写一半，审查 A8、A10）、IndexedDB 里也没有的，留下"本机草稿因浏览器存储损坏丢失"的提示（`lost`，另一个事务里核对库里仍没有之后写下）。
  - 两种提示由 P3（打开文档时）、P4（本机草稿页）读出、如实告诉用户，看过之后清除（清除时带上读出的那一条的时刻，不清掉读出之后才留下的新提示）；放弃、按用户清理与保留期一并清掉。
- **防不了的**：清除站点数据、浏览器回收存储空间——两份在同一个存储桶里，`persist()` 照旧申请。本机占用约翻倍。
- **放置**：进程内的放置没有镜像（同步访问句柄只在专用 Worker 里有）。真实浏览器的复核之后三个浏览器都用 Worker 放置（DEF-011 的定论，ADR-020）；进程内放置只作 Worker 起不来时的退路，P2 设计退路时要把"Chromium 上退到进程内就没有镜像"算进去（WebKit 的 IndexedDB 是 SQLite，290 次强制结束没有丢失）。
- **崩溃用例的口径不变**：断言"发件箱读回的是旧的或新的一份"，从 OPFS 恢复的也算；Chromium 删库的那几次（日志结尾的前兆）如实记成附件。原子性按生产会用到的配置跑：Chromium 系只跑 Worker 放置（带镜像），进程内放置只在 WebKit 上跑；功能性的浏览器层用例照旧三个浏览器都跑两种宿主。另加三条：
  - 写镜像途中结束进程，两个槽位读回旧的或新的；
  - 用"日志结尾补一个只有头的记录"确定地造出删库，核对从 OPFS 恢复、提示如实。
  - 镜像落后一份（把存着最新一份的槽位改坏）→ 登记时补写镜像 → 造出删库 → 读回的仍是最后一次提交的那一份。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 真实 Safari 上空定时器无效，Worker 仍停顿 | 写入管道与放置无关（§3.1），WebKit 改在主线程放置；S1 先测，S8 再确认 |
| 不可导出的 `CryptoKey` 在真实 Safari 里交不给 Worker，或弹出钥匙串的提示 | S1 第 7 项先测；不行就改为在 Worker 里导入（§3.4.8） |
| 持久上下文里的写入耗时、`strict` 的开销比 M0 的内存库数字大很多，影响"已保存在本机 ≤ 2 秒"的预算 | S1、S8 实测；超出时先看 Worker 段与写入段哪一段，P2 按实测调整捕获间隔（计划书 §7.2"大文档"一行） |
| Safari 的 IndexedDB 偶发连接断开、打开挂住 | 看门狗、重开一次、写入的重试幂等（§3.4.1、§3.4.8） |
| 崩溃工具认错进程 | 只从这次启动的根往下认；WebKit 的 XPC 要求独占，别的实例存在时报错；按角色断言、核对没有幸存者；进程的解析是单元测试过的纯函数 |
| Linux 上的崩溃用例上 CI 才暴露问题 | 先在本机 Docker 里 Playwright 的 Linux 镜像跑多轮 |
| 镜像写一半，或两个标签页争同一个文件的句柄 | 两个槽位轮流写、带校验；句柄的独占由浏览器保证，拿不到时退避、照旧写 IndexedDB |
| OPFS 的目录库同样会坏 | 平时只改写已有的文件，不碰目录库；只在建文件与清理时碰 |
| 本机占用翻倍，更早写满 | 写满如实说明；镜像写满不影响主存储 |
| 平台首屏余量只有约 4 KiB | P1 不往平台页面引入任何东西；lint 的区域规则先加上；P4 接列表标记时按需加载 |
| Worker 里误打进 zod | 协议用手写守卫；lint 的区域规则；门禁兜底 |
| jsdom 的 realm 让 `instanceof` 失真 | 字节的守卫与断言不用 `instanceof` |

未决：
- **Safari 的私密窗口**：自检做不了，要需求方手动打开私密窗口跑一次，可选，到时另说。
- **写入耗时**：持久上下文里的写入耗时是否需要调整计划书的"已保存在本机 ≤ 2 秒"，S1、S8 之后定。
