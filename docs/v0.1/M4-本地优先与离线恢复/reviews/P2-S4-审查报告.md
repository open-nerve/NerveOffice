## 任务 1：捕获、保存与单份上传所有权

捕获同步交给 WorkingDraft；autosave 只持引用，保存协调只持固定上传和元数据。SaveRequest 移除 JSON，使用来源冻结的格式及实际 contentSeq。页面会话先接单一内存来源，持久准备由任务 2 接入。遇旧请求结果未知时，先按原 requestId/格式/标记/gzip 核对，完成后才向来源索取最新捕获。云端确认即推进云端事实，本机确认链不会回退它；后续准备必须等待最新确认链收尾。

原 M3 业务故事保留：输入提交、公式补存、自动捕获/上传节奏、退避、显式保存、续租采纳、版本冲突与失效保护。相应网络顺序调整为先核对旧请求；上传序号不再等于编辑修改计数。正文断言从实际字节读取：核心单元只替换 codec 耗时边界，编辑会话/页面及新增整合使用真实 gzip。

## 审查发现与修复

| 来源 | 发现 | 修复和回归 |
|---|---|---|
| 自审 | 外部 replay 只等待 tail，没有加入队列，后续 save 可并行重放同一 pin | replay 纳入同一 tail；busy 包含外部核对；内部只调用 replayOnce |
| 独立第一轮 Important | HTTP 已未知结束后才 adopt，确认后旧 pin 不释放，后续 DraftBusy；已解决元数据也妨碍去重 | 跟踪上传流程 running，确认后仅在流程结束时释放；清 adopted 元数据；新正文/同正文与持有确认回归 |
| 独立第一轮 Important | replay 429 的 Retry-After 被新上传吞掉 | 返回 retry 给原调度，保留退避；30 秒用例 |
| 独立第一轮 Important | 普通保存核对在 mark 等待时 stop 后仍发请求 | 内部核对检查停写；显式结果核对仍可在 stopped 下进行 |
| 独立第二轮 Important | save 已等待旧 localTail 后微任务 adopt，新确认链尚未完成就 prepare | 在 prepare 紧前循环等待并同步核验最新链，随后再检查 stop/dispose/终态；确定微任务交错先红后绿 |
| 独立第二轮 Minor | replay 422 后自动保存再次发送相同正文 | 保存拒绝引用/摘要，AUTO 同内容等待新捕获；不同正文、无摘要的新引用及显式重试照常 |
| 回归 | codec 失败的 ready 结果不可变，重复 prepare 同一引用不能重试 | 原有第一次意外退避后重新捕获；第二次失败仍等新修改，不新增无限重试 |

独立复审结论：Critical 0 / Important 0 / Minor 0。审查者另行运行 7 个只读 Node 探针，覆盖迟到 adoption、确认等待期间 stop/dispose、外部 replay 排队及 422 同引用/同摘要/新正文；没有把主线程日志作为独立执行证据。
