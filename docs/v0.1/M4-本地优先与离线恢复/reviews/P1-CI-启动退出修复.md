# P1 合并后 CI：启动成功时已经接管退出信号

> 日期：2026-10-10｜基线：main `a9ef2201`｜修复分支：`codex/m4-p1-ci-fix`。修正 API 进程入口的就绪通知顺序。

## 故障与根因

关页竞态修复后的 [CI 38023436931](https://github.com/open-nerve/NerveOffice/actions/runs/38023436931) 中，生产容器通过，基础门禁有 12,072 项通过、1 项失败：`process.test.ts` 的主密钥文件用例读到启动日志后发送 SIGTERM，预期退出码 0，实际为 null。

`main.ts` 先同步输出“HTTP 服务已启动”，再调用 `handleShutdownSignals`。观察启动日志的一方可能立即发信号，此时默认信号行为会直接结束进程，来不及执行应用的优雅退出。这是生产入口的时序缺陷。

为确认因果，临时在启动日志后加入 200 ms 同步停顿，使用真实构建产物与独立 PostgreSQL 运行原失败用例，确定得到 `{ code: null, signal: 'SIGTERM' }`。没有修改测试等待时间或接受信号退出；临时停顿始终由脚本 finally 恢复。

## 修复与回归

监听完成后先注册 SIGTERM / SIGINT，再公布启动成功。运行时的关闭顺序、超时和退出码规则不变。

新增入口回归静态导入真实 `main.ts` 和 `process-handlers`，将进程换成独立的事件接口，在收到启动日志的同一刻发出 SIGTERM。撤回修复后因未调用 shutdown 而失败，恢复后通过。原真实进程用例改为同时检查退出码与信号，并核对开始退出、graceful 完成两条日志，失败时能分清直接被信号结束与应用主动退出。
