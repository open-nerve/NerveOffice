### Important 1：后台先完成同一次清理，会令前台跳过服务器退出

**位置：** `apps/web/src/shared/local-drafts/logout-flow.ts:156`、`:189`；并发调用来自 `shared/local-drafts/draft-maintenance.ts:62`。

**触发条件：** 前台已完成原许可核对并取得清理许可；另一页面的维护在前台 `removeUser` 获得同源锁之前，凭同一个许可完成清理，将持久状态推进到 `cleared`。

**错误行为与影响：** 前台 `removeUser` 正确拒绝已经结束的清理许可，返回 `invalidated`。但 `clean()` 立即把整个退出流程永久标成失效，随后 `qualify()` 因 `live()` 为假直接退出，根本不会执行 `requestLogout`。因此草稿已删除，服务器会话仍有效，界面却要求用户因“登录状态变化”重新预览。这里没有发生新登录。

**建议修法：** 在清理返回 `invalidated` 时，先使用现有原来源核对器重新读取状态。若仍是同一来源、同一退出原因且已 `cleared`，采纳清理完成结果并继续原 CSRF 的退出；确有来源变化才结束流程。保持删除许可的严格拒绝，不能重新申请许可补授权。

**测试缺口：** `logout-flow.test.ts:244` 只测试重试开始前已经 `cleared`，没有覆盖“先核对为 clearing → 后台完成 → 本次删除被拒绝”的窗口。应固定这个交错，断言原退出请求恰好一次、服务端最终 401；同人重登和换人的反向用例仍须拒绝旧操作。

### Important 2：HTTP 成功后的取消没有阻止本机激活及全局会话采纳

**位置：** `apps/web/src/shared/local-drafts/session-activation.ts:57`、`:67`；`apps/web/src/features/auth/session.ts:48`；`shared/api/client.ts:32`。

**触发条件：** 会话 HTTP 请求及正文校验已经成功，流程仍在等待来源摘要或同源锁，此时调用方取消查询。`withinRequestDeadline` 已在 `request-deadline.ts:54` 移除取消监听，而后续成功路径没有再检查 signal。

**错误行为分两层：**

1. 没有后续换代时，已经取消的查询仍可能调用 `acceptSessionCheck`、建立持久许可并关联响应。
2. 若期间新登录已经换代，**持久 CAS 会正确拒绝旧 ticket**；但 `track()` 仍返回旧响应，`fetchSession()` 随即无条件 `setApiSession`，覆盖较新会话的全局 CSRF、许可关联和 `currentApiSession`。

后一种情况会使当前页面重新使用旧 CSRF，并让维护订阅者失去较新响应的许可。这里没有证据表明旧 ticket 能突破持久栅栏删除新账户数据；问题是取消失效与全局采纳越过了该栅栏的结果。

**建议修法：** 将取消贯穿本机处理和最终采纳：成功返回、摘要完成、排队锁进入及返回调用方之前检查取消，不能被“本机故障降级”的 catch 吞掉；全局采纳处也需防止已取消结果生效。取消后的收尾只能针对自己的原 ticket，不能撤销或借用后来许可。

**测试缺口：** `session-activation.test.ts:78` 只测试 signal 已取消且网络 mock 同时拒绝原 reason。应增加 HTTP 已成功后暂停摘要、暂停锁两种反例，并让较新响应先被采纳；断言旧操作拒绝原取消原因、不覆盖全局会话、不提供旧响应许可、不重复请求。

### Important 3：OPFS 根目录读取失败被当成镜像不存在，可能虚报清空并留下可复活的镜像

**位置：** `apps/web/src/shared/outbox/local-cleanup.ts:202`、`:219`、`:276`；根因分类在 `shared/outbox/mirror-directory.ts:164`。

**触发条件：** 当前用户确有非空 OPFS 镜像，明确退出、停用清理或保留期维护期间，`getDirectory()` 暂时拒绝，例如 `UnknownError`；主库及其他清理项目正常。

**错误行为与影响：** `rootDirectory()` 将任何异步拒绝统一折成 `unsupported`。完整清理把它视为没有文档，清掉主库及墓碑，并允许 `finishUserCleanup` 标记 `cleared`；保留期路径也把它变成空的 remaining 集合并删除墓碑。实际上镜像尚在。根目录恢复可读后，同一用户以新会话登录，留下的镜像可能重新写回主库，出现“已清理”的草稿复活。

这是 P4 将既有目录分类用于真实退出及清理完成判定后暴露的问题。

**建议修法：** 将“没有对应能力”“目录明确不存在”和“无法确认目录内容”分开。写入宿主可以继续按不可用降级；读取、枚举和删除失败则必须保留未完成状态及必要墓碑，不能据此证明删除完成。还需检查共用 `problemOf(SecurityError)`，避免换一条异常路径后仍折回 `unsupported`。

WebKit 临时上下文确有 `getDirectory()` 报 `UnknownError` 的既有边界，**这一事实不能证明已有镜像已经不存在**，也不能作为清理成功证据。

**测试缺口：** `mirror-directory.test.ts:242–249` 明确把 API 缺失和根目录 `UnknownError` 设为相同结果，固化了上述前提。现有真实清理失败测试主要注入 `removeEntry` 占用。应先证明持久上下文中有非空镜像，再注入根目录失败，验证不报告 cleared、不丢墓碑、服务器仍可退出；解除故障后原资格重试完成，重新登录不复活草稿。保留期也需相同反例。
