## 一、做法

### 1.1 结构

沿用 M3 的页面自检（测试构建的入口页 `selftest.html` 登录 → 编辑器页 → `editor/testing/` 下的场景 → 整页跳到收集端交回结果、驱动脚本 `safari:selftest`），不新建测试入口页（M3-P2 复核 B4）。新加的部分：

1. **探针**（`apps/web/src/editor/testing/`，只在测试构建里；不依赖发件箱的生产代码）：
   - 探针 Worker `storage-probe-worker.ts`（只用 IndexedDB、CompressionStream、crypto.subtle、Web Locks），消息 `storage-probe-protocol.ts`（每个请求带 id，出错带名字），客户端 `storage-probe-client.ts`（按 id 对应、每个请求有时限，Worker 出错、加载失败、终止时在途的全部失败，不挂住页面）；
   - 共用的办法 `probe-bytes.ts`（不经 Blob 的 gzip——WebKit 离线时读不了 Blob；SHA-256；像密文那样的随机字节；IndexedDB 的 Promise 写法），主线程的监视 `probe-measure.ts`（事件循环两拍之间与动画帧的最长间隔，M0 的口径：停下时先让出一次、把"上一拍到现在"算进去）；
   - 场景：`selftest-storage.ts`（storage、key-transfer、storage-quota）、`selftest-stall.ts`（worker-stall）、`selftest-cost.ts`（capture-cost、perf-baseline）、`selftest-outbox.ts`（outbox-stall、outbox-pipeline：生产的发件箱）。
   - **生产的发件箱**经页面自检的挂接交进来：挂接（`features/sheet-editor/selftest-hook.ts`）在场景要用时动态引入 `features/sheet-editor/outbox/testing/outbox-review-probe.ts`（只在测试构建里，只引用生产模块，不改甲、乙的探针），按 `editor/testing/outbox-review-api.ts` 的形状交进 `SelftestHost.outboxReview`（editor/testing 不能引用 features）。生产 Worker 的写法与 P2 的编辑器页相同：`createOutboxWorker()` + `createOutboxWorkerClient({ keepAlive: true })`，本机密钥经生产的 `importLocalKey` 导入、按 `keyTransferOf` 交给 Worker；进程内各段用 `draft-codec` 与 `draft-store`。
   - **OPFS 镜像那一段**：同步访问句柄只在专用 Worker 里有，进程内各段量不到它，另起一个测试 Worker（`outbox/testing/mirror-review.worker.ts`）调用生产的 `createDraftMirror` 与 `opfsMirrorDirectory`；量法在 `mirror-review.ts`（单元测试配内存里的目录）：目录交出的句柄外面包一层、记下截断与写、flush、拿句柄各用了多久，不改生产的写法。收尾时关掉各个 Worker、按复核用户删掉镜像目录（Worker 终止之后句柄是异步放开的：被占着就隔 0.1 秒再删，至多 10 秒），删成了没有记成事实。
2. **结果的格式**（`selftest-report.ts`）：加 `facts`（"项.名" → 字符串、有限的数、真假或 null，读回时校验）；地址参数 `runs`（运行次数，1–400，入口页从 # 片段读、带到编辑器页的地址上）。页面只核对"跑完、数据齐"——每一项做完、事实记下；**是否符合预期由驱动脚本一侧的纯函数判定**（`tests/e2e/support/probe-verdicts.ts`，单元测试覆盖，§三）。
3. **挂接**（`features/sheet-editor/selftest-hook.ts`）：记下第一次载入时容器第一次到 ready（渲染完成）与 steady 的时刻（首屏，订阅在载入之前）；capture-cost、perf-baseline 先进入编辑。
4. **样本**（`capture-samples.ts`，与 E2E 的生成器共用）：按字节数生成的明细表（M0-P3 big-1m、big-5m 同样的种子与列：约 1 MiB、约 4.9 MiB，仍在快照上限之内）；perf-50k（数据表 50,010 格、汇总 716 格，1,000 个公式带按定义算出的缓存值，增量计算改数据表 D 列、牵动约 320 个公式）。
5. **驱动脚本**：`--runs`（默认 40）；复核的几步交回之后逐项判定、打印，写进结果文件的 `probe` 一节（判定只是复核的结论，不影响退出码）。一次运行里由驱动脚本打开的第一步是冷的（这次运行的端口是新的，浏览器缓存里没有这个源的脚本），之后的是热的。

- key-transfer 单独一步（主会话同意）：WebKit 序列化 CryptoKey 可能要用钥匙串里的主密钥，万一弹出钥匙串的提示、页面停住，别的几项的结果已经交回。先试退路（原始字节转移给 Worker、在 Worker 里导入并清零），再试交 CryptoKey；失败（DataCloneError）、超时都如实记下，不去点掉系统的提示。
- 写满（storage-quota，第 4 项）不在真实 Safari 的步骤里：Safari 没有覆盖配额的接口。它在 Playwright 的持久上下文里做（Chromium 系经 CDP 把配额覆盖成 12 MiB），一条一条地加 1 MiB，最多写 64 MiB——页面看不出配额有没有被覆盖（estimate() 照旧报真实的配额），所以靠上限保证有界。
- 每个场景用自己的库（随机名字），收尾时删掉；Worker 自己的库同样删掉。
- 自动保存：capture-cost、perf-baseline 暂停定时的上传，捕获的静默与上限调到一小时（调度的捕获不落进计时里）。

### 1.3 各项怎么量

| 项 | 量法 |
|---|---|
| 1 持久保存 | `persisted()` → `persist()`（新的源、没有用户激活）→ `persisted()`；Chromium 系另经 CDP 造出"已授予"再跑一次（本机实测） |
| 2 配额与用量 | 写 5 MiB 随机字节（像密文）之前与之后的 `estimate()`；Chromium 系另有 `usageDetails.indexedDB` |
| 3 durability | 请求 strict、default 时事务的 `durability` 属性；同一个键交替覆盖写约 1.3 MiB（约 5 MiB 快照 gzip 之后），default 与 strict 各 N 次，从建事务到 complete |
| 4 写满 | Chromium 系 CDP 覆盖 12 MiB：加到失败（错误名、出在请求还是事务上）、失败的那一条不在；4 MiB 覆盖已有的一条失败之后原记录逐字节不变、能解开 |
| 5 回滚 | 两个仓库的事务：put 都成功之后 abort；put 之后 add 一个已有的键（ConstraintError）——已有记录逐字节不变、新的不在、写入者不变 |
| 6 IndexedDB | 两个仓库（键 `[userId, documentId]`）、5 MiB 写读摘要一致、只做加法的升级、Worker 里读写同一个库、Worker 以更高版本打开时页面收到 versionchange、`databases()` 列出、删掉之后不列出 |
| 7 密钥交给 Worker | 页面 `importKey('raw', …, false)`，原始字节清零；CryptoKey 经 postMessage 交给 Worker：类型、不可导出、Worker 解开页面封的（AES-GCM 带 AAD）、改一个 AAD 字段之后解不开、Worker 封的页面解得开、Worker 里 gzip 往返与 SHA-256；退路同样一套 |
| 8 Web Locks | 页面拿着：Worker `ifAvailable` 得 null、`query()` 看得到；Worker `steal`：页面的申请以 AbortError 结束；终止 Worker 之后多久重新拿到 |
| 9 Worker 停顿（探针） | 有、没有 100 ms 空定时器的探针 Worker（每组新起一个、先热身一次；两个条件同一串空闲、先后轮流）；Worker 空闲 T 之后转移约 5 MiB 的类表格 JSON，依次 SHA-256 → gzip → AES-GCM → IndexedDB（strict），各段与往返、送达、交回 |
| 9 Worker 停顿（生产） | 生产的发件箱 Worker（带空定时器），空闲 T ≥ 1 秒之后写一份约 5 MiB（不去重：SHA-256 → gzip → 加密 → 写入 strict → OPFS 镜像，交回 gzip 与镜像写成了没有）；生产的协议不交回 Worker 里各段的计时，记页面这一侧的往返（Worker 段加上来回的消息，偏保守）。**有 OPFS 的上下文里往返含镜像写入**（IndexedDB 提交之后写进两个槽位之一：截断 → 内容 → 头 → flush），每次记下写成了没有。每组新起一个 Worker、先热身一次 |
| 10 捕获成本 | 编辑时：`save()`、序列化、编码分开计；Worker 放置时异步段（转移、Worker 里整条管道）主线程的最长阻塞与帧间隔；同样的字节在主线程 gzip、主线程整条管道（写入 strict）的阻塞 |
| 11 磁盘上的管道与恢复 | 进程内（主线程）走一遍生产的写入：SHA-256、gzip、封（AES-GCM 带 AAD）、写入（生产的存储：栅栏的判定与写在同一个 strict 事务里）；同一份记录直接写进同一个库各一次 strict、default（只差 durability）；恢复：读（存储）、解开、解压、解析；核对解压之后与原来的字节相同。各次写同一份文档（登记一次、序号递增：编辑时的样子，库与镜像都是改写）。**OPFS 镜像**（测试 Worker 里调用生产的镜像，库写成之后）：登记（拿句柄、读两个槽位并校验——放开过句柄之后重新登记，第一次另要建目录与文件）、整个写入（编码即内容与头的 SHA-256、截断、写内容、写头、flush），截断与写、**flush 单独计**；恢复一侧先放开句柄（打开平台、登记之前比对时手里没有句柄），再读两个槽位并校验（其中拿句柄另计）、按生产的 `compareDrafts` 取最新并与库里那一份比对；核对最新的合格那一份就是库里那一份（序号、写入者、更新时间、密钥版本、IV 与密文） |
| 12 首屏与公式冻结 | 导航开始到第一次渲染完成、到 steady（冷与热）；增量（改数据表 D2、D3……）与全量（强制重算）从动作到这一轮收齐，期间主线程最长阻塞、最长帧间隔 |

### 1.4 三种运行

- **真实 Safari**（本报告的主体）：`caffeinate -d -i pnpm --filter @nerve-office/e2e run safari:selftest --front --steps perf-worker,perf-main,perf-worker-warm,capture-1m,capture-5m,storage,key-transfer,worker-stall,outbox-stall,outbox-pipeline`，只在用户空闲时跑（默认空闲满 120 秒，跑的时候用户回来就作废）。不用 `caffeinate -u`（会把空闲计数清零，被当成用户回来）。
- **本机持久上下文**（三个浏览器的对照，设计 §1 偏差 7：Playwright 默认的上下文不落盘）：`pnpm --filter @nerve-office/e2e run measure:probe`（`measure/probe.spec.ts`，runs 40，不进 CI）。三个浏览器的持久上下文都有 OPFS（镜像那一段在这里与真实 Safari 上量）；Playwright 的 WebKit 在 macOS 上把持久上下文的 OPFS 放在共用的目录里（S9 的浏览器层用例），探针收尾时按复核用户删掉。
- **Playwright 的校准**（`specs/editor/selftest.spec.ts`，进 CI）：不带 runs，每项最少的次数、小样本，只核对探针本身——页面的检查都通过、数据齐，与时间无关的第 5、6、7、8 项按判定通过；capture-5m 与 perf-worker-warm 不在 CI（主会话同意）；写满单独一条（持久上下文）。生产发件箱的两步另核对 OPFS 镜像：Chromium 系的默认上下文（无痕式，OPFS 在内存里）每次都写成了镜像、收尾时删掉了镜像目录；**Playwright 的 WebKit 默认上下文没有 OPFS**（`getDirectory()` 报 UnknownError，生产的代码按 unsupported 处理），探针照样跑完、记下 `not-mirrored:unsupported`。

## 六、盲区

- **可信的输入**（第 13 项）：编辑响应、第一次键盘输入要可信的按键；自检只能派发合成事件（不算用户操作），驱动脚本按 M3 的约定不用 AppleScript、不开"允许远程自动化"。由 Playwright 的 WebKit 覆盖（M0 V10 的按键到下一帧、画布一出现就键入）。
- **内存**（第 13 项）：Safari 没有页面内存的接口（`performance.memory` 只有 Chromium 系；`measureUserAgentSpecificMemory` 要跨源隔离，Safari 没有）。由 Chromium 经 CDP 覆盖（M3-P2 S5 的 `measure:memory`）。
- **写满**：Safari 没有覆盖配额的接口，真写满要写到磁盘的相当一部分——不做；用第 5 项的事务中止作有界的替代，错误分类在单元测试里注入（S4）。
- **断电**：页面看不出 strict 是否真的落盘；P6 在虚拟机里断电。
- **私密窗口**（第 15 项）：驱动脚本打不开私密窗口（只用 `--front` 把 Safari 带到前台，不用别的办法操作 Safari）；要需求方手动时另说。
- **Safari 隐私浏览里有没有 OPFS**（主会话要求记一笔）：**自检做不了**，同上。印象里较新的 Safari 在隐私浏览里也给 OPFS（数据在关闭窗口时清掉）【待核，未实测】；生产的镜像在没有 OPFS 时按 unsupported 处理、库那一份照常，所以不影响写入，只少一层冗余。要确认时可以手工看：Safari 打开一个隐私浏览窗口，访问任意一个没有严格 CSP 的 https 页面，在网页检查器的控制台里起一个专用 Worker，在 Worker 里 `await navigator.storage.getDirectory()`、建一个文件、`createSyncAccessHandle()`，看成不成、报什么错。
- **计时的精度**：WebKit 的 `performance.now()` 在这些上下文里是 1 毫秒的精度（Playwright 的 WebKit 校准里各段都是整数毫秒；真实 Safari 没有跨源隔离，同样是 1 毫秒）。OPFS 的各段在 1 毫秒上下，Safari 上读到的是 0 或 1 的整数，中位数只能看个大概，要看 p95 与整个写入、整个读的合计。
- **持久保存的授予**：自检里没有用户激活，测到的是"新的源、零访问史、没有激活"时的结果；真实用户点"编辑"时有激活，常用站点的实际授予以本机草稿页显示的为准。
- **一台机器、一个 Safari 版本、窗口在前台**；计时只作对照（这台机器同时有别的子 Agent 在跑测试，各次运行记下负载）。
- Worker 作用域里的错误页面看不到（与 M3 相同），探针 Worker 的出错经回应交回名字与说明。

## 七、Safari 的清理策略与 14 天保留期（第 14 项，按文档写，凭记忆、未联网核对，标【待核】）

- **ITP 的"7 天上限"**【待核：WebKit 博客 2020-03《Full Third-Party Cookie Blocking and More》】：Safari 对"在 7 个使用 Safari 的日子里用户都没有在这个站点上交互过"的站点，删掉它全部脚本可写的存储（IndexedDB、localStorage、Service Worker 的注册与缓存等）；计的是用了 Safari 的日子，不是日历日；用户在站点上的点按、键入会重新计；加到主屏幕（macOS 上加到程序坞）的网页应用有自己的计数。
  - **与 14 天保留期的关系**：发件箱的保留期是 14 天，而 Safari 可能在第 7 个使用日就删掉草稿——用户留下没同步的修改、之后一周多不打开平台，草稿可能已经没了。这比 14 天短，计划书 §4.5 的已知限制与本机草稿页（P4）要写明"Safari 可能在大约一周不访问之后清除本机草稿"。
  - 持久保存（`persist()` 获准）是否让站点免于这条 7 天的规则【待核】；本报告实测的只是新源上 `persist()` 的结果。
- **存储压力**【待核：WebKit 博客 2023《Updates to Storage Policy》，Safari 17】：每个源的配额是磁盘的一部分（浏览器应用约 60%，整体约 80%），超出时按最近使用的先后清掉非持久的源；获准持久保存的源不被自动清。
- **用户清除**：设置里清除网站数据、"清除历史记录"会删掉草稿；私密窗口关闭即清。
- **能验证的**（本轮实测）：`persisted()` 的状态与 `persist()` 在新源上的结果、配额的大小；同一会话里关页、重开之后数据还在、页面进程崩溃之后数据还在留给 P3。
- **不能验证的原因**：要真等 7 个使用日、把磁盘写满或改 Safari 的设置——都不做。
