# P3-S3 手动恢复与冲突处理：实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: 使用 superpowers:executing-plans，由当前实现者在唯一 P3 worktree 逐任务执行；使用既有独立审查者审查，不另开 Task 分支。

**Goal:** 把 S1 判定和 S2 事务/来源接到真实文档页，让未同步内容可恢复、可复制、可明确放弃，并保留所有未知结果和权限边界。

**Architecture:** Reader 管宿主/钥匙/条件动作；恢复协调器管事实与一次用户动作；EditingDraft 管来源生命周期；EditMode 管 SDK、编辑权及打开屏障；Chrome 只展示状态和发出动作。沿用既有保存、副本与确认框，不新增第二套上传协议。

**Tech Stack:** TypeScript、React、现有 Univer 适配器、Vitest、Playwright 三浏览器；无新依赖。

**Spec:** `../specs/P3-S3-手动恢复与冲突处理.md`，基线 `4aa77f92`。

## 全局约束与审查重点

- 主目录 main 不动，分支 `codex/m4-p3-recovery`；一整个 Phase 完成后再 no-ff 合并并仅推 main。
- 测试 PG 53522，不设置 CI，不触碰用户库/真实 Safari；运行任何检查时不编辑源码、测试、文档或提交。临时 JSON 原件放工作树之外，避免被全项目 lint 扫描。
- 保持平台 180 KiB/2 文件、发件箱 Worker 15 KiB 原预算；恢复实现仅由编辑器入口加载。
- 五类优先反例：已确认旧请求之后云端又有新修订；旧钥被误判损坏；登记之后继续使用旧观察；内存恢复成功上传之后清掉别人新登记的记录；换人/失锁之后 SDK 创建或副本结果迟到。分别归属 Task 1、1、2、2、3/4。
- 公式等待上限 10 秒。恢复必须先打开自检与收齐，再捕获/采用；没有额外输入也必须标脏并被现有调度上传。

## Task 1：独立 Reader 与原样核对

**Files:** 新增 `apps/web/src/features/sheet-editor/recovery/recovery-reader.ts`、`resolve-recovery.ts` 及对应 `.test.ts`；复用 S1 `recovery-decision.ts` 和 `editor-api.ts:replayContent`。

**Interfaces:** `createRecoveryReader(options): RecoveryReader`；Reader 提供 `observe(): Promise<ObserveResult>`、`refreshKey(version): Promise<ObserveResult>`、`remove(observation): Promise<ObservedRemoveResult>`、`notices()`、`clearNotice(at)`、`dispose()`。options 固定用户/文档，注入 host/keeper/clock/still。`resolveRecovery({ observed, facts, replay }): Promise<ResolvedRecovery>` 交回原观察与 S1 决定；replay 只调用无租约的旧请求 API。`decodeRecovery(record)` 解码完整 UTF-8 快照，失败有类型化损坏结果。

- [x] 红灯：无记录不取钥；部署关闭仍能读；旧钥刷新一次、更新格式不解压；暂停/关闭/换人使迟到宿主/钥匙失效；remove 只用原宿主凭证。
- [x] 红灯：重放的字段与 gzip 逐字节相同；成功只返回 confirmed 决定；明确租约拒绝重判；网络/超时/其他拒绝不假装未提交；较新的捕获绝不套旧请求。损坏 gzip/UTF-8 不交给 SDK。
- [x] 实现 Reader/解析器；S1 判定仍是唯一分支表，不在 UI 再写一个版本。运行 `pnpm exec vitest run --project unit-web apps/web/src/features/sheet-editor/recovery`，确认新增反例通过和原 S1 回归不变。

## Task 2：协调器、来源准备和初始未同步状态

**Files:** 新增 `recovery/document-recovery.ts`、`recovery/recovery-initializer.ts` 及测试；修改 `editing-draft.ts`、`editing-session.ts`、`save-coordinator.ts`、`autosave.ts` 及对应测试。

**Interfaces:** `DocumentRecovery` 提供 view/subscribe/discover/prepare/restored/copy/beginDiscard/discard/retryCleanup/acknowledge/suspend/dispose；视图不含正文。`RecoveryInitializer(context)` 返回 `none | memory | blocked | restore`；context 区分本次准备是 empty、可显式恢复的 existing（带 observe/remove/retire）或 memory（使用独立 Reader，保留可选 recordKnown 存在事实）。返回 memory 只许可从未见原件且浏览器明确 denied/unsupported 时固定编辑云端内容，不代表恢复成功。restore 携带短期 `capture`、`baseRevision`、`highWater`、可选 `recoveryObservation` 及不持有正文的清理/释放回调。`EditingDraftOptions.recover` 可选；`EditingDraftReady` 增加 blocked，成功恢复在 ready 标出 restored。`SaveCoordinatorOptions.initialUnsaved` 显式起步，Autosave 接受来源既有初值并启动上传计时。

- [x] 红灯：默认 existing-draft 保护不变；恢复回调在本次登记之后观察；初值序号高于观察高水位，打开失败/取消时没有 adopt；采用 changed/fenced 返回 blocked，quota/no-key 保持内存原件。
- [x] 红灯：editorSeq=0 的恢复为 dirty，自动上传不需要一次额外输入；真正确认后 clean，确认前新增输入仍 dirty；普通打开仍 clean，公式正常策略不变。
- [x] 红灯：内存恢复在原文档确认之后且原凭证仍有效时条件清理，错误来源/复制的上传引用/副本 revision 不触发；清理失败可以重试、changed 保留新记录；Worker adopt 超时→内存确认不得重新 observe/自动删除，源销毁后迟到确认也不清理。
- [x] 实现初始化回调与正文转移：不把 capture 放进长期 options/ready 结果；确认后的清理包装只接收经过 WorkingDraft 验证的上传。沿现有 session/keeper 生命周期停写，不新建暗中的登记或 force。
- [x] 定向跑 recovery、editing-draft、editing-session、save-coordinator、autosave 和 working-draft 全部测试；类型/lint 通过后进入 Task 3。
