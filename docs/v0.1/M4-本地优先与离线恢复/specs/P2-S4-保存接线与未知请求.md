# P2-S4 保存接线与未知请求：需求规格

> 状态：依据已批准的 M4/P2 范围自审实施｜日期：2026-10-10｜基线：`b639eca4`

S3 已完成两种工作草稿来源。S4 将自动捕获、保存协调、编辑会话和失效副本接到同一个来源，保持 M3 的输入提交、公式等待、捕获节奏、离开提示及云端事实。用户已授权逐步自主推进；本 Step 不增加恢复入口、全局清理或联网产品文案。

## 1. 接线与所有权

- 同步段内读取 editorSeq、序列化并调用 WorkingDraft.capture；UTF-8 大小来自返回的引用，不再额外编码计数。
- autosave 最新槽位只持有 DraftCaptureRef；不留 JSON、摘要 Promise 或 gzip。捕获即启动本机写入，不依赖联网/登录可上传状态；暂停、终态规则仍由既有调度决定。
- SaveCoordinator 只保留元数据和一份固定 PreparedDraft。先等待本机写入尝试、再等 markInFlight、最后发 HTTP；存储失败保留原 gzip 并通过明确结果上报本机保障，不能当作云端失败或伪造持久成功。栅栏失效按会话的服务端裁决处理。
- SaveRequest 不含 snapshot；包含不可变 requestId、clientInstanceId、真实 contentSeq 作为 localSeq、基准、公式标记及 format。API 使用请求冻结的 format，重试不重新压缩。
- 云端去重仍使用摘要和公式标记；显式保存不去重。已确认的同内容新捕获也须确认到其 editorSeq，并清理/更新对应本机记录，不能留下假未同步记录。摘要不可用就不推断内容相同。
- 云端确认先记录其事实，本机 confirm 的失败另行报告；协调器在下一次准备前等待本机确认收尾。adoptOwnRevision 保持同步布尔返回，持久收尾串行，迟到原请求不能倒退修订、重复清理或覆盖新捕获。

## 2. 未知请求与单份上传

现有 M3 可以在 A 结果未知时发送不同内容 B，同时留下 A 的 JSON 供 B 被拒后重放。这需要两份固定请求正文，与已批准的 M4 单份上传上界不相容。S3 的 DraftBusy 已明确拒绝第二个 pin，不能绕过来源在协调器另藏正文。

选择在下一次上传轮到时先原样重放 A；成功或确定未提交之后释放 A，才准备最新捕获。仍未知、登录/令牌或读取权限使结果无法判断时，保留 A，沿用错误分类和退避，暂不发送 B；B 仍继续捕获进来源，不会丢失。一次调度不循环重放。重放成功且当前内容能由引用或可靠摘要证明相同，则确认当前捕获；内容不同再发新请求，使用已确认的新基准和新的 requestId。

这仅细化未知结果时的网络顺序。正常的捕获、上传触发、退避时长、按钮合并和输入提交不变；没有未知结果时显式保存仍发请求。原 M3 的以下业务保障保留，相关测试按新请求顺序调整而不能删掉：

1. 原请求的标识、字节、基准、格式和公式标记完全相同；新内容绝不套旧标识。
2. 终态前已有未知请求要核对，不能把可能已经提交的内容说成未保存；较新的内容仍显示未保存。
3. 续上识别本页来源时接受已提交事实；晚到网络失败不抹掉已知成功。
4. 登录/CSRF/404 的拒绝不能推断更早那次没提交；真正冲突不能自动覆盖别人。

不选择第二份长期上传缓存，也不选择释放未知正文后用最新内容重放。它们分别破坏内存上界与服务端幂等。

## 3. 编辑会话、租约与密钥

服务端批准、本机锁之后，按当前内容基准准备来源；来源 ready 之后才创建可交互编辑器和保存调度。打开自检失败、准备期间退出/换人/失效必须最终关闭宿主，不开始保存。部署关闭与能力缺失走内存，已有草稿保留。

会话拥有来源及 keeper 订阅；阅读时不取钥。有效心跳的 localKeyVersion 交给 keeper；停用旧钥、新钥重写通过 S3 生命周期方法，晚到发布不得装回旧会话。退出登录/换人先停持久写入再丢钥，当前内存正文仍可留给既有失效流程。

本机锁被抢时在核对请求前同步 suspend 来源；锁恢复持有后经 source.resume 的服务端核对才能恢复持久化。核对未知期间仍可内存捕获。租约续上可能更换 writeEpoch：准备器读取当前代次，准备中代次变化作废旧结果，已准备宿主的旧代次不能继续写。高水位吸收和已有内容处理仍用 S3 契约，不自动 adopt 别页记录。

## 4. 失去编辑权与副本

失效时先停自动捕获和持久写入，按 M3 顺序提交面板/单元格并立即捕获到同一个来源；等待公式的规则不变。临时 readLatest 得到文本仅用于只读重建，用完释放，不在副本模块保存字符串。

等待原保存和一次未知结果核对完成后，原协调器可结束；只有结束原请求所有权后，副本才能准备自己的固定上传。用户选择副本后，原保存不再重试；这属于结束原流程，不是把未知请求判断为未提交。当前来源和持久记录继续保留。副本的 requestId、标题、format、公式标记及 gzip 固定，未知重试不重新压缩；确定拒绝允许新请求。页面重建失败不能抹掉已创建副本的链接。流程放弃、重载成功或卸载时唯一释放来源。

副本成功不拿新文档的 revision 去 confirm 原文档；本 Step 不引入 P3/P4 的恢复或清理决定。已有原草稿的后续处理沿用其真实元数据，不谎称原文档已同步。

## 5. 验收与自审

- 原 M3 的编辑器、保存、自动保存、副本、交接和会话故事继续覆盖；只调整明确改变的序号、数据接口及未知请求发送顺序。
- 真来源证明 editorSeq 重置而 localSeq 继续、先写本机再上传、unknown 字节不变、旧确认保留新捕获、本机失败不阻上传、失效副本接同一内容。
- 确定交错覆盖准备与锁/租约/换人、心跳换钥、未知重放期间新编辑、原确认与副本移交。
- 三浏览器运行完整编辑器回归；接入后的生产发件箱 Worker 预算不超过 15 KiB，平台入口不超过 180 KiB 且最多 2 文件。

自审：网络顺序的变化由单 pin 所有权约束直接推出；本机和云端事实分开；锁与租约的服务端裁决未下沉到 Worker。S5 的联网事实及本机提示、S6 的测量和完整门禁继续按原计划执行。
