# P4-S2 共享恢复与清理资格：规格

> 日期：2026-10-14｜状态：实现、自审及 Step 验收通过｜基线：a515b280｜上层：04-P4-本机草稿页与本机清理.md §3.1、3.3–3.5

## 1. 范围

把 P3 已验证的无界面恢复、原样重放、固定副本请求与条件删除提取到共享层，供编辑器及后续草稿页复用；建立持久的会话资格，阻止清理后的迟到登记/写入，以及新登录之后的旧清理。S2 绑定资格但不增加退出确认界面、不根据错误自动删除数据；这些触发与用户提示归 S3/S4。

现有不足是具体的：`retireUser` 只能停用已经存在的写入者，`removeUserData` 完成后，未登记过的旧页面仍能登记；`removeUser(userId)` 的重试也不认识重新登录。广播和一份新目录快照均不能填补这个空隙。

## 2. 共享层

- `shared/local-drafts/` 接收 recovery-decision、resolve-recovery、recovery-reader、document-recovery、recovery-initializer 类型及副本协调。保留 P3 原规则、错误分类和原件观察所有权，不能复制一份草稿页判定器。
- WorkingDraft 的纯类型、来源调度和内存实现一并共享；编辑器的捕获、SDK 安装、公式、编辑租约、文档锁与控件仍在 sheet-editor/editor。`captureLostContent` 留在编辑器，副本请求固定与结果分类移到共享层。
- 无 SDK 的宿主、Worker 客户端/协议/处理器和生产 Worker 移到 shared/outbox；编辑会话和持久 WorkingDraft 的编辑器适配仍在原处。时钟使用共享的纯接口，Worker 不导入页面 API、Zod 或 React。
- 平台入口只能动态载入草稿管理与会话资格实现；共享层不能反向导入 app、features 或 editor。现有 lint 规则按明确的新模块位置调整，并用正反例验证，不能整体豁免 shared。
- 一次只借用当前草稿的正文。未知副本结果继续保留原 requestId、标题和 gzip，成功或确定拒绝才结束固定上传；条件清理仍使用完整原件、写入者及产生观察的活宿主，不能退回只比序号。

## 3. 持久会话状态

浏览器同源共用一套 Cookie，因此只需在 outbox 的新对象仓库保存一条当前本机会话状态；这条状态包含当前用户与清理资格，不再按文档推定用户是否退出。数据库版本从 1 升到 2，只新增仓库，旧草稿、写入者及提示格式不变。状态在完成清理后仍保留；保留期回收不得删除它，防止旧资格重新有效。

状态字段仅为非秘密元数据：固定 slot、每次转移新生成的 UUID generation、状态、已识别的 userId、会话来源摘要和清理原因（clearing 本身表示 pending，不重复保存布尔值）。active 另记 activatedFrom，限定可共享本次激活的并发票据；unconfirmed 记录是否有变更请求未决、此前来源是否已经退役。来源摘要为带用途前缀、用户 id 和 CSRF 令牌的 SHA-256；不保存 Cookie、CSRF 原值、密钥或正文。现有服务端的 CSRF 在同一条会话内稳定、换会话时改变。摘要只比较本机操作来源，不能用来向 API 认证。

| 状态 | 允许的事情 |
|---|---|
| unconfirmed | 尚无经确认的本机来源，或登录/改密等变更正在进行；不接受草稿写入或删除 |
| active | 持有相同 userId/generation 的宿主可以执行用户级存储操作；文档写入另受原写入者栅栏约束 |
| suspended | 当前来源暂停；不删除草稿，新的会话复核可产生新资格 |
| clearing | 已建立明确退出/已核实停用的清理资格；旧宿主不再写，只有该资格可以清理与重试 |
| cleared | 本机清理已完成，保留失效代次；同一旧来源不能借迟到会话回包恢复写入 |

`DraftSessionPermit = { userId, generation }` 是宿主的非秘密资格描述。Worker 接收它后仍须核对数据库，传字段本身不能绕过状态。每个宿主只绑定一次，换资格必须关闭旧宿主、以新资格重建；未绑定或资格已失效时拒绝用户数据操作，不自动读取“当前代次”代替旧来源。

## 4. 会话请求与迟到回包

先建立本机检查票据，再发出真实会话请求；票据记录请求开始时的 generation。空库先写入随机初始代次，不能把两次“无记录”当作同一个时刻。请求与摘要计算在 IDB 事务及发件箱互斥之外完成。

- 普通会话查询只观察代次，不中断仍有效的写入。
- 登录、改密、接受邀请和完成重置属于会话变更：发请求前先以新代次转入 unconfirmed，让旧写入和清理失效。失败保留数据，后续真实会话复核决定能否恢复。
- 返回时以原票据比较并交换。仍是同一代次才可按真实响应激活；并发查询只有来自当前 generation 或本次 activatedFrom 且来源相同，才可共享 active 资格，更早代次不能借此复活。
- 会话变更未决时普通查询不能抢先激活旧 Cookie 的来源；只有该次变更回包可完成激活。变更失败只在票据仍匹配时结束未决状态，转到新的 unconfirmed 代次，之后须发出新的真实查询；旧失败不能撤销已成功的新登录。
- 未决状态保存开始时间与 60 秒截止窗口，大于当前请求层 30 秒完整时限。浏览器在网络期间关闭后，下一次查询可在窗口到期或本机时钟回拨时以新代次结束遗留状态，再发真实请求；没有下一次查询时，超期变更回包本身也不能激活。时间仅取消资格，不授予恢复或清理资格；退役来源标记仍保留。窗口内其他查询的认证结果照常返回，本机资格暂不授予。
- 旧查询遇到 clearing/cleared 的相同来源不能重新激活；遇到不同来源或不同的未决变更不得抢占。不同的新来源只有与检查票据一致时才能激活。
- 从清理状态开始新的登录变更时仍记住已退役来源；即使新登录失败或再次重试，也不能让原来源重新取得资格。只有真正不同的会话来源才能解除这项限制。
- 一个旧响应不能重新拍一张票据来包装自己；需重查时必须重新发真实请求。票据过时/数据库不可用只使本机资格不可用，不伪造认证失败，也不能拦住本来应该结束的服务端会话。
- 返回的 SessionResponse 仍符合原契约；本机资格通过同一响应对象的内存关联交给调用方，不向服务端响应塞自定义字段。编辑器/恢复读者在开始创建宿主时固定它，异步准备不能偷换为后来那次登录。
- 会话查询和登录/改密等直接写入查询缓存时必须保留原响应对象，禁用该查询键的结构复用；相同字段的新响应也可能属于不同代次或没有本机许可，不能沿用旧对象的关联。其他查询仍按原规则复用。

会话入口统一包装上述过程，不分散在 React 组件里实现。S4 再把明确退出、已核实停用、普通失效保留和广播接入生命周期；S2 不因单独收到 logout 原因清理。

## 5. 原子存储与镜像顺序

所有用户级存储操作在它自己的事务中读取会话状态、核对绑定资格，再读/改草稿、写入者和提示。登记、写入、重封、确认、原子接手、条件删除、镜像回写与提示修改均不可漏掉；读者同样不能在换人后继续借用旧资格。IDB 的检查与修改之间不 await 外部异步。原文档的 writeEpoch/writerId/高水位/完整观察仍照常核对。

会话状态转移、一次完整主库+镜像操作、清理和新激活共用既有同源发件箱互斥。同一把锁内不重入；开始执行后等实际完成再释放，不用超时 Promise 提前放行。网络请求不持锁。清理若先取得锁，只能完成新激活之前的一次操作；新激活若先取得锁，旧清理不碰库或 OPFS。

存储按职责分开用户操作与维护操作，Worker 不携带它用不到的用户批量删除/保留期维护实现。共用连接与 strict 事务工具，不能复制两套存储规则。全用户保留期维护仍按原规则，不获取正文、不展示他人标题，也不回收会话代次。

## 6. 清理协调

清理必须从匹配的 active 资格开始，原因只接受用户已确认的 logout 或已核实同一用户的 account_disabled；在同源锁下持久化 clearing 后交回 `UserCleanupPermit`。该许可绑定用户、代次和原因，后续每轮重试均重新核对持久状态。

在原有顺序中清理：停用该用户全部写入者 → 清镜像 → 清主库；镜像忙/失败的文档保留墓碑及 pending 事实，不能声称清空。迟到登记即使 force=true、文档从未有写入者也被会话资格拒绝。完毕后转入 cleared，保留代次；pending 则保留 clearing，后续可从该持久事实接续。

新会话变更开始、同一人新的登录激活或换人，使原许可失效。旧回包不能把新状态改回 clearing/cleared；旧 pending 操作不能删除新一轮写下的记录。草稿页逐条放弃继续调用共享恢复读者的完整观察条件删除，不使用历史 `abandon(key, expectedSeq)` 作为用户操作入口。

本机清理与服务端退出是两个结果。S2 只交回清理事实/资格；S4 必须在清理失败或 pending 时继续结束服务端会话，按原资格处理未知结果，且新登录后不延续旧退出意图。
