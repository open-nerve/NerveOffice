# M4 本地优先与离线恢复：总设计

> 文档编号：00｜所属版本：v0.1｜状态：已评审（2026-10-09 审批通过），进行中｜日期：2026-10-09

## 1. 目标与范围

- **目标**：断网不丢，崩溃可以恢复。修改先加密写进浏览器的本机发件箱，再同步到服务器：网络只影响同步什么时候完成，不影响已输入的内容还在不在。浏览器崩溃、被误关或被杀之后，联网重开能恢复到最后一次写入本机的内容；同一浏览器换一个标签页接着编辑时，没同步的修改随之接上；真冲突一律另存为副本，绝不自动覆盖；退出登录、撤权之后，这台设备上不留不该留的草稿。对应 00 号计划书 §13.2 的 M4 一行（按 r21 调整，见 §6.12）。
- **范围内**：
  1. 本机发件箱（计划书 §7.5、§7.6）：IndexedDB 里每个用户的每份文档一条记录，AES-GCM-256 加密（密钥是 M3 的本机密钥）；发件箱 Worker 做去重、压缩、加密与写入；`durability: 'strict'`；写入栅栏。另把同一份记录镜像进 OPFS：Chromium 崩溃重开时可能删掉整个来源的 IndexedDB（M4-P1 的发现，§6.1 的"OPFS 的冗余"）。
  2. 本地优先的保存管道（§7.2）：M3 的两级自动保存不变，捕获改为写进发件箱，上传取发件箱 Worker 压缩好的同一份数据，服务端确认之后只删到已确认的序号。
  3. 离线体验（§7.5、§7.7）：断网照常编辑、写进本机；横幅与页头的状态；需要服务端参与的操作离线时不可用；恢复联网之后自动续租或续上、同步。
  4. 恢复与冲突（§7.5）：重新打开时发现未同步的修改；能快进就恢复、接着编辑；"自己追自己"；真冲突另存为副本或放弃；"公式待更新"的强制重算；同一个标签页意外重新载入时自动恢复（§2.1 第 4 条）。
  5. 标签页协调（§7.5，在 M3 的 Web Locks 之上）：写入栅栏；锁被抢时先停写、按服务端的裁决处理；本人接管时从发件箱接手（DEF-064）。
  6. 本机密钥的客户端（§7.6）：取用、导入、交给 Worker、版本变化时换用新密钥；解不开时区分"已吊销"与"已损坏"。
  7. 本机草稿页与列表的标记（§7.7，§2.1 第 3 条）；存储状态、写满与不可用的提示。
  8. 本机清理（§7.5、§7.6）：退出登录；撤权、移出空间、取消分享、删除与移走；账户停用（经会话失效的原因，§2.1 第 1 条）；14 天的保留期；Univer 自己的本机存储；M3 留在浏览器里的记号。
  9. 敏感部署关闭本机草稿（§7.6，§2.1 第 2 条）。
  10. 公式 Worker 起不来时以主线程模式重建；评估 Worker 内的让出间隔（§10.2）。
  11. 真实浏览器的复核：存储行为（DEF-009，断电在虚拟机里模拟，§2.1 第 5 条）、发件箱 Worker 的停顿（DEF-011）、捕获成本与性能基线（DEF-012）；真实 Safari 上的崩溃恢复与持有者的页面真的被暂停（DEF-069，§2.1 第 6 条）。
  12. 目标为 M4 的其余延期项：DEF-041（请求的时限）、DEF-059（不处理，§2.2）、DEF-064（本人接管的时限）。
- **范围外**（归属以 00 号计划书 §13.2 为准）：
  - 离线冷启动：断网时打开平台、打开文档（计划书 §7.8 不承诺；恢复要联网取密钥）；
  - mutation 增量日志（DEF-010，v0.2）；
  - 记录的键改为按用户密钥计算的 HMAC、防本机回滚（计划书 §7.6 的已接受风险）；
  - 草稿跨设备同步（草稿只在这台设备的这个浏览器里）；
  - 插入图片、CSV 导入在离线时禁用，随 M5 的功能一起做（M4 定下规则）；文字文档接入发件箱在 M6（发件箱按与文档类型无关来设计）；
  - 主密钥轮换、批量作废、压测（M7）。

### 2.1 启动讨论中已确认的决定（2026-10-09）

| # | 事项 | 决定 |
|---|---|---|
| 1 | 账户被停用时的本机草稿 | 服务端在会话失效的回应里带上原因（账户停用、密码被重置、过期），只给持有这次登录的请求。页面收到"账户停用"就删掉此人在这台设备上的全部草稿，并说明原因；收到"密码被重置"就提示重新登录，草稿保留。登录页照旧不暴露停用；被停用的人会从开着的页面得知自己被停用 |
| 2 | 敏感部署关闭本机草稿 | 做成部署配置：环境变量，与"最低客户端构建版本"等运维开关一样，改了重启生效，页面经服务端得知。关闭时修改只在页面内存里，加离开提示（M3 的做法），页头写明风险；设备上已有的草稿照常可以恢复或另存为副本，处理完删除，不再新写 |
| 3 | 未同步的修改在哪里集中查看 | 除了文档列表标出"未同步"、打开文档时提示，账户菜单里加一页"本机草稿"：列出这台设备上属于本人的全部未同步修改（含已经打不开、只能另存为副本、解不开的），逐条恢复、另存为副本或放弃，并显示本机存储的状态。退出登录的提示指向这里 |
| 4 | 意外重新载入之后 | 同一个标签页意外重新载入（浏览器回收了后台标签页、Safari 的页面崩溃后自动重载、误按了刷新），期间没人存过、没人在编辑，就自动回到编辑并恢复修改，页头说明"已恢复 14:32 未同步的修改"。接不上，或者是重新打开文档、换了标签页，照计划书提示"发现 14:32 未同步的修改" |
| 5 | 断电的验证（DEF-009） | 在虚拟机里模拟断电：Linux 虚拟机跑 Chrome、Edge，macOS 虚拟机跑 Safari；写入之后强制关掉虚拟机，再开机核对报告过完成的写入还在不在。结论写进丢失边界（计划书 §7.8）与已知限制。它测的是浏览器在报告写入完成之前有没有把数据交给磁盘，不测硬盘自己的缓存 |
| 6 | 真实 Safari 上动进程 | 同意由驱动脚本对承载测试页的那一个 Safari 页面进程做"结束"（崩溃恢复，A16 的 Safari 部分）与"暂停再继续"（DEF-069）：只在用户空闲时跑；认准那个进程才动，认不准就跳过并记下；不碰 Safari 的主进程和用户的其他标签页。DEF-069 由 M7 提前到 M4 |

### 2.2 本设计的细化（随本总设计一起审批）

- **离线时**：
  - 已在编辑的页面照常编辑、写进本机；阅读中的页面照常阅读。
  - 不能进入编辑（编辑权要服务端批准），不能离线冷启动打开文档（计划书 §7.8）。
  - 分享、移动、改名、复制、删除、请求编辑等需要服务端参与的操作，离线时不可用，并说明原因。
  - 离线超过编辑权的有效期（90 秒）时说明：恢复联网之后，如果别人在这期间存过，你的修改会另存为副本。
  - 是否离线看请求的结果（网络错误、超时），结合浏览器的联网事件，不只看 `navigator.onLine`。
- **页头**：按计划书 §7.7 增加"已保存在本机（等待同步）""已离线，修改已保存在本机""本机存储空间不足""本部署关闭了本机草稿"。离开提示照旧：还没同步到云端就拦。已经写进本机的也拦，因为别人还看不到，换了设备也取不回。
- **写入栅栏按服务端的代次排先后**：
  - 发件箱为每份文档记下"当前写入者"（这一代的代次与每次登记随机生成的 `writerId`），只有代次更大的能登记；写入、删除都在同一个事务里核对，不符就中止。
  - 锁被抢的一方先停写，再向服务端核对：确实被取代，才把记录交给新的写入者；仍是当前的，就恢复写入（M3 交接单）。
- **草稿序号**：发件箱用一条持久、单调的序号，每份文档一条线，恢复之后接着编。"只删到已确认的序号"比较它，上传带的 `localSeq` 也改用它。编辑器的修改计数每次重建都归零，这两处都不能用它。
- **"自己追自己"的判法**：发件箱每份文档只留最新的一份；被新的捕获覆盖之后，原来的请求再重放，服务端会判为"同一个请求标识、不同的内容"而拒绝。所以恢复时：
  - 记录就是在途的那一份时，按原样重放（原来的字节、基准修订号、标记与版本）；
  - 否则看服务端当前修订的来源，是不是记录里在途的那一次（客户端实例与序号）；
  - 两条都认不出，按真冲突处理（给副本），不自动上传。

  记录因此要存下在途请求的这些字段（计划书 §7.5 的字段表补上）。
- **本人接管（DEF-064）**：保留 20 秒的总时限。到点之后，新标签页抢锁、登记为写入者，从发件箱接过旧标签页没同步的修改，不再只剩副本一条路。
- **时限（DEF-041）**：保存、申请编辑权、核对与续上的请求都加应用层的时限，到点按"结果未知"处理——保存按原来的请求标识重试；申请沿用 M3 的"结果未知的申请"记号。页面说明"网络没有回应，正在重试"。
- **DEF-059 不处理**：去掉"没人引用的样式"会改变内容哈希的规格；引用的地方一旦认漏，就会把真修改判成"内容相同"而静默丢掉（计划书 r16 的原则）。它的好处只是"改了又撤销"之后少一个修订。客户端也不复现规范化：内容是否相同由服务端判断，会话内去重照计划书 §7.2 用原文的哈希。
- **Univer 自己的本机存储**：
  - 用依赖注入换成内存实现，Univer 不再往浏览器里写。数字格式的使用习惯、最近用过的表情随之不跨页面保留。
  - `@univerjs/ui` 加载时就会建 `UniverLocalStorage` 库，这一步挡不住；清理时删掉它，以及 `UniverLocalStorage/` 开头的键。
- **M3 的记号**：`pending-save`、`edit-request` 两类记号改为按用户区分，列进清理清单。
- **公式 Worker 起不来时**：
  - 判定：创建时抛错、脚本加载失败、就绪之前出错或握手超时，以及就绪之后 Worker 崩溃。
  - 处理：销毁编辑器，以主线程模式的档案变体重建；M3 的"计算中先停下再销毁"必须保留。
  - 页头说明"公式在本页计算，大表格可能卡顿"，并上报（与打开自检同一个通道）。
- **开工前的复核**（P1）：真实 Safari 与 Chrome 上的存储行为、发件箱 Worker 的停顿与空定时器、捕获成本与性能基线。结果可能改变放置，例如 WebKit 改在主线程压缩（P1 的结论：三个浏览器都保留 Worker 放置，ADR-020）。
- **崩溃的 E2E**：用持久化的浏览器目录，结束整棵浏览器进程，再以同一个目录重开。本机（macOS）与 CI（Linux）各有一套认进程的方法，断言被结束的进程数。
- **保留期**：14 天的常量放进前后端共用的契约；服务端修订记录保留期的下限由它推出（至少多 1 天），不再各写一处。
- **批量查询文档**：本机草稿页与清理要知道一批文档的标题、能否读写、当前修订号、是否有人在编辑。新加一个批量的只读接口，复用权限的单一入口；看不到与不存在同样回答。

## 3. 用户故事

E2E 用例的标题以故事编号开头。浏览器 E2E 在本机的 Chromium、Chrome、WebKit 上通过，CI 上另加 Edge；崩溃的用例在本机（macOS）与 CI（Linux）上都要跑通。与时间有关的规则（离线 10 分钟、编辑权的有效期、14 天）用可控的时钟，不真等。

| 编号 | 角色 | 故事 | 验收 |
|---|---|---|---|
| US-M4-01 | 编辑者 | 修改先存进本机，再同步到云端 | 修改停顿约 1 秒就加密写进本机发件箱，页头显示"已保存在本机"；随后上传，服务端确认之后显示"已保存到云端"，并删掉本机记录（只删到已确认的那一次）。上传进行中继续输入的修改不会被标成已保存，也不会被删掉（A08）。没同步到云端时离开页面照旧提示。内容没变时不重复写入本机 |
| US-M4-02 | 编辑者 | 断网时照常编辑，恢复联网后自动同步 | 断网后横幅提示"已离线，修改已保存在本机"，修改持续写进本机。需要服务端参与的操作不可用，并说明原因；离线超过编辑权的有效期时，说明恢复之后可能另存为副本。恢复联网后自动续租或续上，期间没人接手就把最新的内容同步上去（快进）。断网持续编辑 10 分钟（可控时钟）之后照样全部同步（A15 前半） |
| US-M4-03 | 编辑者 | 断网期间别人接手并保存了，不覆盖对方 | 恢复联网之后，页面得知别人在这期间存过：本机的修改可以另存为副本或放弃，服务器上的版本不动；旧内容的提交一定被拒绝（A15 后半、A05 的离线部分） |
| US-M4-04 | 编辑者 | 浏览器崩溃、被误关或被杀之后，联网重开能恢复 | 重新打开这份文档，或从文档列表、本机草稿页进入时，提示"发现 14:32 未同步的修改"；期间没人存过，就一键恢复、接着编辑。记录带"公式待更新"时，恢复之后先全量重算再保存。同一个标签页意外重新载入、能接上时自动恢复（§2.1 第 4 条）。三个浏览器结束浏览器进程之后，联网重开都能恢复到最后一次写入本机的内容；真实 Safari 上结束测试页的页面进程之后同样（A16） |
| US-M4-05 | 编辑者 | 保存的确认没收到就崩溃，恢复时不重复、不误判 | 上传已经提交、确认还没收到时浏览器被结束：恢复时按原样重放，或按服务端这一版的来源认出"是自己存的"——不重复写入、不重复增加修订号，也不误判为冲突（A07 的崩溃部分） |
| US-M4-06 | 编辑者 | 同一浏览器换一个标签页接着编辑，没同步的修改随之接上 | 另一个标签页正在编辑时点"在此编辑"：它先同步再交出；它 20 秒内没完成，本页就接手，并从本机发件箱接上它没同步的修改，不只剩副本（DEF-064）。被抢的标签页立即停写，确实被取代之后转为只读；它在途的写入被写入栅栏拦下 |

## 5. Phase 规划

执行顺序为 P1 → P6，分支依次为 `m4-p1-outbox`、`m4-p2-local-first`、`m4-p3-recovery`、`m4-p4-drafts-cleanup`、`m4-p5-formula-fallback`、`m4-p6-closing`。大的 Phase 可以一个 Step 一个分支。每个 Phase 的详细设计，在该 Phase 开始时基于最新的代码编写。

M4 切成 6 个 Phase（多于通常的 2–5 个），让每次审查的范围小一些。顺序是：
1. 先做发件箱的底座，并在真实浏览器上复核——复核的结果可能改变放置。
2. 再把保存管道接上发件箱（先拆 `edit-mode.ts`）。
3. 恢复与标签页接手随后，它们依赖可靠的写入与写入栅栏。
4. 本机草稿页与清理用到前三者。
5. 公式 Worker 的退路与发件箱无关，放在后面。
6. 最后收尾。

## 6. 架构影响

### 6.1 本机发件箱

- **库**：一个 IndexedDB 库，带版本号，结构变化走库的升级（v0.1 在 M8 试运行之前没有真实用户，升级仍按正式的做法写）。三个对象仓库（草稿、写入者、恢复的提示；M4-P1 加了提示），键都是 `[userId, documentId]`——用平台的文档 id，不用 `unitId`（计划书 §7.5）：
  - **草稿**：
    - 明文的元数据：文档、基准修订号、`writeEpoch`、草稿序号、在途的请求（请求标识、客户端实例、序号、发出时刻）、密钥版本、写下它的客户端实例与构建版本、数据格式、"公式待更新"、更新时间；
    - 密文：gzip 之后的快照，AES-GCM-256，每条一个随机 IV；
    - 附加数据（AAD）覆盖全部参与恢复决策的明文元数据（计划书 §7.6 的清单补上在途请求与更新时间），改动任何一项，解密都失败；
    - 存字节，不存 Blob（WebKit 离线时读不了 Blob）。
  - **写入者**：这份文档当前的写入者（这一代的 `writeEpoch` 与每次登记随机生成的 `writerId`），以及草稿序号的高水位。写入、删除都在 [草稿, 写入者] 的同一个 `strict` 事务里核对。
- **写入**：每次覆盖同一个键，原子性由事务保证（M0 实测，计划书 §7.5）；"只删到已确认的序号"在同一个事务里比较；写满（`QuotaExceededError`）时整个事务回滚，已有记录不变。
- **发件箱 Worker**（每个编辑器页一个）：
  - 主线程只做 `save()`、序列化与一次编码，然后把字节转移给 Worker。
  - Worker 里依次做：去重哈希（与上次写入的相同就跳过）→ gzip → 加密 → 写入；再把 gzip 的结果交回主线程上传。
  - 保持 100 ms 的空定时器（DEF-011）；真实 Safari 上实测有效（M4-P1：带空定时器的发件箱 Worker 0 次停顿），WebKit 保留 Worker 放置。
  - Worker 出错或崩溃时，在途的请求以失败结束、不挂住，页面按"本机写入失败"处理（M0 审查 S5）。
  - 新的 Worker 登记体积预算（门禁）。
- **持久保存**：第一次进入编辑时申请 `navigator.storage.persist()`；结果与用量、配额显示在本机草稿页。
- **M4-P1 实施中定下的**（P1 设计 §1 的偏差，ADR-020）：
  - 写入者不存租约令牌（令牌只在标签页的内存里，ADR-018）；草稿序号的高水位放在写入者记录里，草稿删掉之后序号不回头；
  - 在途的请求不另存公式标记、构建与格式：原样重放只在"记录还是在途的那一份"时做，那时这几样就是记录本身的；
  - 存储层不覆盖别的写入者留下、还没接手的草稿，接手要显式进行（P3）。
- **OPFS 的冗余**（M4-P1 S9，需求方 2026-10-09 决定"冗余 + 如实告知"；ADR-020、UR-034）：
  - 起因：Chromium（含 Google Chrome）的 IndexedDB 在进程被结束于日志写到一半时，再下一次启动会删掉这个来源的全部 IndexedDB（Google Chrome 不注入时 1400 次强制结束里 5 次；WebKit 0/290），应用认不出；localStorage 延后落盘、同样会丢，不能用。
  - 做法：IndexedDB 仍是主存储；每次写成之后同一份记录镜像进 OPFS——只在发件箱 Worker 里用同步访问句柄改写事先建好的两个槽位文件（轮流写、带校验，不碰 Chromium 的 LevelDB）；读时取校验通过、解得开的最新一份；镜像比库新时写回库并留下"已从备份恢复"的提示，库比镜像新时补写镜像，两个槽位都坏、库里也没有时留下"因浏览器存储损坏丢失"的提示；提示存在库里，由 P3、P4 如实告诉用户。
  - 进程内的放置没有镜像，生产里 Chromium 系一律用 Worker 放置（P2 设计 Worker 起不来时的退路要算进去）。防不了清除站点数据与浏览器回收存储空间；本机占用约翻倍。
- **不可用时**：浏览器不让用 IndexedDB（打不开、被策略禁止）时，退化为内存实现，与"关闭本机草稿"走同一条路，页头说明。
- **模块位置**（P1 设计定）：
  - 存储格式、按用户列出与清理，供编辑器页、文档列表、本机草稿页、退出登录共用：放在 `shared` 层，或一个经 `index.ts` 对外的新功能模块；
  - 发件箱管道与它的 Worker 放在编辑器页（`features/sheet-editor`）；
  - 适配层（`editor`）只放 Univer 本机存储的替换与公式 Worker 的退路；
  - 平台页面的首屏只装列表标记要用的那一小块，其余按需加载（首屏的文件数有门禁）。

### 6.2 保存管道（本地优先）

```text
捕获（M3 的捕获时机不变）
  │ 主线程：save() → 序列化 → 编码一次
  ▼
发件箱 Worker：去重 → gzip → 加密 → 写入（核对写入者）──► 页头："已保存在本机"
  │ 交回 gzip 的数据
  ▼
上传（M3 的节奏不变）
  │ 服务端确认
  ▼
删除本机记录（只删到已确认的序号）──► 页头："已保存到云端"
```

- **一个来源**：M3 内存里的三份快照（自动保存的"最近一次捕获"、保存协调留着的重试数据、副本流程的快照）收成发件箱这一个来源；页面内存里只留在途那一份的字节，重试用。
- **拒绝时记录保留**：版本冲突、失去编辑权、容量超限、客户端过旧——数据都不丢。客户端过旧时，刷新之后从发件箱恢复；M3 里"刷新会丢掉本页的修改"的窗口随之关闭。
- **去重**：会话内按 `save()` 原文的哈希，加上"公式待更新"（计划书 §7.2）；内容是否与服务器相同由服务端判断，"内容相同不递增"的回执同样删掉本机记录。
- **本机草稿关闭**（§2.1 第 2 条）**或不可用时**：用同一个接口的内存实现——捕获进页面内存，上传与离开提示照旧。
- **编辑器页的结构**：`edit-mode.ts`（2272 行）编排了全部转移，再加写入栅栏与恢复会失控。P2 先把"编辑会话"（租约、本机锁、写入者的登记、保存的状态机与调度）与"副本流程"拆成各自的单元，用假的编辑器与可控的时钟做单元测试；这一步 M3 的 E2E 全部不改、照常通过；然后再接发件箱。

### 6.3 写入栅栏与标签页协调

在 M3 的本机锁之上（先服务端、后本机锁；锁的争用以服务端的事实裁决，ADR-018）：

| 时机 | 做法 |
|---|---|
| 取得编辑权并拿到锁 | 以这一代的代次与随机的 `writerId` 登记为写入者，只有代次更大的能登记；之后每次写入、删除都核对 |
| 锁被抢 | 先停写（不再交给 Worker、不再删除），向服务端核对：确实被别的一代取代 → 转为只读，记录留给新的写入者；这一代自己失效 → 交给租约已有的失效处理；仍是当前的 → 恢复写入 |
| 本人接管（同一浏览器） | 旧标签页在：它先同步、再交出、释放锁。20 秒内没完成：新标签页抢锁、登记为写入者，读旧标签页留下的记录，按 §6.4 接上（DEF-064） |
| 本人接管（跨设备） | 草稿只在本机；旧设备之后得知失去编辑权，它的记录按 §6.4 处理——新设备已经存过就是真冲突（给副本），还没存就是"别人正在编辑、还没存" |
| Web Locks 不可用 | M3 退化为"当作已持有"；这时真正的防线是写入者的核对 |
| 同一浏览器里退出登录 | 广播，让其他页面停写、丢掉密钥。清理与写入在同一个库里按事务排队；清理之后才到的写入，因写入者已被删除而中止 |

### 6.4 恢复与冲突

恢复只在取得编辑权、拿到本机锁、登记为写入者之后进行（计划书 §7.5）；待决定期间，页面是阅读模式。恢复要联网取密钥，离线时提示"联网之后可以恢复"。

| 情形（与服务端当前的修订比较） | 行为 |
|---|---|
| 当前修订号等于记录的基准 | 用记录的内容以可编辑重建编辑器，接着编辑；随后的上传就是快进。记录带"公式待更新"时，先强制全量重算、收齐之后再保存 |
| 记录就是在途的那一份 | 先按原样重放：已提交，就得到原来的结果，以它为基准（内容相同，删除记录）；没提交，就按其余各行判断 |
| 当前修订号比基准大 1，来源是记录里在途的那一次 | "自己追自己"：以当前修订为基准，用记录的内容接着编辑、上传 |
| 别人在这期间存过（其余情况） | 真冲突：另存为副本或放弃，服务器上的版本不动 |
| 别人正在编辑、还没存 | 可以请求编辑（拿到之后接着恢复）、另存为副本，或者先留在本机 |
| 只能阅读了（被降级、空间归档、移到只能读的空间） | 另存为副本或放弃，之后删除记录 |
| 读不到了 | 删除记录，并说明原因（不给副本，计划书 r13） |
| 解不开 | 记录的密钥版本小于当前版本 → "密钥已吊销，无法恢复"；否则 → "记录已损坏，无法恢复"。都删除 |
| 记录由更新的客户端写下（数据格式比本页新，例如部署回滚之后） | 不动它，说明需要更新的页面 |

- **入口**：
  - 打开文档时：阅读模式下的提示条"发现 14:32 未同步的修改"，按情形给出上表的操作；
  - 文档列表的"未同步"标记；
  - 本机草稿页。
- **自动恢复**（§2.1 第 4 条）：
  - 依据：标签页的会话存储里记着"这个标签页正在编辑这份文档"（这个用户、这一代）。
  - 重新载入之后，同时满足以下条件，就自动进入编辑并恢复，页头说明：
    - 记录是这个标签页上一个实例写下的；
    - 编辑权空着，或者仍是这个标签页上一个实例的；
    - 按上表能直接接上（第 1、3 行）。
  - 其余一律提示。
- **判定的写法**：判定写成一个表驱动的纯函数，每一行都有单元测试与 E2E。拿不准的一律按真冲突给副本，不自动上传。
- **并发的限制**：每个账户同时至多检查 2 份快照（M3），本机草稿页的批量操作串行进行。
- **恢复的提示**（M4-P1）：打开文档时读出库里的 `restored`（已从备份恢复）、`lost`（因浏览器存储损坏丢失）提示，如实告诉用户，看过之后清除。

### 6.5 本机密钥（客户端）

按 ADR-019 与 M3 交接单：
- **取用**：进入编辑、恢复、另存为副本之前，取当前的密钥（`POST /api/local-key`）；导入为不可导出的 `CryptoKey`，只放在内存里并交给发件箱 Worker，原始字节用完清零。阅读时不取。
- **版本变化**：心跳带来的版本与内存里的不同时，停用旧密钥、重新取，用新密钥重写当前的内容；同一个键，旧版本的记录随之被覆盖。US-M3-17 的 E2E 里"页面上没有可见的反应"那几句随之改写。
- **失败**：
  - 会话类失败按 M3 的口径：只有连着的第一次，在确认会话之后立即重试；
  - 500 按"暂时取不到"处理，退避，不重试成风暴；
  - 取不到密钥时不写本机（按不可用处理并说明），上传照旧。

### 6.6 本机清理

| 触发 | 做法 |
|---|---|
| 退出登录（平台页面的账户菜单） | 有未同步的修改时，列出这些文档并提示，可以先去本机草稿页处理。确认之后：广播，让同一浏览器里的其他页面停写、丢掉密钥 → 删除本机属于此人的全部数据（发件箱的记录与写入者、Univer 的库与键、两类记号）→ 退出 |
| 会话失效的原因（服务端，§2.1 第 1 条） | 401 带原因，只给持有这次登录的请求。账户停用 → 删除此人在本机的全部草稿，并说明原因；密码被重置、过期 → 提示重新登录，草稿保留，重新登录之后照常恢复 |
| 撤权、移出空间、取消分享、删除、移走（文档级） | 页面经保存、续租、申请、打开得到的 403、404，或本机草稿页的批量查询得知之后：还读得到 → 另存为副本或放弃，之后删除；读不到 → 删除，并说明原因 |
| 密钥吊销 | 打开着的页面换用新密钥（§6.5）；用旧版本写下的记录解不开，发现时说明并删除 |
| 保留期 14 天 | 平台的任何页面启动时，删除这台设备上超过 14 天的记录，不论属于谁（别人的记录本来就解不开）；属于当前用户的，说明删了哪几份 |
| 本机草稿关闭（部署配置） | 不再新写；已有的照常可以恢复或另存为副本，处理完删除 |

- Univer 的本机存储换成内存实现；它建的库与键，在退出登录与清理时删除（§2.2）。
- 本机数据库与 OPFS 镜像的清理合在一处（M4-P1 的 `local-cleanup.ts`）：按用户清理、放弃、保留期都两份一起清；镜像的句柄被占着时这一次跳过、交回还没清掉的，之后再清（只在这个人仍是退出的时候）。
- 账户被停用时，如果没有开着的页面，就不会当场得知：这台设备上的草稿取不到密钥、解不开，保留期到了删除。

### 6.8 公式 Worker 的退路（计划书 §10.2）

- **判定**：创建 Worker 时抛错、脚本加载失败、就绪之前出错或握手超时；就绪之后 Worker 崩溃同样处理（现在就绪之后不监听 Worker 的出错）。
- **流程**：
  1. Worker 模式下，主线程的公式插件在注册时就设了 `notExecuteFormula`，不能原地切换，只能重建。
  2. 编辑中时先捕获当前的内容，公式结果按"公式待更新"处理。
  3. 销毁实例。M3 的"主线程模式下计算中先停下再销毁"（UR-032 的规避）必须保留。
  4. 以主线程模式的档案变体重建：M3-P4 已有这个变体，去掉"只给测试构建用"的限制。
  5. 重建之后强制全量重算。
- **阅读模式**同样适用：阅读也用同一份档案。
- **说明与上报**：页头说明；打开自检的上报加一类，只带种类。
- **让出间隔**：评估 Worker 内的让出间隔（20–100），测 stop 生效的时间与计算开销，结论写进 ADR-010。

### 6.10 测试与验证

- **单元**：
  - 发件箱：写入者的登记与核对、草稿序号、只删到已确认的序号、写满、加密与 AAD、保留期；
  - 恢复的判定表；
  - 编辑会话的状态机（假的编辑器、可控的时钟）。
- **浏览器层**：发件箱 Worker 与 IndexedDB 在三个浏览器里的行为，用 Playwright 的页面级测试，入口在测试构建里。
- **E2E**：
  - 断网：`setOffline` 与拦请求（M3 的 `blockSaves`、`blockLeaseRenewals`、`disconnectTab`），可控时钟走过 10 分钟与编辑权的有效期；
  - 崩溃（工具已在 M4-P1 建好）：持久化的浏览器目录 + 结束整棵浏览器进程 + 以同一个目录重开；另能往 Chromium 的 IndexedDB 日志结尾补一个只有头的记录，确定地造出删库，核对从 OPFS 恢复。macOS 上 WebKit 的网络与页面进程由 launchd 拉起，不在进程树里，要另外认；CI 是 Linux。重开之后登录不一定还在（Cookie 不一定已落盘），没有就重新登录，再取密钥；
  - 多标签页：写入栅栏、锁被抢、本人接管从发件箱接手；
  - 清理：退出登录、撤权的各种范围、账户停用、保留期；
  - E2E 默认暂停定时的自动保存（M3-P4）；恢复与离线的用例另在 `E2E_AUTOSAVE=running` 下跑。
- **容器 E2E**：加上离线编辑与崩溃恢复的主链路（生产镜像、HTTPS）。
- **真实 Safari**（页面自检）：
  - P1：存储行为、发件箱 Worker 的停顿、捕获成本与性能基线；
  - P3：崩溃恢复——驱动脚本结束承载测试页的页面进程，Safari 自动重载之后，核对自动恢复；
  - P6：DEF-069——暂停持有者的页面进程，走到到期之后再继续。
- **虚拟机里的断电**（P6，§2.1 第 5 条）：
  - Linux 虚拟机跑 Chrome、Edge，macOS 虚拟机跑 Safari；
  - 页面连续写入，把每次报告完成的序号报给宿主机；强制关掉虚拟机，开机之后核对本机留下的最后一个序号不小于报告过的；
  - `strict` 与默认的持久性各做一组。
- **工程规范**：新的确定交错（多标签页、清理与写入）按规范 §5 的做法写；`tests/stories.json` 加上 US-M4-01 至 15。

### 6.12 对 00 号计划书的修订（r21，随本总设计审批生效）

- §7.2：上传与本机共用发件箱 Worker 压缩的同一份数据；上传带的序号用发件箱的草稿序号。
- §7.5：
  - 发件箱记录的字段补上在途请求（请求标识、客户端实例、序号、"公式待更新"、客户端构建版本与数据格式）；

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| 写入栅栏、本机锁与服务端的裁决三者对不上，旧标签页写坏草稿，或删掉新一代的记录 | 写入者按服务端的代次排先后，写入与删除都在事务里核对；锁被抢先停写；确定交错的单元测试与多标签页 E2E；合并之前的对抗评审 |
| 恢复的判定出错：覆盖了别人的保存，或把自己的修改当成冲突 | 判定集中成表驱动的纯函数，每一行都有单元测试与 E2E；拿不准一律给副本、不自动上传；服务端的修订号与代次兜底（绝不自动覆盖） |
| 拆 `edit-mode.ts` 引入回归 | 先拆再接功能；拆的那一步 M3 的全部 E2E 不改、照常通过；分步提交 |
| 真实 Safari 上 Worker 的停顿、存储行为与无头的 WebKit 不同 | P1 开工前复核；结论：空定时器有效，WebKit 保留 Worker 放置（M4-P1，ADR-020） |
| 浏览器清理站点数据（Safari 的自动清理、用户清除数据）丢掉草稿 | 申请持久保存，在本机草稿页显示存储状态；已知限制写明；14 天保留期 |
| Chromium 崩溃重开时删掉整个来源的 IndexedDB，本机草稿静默丢失（M4-P1 的发现） | OPFS 的冗余与如实的提示（§6.1）；崩溃用例的口径不放宽；上游报告的草稿 UR-034（照需求方的决定先不提交） |
| 本机存储写满或不可用 | 写入失败时整个回滚，已有记录不变；页头如实说明；不可用时退化为内存，离开提示照旧 |
| 崩溃 E2E 依赖认进程的方法，本机（macOS）与 CI（Linux）不同，容易不稳 | 认法封装成一个工具，并断言被结束的进程数；上 CI 之前先单独跑多轮 |
| 同一浏览器里退出登录，与另一个页面正在写入相互竞争 | 清理与写入在同一个库里按事务排队，写入核对写入者；广播停写；确定交错的用例 |
| 动 Safari 的进程影响用户 | 只在用户空闲时跑，只动认准的那一个测试页进程，认不准就跳过；与 M3 的盖屏一样可以随时中止 |
| 虚拟机工具要安装、系统镜像要下载 | 事先说明，需要管理员密码时请需求方输入；实验与正式门禁分开，不进 CI |
| 会话失效的原因让被停用的人得知自己被停用 | 需求方已接受（§2.1 第 1 条）；登录页照旧不暴露 |
| E2E 变多，CI 变慢 | 加用例之前看各分片的时长，必要时增加分片；与时间有关的用例用可控的时钟 |
