# M6-P1 S8：编辑模式、页面与页头按类型拆分

> 日期：2026-11-21｜对应 [P1 设计](../01-P1-文字文档底座.md) §3.5 第 4～6 步与 S8｜状态：S8a、S8b 已完成；S8c 已定

S8 把编辑器页里剩下的三块拆成“共用会话层的通用部分 + 表格的扩展”：编辑模式（edit-mode）、页面（editor-page）、页头（editor-chrome）。页面上报的档案改为按类型注入，start 与 mount 按类型装配。之后 P2 的文字文档只需提供自己的编辑器与扩展。

**不变的**：
- 表格的行为不变；
- 协议、日志、存储里的字符串不变；
- `#sheet-editor`、`data-editor-*` 选择器不变；
- 第 1.6 节列的通知顺序不变。

拆分中如果发现必须改变表格的行为，按设计 §3.5 停下请示。

现状由一个只读的同模型子 Agent 调研。主审抽查了构造顺序、通知函数、打开自检的类型与 CSV 目标，属实。

## 1. S8a：编辑模式拆成通用核心与表格扩展

### 1.1 表格专有的部分

edit-mode.ts 约 2,400 行。表格专有的部分分五类：

| 类 | 内容 | 在通用流程里的位置 |
|---|---|---|
| CSV | `csvTarget(newDocument)`；会话或本机代次一变就作废的 `csvSessionGeneration` | 不在流程里，由页面的 CSV 控制器拉取。它读编辑模式的大量私有状态：代次、模式、租约与写入代次、保存的状态机、本机锁、待处理的失权与阻断、显示的快照、会话、是否隐藏 |
| 工作表名 | `sheetName(id)` | 不在流程里，只读当前接上的实例 |
| “公式待更新”与重算 | 服务端的标记 `latestFlag`，阅读模式的 `formulasPending`；进入编辑与本机恢复时 `recalculate`；保存状态机的初值 | 打开、阅读检查、进入、离开、进入失败、重载、刷新 |
| 公式的回退与恢复 | `formulaFallback` 包住工厂；`formulaRecovery`；`recoveryBusy()` 挡约 14 个入口；交接回应 `'recovering'` | 通知函数的开头；会话变化、页面隐藏、卸载时撤销 |
| 故障上报 | 公式 Worker 故障的上报 `reportFormulaFault` | 通知函数里的稳定状态；每次创建之后 |

另有**打开自检**（`openCheckOf`、阅读模式的 `damaged`）。它不是表格专有的：
- 失败的种类、资源名与上报的格式都在 contracts；
- 资源名的写法本来就包括 `DOC_`。

所以它随核心进会话层，`OpenCheck` 的类型由会话层按 contracts 定义，做法同 S7 的 `UncommittedInput`。

### 1.2 切法：装配时注入一个扩展对象

调研列出三种切法：

| 切法 | 结论 |
|---|---|
| 外层包装：表格包住通用的编辑模式，在入口先判断再转发 | 不采用。包不住核心内部自己触发的路径（自动交出、空闲释放、交接回应、请求获准后的自动进入、保存的二次判断）；恢复的同步只能接在通知之后，改变第 1.6 节的 D1、D2、D10 |
| 生命周期钩子散在约 25 处 | 与扩展对象的挂点相同，只是接口分散 |
| **扩展对象**：核心在构造时调用表格给的工厂，得到一个扩展，在原来的位置调用它 | **采用**。挂点与今天的调用点一一对应，顺序不变；接口集中在一处，文字文档给一个空实现 |

### 1.3 通用核心（`document-editor/edit-mode.ts`）

用 `git mv` 把 `sheet-editor/edit-mode.ts` 搬进会话层，保留历史，再把表格专有的部分抽到表格一侧。核心保留：

- 阅读、进入、退出、交接、请求编辑、本人接管、失去编辑权、刷新、重载、卸载的全部流程。
- **打开自检**：`openCheckOf`、阅读模式与打开结果里的 `damaged`、上报。上报的请求体 `open-check-report.ts` 一起搬进会话层。页面上报的档案在 S8b 注入，S8a 里仍取 `PAGE_CLIENT_FORMAT`。
- **服务端的“公式待更新”标记**：`latestFlag`、阅读模式的 `formulasPending`。这是协议里的字段，按 S7 spec §5.2 第二类照旧，文字文档恒为假。
- **本机恢复安装前等派生内容收齐**：`settleFormulas(10_000)`，不收齐就以 `'formulas'` 阻断。方法名与取值照旧，文字文档在 P2 恒为已收齐。

**编辑器的类型**是核心的类型参数，要求的是会话层的窄接口并集：
- 保存（`EditingSessionEditor`）；
- 槽位（`SlotEditor`）；
- `openCheck`。

视图状态、生命周期的阶段与创建的选项随之成为类型参数。

**视图**：`EditModeView<Stage, Extra>` 是通用的五项（原来的六项去掉 `formulaRecovery`），再并上扩展的视图。`Stage` 是编辑器生命周期的阶段，surface 的类型随它。
- 核心记下扩展上一次交出的视图对象，按引用比较是否变化，与今天比较 `formulaRecovery` 的写法相同。
- 扩展要保证没有变化时交出同一个对象。
- 表格的扩展交出 `{ formulaRecovery }`，所以 `view().formulaRecovery` 对页面与测试不变。

**动作目标**：CSV 目标里与类型无关的部分由核心给出，即 `actionTarget()`。它交回：
- 当前编辑器；
- 一个 `current()` 谓词：代次、会话代次、会话、隐藏、实例、模式、租约与写入代次、本机锁、待处理的失权与阻断、保存的状态机，任何一项变了就为假；阅读时另要求没读不到、没有自检失败与不兼容、没有在刷新与接手；
- 新文档判断要用的几项事实：模式、修订号、保存状态机的“未保存”、显示的快照；
- `writable()`：不由用户发起的写的门槛，即核心原来的 `writableUnprompted`；
- `formulasPending()`：阅读时服务端的标记。

后两项都读核心的私有状态，与类型无关。如果改从 `view().mode` 读，在通知的过程中可能落后一拍。

`csvSessionGeneration` 改为核心的会话代次。setSession 里加一的位置不变，仍在撤销扩展之前。

### 1.4 扩展的接口

**扩展从核心拿到的（`EditModeHost`）**，即今天 `createFormulaRecovery` 与 CSV 用到的：
- `editing`、`slot`、`clock`、`reportError`；
- `context()`：代次、访问方式、会话是否本人、是否允许、修订号。取法与今天 `formulaRecovery` 的 context 逐字相同；
- `openCheck(created, context)`：核心的打开自检；
- `notify()`、`retryRequests()`；
- `session()`、`hidden()`、`disposed()`，供上报判断。代次已在 `context()` 里，表格用不到 `still(token)`，所以没有放；
- `actionTarget()`。

**核心调用扩展的地方（`EditModeExtension`）**：

| 成员 | 今天的调用点 | 表格的实现 |
|---|---|---|
| `onNotify(stable)` | 通知函数的开头：先 sync，再按稳定状态上报。`stable` 是取值函数，不是值：原来是先 sync、后看模式，sync 里嵌套的通知可能已经换了状态（D2）。它只交打开方式与修订号，起因 `'formula-recovery'` 由表格补上 | `formulaRecovery.sync()`，再取 `stable()` 上报 |
| `afterCreate(context)` | `replaceEditor` 里 `slot.replace` 之后，`still(token)` 时 | `reportFormulaFault(context)` |
| `blocksActions()` | `recoveryBusy()` 的后半 | `formulaRecovery.view()?.blocksActions === true` |
| `view()` | `computeView()` | 引用稳定的 `{ formulaRecovery }` |
| `cancel()` | setSession 里会话变了、releaseOnHide | `formulaRecovery.cancel()` |
| `dispose()` | dispose | `formulaRecovery.dispose()` |
| `enterOptions(pending)` | 进入编辑、本机恢复两处创建的选项 | `pending ? { recalculate: true } : {}` |
| `savingPending(flag)` | `startSaving` 的“公式待更新”初值（非恢复时） | `flag \|\| fallback.failure() !== undefined` |

**装配交给核心的**（`EditModeAssembly`）：槽位的 `defaultOptions` 与扩展的工厂。核心的选项是原来那些项与它的交集。

**表格扩展的构造**沿用今天的位置：
- 回退包住工厂，在核心之前建；
- 核心建好 tabs 之后、`current = computeView()` 之前，调用扩展的工厂。

扩展的 onChange 与今天相同：先 `host.notify()`，阶段到 ready 再 `host.retryRequests()`。

**`busy()`**：核心保留今天的判断，即编辑中，或阅读且不在刷新，再加上 `extension.blocksActions()`。约 14 个入口照旧在第一句判断，交接回应照旧回 `'recovering'`。

**文字文档的空实现**留到 P2。核心的测试用一个空扩展。

### 1.5 表格的扩展与门面（`sheet-editor/sheet-edit-mode.ts`）

`createSheetEditMode(options)` 依次做三件事：
1. 建回退；
2. 以表格的扩展工厂建通用核心；
3. 交回 `SheetEditMode`：核心的 EditMode，加上 `csvTarget`、`sheetName`、`retryFormulaRecovery`。

- **选项与今天的 `EditModeOptions` 相同**，`createEditor` 仍是 `CreateModeEditor`。页面与测试只改引用。
- **`csvTarget`** 由动作目标加上表格的条件组成：
  - 自检通过；
  - 没有 Worker 故障；
  - 不在恢复；
  - 新文档时是表格的空白模板、而且没改过。

  阅读时的 `formulasPending` 取核心的阅读模式。
- **`sheetName`**：取核心当前接上的实例。

## 2. S8b：页面按类型装配，档案按类型注入

### 2.1 表格专有的部分

### 2.2 切法：载入详情之后按类型选装配，选中时建页面扩展

类型要等详情载入之后才知道，P2 起同一个页面要能打开两种文档。所以页面收一张装配表，载入之后按详情里的类型选；页面扩展在选中时建。

| 切法 | 结论 |
|---|---|
| 页面构造时建扩展，即今天 CSV 的位置 | 不采用。构造时还不知道类型：P1 只有表格，看不出差别；到了 P2，就得先建、再丢掉选错的那个 |
| 外层包装 | 不采用。够不到会话钩子的第一句、“CSV 先于页面的监听者”与 pagehide 里的先后，理由同 §1.2 |
| **选中装配时建扩展** | **采用** |

选中时建，CSV 控制器就从页面构造时挪到了载入之后。核对过，这不改变行为：
- 控制器构造时没有副作用。它只发布一次视图，这时编辑模式还没有，目标为空，视图与初值相同，不通知。
- 载入完成之前没有人用它。页头在载入完成（ready）之后才渲染 CSV 入口；新建表格之后的导入也等到载入完成。
- 选中之前的 `environmentChanged` 都是空操作：目标为空，视图不变。
- 载入期间页面已经隐藏：今天 pagehide 时 CSV 已经销毁。选中时建好扩展之后，页面已隐藏就立即调扩展的 `hide`，结果相同。
- 选中之前已经有 `if (disposed) return`，所以不会在卸载之后建。

### 2.3 装配与选择

**装配表**：类型是 `Partial<Record<DocumentType, EditorPageAssembly>>`。
- start 给出 `{ sheet: 表格的装配 }`，写成 `satisfies Record<OpenableDocumentType, …>`。
- 这样它与 §2.6 的“本构建能打开的类型”一致，多一项或少一项都编译不过。

**一项装配**有两样：
- `format`：这类文档的页面档案，即 `clientFormatOf(type)`。
- `assemble(host)`：选中时调用，交回页面扩展与编辑模式的工厂。两者共用一个闭包，表格的扩展经它拿到有类型的 `SheetEditMode`，页面只看到通用的 `EditMode`。

编辑器的工厂不是装配的字段，留在装配的闭包里（实施时改，初稿是第三样 `createEditor`）：
- 表格的装配写成 `sheetEditorAssembly(createSheetEditor)`，工厂仍由 start 给出。
- 页面建编辑模式时，交给装配的工厂一个 `bindEditor`，即原来 P12 的包装；装配调 `bindEditor(createEditor)`，得到编辑模式要的工厂。
- 理由：工厂作为字段，编辑器与它入参的类型就落在页面一侧装配类型的参数位置上（逆变）。到了 P2，装配表要同时放表格与文字文档，不用 `as` 就放不下。
- 编辑模式的选项里只有编辑器的工厂用到类型参数。页面一侧的选项去掉它、另加 `bindEditor`，就不带类型参数。

**选择**在 `isKnownFormat` 原来的位置。三条都成立才选中：
- 详情的类型有装配；
- 档案等于装配的档案；
- 格式版本在 `PLATFORM_FORMAT_VERSIONS` 里。是数组包含，不是等于单值。

否则照旧进入“格式不受支持”，不建扩展、编辑器与恢复。`'unknown'` 与 P1 的 `doc` 都在这里被挡下。

### 2.4 页面扩展

**挂点**都放在今天调用表格代码的位置：

| 挂点 | 位置 | 表格的实现 |
|---|---|---|
| `environmentChanged()` | 见表下 | CSV 控制器的同名方法 |
| `blocksActions()` | 7 个入口的第一句 | 编辑模式视图里的 `formulaRecovery.blocksActions` |
| `blocksInput()` | `modeChanged` 里屏障条件的原位：切换中、正在新建，或者它为真 | 编辑模式视图里的 `formulaRecovery.blocksInput` |
| `hide()` | pagehide 的第一件，在记下已隐藏之后；选中时页面已隐藏也调 | 销毁 CSV 控制器 |
| `dispose()` | 卸载的第一件，在记下已卸载之后 | 同上 |

`environmentChanged()` 的 6 处：
- 写资格变了时，在 `signalPage` 之后；
- `update` 里，在算视图之前；
- `writeProblem`、`saveUnauthenticated`、`saveStale`、`readProblem` 里，在身份代次加一之后。

没有扩展时，也就是载入之前与格式不受支持时，挂点都不调，`blocksActions`、`blocksInput` 按假算。这与今天编辑模式还没建时相同。

`blocksInput` 读编辑模式此刻的视图。`modeChanged` 从开头取视图到屏障判断之间，只做了图片许可与 `update`，都不改编辑模式，所以读到的是同一个对象。

**页面交给扩展的一面**，即宿主：
- `actionGate()`：CSV 目标里页面的那一半。未登录、会话确认在途或有会话问题时交回空；否则交回一个谓词。谓词记下此刻的身份代次与会话，依次查：
  - 未卸载、不在离开、未隐藏；
  - 载入完成、会话是本人；
  - 没有待确认的未登录，没有过期；
  - 身份代次未变，会话的用户与令牌未变。
- `writeReady()`：服务可用，并且会话已确认可写。
- `confirmBeforeWrite()`：导入之前服务可用就确认一次会话，即今天的 `prepareImport`。
- `title()`、`documentId`、`pageSession()`：用于导入的标题，以及新建表格之后导入时核对意图。
- `sessionActive()`：未卸载，并且会话是本人。这是 `sheetName` 的门槛。

`csvIdentityEpoch` 改名为页面的身份代次，加一的 6 处不动。

**表格的 CSV 目标**按今天的先后组合：
1. 先取编辑模式门面的目标。新文档时，它会捕获一次。
2. 再取 `actionGate()`。
3. 现行判断先查页面一侧，最后查编辑模式的目标。
4. 可写在现行判断之后，依次查编辑模式的可写与 `writeReady()`。

**对外的成员**经 `page.extension()` 取，选中之前为 undefined。表格的扩展给出 `csv`、`importCreatedCsv`、`sheetName`、`retryFormulaRecovery`，写法与今天页面上的相同。

### 2.5 视图与类型

- **视图**：页面的视图 = 通用的各项 + 编辑模式视图里扩展的部分。表格扩展的部分是 `formulaRecovery`。编辑模式还没建时，这一项不在视图里；按键比较时与今天的 undefined 等价，不多通知。扩展的部分排在最前，今天 `formulaRecovery` 排第 5；视图没有被枚举或序列化，比较按键逐项，看不出差别。
- **类型参数**：通用页面是 `EditorPage<Extension, Extra, ImageState>`，三个参数依次是交给使用方的成员、编辑模式视图里扩展的部分与图片操作的状态，都只在协变的位置。表格一侧的别名是 `SheetEditorPage` 与 `SheetEditorPageView`；页头等表格编辑器里的使用方用表格的别名，留给 S8c。
- **图片操作留在通用页面**，与 spec 初稿的清单不同。理由：
  - 它的处理是通用的会话确认与图片许可；
  - 它的实例守卫与图片读取失败共用；
  - P4 的文字文档也有系统的图片输入。

  状态的类型由装配给出类型参数，约束只有 `kind` 与可选的 `reason`。页面只看“失败，并且原因是没有权限”。适配层的 `ImageInputState` 满足这个约束，由表格装配处的类型检查核对。
- **编辑器工厂的入参**：页面绑定容器、页面界面、图片的读取许可与三个回调，键与今天的完全相同。页面测试有 9 处按键集合断言。这些入参的类型由会话层自己定义，表格装配处核对同形，做法同 S8a 的 `OpenCheck`。
- 会话层不用 `as` 断言，`as const` 除外。

### 3.2 页头：通用骨架加插槽

| 插槽 | 收什么 → 交回什么 | 骨架里的位置 | 表格的实现 |

| `notice` | 视图与页面 → 元素或 undefined | 原来公式恢复块的位置：image-status 之后、reading-note 之前 | 原 CH:1221–1230，原样搬 |
| `snapshotProblem` | 详情与页面 → 文字 | 保存被拒与副本被拒的 `SNAPSHOT_INVALID` 分支 | `snapshotProblem(details, 'sheet', id => page.extension()?.sheetName(id))` |

**交付**：表格页面扩展的成员 `SheetEditorPageMembers` 加一项 `chrome`，值是上面的常量。骨架取 `page.extension()?.chrome`。
- 插槽在选中装配之后才有，与今天 `formulaRecovery`、`csv` 出现的时机相同。之前没有插槽：挡住按假算，两个位置不渲染，第三件事实为 undefined。
- P2 的同一页按类型拿到文字文档的插槽，通用页面不用改，也不用暴露选中的类型。
- 不采用“页头收一个 `slots` 属性、由 start 给出”：P2 要在载入之后按类型换插槽，届时还得改。
- 没有插槽时快照的说明用 `describeError`。实际走不到：能保存时一定已经选中装配。

**不变的**，实施时逐条保住：
1. **子节点的位置**：两个插槽各占原来那一个位置，只交回 undefined 或单个元素，不并进相邻的条件、不改成数组拼接。位置一变，React 会重建相邻的节点，例如正有焦点的“重试公式恢复”。
2. **hook**：插槽是纯函数或交回元素的函数，不在骨架的渲染里直接调 hook（选中前后 hook 的个数会变）。元素内部有 hook 没关系。
3. **组件身份**：插槽对象是模块级常量，不在取值时现定义组件；否则每次渲染都是新的组件类型，CSV 对话框的状态会丢。
4. **读哪一份视图**：挡住动作在骨架里读渲染时的快照，确认框、“放弃本机修改”、重试按钮读 `page.view()` 的当前值，与今天相同。不改用页面扩展的 `blocksActions()`：它读编辑模式此刻的视图，与页头的快照可能差一拍。
5. **用到时才读扩展**：插槽在渲染、点击的那一刻读 `page.extension()`，不在建插槽时把成员抓进闭包。
6. **读屏区**：`SaveAnnouncer` 与 `StatusRegion` 一直在，骨架不为插槽另加 status 区。
7. **焦点**：插槽的内容都在 `useFocusRescue` 那一层里面。
8. **React key** 不动。

**页头的待确认状态**里 `requiresFormula` 改个通用的名字，只在页头内部。

### 3.3 start 与 mount

- `testHooks?()`：测试构建里引入自动保存控制与交接日志，交回一个 `install(window)`；
- `selftest?()`：测试构建里引入页面自检的挂接，交回 `watchForSelftest`。

两个加载器都在函数里面按 `import.meta.env.MODE === 'e2e'` 判断，`import()` 写在判断成立的分支里，与今天 ST 的写法相同。生产构建靠常量折叠去掉这两块，由门禁 artifacts 核对：按来源、按分块名、禁用关键字三道。

**表格的 kit** `sheetEditorPageKit` 写在 `sheet-editor/start.tsx`。文件名照旧，按路径写的规则少动：
- 装配表写成 `satisfies Record<OpenableDocumentType, …>`；
- 编辑器的工厂是适配层的 `createSheetEditor`；
- 加载失败的判别是 `SheetEditorLoadError`。

**自检的挂接**：`selftest-hook.ts` 留在表格编辑器，文件名不变，由表格 kit 的 `selftest` 加载器接上。
- 不能挂在 S8b 的页面装配上：页面装配在载入详情之后才选中，挂接必须在 `page.load()` 之前装好。审查 B8 要求吞交接消息的频道在第一次打开交接频道之前换上。
- 同理，自动保存控制与交接日志也要在建页面之前装好。
- 它的类型可以换成会话层通用的。

**测试构建里的先后不变**：
1. 地址带探针参数时，先“发出即不管”地引入发件箱探针与崩溃探针。这两个在会话层的 `testing/` 下，改由会话层的 start 自己引入。
2. 没有文档身份而地址带探针参数时，只装探针就返回。
3. kit 的 `testHooks` 与刷新诊断同时引入，引入失败照常组装、不上报。
4. 再判一次已停止。
5. 依次装刷新诊断、自动保存控制、交接日志。
6. 组装页面。
7. 地址带 selftest 时，先装好挂接再载入，引入失败照常载入并上报。
8. 卸载的先后不变。

两个加载器多一层 then，只差微任务，先后不变。

**会话层的 start 是组合处专用的窄入口**：会话层的 `index.ts` 只转出它的类型，值 `startEditorPage` 由编辑器页的入口 `entries/editor/mount.tsx` 直接引用。
- 公开入口给表格编辑器（P2 起还有文字文档编辑器）取会话层的部件。启动页面只有组合处用得到，两种使用方分开（接口隔离）。
- 表格编辑器的生产代码与测试都经公开入口引用会话层。从公开入口转出 start，它们的模块图里都会多出 React DOM、分享对话框、弹窗等页面外壳。
- 先例：本机数据的 `notice.ts` 也是只给指定引用方的窄入口。

**mount**：
- 正式页：`startEditorPage({ chrome, surface }, sheetEditorPageKit)`。
- 新建表格页：`startCsvCreatePage({ chrome, surface }, elements => startEditorPage(elements, sheetEditorPageKit))`。`csv-create-start.tsx` 改收启动函数，不再引用表格的 start。
- 表格编辑器的公开入口改为转出 `startCsvCreatePage` 与 `sheetEditorPageKit`。
- P2 组合两份 kit 时再定组合的写法。

**页头的测试取骨架**：经会话层的测试入口 `index.test-support.ts`。它的 7 个引用方随之多载入页头，只是测试。
