# M6-P1 S3、S4：文字文档的快照规则

> 日期：2026-11-18｜对应 [P1 设计](../01-P1-文字文档底座.md) §3.2、§3.4 与 S3、S4｜状态：已定，实施中

S3 扩展资源规则模型，加上文字文档的规则标识、位置与说法。S4 实现 doc@1 的结构、链接、图片位置规则与交叉核对，并按档案规范化。原则沿用 M3：只拒绝有证据会出问题的内容，没有证据的结构不判，误拒的代价是存不进去（M0-P2 报告 §3，M3 总设计 §7）。

## 1. 证据

**M0 的样本**：
- `spikes/m0/fixtures/doc` 9 份：6 份经 SDK 保存的形状，另 3 份是手写的种子（empty、minimal、p5-cap）。
- `spikes/m0/e2e/results/v03/s1` 里文字文档 21 份：7 个样本在 Chromium、Chrome、WebKit 里经 SDK 打开再保存。

两组样本核对出的事实：

| 事实 | 依据 |
|---|---|
| SDK 存下的快照顶层有 14 个键：`body`、`documentStyle`、`drawings`、`drawingsOrder`、`footers`、`headers`、`id`、`locale`、`noteSettings`、`notes`、`resources`、`settings`、`tableSource`、`title` | 21 份 |
| `documentStyle.documentFlavor` 都是 2（MODERN）；页眉页脚的各个 id 都是空串 | 21 份 |
| `headers`、`footers`、`notes`、`noteSettings`、`settings` 都是 `{}` | 21 份 |
| `dataStream` 以 `\n` 结尾，但表格之外的 `sectionBreaks` 多半为空，只有 minimal 有文末的一个 | 21 份；**按“恰好一个”判会误拒** |
| 表格里每个单元格各有一个分节符，落在 `body.tables` 的 `[startIndex, endIndex]` 里 | doc-all、doc-table |
| 资源：`DOC_OBJECT_PERMISSION_PLUGIN` 是 `[]`，`DOC_WORD_STYLES_PLUGIN`、`DOC_NOTE_PLUGIN` 是空串 | 21 份；**`[]` 按现有资源规则会被判 resource-data** |
| `DOC_DRAWING_PLUGIN` 等于 `{data: drawings, order: drawingsOrder}` | 21 份 |
| `DOC_HYPER_LINK_PLUGIN` 等于正文 HYPERLINK 区间按顺序的 `{id: rangeId, payload: url}` | 21 份 |

**Univer 1.0 的源码**（`refer/univer`）：
- `DocumentFlavor`：UNSPECIFIED 0、TRADITIONAL 1、MODERN 2、DRAWINGML 3。`CustomRangeType`：HYPERLINK 0、FIELD 1、BOOKMARK 3，等等。
- 目录块（docs-toc，doc@1 不注册）写入 FIELD 区间（`properties.fieldType` 为 `TOC` 与 `PAGEREF`），另有指向标题的 HYPERLINK 与 BOOKMARK。
- docs-drawing：
  - 资源的 toJson 是 `{data: snapshot.drawings ?? {}, order: snapshot.drawingsOrder ?? []}`；
  - onLoad 按资源设置图片，加载时以资源为准。
- docs-hyper-link：
  - toJson 依次取页眉、页脚、正文里 HYPERLINK 区间的 `{id: rangeId, payload: url || ''}`；
  - onLoad 按 id 把资源里的地址写回区间，加载时资源覆盖正文的地址。
- `IDocumentSettings` 只有 `zoomRatio`。
- 脚注尾注：`notes` 里每一项有自己的 `body`、`drawings`，另有 docx 的 `footnotes`、`endnotes`。页眉页脚的数据（`IHeaderData`）同样可以带 `drawings`。
- 计划书 §11.2 写明“本期不支持的结构（页眉页脚、脚注尾注等）要求为空”，总设计 §6.2 也写了“页眉、页脚、脚注这类位置出现即拒”。

## 2. 资源规则模型（S3）

`ResourceRule` 改为判别联合：

| kind | 用于 | data 的结构（resource-data） | 必须为空（resource-not-empty） |
|---|---|---|---|
| `entries` | sheet@1 的十项，语义与现在完全相同 | 空串，或者顶层是对象、每个键下的值都是数组或都是对象 | 按 `mustBeEmpty` |
| `empty` | `DOC_OBJECT_PERMISSION_PLUGIN`、`DOC_WORD_STYLES_PLUGIN`、`DOC_NOTE_PLUGIN` | 空串或任何 JSON，不要求顶层是对象 | 是，深层为空 |
| `shaped` | `DOC_DRAWING_PLUGIN`、`DOC_HYPER_LINK_PLUGIN` | 空串，或者通过这一项的结构判定 | 否 |

- `checkResources` 的检查顺序不变：resources → resource-duplicate → resource-unknown → resource-data → resource-not-empty。
- sheet@1 的规则表只加 `kind: 'entries'`，现有用例不改即通过。
- doc@1 两项 `shaped` 的结构：
  - `DOC_DRAWING_PLUGIN`：对象，`data` 是对象、每个值都是对象，`order` 是字符串数组；
  - `DOC_HYPER_LINK_PLUGIN`：对象，`links` 是数组、每一项是 `{id: 字符串, payload: 字符串}`。
  - 多出的键不看，与“只核对最小的结构”一致。
- 页面的打开自检用同一份规则（`lostResources`），只看“在而非空”，不受影响。

## 3. 文字文档的规则（S4）

检查顺序：

1. 不分档案的检查：编码、嵌套、数量、JSON、内存。
2. 结构，以及文字文档的五条规则。
3. 资源。
4. 图片地址。
5. 链接。
6. 交叉核对。
7. 事务里的 unitId 与不缩水。

结构不通过，后面的规则都不再看。

| 规则 | 判定 | 拒绝的样本（逐条有单元用例） |
|---|---|---|
| `structure` | 顶层是对象；`id` 是非空字符串；`body` 是对象，`body.dataStream` 是字符串；`body` 的 paragraphs、sectionBreaks、tables、customRanges、customBlocks 在时都是数组；`documentStyle`、`headers`、`footers`、`drawings` 在时都是对象；`drawingsOrder` 在时是数组 | 表格的快照、没有正文、dataStream 不是字符串 |
| `doc-flavor` | `documentStyle.documentFlavor` 等于 2（MODERN）；缺少也拒绝 | 0、1、3、缺少 |
| `doc-header-footer` | `headers`、`footers` 不在或深层为空；`documentStyle` 里页眉页脚的 id 不单独判 | 有一个页眉，里面有正文 |
| `doc-notes` | `notes`、`footnotes`、`endnotes` 不在或深层为空；`noteSettings` 不单独判：它除了编号的设置，还能带分隔符等几段正文（Univer 的 `INoteSettings`），这些正文只在有脚注尾注时排版，而脚注尾注已要求为空。P2 定稿 doc@1 时核实它们会不会显示（P1 审查 A 的 M-2，DEF-090） | 有一条脚注；docx 的尾注 |
| `doc-section-break` | 不在任何表格 `[startIndex, endIndex]` 里的分节符至多一个；有的话，它的 startIndex 必须是 `dataStream.length - 1`。表格的区间排序合并之后二分查找，耗时不随表格数与分节符数的乘积增长；写法不对的表格不算，写法不对的分节符按表格之外算。表格以 `dataStream` 里的控制符为准：起点是表格开始 `\x1A`，终点的前一位是表格结束 `\x0F`（SDK 写表格的写法，M0 的 8 个表格都是），不是的区间不算表格，两端不落在控制符上的伪造区间藏不住分节符（P1 审查 A 的 M-1）。只核对两端：两端都落在控制符上但不是一对的区间、正文里自造的一对控制符，以及 `dataStream` 里没有记录的分节符，P2 定稿 doc@1 时按控制符的完整结构判定（P1 复验的 Minor-1，DEF-089） | 文中多一个分节符；唯一的一个不在末尾 |
| `doc-toc` | `body.customRanges` 里没有 FIELD 区间（rangeType 1）带 `fieldType` 为 `TOC` 或 `PAGEREF` | 目录块的外层区间、页码区间 |
| `image-source` | 沿用：任何深度上名为 `source` 的字段都必须是平台的图片地址 | 顶层 drawings、资源里各一份外链 |
| `link-structure`、`link-address`、`link-range-id` | 沿用 `checkCellLinks`，作用于 `body.customRanges` | 外链脚本地址、不是规范写法、rangeId 写法不对 |
| `resource-mismatch`（新） | 见下 | 链接资源的地址与正文不同；多一条或少一条；顺序不同；图片资源与 `drawings` 不同 |

**交叉核对**（`resource-mismatch`）：

- `DOC_HYPER_LINK_PLUGIN` 在时（空串按 `{links: []}`），`links` 必须与正文里 HYPERLINK 区间按出现顺序一一对应：条数相同，逐项的 `id` 等于 `rangeId`、`payload` 等于 `url`。
  - 只比这两个字段：SDK 加载时只读它们，多出的键不看。
  - 页眉页脚已要求为空，只看正文。
  - 加载时资源会覆盖正文的地址；如果不核对，伪造的资源就能绕过正文的链接检查。
- `DOC_DRAWING_PLUGIN` 在时（空串按 `{data: {}, order: []}`），`data` 必须按 JSON 值等于 `drawings ?? {}`，`order` 必须等于 `drawingsOrder ?? []`。对象不看键序，数组看顺序。
  - 只比这两个字段：SDK 加载时只读 `data` 与 `order`（`resetDrawing(data, order)`），多出的键不看。
- 两项资源不在时不判。资源消失由“不缩水”管：上一版非空的资源，这一版必须还在。

**不做的**：
- `noteSettings`（理由见上表 `doc-notes` 一行）、书签区间、图片逐字段的结构、`headerFooterDrawingsOrder`（只在类型里声明，源码里没有读写）：没有证据说有害，不判。
- 加载时规范：P2 在页面上做，服务端只拒绝。

## 4. 规则标识、位置与说法（S3）

- **规则标识**：`SNAPSHOT_RULES` 按检查的先后加 `doc-flavor`、`doc-header-footer`、`doc-notes`、`doc-section-break`、`doc-toc`（排在 `structure` 之后），以及 `resource-mismatch`（排在链接三条之后、`unit-id` 之前）。
  - `doc-notes` 在 S4 补上：S3 起初漏了计划书 §11.2 的“脚注尾注要求为空”。
  - 旧页面遇到新规则，按“格式不正确”说（响应解析本来就宽容）。
- **位置**：
  - 图片位置加 `{kind: 'doc-drawing', drawingId}`（顶层 drawings 里的一张）与 `{kind: 'document'}`（文档里别的位置）。资源里的沿用 `{kind: 'resource', resourceIndex}`。
  - 链接位置加 `{kind: 'paragraph', paragraph}` 与 `{kind: 'document'}`。paragraph 从 0 起算，是区间起点所在的段落：第一个 `startIndex` 不小于区间起点的段落。
  - 旧页面遇到新的位置形状，就忽略位置。
- **说法**：
  - 服务端的提示按文档类型给出“表格里……”或“文字文档里……”，不再写死表格。
  - 页面的规则说法表加上新规则（穷举，类型检查强制）；位置的描述加“第 N 段”“一张图片”。

## 5. 规范化（S4）

- `canonicalContentTextOf(snapshot, profile)`：
  - sheet@1 的结果逐字节不变，现有向量照旧通过；
  - doc@1 在第 1 步去掉 `settings.zoomRatio`。
  - 第 2 步的资源处理不分档案。`DOC_DRAWING_PLUGIN` 的 `order` 为空数组时会在第一层被去掉，但顶层的 `drawingsOrder` 保留在规范文字里，图片顺序的差别仍然体现在哈希里。
- `canonicalContentTextOf`、`canonicalContentText` 的档案参数是必填的，调用方（服务端的检查、各层测试与测量脚本）都传档案。
- 测试工具里的第二份实现（`apps/web/src/editor/testing/content-compare.ts`）加档案参数，口径与上面相同，单元测试逐对核对两边的判断。
  - 它的默认值是 sheet@1：现有的自检与 E2E 都是表格，不必逐处改写；文字文档的自检与 E2E（P2 起）显式传 doc@1。
  - 漏传时用表格的口径比较文字文档，缩放的差别会被当成内容变化，判断偏向“不同”，用例会失败而不会误放行。
- 补文字文档的哈希向量，并与第二份实现对照。

## 6. 测试

- **contracts**：
  - 资源规则：sheet@1 现有用例不改即通过；三种 kind 的合规与违规样例；M0 文字文档样本的资源检查通过。
  - 规则标识与位置的解析：新位置能解析；旧位置照旧；不认识的忽略。
  - 规范化：表格向量不变；文字文档的向量；两份实现一致。
- **api**：
  - doc@1 的每条规则有拒绝样本，并指出位置；
  - M0 的文字文档样本（6 份 SDK 形状、21 份 v03/s1）按 doc@1 全部通过；
  - 表格快照按 doc@1、文字文档快照按 sheet@1 都在结构一步拒绝；
  - 服务端说法按类型给出。
- **集成**：在 S5 随 DEF-055 一起，经真实接口保存文字文档，被拒时的状态码与详情。
