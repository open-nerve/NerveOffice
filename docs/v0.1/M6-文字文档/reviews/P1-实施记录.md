**实现中的调整**：

- **宽容的范围收窄。** 起初用 `.catch('unknown')`，缺少与非字符串也解析为 unknown。这违反了 M4-P4 草稿事实测试“可读项的 type 缺失不能猜测为默认事实”。改为只宽容没见过的非空字符串，缺少、空串与非字符串仍是格式错误。
- **不另立服务端的产出类型。** 服务端由数据库的行产出类型，受 CHECK 约束，只会是已知类型，也不按类型字段分支。页面按类型分支的地方，由类型检查强制处理 unknown。设计 §3.2、§7 已按实现改准。
- **旧用例改写。** client-format-gate 的一条旧用例把 `doc@1` 当作服务端不认识的档案，改成正向用例：doc@1 是服务端现在写的档案，与文档无关的一半通过。
- **迁移 0040。** 用 `pnpm db:generate --name m6_doc_type` 生成，只重建三条约束，照 0023 加了中文头注。
- **集成测试要先构建后端。** 第一次运行时图片处理的子进程初始化失败，原因是这个 worktree 还没构建后端。执行 `pnpm --filter "@nerve-office/api..." run build` 之后通过。

## main CI #109 的依赖漏洞（2026-11-18）

- **现象**：M6 总设计合入之后的 main CI #109（run `44269592484`，`b3302447`）只有 verify 一项失败，其余五项成功。失败在最后一步 audit（0.9 秒）；lint、typecheck、门禁、单元与集成覆盖率、构建都通过。
- **原因**：picomatch 新公布了高危通告 [GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf)：单分支重复的 extglob 会引起 ReDoS。受影响的版本是 4.0.7 及以下，上游还没有修复版本。依赖链是 tools → vite → tinyglobby → fdir → picomatch@4.0.7。tools 把 vite 写在 dependencies 里，所以算作生产依赖。这次合并没有改动依赖。
- **影响**：
  - 运行时镜像只装 api 的生产依赖（`deploy/Dockerfile` 的 prod-deps 阶段），不含 vite 与 picomatch。
  - vite 只在构建阶段运行，交给 picomatch 的匹配模式都来自本仓库的配置，不接收外部输入。
- **处理**：按《工程规范与完成定义》的规定（生产依赖出现高危漏洞，在当前 Phase 内升级、替换，或者登记例外并写明缓解措施），在 `tools/src/gates/policy.ts` 登记第一条漏洞例外，到期日 2026-12-18。
  - 修复版本发布满 3 天（供应链冷却期）就升级，并删掉这条例外。
  - 例外到期，或者对应的漏洞不再出现，门禁都会失败，迫使重新评审。
- **验证**：本机 audit 门禁，登记前失败（1 处违规），登记后通过。
- main 的 CI #109 不重跑。这条例外随 P1 合入 main 之后，由 main 同 SHA 的 CI 验证。
