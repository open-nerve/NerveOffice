## 审查方式

- S8c 提交之后，按两半分给 2 名同模型（claude-opus-5-5）只读审查员。他们只用 git、grep 与读文件，没有运行测试、构建、lint、typecheck 或 pnpm 脚本，没有改仓库文件；静态核对的小脚本放在会话的临时目录，只读 JSON。
  - **A**：契约、服务端与数据（S2～S5）：`packages/contracts`、`apps/api/src/modules/documents`、迁移 0040、页面上报的档案与草稿事实、类型的说法、历史预览、门禁的漏洞例外、托管例外、故事登记。
  - **B**：前端的共用编辑会话层与 #106 方案 A（S6～S9）：`features/document-editor`、`features/sheet-editor`、编辑器页的入口、eslint 的模块边界、门禁 artifacts、S9 的自检。
- 每名审查员核对：是否符合设计与 spec；有没有引入新缺陷；表格的行为是否不变；测试能否抓住问题，有没有放宽断言或时限；文档与实现是否一致。
- 主审逐条核实：读代码与 spec 复核失败场景；B 的 I-1 由修复时先写的类型回归用例在修复前的代码上 typecheck 报错证实。审查员的发现都成立。
- 修复：A 的 M-1 由主审先写失败用例再修；B 的两项交同模型实现子 Agent 按主审写的说明修，不提交，主审逐段审查、自己重跑验证后提交。修复之后再请 1 名同模型复验者只读审查修复这一批（见“复验”）。
