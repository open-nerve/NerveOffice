# 团队在线文档平台：项目计划书

**文档编号：00｜文档修订：r4｜适用产品版本：v0.1（MVP）｜日期：2026-09-26｜状态：M0 技术验证已完成；r4 随 M1 总设计评审修订（2026-09-26 审批通过）**

**技术方向：Node.js 24 / TypeScript + PostgreSQL 18 + Univer 开源 SDK（1.0 线，基线锁定 1.0.0）**

> 本期建设一个自部署、单租户的团队在线表格与文字文档平台。只采用可核实的开源能力，不引入 Univer Pro，不实现同一文档的多人实时共编，不接入 Agent。
>
> 多人使用采用"空间内默认可见、单文档单写者、编辑权可交接、不同文档并行编辑"。保存采用"本地优先"管道：修改先写入本机加密发件箱，再同步到服务器，断网期间已输入的内容不丢失。
>
> 本文档在初稿基础上，结合对 Univer 源码（`refer/univer`，dev 分支 d31d624，1.0.0-rc.0）的逐项核查与评审讨论修订而成（r1、r2）。r3 按 M0 技术验证的结论修订：版本基线为 Univer 1.0.0，`refer/univer` 已切换到 tag v1.0.0（d592fb7）。经 M0 验证的做法，以 M0 的验证报告为证据（`docs/v0.1/M0-技术验证/reports/`，文中写作"M0-P3 报告 §3.4"这类形式）；其余实现方式、参数与指标仍是建议方案，在实施与压测中确认。

## 1. 决策摘要与默认前提

### 1.1 需求方已明确的决定

| 项目 | 决定 |
|---|---|
| 产品形态 | 独立的团队在线文档平台，而非外部云文档的跳转入口 |
| 部署形态 | 自部署、单租户：一套部署服务一个组织，组织内可划分多个团队空间 |
| 商业依赖 | 依赖付费组件的功能全部排除，不以试用许可证作为生产方案 |
| 项目阶段 | 从零开始建设符合生产验收要求的 MVP |
| 后端语言 | Node.js / TypeScript |
| Agent | 不进入 MVP：不建设对话框、模型接入、Agent 调度或 MCP |
| 可定制性 | 保留自主控制产品、数据和扩展逻辑的能力 |

### 1.2 本轮评审确认的决策

| 编号 | 决策 | 结论 |
|---|---|---|
| D1 | SDK 使用方式 | 依赖 npm 发布包，定制通过自有插件与适配层实现；确需改源码时用登记过的补丁管理；`refer/univer` 仅作只读参考 |
| D2 | 版本基线 | 1.0 线，基线锁定 1.0.0 正式版（§3.2） |
| D3 | 组织与空间 | 个人空间 + 团队空间；空间决定默认可见范围，不是隔离墙；团队空间仅系统管理员可创建；系统管理员默认看不到文档内容（§5） |
| D4 | 编辑权交接 | 显式进入编辑、空闲释放、请求编辑、本人接管、强制接管；被中断方的未同步内容另存为副本（§6） |

### 1.3 本稿采用的默认值

以下是为形成完整方案采用的默认值，没有逐项单独评审。可以在后续调整，但变更时需要同步修改验收范围。

| 事项 | 默认 |
|---|---|
| 数据库 | PostgreSQL 18；镜像按摘要锁定（M1 总设计 §2.2） |
| 首发编辑类型 | 在线表格、文字文档；Slides、PDF 延后 |
| 内容格式 | 用平台信封封装的 Univer 原生快照；不承诺 Office 文件互通 |
| 服务组织 | 模块化单体，不拆微服务，不建独立的协同服务 |
| 首发终端 | 桌面 Web、简体中文；移动端编辑与 Electron 不进入 MVP |
| 用户入口 | 由系统管理员邀请注册；关闭公网自由注册与匿名分享 |

| 回收站 | 保留 30 天后彻底删除 |

### 1.4 术语

| 术语 | 含义 |
|---|---|
| 登录会话 | 用户登录后的服务端 Session，由 Cookie 标识 |
| 编辑租约 | 某份文档当前唯一可提交修改的编辑权，有有效期，靠心跳续租 |
| 租约代次（`writeEpoch`） | 文档上单调递增的计数器，每产生一代新的编辑租约就加一，用于拒绝过期会话的写入 |
| 修订号（`revision`） | 文档内容每成功保存一次就加一 |
| 快照 | Univer 原生的文档完整数据（工作簿或文字文档），含插件资源 |
| 插件档案 | 某种文档类型固定使用的插件列表、配置与适用的 SDK 版本（§8.2） |
| 本机发件箱 | 浏览器 IndexedDB 中尚未同步到服务器的快照记录（§7.5） |
| SDK 版本 / 平台格式版本 | 前者是 Univer 包的版本；后者是本平台快照信封的格式版本，两者独立 |

## 2. 目标、定位与非目标

### 2.1 产品目标

团队成员可以登录，进入个人空间或所在的团队空间，新建表格或文字文档，把文档分享给同事查看或编辑。遇到断网、关闭页面、重新登录或应用重启，已输入的内容仍然可以继续使用。系统管理员管理账户与空间，空间管理员管理空间成员与空间内的文档，运维人员可以检查审计记录并执行故障恢复。

MVP 的价值不在功能数量，而在一个可靠的闭环：

**创建 → 编辑 → 写入本机 → 云端确认 → 分享 → 交接编辑 → 重新打开 → 故障恢复。**

### 2.2 本期不是完整的 Office 替代品

本期不承诺上传已有的 `.xlsx`、`.docx`、`.pptx` 后可以直接编辑，也不导出这些格式。数据进出的正式通道有两个：表格的 CSV 导入导出，以及剪贴板。剪贴板只保证验收范围内的文本与表格数据，不保留外部 Office 的复杂格式。

平台备份与恢复的是自身的数据格式，这不等于 Office 文件转换。产品说明使用"在线表格""在线文字文档"，不宣传为"完整 Excel/Word 在线版"。

### 2.3 明确不做的工作

- 不实现 OT/CRDT、实时光标、逐操作同步和同文档多人同时写入，也不自研这些能力来替代商业协同组件。
- 不引入官方 Office 转换、打印、PDF 导出、图表、数据透视表、行列分组（大纲）、迷你图、形状、协同编辑历史、Pro 服务端或许可证管理。Univer 把这些列为 Pro 能力。[S1]
- SSO、对外开放平台、复杂审批、全文搜索、单元格级权限、文件夹级权限、跨文档计算、Agent 自动修改、离线冷启动（断网状态下打开应用），都不进入本期。

### 3.2 版本决策

- 基线锁定 1.0.0 正式版：M0-P1 锁定版本时它已发布，所以直接锁定，不再经过 rc，r2 的"M5 正式版门槛"随之满足（M0-P1 报告 §1）。所有 `@univerjs/*` 协调发布包使用完全相同的精确版本，不用 `^` 或 `~`；独立发版的包按包清单声明的兼容范围单独锁定（`@univerjs/icons` 为 1.43.0，与 `@univerjs/ui@1.0.0` 声明的版本一致）。
- 1.0.0 作为首发基线冻结。此后的 1.x 升级只在 Phase 边界进行，按 §8.7 回归样本后再冻结新的基线。
- 生产构建禁止使用浮动的 `latest`、未经评审的候选版或远程动态加载的 SDK；锁文件纳入版本控制。
- 实现依据优先使用锁定版本对应 tag 的源码、类型声明与示例；官网文档只作概念参考。

### 3.3 开源依赖准入

为每个启用的功能记录：功能名、npm 包、版本、源码位置、许可证、传递依赖、浏览器验证结果、保存重开结果。

生产依赖图和构建产物中不允许出现 `@univerjs-pro/*`。除了检查包名前缀，还要核查实际许可证、运行时的网络行为（§11.3），以及是否需要商业运行资源。

- 采用显式的插件白名单，即插件档案（§8.2）；没有验证过的功能隐藏入口，也不注册对应插件。
- 保留 LICENSE / NOTICE，生成第三方依赖清单；授权不明的依赖默认不纳入。
- 不把上游的 examples 工程复制过来作为生产平台，只作参考。
- 不使用 presets，直接按插件模式组装。原因是插件集合必须由我们精确控制，而 preset 会带入额外的插件。

**M0 核实的依赖事实与 A01 的检查细则**（M0-P1 报告 §2.2、§7）：
- `@univerjs/core` 经 `@univerjs/protocol` 引入 `@grpc/grpc-js`：只增加安装时的依赖面（33 个包），不进入构建产物；可以用 pnpm `overrides` 去掉（ADR 候选）。
- 安装脚本：全图只有 `protobufjs` 带 `postinstall`，已显式拒绝；CI 维护安装脚本白名单。
- pnpm 的发布冷却：内置默认值是非严格的，发布不满一天的版本照样安装，并自动写入豁免名单；必须显式配置 `minimumReleaseAge` 才会拦截，豁免名单的变更纳入评审。[S17]
- 许可文本：构建产物会压掉许可注释，另有 6 个包的发布包里没有 LICENSE 文件。生产构建用平台自己的许可收集插件生成第三方许可清单（M1-P1：Vite 的 `build.license` 不收集 Worker 的产物，所以不用它），补齐这 6 个包的许可正文，清单随部署包分发，由 CI 校验完整性。
- `@univerjs/telemetry` 只定义了 `ITelemetryService` 接口，开源版没有实现；平台不注册任何实现（§11.3）。
- A01 的 CI 检查以 M0 的依赖报告脚本为蓝本（版本一致、按安装路径检查单例、没有 Pro、许可分类），再加上安装脚本白名单、编辑器产物的关键字与动态代码扫描；扫描范围包括 Worker 自己按需加载的子块（它们不在构建清单里）。

### 3.4 参考源码的管理

`refer/univer` 只用于阅读与调试，不参与构建，保持只读。M0 已把它从 dev 分支的浅克隆（d31d624，2026-09-22）切换到与基线对应的 tag v1.0.0（d592fb7）；此后随基线升级同步切换。

## 4. MVP 功能范围

### 4.1 平台功能

| 模块 | MVP 目标 | 范围约束 |
|---|---|---|
| 账户 | 邀请注册、登录、退出、修改密码、由管理员发起的重置密码 | 不开放匿名注册；重置链接单次有效，并记入审计 |
| 组织与空间 | 个人空间；团队空间的创建与归档、成员与空间角色管理；全员可见空间 | 团队空间只有系统管理员能创建（§5） |
| 文档管理 | 新建、重命名、列表、按标题搜索、文件夹、移动（含跨空间）、复制、回收站、恢复 | 不做全文索引；文件夹不设独立权限 |
| 分享 | 把文档分享给指定同事（查看者或编辑者），可以跨空间；"与我共享"列表 | 不做匿名链接，不做公开发布 |
| 编辑权 | 申请编辑、显示占用者、请求编辑、空闲释放、本人接管、强制接管 | 同一文档只有一个写者；同一用户开两个标签页也按两个会话处理（§6） |
| 保存与离线 | 本地优先保存、断网继续编辑、崩溃恢复、冲突时另存为副本、保存状态显示 | 可靠性边界见 §7.8 |
| 历史版本 | 编辑者可查看小时级历史版本、只读预览、恢复为副本；空间管理员可清除 | 不做逐操作回放、差异对比、就地回滚（§8.6） |
| 数据导入导出 | 表格按工作表导出 CSV；可从 CSV 新建表格，或导入为新工作表 | 使用带 BOM 的 UTF-8；防 CSV 公式注入 [S15]；受快照容量限制；在客户端完成 |
| 图片资源 | 受控上传、授权读取、文档内引用；复制与恢复后资源完整 | 支持 PNG/JPEG/WebP/GIF（SDK 默认的格式清单与此不一致，由平台对齐，§8.5），单张不超过 5 MiB；不做任意附件，不做远程抓图 |
| 产品体验 | 简体中文；加载、错误、只读、离线等状态；保存状态；无权限提示；已知限制在产品内可见 | 编辑器能力不足时，不显示用不了的按钮 |
| 运维 | 迁移、健康检查、日志、监控、审计、备份、恢复演练、发布回滚方案 | 属于上线门槛，不作为"以后再补"的增强项 |

### 4.2 在线表格

**目标能力**：
- 多工作表、单元格编辑；
- 行列的插入、删除与宽高调整；
- 常用格式与数字格式；
- 常用公式，以及工作簿内的跨表引用；
- 冻结、筛选、排序；
- 数据验证、条件格式；
- 查找替换、超链接、备注（note）；
- 浮动图片与单元格图片。

**排除**：
- 行列分组（大纲）、图表、透视表、迷你图、形状、打印，这些都属于 Pro；
- 单元格保护与工作表保护：开源实现是客户端模拟，不构成安全边界，所以隐藏入口（§6.5）；保护类资源在服务端必须为空（§8.2）；
- 工作表背景图片（入口在"视图 → 显示"）：不在目标能力内，隐藏入口；服务端只接受平台的图片地址（§11.2）；
- 线程评论（§4.4）。

不承诺所有公式都能用，也不承诺任意复杂度的文件都能兼容；以 M0 的能力矩阵（`docs/v0.1/M0-技术验证/reports/能力矩阵.md`）和保存重开样本为准。

**M0 结论**（能力矩阵 §2）：目标能力都已验证为可用或有条件可用，保存重开一致，修改都能被检测到，三个浏览器一致。需要注意的几项：
- 常用公式：有条件可用。捕获时机按 §7.3 的收齐规则；默认启用公式 Worker（§8.2）。
- 超链接：有条件可用。M0 只验证了文字文档一侧的链接地址白名单与规范写法；表格一侧由 M5 按同一规则（§11.3）实现并验证。
- 浮动图片：有条件可用。图片所跨的行因自动行高变高后（换行文字、放大字号、单元格图片），切换工作表或重开时图片被拉伸，下一次保存就写进快照。这是 SDK 缺陷（DEF-002），关联 A02，必须在 M5 修复（M0-P2 报告 §2.3）。
- 表格的证据来自保存重开、变更检测、阅读模式与图片路径的实验，没有像文字文档那样逐项走界面入口；逐项走界面入口与撤销重做，由 M5 的能力验收完成。

### 4.3 文字文档

以下能力由开源 1.0 线提供，M0 已逐项验证（V13 有条件通过，M0-P5 报告 §2，能力矩阵 §1）。"可用"指用户入口可用、撤销重做与保存重开一致、三个浏览器一致；"有条件可用"的条件由平台落实，已在验证工程中实现，并在三个浏览器上与 SDK 默认行为对照验证：

- 正文与标题样式（标题、副标题、H1–H5）：可用
- 字符格式（粗体、斜体、下划线、删除线、上下标、字体、字号、文字颜色、高亮）：可用
- 段落对齐：可用
- 有序、无序、复选列表：可用
- 基础表格：有条件可用。限制：不支持嵌套表格（SDK 拒绝）；单元格里不能插入图片，由平台落实：命令守卫覆盖插入、移动、拖动与改为内联，粘贴时去掉图片（SDK 只禁用了工具栏按钮）。SDK 默认下单元格里的图片保存重开一致，以后要放宽这条限制，需走范围变更
- 图片：内联，以及浮动环绕（五种环绕方式）：可用
- 超链接：有条件可用，链接地址按白名单保存规范写法（§11.3）
- `/` 快捷插入（只包含已启用的能力）：有条件可用。SDK 在任何位置拦下 `/`：弹出的菜单抢走焦点，其后键入的字全部丢失；表格单元格里不弹菜单，`/` 直接被吞掉。平台只在表格之外的空段落里放行，由 SDK 弹出菜单，其他位置原样插入 `/`
- 查找替换：可用
- 文档大纲（目录）：以只读的大纲侧栏提供（DocsUI 的 `toc` 配置）：列出标题与 H1–H5，点击跳转，不写任何内容，阅读模式下同样可用。在正文里插入的目录块暂缓（§4.4）

**附加能力**（§4.3 原清单之外，M0 已验证并保留入口，撤销重做与保存重开一致）：分割线、符号、表情、格式刷、清除格式、段落设置（缩进、间距、行距）、段落把手（复制、剪切、删除段落，拖动移动段落）、粘贴选项（仅保留文本）。

**中文输入与复制粘贴**（有条件可用，M0-P5 报告 §3、§4）：
- 中文输入（macOS 的拼音、五笔、中文标点）：在段落各处、标题、列表、表格单元格、粗体与链接文字里都正确。条件：
  - 输入法事件归一：按 WebKit 的提交顺序（`compositionend` 的数据与最后一次更新不同）[S18]，SDK 的撤销会多删字、重做会插回拼音；平台在 `compositionend` 之前补发一次携带最终文字的更新；
  - 捕获时机感知组合输入（§7.3）；
  - macOS 真实输入法的人工核对（M0-P5 报告附录 A），在 M6 开始前完成（DEF-013）。

  Windows 输入法在 M6 开始前补测（DEF-005）。输入法候选框贴着 SDK 隐藏输入元素里的光标，而这个元素放在组合文字的末尾、字号固定，与画布上的文字对不齐（实测偏右 13–27 px，随换行向下偏 18–54 px）；真实候选框的位置以人工核对为准，由 M6 缓解。
- 复制粘贴（Word、WPS、网页、Google Docs、飞书、本平台）：标题、列表、表格、链接与常用文字样式大多保留，脚本不执行，危险链接被去掉。条件：链接地址的规范写法覆盖粘贴，包括"内部片段"（§11.3）。一批格式转换偏差列入已知限制（§4.5），由 M6 决定在平台侧修正还是提交上游；真实应用与真实剪贴板的复核见 DEF-006。

**版式**：固定使用无分页的网页式版式（MODERN）。
- 加载时规范：版式改为 MODERN，去掉页眉页脚数据与表格之外多余的分节符；服务端保存时拒绝这类数据（§11.2）。正常流程里它们只可能来自缺陷或绕过客户端的请求，加载时的规范保证历史数据打开后仍能保存。
- 隐藏以下入口（共 30 个菜单项，功能搜索里也找不到）：页面模式切换（1.0 已去掉按钮，命令仍可执行）、页面设置（MODERN 下是"内容宽度"，会改写版式）、页眉页脚、分隔符与各种分节符、分节设置、形状（含子项；形状写入 SVG 的 data URL），以及 §4.3 之外、没有验证过的浮动图片组合、层级与对齐。
- 隐藏菜单不会停用命令，平台另用命令守卫取消 15 个命令，涵盖切换版式、页面设置、分节与分节符、分栏符、页眉页脚、形状（M0-P5 报告 §5）。
- 开源版没有内嵌公式；网页式版式下不绘制页面背景。

**Docs 是 MVP 目标，不是可以悄悄取消的按钮。**
- M0 已单独验证中文输入法、复制粘贴、列表、表格、图片、保存与重开（M0-P5 报告）。
- 某一项能力在 M0 中验证不稳定的，隐藏它，并记为范围变更。M0 没有验证出不稳定的能力；入口清单的增减已按范围变更处理（修订记录 r3）。
- 如果基础 Docs 整体达不到要求，须提交范围变更评审，例如改成"先发布仅表格版本"；不得在未说明的情况下宣称完成了全部 MVP。

### 4.4 开源但暂缓的能力

- **线程评论**：开源实现默认把评论存进快照，而查看者没有写快照的权利。后续可以利用开源提供的可替换评论数据源（`IThreadCommentDataSourceService`）和独立的评论权限点，把评论单独存到平台接口，实现"查看者也能评论"。
- 其他暂缓项：Slides、目录块（在正文里插入的目录；文档大纲侧栏已纳入 §4.3）、分页版式与页眉页脚、xlsx 数据级导入导出、查看者本地筛选（表格的 `filterOnly` 模式）、按用户组分享。
- **目录块**暂缓的原因：它在正文里写入 FIELD、HYPERLINK、PAGEREF 区间，无分页版式下页码全是 1，目录里的链接没有地址；纳入它还要扩展链接白名单与服务端校验，收益有限。本期不注册目录块插件，服务端拒绝目录块的区间（M0-P5 报告 §5.3）。
- **查看者本地筛选**将来不能直接沿用 1.0.0 的 `FWorksheetPermission.setMode()`：它要求先创建保护规则，会写入必须为空的保护类资源（§6.5）。

暂缓不等于"都是商业功能"，原因在于首发范围、成熟度和额外的产品工作量。

### 4.5 在产品内可见的已知限制

- 同一文档同一时刻只有一个人可以编辑；阅读者看到的是已保存的版本，不是实时输入。
- 不支持 Office 文件的导入导出（表格支持 CSV）；不支持打印与 PDF。
- 浏览器崩溃或页面被强制关闭时，还没写入本机的最后几秒输入可能丢失；恢复本机保存的未同步修改需要联网；清除浏览器数据或换了设备后，未同步的修改无法恢复。
- 历史版本按小时生成，保留 7 天。
- 字体渲染依赖用户系统里的字体，不同操作系统上显示可能不同。
- 公式在浏览器中计算，结果不能作为可信的财务结算依据。
- 隐藏的行、列、工作表不是保密手段，有读取权的人可以看到全部内容。
- 单份文档有容量上限（默认解压后快照不超过 5 MiB），接近上限时会提示。
- 从其他应用粘贴到文字文档时，部分格式可能丢失或改变。
- 在文字文档的空段落里键入 `/` 会打开插入菜单，这时接着键入的字会丢失，要先按 Esc 关闭菜单再输入。
- 移动端不支持编辑。

## 5. 组织、空间与权限

### 5.1 概念模型

| 层级 | 说明 |
|---|---|
| 组织 | 就是这一套部署，也是唯一的租户。所有账户都属于组织，同事之间可以互相分享文档 |
| 个人空间 | 每个账户自动有一个。默认只有本人可见；里面的文档可以单独分享给任何同事 |
| 团队空间 | 按部门或项目划分，由系统管理员创建并指定空间管理员。成员有空间角色，对空间内所有文档默认生效。可以设为"全员可见"，即所有有效账户自动成为该空间的查看者 |
| 文件夹 | 属于某个空间，只用于整理，不设独立权限，继承空间的权限 |
| 单独分享 | 文档可以额外分享给具体的人（可跨空间），角色为查看者或编辑者 |

团队空间的文档归空间所有，所以人员离职不会留下没人管的文档；个人空间的文档归本人所有。

### 5.2 角色与有效权限

- **系统角色**：系统管理员、成员。
- **空间角色**（团队空间）：空间管理员、编辑者、查看者。个人空间的所有者，相当于该空间的空间管理员。
- **文档授权**：查看者、编辑者。

用户对文档 D（位于空间 S）的有效权限，取下面两项中较高的一个：

1. 用户在 S 中的空间角色。全员可见的空间，把所有有效账户视为查看者；
2. 用户在 D 上的单独授权。

两项都没有，就是无权访问，而且不暴露这份文档是否存在。账户被停用，所有权限全部失效。

**系统管理员默认没有内容访问权。** 系统管理员负责账户、空间和运维操作；需要看文档内容时，必须先把自己加入相应的团队空间，这个操作会记入审计。个人空间的内容对系统管理员始终不可见。

### 5.3 操作权限

| 操作 | 查看者 | 编辑者 | 空间管理员 / 个人空间所有者 | 系统管理员（未加入该空间时） |
|---|---|---|---|---|
| 阅读文档 | ✓ | ✓ | ✓ | — |
| 申请编辑、保存 | — | ✓ | ✓ | — |
| 查看历史版本、恢复为副本 | — | ✓ | ✓ | — |
| 在空间内新建文档与文件夹 | — | ✓（需空间角色） | ✓ | — |
| 删除文档 | — | 仅本人创建的 | ✓ | — |
| 分享文档、调整单独授权 | — | — | ✓ | — |
| 移出本空间（跨空间移动） | — | — | ✓（在目标空间也需有新建权限） | — |
| 强制接管编辑 | — | — | ✓ | — |
| 强制结束编辑（运维） | — | — | ✓ | ✓ |
| 清除历史版本 | — | — | ✓ | — |
| 管理空间成员与角色 | — | — | ✓（团队空间） | ✓ |
| 创建、归档团队空间，设置全员可见 | — | — | — | ✓ |
| 账户管理、邀请、重置密码 | — | — | — | ✓ |

补充说明：
- 被单独授权为"编辑者"但不是空间成员的人，按"编辑者"一列执行，但不能在该空间新建文档，因为新建需要空间角色。
- 回收站按空间划分，删除者和空间管理员可以恢复。
- 首发阶段，编辑者不能分享文档；以后可以通过设置放开。

### 5.4 生命周期规则

- **移出空间**：空间角色带来的权限立即失效，单独授权保留。该用户在这个空间里持有的编辑租约立即终止（§6.4）。
- **账户停用**：全部权限失效，登录会话与编辑租约立即终止。这个人个人空间里的文档，由系统管理员转移到其他人的个人空间或某个团队空间。转移时管理员能看到文档标题列表，但不能打开内容。
- **跨空间移动文档**：权限随之改变；移动时终止当前的编辑租约。
- **团队空间归档**：空间变为只读，成员可以阅读、不能编辑；系统管理员可以恢复。

### 5.5 可见性与防泄漏

- 用户只能看到自己的个人空间、自己所在的团队空间，以及"与我共享"。
- 通过单独分享得到的文档，只出现在"与我共享"里，不暴露它所在空间的目录结构（可以显示所属空间的名称）。
- 列表、搜索、计数、资源接口和错误信息，都不得泄漏无权文档的标题或是否存在。
- 按每个请求在服务端做授权，默认拒绝，最小权限；不能只靠编辑器界面来表达权限。[S11]

## 6. 编辑权：租约与交接

### 6.1 产品行为

打开文档一律进入阅读模式，显示用户有权读取的最新已保存版本。有编辑权的用户点击"编辑"才申请编辑租约。申请成功后，以服务端返回的当前修订号为基准进入编辑状态；如果和本地的修订号不一致，先重新加载。

文档已经有人在编辑时，其他人仍可以阅读，会看到"张三正在编辑（最后活动 3 分钟前）"，也可以请求编辑。不同文档之间互不占用。

阅读者看到的是已保存的版本。页面默认每 30 秒做一次轻量的修订号检查（用基于修订号的 ETag，没有变化就不传内容）；有新版本时提示"有更新，点击刷新"，不做整份内容的轮询。

### 6.2 租约机制

- 租约存放在 PostgreSQL 里，不以进程内的变量为准。起始参数：有效期 **90 秒**，每 **20 秒**心跳续租一次。这两个值都要经过网络波动、后台标签页、休眠恢复等测试后再调整。
- 心跳时带上客户端最后一次用户操作的时间（`lastActiveAt`），服务端据此执行空闲回收。
- 每次续租、释放、提交，都要校验租约令牌（服务端只存摘要）和租约代次 `writeEpoch`。
- 只在申请、续租、保存这些动作中使用短事务，**不在整个编辑期间持有数据库事务或行锁**。[S8]
- 租约的时间以数据库时间为准，不信任浏览器的时钟。
- 正常关闭页面时，尽力释放租约（`pagehide` 事件 + 带 `keepalive` 的请求）。但正确性依赖租约到期，而不是依赖浏览器回调一定会执行。

### 6.3 交接规则

| 规则 | 行为 | 起始参数 |
|---|---|---|
| 显式进入编辑 | 打开文档即为阅读模式；点击"编辑"才申请，不自动抢锁 | — |
| 空闲释放 | 编辑者没有键盘、鼠标操作达到阈值后，客户端先完成保存再释放，回到阅读模式；服务端按 `lastActiveAt` 兜底回收 | 客户端 10 分钟，服务端 12 分钟 |
| 请求编辑 | 他人点击"请求编辑"：持有者已空闲达到阈值，就由持有者的客户端保存后自动交出；持有者正在编辑，则弹窗让持有者选择交出或继续。持有者的客户端没有响应时，按租约到期处理 | 自动交出阈值 2 分钟 |
| 本人接管 | 同一用户在其他标签页或设备上点击"在此编辑"。同一浏览器内，由旧标签页先同步再交出，并释放本机的标签页锁；旧标签页没有响应时，新标签页抢占锁（`steal`），从本机发件箱接手未同步的修改（§7.5）；跨设备时，旧会话立即失效，它的未同步修改按冲突处理 | — |
| 强制接管 | 空间管理员或个人空间所有者可以强制接管；系统管理员可以强制结束编辑 | 记入审计 |
| 被中断方 | 旧会话中没同步的修改，一律提供"另存为副本"，不覆盖 | §7.5 |
| 异常中断提示 | 租约因过期（而不是主动释放）结束后的一段时间内，其他人申请编辑时会被提示："上一位编辑者的会话异常中断，可能还有未同步的修改" | 30 分钟 |

### 6.4 失效、抢占与撤权

- 用服务端单调递增的 `writeEpoch`（存在文档行上）区分前后两代编辑会话。旧会话即使恢复了网络，也不能凭旧代次写入。释放租约时同样校验代次，避免旧页面误释放了新会话。
- 以下操作都在**同一个事务内**递增受影响文档的 `writeEpoch` 并终止租约：撤权、移出空间、账户停用、删除或移动文档、强制接管。保存以"代次和修订号都匹配"为条件执行更新，所以"撤权提交之后的保存必定被拒绝"是由数据库保证的，而不是靠前端按钮变灰。
- 已经发送到客户端的内容收不回来；撤权保证的是后续的访问与写入被阻止。撤权后，客户端会删除该文档在本机的未同步修改（§7.6）。

### 6.5 前端只读加固

源码核查与 M0 实测表明：Univer 的权限体系完全在客户端执行，默认的授权服务在源码注释中写明"不要用于生产"；表格的只读存在多处缺口，官方的工作表只读接口也不可用（M0-P3 报告 §5）。因此：

- **前端只读只是体验层；服务端的租约与代次检查，才是写入的边界。** 阅读模式下的任何本地改动都不会被提交。
- **做法：本地权限点 + mutation 防火墙**。M0 实测：表格 28 个、文字文档 8 个编辑入口在三个浏览器中全部被拦截，表格在公式 Worker 模式下同样有效；进入阅读模式不产生 mutation，也不写入任何保护类资源；复制仍可用。
  - 权限点：表格用工作簿级的 `setEditable(false)`，再用 `IPermissionService` 在本地关掉工作表的权限点，保留"查看"与"复制"，不创建保护规则；文字文档用公开的 `FDocument.getPermission().setReadOnly()`（平台不配置 `objectPermissionTypes`，它只设本地权限点、不写资源；以后如果配置了，要复核）。
  - mutation 防火墙：在 `BeforeCommandExecute` 中取消作用于本文档（或没有 `unitId`）的非本地 mutation。只拦本文档：单元格编辑器每次点选单元格都会往内部的文档单元写入内容，这也是非本地 mutation，拦住它会让之后的编辑写错内容。权限检查没有覆盖的入口，由防火墙兜住。
  - 在命令执行前拦截撤销和重做，因为重做会直接重放底层 mutation，绕过权限检查；同时清空撤销栈。
- **不使用表格的 `FWorksheetPermission.setReadOnly()`**：1.0.0 要求先创建保护规则，会写入必须为空的保护类资源（§8.2），退出后仍有残留，还会禁止复制；即使补上保护规则，筛选、排序、新增/删除/复制/隐藏工作表、合并、超链接、备注这 9 个入口照样能用。
- **界面**：通过 UI 插件的菜单配置 `hidden`，隐藏单元格保护、工作表保护相关的菜单和右键项，以及不支持功能的入口，避免用户误以为数据受到了保护；两种模式下都隐藏。原地进入阅读模式时，在运行时隐藏工具栏、停用右键菜单，并隐藏工作表标签菜单里的结构性操作与网格线开关；销毁重建时，用静态配置关掉工具栏、右键菜单与底栏菜单，隐藏新增工作表按钮（插件档案 v1 §5.2）。
- **进入编辑**：取得编辑权后，只要本地修订号落后，或者阅读模式下检测到本地有过改动，就销毁实例、从服务端重新加载，再进入编辑（到 `Rendered` 约 0.32–0.36 秒）；否则原地切换（进入、退出都在 45 ms 以内，切换后编辑正确）。
- 失去编辑权时切换为只读，并清空撤销栈。清空要调用 `IUndoRedoService.clearUndoRedo`，Facade 没有暴露这个接口，需要通过注入器获取。
- **不把真实用户身份交给 SDK 的本地授权服务**：它按用户 id 的前缀判断角色，只有 `Owner_`、`Editor_` 开头的 id 能编辑；设置真实用户 id 后，连没有保护规则的单元格也改不了（三个浏览器一致）。M1 的决定：在编辑器适配层用"全部允许"的 `IAuthzIoService` 实现替换它，也不调用 `setCurrentUser` 设置真实用户（M1 总设计 §6.6；替换对资源 `SHEET_AuthzIoMockService_PLUGIN` 的影响由 M1-P4 核实）；写入边界在服务端。

## 7. 保存与离线防护：本地优先管道

### 7.1 设计原则

- **先写本机，再同步服务器。** 这样网络状况只影响同步什么时候完成，不影响已输入的内容还在不在。
- **写入边界由服务端的三重检查保证**：
  - 编辑租约，决定当前谁可以写；
  - 修订号 `revision`，阻止旧内容覆盖新内容；
  - 租约代次 `writeEpoch`，阻止已失效的会话写入。
- **全量快照是累积状态。** 在单写者的前提下，"本会话追上自己之前的保存"总是可以安全地直接快进；只有"别人在中间产生了新的修订"才算真正的冲突。判断这一点只需要比较修订号，不需要合并算法。
- **绝不自动覆盖。** 出现真冲突时保留双方的内容：服务器上的版本不动，本地的内容另存为副本。

### 7.2 管道

```text
用户编辑 ─► 编辑器内存（Univer 模型）
             │ 变更检测（§7.3）：检测到修改，进入"待捕获"
             │ 捕获时机（§7.3）：防抖，等公式收齐与组合输入结束，最长 3 秒
             ▼
       ① 主线程：捕获快照 → 序列化 → 编码
             │ 捕获串行执行，本地序号 localSeq 在这一步分配
             │ 字节转移给发件箱 Worker
             ▼
       ② 发件箱 Worker：内容哈希（与上次相同则跳过）→ gzip → 加密
             │ → 写入本机发件箱（IndexedDB，同一事务里核对写入栅栏）
             │                                 ─► 状态："已保存在本机"
             │ 在线，并且持有编辑租约
             ▼
       ③ 上传服务器（条件写入，同时只有一个请求在途）
             │ 服务端确认
             ▼
       ④ 删除本机记录（只删到已确认的序号）─► 状态："已保存到云端"
```

**起始参数**（本机捕获一行经 M0 实测确认，其余以压测结果为准进行调整）：

| 环节 | 参数 |
|---|---|
| 本机捕获 | 修改停止 1 秒后捕获；持续编辑时，从第一处未保存的修改算起最长 3 秒捕获一次 |
| 上传服务器 | 本机有更新的快照、且没有在途请求时上传：停顿 2 秒后上传；持续编辑时最长每 15 秒上传一次 |
| 立即上传 | 释放编辑权、交出编辑权、标签页转入后台时 |
| 大文档 | 按实测的捕获耗时和体积拉长间隔，例如捕获间隔不小于捕获耗时的 10 倍 |

同一份序列化并压缩后的数据，既用来写入本机，也用来上传，不需要重复捕获。

**放置**（M0-P6 报告 §2.3）：SDK 的模型只在主线程上，`save()`、序列化与编码必须在主线程做，5 MiB 表格时 p95 74–87 ms（三个浏览器），这是单快照上限下主线程成本的下限。之后的去重哈希、gzip、加密与写入放进发件箱 Worker：gzip 是其中最大的一段（5 MiB 表格：Chromium 内核约 90 ms，WebKit 约 63 ms），放进 Worker 后，异步段的主线程最长阻塞 Chromium 内核约 6 ms、WebKit 约 9 ms；加密 p95 不超过 2 ms，写入 IndexedDB 的 p95 不超过 4.3 ms。WebKit 上发件箱 Worker 空闲之后，第一次异步操作（去重哈希或 gzip）偶尔多等约 1 秒，5 MiB 表格约八分之一的捕获因此要约 2.2 秒；Worker 里保持一个 100 ms 的空定时器后，40 次都没有出现（M0-P6 报告 §2.3 第 11 条）。M4 采用这个做法，或者在真实 Safari 上验证过的等效做法（DEF-011）。

**会话内去重**直接对 `save()` 的 JSON 文本（或它的 gzip 结果）算哈希，不需要规范化：这种口径的误差只会让内容没变的快照多上传一次，不会漏传。跨加载与服务端的内容哈希口径见 §7.4。

### 7.3 变更检测与快照捕获

以下依据源码核查与 M0 实测（M0-P3 报告 §2、§3，M0-P5 报告 §1.2 第 3 条，M0-P6 报告 §1.2 第 5 条）。

**变更检测**：
- **只看 `MUTATION` 类型的命令。** 监听 Facade 的公开事件 `CommandExecuted`，排除带有 `onlyLocal`、`fromCollab`、`fromChangeset`、`fromFormula` 标记的 mutation，以及作用于其他单元的 mutation（参数里的 `unitId` 不是本文档，例如单元格编辑器内部的 `doc.mutation.rich-text-editing`）。官方 Facade 的示例用的也是同样的过滤方式。M0 实测：23 个样本的 37 种打开组合都没有被判定为有修改；48 种改内容的动作都被检测到，8 种只改视图的动作都没有被检测。
- **排除 `onlyLocal` 有前提**：备注与超链接的位置联动、公式文本的引用更新、公式结果写回，都以 `onlyLocal` 修改持久化内容。前几类都紧随一次被检测到的修改，由同一次捕获带上；公式结果由下面的捕获时机收齐。
- **不排除行高自适应**（更正 r2）：1.0.0 打开文档不会触发它；如果排除，5 万行改字号时有三到六成的行高变化晚于捕获到达，会一直漏存。自己维护的排除名单只有两条：`sheet.operation.clear-drawing-transformer`、`doc.operation.clear-drawing-transformer`（名为 operation，类型却声明为 `MUTATION`，只清除界面上的图片变换框）。排除名单随 SDK 版本维护，并纳入回归测试。
- **关掉大表操作的拆分**：SDK 默认把大表操作拆开执行，复制大表后立即捕获只拿到 3,000 个单元格，其余部分在空闲时以 `onlyLocal` 执行，既检测不到，又可能被忙碌或后台的标签页任意推迟，"立即上传"（§7.2）的快照就会缺数据。表格档案把 `largeSheetOperation.largeSheetCellCountThreshold` 设为最大值（§8.2），代价是复制大表多花 4–56 ms 主线程时间，大表复制、删除的撤销记录会带上整表数据。关掉之后，删除大表也不再清空整个撤销栈（SDK 删除时按行数判断"大表"，实测删除约 1.33 万行的表时撤销栈被清空）。
- 打开文档时，默认的计算模式 `WHEN_EMPTY` 不会重算已有的公式缓存值；易变函数（NOW、RAND 等）例外，它们会被重算并以 `onlyLocal` 写回，不算修改。

**捕获时机**（一条规则，捕获前必须按它等待）：
- 用户修改进入"待捕获"；公式结果写回本身不进入待捕获，否则打开含易变函数的文档就会被当成有修改。
- 在最后一次修改之后发起一次 `getFormula().onCalculationResultApplied(timeout)`，并等到距最后一次修改满 1 秒（防抖）。
- 等公式计算"收齐"，以下三条同时满足：没有排队的下一轮；这一轮没有被 stop；逐表收齐，即每张有结果的工作表都收到写回（修改没有牵动公式、只收到完成通知时视为收齐）。
- 组合输入（输入法）进行中不捕获，因为 SDK 在组合中就把拼音写进模型；防抖从"最后一次修改"与"最后一次组合结束"中较晚的一个算起；隐藏输入元素失焦时复位组合状态。
- 等待期间又有修改，就从头再来。
- 上限：从第一处未保存的修改算起最长 3 秒，这个上限同时约束公式收齐与组合输入的等待。超过上限照常捕获，记录标记"公式待更新"；公式收齐后补捕获一次，写入不带标记的记录。恢复带标记的快照时强制全量重算，算完再捕获（§7.5）。
- **只用等待接口不可靠**：公式 Worker 模式下，它在第一张工作表的结果写回后就返回（SDK 缺陷）；它也只等调用时正在进行的一轮，不覆盖因之前的修改而排队的下一轮。只等"最近一轮"的规则在"计算进行中再改一次"时会存下多达 204/406 个过期值，而过期值一旦被捕获，之后不会补捕获，默认模式重开也不重算。
- 按这条规则，M0 的五类公式场景、"静默窗口内再改一次"与"计算进行中再改一次"，在主线程与公式 Worker 两种模式、三个浏览器下，快照中的公式值都与公式定义一致。规则依赖几个内部约定（执行选项 `applyFormulaCalculationResult`、公式 mutation 的 id 与完成通知的 `functionsExecutedState`、`IActiveDirtyManagerService` 的脏区判断），在适配层集中登记（§10.1），升级 SDK 时回归。

**其他**：
- **视图状态**：表格缩放由渲染控制器直接写进 `zoomRatio`，文字文档缩放由 operation 写进 `settings.zoomRatio`。它们不触发变更检测，会随下一次真实修改一起保存，可以接受。比较内容时去掉视图状态字段（`zoomRatio`、`scrollTop`、`scrollLeft`、`settings.zoomRatio`）。
- **SDK 没有内置脏标记**：快照里的 `rev` 字段从来不会被递增。本地修改序号由平台自己维护。
- 捕获使用 `FWorkbook.save()` / `FDocument.save()`，得到的结果包含插件资源。适配层在捕获前不调用 Facade 的读取方法，例如 `getDataValidations()` 会给模型建空条目，改变保存的字节。

### 7.4 服务端提交

每次上传包含：
- 文档标识、租约令牌、`writeEpoch`、`baseRevision`；
- 请求标识 `requestId`、客户端实例标识 `clientInstanceId`、本地序号 `localSeq`；
- 客户端构建版本；
- gzip 压缩的快照。

会话令牌与租约令牌不得出现在 URL 或普通日志里。

服务端的处理顺序：

1. **解压与校验**：解压时限制解压后的体积，防止压缩炸弹；然后做快照校验（§11.2），并按规范化口径计算内容哈希（见本节末）。
2. **幂等**：如果 `document_revisions` 里已经有相同的 `requestId`，负载摘要一致就返回原来的确认结果，不一致就拒绝。这一步只要求请求者对文档仍有访问权，不要求租约依然有效。
3. **单事务写入**：按统一的加锁顺序，依次执行：
   - 校验权限；
   - 校验租约与代次；
   - 校验 `baseRevision` 等于当前修订号；
   - 校验插件资源没有缩水（§8.2）；
   - 内容哈希与当前相同时，不递增修订号，直接返回确认；
   - 否则写入内容、修订号加一、写入 `document_revisions`、按授权更新资源引用（§8.5）。
4. **拦截旧客户端**：客户端构建版本低于服务端要求的最低版本，或低于这份文档记录的 SDK 版本时，拒绝保存（`CLIENT_OUTDATED`）并要求刷新页面。这是为了防止部署新版本后，还开着的旧标签页用旧 SDK 把文档写回旧格式。
5. **拒绝时返回机器可读的原因**：无权限、租约失效、文档被占用、修订号冲突、负载超限、格式不兼容、客户端过旧。其中修订号冲突的响应，要附带当前修订号及其来源（`clientInstanceId`、`localSeq`），让客户端能判断是不是"自己追自己"。

**内容哈希的口径**（M0-P3 报告 §4.3）：同样的内容在两次加载之间，`save()` 的文本会因 SDK 补齐默认字段、资源顺序、空值写法、视图状态而不同；gzip 的结果还因浏览器而异。所以服务端"内容相同不递增修订号"与平台信封的内容哈希（§8.1），都基于规范化后的内容计算：以 JSON 文本为准，资源按名称排序并做空值等价归一化（`""` 与 `{}`、按工作表分组的空数组），去掉视图状态字段（§7.3）。客户端与服务端使用同一种规范化算法；它是同步计算，1 MiB 约 19–26 ms、5 MiB 约 73–85 ms（p50–p95，三个浏览器），放在 Worker 或服务端做。§7.2 的会话内去重不需要规范化。

### 7.5 本机发件箱与恢复

以下方案经 M0 原型验证（M0-P6 报告 §1.2、§2），生产实现由 M4 按正式流程设计。

**发件箱记录**：每个用户的每份文档最多一条。内容包括：文档标识、基准修订号、`writeEpoch`、`localSeq`、在途请求标识、客户端构建版本、密钥版本、"公式待更新"标记、加密后的快照（每条记录一个随机 IV）、更新时间。
- 每次覆盖写入同一个键，由 IndexedDB 事务保证原子性，不需要"先写新、再删旧"。M0 实测：写入 5 MiB 表格的过程中被杀（每个浏览器 7 次）、提交附近被杀（每个浏览器 8 次），重启后都是完整的旧记录或新记录，都能解密、解压、解析（三个浏览器）。
- 写入用 `durability: 'strict'`：在 macOS 上没有可测的额外开销，但不等于已经完整落盘，断电下的效果没有验证（DEF-009）。
- 捕获串行执行，序号在 `save()` 的同步段里分配，同一份文档的写入排队；"只删到已确认的序号"在同一个事务里比较。
- 记录的键与锁名都用平台的 `documentId`，不用 `unitId`（两者解耦，§8.3）。

**标签页协调与写入栅栏**：
- 处于编辑状态的标签页，通过 Web Locks 持有这份文档的排他锁（锁名 `nerve-doc:<documentId>`，以 `ifAvailable` 申请）；页面关闭、崩溃或导航离开后，锁会自动释放。[S16]
- 拿不到锁的标签页只读，提示"另一个标签页正在编辑"，不写发件箱、不上传，排队等锁。M0 实测：持有者关闭、导航离开后，等锁的标签页 0–13 ms 内接手；渲染进程崩溃后 11–219 ms（崩溃只能在 Chromium 内核上模拟）。
- 拿到锁后登记为持有者（令牌 + 代次），之后每次写入、删除都在同一个事务里核对持有者令牌，不符就中止（写入栅栏）。只靠锁不够：锁被抢走时，原标签页可能正在等待一次捕获，或者 Worker 里还有一次写入在途。
- 锁被抢走（`steal`）时，原标签页立即停止自动保存、转为只读，不再处理上传确认后的删除；绕过锁检查的写入被写入栅栏拒绝。
- 恢复流程只有拿到锁之后才启动，避免多个标签页争抢同一份草稿；待恢复决定期间只读。接手时服务端的修订号比打开时新，先从服务端重新加载。
- 同一浏览器内的"本人接管"（§6.3）：正常交出时，旧标签页先同步，再释放锁；旧标签页没有响应时，新标签页用 `steal` 接手，从发件箱恢复。

**恢复规则**：

| 场景 | 行为 |
|---|---|
| 断网后继续编辑 | 修改持续写入本机，横幅提示"已离线，修改已保存在本机"；恢复网络后自动续租并同步 |
| 断网时间超过租约有效期，但期间没人接手 | 恢复网络后重新申请编辑权。服务器修订号等于本地的基准修订号，就直接上传最新快照（快进），用户基本感觉不到 |
| 断网期间已经有人接手并保存 | 这是真冲突。不覆盖对方，提供"另存为副本"或"放弃本地修改" |
| 上传已经发出、确认还没收到，接着断网或崩溃 | 恢复时先用原来的 `requestId` 做幂等重试。如果服务器当前的修订号正是本机早先的请求产生的，就以新修订号为基准，重发最新的快照 |
| 标签页崩溃、被误关、浏览器被杀、系统休眠后页面被回收 | 重新打开这份文档，或者从文档列表的"未同步修改"提示进入时，提示"发现 14:32 未同步的修改"。修订号没变的话，一键恢复后继续编辑；记录带"公式待更新"标记时，恢复后强制全量重算 |
| 本机密钥被吊销，或记录被篡改 | 解密失败，记录作废，提示"本机的未同步修改无法恢复"；按密钥版本区分"已吊销"与"被篡改" |
| 被撤权、被移出空间、账户被停用 | 删除本机的未同步修改，不允许另存为副本 |
| 退出登录 | 有未同步修改时先提示；退出后清空该用户在本机的全部数据 |
| 本机记录超过保留期限 | 下次登录时提示，然后删除 |

**恢复的前提与实测**：
- 密钥只在内存里，恢复前要联网向服务端重新取密钥，所以离线时打开文档无法解密本机记录，恢复在联网之后进行（与 §7.8"不承诺离线冷启动"一致）。
- 修订号与记录的基准相同才能一键恢复；不同时，先按上表用原来的 `requestId` 做幂等重试，修订号由本机早先的请求产生时不算冲突（M0 没有验证这一步）；其余情况是真冲突，不自动恢复。
- 恢复带"公式待更新"标记的快照时，强制全量重算，算完再捕获。M0 实测：三个浏览器都出现了公式没收齐的捕获，恢复（含强制重算）约 3.9 秒，恢复后 201 个公式与输入一致。
- M0 实测：浏览器进程被杀（SIGKILL）后，都能恢复到最后一次写入本机的内容；5 MiB 表格的恢复路径（读取、解密、解压、解析）合计 p50 21–30 ms、p95 29–45 ms（三个浏览器）。

**另存为副本**：
- 在原文档所在的文件夹里新建一份文档（前提是用户在该空间有新建权限），否则放进用户的个人空间；
- 标题后面追加"（冲突副本 时间）"；
- 副本不继承原文档的单独授权。

**离线时禁用**：插入图片、CSV 导入、分享、移动等需要服务端参与的操作。

**mutation 增量日志（M0 结论：可行；v0.1 不纳入）**：在两次快照之间，把用户产生的每一条 mutation 追加写入本机；崩溃后用"最近一次快照 + 重放这些 mutation"来恢复，可以把丢失窗口从 1–3 秒降到约 0.1 秒（按日志的批量间隔推算）。
- M0 验证可行（M0-P6 报告 §3）：参数能结构化克隆；表格补全 4 类 mutation（样式附带记录、批注 id 回填）后，12 个场景重放后逐字节一致；文字文档 7 个场景不补全就一致；"快照 + 日志"在进程被杀后能恢复到被杀前的内容。
- 不纳入的原因：它依赖不公开的协同钩子 `onMutationExecutedForCollab`（开源代码里没有使用者），每次升级 SDK 都要重新排查全部 mutation；恢复时没有"标准答案"可比，重放一旦出错会悄悄写坏文档，比丢失最后几秒更糟；日志同样要加密、按用户隔离、随快照截断，发件箱的复杂度与测试面大约翻倍。快照已经满足 §7.8 的承诺。
- 所以 M4 只做快照；增量日志列为 v0.2 候选（DEF-010），纳入时的要求见延期登记。

### 7.6 本机数据安全

- **只存未同步的修改**：同步确认后立即删除，本机不缓存文档正文。
- **AES-GCM-256 加密**（M0-P6 报告 §1.2 第 3 条）：
  - 密钥按用户生成，服务端用自己的主密钥加密后保存，登录后按会话下发给客户端；
  - 客户端把下发的原始密钥导入为不可导出的 `CryptoKey`，只放在内存里（可以传给 Worker），所以退出登录或会话失效后，本机数据就无法解读；每条记录一个随机 IV；
  - 附加数据（AAD）覆盖全部参与恢复决策的明文元数据：用户、文档、序号、基准修订号、`writeEpoch`、密钥版本、客户端构建版本、"公式待更新"标记。改动其中任何一项，解密都会失败（M0 实测：把基准修订号改成服务端的，解密失败）；
  - 设备丢失时，管理员可以吊销该用户的本机密钥，这个人所有的本机草稿随即作废；恢复时按密钥版本区分"已吊销"与"被篡改"。吊销后，已打开的标签页要尽快停止写入，与在线会话联动；
  - 已接受的风险：把同一文档的旧记录整条写回（本机回滚）防不住；记录键里的文档 id 是明文，需要时改用按用户密钥计算的 HMAC。
- 发件箱记录按用户隔离（M0 实测：另一个用户打开同一文档看不到记录）；单条记录最长保留 14 天。
- **存储空间**：仍然向浏览器申请持久化存储（`navigator.storage.persist()`），但它不可靠：无头浏览器都返回 false，真实浏览器的授予条件各不相同（DEF-009）。所以产品要显示存储状态。写满时报 `QuotaExceededError`：失败的写入整个事务回滚，已有记录不变、仍能解密，自动保存保持"未保存"并提示存储空间不足。
- **退出登录时清空本机数据**（§7.5），要覆盖 Univer 自己的存储：IndexedDB 库 `UniverLocalStorage`、localStorage 中以 `UniverLocalStorage/` 开头的键、`univer-mobile-recent-formula-functions`；也可以用依赖注入把 `ILocalStorageService` 换成内存实现（M0-P2 报告 §4.2）。
- 敏感部署可以在系统设置里整体关闭本机草稿。关闭后退化为"内存暂存 + 离开提示"，并在界面上明确提示风险。

### 7.7 保存状态与用户提示

界面至少要区分这几种状态：已保存到云端、同步中、已保存在本机（等待同步）、离线、编辑权已失效、版本冲突、容量超限、本机存储空间不足（本机写入失败）、另一个标签页正在编辑（本页只读）、文档数据不完整（打开自检失败，已阻止编辑，§8.2）。只有服务端确认成功后，才显示"已保存到云端"。

- 有未同步修改时离开页面，弹出浏览器的离开提示。
- 快照达到容量上限的 80% 时提示；超过上限后上传会被拒绝，界面持续提示"文档超过容量上限，最近的修改无法同步"，本机记录保留。
- 文档列表页标出当前用户有未同步修改的文档。

### 7.8 可靠性承诺与丢失边界

| 情况 | 承诺 |
|---|---|
| 服务端已确认的数据 | 不会因应用重启或客户端异常而丢失；受备份保护，恢复目标见 §12.4 |
| 网络中断期间的输入 | 不丢失，因为已经写入本机；恢复网络后同步，或另存为副本 |
| 页面崩溃或被强制关闭 | 丢失的只是最后一次写入本机之后的输入：停顿后约 1 秒（公式计算慢的文档延长到公式收齐，受 3 秒上限约束）；连续输入时最多约 3 秒，再加上轮询与写入本机的耗时（几十到几百毫秒） |
| 断电或操作系统崩溃 | 最近一次写入本机的内容能否保住，取决于浏览器是否已把它落盘。写入用 `durability: 'strict'`，但 M0 无法验证断电下的效果（DEF-009） |
| 清除浏览器数据、更换设备、本机草稿被关闭 | 未同步的修改无法恢复 |

M0 实测（M0-P6 报告 §2.3）：持续编辑时每 200 ms 改一处，分别改 16、23、30 处后杀掉浏览器进程，恢复出的修改都是连续的前缀；丢失窗口（第一处丢失的修改到杀进程）Chromium 与 Chrome 约 0.2、1.7、0 秒，WebKit 约 0.5、2.0、0.5 秒，都在上限以内（3 秒，加 50 ms 的轮询与最多两次写入管道）。

不把关闭页面时发出的异步请求当作保存机制；不承诺离线冷启动，恢复本机的未同步修改需要联网取密钥（§7.5）。

## 8. 内容存储与数据模型

### 8.1 快照存储与平台信封

文档内容以 Univer 原生快照的形式保存，不把单元格映射成业务表；元数据用普通的关系表。

**快照用 `bytea` 存 gzip 压缩后的原始 JSON 字节，不用 `jsonb`。** 原因如下：

- `jsonb` 不接受 `\u0000`：用户粘贴一段带 NUL 字符的文本后，这份文档就再也存不进去了。[S9]
- `jsonb` 会重排键、去掉重复键，导致内容哈希和客户端算出来的对不上；而且每次写入都要解析整份 JSON。
- 服务端不需要在数据库里查询快照内部的字段。
- 压缩后，库的体积、WAL 和备份量都会明显下降；读取时还可以直接以 `Content-Encoding: gzip` 下发给浏览器。

**平台信封的字段**：
- 文档类型、平台格式版本；
- 插件档案的标识与版本；
- 写入时的 SDK 版本、客户端构建版本；
- 内容哈希（SHA-256，基于规范化后的内容计算，口径见 §7.4）；
- 修订号。

不以 SDK 版本号作为平台格式的唯一版本号。

**新建文档使用收敛后的模板快照**：即使是 SDK `save()` 的输出，也要再经过一次"重开 → 保存"才逐字节稳定（资源会在 `""` 与 `{}` 之间变化，按工作表分组的空数组会被删掉）；手写的快照第一次打开时会被补齐默认字段，缺少的 id 会被随机生成（例如文字文档的 `sectionId`）。所以平台新建文档时，使用收敛之后的模板快照（M0-P2 报告 §2.3）。

### 8.2 插件档案与资源完整性

源码核查的结论是：保存时，SDK 只输出当前已注册插件的资源，并用它整体覆盖快照里的 `resources`。所以**没有注册的插件，它的资源会被静默丢弃**（`resource-loader.service.ts:164-173`）。M0 另外证实了两类同样静默的问题：资源数据损坏时，多数插件的解析不报错，直接把资源清空，下一次保存就写回空值；同名资源 SDK 只取第一条，重复条目能让伪造的数据生效（M0-P2 报告 §3）。对策如下：

- 为每种文档类型定义一份固定的"插件档案"，例如 `sheet@1`、`doc@1`，内容包括插件列表与注册顺序、各插件影响数据的配置、适用的 SDK 版本、资源名称白名单，以及编辑器适配层安装的平台策略。M0 定稿插件档案 v1（`docs/v0.1/M0-技术验证/reports/插件档案v1.md`），要点如下：
  - `sheet@1`：按官方 preset 的分组与顺序注册。影响数据的配置：`UniverSheetsPlugin` 设 `onlyRegisterFormulaRelatedMutations: false`，`largeSheetOperation.largeSheetCellCountThreshold` 取最大值（关掉大表操作的拆分，§7.3）。默认启用公式 Worker：主线程注册 `UniverRPCMainThreadPlugin`，三个公式相关插件设 `notExecuteFormula: true`。理由：主线程模式下，一次牵动约 320 个公式的修改会冻结界面 0.66–0.83 秒；Worker 模式下计算期间帧间隔 p95 ≤ 34 ms，代价是多约 8–9 MiB 内存（性能样本 `perf-50k`，M0-P3 报告 §6）。Worker 创建失败时，销毁实例、以主线程模式重建，并把公式引擎的让出间隔 `intervalCount` 调到 20（§10.2）。
  - `doc@1`：Docs、RenderEngine、UI、DocsUI（`toc: true`，即文档大纲侧栏），加上图片、超链接、查找替换三组。不注册公式引擎：文字文档启用的插件都不依赖它，去掉后按 `doc@1` 的插件清单构建，首屏 JS 未压缩从 5.13 MiB 降到 3.75 MiB（−27%），gzip 后从 1.23 MiB 降到 0.99 MiB（−19%）。不注册目录块插件（§4.4）。排版 Worker 暂不启用：Worker 模式下，在表格单元格里键入后立即按 Tab，Tab 会丢失，后面的字写进同一格（DEF-007，M6 重新评估）。
  - 两种档案都不注册 `@univerjs/network`、线程评论、水印等插件，也不注册任何 `ITelemetryService` 实现。
- 编辑器页面必须把档案里的插件全部加载完，才允许进入编辑；任何一个插件加载失败，都只允许阅读。
- **客户端打开自检**（编辑器适配层，M0-P2 报告 §3.3）：
  - 档案完整性：运行时注册、适用于本文档类型的资源 hook，必须与档案白名单一致；
  - 资源比较：加载后立即捕获一次，原来非空的资源消失或变空，就判定失败。有意不把"内容有变化"算作失败，因为 DEF-002 的图片尺寸与空值等价会合法地改变内容；
  - 资源加载错误捕获：用依赖注入覆盖 `IResourceManagerService`，包装每个 hook 的 `parseJson` 与 `onLoad`，识别"解析抛错""非空输入被吞成空值""加载抛错"三种失败（内部 API，§10.1）。它能发现资源比较拦不住的"结构不对"；
  - 失败后只允许阅读，提示"文档数据不完整，已阻止编辑"，并把失败详情上报服务端、告警；由运维从历史版本或检查点恢复，或者修复档案后重新打开；
  - 成本：打开自检的这次捕获，1 MiB 表格约 14–22 ms，5 MiB 约 36–41 ms；资源加载错误捕获对首屏的影响在测量误差以内（M0-P3 报告 §4.2）。
- 文档信封里记录它用的档案标识。档案变更（增删插件、改变影响数据的配置）视为数据格式变更，走 §8.7 的流程。
- **服务端校验**（与 §11.2 的快照校验一起执行）：
  - 结构：资源名唯一，`data` 必须是字符串；
  - 资源名称必须在档案的白名单内；
  - 上一版中非空的资源，在新快照里消失了，就拒绝保存并告警。但不能因为资源"变为空"而拒绝：用户删光规则时，资源会合法地变空；
  - 每一项资源按下表处置。
- 阅读模式也加载同一份档案，因为渲染需要它（比如条件格式）。这不会影响数据，因为阅读模式不保存。
- 资源名称清单已在 M0 按锁定版本生成：以运行时注册、适用于本文档类型的资源 hook 为准，三个浏览器一致，并与源码检索交叉核对；随版本升级复核。

| 资源 | 文档类型 | 服务端处置 |
|---|---|---|
| `SHEET_CONDITIONAL_FORMATTING_PLUGIN`、`SHEET_DATA_VALIDATION_PLUGIN`、`SHEET_DEFINED_NAME_PLUGIN`、`SHEET_DRAWING_PLUGIN`、`SHEET_FILTER_PLUGIN`、`SHEET_NOTE_PLUGIN` | 表格 | 允许；做结构校验 |
| `SHEET_RANGE_PROTECTION_PLUGIN`、`SHEET_WORKSHEET_PROTECTION_PLUGIN`、`SHEET_WORKSHEET_PROTECTION_POINT_PLUGIN`、`SHEET_AuthzIoMockService_PLUGIN` | 表格 | 必须为空（保护规则不是安全边界，界面也隐藏了解除入口，§6.5） |

### 8.3 unitId 与文档复制

- 平台的 `documentId` 和 Univer 内部的 `unitId` 相互独立。`unitId` 在文档创建时生成、存在快照里，终身不变。复制文档时快照原样复制，**不改写** `unitId` 和工作表 id。
- 原因：`unitId` 与工作表 id 内嵌在图片、评论等对象的内部；筛选、验证、条件格式等资源又以工作表 id 为键；文档内部的链接也引用工作表 id。逐个字段改写很脆弱，而且会随版本变化。
- 约束：同一个 Univer 实例里，不能同时加载两份 `unitId` 相同的文档，否则 SDK 会抛异常。本期编辑器一页只加载一份文档，满足这个约束。将来如果需要在同一页加载多份文档（比如跨文档引用），再引入改写方案。
- M0 验证成立（M0-P2 报告 §4）：两份 `unitId` 相同的文档在两个标签页中同时编辑、保存、重开，互不影响，语义与资源都没有丢失；同一实例里重复创建相同的 `unitId` 会抛异常。Univer 自己的浏览器存储（`UniverLocalStorage`）只存用户习惯，不按 `unitId` 区分，也没有使用 BroadcastChannel、SharedWorker 或 Service Worker，不会串扰。本机发件箱的键与锁名用 `documentId`（§7.5）。
- 复制还需要处理：新文档的标识与授权（按目标空间的规则），以及资源引用关系（新增 `document_asset_links` 记录，不复制图片文件）。

### 8.5 图片资源

以下方案经 M0 验证（V11、V12，M0-P4 报告 §1.2），由 M5 实现。

- **上传**：通过 `UniverDrawingPlugin` 配置里的 `override` 替换 `IImageIoService`，表格与文字文档都要注册（官方 preset 不开放 `override`，档案本来就逐个注册插件）。用户插入或粘贴图片时，先上传到平台，再返回同源地址 `/api/assets/{assetId}`；快照里只保存这个地址（`ImageSourceType.URL`），不内联 Base64。平台图片服务的约定（SDK 的调用方有硬性要求）：
  - `saveImage` 先在客户端检查类型与大小，再上传，返回 `URL` 类型的同源相对地址；`base64Cache` 用同一个地址（插入流程用它量尺寸）；
  - `imageId` 每次随机生成，不用 assetId（它直接当作 drawingId，而同一张图可能被插入多次）；
  - 失败时以 `Error(ImageUploadStatusType.X)` 拒绝，SDK 才会显示本地化提示：413 对应"大小超过限制"，415 对应"类型错误"，其他对应"无效图片"；
  - `change$` 在上传开始时发出正数、结束时回到 0；加载失败的元素从缓存中删除。
- **格式对齐**：SDK 默认的文件选择框接受 `.png,.jpeg,.jpg,.gif,.bmp`（没有 WebP，却有平台会拒绝的 BMP），粘贴时挑选图片的类型集合没有 GIF；默认下，表格粘贴 WebP、文字文档粘贴 GIF 都插不进去。平台启动时把 `DRAWING_IMAGE_ALLOW_IMAGE_LIST` 与 `imageMimeTypeSet` 改为 PNG、JPEG、GIF、WebP（模块级状态，内部 API，§10.1）；类型与大小由客户端、服务端各查一次（§11.4）。
- **粘贴与命令**：粘贴钩子与命令守卫对任何位置的图片地址默认拒绝（§11.3）。文字文档粘贴时，钩子返回的相对地址会被 SDK 转成绝对地址，由粘贴钩子规范回相对地址。
- **鉴权读取**：Univer 渲染图片时使用 `crossOrigin="anonymous"`，而同源请求在这种模式下仍然会带上 Cookie，所以读取可以走正常的鉴权。M0 实测：浮动图片以 cors 方式、单元格图片以 no-cors 方式读取，都带上了会话 Cookie。无权与不存在都返回 404，不暴露 assetId 是否存在；没有会话时返回 401。
- **读取失败返回平台占位图**：返回 200，把真实状态放在 `X-Asset-Status` 头里，并带 `no-store`（否则占位图会以真实图片的地址被缓存）。原因：读取失败时，SDK 渲染可能对破损的图片调用 `drawImage`，抛出未捕获的 `InvalidStateError`（返回错误状态码时 9 次里出现 5 次，返回占位图时 0 次）。局限：截断的图片、网络失败、离线编辑仍会触发，由 M5 评估客户端兜底或补丁（§10.3）；走 `fetch` 的路径（例如"保存单元格图片"）要检查 `X-Asset-Status`，否则会静默拿到占位图。
- **存储方式**：每次上传都生成独立的 assetId 并记录上传者；图片文件按内容哈希（SHA-256）去重存储，多个 assetId 可以指向同一个文件。文件只追加、不修改。
- **引用关系**：由服务端从快照解析后的全部字符串值中提取本平台的资源地址（按 `/api/assets/{uuid}` 模式匹配），`IMAGE()` 公式里的地址也算；不在原始 JSON 文本上扫描，否则 `\/` 转义会让扫描漏掉。这样不需要理解 Univer 的内部结构；本站的 origin 取自配置，不取自请求头。每次保存时按授权更新 `document_asset_links`（见"保存校验"）。
- **读取授权**：满足以下任一条件即可读取：
  - 请求者能读取任意一份引用了这张图片的文档；
  - 请求者是上传者，且图片上传还不到 24 小时。这是为了覆盖"已上传、但还没随快照保存"的窗口。
- **保存校验**：
  - 快照中任何深度上名为 `source` 的字段，都必须是平台地址 `/api/assets/{uuid}`（不带查询参数与片段），否则拒绝保存（§11.2）；存储前把本站的绝对地址改写为相对地址。
  - 引用关系只为保存者有权读取的图片建立：这份文档原来就引用它、保存者是 24 小时内的上传者，或者保存者能读引用它的其他文档。无权的地址不建立引用，但保存照常成功，因为拒绝保存会让本地优先管道反复重试。这样，把别人的图片地址写进自己的文档，不会因此获得读取权。
- **回收**：没有任何文档、历史版本或检查点引用的 assetId，超过宽限期后删除；某个文件已经没有任何 assetId 指向时，才删除这个文件。**宽限期不短于备份保留期**，这样数据库做时间点恢复之后，被引用的图片一定还在。只上传、没有被引用的孤儿文件（例如在编辑栏里粘贴图片：先上传，再被编辑栏拒绝）也由回收处理。
- **复制与恢复**：复制文档、从历史版本恢复为副本，都只新增引用关系，不复制文件（M0 实测：文件数不变，原文档删除后副本里的图片仍能读取）。
- **表格复制补救**：SDK 复制 `URL` 类型的浮动图片时，200 ms 后往系统剪贴板写空文本，另一个文档与外部应用都拿不到图片。平台在它之后把同源图片转成 PNG 写入剪贴板；这依赖计时与剪贴板权限，真实 Safari 下的行为见 DEF-004。

### 8.6 历史版本与恢复检查点

- 当前快照始终保留。
- 文档有变更时，每小时最多生成一个检查点，保留 7 天。这就是用户可以看到的"历史版本"。
- 删除文档之前，以及 SDK 或插件档案升级迁移之前，额外生成检查点，保留 30 天，只供运维恢复。
- **谁能看**：编辑者可以查看历史版本列表（时间、保存人）、只读预览、"恢复为副本"。查看者看不到，因为历史版本中可能留着后来被删掉的敏感内容。空间管理员可以清除某份文档的全部历史版本，操作记入审计。
- **不做**：逐操作回放、差异对比、就地回滚。这和 Pro 的编辑历史是两回事，本平台只保存整份快照。
- 容量与保留策略，在试运行前按实际数据量验证。

### 8.7 SDK 升级与数据格式

源码核查的结论是：Univer 没有跨版本的快照迁移机制；`appVersion` 只是个信息字段，而文字文档的快照里连这个字段都没有。因此：

- SDK 升级与数据迁移分开评审。升级前，用历史样本（每个插件的保存/重开样本）做回归：差异与基线一致、语义与预期一致、档案声明的资源名与运行时资源 hook 一致，比较前先做空值等价归一化（M0-P2 报告 §2.2）；同时回归变更检测与捕获时机（含"计算进行中再改一次"与公式 Worker 的写回时序），以及文字文档锁定 SDK 行为的对照用例（M0-P5 报告 §7）。增删插件、改变影响数据的配置，也按数据格式变更处理。
- 新版 SDK 打开旧快照并保存后，文档就按新格式写入了。所以升级前要为所有文档生成迁移前检查点。
- 未知的平台格式版本或档案标识，不得被静默改写；客户端拒绝编辑并给出提示。
- 服务端要求的最低客户端构建版本随发布更新，旧标签页不能再保存（§7.4）。
- 后续可以利用 Univer 在 Node.js 下的无界面运行能力，在服务端批量"打开再保存"来完成格式迁移；本期不实现。M0 的可行性记录（V16，M0-P6 报告 §4）：
  - 纯 Node 24（不用 happy-dom）用发布的包加载 20 个样本再保存，只注册有数据的无界面插件与 `UniverRenderEnginePlugin`，资源 hook 与浏览器一致；
  - 生命周期只到 Ready，依赖 Rendered、Steady 才初始化的控制器在 Node 下不工作，迁移时要逐项确认；
  - 没有文字测量，自动行高与依赖行高的图片变换不会重算，所以适合"打开再保存"，不适合需要重新排版的迁移；
  - 迁移用 `NO_CALCULATION` 加载，避免加载时重算改变输出（按源码推断）。

## 9. 总体技术架构

### 9.1 推荐方案

一个前端应用，加一个模块化的 Node API 应用。Univer 运行在浏览器里；后端负责身份、组织与空间、授权、快照、租约、资源、历史版本和运维接口。

```text
浏览器：React + TypeScript + Vite
  ├─ 登录、个人空间、团队空间、与我共享、回收站、系统管理
  └─ 编辑器页（整页加载）：Univer 开源插件 + 平台适配层 + 本机发件箱（IndexedDB + Web Locks）
       └─ Web Worker：公式计算（表格默认启用）；发件箱的压缩、加密与写入
                     │
                HTTPS / REST（同源）
                     │
             Node.js + NestJS 模块化单体
              ├─ 账户 / 组织与空间 / 文档授权
              ├─ 文档元数据 / 快照 / 修订 / 编辑租约与交接
              ├─ 图片资源 / 历史版本 / 审计 / 健康检查
              └─ 本机密钥 / 备份与运维入口
                     │
            PostgreSQL + 持久化资源目录
                     │
              独立故障域的备份目的地
```

**不需要官方的协同 Server SDK，也不需要实现它的 PostgreSQL Adapter。** MVP 不要求服务端加载编辑器或重算公式；服务端也不把客户端算出的公式结果当作可信的业务事实。

### 9.2 技术选型

| 层次 | 建议 | 说明 |
|---|---|---|
| 前端 | React + TypeScript + Vite | Univer 视图层基于 React，支持 React 18/19（peer 范围 16.9–19，M0 用 19.3.0 验证）；编辑器页是独立入口，整页加载 |
| 编辑器 | Univer 开源 1.0 线，插件模式 | 固定插件档案；不使用 presets；不引入 Pro |
| 后端 | Node.js 24 LTS + NestJS 12 | 模块化单体；请求体上限按快照容量单独配置 |
| 数据库 | PostgreSQL 18 | 支持到 2030 年 11 月；镜像按摘要锁定，不用浮动标签 |
| 数据访问 | Drizzle ORM + pg | 类型化模型与迁移；关键写入直接用参数化 SQL 与显式事务 |
| 会话 | 服务端 Session + PostgreSQL | 浏览器只持有 HttpOnly Cookie |
| 本机存储 | IndexedDB + Web Locks + WebCrypto + CompressionStream | 发件箱、标签页协调、AES-GCM 加密、gzip 压缩；压缩、加密与写入放在发件箱 Worker（§7.2） |
| 资源 | StorageAdapter + 私有持久化目录 | 初期只实现文件系统驱动；S3 兼容驱动留作后续扩展 |
| 工程组织 | pnpm workspace | 一个 Monorepo，不引入额外的构建编排层 |
| 测试 | 单元测试、真实 PG 集成测试、Playwright E2E | 并发写入、断网、崩溃恢复都在真实环境中验证 |
| 部署 | 容器、反向代理、持久化卷、受控迁移 | 单实例首发；备份与恢复必须可用 |

Node.js v24 是当前的 LTS 版本；NestJS 支持 TypeScript 模块化服务；Drizzle 使用 Apache-2.0 许可证。[S5][S6][S7]

**版本基线**（M1 总设计 §2.2）：工具组合与代码风格与 opennerve 一致，版本号不强求一致。取各依赖当前的稳定大版本，补丁取发布满 3 天的最新版，全部精确锁定；新的大版本发布不满两个月、而上一个大版本仍在正常维护的，先用上一个大版本。

### 9.3 有意不增加的设施

首发不引入 Redis、消息队列、WebSocket、微服务、Kubernetes、Service Worker 或独立的文档服务。会话、租约、幂等记录都存在 PG 里。定时任务（回收、清理）在应用内执行，并用 PG 的 advisory lock 防止将来多实例时重复执行。

"单实例"只是部署规模上的选择，并不意味着把关键状态放在内存里。将来增加 API 副本之前，需要先迁移到共享的资源存储，并重新验证定时任务、限流与故障行为。


其他共享包，等出现第二个使用方时再拆。编辑器适配层只封装实际需要的入口：创建与销毁、载入与捕获快照、订阅变更、切换只读、能力清单。按 M0 的结论，这些入口背后还要承担：捕获时机（§7.3）、阅读模式（§6.5）、打开自检与资源加载错误捕获（§8.2）、图片服务与剪贴板钩子、命令守卫与 `IMAGE()` 的限制（§8.5、§11.3）、文字文档的平台策略（`/` 键、输入法事件归一、链接规范写法、加载时规范，§4.3），以及内部 API 的集中封装与登记（§10.1）。不为"将来可能替换编辑器"提前建设通用框架。

## 10. SDK 集成要点

### 10.1 定制方式（按优先级）

1. **插件配置与菜单配置**：例如用 UI 插件的 `menu` 配置隐藏不支持的菜单项。菜单配置是全局的：各 UI 插件的 `menu` 合并成一份，按菜单项 id 生效。隐藏菜单不会停用命令，隐藏父菜单后子项仍能被功能搜索找到，所以子项要一并隐藏，不支持的命令另用命令守卫取消。
2. **依赖注入覆盖**：例如用 `UniverDrawingPlugin` 的 `override` 替换图片读写服务；覆盖 `IResourceManagerService` 捕获资源加载错误（§8.2）；按 M1 的决定替换 `IAuthzIoService`（§6.5）；可选地把 `ILocalStorageService` 换成内存实现（§7.6）。
3. **自有插件**：例如变更检测、只读加固、粘贴清洗、命令守卫、剪贴板钩子、`IMAGE()` 的包装、平台自己的菜单项。
4. **Facade API**：快照读写、权限切换、公式事件、命令执行前后的事件（`BeforeCommandExecute`、`CommandExecuted`）等。

根据官方的 API 稳定性策略，优先使用公开的稳定 API。必须使用内部 API（例如 `IUndoRedoService`）时，在适配层集中封装并登记，升级时重点回归。[S3] M0 各报告的"内部 API 登记"是初始清单（M0-P3 报告 §7、M0-P4 报告 §4、M0-P5 报告 §7、M0-P6 报告 §6；P6 的协同钩子只在纳入 mutation 增量日志时需要）。其中两条约定要特别注意：文字文档剪贴板钩子的 `onBeforePasteImage` 只有第一个注册者生效，适配层启动时要断言自己是第一个；图片格式清单是模块级状态，对页面里的所有实例都生效。

### 10.2 编辑器页面的生命周期

- 编辑器页面整页加载，一页只承载一份文档；离开时整页卸载。这样可以避开 Univer 实例在单页应用中反复创建、销毁造成的内存泄漏[S4]，以及用相同 `unitId` 重复创建时抛出的异常。
- 在阅读模式和编辑模式之间切换、需要重新加载快照时，先 `disposeUnit`，再重新创建；不需要重新加载时原地切换（§6.5）。
- 表格的公式 Worker 创建失败时，销毁实例、以主线程模式重建：Worker 模式下，主线程的公式插件在注册时就设了 `notExecuteFormula`，不能原地切换。判定条件与重建流程由 M4 设计；Worker 内的让出间隔（20–100）对 stop 生效时间与计算开销的影响，也由 M4 评估（M0-P3 报告 §6.3）。
- 编辑器按文档类型分别打包，按需懒加载。`doc@1` 不含公式引擎，首屏 JS 明显变小（§8.2）。

### 10.3 补丁策略

只有公开配置、插件、依赖注入和 Facade 都解决不了的具体缺陷，才进入源码补丁评审。
- 补丁用 `pnpm patch` 管理，登记上游版本、修改原因、测试、影响范围，以及升级时如何重放。
- 不直接修改 `node_modules`，也不把上游代码复制进业务代码。
- 能提交给上游的修复，优先提交上游。

**M0 评估出的补丁候选**（M0 只评估必要性与规模，不实施）：
- DEF-002（浮动图片被拉伸）：上游修复要扩展公共的 `refreshTransform`，或者在表格侧另行写回锚点，规模由 M5 按源码确认；也可以用平台插件回写锚点；"保存时修正"不可行（M0-P2 报告 §2.3）。
- 图片读取失败时渲染对破损的图片调用 `drawImage`，抛出未捕获的异常：补丁或客户端兜底，由 M5 评估（M0-P4 报告 §2.3）。

M0 各报告列出的上游报告清单（P3 4 条、P4 3 条、P5 11 条）从 M1 起提交并跟踪。平台的规避做法有对照用例锁定 SDK 的现有行为（例如 DEF-002 的复现用例、文字文档 V13 的对照用例），升级 SDK 时先跑。

## 11. 安全要求

### 11.1 认证与会话

- 使用服务端 Session。Cookie 设置 HttpOnly、Secure、SameSite；对状态变更接口做 CSRF 防护与 Origin 检查；配置空闲过期和绝对过期；重置密码、停用账户时，让相关会话失效。[S12]
- 密码使用有人维护的 Argon2id 实现，参数按部署机器的基准测试结果设置。[S13]
- 邀请与重置令牌单次有效、有时限、只存摘要，并做尝试限流与审计。不依赖外部邮件服务，由管理员通过受控渠道分发链接。
- 前端不把真实用户身份交给 SDK 的本地授权服务（§6.5）；前端的权限只是体验层，写入边界在服务端。

### 11.2 输入校验

- API 做运行时的结构校验，并限制正文长度、JSON 嵌套深度、键的数量、文档容量和请求频率。TypeScript 类型不能代替网络输入校验。
- 快照校验包括（校验与计算哈希都以 JSON 文本为准，例如内存中的 `Infinity` 写成 JSON 后是 `null`；服务端的保存校验统一写在这里，§8.1、§8.2、§8.5 只做引用）：
  - 解压后的体积上限、嵌套深度；
  - 顶层类型和 `unitId` 与文档记录一致；
  - 资源：结构（名称唯一、`data` 为字符串），名称在白名单内，且没有缩水；必须为空的资源为空；已知资源做结构校验；文字文档的超链接资源与正文一致（§8.2）；
  - 图片地址：任何深度上名为 `source` 的字段都必须是平台地址，否则拒绝；引用关系按授权建立（§8.5、§11.3）；
  - 链接地址：合法，并且等于它的规范写法（§11.3）；
  - 文字文档的结构：只接受 MODERN 版式；不接受页眉页脚；表格之外只允许文末一个分节符（表格的每个单元格里各有一个分节符，是正常结构，所以不能笼统地"拒绝分节"）；不接受目录块的区间（§4.3、§4.4）；
  - 本期不支持的结构（页眉页脚、脚注尾注等）要求为空。
- **统一的地址提取器**覆盖全部可能含图片或链接的位置（M0-P2 报告 §2.3）：表格的 `SHEET_DRAWING_PLUGIN`、单元格富文本的 `p.drawings` 与 `customRanges`、`sheets[*].backgroundImage.source`；文字文档的顶层 `drawings`、`DOC_DRAWING_PLUGIN`、正文 `customRanges`、`DOC_HYPER_LINK_PLUGIN`，以及 `headers`、`footers`、`notes`、`footnotes`、`endnotes`。相对地址按平台的源解析，与 SDK 的 `isSafeUrl` 一致，否则会误拒合法的保存。
- 上传请求的体积同样受限，并防止压缩炸弹。

### 11.3 外部资源与内容安全策略

源码核查与 M0 实测确认了几件好事（M0-P1 报告 §2）：开源 SDK 默认没有遥测（`@univerjs/telemetry` 只定义接口，平台不注册任何 `ITelemetryService` 实现），不从 CDN 加载资源，关闭 CSP 运行时也只有同源请求；编辑器产物（含两个 Worker 及排版 Worker 按需加载的块）中没有 `eval`、`new Function`、字符串形式的定时器与 WebAssembly，只有 3 处 lodash 的全局对象探测 `Function('return this')()`，运行时会被短路；WEBSERVICE 函数没有实现；超链接点击前会经过 `isSafeUrl`，只放行 http、https 和 mailto。

但链接的保存没有把关（M0-P5 报告 §2.3）：链接框用 `isLegalUrl` 校验，`javascript://x@example.com/%0Aalert(1)` 这类地址能通过并原样保存；添加、修改链接的命令本身不做任何检查；复制时 `href` 不转义，带引号的地址会在剪贴板 HTML 里注入元素。

另外，以下路径会让浏览器请求外部地址（M0-P4 报告 §2.3、§3.3）：

- 文字文档粘贴 HTML 时，会保留外部 `<img src>` 地址；
- 文字文档粘贴"内部片段"（`<!--univer-doc-fragment:…-->` 注释或 `application/x-doc-fragment+json`，任何网页都能在复制时放进剪贴板）时，不经过 HTML 转换，片段里的文字填充图片、数组形式的地址、没有类型字段的图片照样会加载；
- `IMAGE()` 公式会把任意 URL 当作图片加载；
- Facade 的 `FWorksheet.insertImage`、`FRange.insertCellImageAsync` 在执行命令之前就用 `new Image()` 加载地址量尺寸，命令守卫来不及介入，所以平台代码不以外链调用它们。

这些路径都可能被用来追踪谁打开了文档，或者探测内网地址。对策如下：

- **严格的 CSP**（M0 定稿，M0-P4 报告 §3.4；P5 在文字文档的场景下复核，结论不变）：
  `default-src 'self'; img-src 'self' data: blob:; connect-src 'self'; font-src 'self'; style-src 'self' 'unsafe-inline'; script-src 'self'; worker-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`
  - 相对 r2 的起点策略，去掉了 `font-src data:` 与 `worker-src blob:`：P1–P5 的全部场景都没有用到。
  - 保留的放宽项都有用处：`img-src data:` 用于表格界面的图标与 SDK 自带的破损图片 SVG；`img-src blob:` 用于文字文档粘贴图片文件时 SDK 用 `URL.createObjectURL` 量尺寸，这个 `Image` 没有 `onerror`，去掉会让粘贴一直挂起；`style-src 'unsafe-inline'` 用于主题变量、格式刷光标、通知组件的内联样式，三者都不支持 nonce。样式哈希能否代替 `'unsafe-inline'` 没有评估，保留 `'unsafe-inline'`，由 M7 的独立安全审查复核。
  - 策略必须随所有响应下发，至少包括 HTML 与 Worker 脚本：Worker 内生效的是它自己脚本响应上的策略，只给 HTML 加头时 Worker 完全不受约束（三个浏览器与真实 Safari 一致）。构建约束：Worker 以同源脚本加载，不内联成 blob 或 data Worker；构建不注入内联脚本。从 M1 起按定稿下发。
  - 违规报告发到平台自己的接口，但只作抽样信号：Chromium 会把相同的报告去重，WebKit 与 Safari 不上报 Worker 内的违规，`report-to` 没有验证。不能把它当作"没有违规"的证据。
- **粘贴清洗**（默认拒绝，编辑器适配层的剪贴板钩子）：
  - `onBeforePasteImage`：粘贴的图片文件、HTML 里的 `data:` 图片改为上传（默认实现会把它们读成 data URL，不经过图片服务）；
  - `onBeforePaste`：处理整个粘贴内容，包括内部片段。本站的绝对地址规范回相对地址；`drawings` 里的非平台地址替换成平台内置的占位图（不删除图片对象，避免破坏正文里的占位字符）；文字填充图片整项去掉；其他位置持有 `source` 的项去掉；链接地址按下面的规则规范化，不合法的去掉（纯文本粘贴时，SDK 把整段文字当成链接地址，链接文字本身合法时改用链接文字）；去掉表格之外的分节符；粘贴目标在表格单元格里时去掉图片。
- **命令守卫**（Facade 的 `BeforeCommandExecute`）：取消参数里带非平台 `source` 的命令。它只看 COMMAND，看不到命令内部执行的 mutation，所以兜住的是平台代码的误用，不是所有路径；全量遍历参数时，20 万单元格的写值约 74 ms，生产上只检查与图片有关的命令。
- **限制 `IMAGE()`**：采用 `restricted`，参数是平台资源地址才交给原执行器，否则返回 `#VALUE!`，不发请求；外链、data URL、单元格引用、区域、数组常量、拼接出来的地址、带查询参数的地址都被拒绝。在主线程与公式 Worker 里各安装一次，都在生命周期到达 Ready 之后；Worker 要回报安装结果。不选整体禁用，因为它会让已有的 `IMAGE()` 全部变成 `#NAME?`。
- **服务端校验快照中的图片地址**：只接受本平台的资源地址（§8.5、§11.2）。M0 的路径矩阵中，所有插入、粘贴路径都得到平台地址，或者被按预期处理掉，所以 `data:` 图片也不再接受。`img-src` 必须保留 `data:`，CSP 拦不住 data 图片，服务端校验是最终防线。
- **链接与脚本**：命令守卫、粘贴清洗与服务端保存校验共用同一个链接地址判定，判定之后一律保存规范写法（M0-P5 报告 §1.2 第 4 条）：
  - 含控制字符（制表符、换行等）的地址一律拒绝，因为浏览器解析时会去掉它们，`/\t/evil.example` 会变成协议相对地址；
  - `http`、`https`、`mailto` 保存 URL 解析后的 `href`，引号、尖括号、空格都被百分号编码，复制时不会注入 HTML；
  - 本站相对地址按站点源解析，结果必须仍在本站；文档内锚点 `#…` 不能含空白、引号与尖括号；
  - 命令守卫对任何来源的添加、修改链接命令生效（链接框、Facade、协同回放）：不合法就取消，写法不规范就改成规范写法再执行；服务端要求保存的地址等于它的规范写法。

  M0 只在文字文档上验证了这套规则；表格的超链接由 M5 按同一规则实现并验证。不启用任意用户脚本、宏、远程数据读取，也不加载不受控的插件。Uniscript 已从 1.0 线移除，不引入。

### 11.4 图片上传

- 检查扩展名、真实的媒体类型（文件头）、大小和像素数；类型与大小由客户端、服务端各查一次，伪装成 PNG 的 HTML 由服务端按文件头拒绝（415）；
- 只查文件头不够：截断的文件、0×0 的图片都能上传，4,000 万像素的图片解码约占 160 MB 内存。所以 M5 上传时完整解码并重新编码（顺带去掉 EXIF 里的 GPS 等信息），设最小尺寸，按内存预算定像素上限，限制 GIF 帧数（M0-P4 报告 §2.3）；
- 由服务器生成文件名，不采信客户端提供的路径；
- 只接受 PNG/JPEG/WebP/GIF，不接受 SVG、HTML 等主动内容；
- 文件存放在不可执行、不公开的目录里，经过鉴权接口读取，响应带上 `Content-Type`、`X-Content-Type-Options: nosniff` 与 `Cross-Origin-Resource-Policy: same-origin`。[S14]

### 11.5 日志与隐私

- 日志中禁止写入密码、会话令牌、租约令牌、本机密钥、完整快照，以及未脱敏的敏感信息。
- 静态资源、字体与 SDK 依赖全部自己托管，不从第三方 CDN 加载。
- 审计事件不记录文档正文。

## 12. 生产验收目标

下列数字是项目目标与边界，**不是 Univer 官方的性能承诺**。M0 的实测只作相对基线（验证工程、无头浏览器），不等于生产环境的测试结果；M7 压测与试运行中必须记录真实的环境、样本和测量结果。

### 12.1 起始规模与容量

| 项目 | 起始目标 / 边界 |
|---|---|
| 组织规模 | 约 100 名成员，若干个团队空间 |
| 在线负载 | 50 个在线会话，其中 20 个会话在不同文档上持续编辑 |
| 单文档并发 | 读者数量受整体容量限制；可提交修改的编辑会话最多一个 |
| 单快照上限 | 解压后的 JSON 默认不超过 5 MiB；异常嵌套与超量对象另外限制 |
| 表格样本 | 约 5 万个实际使用的单元格，其中至少 1,000 个公式 |
| 文字样本 | 约 2 万汉字，包含标题、列表、基础表格与图片 |
| 图片 | 单张不超过 5 MiB，另设像素上限与组织级配额 |
| 浏览器 | 桌面 Chrome / Edge 的当前版本和前一个主要版本；Safari 的当前主要版本单独验收 |

全量快照的路线面向中小型文档，不承诺百万行、无限大的文件或无限复杂的公式依赖。

### 12.2 性能目标

基准环境从 4 vCPU / 8 GiB 内存、SSD 的应用与数据库测试部署开始，同时记录浏览器所在机器、网络和数据库的配置。

| 指标 | 目标 |
|---|---|
| 1 MiB 快照的保存请求，服务端处理耗时 | p95 ≤ 1 秒 |
| 在 100 ms 往返延迟、20 Mbps 带宽下，从捕获到"已保存到云端" | p95 ≤ 3 秒 |
| 从修改停止到"已保存在本机"（含公式等待） | p95 ≤ 2 秒（样本条件：公式计算不超过约 0.9 秒） |
| 1 MiB 文档捕获快照时的主线程阻塞 | p95 ≤ 100 ms（M0 实测确认） |

前两项 M0 没有测量（M0 不含服务端与上传）。后两项与性能基线的 M0 实测如下（相对基线：Apple M4 Pro、macOS 26.5（P6 的写入管道数据在 macOS 27.0 上），Playwright 无头的 Chromium 153、Chrome 153、WebKit 26.6；正式压测在 M7）：

- **从修改停止到"已保存在本机"**（M0-P6 报告 §2.2，发件箱原型，各 5 次）：
  - 不牵动公式的修改：p50 1.02–1.18 秒，最大 1.19 秒（表格 1 MiB 与 5 MiB、文字 2 万字与 1 MiB，发件箱放在主线程与 Worker 两种方式，三个浏览器；每次都确认真的写入了发件箱）；
  - 牵动约 320 个公式的修改（`perf-50k`，默认配置：公式 Worker 与发件箱 Worker）：p50 1.05–1.06 秒，最大 1.07 秒；公式主线程模式 p50 1.04–1.05 秒；公式在 1 秒的防抖期间就算完了；
  - 最坏值：WebKit 上 5 MiB 表格、发件箱 Worker 放置时，约八分之一的捕获要约 2.2 秒（§7.2"放置"），超过本目标；Worker 保持空定时器后最大 1.19 秒。M4 按 §7.2 处理，并在真实 Safari 上复核（DEF-011）。M0-P3 记录的"WebKit 公式 Worker 模式打开后第一次修改 1.77 秒"，M0-P6 在同样条件下没有复现（1.04–1.05 秒）；
  - 样本条件：公式计算超过约 0.9 秒的文档达不到 2 秒。V07 的慢计算（200 个 `SUMPRODUCT`）在 Chromium、Chrome 上光是等到能捕获就要 2.2–2.4 秒（M0-P3 报告 §4.1、§4.4）。
- **捕获时的主线程阻塞**（M0-P3 报告 §4.1）：
  - 1 MiB 表格 p95 ≤ 32 ms，整条捕获管道约 50–55 ms；1 MiB 文字文档的同步段 p95 ≤ 11 ms；
  - 5 MiB 表格（单快照上限）：同步段（`save()` + 序列化）p95 66–82 ms，gzip 期间的最长阻塞 p95 63–92 ms，规范化 73–85 ms（p50–p95），都接近 100 ms。所以压缩、规范化与加密放进 Worker（§7.2、§7.4），主线程只剩同步段（含编码 p95 74–87 ms，M0-P6 报告 §2.1），这是 5 MiB 下主线程成本的下限。
- **表格性能基线**（M0-P3 报告 §6，§12.1 的表格样本 `perf-50k`：50,410 个单元格、1,000 个公式）：
  - 首屏（从导航到 `Rendered`）：第一次打开 0.64–0.74 秒，之后的中位数 0.52–0.56 秒；画布一出现就键入，三个浏览器都被接受；
  - 编辑响应（按键到下一帧）：p50 24–26 ms，p95 33–36 ms；
  - 公式计算：牵动约 320 个公式的修改到结果收齐 0.69–0.86 秒，强制全量重算 0.75–0.96 秒；
  - 计算期间的界面冻结（帧间隔口径）：主线程模式下增量 0.66–0.83 秒、全量 0.71–0.89 秒；公式 Worker 模式下帧间隔 p95 ≤ 34 ms，JS 堆合计多约 8–9 MiB。据此表格默认启用公式 Worker（§8.2）。
- **文字文档性能基线**（M0-P5 报告 §5.2，§12.1 的文字样本 `doc-20k-full`：约 2 万字，8 个表格、10 张图片；主线程排版，三个浏览器）：到 `Rendered` 约 0.49–0.52 秒；键入到画出来 p50 94–110 ms，输入法组合更新到画出来 p50 90–107 ms；快速键入时主线程最长阻塞 81–123 ms。排版 Worker 能降到 p50 64–71 ms、最长阻塞 25–51 ms，但有缺陷，暂不启用（DEF-007）。
- 首屏一律以 `Rendered` 计：`Steady` 是 `Rendered` 之后固定的 3 秒延时，不能当作指标。

首屏可编辑时间、编辑响应、事件循环延迟、内存增长、PG 写入量与 WAL 增长，都要测量；M7 以上面的数据为起点。"编辑响应"与"事件循环延迟"的目标值在 M7 确定，建议以"计算期间帧间隔 p95 ≤ 100 ms"作为界面不冻结的目标。

如果保存频率和快照体积造成了瓶颈，优先限制体积、去重、调整保存频率；不要临时引入未经设计的"增量协同"来掩盖问题。

### 12.3 写入量与存储预算

- **估算公式**：WAL 写入量 ≈ 同时编辑的人数 × 压缩后的快照体积 ÷ 上传间隔。
- **示例**：20 人持续编辑 1 MiB 的表格、每 15 秒上传一次；按 M0 实测的压缩率（表格约 25%），WAL 约 20 × 0.25 MiB ÷ 15 秒 ≈ 1.2 GiB/小时（r2 按假设的 10%–20% 估为 0.5–1 GiB/小时）。会话内去重只能跳过内容完全没变的上传，持续编辑时不减少写入量。
- **压缩率**（M0-P3 报告 §4.1、§4.3）：gzip 后，表格约为原来的 25%（25.2%–26.5%），文字文档约 45%（43%–47%），都高于原先假设的 10%–20%。表格样本的数值是随机生成的两位小数，比真实数据难压缩，这个数字偏保守，M7 用真实样本复核。gzip 的结果因浏览器而异（WebKit 压缩后比 Chromium 内核大：表格约 5%，1 MiB 文字文档约 2%），所以不能对 gzip 结果跨浏览器比较哈希（§7.4）。
- **需要单独预算的存储**：时间点恢复所需的 WAL 归档保留期、小时级检查点（保留 7 天）、`document_revisions` 元数据。

### 12.4 运维与恢复

**上线前必须具备**：
- HTTPS、环境变量校验、进程优雅退出、数据库连接池、超时控制、请求标识、就绪与存活探针；
- 监控：错误率、按原因分类的保存失败、租约冲突、客户端上报的同步延迟、CSP 违规报告（只作抽样信号，§11.3）、快照体积分布、客户端打开自检失败（资源加载失败）的上报与告警（§8.2）。

**迁移与升级**：数据库采用受控迁移，发布前先备份；不在每个应用实例启动时并发执行不可逆的迁移。编辑器升级前，先跑历史样本回归。

**恢复**：
- 数据库用基础备份加 WAL 归档，支持时间点恢复。[S10]
- 建议的灾备目标：**RPO 不超过 1 小时，RTO 不超过 4 小时**。两者都要经过演练验证，不视为已达成的 SLA。
- 图片与数据库必须能恢复到相互对应的水位：图片只追加、延迟删除，并持续同步到备份目的地（§8.5）。
- 备份放在独立于主机的故障域，限制访问并加密。备份任务的成功日志，不能代替真正的恢复演练。

初期单实例不提供自动高可用。MVP 的生产标准是：边界明确、数据有保护、故障可以被发现也可以恢复；而不是宣称具备并不存在的跨机房容灾。

## 13. 实施里程碑

排期按交付物与验收门槛推进。具体的日历工期，要在 M0 摸清真实的兼容性和工作量之后，结合实际投入的人员再确定。

### 13.1 编排原则

- **颗粒度**：每个 M 是一块内聚的能力增量，通常包含 2–5 个 Phase。
- **独立性**：每个 M 只依赖前面 M 的产出；完成后不需要回头修改前面 M 的代码；数据模型只做加法。
- **可验证性**：每个 M 都有自己的用户故事（US 编号）和 E2E，并明确负责哪几条上线门槛（§13.3）。
- **风险前置**：保存正确性、离线恢复这类风险最高的部分尽早做，并且各自独立验收。
- **质量不随范围打折**：范围可以通过延期收缩，质量门槛不能降低（§13.5）。

为了让各个 M 相互独立，约定：
- M1 就建 `spaces` 表（这时只有个人空间），M2 再加团队空间；M1 的文档表就带 `revision`，M3 再加租约和代次。
- M2 里的撤权、移动、停用等操作，一开始就递增 `writeEpoch`。这样 M3 只需接入租约校验，不必回头修改 M2 的事务。
- 审计、错误码、配置、日志、迁移这些基础设施在 M1 建好，后面各 M 只需接入。

### 13.5 文档与交付流程

- **JIT 滚动推进**：
  - 以本文档为版本总纲；
  - 每个 M 开始时，编写 `M{n}-<短名>/00-M{n}-总设计.md`，内容包括 Phase 规划、用户故事和负责的门槛；
  - 每个 Phase 开始时，基于上一个 Phase 完成后的最新代码，编写 `NN-P{k}-<短名>.md`（架构设计与实施规划，拆到 Step 为止）；
  - Step 按需要先写 spec，再写 plan。
- **审批与自主推进**：每个 M 的总设计须经用户讨论并审批；审批通过后，自主逐个推进 Phase，Phase 设计文档编写并自审后直接实施。遇到架构回归、跨模块的协同调整或意料之外的高风险发现时，停下来汇总问题和建议方案，由用户决策。
- **Phase 完成审查**：每个 Phase 完成后，必须经过代码审查（优先由独立的审查者进行）、修复与复验，审查报告存入 `reviews/`。
- **分支纪律**：每个 Phase 一个分支；审查通过后以 `git merge --no-ff` 合并到 `main`，保留分支提交线。
- **每个 Phase 收尾**：更新架构总览与 ADR；编写交接单，存入 `handoffs/`；延期项登记到《延期事项登记》（`docs/v0.1/02-延期事项登记.md`）。
- **延期的边界**：只能延期功能，不能延期质量门槛。触及本文档范围或上线门槛的延期，必须走范围变更，并更新本文档的修订记录。
- **具体约定**：见仓库根目录的 `CLAUDE.md`，以及《工程规范与完成定义》（`docs/v0.1/01-工程规范与完成定义.md`，在 M1 开始前定稿）。

## 14. 上线硬门槛

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A01 | 开源依赖 | 生产依赖图与构建产物中没有 Pro；功能不依赖许可证服务；第三方清单完整 |
| A02 | 原生内容完整性 | 表格与文字文档的目标功能在保存、关闭、重开后，内容与资源一致；二次保存结果稳定 |
| A03 | 越权访问 | 修改 URL、文档 ID、空间 ID、资源 ID，都不能读取或写入无权的数据；单独分享、空间角色、全员可见、系统管理员无内容权限等规则都按 §5.3 生效 |
| A04 | 编辑唯一性 | 两个用户同时申请同一份文档的编辑权，最多一个成功；同一用户开两个标签页时同样适用 |
| A05 | 过期旧会话 | A 失去租约、B 接手并保存后，A 恢复网络提交旧内容一定被拒绝，A 的内容可以另存为副本 |
| A06 | 撤权一致性 | 编辑过程中被撤权、被移出空间或账户被停用，之后的保存、续租、资源访问都被拒绝，本机的未同步修改被删除 |
| A07 | 确认丢失 | 服务端已经提交、客户端却没收到确认时，重试不会重复写入、不会重复递增修订号，也不会误判为冲突 |
| A08 | 保存中继续输入 | 保存的回包不会把之后发生的修改误标为已保存，也不会丢掉最新的待保存状态 |
| A09 | 进程与浏览器异常 | API 重启不会丢失已确认的数据；休眠、后台标签页、网络切换时，有清晰的只读或恢复行为 |
| A10 | 复制与资源 | 新文档拥有独立的身份与授权；图片引用和图片回收不会相互串扰、损坏 |
| A11 | 输入与容量 | 超限的快照、危险链接、伪造图片、外链图片、伪造的资源地址和异常结构都被拒绝，并且不能拖垮整个服务 |
| A12 | 恢复演练 | 在独立环境中，从备份恢复真实的样本文档和图片，核对恢复耗时与一致性 |
| A13 | 升级回归 | 旧数据样本在目标版本中可以读取；不会静默丢弃资源；旧客户端不能保存；不可逆的升级有明确的恢复路径 |
| A14 | 体验真实 | 没有实时共编、没有 Office 转换、容量与丢失边界，这些都在产品中可见；不显示虚假的"已保存到云端" |
| A15 | 断网编辑 | 断网状态下持续编辑 10 分钟后恢复网络：没人接手时全部同步；有人接手时不覆盖对方，本地内容可以另存为副本 |
| A16 | 崩溃恢复 | 编辑过程中强制结束浏览器进程，在联网状态下重新打开后，可以恢复到最后一次写入本机时的状态（恢复要向服务端取密钥，§7.5） |
| A17 | 插件资源完整 | 插件没加载全、或者资源加载失败（被静默清空）的客户端无法进入编辑；资源缩水的快照被服务端拒绝 |
| A18 | 公式一致性 | 保存下来的公式结果，与重新计算的结果一致 |
| A19 | 外部请求 | 打开和编辑任意样本（包括含外链图片、`IMAGE()` 的样本）期间，浏览器不向第三方地址发起任何请求 |
| A20 | 交接规则 | 空闲释放、请求编辑时自动交出、本人接管、强制接管、异常中断提示，都按 §6.3 工作 |

## 17. 范围冻结与后续评审

本稿冻结的首发方向是：

**自部署、单租户的团队文档平台；Node.js / TypeScript + PostgreSQL；Univer 开源 1.0 线；个人空间 + 团队空间；在线表格与基础文字文档；单文档单写者与编辑权交接；本地优先保存；不使用 Pro，不建设 Agent。**

本稿中的实现方式、容量参数与里程碑，除注明经 M0 验证的部分外，都属于建议方案。M0 已完成，本稿按其结论修订；但 M0 是原理验证，验证代码不进入生产，不要把这份计划文档当作已经验证过的生产架构、已经通过的安全审计，或已经实现的产品。

以下是接口职责的草案，不是已实现的接口；详细的字段和错误结构在实施设计中锁定。

错误需要区分：无权限、租约失效、文档被占用、修订号冲突、负载超限、格式不兼容、客户端过旧。对于没有读取权限的对象，不暴露其是否存在；HTTP 状态与业务错误码保持统一。
